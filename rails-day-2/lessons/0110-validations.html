Validation — คนดูแลสต็อกตรวจแฟ้มก่อนเก็บ

~20 นาที · ควรผ่าน บทเรียน 107 (console CRUD) มาก่อน · ใช้ของจาก บท 102 และ บท 93 ด้วย

ตอนนี้แอปบล็อกของเรารับบทความที่ไม่มีชื่อเรื่องลงฐานข้อมูลได้หน้าตาเฉย ไม่มีใครห้าม
บทนี้คุณจะเขียนกฎให้ model ตรวจข้อมูลก่อนบันทึก เช่น "ชื่อเรื่องห้ามว่าง" แล้วลองในครัวทดลอง (console) ว่าข้อมูลผิดโดนตีกลับยังไง
อ่านจบแล้วคุณจะ: ใช้กฎสำเร็จรูป 5 แบบเป็น · เขียนกฎของร้านเราเองได้ · ไม่ตกกับดักตัว s ตัวเดียว · และเลือกได้ว่าเมื่อไหร่ใช้ save เมื่อไหร่ใช้ save!

🔁 ทวนก่อนเริ่ม — คำพวกนี้จะโผล่ในบทนี้ทั้งหมด

  • model Post (บท 106) — class ใน app/models/post.rb เปรียบเป็นคนดูแลสต็อกที่รู้ว่าแฟ้มบทความเก็บลิ้นชักไหน
  • new · save · create · persisted? (บท 107) — สร้างแฟ้มในมือ · เอาเข้าตู้ · ทำสองอย่างรวดเดียว · ถามว่า "อยู่ในตู้แล้วหรือยัง"
  • post.errors.full_messages · User must exist (บท 107) — ตอน save บทความที่ไม่มีผู้เขียนแล้วได้ false เราถามด้วยคำสั่งนี้ว่า "ไม่รับเพราะอะไร" · บทนี้คือเรื่องเต็มของมัน
  • console (บท 104) — ครัวทดลองหลังร้าน เปิดด้วย bin/rails console · แก้ไฟล์ใน app/ แล้วต้องพิมพ์ reload! ก่อนลองใหม่
  • ! ท้ายชื่อ method (บท 93) — ป้าย "ระวัง ตัวนี้อันตรายกว่าตัวที่ไม่มี !"
  • render · redirect_to · 422 (บท 102 · บท 100) — ยกจานให้เลย · ชี้ไปเคาน์เตอร์อื่น · status "ข้อมูลที่ส่งมาใช้ไม่ได้"

validation คือกฎที่ model ตรวจข้อมูลก่อนบันทึก · ถ้าผิดกฎข้อไหน Rails ไม่ยอมเขียนลงฐานข้อมูล แล้วจดไว้ว่าผิดอะไร เพื่อเอาไปบอกผู้ใช้ได้ · กฎเขียนไว้ใน model ที่เดียว จึงตรวจทุกทางที่ข้อมูลผ่าน model — หน้าเว็บ · console · seeds

🗂 เทียบให้เห็นภาพ — คนดูแลสต็อกตรวจแฟ้มก่อนเก็บ

model Post คือคนดูแลสต็อกที่ฝังอยู่ในแฟ้มทุกแผ่น พาแฟ้มเดินเข้าตู้เอง (บท 106) · ตอนนี้เขารับทุกแผ่นที่ยื่นมา แม้จะเป็นกระดาษเปล่า
validation คือรายการตรวจที่เราแปะไว้บนโต๊ะเขา: "ช่องชื่อเรื่องห้ามว่าง" · ถ้าแฟ้มไม่ผ่าน เขาส่งคืนพร้อมโน้ตสีเหลืองบอกว่าผิดข้อไหน ไม่เดินไปตู้เลย

ที่ไม่เหมือนกัน: คนดูแลสต็อกจริงเห็นแฟ้มแปลก ๆ แล้วสงสัยเองได้ · Rails ตรวจเฉพาะข้อที่เขียนไว้ในรายการ ไม่มีสามัญสำนึก ไม่เขียนกฎ = ไม่ตรวจ · และคนดูแลสต็อกคนนี้ยืนอยู่หน้าประตูบานเดียว — ใครเดินอ้อมไปทางหลังร้าน (มีทางเลี่ยงจริง เดี๋ยวดูในบท 111) เขาไม่เห็น

เทียบกับ Go: ใน Gin (บท 39) เราติด tag binding:"required" บน struct ที่รับข้อมูลจาก request · การตรวจเกิดที่ handler ตอน c.ShouldBindJSON(&in) · โค้ดทางอื่นที่สร้างข้อมูล (สคริปต์ · งานเบื้องหลัง) ต้องตรวจเองอีกรอบ
Rails ย้ายกฎไปไว้ที่ model · ใครก็ตามที่บันทึกผ่าน Post โดนตรวจด้วยกฎชุดเดียวกัน

Go (Gin) — กฎอยู่บน struct ของ request

type PostInput struct {
    Title string `json:"title" binding:"required"`
}

// ตรวจตอน handler อ่าน body
var in PostInput
if err := c.ShouldBindJSON(&in); err != nil {
    c.JSON(400, gin.H{"error": err.Error()})
    return
}

🗣 ศัพท์ที่เพิ่งเรียนไป
validation
กฎตรวจข้อมูลที่ model ทำก่อนบันทึก · ไม่ผ่าน = ไม่เขียนลงฐานข้อมูล + มีรายการปัญหาให้โชว์ · ถาม senior ได้ว่า "กฎข้อนี้ควรเป็น validation ใน model หรือเช็คใน controller" (คำตอบส่วนใหญ่คือ model)
INSERT · BEGIN · COMMIT
INSERT = คำสั่ง SQL "เพิ่มแถวใหม่" · BEGIN/COMMIT = เริ่มงาน/ยืนยันงาน (transaction — กลุ่มคำสั่งที่ "ทำทั้งหมดหรือไม่ทำเลย" · บท 111 ใช้จริง) · เวลาส่ง log ให้ AI ดู พิมพ์ได้ว่า "this INSERT ran even though title is empty — which validation should stop it?"

2 · กฎแรก — validates :title, presence: true

เปิดไฟล์ model แล้วเพิ่มบรรทัดเดียว:

# app/models/post.rb
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments

  validates :title, presence: true
end
  • validates = "ขอตั้งกฎสำเร็จรูปให้ช่องนี้" · เป็น method ที่ ApplicationRecord ให้มา (เรียกในตัว class ได้เลย แบบเดียวกับ belongs_to)
  • :title = ชื่อช่องที่จะตรวจ (symbol — บท 92)
  • presence: true = ชื่อกฎ "ต้องมีของ" · ว่าง (nil) · ข้อความว่าง ("") · ช่องว่างล้วน ไม่ผ่านทั้งหมด · เป็น hash ท้าย argument ที่ไม่ต้องใส่ปีกกา (บท 97)

สังเกต: เราเขียนกฎแค่ข้อเดียว แต่ได้ error สองข้อ · "User must exist" มาจากไหน?
มาจาก belongs_to :user ซึ่งแอบเพิ่มกฎ "ต้องมีผู้เขียน" ให้เอง (ตัวเดียวกับที่เจอในบท 107) · บทความทุกชิ้นต้องเป็นของ user สักคน (เรื่อง belongs_to ละเอียดในบท 115) · ถ้าเปิดสไลด์หน้า 23 จะเห็นแค่ ["Title can't be blank"] เพราะตัวอย่างในสไลด์ไม่มี belongs_to

3 · คลังกฎสำเร็จรูป — 5 แบบที่ใช้บ่อย

Rails มีกฎสำเร็จรูปให้เลือกหลายแบบ ไม่ต้องจำครบ แค่รู้ว่ามี — เวลาอ่านโค้ดที่ AI เขียนมาจะได้รู้ว่าแต่ละบรรทัดตรวจอะไร
ผมเขียนกฎลง Post 4 ข้อ กับ User 1 ข้อ (ใช้ช่องที่มีจริงในตารางของเรา): 

# app/models/post.rb
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments

  validates :title, presence: true
  validates :title, length: { in: 5..120 }
  validates :views, numericality: { greater_than_or_equal_to: 0 }
  validates :published, inclusion: { in: [true, false] }
end

# app/models/user.rb
class User < ApplicationRecord
  has_many :posts
  has_many :comments

  validates :email, format: { with: /\A[^@\s]+@[^@\s]+\z/ }
end

สังเกตว่ากฎเหล่านี้มีปีกกาซ้อนอีกชั้น เช่น length: { in: 5..120 } — ชื่อกฎอยู่หน้า : ส่วนในปีกกาคือรายละเอียดของกฎ ("ยาวเท่าไหร่ถึงผ่าน") · ต่างจาก presence: true ที่ไม่มีรายละเอียดอะไรให้บอก แค่ "เปิดใช้"

4 · กฎของร้านเราเอง — validate + errors.add

บางกฎไม่มีของสำเร็จรูป เช่นกฎของร้านเรา: "บทความที่จะเผยแพร่ ต้องมีเนื้อหา (draft ไม่มีเนื้อหาได้)" · กฎแบบนี้เขียนเป็น method ธรรมดาแล้วบอก Rails ว่า "ตอนตรวจ ให้เรียก method นี้ด้วย"
ผมเปลี่ยน app/models/post.rb เป็นแบบนี้ (เอากฎทดลองในหัวข้อ 3 ออก เหลือที่ใช้จริง): 

# app/models/post.rb
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments

  validates :title, presence: true, length: { maximum: 120 }
  validates :views, numericality: { greater_than_or_equal_to: 0 }
  validate :body_needed_to_publish

  private

  def body_needed_to_publish
    return unless published
    if body.blank?
      errors.add(:body, "ต้องมีเนื้อหาก่อนเผยแพร่")
    end
  end
end

private method ข้างล่างใช้ได้แค่ภายใน class · คนนอกเรียก post.body_needed_to_publish ไม่ได้ (บท 102)

7 · ใน controller — if @post.save … else render :new

ฟอร์ม "เขียนบทความใหม่" คืองานแบบ "ผู้ใช้กรอก ผิดได้บ่อย" จึงใช้ save แบบไม่มี ! · นี่คือ action create ที่บท 102 ให้อ่านล่วงหน้า · ตอนนี้รันได้จริงแล้ว (ผมเขียน route · controller · view ทดลองใน sandbox แล้วยิง request ดู): 

# app/controllers/posts_controller.rb (ตัดมาเฉพาะ action create)
def create
  @post = Post.new(post_params)
  @post.user = User.first   # ชั่วคราว: ยังไม่มีระบบ login
  if @post.save
    redirect_to @post, notice: "สร้างบทความแล้ว"
  else
    render :new, status: :unprocessable_content
  end
end
บรรทัดแปลเป็นภาษาคน
@post = Post.new(post_params) สร้างแฟ้มจากของที่ผู้ใช้กรอก · post_params = method ที่หยิบเฉพาะช่องที่อนุญาต (เขียนด้วย params.expect — ละเอียดในบท 117) · วางบนถาด @ ให้ view ใช้ได้
@post.user = User.first ใส่ผู้เขียนให้ ไม่งั้นโดน User must exist · ของจริงจะเป็น "คนที่ login อยู่" (Day 4)
if @post.save ตรวจตามกฎแล้วบันทึก · ได้ true เข้า if · ได้ false เข้า else
redirect_to @post, … สำเร็จ → พาไปหน้าบทความนั้น (/posts/เลข id) · กด refresh แล้วไม่ส่งฟอร์มซ้ำ (บท 102)
render :new, status: :unprocessable_content ไม่ผ่าน → โชว์ฟอร์มเดิม ด้วย @post ตัวเดิมที่มีทั้งของที่ผู้ใช้พิมพ์และโน้ตสีเหลือง (@post.errors) · ตอบ status 422 · render :new ไม่ได้รัน def new (บท 102)

  1. เปิด app/models/user.rb · ถ้ายังไม่ได้พิมพ์ตามหัวข้อ 3 ให้เพิ่มบรรทัด validates :email, format: { with: /\A[^@\s]+@[^@\s]+\z/ } ก่อน · แล้วเพิ่มกฎ presence ให้ :name · และรวม presence เข้ากับ format ของ :email ในบรรทัดเดียว (ท่ารวมกฎท้ายหัวข้อ 3)

ควรเห็น: valid? เป็น false · full_messages มี 2 ข้อ (ชื่อว่าง · อีเมลผิดรูป) · create! ระเบิดด้วย RecordInvalid ที่บอก 2 ปัญหาของ email · บรรทัดสุดท้ายได้ true

ทดสอบความเข้าใจ

1. Post มี belongs_to :user และ validates :title, presence: true · พิมพ์ p = Post.new(title: "ลาบหมูทอด") (ไม่ได้ใส่ผู้เขียน) แล้ว p.save จะได้อะไร?

ตัวเลือกที่ 2 ถูก · ผมลองแล้วได้ => false และ p.errors.full_messages เป็น ["User must exist"] · ไม่มี SQL โผล่เลยสักบรรทัด (ไม่มี INSERT) — คนดูแลสต็อกตีกลับก่อนเดินไปตู้

ตัวเลือกที่ 1 ผิด — belongs_to แอบเพิ่มกฎ "ต้องมีผู้เขียน" ไว้ให้ แม้เราไม่ได้เขียน · ตัวเลือกที่ 3 ผิด — save ไม่มี ! แค่คืน false ไม่ระเบิด · ตัวเลือกที่ 4 ผิด — validation ตีกลับก่อนถึงฐานข้อมูล ฐานข้อมูลจึงไม่ได้เห็นแฟ้มนี้เลย

จุดที่ต้องจำ: บันทึกไม่ผ่านแล้วงง ให้ดู errors.full_messages ก่อน · กฎบางข้อมาจาก belongs_to ไม่ได้มาจากบรรทัดที่เราเขียน

2. เพื่อนเขียน validate :title (ไม่มี s และไม่มี presence: true) ไว้ใน Post · Post.new(user: User.first, title: "").valid? ได้อะไร?

ตัวเลือกที่ 4 ถูก · ผมลองแล้วได้ => true · validate :ชื่อ = "เรียก method ชื่อนี้ตอนตรวจ" · title เป็น method อ่านค่าช่องที่มีอยู่แล้ว มันคืนค่าออกมาเฉย ๆ ไม่ได้เรียก errors.add

ตัวเลือกที่ 1 ผิด — Rails เตือนเฉพาะตอนเขียน validate :title, presence: true (มีชื่อกฎต่อท้าย) · แบบไม่มีชื่อกฎ Rails ไม่มีเบาะแสให้จับ · ตัวเลือกที่ 2 ผิด — Rails ไม่เดาใจ ทำตามที่เขียนเป๊ะ ๆ · ตัวเลือกที่ 3 ผิด — title มีอยู่จริง เพราะ Rails สร้าง method ให้ทุกคอลัมน์ (บท 106)

จุดที่ต้องจำ: เขียนกฎเสร็จ ลองให้มันพังหนึ่งครั้งเสมอ · มี s = กฎสำเร็จรูป · ไม่มี s = เรียก method ของเรา

3. ใน db/seeds.rb ถ้าบรรทัดไหนสร้างผู้ใช้ไม่ผ่านกฎ อยากให้รู้ทันทีตอนรัน · ควรเขียนแบบไหน?

ตัวเลือกที่ 3 ถูก · seeds เป็นข้อมูลที่เราเขียนเอง ผิดแปลว่าบั๊ก · create! โยน Validation failed: … ทันที (seeds ของแอปเราก็ใช้ create! ทุกบรรทัด)

ตัวเลือกที่ 1 ผิด — create ที่ไม่ผ่านคืนแฟ้มที่ id: nil มาเงียบ ๆ สคริปต์วิ่งต่อจนจบโดยไม่มีใครเปิด errors ดู · ตัวเลือกที่ 2 ผิด — new ไม่บันทึกอะไรเลย seeds จึงไม่ได้ข้อมูล · ตัวเลือกที่ 4 ผิด — find_by! คือ "หา" ไม่ใช่ "สร้าง" · ! แปลว่าหาไม่เจอให้ระเบิด

จุดที่ต้องจำ: ผิดเป็นเรื่องปกติ (ฟอร์มผู้ใช้) → ไม่มี ! แล้วเช็คผล · ผิดคือบั๊ก (seeds · สคริปต์) → มี ! ให้ระเบิดดัง ๆ

4. ใน action create ถ้า @post.save ได้ false ทำไมถึง render :new, status: :unprocessable_content แทนที่จะ redirect_to ไปหน้าฟอร์ม?

ตัวเลือกที่ 1 ถูก · @post ที่ save ไม่ผ่านยังถือทั้งค่าที่ผู้ใช้กรอกและ @post.errors · render ส่งต่อให้ view ใน request เดิม ผู้ใช้เห็นว่าผิดตรงไหนโดยไม่ต้องพิมพ์ใหม่

ตัวเลือกที่ 2 ผิด — action ที่รับ POST redirect ได้ปกติ (ตอนสำเร็จเราก็ redirect) แต่ redirect = request ใหม่ @post กับ errors หายหมด (บท 102) · ตัวเลือกที่ 3 ผิด — render :new แค่ใช้ไฟล์ view ชื่อ new ไม่ได้รัน def new · ตัวเลือกที่ 4 ผิด — 422 แค่บอกว่า "ข้อมูลใช้ไม่ได้" ค่าในฟอร์มมาจาก @post ไม่ได้มาจาก browser

จุดที่ต้องจำ: save สำเร็จ → redirect · save ไม่ผ่าน → render ฟอร์มเดิมพร้อม 422 · ใช้ :unprocessable_content ไม่ใช่ชื่อเก่า

ถามกลับได้เลย — ถ้าบันทึกไม่ผ่านแล้วไม่รู้ทำไม ให้ก็อปผลของ p.errors.full_messages และไฟล์ model มาถาม · สองอย่างนี้บอกเกือบทุกอย่างว่ากฎข้อไหนตีกลับ และกฎนั้นมาจากบรรทัดไหน
