บทเรียน 117 · Rails · Day 2

REST ใน Rails — resources, ช่องโหว่ mass assignment และ params.expect

~20–25 นาที (มีส่วนที่ยิง request จริงหลายรอบ) · ควรผ่าน บทเรียน 101 (Routing) · บท 103 (CSRF) และ บท 115 (Association) มาก่อน

บทนี้มีสองครึ่ง · ครึ่งแรกต่อจาก resources :posts ของบท 101: ทำยังไงเมื่อเมนูมาตรฐาน 7 อย่างไม่พอ หรือมากเกินไป และทำยังไงให้ URL บอกได้ว่า "คอมเมนต์นี้เป็นของบทความเลขไหน"
ครึ่งหลังคือเรื่องความปลอดภัย: ฟอร์มของเรามีแค่ 2 ช่อง แต่คนร้ายแอบส่งช่องที่ 3, 4, 5 มาได้ · คุณจะได้ลองเจาะแอปตัวเองจริง ๆ ให้ยอดวิวกลายเป็น 999999 แล้วปิดช่องนั้นด้วยบรรทัดเดียว
อ่านจบแล้วคุณจะเขียน route แบบซ้อนกันได้ · อ่าน bin/rails routes ออก · และเขียน params.expect ที่กันช่องแปลกปลอมได้

🔁 ทวนก่อนเริ่ม — คำพวกนี้จะโผล่ในบทนี้ทั้งหมด

  • resources :posts (บท 101) — บรรทัดเดียวใน config/routes.rb ที่ได้ "เซ็ตเมนูมาตรฐาน" ของแผนกบทความ · bin/rails routes -c posts = พิมพ์รายการของพนักงานต้อนรับเฉพาะแผนก posts
  • params (บท 102) — กล่องรวมของทุกอย่างที่ลูกค้าส่งมากับใบสั่ง · ใช้เหมือน Hash · ค่าข้างในเป็นข้อความเสมอ
  • private (บท 102) — method ที่อยู่ใต้คำนี้ไม่ใช่เมนู route ชี้มาหาไม่ได้ ใช้ได้แค่ใน class
  • CSRF token / บัตรคิว (บท 103) — ใบสั่งที่เปลี่ยนข้อมูล (POST · PATCH · DELETE) ต้องแนบรหัสที่ได้จากหน้าเว็บของเรา ไม่งั้นได้ 422
  • post.comments · save! (บท 115 · บท 110) — คอมเมนต์ทั้งหมดของบทความนี้ · บันทึก ถ้าไม่ได้ให้ระเบิด

🧰 เวอร์ชันที่ใช้ตรวจ: Ruby 4.0.9 · Rails 8.1.4 · PostgreSQL 17 (สไลด์ใช้ Ruby 4.0.6 · Rails 8.1.3 — เรื่องในบทนี้ไม่ต่างกัน)
📦 ข้อมูลตัวอย่าง: ใช้ตาราง users / posts / comments และข้อมูลตัวอย่าง (seeds) ชุดเดียวกับ บท 107 หัวข้อ "เตรียมตู้ของวันที่ 2" (สมชาย · สมหญิง · มานะ · บทความ 6 ชิ้น · คอมเมนต์ 7 อัน) · ผลรันทุกกล่องมาจากเครื่องจริงที่เปิด server พอร์ต 3000 · เวลา ms · เลข 0x… · วันเวลาใน log ของคุณจะไม่ตรงกับของผม · ผลในบทรันกับตารางสามลิ้นชักแบบบท 107 เปล่า ๆ — ถ้าแอปของคุณยังมีของจากบท 116 (ช่อง comments_count · counter_cache · touch) บรรทัด INSERT INTO "posts" จะมีช่อง comments_count เพิ่ม และตอนสร้างคอมเมนต์จะมีบรรทัด UPDATE "posts" ตามมาอีกบรรทัด — ไม่ใช่ error

ทวน — REST และ resources :posts คือ 7 เมนูมาตรฐาน วางข้าง Gin ทีละแถว

REST คือคำที่คุณเจอแล้วในฝั่ง Go (บท 33) · ภาษาคน: ตั้งชื่อ URL เป็นชื่อของ (คำนาม เช่น /posts) แล้วให้ verb (GET · POST · PATCH · DELETE) บอกว่าจะทำอะไรกับของนั้น · ไม่ตั้ง URL เป็นคำกริยาอย่าง /deletePost

ในร้านเรา REST คือกฎแฟรนไชส์ที่ให้ทุกแผนกรับใบสั่งรูปแบบเดียวกัน: ชื่อแผนก + เลขจาน (ถ้ามี) + อยากทำอะไร · "ของหนึ่งชนิดที่มี URL ของตัวเอง" (บทความ · คอมเมนต์) เรียกว่า resource — ที่มาของชื่อคำสั่ง resources

ในบท 101 เราพิมพ์ resources :posts บรรทัดเดียว แล้ว Rails ลงรายการให้พนักงานต้อนรับครบชุด · สไลด์หน้า 46 นับได้ 7 route แต่ตอนรัน bin/rails routes ในบท 101 เราเห็น 8 แถว — ไม่มีใครผิด: 

$ bin/rails routes -c posts
   Prefix Verb   URI Pattern               Controller#Action
    posts GET    /posts(.:format)          posts#index
          POST   /posts(.:format)          posts#create
 new_post GET    /posts/new(.:format)      posts#new
edit_post GET    /posts/:id/edit(.:format) posts#edit
     post GET    /posts/:id(.:format)      posts#show
          PATCH  /posts/:id(.:format)      posts#update

ดูคอลัมน์ขวาสุด · PATCH กับ PUT ไปที่ posts#update เมนูเดียวกัน · นับเป็น "เมนู" (action) ได้ 7 · นับเป็น "บรรทัดในรายการ" ได้ 8 · เวลาคนพูดว่า "resources ให้ 7 route" เขานับเมนู

🗣 ศัพท์ที่ทวนไป
REST · RESTful
แนวตั้ง URL เป็นชื่อของ (คำนาม) แล้วใช้ verb บอกว่าทำอะไร · route ที่ทำตามแนวนี้เรียกว่า RESTful · ถาม senior ได้ว่า "URL /deletePost?id=3 นี่ไม่ RESTful ใช่ไหมครับ ควรเป็น DELETE /posts/3"
resource
ของหนึ่งชนิดที่มี URL ของตัวเอง (posts · comments) · resources :ชื่อ สร้างเซ็ตเมนูมาตรฐานของมันให้ · พิมพ์บอก AI ได้ว่า "add RESTful routes for comments using resources"

ที่เหลือของครึ่งแรกคือ 4 ท่าสำหรับวันที่เซ็ตมาตรฐานไม่พอดีกับร้านเรา · ทุกท่าผมรัน bin/rails routes จริงให้ดูผล

ท่าที่ 1 · ตัดเมนูที่ไม่ใช้ทิ้ง — only: กับ except:

ถ้าแอปเรายังไม่มีหน้าลบบทความ ก็ไม่ควรเปิดทาง DELETE /posts/:id ทิ้งไว้ · เส้นที่เปิดไว้แต่ไม่ได้ใช้ คือประตูที่ไม่มีคนเฝ้า วันหนึ่งมีคนเผลอเขียน def destroy เพิ่มเข้ามา ประตูนั้นก็ใช้ได้ทันทีโดยไม่มีใครตั้งใจ 

# config/routes.rb
resources :posts, only: [:index, :show]
$ bin/rails routes -c posts
Prefix Verb URI Pattern          Controller#Action
 posts GET  /posts(.:format)     posts#index
  post GET  /posts/:id(.:format) posts#show
  • only: [:index, :show] — "เอาแค่เมนูในรายการนี้" · ผลคือเหลือ 2 เส้นจาก 8 · [ ] คือ array ของ symbol (บท 92)
  • เขียน only: ต่อท้ายด้วยลูกน้ำได้ เพราะเป็น hash ท้าย argument ที่ไม่ต้องใส่ปีกกา (บท 97)

ถ้าอยากได้เกือบครบ ขาดแค่ตัวเดียว ใช้ except: (= "ทุกเมนู ยกเว้น…") จะสั้นกว่า:

resources :posts, except: [:destroy]
$ bin/rails routes -c posts
   Prefix Verb  URI Pattern               Controller#Action
    posts GET   /posts(.:format)          posts#index
          POST  /posts(.:format)          posts#create
 new_post GET   /posts/new(.:format)      posts#new
edit_post GET   /posts/:id/edit(.:format) posts#edit
     post GET   /posts/:id(.:format)      posts#show
          PATCH /posts/:id(.:format)      posts#update
          PUT   /posts/:id(.:format)      posts#update

แถว DELETE หายไป · ตอนนี้ใบสั่ง DELETE /posts/1 จะได้ Routing Error ทันที (ผมถาม router ดูแล้วได้ No route matches "/posts/1" · พนักงานต้อนรับไม่มีบรรทัดนี้ในรายการ — 404 แบบที่ 1 ของบท 101)

ท่าที่ 2 · ซ้อนกัน — คอมเมนต์ของบทความเลขไหน

คอมเมนต์ไม่ได้ลอยอยู่เฉย ๆ มันอยู่ใต้บทความเสมอ (ในตู้ ใบคอมเมนต์มีช่อง post_id — บท 115) · เวลาจะเขียนคอมเมนต์ใหม่ URL ก็ควรบอกด้วยว่า "ใต้บทความเลขไหน" · Rails ทำได้ด้วยการวาง resources ซ้อนใน do … end: 

# config/routes.rb
resources :posts do
  resources :comments
end
$ bin/rails routes -c comments
           Prefix Verb   URI Pattern                                 Controller#Action
    post_comments GET    /posts/:post_id/comments(.:format)          comments#index
                  POST   /posts/:post_id/comments(.:format)          comments#create
 new_post_comment GET    /posts/:post_id/comments/new(.:format)      comments#new
edit_post_comment GET    /posts/:post_id/comments/:id/edit(.:format) comments#edit
     post_comment GET    /posts/:post_id/comments/:id(.:format)      comments#show
                  PATCH  /posts/:post_id/comments/:id(.:format)      comments#update
                  PUT    /posts/:post_id/comments/:id(.:format)      comments#update
                  DELETE /posts/:post_id/comments/:id(.:format)      comments#destroy

ของใหม่ในตารางนี้มีสามอย่าง:

  • ทุก URL ขึ้นต้นด้วย /posts/:post_id/ — ช่องว่างที่รอเติมเลขบทความ · ชื่อช่องคือ :post_id ไม่ใช่ :id เพราะ :id สงวนไว้ให้เลขของคอมเมนต์เอง · ใน controller อ่านด้วย params[:post_id]
  • ยังไปแผนก comments (= CommentsController) ไม่ใช่แผนก posts · การซ้อนเปลี่ยนแค่หน้าตา URL ไม่ได้ย้ายแผนก
  • ชื่อ route ได้คำว่า post_ นำหน้า — post_comments · post_comment → helper คือ post_comments_path · post_comment_path (หัวข้อ route helper ด้านล่าง)
🧾 เทียบกับร้านอาหาร — ใบสั่งที่ต้องระบุเลขจานแม่

ใบคอมเมนต์ในตู้มีช่อง "เป็นของบทความเลขที่ …" อยู่แล้ว (บท 115) · nested route คือการพิมพ์ช่องเดียวกันนี้ไว้บนใบสั่งของลูกค้าด้วย: "ขอเขียนคอมเมนต์ ใต้บทความจานที่ 5" = POST /posts/5/comments · พนักงานต้อนรับเห็นเลข 5 ก็จดใส่ params[:post_id] แล้วส่งเข้าแผนกคอมเมนต์

ที่ไม่เหมือนกัน: พนักงานต้อนรับไม่ได้เปิดตู้เช็คว่าบทความเลข 5 มีจริงไหม หรือคอมเมนต์เลข 9 อยู่ใต้บทความ 5 จริงไหม · เขาแค่จดตัวเลขตามใบสั่ง · คนที่ต้องเช็คคือเชฟ (controller) — เช่น Post.find(params[:post_id]) ถ้าไม่เจอได้ 404 (เห็นจริงในภารกิจท้ายบท)

เทียบกับ Go: ใน Gin คุณเขียนเองว่า r.POST("/posts/:post_id/comments", h.CreateComment) แล้วอ่าน c.Param("post_id") · Rails ได้ชุดนี้ครบ 8 บรรทัดจากการวาง resources :comments ไว้ใน block ของ posts

กฎ: ซ้อนแค่ชั้นเดียวพอ

ถ้าคอมเมนต์มีการตอบกลับ (replies) อีกชั้น แล้วซ้อนลงไปตรง ๆ จะได้แบบนี้ (ตัดมา 3 แถวจาก 8):

# ❌ ซ้อนสองชั้น
resources :posts do
  resources :comments do
    resources :replies
  end
end

   post_comment_replies GET    /posts/:post_id/comments/:comment_id/replies(.:format)          replies#index
edit_post_comment_reply GET    /posts/:post_id/comments/:comment_id/replies/:id/edit(.:format) replies#edit

URL ยาวเป็นพรืด และทุกครั้งที่สร้างลิงก์ต้องส่งเลขครบสามตัว (บทความ · คอมเมนต์ · การตอบ) · คู่มือ Rails เองแนะนำว่า ซ้อนไม่เกิน 1 ชั้น · สไลด์หน้า 47 เรียก /posts/1/comments/2/replies/3 ว่า "สัญญาณว่าออกแบบผิด"

ทางออกคือ: ใช้ URL ซ้อนเฉพาะตอนที่ต้องรู้แม่ (ดูรายการคอมเมนต์ของบทความ · เขียนคอมเมนต์ใหม่ใต้บทความ) · ส่วนคอมเมนต์ที่มีเลขของตัวเองแล้ว ใช้ URL สั้น /comments/9 ได้เลย เพราะคอมเมนต์ 9 รู้อยู่แล้วว่าตัวเองอยู่ใต้บทความไหน · Rails มีตัวเลือก shallow: true ที่ทำแบบนี้ให้อัตโนมัติ (แค่รู้จักไว้ · ตัวอย่างเต็มอยู่ในคู่มือ Rails ลิงก์แรกของหัวข้ออ้างอิง): 

resources :posts do
  resources :comments, shallow: true   # index · new · create ซ้อน · ที่เหลือใช้ /comments/:id
end
🗣 ศัพท์ที่เพิ่งเรียนไป
nested resources
การวาง resources ซ้อนใน block ของอีกตัว ได้ URL แบบ /posts/:post_id/comments · พิมพ์บอก AI ได้ว่า "nest comments under posts in routes.rb, only index and create"
parent id (:post_id)
เลขของแม่ที่ติดมาใน URL · อ่านด้วย params[:post_id] · ส่วน params[:id] คือเลขของลูก · ถาม senior ได้ว่า "action นี้ควรหา comment ผ่าน post.comments.find หรือ Comment.find ตรง ๆ ครับ" (คำตอบส่วนใหญ่คืออย่างแรก เพราะเช็คว่าเป็นของบทความนี้จริง)
shallow nesting
ซ้อนเฉพาะเส้นที่ยังไม่มี id ของลูก · เส้นที่มี id แล้วใช้ URL สั้น · คุยกับทีมได้ว่า "เส้นนี้ลึกเกิน ใช้ shallow ดีไหม"

ท่าที่ 3 · เมนูพิเศษ — member กับ collection

ร้านเราอยากได้สองหน้าที่ไม่อยู่ในเซ็ตมาตรฐาน: ปุ่ม "เผยแพร่" ของบทความหนึ่งชิ้น (publish) และหน้ารวมบทความที่ยังเป็นร่าง (drafts) · สองอย่างนี้ต่างกันตรงที่ อันแรกต้องรู้ว่าบทความชิ้นไหน (มีเลข id) · อันหลังเป็นเรื่องของทั้งแผนก (ไม่มีเลข id) 

# config/routes.rb
resources :posts do
  member do
    post :publish        # เรื่องของบทความชิ้นเดียว → มี :id
  end
  collection do
    get :drafts         # เรื่องของทั้งแผนก → ไม่มี :id
  end
end

             DELETE /posts/:id(.:format)         posts#destroy

  • post :publish — คำว่า post ตรงนี้คือ verb POST (เหมือน get ในบท 101) ไม่ใช่ชื่อ model · ที่ใช้ POST เพราะการเผยแพร่คือ "เปลี่ยนข้อมูล"
  • collection do … end — "เมนูสำหรับทั้งแผนก" · ได้ /posts/drafts ไม่มี :id · ชื่อ drafts_posts (พหูพจน์)
  • สังเกตว่าสองเส้นใหม่ถูกวางไว้บนสุด เหนือ /posts/:id · Rails จัดให้เอง /posts/drafts เลยไม่โดน :id แย่งไปเป็น show (กับดักเรื่องลำดับในบท 101)
⭐ เทียบกับร้านอาหาร — เมนูพิเศษนอกเซ็ต

member คือคำสั่งพิเศษที่ต้องบอกเลขจาน: "จานที่ 5 ยกขึ้นตู้โชว์หน้าร้านได้แล้ว" (publish) · collection คือคำสั่งกับทั้งแผนก ไม่ต้องบอกเลข: "ขอดูรายการจานที่ยังไม่ได้ขึ้นตู้โชว์" (drafts) · ทั้งสองอย่างคือการเขียนบรรทัดเพิ่มลงในรายการของพนักงานต้อนรับ

ที่ไม่เหมือนกัน: ร้านจริงประกาศเมนูพิเศษแล้วเชฟก็รู้ว่าต้องทำอะไร · ใน Rails การเพิ่มบรรทัดใน routes.rb คือแค่จดลงในรายการ · เชฟยังไม่มีสูตร ต้องเขียน def publish กับ def drafts ใน PostsController เอง ไม่งั้นยิงไปได้ Unknown action (404 แบบที่ 2 ของบท 101)

เทียบกับ Go: ใน Gin ไม่มีคำว่า member/collection · คุณแค่เขียนเพิ่มสองบรรทัด r.POST("/posts/:id/publish", h.Publish) กับ r.GET("/posts/drafts", h.Drafts) · Rails แยกสองคำนี้ไว้เพื่อให้มันเติม :id ให้ถูกและตั้งชื่อ route ให้เอง

ท่าที่ 4 · ของที่มีชิ้นเดียว — resource (ไม่มี s)

บางอย่างผู้ใช้แต่ละคนมีแค่ชิ้นเดียว เช่น "หน้าโปรไฟล์ของฉัน" · ไม่มีหน้ารวมโปรไฟล์ทุกคน และไม่ต้องใส่เลข id ใน URL เพราะ "ของฉัน" ก็คือของคนที่ login อยู่ (ระบบ login มาใน Day 4) · ใน Gin คุณก็แค่เขียน r.GET("/profile", h.ShowProfile) ไม่มี :id · Rails ใช้ resource ที่ไม่มี s: 

# config/routes.rb

    @posts = Post.order(:id)
  end

  def create
    @post = Post.new(params[:post])
    @post.user = User.first   # ชั่วคราว: ยังไม่มีระบบ login

  • index + view — มีไว้ให้เราไปขอบัตรคิว (CSRF token) เท่านั้น · หน้าที่มี layout จะมีรหัสฝังอยู่ใน <head> (บท 103) · Post.order(:id) = บทความทั้งหมดเรียงตามเลข id (บท 113)
  • params[:post] — ฟอร์มของ Rails ตั้งชื่อช่องว่า post[title] · post[body] · Rails จึงรวบเป็นกลุ่มเดียว {"title" => …, "body" => …} ไว้ใน params[:post]
  • Post.new(params[:post]) — "สร้างแฟ้มบทความจากทุกช่องในกลุ่มนั้นรวดเดียว" · บรรทัดนี้คือตัวเอกของครึ่งหลัง
  • @post.user = User.first — ใส่ผู้เขียนเป็นสมชาย (คนแรกในตู้) แบบเดียวกับบท 110 · ของจริงคือคนที่ login อยู่ (Day 4)
  • render plain: … — ตอบเป็นข้อความเปล่า ให้ curl เห็นผลทันที (ของจริงจะ redirect_to @post) · @post.attributes = Hash ของทุกช่องบนแฟ้ม · .slice("title", …) = หยิบเฉพาะช่องที่ระบุมาโชว์

เปิด server (bin/rails server) ทิ้งไว้หนึ่งหน้าต่าง แล้วเปิดอีกหน้าต่างมาขอบัตรคิว · บรรทัดนี้ยาว ก็อปไปวางได้เลย หน้าตาเดียวกับบท 103 แค่เก็บรหัสไว้ใช้หลายรอบ: 

$ TOKEN=$(curl -s -c jar.txt http://localhost:3000/posts | grep -o 'name="csrf-token" content="[^"]*"' | sed 's/.*content="//;s/"$//')
  • เปิดหน้า /posts เหมือนลูกค้าจริง · เก็บ cookie ลงไฟล์ jar.txt (-c) · ตัดเอารหัสใส่ตัวแปร TOKEN
  • ทุกคำสั่ง POST ต่อจากนี้จะแนบ -b jar.txt (cookie) และ -H "X-CSRF-Token: $TOKEN" (รหัส) · -d "post[title]=…" = ส่งช่องหนึ่งช่องเหมือนกรอกฟอร์ม
  • คำสั่งยาว ผมตัดบรรทัดด้วย \ (= "บรรทัดนี้ยังไม่จบ") พิมพ์รวดเดียวบรรทัดเดียวก็ได้ผลเหมือนกัน

⚠️ เราถือบัตรคิวไปเหมือนลูกค้าจริง ไม่ได้ปิดการตรวจ CSRF · บทความในเน็ตหลายที่แนะนำให้ปิดเพื่อยิง curl ง่าย ๆ — อย่าทำ · ปิดแล้วลืมเปิด = เปิดทางให้เว็บอื่นปลอมใบสั่งแทนผู้ใช้ (บท 103) · ถ้าเห็น 422 + Can't verify CSRF token authenticity. แปลว่าลืม -b jar.txt หรือ -H · หรือเปิดหน้าต่าง terminal ใหม่ (ตัวแปร TOKEN อยู่แค่ในหน้าต่างที่สั่ง หน้าต่างใหม่ $TOKEN ว่าง) → สั่งบรรทัดขอบัตรคิวใหม่ในหน้าต่างนั้น

mass assignment — ลูกค้าแอบเขียนเพิ่มในใบสั่ง

ฟอร์มเขียนบทความของเรามีแค่ 2 ช่อง: ชื่อเรื่องกับเนื้อหา · แต่ ฟอร์มเป็นแค่หน้าตาบนจอ · ของที่ถึงร้านจริงคือ request ซึ่งใครจะเติมช่องอะไรลงไปก็ได้ (ด้วย curl หรือเครื่องมือในเบราว์เซอร์) เช่น post[views]=999999 · post[published]=true

ใบสั่งของร้านพิมพ์ช่องไว้สองช่อง: "ชื่อเมนู" กับ "รายละเอียด" · ลูกค้าคนหนึ่งเขียนเพิ่มที่ขอบกระดาษว่า "ฉันเป็นผู้จัดการ · ฟรี · ลงบัญชีโต๊ะอื่น" · ถ้าครัวทำตามทุกบรรทัดที่เขียนบนกระดาษ ร้านก็เจ๊ง — นี่คือ mass assignment

⚠️ permit! (มี !) แปลว่า "รับทุกช่อง ไม่ต้องตรวจ" · ใส่ในบทนี้เพื่อให้เห็นช่องโหว่กับตาเท่านั้น · ถ้าเห็นในโค้ดจริงหรือในคำตอบของ AI ให้ถือว่าเป็นบั๊ก · ทำหัวข้อนี้เสร็จแล้วเปลี่ยนกลับตามหัวข้อถัดไปทันที

"อนุญาตทุกช่อง" · ปิด error ได้แต่เปิดช่องโหว่กลับมาทั้งหมด · ในการรีวิวโค้ด เจอคำนี้กับ params จากผู้ใช้ ให้ทักทุกครั้ง

strong parameters — รับเฉพาะช่องที่อยู่บนแบบฟอร์ม

ทางแก้คือเขียนรายชื่อช่องที่ยอมรับ ไว้ใน method แยกใต้ private แล้วให้ create เรียกใช้ · ช่องที่ไม่อยู่ในรายชื่อจะถูกทิ้งก่อนถึงแฟ้ม · เปลี่ยนไฟล์ controller เป็น: 

# app/controllers/posts_controller.rb
class PostsController < ApplicationController
  def index
    @posts = Post.order(:id)
  end

  def create
    @post = Post.new(post_params)
    @post.user = User.first   # ชั่วคราว: ยังไม่มีระบบ login
    @post.save!
    render plain: "บันทึกแล้ว: #{@post.attributes.slice("title", "views", "published", "user_id")}\n"
  end

  private

  def post_params
    params.require(:post).permit(:title, :body)
  end
end
  • Post.new(post_params) — เปลี่ยนจาก params[:post] เป็นการเรียก method post_params ที่กรองแล้ว
  • params.require(:post) — "ใบสั่งนี้ต้องมีกลุ่มชื่อ post" · ไม่มีให้หยุดเลย
  • .permit(:title, :body) — "จากกลุ่มนั้น รับแค่ title กับ body" · ที่เหลือทิ้ง
  • อยู่ใต้ private เพราะไม่ใช่เมนู ลูกค้าเรียกตรง ๆ ไม่ได้ · ตั้งชื่อ ชื่อmodel_params เป็นธรรมเนียมที่ทุกร้าน Rails ใช้ และใช้ซ้ำได้ทั้งใน create กับ update

require เหมือนพนักงานต้อนรับที่ถามแค่ว่า "มีกระดาษที่เขียนว่า ใบสั่ง ไหม" · ลูกค้ายื่นกระดาษที่เขียนคำว่า "hello" คำเดียวมา พนักงานก็รับส่งเข้าครัว · เชฟหาช่องชื่อเมนูไม่เจอ ทำจานตกแตก (500)
expect คือพนักงานที่ดูก่อนว่าเป็นแบบฟอร์มที่มีช่องจริง ๆ · ถ้าไม่ใช่ คืนลูกค้าที่หน้าร้านเลยว่า "ใบสั่งผิดแบบครับ" (400) ครัวไม่ต้องรู้เรื่อง

ที่ไม่เหมือนกัน: การตรวจนี้จริง ๆ เกิดในครัว (ตอน create เรียก post_params) ไม่ใช่หน้าร้าน แค่เกิดก่อนเชฟลงมือ · พนักงานจริงที่คืนใบสั่งจะบอกว่าผิดตรงไหน แต่ expect บอกแค่ชื่อกลุ่ม (invalid: post) · และเรื่องช่องเกิน expect ทิ้งเงียบกว่า require/permit อีก — ผมยิงห้าช่องของคนร้ายเข้าท่า expect แล้วไม่มีบรรทัด Unpermitted parameters ใน log เลย · ช่องเกินยังถูกทิ้งเหมือนเดิม แค่ไม่มีใครบอก

เรื่อง AI: สไลด์หน้า 49 เตือนว่า AI มักเขียน require/permit ให้ เพราะเรียนจากโค้ดยุค Rails 6–7 · ไม่ผิด กันช่องเกินได้เหมือนกัน แต่ได้ 500 ตอนเจอรูปร่างแปลก · ขอให้ AI ใช้ params.expect ตรง ๆ ได้เลย · ส่วน bin/rails generate scaffold ของ Rails 8.1.4 เขียน params.expect ให้แล้ว (ผมเปิดไฟล์แม่แบบของมันดู — บท 118 จะอ่านโค้ดที่มันสร้าง)

ภารกิจ — ช่องเขียนคอมเมนต์ใต้บทความ ที่กันคนสวมรอยได้

🎯 nested route + params.expect (~10 นาที)

ต่อจากแอปทดลองข้างบน (ต้องมี posts#index + view ไว้ขอบัตรคิว) · คอมเมนต์ต้องเป็นของ "คนที่ login อยู่" เสมอ ไม่ใช่คนที่ใบสั่งอ้าง

  1. แก้ config/routes.rb ให้มี POST /posts/:post_id/comments เส้นเดียว ซ้อนใต้ posts (ใช้ only: ทั้งสองชั้น ให้ posts เหลือ index กับ create เหมือนเดิม · ใบ้: only: […] เขียนไว้ก่อนคำว่า do ได้ เช่น resources :posts, only: [...] do)
  2. สั่ง bin/rails routes -c comments · ควรเห็นแถวเดียว ชื่อ post_comments ไปที่ comments#create
  3. สร้างไฟล์ app/controllers/comments_controller.rb · action create ให้: หาบทความจาก params[:post_id] · สร้างคอมเมนต์ใต้บทความนั้นด้วย post.comments.new(comment_params) (new = build ในบท 115) · ใส่ผู้เขียนเป็น User.last (สมมุติว่าคนที่ login คือมานะ) · save! · แล้ว render plain: ข้อความบอกว่าใครเขียนอะไรใต้บทความไหน
  4. เขียน comment_params ใต้ private ด้วย params.expect ให้รับแค่ body
  5. ขอบัตรคิวใหม่ (บรรทัด TOKEN=…) แล้วยิงแบบคนร้ายที่อ้างว่าเป็นสมชาย: 
    $ curl -s -b jar.txt -H "X-CSRF-Token: $TOKEN" -X POST http://localhost:3000/posts/5/comments \
    -d "comment[body]=ขอสูตรด้วย" -d "comment[user_id]=1"

ควรเห็น: ข้อความที่บอกว่าผู้เขียนคือ มานะ ไม่ใช่สมชาย · บทความเลข 5 ใน seeds คือ "ผัดกะเพราหมูสับ" (ถ้าของคุณเลขไม่ตรงเพราะเคยเพิ่ม/ลบบทความ ใช้เลขบทความที่มีอยู่จริงในตู้ของคุณแทนได้)

ถ้าเจอ error แปลว่า…

  • 400 + param is missing or the value is empty or invalid: comment → ชื่อกลุ่มใน -d ไม่ตรงกับใน expect เช่นส่ง -d "body=…" หรือ post[body]
  • 422 + Can't verify CSRF token authenticity. → ลืม -b jar.txt / -H หรือยิงจากหน้าต่าง terminal ใหม่ที่ยังไม่ได้สั่งบรรทัด TOKEN=… ($TOKEN ว่าง)
  • uninitialized constant CommentsController → ชื่อไฟล์หรือชื่อ class ไม่ตรงกฎ (ต้อง comments_controller.rb + CommentsController พหูพจน์)
  • 404 + Couldn't find Post with 'id'="999" → ไม่มีบทความเลขนั้นในตู้ · Post.find ทำงานถูกแล้ว

② controller:

# app/controllers/comments_controller.rb
class CommentsController < ApplicationController
  def create
    post = Post.find(params[:post_id])
    comment = post.comments.new(comment_params)
    comment.user = User.last   # ชั่วคราว: สมมุติว่าคนที่ login คือมานะ
    comment.save!
    render plain: "คอมเมนต์ใหม่บน #{post.title} โดย #{comment.user.name}: #{comment.body}\n"
  end

  private

  def comment_params
    params.expect(comment: [:body])
  end
end
  • params[:post_id] — เลขบทความจาก URL (ไม่ใช่ params[:id])
  • post.comments.new(…) — สร้างใบคอมเมนต์ที่ช่อง post_id ถูกเติมเป็น 5 ให้แล้ว (บท 115)
  • comment.user = User.last — ผู้เขียนมาจากฝั่งเรา ไม่ได้มาจากใบสั่ง · ต่อให้ไม่มีบรรทัดนี้ user_id ของคนร้ายก็ไม่ผ่าน expect อยู่ดี

ข้อ 1 · routes.rb มีแค่ resources :posts do resources :comments end · ใบสั่ง DELETE /posts/5/comments/9 ไปที่ไหน และ params มีอะไร?

ตัวเลือกที่ 3 ถูก · ผมถามพนักงานต้อนรับตรง ๆ ด้วย Rails.application.routes.recognize_path (ท่าเดียวกับ quiz ข้อ 4 ของบท 105) วนทีละเส้นครบห้าเส้นของสไลด์ แล้วพิมพ์ผล:

POST /posts/5/comments => {controller: "comments", action: "create", post_id: "5"}
DELETE /posts/5/comments/9 => {controller: "comments", action: "destroy", post_id: "5", id: "9"}
GET /posts/new => {controller: "posts", action: "new"}

ตัวเลือกที่ 1 ลืมว่า URL ที่มี /comments ไปแผนก comments · ตัวเลือกที่ 2 ไปแผนกถูก แต่สลับเลข — :id เป็นของคอมเมนต์ (ลูก) ส่วนเลขบทความ (แม่) ชื่อ post_id · ตัวเลือกที่ 4 ผิดทั้ง verb และแผนก — DELETE ไปเมนู destroy เสมอ

จุดที่ต้องจำ: ใน nested route เลขของแม่ชื่อ :ชื่อแม่_id · เลขของลูกชื่อ :id · ตอบไม่ได้เมื่อไหร่ สั่ง bin/rails routes -c comments ดูได้เลย

ข้อ 2 · บน Rails 8.1 · action create เขียน @post = Post.new(params[:post]) (ไม่มี permit/expect) แล้วผู้ใช้ส่งฟอร์มธรรมดาที่มีแค่ title กับ body · เกิดอะไรขึ้น?

ตัวเลือกที่ 2 ถูก · ผลจริงในหัวข้อ mass assignment ขั้นที่ 1: 500 · log เขียน ActiveModel::ForbiddenAttributesError · 0 queries · คู่มือ Rails (Action Controller Overview หัวข้อ Strong Parameters) ก็เขียนตัวอย่างเดียวกันไว้ว่าบรรทัดแบบนี้จะโยน error ตัวนี้

ตัวเลือกที่ 1 คือสิ่งที่สไลด์หน้า 48 และ 50 พูดถึง — เกิดจริงเฉพาะตอนมีคนเติม permit! เข้าไป · ตัวเลือกที่ 3 ผิด — Rails ไม่รู้ว่าฟอร์มเรามีช่องอะไร ต้องเขียนรายชื่อเอง · ตัวเลือกที่ 4 ผิด — 400 มาจาก expect/require ตอนไม่มีกลุ่ม post ไม่ใช่เพราะลืมเขียน

จุดที่ต้องจำ: Rails 8 ปิดประตู mass assignment ไว้ก่อน · คนที่เปิดกลับคือเราเอง (ด้วย permit!) · ทางแก้ error นี้ที่ถูกคือเขียน strong parameters

ข้อ 3 · post_params เขียน params.require(:post).permit(:title, :body) · คนร้ายส่ง title · body และแอบเติม post[views]=999999 · ผลคืออะไร?

ตัวเลือกที่ 1 ถูก · ผลจริง: บันทึกแล้ว: {"title" => "ร้านผม", "views" => 0, …} และ log มี Unpermitted parameters: :views, :published, :user_id · SQL INSERT ใส่ views เป็น 0

ตัวเลือกที่ 2 กับ 4 ผิด — permit ไม่ปฏิเสธใบสั่ง แค่ทิ้งช่องเกินแล้วไปต่อ (status 200) · ตัวเลือกที่ 3 ผิด — log จดไว้ก็จริง แต่ช่องนั้นไม่ได้ลงตู้ · คำเตือนไม่ใช่การปล่อยผ่าน

จุดที่ต้องจำ: permit = allowlist ที่ทิ้งเงียบ ๆ · คนส่งไม่รู้ตัว · เราดูได้จาก log ตอนพัฒนา

ข้อ 4 · มีคนป่วนส่ง -d "post=hello" (post เป็นข้อความคำเดียว) · ถ้า post_params เขียนด้วย require/permit กับเขียนด้วย params.expect จะได้ status อะไรตามลำดับ?

ตัวเลือกที่ 4 ถูก · ผลจริงในตารางหัวข้อ params.expect: require/permit ได้ 500 + undefined method 'permit' for an instance of String · expect ได้ 400 + ParameterMissing

ตัวเลือกที่ 1 ผิดครึ่งเดียว — ท่าเก่าไม่ได้ 400 เพราะ require เห็นว่ามี post ก็ปล่อยผ่าน · ตัวเลือกที่ 2 ผิดครึ่งเดียว — expect เช็ครูปร่างก่อน จึงไม่พัง · ตัวเลือกที่ 3 ผิด — ทั้งสองท่าไม่ไปถึงบรรทัด save! เลย

จุดที่ต้องจำ: expect = require + permit + เช็ครูปร่าง · ใบสั่งผิดแบบได้ 400 (ความผิดคนส่ง) ไม่ใช่ 500 (ครัวพัง)

ข้อ 3 ปลายเปิดของสไลด์หน้า 50 ("แก้ให้ปลอดภัยแล้ว ยังมีอีก 2 เรื่องที่ควรแก้ · เรื่องหนึ่งเกี่ยวกับ save อีกเรื่องเกี่ยวกับผู้ใช้ที่กรอกผิด") · ลองคิดเองก่อน แล้วเทียบกับ action create ในบท 110 หัวข้อ 7 ที่ใช้ if @post.save … else render :new, status: :unprocessable_content · โค้ดในสไลด์ไม่ดูผลของ save แล้ว redirect เสมอ แม้บันทึกไม่สำเร็จ
