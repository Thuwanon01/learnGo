ลองในครัวทดลอง — สร้าง อ่าน แก้ ลบบทความด้วย console

~25 นาที (ครึ่งหลังเป็นการเตรียมข้อมูลของวันที่ 2 ราว 10 นาที) · ควรผ่าน บทเรียน 106 (Active Record คืออะไร) และ บทเรียน 104 (bin/rails console) มาก่อน

บท 106 บอกว่าแฟ้มของ Rails “เดินเข้าลิ้นชักเองได้” · บทนี้เราจะสั่งให้มันเดินจริง
อ่านจบแล้วคุณจะ สร้าง · หยิบมาอ่าน · แก้ · ทิ้ง บทความได้เองจาก bin/rails console และอ่านบรรทัด SQL ที่ console พิมพ์ออกมาได้ว่าแต่ละบรรทัดสั่งตู้ทำอะไร
ท้ายบทคุณจะมีข้อมูลตัวอย่างของวันที่ 2 (ผู้ใช้ 3 คน · บทความ 6 ชิ้น · คอมเมนต์ 7 อัน) อยู่ในเครื่อง พร้อมใช้ในบทที่เหลือทั้งหมด

🔁 ทวนก่อนเริ่ม — คำจากบทก่อน ๆ ที่บทนี้ใช้

  • model (บท 99, 106) — class อย่าง Post ที่เป็น “คนดูแลสต็อก” ของลิ้นชัก posts
  • ตาราง · แถว · คอลัมน์ · SQL (บท 106) — ลิ้นชัก · แฟ้มหนึ่งแผ่น · ช่องบนแฟ้ม (เช่นช่อง title) · SQL = ภาษาที่คนดูแลสต็อกใช้สั่งตู้
  • bin/rails console (บท 104) — ครัวทดลองหลังร้าน พิมพ์ Ruby ทีละบรรทัด · => นำหน้าผลลัพธ์
  • nil (บท 94) — “ไม่มีค่า” · เรียก method บน nil จะได้ NoMethodError
  • title: "…" (บท 92) — ส่งค่าเป็นคู่ “ชื่อช่อง: ค่า” (hash ที่ใช้ symbol เป็นชื่อ)

🧰 ตรวจด้วย Ruby 4.0.9 · Rails 8.1.4 · PostgreSQL 17 (สไลด์ใช้ Ruby 4.0.6 · Rails 8.1.3 — รุ่นแก้บั๊กในสายเดียวกัน ใช้แทนกันได้)

📦 ข้อมูลที่บทนี้ใช้: ครึ่งแรกใช้ตาราง posts ที่มีแค่ title กับ body (แบบเดียวกับบท 99) · ครึ่งหลังเราจะสร้างข้อมูลกลางของวันที่ 2 ที่บท 108–119 ใช้ร่วมกัน

ผลทุกก้อนรันจริงแล้วก็อปมา · เวลา (ms) · วันเวลาในแฟ้ม · เลข 0x… · เลขบรรทัดของ prompt ของคุณจะไม่ตรงกับในบท และจอคุณจะมีสี

CRUD — งานสี่อย่างของคนดูแลสต็อก

ไม่ว่าเว็บไหน งานที่ทำกับข้อมูลมีแค่สี่แบบ: เก็บของใหม่ · หยิบมาดู · แก้ · ทิ้ง
คนในวงการเรียกรวมว่า CRUD (อ่านว่า “ครัด”) ย่อมาจาก Create · Read · Update · Delete
บล็อกของเราก็คือ CRUD ของบทความ: เขียนบทความใหม่ · เปิดอ่าน · แก้คำผิด · ลบทิ้ง

ตัวอักษรภาษาคนคำสั่ง Rails ที่จะได้ลองคำ SQL ที่ console จะโชว์
Createเก็บแฟ้มใหม่ลงลิ้นชักPost.new + save · Post.createINSERT
Readหยิบแฟ้มมาอ่านfind · find_by · where · first · last · all · countSELECT
Updateแก้แฟ้มที่อยู่ในลิ้นชักupdateUPDATE
Deleteทิ้งแฟ้มออกจากลิ้นชักdestroyDELETE

เทียบกับ Go: ในบท 27 คุณเขียน repository (ไฟล์ที่รวมคำสั่งคุยกับฐานข้อมูลไว้ที่เดียว) ที่มี Create · FindByID · FindAll ด้วย GORM — นั่นคือตัว C กับ R ของ CRUD · บทนี้คือของชุดเดียวกันฝั่ง Rails แต่ไม่ต้องเขียน repository เอง เพราะ model ทำให้หมดแล้ว

🗄️ เทียบให้เห็นภาพ — คนดูแลสต็อกมีงานแค่สี่อย่าง

ห้องเก็บของของร้าน มีตู้เก็บแฟ้ม (database) และลิ้นชัก posts · คนดูแลสต็อก (model Post) ทั้งวันทำแค่สี่อย่าง: รับแฟ้มใหม่มาเก็บ · หยิบแฟ้มให้คนที่ขอ · แก้ข้อความบนแฟ้ม · ทิ้งแฟ้มที่ไม่ใช้
ทุกครั้งที่ทำ เขาสั่งตู้ด้วยภาษาเฉพาะของตู้ชื่อ SQL · เราพูด Ruby กับเขา เขาแปลเป็น SQL ให้เอง

ที่ไม่เหมือนกัน: คนจริงทิ้งแฟ้มลงถังขยะ ยังคุ้ยคืนได้ · destroy ใน Rails ลบออกจากตู้จริง ไม่มีถังขยะให้คุ้ย (ยกเว้นเปิด console แบบ --sandbox จากบท 104 ที่ยกเลิกทุกอย่างตอนออก)

🗣 ศัพท์ที่เพิ่งเรียนไป
CRUD
Create · Read · Update · Delete = งานพื้นฐานสี่อย่างกับข้อมูล · หน้าเว็บส่วนใหญ่คือ CRUD ของอะไรสักอย่าง · พิมพ์บอก AI ได้ว่า “build basic CRUD for posts in Rails” แล้วจะได้ของครบสี่อย่าง (บท 118 จะสอนอ่านสิ่งที่ได้มา)
SQL
ภาษาที่ใช้สั่งฐานข้อมูล เช่น PostgreSQL · Active Record แปลคำสั่ง Ruby เป็น SQL ให้ · เราไม่ต้องเขียนเอง แต่ต้องอ่านออก · ถาม senior ได้ว่า “บรรทัดนี้ Active Record ยิง SQL อะไรออกไป”

เปิดครัวทดลอง แล้วถาม Post ว่ารู้อะไรบ้าง

ทำในโปรเจกต์ wongnok_blog เดิมจากบท 106 · เปิด terminal หน้าต่างใหม่ต้อง export DATABASE_URL=… ก่อนทุกครั้ง (แบบบท 105)
ต้องมี model Post กับตาราง posts ก่อน · เช็คด้วย ls app/models ในโฟลเดอร์โปรเจกต์
ถ้ายังไม่มีไฟล์ post.rb ให้สร้างแบบเดียวกับบท 99 (ถ้ามีแล้วจากบท 106 ข้ามได้เลย): 

$ bin/rails generate model Post title:string body:text
$ bin/rails db:migrate
  • บรรทัดแรก = สร้างไฟล์ model กับ “ใบสั่งช่าง” (migration) ที่ขอลิ้นชัก posts มีช่อง title กับ body
  • บรรทัดสอง = สั่งช่างลงมือตามใบสั่ง · ลิ้นชักเกิดขึ้นจริงในตู้ (บท 108 อธิบายเต็ม)
  • ถ้าเผลอสั่งบรรทัดแรกซ้ำ จะได้ The name 'Post' is either already used in your application… — ไม่มีอะไรเสีย แค่บอกว่ามีอยู่แล้ว

เปิด console แล้วถามว่า “ตอนนี้ลิ้นชักมีกี่แผ่น” (ผลจริง):

$ bin/rails console
Loading development environment (Rails 8.1.4)
wongnok-blog(dev):001> Post.count
  Post Count (54.6ms)  SELECT COUNT(*) FROM "posts" /*application='WongnokBlog'*/
=> 0

บรรทัดกลางคือของใหม่ที่ Day 1 ยังไม่เคยเห็น (บท 106 แอบเห็นมาแล้วหนึ่งครั้ง) — console บอกเราว่ามันเพิ่งไปคุยกับตู้มา · แยกทีละส่วน:

  • Post Count — ใครทำอะไร: “คนดูแลสต็อกของ Post กำลังนับ”
  • (54.6ms) — ใช้เวลากี่มิลลิวินาที · ครั้งแรกหลังเปิด console มักช้ากว่าครั้งต่อ ๆ ไป · ของคุณจะได้เลขอื่น
  • SELECT COUNT(*) FROM "posts" — SQL ที่ส่งไปจริง · SELECT = “ขอ/หยิบ” · COUNT(*) = “นับจำนวนแผ่น” · FROM "posts" = “จากลิ้นชัก posts”
    → อ่านรวมว่า “นับให้หน่อยว่าลิ้นชัก posts มีแฟ้มกี่แผ่น”
  • /*application='WongnokBlog'*/ — ป้ายชื่อแอปที่ Rails แปะท้ายทุกคำสั่ง (/* */ คือโน้ตใน SQL ตู้ไม่สนใจ) · ข้ามไปได้เลย
  • => 0 — คำตอบ: ยังไม่มีแฟ้มสักแผ่น
📒 เทียบให้เห็นภาพ — สมุดบันทึกการเบิกของ

ทุกครั้งที่คนดูแลสต็อกเดินไปที่ตู้ เขาจดลงสมุดหนึ่งบรรทัด: ใครไป · ไปทำอะไร · ใช้เวลาเท่าไหร่ · พูดกับตู้ว่าอะไร · บรรทัดที่ขึ้นต้นด้วย Post Count (…ms) คือหน้าสมุดเล่มนั้น
อยากรู้ว่าคำสั่ง Ruby หนึ่งบรรทัดทำให้เดินไปตู้กี่รอบ → นับบรรทัดในสมุด

ที่ไม่เหมือนกัน: สมุดจริงต้องมีคนนั่งจด · ที่นี่ Rails จดให้เองทุกครั้งโดยไม่ต้องสั่ง · และจดเป็นภาษา SQL ไม่ใช่ภาษาคน — งานของเราคืออ่านให้ออก (บทนี้จะแปลให้ทุกบรรทัด)

คำถามเรื่องโครงของลิ้นชัก (Post.table_name · Post.column_names · Post.columns_hash) คุณลองไปแล้วในภารกิจบท 106 · บทนี้จึงข้ามไปที่ของใหม่เลย: สั่งให้แฟ้มเข้าออกลิ้นชักจริง แล้วอ่านสมุดบันทึกทุกบรรทัด

🗣 ศัพท์ที่เพิ่งเรียนไป
SQL log (log ของ query)
บรรทัดที่ Rails พิมพ์บอกทุกครั้งที่คุยกับฐานข้อมูล (ใครทำ · ใช้เวลาเท่าไหร่ · SQL ที่ส่งไป) · ในบทนี้เห็นใน console · ตอนรันเว็บจะเห็นในหน้าต่าง server · พิมพ์บอก AI ได้ว่า “here is the SQL log from rails console” แล้วแปะทั้งก้อน — ได้คำตอบตรงกว่าเล่าเป็นคำพูดมาก
COUNT(*)
คำ SQL “นับจำนวนแถว” · ฝั่ง Ruby คือ Post.count · ใช้เช็คเร็ว ๆ ว่ามีข้อมูลอยู่กี่แถวโดยไม่ต้องหยิบออกมาทั้งหมด · ถาม senior ได้ว่า “ตารางนี้ตอนนี้มีกี่ row ใน dev กับใน production”

C — สร้าง: new ยังอยู่ในมือ · save ถึงลงลิ้นชัก

Post.new(...) ทำแค่จังหวะแรก · ลองดู (ผลจริง): 

wongnok-blog(dev):002> post = Post.new(title: "ต้มยำกุ้งน้ำข้น", body: "สูตรต้มยำกุ้งแบบร้านดัง")

#<Post:0x0000000127dc4650

 body: "สูตรต้มยำกุ้งแบบร้านดัง",

  • post = Post.new(title: …, body: …) — สร้างบทความหนึ่งชิ้นแล้วกรอกช่อง · เก็บไว้ในตัวแปร post
    console ย่อผลเหลือ ... เพราะเป็นบรรทัดตั้งตัวแปร · พิมพ์ post เฉย ๆ อีกบรรทัดเพื่อดูเต็ม
  • #<Post:0x0000000127dc4650 … > — วิธีที่ Ruby โชว์ object หนึ่งตัว: “นี่คือบทความ (object ของ class Post)” · เลข 0x… คือที่อยู่ในหน่วยความจำ ไม่ต้องสนใจ (ของคุณจะต่าง) · บรรทัดข้างในคือช่องบนแฟ้มทีละช่อง
  • id: nil · created_at: nil — ยังไม่มีเลขที่แฟ้ม ยังไม่มีเวลาเก็บ
  • new_record? — “เป็นแฟ้มใหม่ที่ยังไม่เคยเข้าลิ้นชักใช่ไหม” → true · ชื่อลงท้ายด้วย ? = ถามตอบใช่/ไม่ใช่ (บท 93)
  • persisted? — “อยู่ในลิ้นชักแล้วใช่ไหม” → false · เป็นคำถามกลับด้านของ new_record?
  • ไม่มีบรรทัด SQL สักบรรทัด — ยังไม่มีใครเดินไปตู้

  Post Count (1.6ms)  SELECT COUNT(*) FROM "posts" /*application='WongnokBlog'*/

count ไปนับที่ลิ้นชักจริง · แฟ้มที่ new ไว้ยังอยู่ในมือเรา (ในหน่วยความจำของ console) ไม่ได้อยู่ในลิ้นชัก · ถ้าปิด console ตอนนี้ แฟ้มนี้หายไปเลย ไม่มีใครรู้ว่าเคยมี

จังหวะที่สอง — save คือ “เดินเอาแฟ้มเข้าลิ้นชัก” (ผลจริง):

wongnok-blog(dev):008> post.save
  TRANSACTION (1.4ms)  BEGIN /*application='WongnokBlog'*/
  Post Create (3.1ms)  INSERT INTO "posts" ("title", "body", "created_at", "updated_at") VALUES ('ต้มยำกุ้งน้ำข้น', 'สูตรต้มยำกุ้งแบบร้านดัง', '2026-11-04 12:17:23.004987', '2026-11-04 12:17:23.004987') RETURNING "id" /*application='WongnokBlog'*/
  TRANSACTION (1.7ms)  COMMIT /*application='WongnokBlog'*/
=> true

=> 1
wongnok-blog(dev):010> post.new_record?
=> false
wongnok-blog(dev):011> post.persisted?

สมุดบันทึกมีสามบรรทัด · แปลทีละบรรทัด:

  • BEGIN — “เริ่มกรอบงาน” · ทุกอย่างหลังจากนี้ ถ้าสำเร็จหมดค่อยนับ ถ้ามีอะไรพังกลางทางให้ยกเลิกทั้งหมด
  • INSERT INTO "posts" ("title", "body", "created_at", "updated_at") VALUES ('ต้มยำกุ้งน้ำข้น', …) — “ใส่แฟ้มใหม่ลงลิ้นชัก posts ช่อง title เขียนว่า ต้มยำกุ้งน้ำข้น · ช่อง body เขียนว่า … · ช่องเวลาสร้างกับเวลาแก้เขียนเวลานี้”
    INSERT INTO = ใส่เข้าไปใน · วงเล็บแรก = ชื่อช่อง · VALUES (…) = ค่าของแต่ละช่อง เรียงตามลำดับเดียวกัน
    สังเกตเครื่องหมายคำพูด: ใน SQL ชื่อลิ้นชักกับชื่อช่องอยู่ใน "…" ส่วนค่าที่เป็นข้อความอยู่ใน '…' (ต่างจาก Ruby ที่ใช้ได้ทั้งคู่)
  • เวลาสองช่องนั้น Rails เติมให้เอง · เป็นเวลาสากล (UTC) ช้ากว่าเวลาไทย 7 ชั่วโมง — ตั้งเปลี่ยนได้ ยังไม่ต้องสนใจ
  • RETURNING "id" — “เก็บเสร็จแล้วบอกเลขที่แฟ้มกลับมาด้วย” · ตู้เป็นคนแจกเลข ไม่ใช่เรา
  • COMMIT — “ยืนยัน ปิดกรอบงาน” · ตั้งแต่ตอนนี้แฟ้มอยู่ในลิ้นชักจริง คนอื่นเห็นแล้ว
  • => true — save ตอบว่าสำเร็จ · จากนั้น id กลายเป็น 1 และคำถามสองข้อกลับด้านหมด

กรอบ BEGIN … COMMIT ชื่อทางการคือ transaction = “ทำทั้งหมด หรือไม่ทำเลย” · เทียบกับ Go: คือ tx, _ := db.Begin() … tx.Commit() ในบท 8 (คู่กับ defer tx.Rollback()) — Rails ครอบให้ทุกครั้งที่ save โดยไม่ต้องเขียนเอง · ทำไมต้องครอบแม้มีคำสั่งเดียว และใช้เองยังไง อยู่บท 111

📝 เทียบให้เห็นภาพ — กรอกแฟ้มในมือ กับ เดินเอาเข้าลิ้นชัก

Post.new = หยิบแฟ้มเปล่ามากรอกข้อความ แล้วถือไว้ในมือ · ยังไม่มีเลขที่แฟ้ม ลิ้นชักไม่รู้ว่ามีแฟ้มนี้ · save = แฟ้มเดินเข้าลิ้นชักเอง (บท 106) ตู้ประทับเลขที่ให้ แล้วแฟ้มก็จำเลขนั้นไว้
new_record? คือถามว่า “ยังถืออยู่ในมือใช่ไหม” · persisted? คือถามว่า “เข้าลิ้นชักแล้วใช่ไหม”

ที่ไม่เหมือนกัน: แฟ้มกระดาษในมือ วางลืมไว้ก็ยังอยู่บนโต๊ะ · แฟ้มที่ new แล้วไม่ได้ save อยู่แค่ในหน่วยความจำ — ปิด console หรือ request จบ ก็หายไปทันทีโดยไม่มีอะไรเตือน

🗣 ศัพท์ที่เพิ่งเรียนไป
INSERT · RETURNING
คำ SQL สำหรับ “ใส่แถวใหม่” · RETURNING "id" = ขอเลขที่ได้กลับมา (ของ PostgreSQL) · ถาม senior ได้ว่า “save หนึ่งครั้งยิง INSERT กี่ครั้ง ดูจาก log ตรงไหน”
transaction (BEGIN / COMMIT)
กรอบงาน “ทำทั้งหมดหรือไม่ทำเลย” · BEGIN = เริ่ม · COMMIT = ยืนยัน · ROLLBACK = ยกเลิกทั้งกรอบ · พิมพ์บอก AI ได้ว่า “wrap these two saves in a transaction” (เรื่องเต็มบท 111)
new_record? · persisted?
ถามสถานะของแฟ้ม: ยังอยู่ในมือ / อยู่ในลิ้นชักแล้ว · ใช้ตอนงงว่า “ตกลง save ไปหรือยัง” · ถาม senior ได้ว่า “ตรงนี้ object persisted แล้วหรือยัง” — คนทำ Rails ใช้คำนี้คุยกันจริง

🙋 เทียบให้เห็นภาพ — ถามคนดูแลสต็อกสามแบบ

find(99) = “เอาแฟ้มเลขที่ 99 มาให้ที” · คนดูแลสต็อกถือว่าคุณมั่นใจว่ามี — ไม่มีก็โวยวายเสียงดัง ให้รู้ว่ามีอะไรผิดปกติ
find_by(…) = “มีแฟ้มชื่อนี้ไหม ถ้ามีเอาแผ่นแรกมา” · ไม่มีก็ยักไหล่ตอบ “ไม่มีครับ” (nil)
where(…) = “เอาทุกแผ่นที่ตรงเงื่อนไขใส่ตะกร้ามา” · ไม่มีก็ยื่นตะกร้าเปล่ามาให้ ([])

ที่ไม่เหมือนกัน: คนจริงตอบ “ไม่มีครับ” แล้วเราก็รู้ทันที · แต่ nil ไม่ร้องเตือน ถ้าเราไม่เช็คแล้วเอาไปใช้ต่อ เช่น .title จะพังทีหลังด้วย NoMethodError ในบรรทัดที่ห่างจากต้นเหตุ (เจอจริงในภารกิจท้ายบท)

เทียบกับ Go: บท 27 เจอเรื่องเดียวกันใน GORM — db.First(&missing, 9999) คืน gorm.ErrRecordNotFound (ตรงกับ find) · ส่วน db.Where(…).Find(&list) ไม่ถือว่าเป็น error แค่ได้ slice ว่าง (ตรงกับ where) · ต่างกันที่ Go คืน error มาให้เช็ค ส่วน Ruby โยน error ออกมา (rescue บท 96)

🗣 ศัพท์ที่เพิ่งเรียนไป
SELECT · WHERE · ORDER BY · LIMIT
สี่คำที่จะเจอในทุก query อ่าน: ขอช่องไหน · เฉพาะแผ่นที่… · เรียงตาม… · เอามากี่แผ่น · ถาม senior ได้ว่า “query นี้มี WHERE ด้วยช่องไหน ช่องนั้นมี index ไหม” (index คือสารบัญของลิ้นชัก บท 109)
ActiveRecord::RecordNotFound
error ของ find เมื่อหาไม่เจอ · ใน controller Rails แปลงเป็นหน้า 404 ให้ในเว็บจริง · พิมพ์บอก AI ได้ว่า “use find_by and handle nil instead of find here” ถ้าการไม่เจอเป็นเรื่องปกติของหน้านั้น

หน้าค้นหาบทความ: ผู้ใช้พิมพ์ชื่อเรื่องมา ซึ่งอาจไม่มีอยู่จริง · ถ้าไม่เจอ อยากโชว์ข้อความ “ไม่พบบทความ” แทนที่หน้าเว็บจะพัง ควรใช้คำสั่งไหน?

ตัวเลือกที่ 2 ถูก — find_by ค้นตามช่องไหนก็ได้ ไม่เจอก็ตอบ nil เงียบ ๆ (ผลจริง: Post.find_by(title: "ไม่มีเรื่องนี้") → => nil) · เราเช็ค nil แล้วโชว์ข้อความเองได้

ตัวเลือกที่ 1 ผิด เพราะ find รับเลขที่แฟ้ม ไม่ใช่ชื่อเรื่อง · ไม่เจอมันระเบิดเป็น RecordNotFound ไม่เคยคืน nil (ผมลองส่งชื่อเรื่องเข้าไป ได้ RecordNotFound จริง) · ตัวเลือกที่ 3 ผิด เพราะ first รับได้แค่ “จำนวนแผ่น” เช่น first(3) ไม่รับเงื่อนไข · ลองแล้วได้ TypeError · ตัวเลือกที่ 4 ผิด เพราะ count คิดว่าคำที่ส่งไปเป็นชื่อช่อง · ลองแล้วพังเป็น PG::UndefinedColumn และต่อให้ไม่พังก็ได้แค่ตัวเลข ไม่ได้ตัวบทความไปโชว์

จุดที่ต้องจำ: มั่นใจว่ามีแน่ (เลขที่จากลิงก์) → find · อาจไม่มีก็ได้ → find_by แล้วเช็ค nil · อยากได้หลายแผ่น → where

  • &p · &list ฝั่ง Go = ส่ง pointer ของ struct/slice ให้ GORM เติมค่าลงไป · ฝั่ง Ruby ไม่มี เพราะ find คืนแฟ้มกลับมาให้เลย
  • "title = ?" ฝั่ง Go — ? คือช่องว่างที่ GORM เติมค่า x ให้ · ฝั่ง Ruby เขียนเป็น hash title: x แทน (SQL ที่ได้หน้าตาเดียวกัน)

ใน GORM ถ้าอยากใช้ชื่อตารางแปลก ๆ ต้องเขียน method TableName() · ใน Rails ถ้า class ชื่อ Post และตารางชื่อ posts (ตามกติกา) ต้องเขียนอะไรเพิ่มใน post.rb?

ตัวเลือกที่ 4 ถูก — ผลจริง: post.rb มีแค่ class Post < ApplicationRecord กับ end แต่ Post.table_name ได้ => "posts" · นี่คือ Convention over Configuration (ร้านแฟรนไชส์ ทุกสาขาวางของที่เดิม)

ตัวเลือกที่ 1 ผิด เพราะเขียนได้แต่ไม่จำเป็น — ใช้เฉพาะตอนชื่อตารางไม่ตามกติกา เช่นต่อกับฐานข้อมูลเก่าที่ตั้งชื่อไว้แล้ว · ตัวเลือกที่ 2 ผิด เพราะชื่อตารางเป็นเรื่องของทั้ง class ไม่ใช่ของแฟ้มแต่ละแผ่น · method แบบนี้จึงไม่ได้ช่วยให้ Post.table_name เปลี่ยน · ตัวเลือกที่ 3 ผิด เพราะบรรทัดนั้นบอกแค่ว่าสืบทอดจากใคร Ruby ไม่ได้มีที่ให้ใส่ชื่อตาราง

จุดที่ต้องจำ: ตั้งชื่อตามกติกา = ไม่ต้องเขียนอะไร · self.table_name มีไว้สำหรับกรณีพิเศษเท่านั้น (ทั้งสองภาษาคิดแบบเดียวกัน)

เพื่อนแปะ log มาให้ดูหนึ่งบรรทัด (ตารางของเพื่อนมีช่อง views = ยอดวิว ซึ่งเราจะเพิ่มกันในหัวข้อถัดไป): UPDATE "posts" SET "views" = 121, "updated_at" = '…' WHERE "posts"."id" = 1 — คำสั่ง Ruby ที่ทำให้เกิดบรรทัดนี้น่าจะเป็นอันไหน?

ตัวเลือกที่ 3 ถูก — UPDATE … SET "views" = 121 … WHERE "posts"."id" = 1 แปลว่า “แก้แฟ้มแผ่นเลขที่ 1 ให้ช่อง views เป็น 121” · ตรงกับ update บนแฟ้มเลขที่ 1

ตัวเลือกที่ 1 ผิด เพราะสร้างใหม่จะเห็น INSERT INTO ไม่ใช่ UPDATE · ตัวเลือกที่ 2 ผิด เพราะการหาจะเห็น SELECT … WHERE "posts"."views" = 121 · ไม่มีอะไรถูกแก้ · ตัวเลือกที่ 4 ผิด เพราะการทิ้งจะเห็น DELETE FROM และเลข 121 จะอยู่หลัง "id" =

จุดที่ต้องจำ: อ่านคำแรกของ SQL ก่อน — INSERT สร้าง · SELECT อ่าน · UPDATE แก้ · DELETE ลบ · แล้วดู WHERE ว่าโดนแผ่นไหน

ร้านเก็บใบสั่งช่างทุกใบไว้ในแฟ้ม (db/migrate/) ตั้งแต่วันเปิดร้าน · db:migrate:reset คือยกตู้เก่าทิ้ง ยกตู้เปล่ามาตั้ง แล้วยื่นแฟ้มใบสั่งทั้งหมดให้ช่างทำตามทีละใบ ได้ตู้หน้าตาเดียวกับตู้ล่าสุดเป๊ะ · db:seed คือเอาของตัวอย่างใส่ตู้ ให้มีอะไรหยิบลองเล่น

ที่ไม่เหมือนกัน: ช่างจริงรื้อตู้แล้ว แฟ้มเก่ายังกองอยู่ในกล่องให้ย้ายกลับ · db:migrate:reset ทิ้งข้อมูลทั้งหมดจริง ไม่มีกล่องพักของ — ทำได้สบายใจกับแอปฝึกในเครื่อง แต่ห้ามสั่งกับฐานข้อมูลที่มีข้อมูลจริง

🗣 ศัพท์ที่เพิ่งเรียนไป
seeds · db:seed
ข้อมูลตัวอย่างที่เขียนเป็นโค้ดไว้ใน db/seeds.rb ให้ทุกคนในทีมได้ข้อมูลชุดเดียวกันด้วยคำสั่งเดียว · ถาม senior ได้ว่า “seeds ของโปรเจกต์นี้รันซ้ำได้ไหม หรือต้อง reset ก่อน”
db:migrate:reset
ลบฐานข้อมูลทิ้ง สร้างใหม่ แล้วรัน migration ทุกไฟล์ตั้งแต่ไฟล์แรก · ใช้กับเครื่องตัวเองเท่านั้น (คำสั่งตระกูล reset อื่น ๆ บท 108) · พิมพ์บอก AI ได้ว่า “my dev database is messed up, how do I rebuild it from migrations and seeds”
belongs_to · foreign key
belongs_to :user = แฟ้มนี้เป็นของผู้ใช้หนึ่งคน · ช่อง user_id ที่ชี้ไปหาแฟ้มในลิ้นชักอื่นเรียกว่า foreign key (บท 115) · ถาม senior ได้ว่า “belongs_to ตัวนี้ควรเป็น optional ไหม” (optional = ยอมให้ไม่มีเจ้าของได้) — เจอ User must exist เมื่อไหร่ ให้นึกถึงคำนี้

หลังเพิ่ม belongs_to :user ใน Post แล้ว · post.save ตอบ => false และ full_messages ได้ ["User must exist"] · ข้อไหนถูก?

ตัวเลือกที่ 1 ถูก — ผลจริงหลัง post.save ไม่มีบรรทัด INSERT เลย · คนดูแลสต็อกตรวจแล้วไม่รับตั้งแต่ก่อนใส่ลิ้นชัก · post.id จึงยังเป็น nil

ตัวเลือกที่ 2 ผิด เพราะ false แปลว่าไม่ได้เก็บ และช่อง user_id ถูกตั้งห้ามว่างไว้ด้วย · ตัวเลือกที่ 3 ผิด เพราะไม่มี INSERT ถูกส่งไปให้ตู้ปฏิเสธเลย — ROLLBACK ที่อาจเห็นคือ Rails ยกเลิกกรอบงานเองหลังตรวจแฟ้มไม่ผ่าน ไม่ใช่ตู้ปฏิเสธ · ตัวเลือกที่ 4 ผิด เพราะ console ยังใช้ได้ปกติ ใส่ post.user = … แล้ว save ใหม่ก็ได้ true

จุดที่ต้องจำ: save ตอบ false = ไม่ได้เก็บ · ถามเหตุผลด้วย errors.full_messages · ดู log ว่ามี INSERT หรือเปล่า
