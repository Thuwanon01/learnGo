Active Record คืออะไร — แฟ้มที่เดินเข้าลิ้นชักเองได้

~20 นาที (รวมภารกิจ) · บทแรกของ Day 2 · ควรผ่าน บทเรียน 99 (Post กับ posts) และ บทเรียน 104 (console) มาก่อน · มีเทียบกับ GORM จาก บทเรียน 27

Day 1 เราทำเว็บที่ข้อความทุกตัวเขียนตายตัวในโค้ด · Day 2 ทั้งวันคือเรื่องข้อมูลที่เก็บไว้จริง
อ่านจบบทนี้ คุณจะตอบได้ว่าทำไม class Post < ApplicationRecord ที่ว่างเปล่าถึงรู้จักช่อง title · อ่านโค้ด Rails ที่บันทึกบทความแล้วเทียบกับ GORM ได้ทีละบรรทัด · และเข้าใจว่า "Active Record" คือวิธีคิดแบบหนึ่ง ที่มีทั้งข้อดีและราคาที่ต้องจ่าย

🔁 ทวนก่อนเริ่ม — คำพวกนี้จะโผล่ในบทนี้

  • bin/rails console (บท 104) — ครัวทดลองหลังร้าน พิมพ์คำสั่ง Ruby ทีละบรรทัดโดยแอปทั้งตัวโหลดไว้แล้ว

🗂 ข้อมูลตัวอย่าง: บทนี้ใช้แค่ตาราง posts ที่มีช่อง title กับ body · สร้างด้วยคำสั่งเดียวกับบท 99 (bin/rails generate model Post title:string body:text แล้ว bin/rails db:migrate) · ถ้าในเครื่องคุณยังไม่มี ภารกิจท้ายบทพาสร้างทีละขั้น — อ่านเนื้อหาตามไปก่อนได้เลย

1 · ทำไมทั้งวันพูดเรื่องข้อมูล

สไลด์หน้าแรกของ Day 2 เปิดด้วยประโยคนี้: "แอปพังเพราะโค้ดผิด แก้ 10 นาที · แอปพังเพราะข้อมูลผิด แก้เป็นอาทิตย์"

โค้ดผิดแก้ง่าย เพราะแก้ไฟล์เดียวแล้ว deploy ใหม่ (เอาโค้ดใหม่ขึ้นเครื่องที่ให้บริการจริง) ทุกคนได้โค้ดที่ถูกทันที · แต่ข้อมูลผิดถูกเก็บลงไปแล้ว อาจเป็นพันรายการ และบางรายการมีคนใช้ต่อไปแล้วด้วย
เช่น ระบบยอมให้สมัครด้วยอีเมลซ้ำมาหลายเดือน · วันที่รู้ตัว คุณต้องไล่ดูทีละคู่ว่าบัญชีไหนของจริง แล้วรวมบทความของสองบัญชีเข้าด้วยกัน

🍲 เทียบให้เห็นภาพ — สูตรผิด กับ ของเสียเข้าตู้

โค้ดผิด = สูตรอาหารพิมพ์ผิด ใส่เกลือ 5 ช้อน · แก้สูตรแล้ว จานถัดไปก็ถูก จานที่เสิร์ฟไปแล้วก็จบไป
ข้อมูลผิด = รับวัตถุดิบเสียเข้าห้องเก็บของไปแล้ว ปนอยู่กับของดีหลายร้อยกล่อง · ต้องไล่เปิดทีละกล่อง และบางกล่องถูกเอาไปปรุงแล้วด้วย

ที่ไม่เหมือนกัน: ของเสียในร้านจริงยังดมหรือดูออก · ข้อมูลผิดใน database หน้าตาปกติทุกอย่าง — อีเมลซ้ำสองแถวก็เป็นแค่ข้อความธรรมดาสองบรรทัด ไม่มีอะไรเตือน จนวันที่ลูกค้าล็อกอินแล้วเข้าผิดบัญชี

ทั้ง Day 2 จึงพูดเรื่องเดียว: ทำยังไงให้ข้อมูลที่เข้าห้องเก็บของถูกตั้งแต่แรก และดึงออกมาใช้ได้เร็ว · บทนี้เริ่มจากรู้จัก "คนดูแลสต็อก" ของ Rails ก่อน ว่าเขาทำงานยังไง

3 · ตู้แฟ้มของร้าน — database · ตาราง · แถว · คอลัมน์ · SQL

ก่อนไปต่อ ต้องมีคำพื้นฐานห้าคำ · database คือโปรแกรมที่เก็บข้อมูลให้อยู่ถาวร ปิดแอปแล้วข้อมูลไม่หาย · แอปของเราใช้ PostgreSQL ตัวเดียวกับที่เคยใช้กับ Go

ข้างใน database แบ่งเป็นตาราง (table) ตามชนิดของข้อมูล เช่นตาราง posts เก็บบทความ · ข้อมูลหนึ่งชิ้นคือแถว (row) หนึ่งแถว · แต่ละแถวมีช่องเหมือนกันทุกแถว เรียกว่าคอลัมน์ (column)

นี่คือหน้าตาตาราง posts หลังบันทึกบทความไปสองชิ้น (ตัวอย่างจากเครื่องตรวจ · ตัดเวลาให้สั้น):

2ส้มตำปูปลาร้า(ว่าง — NULL)2026-11-04 11:462026-11-04 11:46

  • id = เลขประจำแถวที่ database แจกให้เอง ไม่ซ้ำกัน · created_at / updated_at = เวลาสร้าง / แก้ล่าสุด (มาจาก t.timestamps ในบท 99)
  • แถวที่ 2 ไม่ได้ใส่ body · ช่องนั้นจึงว่าง · database เรียกค่าว่างแบบนี้ว่า NULL (ฝั่ง Ruby เห็นเป็น nil)

เราไม่ได้เปิดตารางด้วยมือ · ทุกครั้งที่อยากได้ข้อมูล ต้องสั่งเป็นภาษาเฉพาะของ database ชื่อ SQL · เช่นคำสั่งนี้ (Rails "ยิง" คือส่งคำสั่งนี้ไปให้ database เองตอนเราพิมพ์ Post.count — เดี๋ยวเห็นของจริงในหัวข้อ 4): 

SELECT COUNT(*) FROM "posts"
  • SELECT = "ขอดู / ขอหยิบ" · เป็นคำขึ้นต้นของคำสั่งที่อ่านข้อมูล ไม่ได้แก้อะไร
  • COUNT(*) = "นับจำนวนแถว" (* = ทุกแถว ไม่เลือกคอลัมน์)
  • FROM "posts" = "จากตาราง posts" · เครื่องหมาย " " ครอบ = บอก database ว่านี่คือชื่อตาราง ไม่ใช่คำสั่ง
  • รวมเป็นภาษาคน: "นับว่าในลิ้นชัก posts มีแฟ้มกี่แผ่น"
🗄 เทียบให้เห็นภาพ — ตู้เก็บแฟ้มในห้องเก็บของ

database = ตู้เก็บแฟ้มทั้งตู้ · ตาราง posts = ลิ้นชักที่ติดป้าย "posts" · แถว = แฟ้มหนึ่งแผ่น (บทความหนึ่งชิ้น) · คอลัมน์ = ช่องที่พิมพ์ไว้บนแบบฟอร์มของแฟ้ม (ช่องหัวข้อ · ช่องเนื้อหา) · SQL = ภาษาที่คนดูแลสต็อกใช้สั่งตู้ "หยิบแผ่นที่ …" "นับให้หน่อย"

ที่ไม่เหมือนกัน: ลิ้นชักจริงใส่กระดาษหน้าตาไหนก็ได้ · แต่ตารางบังคับให้ทุกแถวมีช่องชุดเดียวกันเป๊ะ — บทความที่ไม่มีเนื้อหาก็ยังมีช่อง body แค่ช่องว่าง (NULL) · และไม่มีใครเปิดลิ้นชักด้วยมือได้ ทุกอย่างต้องผ่านคำสั่ง SQL

🗣 ศัพท์ที่เพิ่งเรียนไป
database · table · row · column
ตู้ · ลิ้นชัก · แฟ้มหนึ่งแผ่น · ช่องบนแฟ้ม · ในทีมมักเรียก row ว่า "record" ด้วย · ถาม senior ได้ว่า "ตาราง posts ตอนนี้มีกี่ row แล้ว และมี column อะไรบ้าง" — คำถามแรกที่ควรถามเวลาเข้าโปรเจกต์ใหม่
SQL · query
SQL = ภาษาที่ใช้สั่ง database (อ่านว่า เอส-คิว-แอล หรือ ซีเควล) · query = คำสั่ง SQL หนึ่งคำสั่ง · พิมพ์บอก AI ได้ว่า "explain this SQL line by line in plain words" แล้วแปะบรรทัดจาก log ไปทั้งบรรทัด

ค่าว่างในช่องของ database · ฝั่ง Ruby เห็นเป็น nil · ถาม senior ได้ว่า "ช่องนี้ปล่อยให้ NULL ได้ไหม" — เป็นคำถามสำคัญมากในบท 111

4 · คำถามจากบท 99 — class ว่างเปล่า แต่รู้จัก title

บท 99 เราเห็นว่า app/models/post.rb มีแค่สองบรรทัด แต่ post.title ใช้ได้ · คำตอบสั้น ๆ คือ Post ไปถามตาราง posts เองว่ามีคอลัมน์อะไร แล้วสร้าง method ตามนั้น · วันนี้ดูให้ชัดขึ้นโดยวางเทียบกับ GORM ที่เคยเขียนในบท 27 (โค้ดจากสไลด์หน้า 5 ปรับให้ตรงกับตาราง posts ของเรา)

Go + GORM

// 1) ต้องประกาศทุกช่องเอง
type Post struct {
	ID        uint
	Title     string
	Body      string
	CreatedAt time.Time
	UpdatedAt time.Time
}

// 2) สร้าง 3) ยื่นให้ db บันทึก 4) เช็ค err เอง
p := Post{Title: "ต้มยำกุ้งน้ำข้น", Body: "เปรี้ยว เผ็ด หอมสมุนไพร"}
if err := db.Create(&p).Error; err != nil {
	return err
}

Ruby + Active Record

# 1) ไม่ประกาศช่องเลย
class Post < ApplicationRecord
end

# 2) สร้าง 3) สั่งตัวมันเองให้บันทึก
post = Post.new(title: "ต้มยำกุ้งน้ำข้น", body: "เปรี้ยว เผ็ด หอมสมุนไพร")
post.save!

ฝั่ง Go ตัดมาจากไฟล์ที่มี package main + import ครบ และ go build ผ่าน ผมรันกับ PostgreSQL ตัวเดียวกันจริง · สไลด์ตั้งชื่อตัวแปรว่า p · ผมใช้ post ฝั่ง Ruby เพราะ p เป็นชื่อคำสั่งพิมพ์ค่าที่เราใช้มาตั้งแต่บท 93 อ่านแล้วจะงง

เทียบทีละงาน:

งานGo + GORMRails
บอกว่าบทความมีช่องอะไรเขียนเองใน struct ทุกช่องไม่เขียน · Rails ไปถามตาราง posts ตอนรัน
สร้างบทความหนึ่งชิ้น (ยังไม่บันทึก)p := Post{Title: …}post = Post.new(title: …)
บันทึกdb.Create(&p) — ยื่นบทความให้ db เป็นคนบันทึก (&p = ส่งตัวจริงไป GORM จึงเติม ID กลับมาให้ได้)post.save! — สั่งบทความตัวเองให้บันทึก
ถ้าบันทึกไม่ได้ได้ .Error กลับมา ต้องเขียน if err != nil เองsave! โยน error ออกมาเอง (! = "ถ้าทำไม่ได้ให้ระเบิด" · แบบไม่มี ! รอบท 110)

มาดูแถวแรกด้วยตาตัวเอง (บท 97 เคยลองแบบเดียวกันมาแล้ว) · เปิด bin/rails console แล้วถามว่า Post รู้จักช่องอะไรบ้าง:

wongnok-blog(dev):001> Post.column_names
=> ["id", "title", "body", "created_at", "updated_at"]

column_names = "บอกชื่อคอลัมน์ทั้งหมดของตารางเรา" · ได้กลับมาเป็น Array ของข้อความ · ไม่มีชื่อไหนเขียนอยู่ใน post.rb เลย · ทั้งห้าชื่อมาจากตาราง posts ใน database ล้วน ๆ

5 · Active Record คือชื่อ "วิธีคิด" ไม่ใช่แค่ชื่อของใน Rails

คำว่า Active Record ที่เห็นในชื่อ ActiveRecord::Base จริง ๆ เป็นชื่อ pattern — แบบแผนการออกแบบที่มีคนตั้งชื่อไว้ให้คุยกันรู้เรื่อง · Rails Guides เล่าว่า Martin Fowler เป็นคนอธิบาย pattern นี้ไว้ในหนังสือ Patterns of Enterprise Application Architecture (สไลด์หน้า 6 อ้างว่าหนังสือออกปี 2002 ก่อน Rails 2 ปี)

📄 เทียบให้เห็นภาพ — แฟ้มที่เดินเข้าลิ้นชักเองได้

ในร้าน Rails คนดูแลสต็อกฝังอยู่ในแฟ้มทุกแผ่น · แฟ้มบทความหนึ่งแผ่นรู้ว่าตัวเองมีช่องอะไร · สั่ง post.save! แฟ้มก็เดินเข้าลิ้นชัก posts เอง · สั่ง post.destroy ก็เดินออกไปทิ้งเอง · ไม่ต้องมีใครถือไปให้

ที่ไม่เหมือนกัน: แฟ้มไม่ได้ "เดิน" ไปจริง — save! แค่แปลเป็นคำสั่ง SQL (INSERT INTO …) แล้วยื่นให้ PostgreSQL ทำ · และกระดาษจริงเป็นแฟ้มได้แม้ไม่มีตู้ · แต่ Post ต้องมีตู้ก่อนถึงจะสร้างแฟ้มเปล่าได้ เพราะต้องไปดูช่องจากลิ้นชัก (หัวข้อ 7 พิสูจน์ให้ดู)

7 · ราคาที่ต้องจ่าย

ข้อดีของ Active Record เห็นแล้ว: เขียนสั้น เริ่มเร็ว ของทุกอย่างอยู่ที่เดียว · สไลด์หน้า 6 บอกราคาที่ต้องจ่ายไว้สามข้อ · แปลเป็นภาษาคน:

  • model อ้วนขึ้นเรื่อย ๆ — กฎตรวจข้อมูล ขั้นตอนอัตโนมัติ วิธีค้นหา ทุกอย่างมากองที่ post.rb · โปรเจกต์อายุสองปี ไฟล์นี้อาจยาวหลายร้อยบรรทัด (บท 112 คุยว่าจะย้ายไปไว้ไหน)
  • ทดสอบยากกว่า — แค่สร้างแฟ้มเปล่าก็ต้องมี database แล้ว (ผลจริงข้างล่าง)
  • ย้ายไปใช้ database แบบอื่นยากกว่า — เพราะโค้ดทั้งแอปเรียก Active Record ตรง ๆ ไม่มีคนกลางคั่น

8 · ApplicationRecord และการเดาชื่อตาราง

ทวนบท 99 สั้น ๆ: Post < ApplicationRecord < ActiveRecord::Base (เขียนย่อให้เห็นว่าใครสืบทอดจากใคร ไม่ใช่โค้ดที่พิมพ์ได้จริง) · ActiveRecord::Base คือของจาก Rails ที่คุยกับ database ได้ทุกอย่าง · ApplicationRecord คือแม่แบบกลางของแอปเรา ไว้ใส่ของที่ model ทุกตัวต้องมี (ตอนนี้ยังว่าง) · Post จึงได้ความสามารถทั้งหมดมาฟรีผ่านการสืบทอด

เทียบกับ Go: GORM ก็เดาชื่อตารางแบบเดียวกัน (บท 27: User → users) · และถ้าชื่อไม่ตามกฎ ให้เขียน method TableName() (ผมรันแล้ว ได้แถวจากตาราง posts จริง) · GORM จะเรียก method นี้ถามเองว่า "Article ใช้ตารางไหน":

	Title string

func (Article) TableName() string { return "posts" }

  self.table_name = "posts"
end

ร้านแฟรนไชส์ (Convention over Configuration — บท 90) ตั้งกฎว่า แฟ้มชื่ออะไร ลิ้นชักติดป้ายชื่อนั้นเป็นพหูพจน์ · คนดูแลสต็อกของแฟ้ม Post จึงเดินไปลิ้นชัก "posts" ได้เลยโดยไม่ต้องถาม · ถ้าร้านเราซื้อตู้เก่ามาที่ติดป้ายไว้แล้ว ก็แปะโน้ตบอกคนดูแลสต็อกทีเดียว (self.table_name)

ที่ไม่เหมือนกัน: คนจริงหาลิ้นชักไม่เจอจะเดินกลับมาถาม · Rails ไม่ตรวจล่วงหน้าเลย — เปิดแอปได้ปกติ แล้วไปพังตอนมีคนใช้ Article ครั้งแรก · และ Rails ไม่ได้รู้ความหมายของคำ — Article กับ Post แปลว่าบทความเหมือนกัน แต่สำหรับ Rails เป็นแค่ตัวอักษรคนละชุด

2. โค้ดแบบไหนตรงกับ Active Record pattern?

ตัวเลือกที่ 4 ถูก · แก่นของ Active Record คือ object หนึ่งตัว = หนึ่งแถว และรู้วิธีบันทึกตัวเอง (แฟ้มเดินเข้าลิ้นชักเอง)

ตัวเลือกที่ 1 ผิด — นั่นคือ Data Mapper (มีพนักงานคลังแยก) · ตัวเลือกที่ 2 ผิด — นั่นคือไม่ใช้ ORM เลย เขียน SQL ด้วยมือ · ตัวเลือกที่ 3 ผิด — ไม่มี database และไม่มี object ที่รู้วิธีเก็บตัวเอง

จุดที่ต้องจำ: แยกสองสายด้วยคำถามเดียว "ใครถือคำสั่ง save" · ตัวข้อมูลเอง = Active Record · คนกลาง = Data Mapper
