Migration ที่ไม่ทำร้านปิด — lock และ expand → migrate → contract

~25 นาที (ยาวกว่าบทอื่นนิดหน่อย เพราะมีของให้ลองสองหน้าต่าง) · ควรผ่าน บทเรียน 107 (console) และ บทเรียน 108 (migration พื้นฐาน) มาก่อน

ในบท 108 migration ของเรารันเสร็จใน 0.003 วินาที เพราะตารางมีแค่ 6 แถว และไม่มีใครใช้เว็บอยู่
บทนี้เล่าเรื่องของร้านที่เปิดอยู่จริง มีลูกค้าเต็มร้าน — migration หน้าตาธรรมดาบรรทัดเดียวอาจทำให้ทั้งเว็บค้างได้
อ่านจบแล้วคุณจะ: รู้ว่า lock กับ index คืออะไร (เห็นของจริงในเครื่องตัวเอง) · สร้าง index แบบไม่ทำให้ใครต้องรอ · และเปลี่ยนชื่อคอลัมน์ได้โดยไม่ต้องปิดเว็บ ด้วยท่า 3 เฟสที่ทีมจริงใช้กัน

🔁 ทวนก่อนเริ่ม — คำจากบทก่อน ๆ ที่บทนี้ใช้

  • ตาราง · แถว · คอลัมน์ (บท 106) — ลิ้นชัก posts · แฟ้มหนึ่งแผ่น · ช่องบนแฟ้ม
  • migration (บท 108) — ใบสั่งช่างมาต่อเติมตู้ (เพิ่มลิ้นชัก เพิ่มช่อง) · รันด้วย bin/rails db:migrate · รื้องานใบล่าสุดด้วย bin/rails db:rollback
  • db/schema.rb (บท 108) — แปลนตู้ฉบับล่าสุด Rails เขียนให้เองหลัง migrate
  • console (บท 104, 107) — ครัวทดลองหลังร้าน · ทุกคำสั่งที่ไปถึงตู้ จะมีบรรทัด SQL โผล่ให้ดู พร้อมเวลาเป็น ms (มิลลิวินาที = 1/1000 วินาที)
  • SQL (บท 106) — ภาษาที่คนดูแลสต็อกใช้สั่งตู้ · Active Record แปลคำสั่ง Ruby เป็น SQL ให้

🧰 ตรวจด้วย Ruby 4.0.9 · Rails 8.1.4 · PostgreSQL 17 (สไลด์ใช้ Ruby 4.0.6 · Rails 8.1.3 — รุ่นแก้บั๊กในสายเดียวกัน ใช้แทนกันได้)

📦 ตัวอย่างในบทนี้ใช้ตาราง users/posts/comments และข้อมูลตัวอย่าง (seeds) ชุดเดียวกับบท 107 · หัวข้อ index จะเติมบทความทดลอง 200,000 แผ่นให้ตารางใหญ่พอเห็นผล (วิธีลบทิ้งอยู่ในกล่อง "เก็บกวาดก่อนไปบทหน้า" ก่อนภารกิจ)

ผลทุกก้อนรันจริงแล้วก็อปมา · ย่อ path ยาวเป็น ~/wongnok_blog และตัดส่วนที่ไม่เกี่ยวเป็น … · เวลา (ms / วินาที) · เลข id · เลขเวลาหน้าชื่อไฟล์ migration ของคุณจะไม่ตรงกับในบท · ท้ายบรรทัด SQL ทุกบรรทัดจะมี /*application='WongnokBlog'*/ — เป็นแค่ป้ายบอกว่ามาจากแอปไหน ไม่ต้องสนใจ

ร้านที่ไม่เคยปิด — production, deploy และ downtime

เว็บที่คุณรันในเครื่องตัวเอง (โหมด development) มีลูกค้าคนเดียวคือคุณ · ส่วนเว็บจริงที่คนอื่นใช้ เรียกว่า production
production ไม่เคยว่าง — ตีสองก็ยังมีคนเปิดอ่านบทความ มีคนเขียนคอมเมนต์อยู่

เวลาเราเขียนโค้ดใหม่เสร็จ แล้วเอาขึ้น production เรียกว่า deploy · ขั้นตอนหลัก ๆ มีสามจังหวะ:

  1. เอาโค้ดใหม่ขึ้นเครื่อง server
  2. รัน bin/rails db:migrate กับ database ตัวจริง (ตู้จริงของร้าน)
  3. เริ่มแอปใหม่ (restart) ให้หันมาใช้โค้ดใหม่

ระหว่างนั้นลูกค้ายังเข้าเว็บอยู่ตลอด · ถ้ามีช่วงที่เว็บใช้ไม่ได้ เรียกว่า downtime (ช่วงร้านปิด) · บทนี้ทั้งบทคือ "ทำยังไงให้ downtime เป็นศูนย์"

สไลด์ยกตัวอย่างว่า: ตาราง posts มี 50 ล้านแถว · มีคน 3,000 คนออนไลน์ · migration ตัวหนึ่งรันนาน 40 วินาที — คำถามคือ 40 วินาทีนั้น 3,000 คนเจออะไร? ตอบได้ตอนจบหัวข้อ lock

🏪 เทียบให้เห็นภาพ — ต่อเติมตู้ระหว่างร้านเปิด

ในเครื่องเรา เหมือนเรียกช่างมาต่อเติมตู้ตอนร้านปิด ไม่มีใครเดือดร้อน · production คือร้านที่เปิด 24 ชั่วโมง ช่างต้องทำงานตอนที่พนักงานยังวิ่งหยิบแฟ้มจากตู้อยู่ตลอด
deploy = วันที่ช่างมาตามใบสั่ง แล้วพนักงานทั้งร้านเปลี่ยนไปใช้คู่มือฉบับใหม่ · downtime = ช่วงที่ร้านต้องแขวนป้าย "ปิดปรับปรุง"

ที่ไม่เหมือนกัน: ช่างในร้านจริงมองเห็นว่ามีพนักงานยืนรอ แล้วรีบทำ หรือหลบให้ก่อนได้ · แต่ migration มองไม่เห็นใครเลย มันทำงานของมันไปจนเสร็จ ส่วนคนที่รอก็ไม่ได้รับข้อความอะไร แค่เห็นหน้าเว็บหมุนค้าง

เทียบกับ Go: ปัญหานี้ไม่ใช่ของ Rails อย่างเดียว · ตอนทำ Go คุณ deploy ด้วยการรัน goose up แล้ว restart โปรแกรม (บท 31) — เจอเรื่องเดียวกันทุกข้อ เพราะต้นเหตุอยู่ที่ Postgres (ชื่อเล่นของ PostgreSQL = โปรแกรม database ตัวที่ทั้งแอป Go และแอป Rails ของเราใช้) ไม่ใช่ภาษา

🗣 ศัพท์ที่เพิ่งเรียนไป
production (prod)
ระบบจริงที่ผู้ใช้ใช้อยู่ · ตรงข้ามกับ development (เครื่องเรา) · ถาม senior ได้ว่า “ตาราง posts บน production มีกี่แถว migration นี้รันนานแค่ไหน”
deploy
การเอาโค้ดเวอร์ชันใหม่ขึ้น production · ใน Rails มักรวมการรัน migration ไว้ในขั้นตอนนี้ด้วย · ถามได้ว่า “ตอน deploy ทีมเรารัน db:migrate ก่อนหรือหลัง restart แอป”
downtime · zero-downtime deploy
downtime = ช่วงที่เว็บใช้ไม่ได้ · zero-downtime = deploy โดยไม่มีช่วงนั้นเลย · พิมพ์บอก AI ได้ว่า “write this migration for zero-downtime deploy on a large Postgres table”

index — ป้ายแท็บเรียงตัวอักษรในลิ้นชัก

ก่อนเข้าเรื่อง lock ต้องรู้จัก index ก่อน เพราะตัวอย่างของเราจะใช้มัน
ปกติเวลาสั่ง "หาบทความชื่อ X" ตู้ต้องหยิบแฟ้มทีละแผ่นจากแผ่นแรกจนแผ่นสุดท้ายแล้วดูว่าชื่อตรงไหม · index คือรายการเสริมที่ตู้ทำเก็บไว้ เรียงชื่อเป็นลำดับพร้อมบอกว่าแผ่นนั้นอยู่ตรงไหน — หาเจอเร็วโดยไม่ต้องไล่ทุกแผ่น
(บท 108 เรียกมันว่า "สารบัญ" ตอนเห็นบรรทัด t.index ใน schema.rb — เป็นของชิ้นเดียวกัน บทนี้ขอเรียกว่าป้ายแท็บ)

📇 เทียบให้เห็นภาพ — ป้ายแท็บ ก ข ค ในลิ้นชักแฟ้ม

ลิ้นชักที่ไม่มีป้ายแท็บ: จะหาแฟ้ม "ผัดกะเพรา" ต้องเปิดดูทีละแผ่น 200,000 แผ่น · ลิ้นชักที่ติดป้ายแท็บเรียงตัวอักษรไว้: เปิดไปที่แท็บ "ผ" แล้วหาต่อในกองเล็ก ๆ เจอในไม่กี่วินาที

ที่ไม่เหมือนกัน: ป้ายแท็บจริงติดครั้งเดียวจบ · แต่ index ใน database ต้องอัปเดตทุกครั้งที่มีแฟ้มใหม่เข้ามา — เก็บแฟ้มช้าลงนิดหนึ่ง และกินพื้นที่เพิ่ม · และ index ช่วยเฉพาะการหาด้วยช่องที่ติดป้ายไว้ (ติดป้ายตามชื่อเรื่อง ก็ไม่ช่วยหาตามยอดวิว)

เทียบกับ Go: ใน บท 31 คุณเขียน SQL CREATE INDEX … เองในไฟล์ goose · และใน บท 27 เห็นป้าย `gorm:"index"` ติดท้าย field ของ struct · ฝั่ง Rails เขียนเป็น Ruby บรรทัดเดียว add_index แล้ว Rails แปลเป็น CREATE INDEX ให้

เตรียมลิ้นชักใหญ่ 200,000 แผ่น

ตาราง posts ของเรามีแค่ 6 แถว เร็วอยู่แล้วไม่ว่าจะทำอะไร · ต้องเติมบทความทดลองให้เยอะก่อน — เปิด bin/rails console แล้ววางโค้ดนี้ทั้งก้อน: 

ActiveRecord::Base.connection.execute(<<~SQL)
  INSERT INTO posts (title, body, user_id, created_at, updated_at)
  SELECT 'บทความทดลอง ' || n, 'เนื้อหาทดลอง', #{User.first.id}, now(), now()
  FROM generate_series(1, 200000) AS n
SQL
  • ActiveRecord::Base.connection.execute(…) — "ส่ง SQL นี้ไปให้ตู้ตรง ๆ ไม่ต้องแปลจาก Ruby" · ใช้เพราะเร็วกว่าสร้างทีละแถวด้วย Post.create! สองแสนรอบ
  • <<~SQL … SQL — เขียนข้อความยาวหลายบรรทัด (heredoc) เริ่มที่ <<~SQL จบที่บรรทัด SQL · ชื่อ SQL ตั้งเองได้
  • INSERT INTO posts (title, …) — SQL แปลว่า "ใส่แฟ้มใหม่ลงลิ้นชัก posts โดยกรอกช่อง title, body, user_id, created_at, updated_at"
  • SELECT … FROM generate_series(1, 200000) AS n — "สร้างตัวเลข 1 ถึง 200,000 เรียกแต่ละตัวว่า n แล้วทำแฟ้มหนึ่งแผ่นต่อหนึ่งตัวเลข" · 'บทความทดลอง ' || n คือเอาข้อความต่อกับตัวเลข ได้ชื่อ "บทความทดลอง 1" ถึง "บทความทดลอง 200000" · now() = เวลาตอนนี้ (ใส่ช่อง created_at / updated_at)
  • #{User.first.id} — ใส่ id ของผู้ใช้คนแรก เพราะทุกบทความต้องมีเจ้าของ (คอลัมน์ user_id ห้ามว่าง)

ติดป้ายแท็บด้วย migration

สร้างใบสั่งช่างใบใหม่ (generator ของบท 108):

bin/rails generate migration AddIndexToPostsTitle

Rails สร้างไฟล์ว่าง ๆ ให้ (เลขหน้าชื่อไฟล์ของคุณจะต่าง) · เปิดไฟล์แล้วเติมบรรทัด add_index:

# db/migrate/20261104115002_add_index_to_posts_title.rb
class AddIndexToPostsTitle < ActiveRecord::Migration[8.1]
  def change
    add_index :posts, :title   # ติดป้ายแท็บในลิ้นชัก posts เรียงตามช่อง title
  end
end

🗣 ศัพท์ที่เพิ่งเรียนไป
lock (table lock)
การที่ database กันไม่ให้คนอื่นทำบางอย่างกับตารางชั่วคราว · มีหลายระดับ เช่น "blocks writes" (ห้ามเขียน อ่านได้) กับ "blocks reads and writes" (ห้ามทั้งคู่) · ถาม senior ได้ว่า “migration นี้ lock ตารางระดับไหน นานเท่าไหร่”
DDL transaction
DDL = คำสั่ง SQL กลุ่มที่เปลี่ยนโครงตู้ ไม่ใช่ข้อมูลในแฟ้ม: CREATE (สร้าง) · ALTER (ดัดแปลง) · DROP (รื้อทิ้ง) — ตาราง คอลัมน์ หรือ index · Rails ห่อ migration ทั้งไฟล์ด้วย transaction เดียว พังกลางทางย้อนคืนหมด แต่ lock ค้างจนจบไฟล์ · พิมพ์บอก AI ได้ว่า “does this Rails migration run inside a DDL transaction, and how long will it hold the lock?”

ติดป้ายแท็บแบบไม่ปิดลิ้นชัก — algorithm: :concurrently

Postgres มีวิธีสร้าง index อีกแบบ ชื่อ CONCURRENTLY (แปลว่า "ไปพร้อม ๆ กัน") — ช่างทำงานช้ากว่าเดิมนิดหน่อย แต่ไม่ห้ามใครเก็บแฟ้ม · ใน Rails สั่งด้วย algorithm: :concurrently
ลอง rollback ตัวเดิมก่อน (bin/rails db:rollback) แล้วแก้ไฟล์ db/migrate/…_add_index_to_posts_title.rb เป็นแบบนี้: 

class AddIndexToPostsTitle < ActiveRecord::Migration[8.1]
  def change
    add_index :posts, :title, algorithm: :concurrently
  end
end

รัน bin/rails db:migrate — พังทันที (ผลจริง ตัดส่วนท้าย):

  • CREATE INDEX CONCURRENTLY cannot run inside a transaction block — Postgres บอกว่า "การสร้าง index แบบไม่ปิดลิ้นชัก ห้ามอยู่ใน transaction"
  • แต่เมื่อกี้เพิ่งเรียนว่า Rails ห่อ migration ทุกไฟล์ด้วย transaction ให้เองเสมอ → ชนกัน
  • .rb:3 — บรรทัดที่ 3 ของไฟล์ คือบรรทัด add_index · this and all later migrations canceled = ไฟล์นี้และไฟล์ที่ต่อจากนี้ไม่ถูกรัน (ตู้ไม่เปลี่ยนอะไร)

ทางแก้คือบอก Rails ว่า "ไฟล์นี้ไม่ต้องห่อด้วย transaction" ด้วยบรรทัด disable_ddl_transaction!:

class AddIndexToPostsTitle < ActiveRecord::Migration[8.1]
  disable_ddl_transaction!   # ไฟล์นี้ไม่ต้องห่อด้วย transaction

  def change
    add_index :posts, :title, algorithm: :concurrently
  end
end

เทียบกับ Go: คุณเจอ error ประโยคเดียวกันเป๊ะมาแล้วใน บท 31 · ฝั่ง goose แก้ด้วยการใส่ -- +goose NO TRANSACTION บรรทัดแรกของไฟล์ · ฝั่ง Rails คือ disable_ddl_transaction! — คนละภาษา แต่คุยกับ Postgres ตัวเดียวกัน

คำถามเดียวที่ต้องถามทุกครั้ง: "แตะกี่แถว และระหว่างนั้นใครต้องรอ"

สไลด์สรุปหลักไว้ประโยคเดียว: ก่อนรัน migration บนตารางใหญ่ ให้ถามว่าคำสั่งนี้ต้องแตะแฟ้มกี่แผ่น และระหว่างนั้นใครใช้ลิ้นชักนี้ไม่ได้
ตารางนี้ย่อ 5 ท่าจากสไลด์หน้า 16 · ไม่ต้องจำ แค่ดูว่าแต่ละท่าตอบคำถามนี้ยังไง · เวลาในวงเล็บคือผลจริงบนเครื่องผม ตาราง posts 200,000 แถว (ตาราง 50 ล้านแถวใหญ่กว่า 250 เท่า)

อยากทำอะไรท่าตรง ๆแตะกี่แผ่น · ใครรอท่าที่ปลอดภัยกว่า
สร้าง indexadd_indexอ่านทุกแผ่นมาเรียง · ห้ามเขียนจนเสร็จ (~15.7 วินาที)algorithm: :concurrently + disable_ddl_transaction!
เปลี่ยนชนิดข้อมูลchange_column :posts, :views, :bigintเขียนใหม่ทุกแผ่น · ห้ามทั้งอ่านและเขียน (~0.16 วินาที · แต่ถ้ามีป้ายแท็บติดอยู่ ต้องทำป้ายใหม่ด้วย นานขึ้นเป็น ~16 วินาที)คอลัมน์ใหม่ + ย้ายข้อมูล + สลับ (หัวข้อถัดไป)

ลบคอลัมน์remove_column :users, :nameเร็วมาก (~0.001 วินาที) แต่แอปที่ยังรันโค้ดเก่าอยู่พังบอก Rails ให้ลืมคอลัมน์ก่อน (ignored_columns) แล้วค่อยลบ

สังเกตแถวสุดท้าย: เร็วไม่ได้แปลว่าปลอดภัย · การลบคอลัมน์ใช้ราว 1 มิลลิวินาที แต่ทำแอปพังได้ — สองหัวข้อถัดไปจะรันให้ดู

เปลี่ยนชื่อคอลัมน์โดยไม่ปิดร้าน — expand → migrate → contract

โจทย์ (สไลด์หน้า 17): เปลี่ยนชื่อคอลัมน์ name ของ users เป็น full_name โดยไม่มี downtime เลยแม้แต่วินาทีเดียว
ท่าที่คิดออกก่อนคือ rename_column :users, :name, :full_name บรรทัดเดียว — เร็วด้วย · แต่ปัญหาไม่ได้อยู่ที่ตู้ อยู่ที่จังหวะ deploy

ย้อนไปดูขั้นตอน deploy: รัน migration (ข้อ 2) ก่อน restart แอป (ข้อ 3) · แปลว่ามีช่วงหนึ่งที่ตู้เป็นแบบใหม่แล้ว แต่แอปยังเป็นโค้ดเก่า · ถ้าสลับลำดับ ก็จะมีช่วงที่โค้ดใหม่วิ่งอยู่กับตู้แบบเก่าแทน — หนีช่วงนี้ไม่พ้น

เวลา ────────────────────────────────────────────────────────▶ ตู้ (DB) [ มีช่อง name ] │ช่างรัน rename│ [ มีแต่ full_name ] แอป [ โค้ดเก่า: อ่าน/เขียน name ...................... ]│restart│[ โค้ดใหม่ ] ▲ ช่วงอันตราย: โค้ดเก่าหาช่อง name ไม่เจอ → error

ประโยคหลักของสไลด์: ไม่มี deploy ไหนที่โค้ดกับตู้เปลี่ยนพร้อมกันได้ — ต้องออกแบบให้มีช่วงที่ของเก่ากับของใหม่อยู่ด้วยกันได้ · ท่ามาตรฐานคือแบ่งเป็น 3 เฟส แต่ละเฟสคือ deploy หนึ่งรอบ:

ที่ไม่เหมือนกัน: ในร้านจริง ประกาศครั้งเดียวทุกคนได้ยินพร้อมกัน · แต่แอปบน production มักมีหลายตัวรันพร้อมกัน และแต่ละตัวจำแปลนตู้ไว้ตั้งแต่ตอนเปิด — ตัวที่ยังไม่ restart จะยังเชื่อแปลนเก่า (หัวข้อถัดไปจะเห็นว่าพังยังไง)

เฟส 2 · migrate — ย้ายข้อมูลเก่าทีละกอง แล้วสลับไปอ่านช่องใหม่

ต้องก็อป name ไปใส่ full_name ให้คนเก่าทุกคน · สมมุติว่าบน production ตาราง users มี 20 ล้านแถว — ถ้าสั่งทีเดียวทั้งตาราง จะกลายเป็นงานใหญ่ที่ lock นาน → แบ่งเป็นกองละ 1,000 แถว แต่ละกองเสร็จเร็วแล้วปล่อยลิ้นชัก (ตัวอย่างนี้สั่งใน console · งานจริงใส่ในงานแยก เช่น bin/rails runner — ดูกฎข้อ 2 ท้ายบท): 

User.where(full_name: nil).in_batches(of: 1000) do |batch|
  batch.update_all("full_name = name")
end

  • .in_batches(of: 1000) do |batch| … end — แบ่งเป็นกองละ 1,000 แผ่น แล้วส่งแต่ละกองเข้า block ในชื่อ batch (block = ก้อนโค้ด do … end บท 93 · in_batches ละเอียดบท 114)

เฟส 3 · contract — บอก Rails ให้ลืมช่องเก่า แล้วค่อยรื้อ

เลิกเขียน name ทุกที่ และเพิ่มบรรทัดเดียวใน model:

# app/models/user.rb
class User < ApplicationRecord
  self.ignored_columns += ["name"]   # ทำเหมือนคอลัมน์ name ไม่มีอยู่

  has_many :posts      # สองบรรทัดนี้มีอยู่แล้ว (ผูก User กับ posts/comments · บท 115)
  has_many :comments
end
  • self.ignored_columns — self. ที่อยู่ใน class ตรงนี้หมายถึงตัว class User ทั้ง class (ตั้งค่าให้ผู้ใช้ทุกคน ไม่ใช่คนใดคนหนึ่ง)
  • += ["name"] — เติม "name" เข้าไปในรายการเดิม (ย่อมาจาก x = x + ["name"])
  • รวมกันแปลว่า "คนดูแลสต็อกของ User ให้ทำเป็นไม่เห็นช่อง name" ทั้งที่ช่องยังอยู่ในตู้

deploy ครั้งที่ 3 · พอแน่ใจว่าแอปทุกตัว restart แล้ว ค่อยรื้อจริงด้วย migration (deploy ครั้งถัดไป): 

bin/rails generate migration RemoveNameFromUsers name:string
# db/migrate/20261104115259_remove_name_from_users.rb (ไฟล์ที่ได้จริง)
class RemoveNameFromUsers < ActiveRecord::Migration[8.1]
  def change
    remove_column :users, :name, :string
  end
end

:string ท้ายบรรทัดไม่จำเป็นต่อการลบ แต่ทำให้ตอน rollback Rails รู้ว่าต้องสร้างช่องคืนเป็นชนิดอะไร (จะเห็นผลในหัวข้อ IrreversibleMigration)

⚠️ ถ้าทำตามในเครื่อง: หลังหัวข้อนี้ตาราง users ของคุณจะไม่มีช่อง name แล้ว แต่บทถัดไปยังใช้ name อยู่ · ไม่ต้องรีบแก้ตอนนี้ — กล่อง "เก็บกวาดก่อนไปบทหน้า" ก่อนภารกิจคืนตู้ให้ครบทุกอย่างในทีเดียว

🗣 ศัพท์ที่เพิ่งเรียนไป
expand → migrate → contract (expand/contract pattern)
ท่าเปลี่ยน schema โดยไม่มี downtime: เพิ่มของใหม่ → ย้ายข้อมูลและสลับการอ่าน → รื้อของเก่า · คั่นด้วย deploy ทุกเฟส · พิมพ์บอก AI ได้ว่า “plan an expand/contract migration to rename users.name to full_name, list each deploy separately”
backfill · batch
backfill = เติมข้อมูลให้คอลัมน์ใหม่ย้อนหลังสำหรับแถวที่มีอยู่แล้ว · batch = ทำทีละกอง · ถาม senior ได้ว่า “backfill ตารางนี้ควรใช้ batch ขนาดเท่าไหร่ และรันจากที่ไหน”
dual write
ช่วงที่โค้ดเขียนลงทั้งคอลัมน์เก่าและใหม่พร้อมกัน (เฟส 1–2) · ทำให้แอปตัวเก่ากับตัวใหม่อยู่ด้วยกันได้ · ถามได้ว่า “ตอนนี้เราอยู่ช่วง dual write หรือยัง ปิดได้หรือยัง”

ทำไมต้อง ignored_columns — แอปที่เปิดอยู่จำแปลนตู้เก่า

Rails บอกตรง ๆ ว่า "ไฟล์นี้ใช้ execute ฉันย้อนให้เองไม่ได้" · ทางที่ 1 คือแยกเป็น up (ทำ) กับ down (ย้อน) เอง (บท 108) · งานนี้ย้อนไม่ได้จริง ๆ เพราะไม่มีใครรู้แล้วว่าอีเมลเดิมตัวไหนเป็นตัวใหญ่ → เขียน down ให้ระเบิดพร้อมเหตุผล: 

class DowncaseUserEmails < ActiveRecord::Migration[8.1]
  def up
    execute "UPDATE users SET email = LOWER(email)"
  end

  def down
    raise ActiveRecord::IrreversibleMigration, "อีเมลตัวพิมพ์ใหญ่เดิมหายไปแล้ว ย้อนกลับไม่ได้"
  end
end

  • raise — โยน error (บท 96) · ActiveRecord::IrreversibleMigration คือชนิด error ที่ Rails เตรียมไว้สำหรับ "ย้อนไม่ได้"
  • .rb:7 = บรรทัด raise · migrate:status ยังเป็น up — ตู้ไม่ถูกแตะ คนที่สั่ง rollback รู้ทันทีว่าต้องหาทางอื่น (เช่นกู้จาก backup = สำเนาตู้ที่เก็บไว้ก่อนหน้า)
  • ทำไมดีกว่าปล่อย down ว่าง: ถ้า down ว่าง rollback จะ "ผ่าน" แต่ข้อมูลไม่ได้ย้อน — คนจะเข้าใจผิดว่าย้อนแล้ว

เทียบกับ Go: goose ไม่มีการเดาขากลับ — ทุกไฟล์คุณเขียนท่อน -- +goose Down เองเสมอ (บท 31) · up / down ของ Rails คือท่าเดียวกันนั้น · ส่วน change คือของแถมที่ Rails เดาขากลับให้ เมื่อมันเดาได้

🗣 ศัพท์ที่เพิ่งเรียนไป
ignored_columns
รายชื่อคอลัมน์ที่บอกให้ model ทำเป็นไม่เห็น ใช้ก่อนลบคอลัมน์ เพื่อให้แอปที่ยังรันอยู่เลิกใส่คอลัมน์นั้นใน SQL · ถาม senior ได้ว่า “ใส่ ignored_columns แล้ว deploy ครบทุกเครื่องหรือยัง ลบคอลัมน์ได้หรือยัง”
IrreversibleMigration · up / down

ของที่ช่วยกันไม่ให้พลาด — strong_migrations และกฎ 4 ข้อ

strong_migrations คือ gem (อุปกรณ์สำเร็จรูป บท 98) ที่ดักทุกคำสั่งใน migration ก่อนส่งไปถึงตู้ ถ้าเจอท่าอันตรายจากตารางข้างบน มันจะหยุด migration ทันที แล้วบอกท่าที่ปลอดภัยให้ · แอปของเราไม่ได้ติดตั้ง บทนี้แค่ให้รู้จัก (หน้า GitHub ของ gem)

ตัวอย่างข้อความจาก README ของ gem (ไม่ได้รันในบทนี้ · ตัดมาบางส่วน) — บังเอิญเป็นเรื่องเดียวกับที่เราเพิ่งพังเอง:

คือ "Active Record จำรายชื่อช่องไว้ ลบคอลัมน์แล้วจะมีปัญหา ให้ใส่ ignored_columns ก่อน" — ตรงกับหัวข้อที่แล้วทุกคำ · ถ้าทีมของคุณใช้ gem นี้ migration อันตรายจะรันไม่ผ่านตั้งแต่เครื่องคุณ

กฎส่วนตัวของผู้สอน (สไลด์หน้า 18) — เลือก 4 ข้อที่ใช้ได้ตั้งแต่วันแรก:

  1. 1 migration = 1 เรื่อง — พังแล้วรู้ทันทีว่าเรื่องไหน · โดยเฉพาะไฟล์ที่ปิด transaction
  2. ย้ายข้อมูลเยอะ ๆ ไม่ทำใน migration — ให้ไปทำในงานแยก (เช่น bin/rails runner หรือ rake task = คำสั่งที่เราเขียนเพิ่มเอง แล้วรันด้วย bin/rails ชื่องาน) แบบเฟส 2 ข้างบน · Rails Guides ก็แนะนำแบบเดียวกัน
  3. ก่อน merge (รวมโค้ดของเราเข้ากิ่งหลักของทีม): rollback แล้ว migrate อีกรอบ — คำสั่งเดียวคือ bin/rails db:migrate:redo (ผลจริง: เห็น reverting ตามด้วย migrating) · ถ้า redo ไม่ผ่าน แปลว่า rollback ใช้ไม่ได้จริง
  4. ตารางเกิน 1 ล้านแถว = คิดเรื่อง lock ทุกครั้ง — ถามคำถามประจำบท "แตะกี่แถว ใครต้องรอ"

ไม่แน่ใจว่า migration ของงานจริงอันตรายไหม → ส่งให้ senior หรือ AI สามอย่าง: ไฟล์ migration ทั้งไฟล์ · ตารางนั้นมีกี่แถว · มีคนเขียนตารางนี้บ่อยแค่ไหน แล้วถามคำถามประจำบทนี้

ส่วน A — เขียนลงกระดาษ (มาจาก Quiz 2 ของสไลด์)

  1. bin/rails generate migration AddIndexToPostsTitle
  2. เปิดไฟล์ที่ได้ เติม add_index :posts, :title, algorithm: :concurrently ใน change — ยังไม่ต้องใส่ disable_ddl_transaction!
  3. bin/rails db:migrate → จด error ที่เห็น
  4. เติม disable_ddl_transaction! ไว้ใต้บรรทัด class แล้ว migrate อีกรอบ
  5. เปิด db/schema.rb หาบรรทัดที่มีคำว่า title
  6. ลอง bin/rails db:migrate:redo ว่าย้อนแล้วทำใหม่ผ่านไหม

  • PG::DuplicateTable: ERROR: relation "index_posts_on_title" already exists → มี index ชื่อนี้อยู่แล้ว (จากตอนลองหัวข้อ index แล้วยังไม่ได้เก็บกวาด) · ทำกล่องเก็บกวาดก่อน แล้วเริ่มข้อ 1 ใหม่

จุดที่ต้องจำ: concurrently มาคู่กับ disable_ddl_transaction! เสมอ · เหมือน -- +goose NO TRANSACTION ใน Go

จุดที่ต้องจำ: สลับการอ่านได้หลัง backfill ครบ · ระหว่างนั้นเขียนทั้งสองช่อง

ข้อ 4 · ลบคอลัมน์ name ด้วย remove_column ไปแล้ว ต่อมาสั่ง bin/rails db:rollback — ข้อมูลชื่อของผู้ใช้เป็นยังไง?

ตัวเลือกที่ 4 ถูก · ผลจริง: rollback รัน add_column(:users, :name, :string) แล้ว User.pluck(:name, :full_name) ได้ [[nil, "มานะ ใจดี"], [nil, "สมชาย"], [nil, "สมหญิง"]] · ตัวเลือกที่ 1 ผิด — rollback คือ "สั่งช่างทำงานกลับด้าน" ไม่ใช่ย้อนเวลา ข้อมูลที่ทิ้งไปไม่กลับ · ตัวเลือกที่ 2 ผิด — ไฟล์นี้บอกชนิด :string ไว้ Rails จึงรู้วิธีสร้างคอลัมน์คืน (IrreversibleMigration เกิดกับงานที่เดาวิธีย้อนไม่ได้ เช่น execute) · ตัวเลือกที่ 3 ผิด — schema.rb คือแปลนตู้ (มีลิ้นชักอะไร ช่องอะไร) ไม่ได้เก็บข้อมูลในแฟ้มสักแผ่น

จุดที่ต้องจำ: rollback ได้ ≠ ข้อมูลกลับ · ก่อนลบคอลัมน์บน production ต้องมั่นใจว่าไม่มีใครใช้แล้ว (ignored_columns + เฟส 3)
