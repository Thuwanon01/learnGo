Callbacks และที่อยู่ของโค้ด — ขั้นตอนอัตโนมัติก่อนเก็บแฟ้ม

~25 นาที · ควรผ่าน บทเรียน 110 (validation) และ บทเรียน 111 (transaction) มาก่อน

บางงานต้องทำทุกครั้งที่บันทึกบทความ เช่น สร้างชื่อสำหรับใส่ใน URL หรือแปลงอีเมลเป็นตัวเล็ก · ถ้าต้องจำเขียนเองทุกที่ สักวันต้องมีคนลืม
อ่านจบบทนี้ คุณจะสั่งให้ Rails ทำงานพวกนี้ให้เองอัตโนมัติ ก่อนหรือหลังเก็บแฟ้มเข้าตู้ได้ · รู้ว่างานไหนต้องรอให้ตู้ยืนยันก่อน (ไม่งั้นได้อีเมลหลอก) · และรู้ว่าโค้ดงานใหญ่ที่มีหลายขั้นควรไปอยู่ไฟล์ไหน

🔁 ทวนก่อนเริ่ม — คำจากบทก่อน ๆ ที่บทนี้ใช้

  • model (บท 106) — คนดูแลสต็อกที่ฝังอยู่ในแฟ้ม · Post หนึ่งตัว = แฟ้มบทความหนึ่งแผ่น ที่เดินเข้าลิ้นชัก posts เองได้
  • validation (บท 110) — กฎที่คนดูแลสต็อกใช้ตรวจแฟ้มก่อนเก็บ เช่น "ไม่มีชื่อเรื่อง ไม่รับ" · save! / update! = ถ้าไม่ผ่านให้ระเบิด
  • migration (บท 108) — ใบสั่งช่างมาต่อเติมตู้ · bin/rails db:migrate = ให้ช่างลงมือ · db:rollback = รื้องานใบล่าสุดออก
  • transaction (บท 111) — กล่องคำสั่ง "ทำทั้งหมด หรือไม่ทำเลย" · ใน log เห็นเป็น BEGIN (เปิดกล่อง) · COMMIT (ยืนยัน) · ROLLBACK (ยกเลิกทั้งกล่อง)
  • ||= (บท 94) — "ถ้ายังว่างค่อยใส่" · before_action :set_post (บท 102) — "ก่อนเข้าเมนู ให้เรียก method นี้ก่อน" · private (บท 102) — method ข้างใต้ใช้ได้แค่ภายใน class

🧰 ตรวจด้วย Ruby 4.0.9 · Rails 8.1.4 · PostgreSQL 17 (สไลด์ใช้ Ruby 4.0.6 · Rails 8.1.3 — รุ่นแก้บั๊กในสายเดียวกัน ใช้แทนกันได้)

📦 ตัวอย่างในบทนี้ใช้ตาราง users / posts / comments และข้อมูลตัวอย่าง (seeds) ชุดเดียวกับบท 107 · บทนี้จะเพิ่มคอลัมน์ slug ให้ posts เฉพาะบทนี้ แล้วคืนสภาพตอนท้ายภารกิจ เพื่อให้บทถัดไปได้ผลตรงกัน

✂️ โค้ด model ในบทนี้โชว์เฉพาะบรรทัดที่เกี่ยวกับเรื่องของบท · validates ที่คุณเติมไว้ตามบท 110–111 เก็บไว้ตามเดิม แล้วแทรกบรรทัดใหม่เพิ่มเข้าไป · ผลรันในบทนี้รันกับ model ที่ไม่มี validates — log ของคุณจึงอาจมีบรรทัดเพิ่ม เช่น User Exists? (Rails เช็คอีเมลซ้ำตามกฎบท 111) ไม่ต้องตกใจ

ผลทุกก้อนรันจริงแล้วก็อปมา · เวลา (ms) · วันเวลา · เลข id · เลขหน้าชื่อไฟล์ migration ของคุณจะต่าง · ทุกคำสั่งพิมพ์ใน bin/rails console ธรรมดา ไม่ใช้ --sandbox (แผ่นใสของ sandbox ทำให้ log รกและดูเรื่อง after_commit ท้ายบทไม่ออก)

callback คืออะไร — กฎ "ทำทุกครั้ง" ที่ติดไว้ข้างตู้

callback คือ method ที่เราฝากไว้กับ model ว่า "ทุกครั้งที่จะเก็บแฟ้ม (หรือเพิ่งเก็บเสร็จ) ให้เรียก method นี้ด้วย" · ไม่ต้องมีใครสั่ง ไม่ว่าการบันทึกจะมาจาก controller · console · หรือ seeds ก็โดนหมด

มีไว้สำหรับงานที่ต้องทำทุกครั้งโดยไม่มีข้อยกเว้น — ถ้าปล่อยให้คนเขียนเองในทุก controller สักวันต้องมีที่หนึ่งที่ลืม

🏷 เทียบให้เห็นภาพ — ป้ายกฎที่ติดไว้ข้างตู้เก็บแฟ้ม

คนดูแลสต็อกติดป้ายไว้ข้างตู้ว่า "แฟ้มทุกแผ่น ก่อนเข้าลิ้นชัก ต้องติดป้ายชื่อย่อที่สันแฟ้ม" · ใครเอาแฟ้มมาส่งก็ตาม — เชฟ พนักงานต้อนรับ หรือผู้จัดการ — คนดูแลสต็อกติดป้ายให้เองทุกแผ่น คนส่งไม่ต้องจำ

ที่ไม่เหมือนกัน: คนจริงเห็นแฟ้มแปลก ๆ ก็หยุดถามก่อนได้ · callback ไม่คิด ทำทุกครั้งเป๊ะ ๆ · และคนที่อ่านโค้ด controller มองไม่เห็นป้ายนี้ — เห็นแค่ post.save บรรทัดเดียว ไม่รู้ว่าข้างในมีงานแอบทำอีกกี่อย่าง (นี่คือที่มาของคำว่า "สะดวกมากและเจ็บมาก" — มีหัวข้อของมันเองข้างล่าง)

หน้าตาคุ้นตาแน่นอน — เพราะคุณเคยเห็นญาติของมันแล้วใน controller: before_action :set_post (บท 102) · callback ของ model เขียนแบบเดียวกันเป๊ะ ต่างกันแค่จังหวะ: before_action ทำก่อนเข้าเมนู · callback ทำก่อน/หลังเก็บแฟ้ม 

class Post < ApplicationRecord
  before_validation :generate_slug   # ก่อนตรวจแฟ้ม ให้เรียก method ชื่อ generate_slug
end

เทียบกับ Go: GORM ก็มีของแบบนี้ เรียกว่า hook — ถ้า struct มี method ชื่อ BeforeSave สะกดตรงเป๊ะ GORM จะเรียกให้เองก่อนบันทึก (ไฟล์นี้ go run ผ่านจริง): 

// main.go
package main

import (
	"fmt"
	"strings"

	"gorm.io/driver/sqlite"
	"gorm.io/gorm"
)

type Post struct {
	ID    uint
	Title string
	Slug  string
}

// BeforeSave คือ hook ของ GORM — ชื่อต้องสะกดตรงเป๊ะ GORM ถึงจะเรียกให้เองก่อน save
func (p *Post) BeforeSave(tx *gorm.DB) error {
	if p.Slug == "" {
		p.Slug = strings.ToLower(strings.ReplaceAll(p.Title, " ", "-"))
	}
	return nil
}

func main() {
	db, _ := gorm.Open(sqlite.Open("file::memory:"), &gorm.Config{})
	db.AutoMigrate(&Post{})

	post := Post{Title: "Green Curry Chicken"}
	db.Create(&post)
	fmt.Println(post.Slug)
}
$ go run main.go
green-curry-chicken

อ่านเฉพาะส่วนที่เกี่ยวกับเรื่องนี้:

  • func (p *Post) BeforeSave(tx *gorm.DB) error — method ของ struct Post (p คือบทความตัวที่กำลังจะถูกบันทึก) · คืน error ได้ ถ้าคืน error GORM จะยกเลิกการบันทึก
  • if p.Slug == "" … — ถ้ายังไม่มี slug ให้เอาชื่อเรื่องมาเปลี่ยนช่องว่างเป็นขีด แล้วทำเป็นตัวเล็ก
  • db.AutoMigrate(&Post{}) — ให้ GORM สร้างตารางจาก struct (บท 27) · db.Create(&post) — บันทึก · ในจังหวะนี้แหละที่ GORM เรียก BeforeSave ให้เอง เราไม่ได้เรียกเลย
  • ฝั่ง Go: GORM เดาจากชื่อ method — สะกด Beforesave ผิดตัวเดียวก็เงียบ ไม่ถูกเรียก (ผมลองแล้ว ได้บรรทัดว่างแทน slug)
  • ฝั่ง Rails: เราประกาศเองตรง ๆ ว่า "จังหวะ before_validation ให้เรียก :generate_slug" · ชื่อ method ตั้งอะไรก็ได้
  • ใช้ SQLite (ฐานข้อมูลในหน่วยความจำ) แค่ให้ตัวอย่าง Go รันได้ในไฟล์เดียว ไม่เกี่ยวกับแอป Rails
🗣 ศัพท์ที่เพิ่งเรียนไป
callback (Active Record callback)
method ที่ Rails เรียกให้เองตอนแฟ้มถูกสร้าง · บันทึก · ลบ · ประกาศด้วยคำอย่าง before_validation · after_commit · GORM เรียกของแบบเดียวกันว่า hook · ถาม senior ได้ว่า “model นี้มี callback อะไรซ่อนอยู่บ้าง ก่อนที่ผมจะไปเรียก save จากที่ใหม่”
lifecycle (วงจรชีวิตของ object)
ลำดับจังหวะที่แฟ้มหนึ่งแผ่นผ่าน ตั้งแต่ "จะบันทึก" จนถึง "ตู้ยืนยันแล้ว" · callback แต่ละตัวคือจุดแวะในเส้นทางนี้ (หัวข้อถัดไป) · พิมพ์บอก AI ได้ว่า “at which point in the Active Record lifecycle should I set this attribute?”

เวลาสั่ง create หนึ่งครั้ง แฟ้มไม่ได้กระโดดเข้าตู้ทันที แต่เดินผ่านจุดแวะเรียงกันตามนี้ (สไลด์หน้า 24 · ผมเรียงตามผลรันจริงข้างล่าง):

อย่าเชื่อแผนภาพ ลองให้ callback ทุกตัว "ตะโกนชื่อตัวเอง" ดีกว่า · เปิดไฟล์ app/models/post.rb แล้วเพิ่ม 7 บรรทัดนี้ชั่วคราว (ใต้ has_many): 

# app/models/post.rb — ตัวทดลอง: ให้ callback ทุกตัวตะโกนชื่อตัวเอง
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments

  before_validation { puts "1 before_validation" }
  after_validation  { puts "2 after_validation" }
  before_save       { puts "3 before_save" }
  before_create     { puts "4 before_create" }
  after_create      { puts "5 after_create" }
  after_save        { puts "6 after_save" }
  after_commit      { puts "7 after_commit" }
end
  • belongs_to :user · has_many :comments — ของเดิมในไฟล์ (บทความเป็นของผู้ใช้หนึ่งคน มีคอมเมนต์หลายอัน — ละเอียดบท 115) ห้ามลบ
  • before_validation { … } — แทนที่จะส่งชื่อ method ก็ส่ง block (ก้อนโค้ดใน { } บท 93) ไปตรง ๆ ได้ · เหมาะกับโค้ดทดลองสั้น ๆ

  • INSERT INTO "posts" (…) VALUES (…) — "เก็บแฟ้มใหม่ลงลิ้นชัก posts โดยเขียนช่องพวกนี้ด้วยค่าพวกนี้" · RETURNING "id" ท้ายคำสั่ง = "เก็บเสร็จแล้วบอกเลขที่แฟ้มกลับมาด้วย" (บท 107) · ตอนนี้ยังไม่มีช่อง slug — จะเพิ่มในหัวข้อถัดไป
  • BEGIN … COMMIT — Rails ครอบการบันทึกทุกครั้งด้วย transaction ให้เอง (บท 111) · ที่ BEGIN โผล่หลังเลข 4 เพราะ Rails ส่งคำนี้ไปบอกฐานข้อมูลตอนจะเขียนจริงเท่านั้น ไม่ต้องสนใจ
  • จุดที่ต้องดูจริง ๆ: เลข 6 (after_save) อยู่ก่อน COMMIT · เลข 7 (after_commit) อยู่หลัง — จำไว้ หัวข้อ after_save หรือ after_commit ข้างล่างใช้เรื่องนี้

before_create / after_create มีไว้เฉพาะแฟ้มใหม่ · ส่วนคำว่า save ครอบทั้งสร้างและแก้ จึงยังโผล่ · SQL เปลี่ยนจาก INSERT เป็น UPDATE "posts" SET "title" = … WHERE "posts"."id" = 7 = "แก้ช่อง title ของแฟ้มในลิ้นชัก posts เฉพาะแผ่นเลขที่ 7" (เลข id ของคุณจะต่าง)

ทดลองเสร็จแล้ว ลบ callback ทั้ง 7 บรรทัดนั้นออก ให้ไฟล์กลับเป็นเหมือนก่อนเริ่มหัวข้อนี้ — หัวข้อถัดไปจะใส่ของจริง

ลงมือ: ให้บทความสร้าง slug เองทุกครั้ง

slug คือชื่อเรื่องที่แปลงให้ใส่ใน URL ได้ เช่น "Green Curry Chicken" → green-curry-chicken (เคยเห็นแล้วในบท 95 ตอนทำ module Sluggable · คือ "ป้ายชื่อย่อที่สันแฟ้ม" ในภาพข้างบน) · เว็บจะได้มี URL แบบ /posts/green-curry-chicken แทน /posts/8 · งานนี้ต้องทำทุกครั้งที่มีบทความใหม่ — เหมาะกับ callback ที่สุด

ที่ไม่เหมือนกัน: กติกาบนลิ้นชักจริงใช้กับแฟ้มเก่าที่อยู่ในลิ้นชักแล้วด้วย · normalizes ไม่ไปแก้แฟ้มเก่าในตู้ให้ — แฟ้มที่เก็บไว้ก่อนเพิ่มบรรทัดนี้ ถ้ามีตัวใหญ่ปนก็ยังเป็นแบบเดิม (ผมลองแล้ว และ find_by กลับหาแฟ้มเก่าพวกนั้นไม่เจอ เพราะคำค้นถูกแปลงเป็นตัวเล็ก)

after_save หรือ after_commit — อีเมลหลอกเกิดได้ยังไง

สมมติอยากส่งอีเมลบอกผู้ติดตาม "มีบทความใหม่!" ทุกครั้งที่สร้างบทความ · ดูเผิน ๆ ใส่ after_save ก็น่าจะได้ · แต่จำแผนภาพได้ไหม — after_save ทำงานก่อน COMMIT ตอนนั้นตู้ยังไม่ได้ยืนยันว่าจะรับแฟ้ม

📱 เทียบให้เห็นภาพ — ส่งไลน์บอกลูกค้าก่อนตู้เซ็นรับ

แฟ้มบทความถูกยื่นเข้าช่องตู้ แต่ยังไม่ได้เซ็นรับ · พนักงานคนหนึ่งรีบส่งไลน์บอกผู้ติดตามว่า "บทความใหม่เข้าตู้แล้ว!" (after_save) · วินาทีต่อมาผู้จัดการสั่งยกเลิกทั้งกล่อง (ROLLBACK) แฟ้มถูกดึงออก — ผู้ติดตามได้ข่าวของที่ไม่มีอยู่จริง · ถ้ารอให้ตู้เซ็นรับก่อนค่อยส่ง (after_commit) จะไม่มีวันส่งข่าวหลอก

ที่ไม่เหมือนกัน: ไลน์ยังพิมพ์ขอโทษตามได้ · อีเมลที่ส่งออกไปแล้วดึงกลับไม่ได้ · และ ROLLBACK ย้อนได้เฉพาะของในตู้ (database) — ของที่ออกไปนอกร้านแล้ว ไม่ย้อนตาม (เหมือนแผ่นใสของ --sandbox ในบท 104)

ลองของจริง · ใส่ทั้งสองแบบไว้ใน Post พร้อมกัน (งานจริงยังไม่ส่งอีเมล แค่พิมพ์ข้อความแทน):

# app/models/post.rb
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments

  before_validation :generate_slug
  after_save   :email_too_early                    # ❌ ตัวอย่างที่ผิด
  after_commit :notify_followers, on: :create      # ✅ ตัวอย่างที่ถูก

  private

  def generate_slug
    self.slug ||= title.to_s.parameterize
  end

  def email_too_early
    puts "📧 after_save: ส่งอีเมลเรื่อง #{title} แล้ว"
  end

  def notify_followers
    Rails.logger.info "📬 after_commit: ส่งงานแจ้งผู้ติดตามเรื่อง #{title}"
  end
end
  • after_commit :notify_followers, on: :create — "หลังตู้ยืนยันแล้ว เรียก notify_followers · เฉพาะตอนสร้างใหม่" · ไม่ใส่ on: จะทำทั้งตอนสร้าง แก้ และลบ
  • Rails.logger.info "…" — จดลงสมุดบันทึกของแอป (log) แทน puts (บท 93 บอกไว้ว่าแอปจริงใช้ตัวนี้) · ใน console จะเห็นขึ้นจอด้วย
  • ของจริงใน notify_followers จะเป็น NotifyFollowersJob.perform_later(id) ตามสไลด์ — แปลว่า "ฝากงานส่งอีเมลไว้ในคิว ให้คนงานเบื้องหลังทำทีหลัง" · job คือเรื่องของ Day 3 · ตอนนี้แอปยังไม่มี job ตัวนี้ ถ้าพิมพ์ตามสไลด์จะได้ uninitialized constant Post::NotifyFollowersJob (ผมลองแล้ว)

🗣 ศัพท์ที่เพิ่งเรียนไป
after_commit (transaction callback)
callback ที่รอให้ฐานข้อมูลยืนยัน (COMMIT) ก่อนค่อยทำ · ถ้า rollback ก็ไม่ทำเลย · ที่สำหรับงานที่ออกไปนอกตู้: ส่งอีเมล · แจ้งเตือน · ฝากงานให้ job · ถาม senior ได้ว่า “callback ที่ส่งอีเมลตัวนี้ ควรย้ายจาก after_save ไป after_commit ไหม”
side effect (ผลข้างเคียง)
สิ่งที่โค้ดทำแล้วมีผลออกไปนอกตัวมัน เช่น ส่งอีเมล · เรียก API ภายนอก · เขียนไฟล์ · rollback ย้อนของพวกนี้ไม่ได้ · พิมพ์บอก AI ได้ว่า “move side effects out of after_save into after_commit and enqueue a job”

โค้ดส่งอีเมลแจ้งผู้ติดตามหลังสร้างบทความใหม่ ควรวางไว้ที่ไหน?

ตัวเลือกที่ 4 ถูก — รอตู้ยืนยันก่อน จะไม่มีวันส่งอีเมลเรื่องที่ไม่มีอยู่จริง · และฝาก job (Day 3) ให้ส่งทีหลัง หน้าเว็บจะได้ไม่ต้องรออีเมลส่งเสร็จ

ตัวเลือกที่ 1 ผิด เพราะยังไม่ได้ตรวจด้วยซ้ำ บทความอาจไม่ผ่าน validation ด้วย · ตัวเลือกที่ 2 คือกับดักของข้อนี้ (ฟังดูถูกที่สุด) — "เขียนลงตู้แล้ว" ไม่ได้แปลว่า "ยืนยันแล้ว" ผลจริงข้างบน 📧 ขึ้นทั้งที่ count ได้ 0 · ตัวเลือกที่ 3 ผิด เพราะ validation มีไว้ตรวจว่าแฟ้มถูกไหม ไม่ใช่ที่ทำงานอื่น (และ valid? เรียกเฉย ๆ ก็ทำงาน ทั้งที่ไม่ได้บันทึก)

จุดที่ต้องจำ: ของที่ออกไปนอกตู้ (อีเมล · API · แจ้งเตือน) → after_commit เสมอ

ทดลองเสร็จ ลบบรรทัด after_save :email_too_early และ method email_too_early ทิ้ง · ให้ Post เหลือ before_validation :generate_slug กับ after_commit :notify_followers, on: :create — หน้าตาเดียวกับสไลด์หน้า 24

callback แบบไหนใช้ได้สบาย แบบไหนเริ่มเจ็บ

สไลด์หน้า 24 แบ่งไว้สองฝั่ง · แปลเป็นภาษาร้าน:

ตัวอย่างทำไม
✅ ใช้ได้สบายสร้าง slug · ทำอีเมลเป็นตัวเล็กเตรียมข้อมูลบนแฟ้มตัวเอง · ไม่ทำแล้วแฟ้มไม่สมบูรณ์ · ไม่ออกไปนอกตู้
⚠️ เริ่มเจ็บยิง API ภายนอก / ส่งอีเมลใน callbackช้า · ถ้าระบบนอกล่ม การบันทึกพังตาม · rollback ย้อนไม่ได้ (หัวข้อที่แล้ว)
⚠️ เริ่มเจ็บcallback ไปแก้ model ตัวอื่น ที่มี callback ต่ออีกโดมิโน: save บทความหนึ่งครั้ง ไปสะกิดผู้ใช้ ผู้ใช้ไปสะกิดอย่างอื่น · ไล่บั๊กยากมาก
⚠️ เริ่มเจ็บsave ทีเดียวมีของเกิด 8 อย่างอ่าน controller เห็นแค่ post.save · ไม่มีใครรู้ว่าจะเกิดอะไรบ้าง · เทสต์ช้าลง (เทสต์คือ Day 4)

หลักง่าย ๆ: callback ควรดูแลแค่แฟ้มของตัวเอง · ถ้างานนั้นต้องคุยกับคนอื่น (model อื่น ระบบอื่น อีเมล) ให้คิดก่อนว่าควรอยู่ใน callback จริงไหม · ส่วนมากคำตอบคือ "ย้ายไปไว้ในไฟล์ของงานนั้นเอง" — หัวข้อถัดไป

business logic ควรอยู่ที่ไหน — ใครในร้านรับผิดชอบงานไหน

business logic คือกฎของธุรกิจเรา เช่น "บทความที่เผยแพร่แล้ว ห้ามเผยแพร่ซ้ำ" หรือ "เผยแพร่แล้วต้องแจ้งผู้ติดตาม" · Rails ไม่ได้บังคับว่าโค้ดพวกนี้ต้องอยู่ไฟล์ไหน — สไลด์หน้า 27 เลยเสนอที่อยู่ 4 แบบ:

ที่ไม่เหมือนกัน: ร้านจริงมีผังองค์กรชัดว่าใครทำอะไร · Rails ไม่มีผังให้ ทุกทีมตกลงกันเอง · ไปทีมใหม่ ต้องเปิดดูโฟลเดอร์ app/ หรือถาม senior ก่อนว่าทีมนี้วางงานแบบไหน — อย่าเดาจากทีมเก่า

concern — ทวนบท 95 ในแบบของ Rails

บท 95 คุณทำ module Sluggable แล้ว include ไปใส่หลาย class · ใน Rails ทำแบบเดียวกันแต่วางไว้ที่ app/models/concerns/ (โฟลเดอร์นี้มีมาให้แล้วตั้งแต่ rails new) · ตัวอย่างนี้ดูหน้าตาไว้ก่อน ไม่ต้องทำตาม (ผมรันจริงแล้ว): 

# app/models/concerns/sluggable.rb
module Sluggable
  extend ActiveSupport::Concern

  included do
    before_validation :generate_slug
  end

  private

  def generate_slug
    self.slug ||= title.to_s.parameterize
  end
end

class Post < ApplicationRecord

end

service object — ลองทำ PublishPost จิ๋ว ๆ

งาน "เผยแพร่บทความ" มีหลายขั้น เหมาะกับ service object · ชื่อเป็นกริยา (PublishPost = "เผยแพร่บทความ") ไม่ใช่คำนาม · เพราะมันคือ "งานหนึ่งอย่าง" ไม่ใช่ "ของหนึ่งชิ้น" · สร้างโฟลเดอร์ app/services/ แล้วสร้างไฟล์นี้: 

# app/services/publish_post.rb
class PublishPost
  def initialize(post)
    @post = post
  end

  def call
    return false if @post.published

    @post.update!(published: true)
    Rails.logger.info "📣 เผยแพร่เรื่อง #{@post.title} ของ #{@post.user.name} แล้ว"
    true
  end
end

  • initialize(post) · @post = post — รับบทความที่จะเผยแพร่มาเก็บไว้ (บท 95)
  • return false if @post.published — ขั้น 1: ถ้าเผยแพร่ไปแล้ว จบเลย คืน false
  • @post.update!(published: true) — ขั้น 2: เปลี่ยนสถานะ · มี ! = ถ้าบันทึกไม่ได้ให้ระเบิด (บท 110)
  • Rails.logger.info … — ขั้น 3: แจ้งผู้ติดตาม (ของจริงฝากให้ job — Day 3) · @post.user.name = ชื่อผู้เขียน (บท 115 จะอธิบายว่าทำไมเรียกแบบนี้ได้)
  • ชื่อไฟล์ publish_post.rb ↔ ชื่อ class PublishPost — กฎตั้งชื่อเดียวกับบท 99 · Rails หาไฟล์เจอเองจากชื่อ ไม่ต้อง require

งาน "เผยแพร่บทความ" ต้องทำ: เช็คว่ายังไม่เคยเผยแพร่ → เปลี่ยนสถานะบทความ → บันทึกสถิติของผู้เขียน → แจ้งผู้ติดตาม · ควรวางโค้ดไว้ที่ไหน?

ตัวเลือกที่ 1 ถูก — งานหลายขั้น ข้ามหลาย model (บทความ · ผู้เขียน · ผู้ติดตาม) = ใบงานหนึ่งใบที่ชื่อเป็นกริยา

ตัวเลือกที่ 2 ผิด เพราะ concern ใช้ตอน model หลายตัวมีของเหมือนกัน · ที่นี่มีแค่ Post ที่เผยแพร่ได้ · ตัวเลือกที่ 3 ผิด เพราะเป็นทุกอย่างในตาราง "เริ่มเจ็บ": ไปแก้ model อื่น + แจ้งคนนอกตู้ใน after_save (ก่อน COMMIT) · ตัวเลือกที่ 4 ผิด เพราะไม่ได้มีฟอร์มที่ผู้ใช้กรอกลงหลายตาราง

จุดที่ต้องจำ: ธรรมชาติของแฟ้ม → model · ซ้ำหลาย model → concern · งานหลายขั้นข้าม model → service object · ไม่แน่ใจ → เริ่มที่ model
