บทเรียน 118 · Rails · Day 2

scaffold — โค้ดที่เครื่องเขียนให้ทั้งชุด แล้วเราต้องอ่านให้ออก

~25 นาที (มีลงมือสองรอบ) · ควรผ่าน บท 110 · บท 111 · บท 117 มาก่อน · ใช้ของจาก บท 102 (controller) ด้วย

Rails มีคำสั่งเดียวที่เขียนแผนกใหม่ให้ทั้งชุด — ตาราง · model · controller · หน้าเว็บ 4 หน้า · เทส — ใช้เวลาไม่ถึงวินาที
บทนี้คุณจะสั่งมันจริง เปิดหน้าเว็บที่ได้ ลองสร้าง แก้ ลบ แล้วอ่านโค้ดที่มันเขียนทีละไฟล์ด้วยความรู้ที่มีอยู่แล้ว
อ่านจบแล้วคุณจะชี้ได้ว่ามันลืมอะไร และมี checklist 8 ข้อไว้ตรวจโค้ดที่ AI เขียนให้ — เพราะของที่ scaffold ลืม คือของชุดเดียวกับที่ AI ลืม

🔁 ทวนก่อนเริ่ม — คำพวกนี้จะโผล่ในบทนี้ทั้งหมด

  • resources :posts (บท 101 · 117) — บรรทัดเดียวได้ URL มาตรฐาน 8 เส้น ไปหา 7 เมนู (index · show · new · create · edit · update · destroy — update มีสองเส้นคือ PATCH กับ PUT)
  • before_action (บท 102) — "ก่อนเข้าเมนูพวกนี้ ให้เรียก method นี้ก่อนเสมอ"
  • if @post.save … else render :new (บท 110) — เก็บได้ก็พาไปหน้าอื่น · เก็บไม่ได้ก็โชว์ฟอร์มเดิมพร้อมข้อผิดพลาด
  • params.expect (บท 117) — รับเฉพาะช่องที่อยู่ในรายการ ช่องอื่นที่ลูกค้าแอบเขียนมาถูกตัดทิ้ง
  • validation กับ constraint (บท 110–111) — กฎใน model คือคนดูแลสต็อกตรวจแฟ้ม · กฎในตาราง (NOT NULL · unique index) คือตัวตู้ที่ใส่แฟ้มผิดแบบไม่ได้เลย

🧰 เวอร์ชันที่ใช้ตรวจ: Ruby 4.0.9 · Rails 8.1.4 · PostgreSQL 17 (สไลด์ใช้ 4.0.6 · 8.1.3 — โค้ดที่ generate ได้ต่างจากสไลด์นิดหน่อย บอกไว้ทุกจุด) · 📦 ข้อมูล: แอป wongnok_blog ที่มีตาราง users/posts/comments และข้อมูลตัวอย่าง (seeds) ชุดเดียวกับบท 107 · บทนี้เพิ่มตารางใหม่ categories (หมวดหมู่อาหาร) ด้วย scaffold ทีละขั้นด้านล่าง · ผลรันทุกกล่องมาจากเครื่องจริง · เวลา (ms) · เลขเวลาในชื่อไฟล์ migration · เลข id ของคุณจะไม่ตรงกับของผม

1 · scaffold คืออะไร — ชุดเปิดแผนกใหม่สำเร็จรูป

ที่ผ่านมาเราสร้างของทีละชิ้น: generate model (บท 99) · เขียน route (บท 101) · เขียน controller (บท 102) · เขียน view (บท 103)
scaffold คือคำสั่ง generate ตัวใหญ่ที่ทำทุกชิ้นนั้นให้ในทีเดียว สำหรับของหนึ่งอย่าง (เช่น หมวดหมู่) ได้หน้าเว็บที่ดูรายการ · ดูทีละชิ้น · สร้าง · แก้ · ลบ ได้ทันที

สไลด์เรียกมันว่า "vibe code รุ่นปี 2005" (vibe code = บอก AI ว่าอยากได้อะไรแล้วรับโค้ดมาใช้เลย โดยไม่ได้เขียนเอง) — สั่งคำเดียวได้โค้ดมาทั้งกอง เหมือนสั่ง AI ทุกวันนี้
ต่างกันที่ scaffold ไม่ได้ "คิด" อะไรเลย มันเติมชื่อที่เราให้ลงในแม่แบบที่เตรียมไว้ · ผลจึงเหมือนกันทุกครั้ง และไม่รู้อะไรเกี่ยวกับร้านเราเลย

เทียบกับ Go: ตอนทำ wongnok API ด้วย Go คุณเขียนเองทุกชิ้น — struct ของ GORM (บท 27) · ไฟล์ SQL ของ goose (บท 31) · handler ของ Gin ทีละตัว (บท 38) · Go ไม่มีคำสั่งมาตรฐานที่เขียนชุดนี้ให้ · Rails มี เพราะทุกแอป Rails วางของที่เดิมตามกฎตั้งชื่อ (ร้านแฟรนไชส์ที่ทุกสาขาวางของตำแหน่งเดียวกัน)

🏪 เทียบให้เห็นภาพ — ชุดเปิดแผนกใหม่จากแฟรนไชส์

ร้านเราอยากเปิดแผนกหมวดหมู่อาหาร · แทนที่จะต่อตู้เอง จ้างเชฟเอง ทำป้ายเมนูเอง สำนักงานใหญ่ส่งชุดสำเร็จรูปมาให้ทั้งกล่อง: ใบสั่งช่างต่อลิ้นชักใหม่ (migration) · คนดูแลสต็อก (model) · หัวหน้าเชฟพร้อมเมนู 7 อย่าง (controller) · แบบจัดจาน 4 แบบ (view) · พนักงานต้อนรับได้รายการใหม่ (route) — แกะกล่องแล้วเปิดแผนกได้วันนั้นเลย

ที่ไม่เหมือนกัน: ชุดของแฟรนไชส์จริงมักมีคู่มือกฎมาด้วย · ชุดนี้ไม่มีกฎเลย — คนดูแลสต็อกรับแฟ้มเปล่า ๆ · ลิ้นชักไม่มีป้ายแท็บ · หัวหน้าเชฟให้ใครก็ได้สั่งทิ้งแฟ้ม (เดี๋ยวเห็นกับตาในหัวข้อ 6) · และของในกล่องกลายเป็นไฟล์ของเราทันที — สำนักงานใหญ่ไม่ส่งรุ่นใหม่มาอัปเดตให้ แก้ได้ทุกบรรทัด และต้องดูแลเองทุกบรรทัด

🗣 ศัพท์ที่เพิ่งเรียนไป
scaffold (นั่งร้าน)
คำสั่ง bin/rails generate scaffold ที่สร้าง migration + model + controller + view + route + test ของ resource หนึ่งตัว (ของหนึ่งอย่างที่มีชุด URL มาตรฐาน 8 เส้น บท 117) ในทีเดียว · ชื่อมาจากนั่งร้านก่อสร้าง — ของชั่วคราวที่ช่วยให้ขึ้นโครงได้เร็ว ไม่ใช่ตัวตึก · ถาม senior ได้ว่า "ฟีเจอร์นี้ scaffold มาเป็นจุดตั้งต้นได้ไหม หรือทีมเขียนมือเท่านั้น"
generator
คำสั่งตระกูล bin/rails generate … ทั้งหมด (model · migration · controller · scaffold) ที่เติมชื่อลงแม่แบบแล้วเขียนไฟล์ให้ · ย้อนได้ด้วย bin/rails destroy … ชื่อเดียวกัน (ใช้ในภารกิจ) · พิมพ์บอก AI ได้ว่า "show me the exact rails generate command, don't write the files by hand" ได้ไฟล์ที่ชื่อตรงกฎแน่นอน

3 · เปิดแผนกใหม่ ลองใช้จริง

เปิดร้านด้วย bin/rails server แล้วเปิด browser ที่ http://localhost:3000/categories · จะเห็นหัวข้อ Categories · ปุ่ม New category · และข้อความ No categories found.

⚠️ ถ้าหน้าเว็บขึ้นเป็นตัวหนังสือดำล้วน ไม่มีปุ่มสี — โค้ดไม่ได้พัง · หน้าของ scaffold ใช้ Tailwind (ชุดคำสั่งแต่งหน้าตาที่ rails new --css=tailwind ใส่ไว้) ซึ่งต้องสร้างไฟล์ CSS (ไฟล์แต่งหน้าตา) ใหม่ทุกครั้งที่มีหน้าใหม่ · เปิด terminal อีกหน้าต่างแล้วสั่ง bin/rails tailwindcss:build หนึ่งครั้ง (ผมลองแล้ว: ขึ้น Done in 42ms · เลข ms ของคุณจะต่าง) แล้ว refresh หน้าเว็บ · ยังใช้ bin/rails server เหมือนเดิม

4 · อ่าน controller ทีละ action

ไฟล์ที่ยาวที่สุด (70 บรรทัด) และสำคัญที่สุด · อ่านทีละท่อน — ทุกบรรทัดใช้ของที่เรียนมาแล้ว ยกเว้นของใหม่ชื่อ respond_to ซึ่งอธิบายตรงที่เจอ

ท่อน 1 — before_action กับ 4 เมนูที่สั้นมาก

  • @categories = Category.all — "เอาแฟ้มทุกแผ่นในลิ้นชัก" วางบนถาดให้หน้ารายการ · จำบรรทัดนี้ไว้ หัวข้อ 6 จะกลับมา
  • def show · def edit ว่างเปล่า — เพราะ before_action หยิบ @category มาวางบนถาดให้แล้ว · ที่เหลือ Rails เปิด view ชื่อตรงกับเมนูให้เอง (implicit render บท 102)
  • @category = Category.new — แฟ้มเปล่าที่ยังไม่ลงลิ้นชัก (บท 107) ให้ฟอร์มใช้เป็นแม่แบบ
  • คอมเมนต์ # GET /categories … เหนือแต่ละเมนู = scaffold จดไว้ให้ว่าเมนูนี้รับ URL ไหน (ตรงกับตาราง routes หัวข้อ 2)

ท่อน 2 — create และของใหม่ชื่อ respond_to

  # POST /categories or /categories.json
  def create
    @category = Category.new(category_params)

    respond_to do |format|
      if @category.save
        format.html { redirect_to @category, notice: "Category was successfully created." }
        format.json { render :show, status: :created, location: @category }
      else
        format.html { render :new, status: :unprocessable_content }
        format.json { render json: @category.errors, status: :unprocessable_content }
      end
    end
  end

ตัด respond_to ออกก่อน จะเหลือท่าเดียวกับบท 110 เป๊ะ:

  • Category.new(category_params) — สร้างแฟ้มจากของในฟอร์ม ที่ผ่านการคัดแล้ว (category_params อยู่ท่อน 4)
  • if @category.save — เก็บได้ (true) → redirect_to @category พาไปหน้าแฟ้มนั้น พร้อมข้อความเขียว (notice: = flash ฝากโชว์หน้าถัดไปครั้งเดียว บท 102)
  • else → render :new, status: :unprocessable_content — โชว์ฟอร์มเดิมพร้อมข้อผิดพลาด ตอบเลข 422 ("ข้อมูลไม่ผ่าน" บท 110) · Turbo ต้องได้ 422 ถึงจะวาดฟอร์มที่มีข้อผิดพลาดให้ (Day 3) · ตอนนี้ทางนี้ไม่มีวันเกิด เพราะไม่มีกฎ save จึงได้ true เสมอ (เห็นแล้วใน predict)

ของใหม่: respond_to do |format| = "ถามก่อนว่าลูกค้าอยากได้คำตอบแบบไหน" · มาจากหน้าเว็บ (HTML) → ทำตาม format.html { … } · มาทาง .json → ทำตาม format.json { … } · { … } คือ block (บท 93) ที่จะรันเฉพาะแบบที่ตรงกับลูกค้า

  • format.json { render :show, status: :created, location: @category } — ฝั่ง JSON ไม่มีหน้าให้ redirect จึงตอบข้อมูลแฟ้มใหม่ (ใช้แบบ show.json.jbuilder) · เลข 201 (:created = "สร้างแล้ว") · location: = แนบที่อยู่ของแฟ้มใหม่ (/categories/1) ไปกับคำตอบ
  • render json: @category.errors — เก็บไม่ได้ก็ส่งรายการข้อผิดพลาด (errors บท 110) กลับไปเป็น JSON แทนการโชว์ฟอร์ม
🥡 เทียบให้เห็นภาพ — ทานที่ร้าน หรือ ใส่กล่องกลับบ้าน

เมนูเดียวกัน (create) แต่ลูกค้ามีสองแบบ: นั่งทานในร้าน (browser — อยากได้หน้า HTML) กับ สั่งกลับบ้าน (แอปมือถือหรือโปรแกรมอื่น — อยากได้ JSON) · เชฟทำอาหารเหมือนกัน (save ครั้งเดียว) ต่างกันแค่ตอนส่ง: จัดจาน หรือ ใส่กล่อง · respond_to คือพนักงานที่ถามว่า "ทานที่นี่หรือกลับบ้านคะ"

ที่ไม่เหมือนกัน: ร้านจริงถามลูกค้าด้วยปาก · Rails ดูท้าย URL (.json) หรือป้ายที่ browser ติดมาเอง ลูกค้าไม่ต้องตอบ · และถ้าแอปเราไม่มีลูกค้าสั่งกลับบ้านเลย ส่วน format.json กับไฟล์ .jbuilder 3 ไฟล์ก็เป็นของเกินที่ลบทิ้งได้

เทียบกับ Go: ใน Gin คุณเลือกเองในแต่ละ handler ว่าจะตอบ c.HTML(…) หรือ c.JSON(…) · ถ้าอยากได้ทั้งสองแบบจาก URL เดียว ต้องเขียน if ตรวจเอง · respond_to คือ if นั้นที่ Rails เตรียมไว้ให้

ท่อน 3 — update กับ destroy

  # PATCH/PUT /categories/1 or /categories/1.json
  def update
    respond_to do |format|
      if @category.update(category_params)
        format.html { redirect_to @category, notice: "Category was successfully updated.", status: :see_other }
        format.json { render :show, status: :ok, location: @category }
      else
        format.html { render :edit, status: :unprocessable_content }
        format.json { render json: @category.errors, status: :unprocessable_content }
      end
    end
  end

  # DELETE /categories/1 or /categories/1.json
  def destroy
    @category.destroy!

    respond_to do |format|
      format.html { redirect_to categories_path, notice: "Category was successfully destroyed.", status: :see_other }
      format.json { head :no_content }
    end
  end
  • update หน้าตาเหมือน create ทุกอย่าง ต่างแค่ @category.update(…) แทน new + save (บท 107) และไม่ผ่านก็กลับไปฟอร์มแก้ (:edit)
  • status: :see_other — คือเลข 303 ที่เห็นใน log หัวข้อ 3 · ส่วน status: :ok ฝั่ง JSON คือเลข 200 = "เรียบร้อย"
  • @category.destroy! — ทิ้งแฟ้ม · ตัว ! แปลว่า "ถ้าทิ้งไม่ได้ให้ระเบิด" (กฎ ! บท 110) · ทิ้งเสร็จพาไปหน้ารายการ (categories_path)
  • head :no_content — ฝั่ง JSON ตอบเลข 204 ("เรียบร้อย ไม่มีอะไรส่งกลับ")

  • private — method ใต้คำนี้ route เรียกตรง ๆ ไม่ได้ เป็นผู้ช่วยหลังครัว ไม่ใช่เมนู (บท 102)
  • คอมเมนต์อังกฤษ Use callbacks … ที่ scaffold เขียนมา — คำว่า callbacks ในที่นี้หมายถึง before_action นั่นเอง (ญาติของ callback ฝั่ง model บท 112)
  • Category.find(params.expect(:id)) — หยิบแฟ้มตามเลขที่ใน URL (บท 107) · params.expect(:id) = "ต้องมี id และต้องเป็นค่าธรรมดา" · ถ้าไม่เจอแฟ้ม find ระเบิด และ Rails ตอบ 404 ("ไม่มีหน้านี้") ให้เอง · ผมลอง /categories/99: log ขึ้น Completed 404 Not Found แต่ในเครื่องเรา browser จะโชว์หน้าแดง ActiveRecord::RecordNotFound in CategoriesController#show กับ Couldn't find Category with 'id'="99" — ไม่ใช่โค้ดพัง เป็นหน้าช่วยนักพัฒนา · ลูกค้าบนเว็บจริงจะเห็นแค่หน้า 404
  • params.expect(category: [ :name, :slug, :description ]) — "เปิดกล่อง category (ที่เห็นใน log หัวข้อ 3) แล้วหยิบแค่สามช่องนี้" · ช่องอื่นที่ลูกค้าแอบเขียนมาถูกตัดทิ้ง = strong parameters (บท 117)

✅ ของที่ scaffold ทำถูก (สไลด์หน้า 53 ชมไว้ ผมเห็นด้วยทุกข้อ): ใช้ before_action แทนการเขียน find ซ้ำ 4 ที่ · ใช้ท่า if save … else render พร้อม status 422 · คัดช่องด้วย params.expect ของ Rails 8 · เก็บผู้ช่วยไว้ใต้ private · ถ้าเขียน controller เอง ใช้ไฟล์นี้เป็นแบบได้เลย

_method (method override)
ช่องซ่อนในฟอร์มที่บอก Rails ว่า "ถือว่าเป็น PATCH / DELETE นะ" เพราะฟอร์ม HTML ส่งได้แค่ GET กับ POST · ถาม senior ได้ว่า "ฟอร์มนี้ส่ง POST แต่ log ขึ้น PATCH เพราะ _method ใช่ไหม"

คำถามที่น่าสนใจ: ฟอร์มชิ้นเดียว ทำไมหน้า new ส่งไปสร้าง แต่หน้า edit ส่งไปแก้? ผมดึง HTML ของสองหน้ามาดูเฉพาะแท็กฟอร์มกับปุ่ม: 

<!-- หน้า /categories/new -->
<form action="/categories" accept-charset="UTF-8" method="post">
<input type="submit" name="commit" value="Create Category" data-disable-with="Create Category" />

<!-- หน้า /categories/1/edit -->
<form action="/categories/1" accept-charset="UTF-8" method="post">
<input type="hidden" name="_method" value="patch" />
<input type="submit" name="commit" value="Update Category" data-disable-with="Update Category" />

form_with ถามแฟ้มว่า persisted? ("อยู่ในลิ้นชักแล้วหรือยัง" บท 107): แฟ้มใหม่ → ส่งไป /categories ปุ่ม Create · แฟ้มที่มีเลขที่แล้ว → ส่งไป /categories/1 ปุ่ม Update · _method = "patch" คือป้ายซ่อนที่บอก Rails ให้ถือว่าเป็น PATCH เพราะฟอร์ม HTML ส่งได้แค่ GET กับ POST

ส่วนที่เหลือในแท็กไม่ต้องสนใจ: accept-charset="UTF-8" = ส่งตัวอักษรแบบที่รองรับภาษาไทย · data-disable-with = กดแล้วปุ่มกดซ้ำไม่ได้ระหว่างรอ (กันลูกค้ากดสองที)

ทดสอบความเข้าใจ

ข้อ 1 · ใน controller ที่ scaffold เขียนให้ before_action :set_category, only: %i[ show edit update destroy ] — ทำไม index · new · create ไม่อยู่ในรายการ?

ตัวเลือกที่ 3 ถูก · set_category ทำ Category.find(params.expect(:id)) ซึ่งต้องมี :id ใน URL · ดูตาราง routes หัวข้อ 2: มีแค่ show · edit · update · destroy ที่ URL มี :id · index ดูทุกแผ่น · new กับ create ทำแฟ้มใหม่ที่ยังไม่มีเลขที่

ตัวเลือกที่ 1 ผิด — ทั้งเจ็ดเป็นเมนูธรรมดา (อยู่เหนือ private) · ตัวเลือกที่ 2 ผิด — ถ้าเติม index เข้าไป find จะหาเลขที่ที่ไม่มีแล้วระเบิด · ตัวเลือกที่ 4 ผิด — ปัญหาไม่ได้อยู่ที่วิธีหา แต่อยู่ที่ไม่มีอะไรให้หา

จุดที่ต้องจำ: before_action … only: = "เมนูที่ต้องหยิบแฟ้มเดิมก่อน" · ดูจาก URL ว่ามี :id ไหม

ข้อ 2 · category_params เขียนว่า params.expect(category: [ :name, :slug, :description ]) — บรรทัดนี้ป้องกันอะไรได้?

ตัวเลือกที่ 1 ถูก · strong params คัดช่อง (บท 117) ไม่ได้ดูคน · ตัวเลือกที่ 2 คือ authorization ซึ่ง scaffold ไม่มี (Day 4) · ตัวเลือกที่ 3 คือ presence ของ validation — predict หัวข้อ 3 พิสูจน์แล้วว่าช่องว่างผ่านได้ · ตัวเลือกที่ 4 คือ uniqueness + unique index — console หัวข้อ 6 ได้ slug ซ้ำ 2 แผ่น

จุดที่ต้องจำ: strong params กันรูปร่างของข้อมูล · validation กันค่า · constraint กันทุกทาง · authorization กันคน — สี่อย่างนี้แทนกันไม่ได้

ข้อ 3 · AI ส่ง model มาให้ มีบรรทัด validates :email, uniqueness: true — คำถามแรกจาก checklist ที่ควรถามคืออะไร?

ตัวเลือกที่ 4 ถูก · checklist ข้อ 1 · บท 111 พิสูจน์ว่า uniqueness อย่างเดียวยังได้อีเมลซ้ำเมื่อมีสองคนกดพร้อมกัน · ต้องมีตัวตู้ (unique index) เป็นคนตัดสินสุดท้าย

ตัวเลือกที่ 1 เป็นคำถามที่ดี (ข้อ 6) แต่ไม่เกี่ยวกับบรรทัดนี้ · ตัวเลือกที่ 2 เรื่องข้อความ ไม่ทำให้ข้อมูลเสีย · ตัวเลือกที่ 3 ไม่เกี่ยวกับความถูกต้องของข้อมูลเลย

จุดที่ต้องจำ: เห็น uniqueness → ถามหา unique index · เห็น presence → ถามหา null: false · กฎใน model ต้องมีคู่ที่ตัวตู้

ข้อ 4 · def index; @categories = Category.all; end ที่ scaffold เขียนให้ — ทำงานได้ถูกต้องวันนี้ แล้วจะเป็นปัญหาตอนไหน?

ตัวเลือกที่ 2 ถูก · log หัวข้อ 6: SELECT "categories".* FROM "categories" ไม่มี LIMIT = ขอทุกแผ่นทุกครั้ง · 3 แผ่นเร็ว · หลายหมื่นแผ่นทั้งช้าและกินหน่วยความจำ · checklist ข้อ 6 · แก้ด้วย limit (บท 113) หรือการแบ่งหน้า

ตัวเลือกที่ 1 ผิด — คนละคนก็ได้ผลแยกกัน ไม่ซ้ำกันเอง · ตัวเลือกที่ 3 ผิด — all ไม่ได้หาแถวไหนเจาะจง ลบไปแล้วก็แค่ไม่โชว์ (เราลบแฟ้มที่ 2 แล้วหน้ารายการยังขึ้นปกติ) · ตัวเลือกที่ 4 ผิด — all ยังใช้ได้ใน Rails 8.1.4 ที่ผมรัน

จุดที่ต้องจำ: โค้ดที่ "ทำงานได้" กับโค้ดที่ "ทำงานได้ตอนข้อมูลเยอะ" คนละเรื่อง · Model.all ใน index = ระเบิดเวลา

ถามกลับได้เลย — ถ้าอ่าน controller แล้วติดบรรทัดไหน หรืออยากรู้ว่า checklist ข้อไหนใช้กับโค้ดในงานของคุณยังไง ก็อปโค้ดนั้นมาถาม AI ได้เลยว่า "ไล่ checklist 8 ข้อนี้กับโค้ดนี้ให้หน่อย"
