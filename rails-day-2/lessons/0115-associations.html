Association — บทความ ผู้เขียน คอมเมนต์ ผูกกันยังไง

~25 นาที (ลงมือใน console เยอะ) · ควรผ่าน บทเรียน 107 (console CRUD + ข้อมูลตัวอย่าง) และ บทเรียน 113 (query) มาก่อน

ในแอปบล็อกของเรา คอมเมนต์ต้องรู้ว่ามันอยู่ใต้บทความไหน · บทความต้องรู้ว่าใครเขียน
บทนี้จะอธิบายว่าข้อมูลสองลิ้นชัก "ผูกกัน" ด้วยอะไร แล้วให้คุณจำกฎข้อเดียวที่ใช้ตัดสินได้ทุกกรณีว่าต้องเขียน belongs_to หรือ has_many ไว้ที่ไหน
อ่านจบแล้วคุณจะสร้างคอมเมนต์ใต้บทความได้โดยไม่ต้องพิมพ์เลขที่บทความเอง · ตั้งชื่อทางลัดอย่าง "บทความที่เผยแพร่แล้วของคนนี้" ได้ · และติดป้าย (tag) ให้บทความได้ ซึ่งเป็นความสัมพันธ์แบบ "หลายต่อหลาย"

1 · ข้อมูลที่ผูกกัน — ใบคอมเมนต์มีช่อง "เป็นของบทความเลขที่ …"

แอปบล็อกเก็บของไว้ 3 ลิ้นชัก: ผู้ใช้ (users) · บทความ (posts) · คอมเมนต์ (comments) · คอมเมนต์ "น่ากินมาก" ต้องรู้ว่ามันอยู่ใต้บทความไหน และใครเป็นคนเขียน

วิธีที่ฐานข้อมูลใช้คือไม่ก๊อปบทความทั้งเรื่องมาไว้บนใบคอมเมนต์ แต่จดแค่เลขที่ของบทความ (id) ไว้ในช่องหนึ่งบนใบคอมเมนต์ · ช่องนั้นชื่อ post_id แปลว่า "เป็นของบทความเลขที่ …"

นี่คือหน้าตาจริงของสองลิ้นชักในแอปเรา (ตัดมาบางแถว บางช่อง):

ลิ้นชัก posts ลิ้นชัก comments ┌─────┬──────────────────┐ ┌─────┬──────────────────────┬─────────┬─────────┐ │ id │ title │ │ id │ body │ post_id │ user_id │ ├─────┼──────────────────┤ ├─────┼──────────────────────┼─────────┼─────────┤ │ 1 │ ต้มยำกุ้งน้ำข้น │ │ 1 │ น่ากินมาก │ 1 │ 2 │ │ 2 │ ส้มตำปูปลาร้า │ │ 2 │ ขอสูตรน้ำพริกเผาด้วย │ 1 │ 3 │ └─────┴──────────────────┘ │ 3 │ เผ็ดแค่ไหนดี │ 2 │ 3 │ └─────┴──────────────────────┴─────────┴─────────┘ post_id ของคอมเมนต์ 1 กับ 2 เป็น 1 → อยู่ใต้ "ต้มยำกุ้งน้ำข้น" · คอมเมนต์ 3 อยู่ใต้ "ส้มตำปูปลาร้า"

ทำไมช่องนี้อยู่บนใบคอมเมนต์ ไม่ใช่บนบทความ? บทความหนึ่งชิ้นมีคอมเมนต์ได้ 0 อัน 2 อัน หรือ 100 อัน — เราเพิ่มช่องบนแฟ้มบทความให้พอทุกกรณีไม่ได้ · แต่คอมเมนต์หนึ่งอันอยู่ใต้บทความได้แค่ชิ้นเดียวเสมอ แค่ช่องเดียวก็พอ
ด้วยเหตุผลเดียวกัน บทความก็มีช่อง user_id = "เขียนโดยผู้ใช้เลขที่ …"

📦 เทียบให้เห็นภาพ — พัสดุที่ห้องนิติของคอนโด

พัสดุทุกกล่องที่วางบนชั้นห้องนิติมีเลขห้อง "1203" เขียนไว้ · ห้อง 1203 ไม่ต้องจดว่าตัวเองมีพัสดุกี่กล่อง อยากรู้ว่าห้อง 1203 มีพัสดุอะไรบ้าง นิติก็ไล่หากล่องที่เขียนว่า "1203"
ตู้แฟ้มของร้านเราก็เหมือนกัน: ใบคอมเมนต์มีช่อง "เป็นของบทความเลขที่ …" (post_id) · อยากรู้ว่าบทความเลข 1 มีคอมเมนต์อะไร คนดูแลสต็อกก็ไปลิ้นชัก comments หยิบทุกแผ่นที่ช่องนี้เขียนว่า 1

ที่ไม่เหมือนกัน: คนส่งของเขียน "ห้อง 9999" ทั้งที่ตึกมีแค่ 30 ชั้นก็ไม่มีใครห้าม · แต่ตู้ของเราตั้งกฎไว้ (foreign key — เดี๋ยวเห็นในหัวข้อ 2) ว่าเลขที่ต้องมีแฟ้มนั้นอยู่จริง ไม่งั้นไม่รับ · และเลขบนใบคอมเมนต์ไม่ใช่ตัวบทความ — ถ้าวันหนึ่งแฟ้มบทความถูกทิ้ง ใบคอมเมนต์ที่อ้างถึงจะเป็นยังไง อยู่ใน บท 116

🗣 ศัพท์ที่เพิ่งเรียนไป
primary key
ช่องที่เป็น "เลขที่แฟ้ม" ไม่ซ้ำกันในลิ้นชัก · ใน Rails คือช่อง id ที่สร้างให้เองทุกตาราง · ถาม senior ได้ว่า "ตารางนี้ใช้ id ธรรมดาเป็น primary key หรือใช้แบบอื่น"
foreign key
ช่องที่เก็บเลขที่ของแฟ้มในลิ้นชักอื่น เช่น comments.post_id · ชื่อมักลงท้ายด้วย _id · คำเดียวกันยังใช้เรียก "กฎที่ตู้" ที่บังคับว่าเลขต้องมีอยู่จริงด้วย · พิมพ์บอก AI ได้ว่า "comments.post_id is a foreign key to posts.id"
association
การบอก model ว่า "แฟ้มลิ้นชักนี้ผูกกับลิ้นชักนั้น" เพื่อให้ Rails สร้าง method อย่าง comment.post ให้ · ถาม senior ได้ว่า "Post กับ Comment ใน repo นี้ผูก association ไว้ครบสองฝั่งไหม"

2 · กฎข้อเดียว: belongs_to อยู่ฝั่งที่มีคอลัมน์ _id

ช่อง _id อยู่ตารางไหน เปิดดูได้ในแปลนตู้ db/schema.rb (บท 108) · นี่คือของจริงจากแอปเรา ตัดมาเฉพาะส่วนที่เกี่ยว: 

# db/schema.rb (ตัดมาบางส่วน)
  create_table "comments", force: :cascade do |t|
    t.text "body"
    t.bigint "post_id", null: false
    t.bigint "user_id", null: false
    …
  end

  create_table "posts", force: :cascade do |t|
    t.string "title"
    …
    t.bigint "user_id", null: false
    …
  end

  create_table "users", force: :cascade do |t|
    t.string "name"
    t.string "email"
    …
  end

  add_foreign_key "comments", "posts"
  add_foreign_key "comments", "users"
  add_foreign_key "posts", "users"
  • t.bigint "post_id", null: false — ลิ้นชัก comments มีช่อง post_id เก็บจำนวนเต็ม (bigint = จำนวนเต็มขนาดใหญ่ ใช้เก็บเลขที่) · null: false = ห้ามเว้นว่าง
  • ลิ้นชัก posts มีช่อง user_id · ลิ้นชัก users ไม่มีช่อง _id ของใครเลย
  • add_foreign_key "comments", "posts" — กฎที่ตัวตู้: "เลขใน comments.post_id ต้องเป็น id ที่มีอยู่จริงในลิ้นชัก posts"
  • … คือส่วนที่ผมตัดออก (ช่องอื่นที่ไม่เกี่ยว เช่น body · published · ช่องเวลาสร้าง/แก้ และสารบัญ t.index ที่ช่วยให้ค้นเร็ว — บท 109)
  • force: :cascade — ข้ามได้ แปลว่า "ถ้ามีลิ้นชักชื่อนี้อยู่แล้วให้รื้อทิ้งสร้างใหม่" ใช้ตอนตั้งตู้ใหม่จากแปลน (บท 108) · ไม่เกี่ยวกับความสัมพันธ์ในบทนี้

ส่วน model ทั้งสามไฟล์ในแอปเราเขียนไว้แบบนี้ (ตั้งแต่บท 107):

# app/models/comment.rb
class Comment < ApplicationRecord
  belongs_to :post   # comments มี post_id
  belongs_to :user   # comments มี user_id
end

# app/models/post.rb
class Post < ApplicationRecord
  belongs_to :user   # posts มี user_id
  has_many :comments # post_id อยู่ฝั่ง comments
end

# app/models/user.rb
class User < ApplicationRecord
  has_many :posts    # user_id อยู่ฝั่ง posts
  has_many :comments # user_id อยู่ฝั่ง comments
end

สังเกตว่าทุกบรรทัดตอบได้ด้วยกฎเดียว: ตารางไหนมีช่อง xxx_id → model ของตารางนั้นเขียน belongs_to :xxx · ฝั่งที่ถูกชี้ถึงเขียน has_many (มีได้หลายอัน)
users ไม่มีช่อง _id เลย → User จึงไม่มี belongs_to สักบรรทัด

✅ กฎข้อเดียวที่ต้องจำ: belongs_to อยู่ฝั่งที่มีคอลัมน์ _id · สงสัยเมื่อไหร่ เปิด db/schema.rb หาว่าช่อง _id อยู่ใน create_table ไหน ตอบได้ทุกกรณี

type Post struct {
    ID       uint
    Title    string
    Comments []Comment // has many: ไม่มีคอลัมน์เพิ่มในตาราง posts
}

type Comment struct {
    ID     uint
    Body   string
    PostID uint // คอลัมน์ post_id อยู่ฝั่งนี้
    Post   Post // belongs to
}

// อยากได้คอมเมนต์มาด้วย ต้องสั่ง Preload เอง
db.Preload("Comments").First(&post, 1)

กฎเดียวกันเป๊ะ: PostID อยู่ใน Comment · ต่างกันที่ GORM ไม่ไปหยิบให้ถ้าไม่สั่ง Preload (ผมลอง db.First(&post, 1) เฉย ๆ ได้ len(post.Comments) เป็น 0) · Rails ไปหยิบให้เองตอนที่คุณใช้ post.comments ไม่ต้องสั่งล่วงหน้า — สะดวก แต่ก็เผลอไปตู้บ่อยเกินได้ (นั่นคือ N+1 ใน บท 114)

4 · ความสัมพันธ์ 5 แบบ — ใช้กฎเดียวกันทั้งหมด

Rails มีคำสั่งผูกความสัมพันธ์ 5 แบบ · ทุกแบบตอบด้วยคำถามเดียว "ช่อง _id อยู่ตารางไหน" (แถว has_one กับ habtm ไม่มีในแอปเรา เป็นตัวอย่างให้เห็นภาพเฉย ๆ):

คำสั่งภาษาคนตัวอย่างในบล็อกช่อง _id อยู่ที่ได้ method
belongs_to"ฉันเป็นของ…หนึ่งตัว" Comment เป็นของ Postcomments.post_id (ตารางตัวเอง)comment.post
has_many"ฉันมี…ได้หลายตัว" Post มีหลาย Commentไม่มีในตารางตัวเอง (อยู่ที่ comments)post.comments
has_one"ฉันมี…ได้แค่ตัวเดียว" User มีหน้าโปรไฟล์ Profile หนึ่งหน้าprofiles.user_id (อีกตาราง)user.profile
has_many :through"หลายต่อหลาย ผ่านตารางกลางที่มี model" Post ติดได้หลาย Tag · Tag อยู่ได้หลาย Postตารางกลาง taggings มีทั้ง post_id และ tag_idpost.tags
has_and_belongs_to_many
(เรียกย่อว่า habtm)		"หลายต่อหลาย ตารางกลางเปล่า ๆ ไม่มี model" เหมือนแถวบนตารางกลาง posts_tagspost.tags

คู่ที่คนสับสนบ่อยคือ belongs_to กับ has_one เพราะภาษาอังกฤษฟังคล้ายกัน ("โปรไฟล์เป็นของผู้ใช้" กับ "ผู้ใช้มีโปรไฟล์") · ไม่ต้องเดาจากความหมาย ใช้กฎ: ช่อง user_id อยู่ที่ profiles → Profile belongs_to :user · User เป็นฝั่ง has_one

🗣 ศัพท์ที่ใช้คุยเรื่องรูปแบบความสัมพันธ์
one-to-many (1 ต่อหลาย)
หนึ่งบทความ หลายคอมเมนต์ · ในโค้ดคือคู่ has_many + belongs_to · ถาม senior ได้ว่า "Post กับ Comment เป็น one-to-many ใช่ไหม foreign key อยู่ที่ comments"
one-to-one (1 ต่อ 1)
หนึ่งผู้ใช้ หนึ่งโปรไฟล์ · คู่ has_one + belongs_to · พิมพ์บอก AI ได้ว่า "User has_one Profile, profiles table has user_id"
many-to-many (หลายต่อหลาย)
บทความหลายชิ้น กับป้ายหลายป้าย · ต้องมีตารางกลางเสมอ (หัวข้อ 7) · ถาม senior ได้ว่า "many-to-many ตัวนี้ใช้ has_many :through หรือ habtm"

🗣 ศัพท์ของ method ที่ได้ฟรี
association methods / collection methods
method ที่ Rails สร้างให้จาก has_many เช่น create · build · << · comment_ids · พิมพ์บอก AI ได้ว่า "create the comment through the association (post.comments.create) instead of setting post_id manually"
build vs create
build = สร้างในหน่วยความจำ ยังไม่ลง DB · create = สร้างแล้ว save เลย · มี create! ที่ระเบิดถ้าเก็บไม่ได้ด้วย · ถาม senior ได้ว่า "ตรงนี้ควร build ก่อนแล้วค่อย save หรือ create ไปเลย"
required belongs_to
belongs_to ใน Rails สมัยนี้บังคับว่าต้องมีของที่ชี้ถึงเสมอ ได้ error "… must exist" · ถ้าอยากยอมให้ไม่มีเจ้าของได้ เขียน belongs_to :post, optional: true (แอปเราไม่ได้ใช้) · ถาม senior ได้ว่า "comment ตัวนี้ควร optional: true ไหม หรือต้องมี post เสมอ"

6 · ตั้งชื่อทางลัด — "บทความที่เผยแพร่แล้วของคนนี้"

# app/models/user.rb
class User < ApplicationRecord
  has_many :posts
  has_many :comments
  has_many :published_posts, -> { where(published: true) }, class_name: "Post"

  • ทำไมต้องห่อ? ถ้าเขียน where(…) เปล่า ๆ Ruby จะพยายามรันมันทันทีตอนอ่านไฟล์ ซึ่งตอนนั้นยังไม่รู้ว่าเป็นผู้ใช้คนไหน · ผมลองแล้ว Rails ไม่รับ ได้ NoMethodError

7 · หลายต่อหลาย — ติดป้ายให้บทความด้วย has_many :through

ตัวเลือกที่ 1 ผิด เพราะ has_many ใช้กับฝั่งที่ไม่มีช่อง _id · การกดถูกใจหนึ่งครั้งเป็นของบทความเดียว ไม่ใช่หลายบทความ · ตัวเลือกที่ 3 ผิด เพราะ has_one หมายถึงช่อง _id อยู่อีกตาราง (เช่น profiles.user_id) · ตัวเลือกที่ 4 ผิด เพราะ post.rb ใส่ has_many :likes ได้ก็จริง แต่ฝั่ง Like ต้องมี belongs_to ด้วย ไม่งั้นถาม like.post ไม่ได้

จุดที่ต้องจำ: ช่อง _id อยู่ตารางไหน model นั้นเขียน belongs_to

จุดที่ต้องจำ: สร้างลูกผ่านแม่ (post.comments.create) แทนการกรอก post_id เอง

ตัวเลือกที่ 1 ถูก — ผลจริงในหัวข้อ 5: count ถามตู้ได้ 3 · size นับตู้ 3 + ที่ถือในมือ 1 = 4

ตัวเลือกที่ 2 ผิด เพราะ build ยังไม่ลงตู้ count จึงไม่เห็น · ตัวเลือกที่ 3 ผิด เพราะกลับด้าน — ตัวที่เห็นของในมือคือ size · ตัวเลือกที่ 4 ผิด เพราะ size รวมของที่ build ไว้ด้วย

จุดที่ต้องจำ: build = อยู่ในมือ · count = ถามตู้อย่างเดียว · size = ตู้ + ในมือ

ทีมอยากเก็บว่า "ใครเป็นคนติดป้ายนี้ และติดเมื่อไหร่" ในความสัมพันธ์บทความ–ป้าย ควรเลือกแบบไหน?

ตัวเลือกที่ 3 ถูก — ข้อมูล "ใครติด · ติดเมื่อไหร่" เป็นของใบจับคู่ · :through มี Tagging ที่เติมช่องได้ (และมีช่องเวลาสร้างให้แล้ว)

ตัวเลือกที่ 1 ผิด เพราะตารางกลางของ habtm ไม่มี model ให้อ่าน/เขียนช่องเพิ่ม (ตาราง posts_tags มีแค่ post_id กับ tag_id) · ตัวเลือกที่ 2 ผิด เพราะบทความหนึ่งมีหลายป้าย ช่องเดียวเก็บไม่พอ · ตัวเลือกที่ 4 ผิด เพราะ has_one คือมีได้แค่ตัวเดียวตลอดไป ไม่ใช่หลายต่อหลาย

จุดที่ต้องจำ: หลายต่อหลาย + อาจมีช่องเพิ่ม → has_many :through ตั้งแต่แรก
