N+1 — โค้ด 3 บรรทัดที่เดินไปตู้ 101 รอบ

~20 นาที · ควรผ่าน บทเรียน 113 (ใบเบิกของ · อ่าน log นับ query) และ บทเรียน 107 (ข้อมูลตัวอย่าง · post.user) มาก่อน

ปัญหาที่เจอกันทุกทีม: หน้าเว็บที่โค้ดดูธรรมดามาก แต่ช้าลงเรื่อย ๆ ตามจำนวนบทความ
อ่านจบบทนี้ คุณจะมองเห็นปัญหาที่ชื่อ N+1 ใน log ได้เอง · นับได้ว่าหน้าหนึ่งไปถามฐานข้อมูลกี่รอบ · แก้ด้วยคำเดียว includes · และรู้ว่าเมื่อไหร่ต้องใช้ preload หรือ eager_load แทน
ประโยคที่จะติดตัวไปจากบทนี้: N+1 ไม่ได้อ่านจากโค้ด — อ่านจาก log

🔁 ทวนก่อนเริ่ม — คำจากบทก่อน ๆ ที่บทนี้ใช้

  • model · ลิ้นชัก · แฟ้ม (บท 106) — Post คือคนดูแลสต็อกของลิ้นชัก posts · หนึ่งแฟ้ม = บทความหนึ่งชิ้น (หนึ่งแถว) · ช่องบนแฟ้ม = คอลัมน์
  • post.user (บท 107) — "ขอผู้เขียนของบทความนี้" · ใช้ได้เพราะ Post เขียนไว้ว่า belongs_to :user (ละเอียดในบท 115)
  • ใบเบิกของ (บท 113) — Post.all · Post.where(…) ยังไม่ไปตู้ จนกว่าจะเริ่มใช้ข้อมูลจริง เช่น วน each · และ count = ให้ตู้นับใหม่เสมอ · size = ถ้าแฟ้มมาอยู่บนโต๊ะแล้ว นับบนโต๊ะ
  • log ของ server (บท 113) — บรรทัด Post Load … = ไปตู้หนึ่งรอบ · ↳ ไฟล์:บรรทัด = บรรทัดไหนสั่ง · (N queries) ท้ายใบสั่ง = รวมกี่รอบ
  • map · &:title (บท 92) — map วนทีละชิ้นแล้วเก็บผลเป็นรายการใหม่ · map(&:title) = map { |p| p.title } แบบย่อ

🧰 ตรวจด้วย Ruby 4.0.9 · Rails 8.1.4 · PostgreSQL 17 (สไลด์ใช้ Ruby 4.0.6 · Rails 8.1.3 — รุ่นแก้บั๊กในสายเดียวกัน ใช้แทนกันได้)

🗂 ตัวอย่างในบทนี้ใช้ตาราง users / posts / comments และข้อมูลตัวอย่าง (seeds) ชุดเดียวกับที่สร้างไว้ใน บท 107 — บทความ 6 ชิ้น · สมชาย สมหญิง มานะ เขียนคนละ 2 ชิ้น · คอมเมนต์ 7 อัน

ผลทุกก้อนรันจริงแล้วก็อปมา · ตัดบรรทัดที่ไม่เกี่ยวเป็น … · เวลา (ms) · วันที่ · เลข 0x… ของคุณจะไม่ตรงกับในบท และจอคุณจะมีสี

ภาพก่อนโค้ด: ขอชื่อผู้เขียน 6 คน ต้องเดินไปตู้ 7 รอบ

สมมติหน้าแรกของบล็อกต้องโชว์ "ชื่อบทความ — โดย ชื่อผู้เขียน" ทั้ง 6 ชิ้น
ชื่อบทความอยู่ในลิ้นชัก posts · แต่ชื่อผู้เขียนอยู่อีกลิ้นชักหนึ่ง คือ users · บนแฟ้มบทความมีแค่ช่อง user_id (เลขที่ของผู้เขียน) ไม่มีชื่อ

ถ้าเขียนโค้ดแบบที่คนส่วนใหญ่เขียนตามธรรมชาติ คนดูแลสต็อกจะทำแบบนี้:

รอบที่ 1 ลิ้นชัก posts → หยิบแฟ้มบทความมาทั้ง 6 แผ่น ← นี่คือ "1" ได้แฟ้มแล้ว เริ่มโชว์ทีละชิ้น … ชิ้นแรกเขียนว่า user_id = 1 รอบที่ 2 ลิ้นชัก users → หาแฟ้มเลขที่ 1 → "สมชาย" รอบที่ 3 ลิ้นชัก users → หาแฟ้มเลขที่ 1 → "สมชาย" (คนเดิม! แต่เดินไปอีก) รอบที่ 4 ลิ้นชัก users → หาแฟ้มเลขที่ 2 → "สมหญิง" รอบที่ 5 ลิ้นชัก users → หาแฟ้มเลขที่ 2 → "สมหญิง" รอบที่ 6 ลิ้นชัก users → หาแฟ้มเลขที่ 3 → "มานะ" รอบที่ 7 ลิ้นชัก users → หาแฟ้มเลขที่ 3 → "มานะ" ← 6 รอบนี้คือ "N" รวม 1 + 6 = 7 รอบ · ถ้ามีบทความ 100 ชิ้น = 1 + 100 = 101 รอบ

ปัญหานี้ชื่อ N+1 — ไปตู้ 1 รอบเพื่อเอารายการ แล้วไปอีก N รอบ (หนึ่งรอบต่อหนึ่งชิ้นในรายการ) · 6 ชิ้นยังไม่รู้สึก · แต่ 100 ชิ้นคือ 101 รอบ และทุกรอบต้องรอฐานข้อมูลตอบ หน้าเว็บจึงช้าลงตามจำนวนข้อมูลไปเรื่อย ๆ

🚶 เทียบให้เห็นภาพ — เดินไปตู้ 101 รอบ หยิบทีละแผ่น

เชฟสั่งคนดูแลสต็อกว่า "เอาแฟ้มบทความมา" · ได้มาแล้วเชฟอ่านทีละแผ่น · เจอช่อง "ผู้เขียนเลขที่ 1" ก็สั่ง "ไปหยิบแฟ้มผู้เขียนเลขที่ 1 มา" · คนดูแลสต็อกเดินไปลิ้นชัก users กลับมา · แผ่นถัดไปก็สั่งใหม่ เดินใหม่ — ทีละแผ่น ทีละรอบ
ทางที่ฉลาดกว่า: อ่านแฟ้มบทความให้ครบก่อน จดเลขผู้เขียนทั้งหมด (1, 2, 3) แล้วเดินไปรอบเดียว หยิบมาทั้งตะกร้า

ที่ไม่เหมือนกัน: คนดูแลสต็อกตัวจริงเดินไปสองสามรอบก็คงฉุกคิดเองว่า "เดี๋ยวนะ ขอเลขให้ครบก่อนดีกว่า" · แต่ Rails ไม่ฉุกคิดเอง — มันทำตามที่โค้ดสั่งเป๊ะ ๆ ทีละบรรทัด เราต้องบอกมันล่วงหน้าเองว่า "เดี๋ยวจะใช้ผู้เขียนด้วยนะ"

🗣 ศัพท์ที่เพิ่งเรียนไป
N+1 query (N+1 problem)
ไปฐานข้อมูล 1 รอบเอารายการ แล้วไปเพิ่มอีกหนึ่งรอบต่อทุกชิ้นในรายการ · เป็นสาเหตุอันดับต้น ๆ ที่หน้าเว็บ Rails ช้า · พิมพ์บอก AI ได้ว่า “this page has an N+1 query on post.user, here is the log”
query
คำสั่ง SQL หนึ่งประโยคที่ส่งไปฐานข้อมูล = เดินไปตู้หนึ่งรอบ · เวลาคนพูดว่า "หน้านี้ยิง 7 query" แปลว่าไปตู้ 7 รอบ · ถาม senior ได้ว่า “หน้านี้ควรยิงไม่เกินกี่ query ถึงจะถือว่าโอเค”

คำนี้เจอแล้วในบท 113 · หลักเดียวกัน คือ "ยังไม่ไปตู้จนกว่าจะต้องใช้" · บท 113 ใช้กับใบเบิกของ (Post.where(…)) · บทนี้ใช้กับผู้เขียนของแต่ละบทความ (post.user)

เทียบกับ Go (GORM บท 27): ใน Go ถ้าจะทำ N+1 คุณต้องเขียนคำสั่งไปตู้ในลูปเองกับมือ — เห็นชัดตั้งแต่อ่านโค้ด:

// Go + GORM — N+1 แบบเห็นด้วยตา
var posts []Post
db.Find(&posts)                  // ไปตู้ 1 รอบ
for _, p := range posts {
    var u User
    db.First(&u, p.UserID)        // ไปตู้อีก 1 รอบ ต่อบทความ 1 ชิ้น
    fmt.Println(u.Name)
}

ฝั่ง Rails คำว่า db.First ถูกซ่อนอยู่ใน p.user · โค้ดสั้นและอ่านง่ายกว่า แต่มองไม่เห็นว่ามีการไปตู้ · นี่คือเหตุผลของประโยคหลักวันนี้: N+1 ไม่ได้อ่านจากโค้ด — อ่านจาก log

🗣 ศัพท์ที่เพิ่งเรียนไป
lazy loading
ยังไม่โหลดของที่ผูกกันอยู่ (เช่น ผู้เขียนของบทความ) จนกว่าจะมีคนถามถึง · เป็นค่าเริ่มต้นของ Rails · สะดวก แต่ถ้าถามในลูปจะกลายเป็น N+1 · ถาม senior ได้ว่า “ตรงนี้ post.user ถูก lazy load ในลูปหรือเปล่า”
association
ความสัมพันธ์ระหว่างสองลิ้นชัก เช่น บทความ เป็นของ ผู้ใช้ (belongs_to :user) · post.user คือการเดินตามความสัมพันธ์นั้น (ละเอียดในบท 115) · พิมพ์บอก AI ได้ว่า “Post belongs_to :user, I loop over posts and call post.user” — AI จะรู้ทันทีว่าเสี่ยง N+1

แก้ด้วยคำเดียว: includes

ทางแก้คือบอก Rails ล่วงหน้าตอนเขียนใบเบิกว่า "เดี๋ยวจะใช้ผู้เขียนด้วยนะ หยิบมาเผื่อเลย" · คำที่ใช้บอกคือ includes(:user) — ชื่อ :user ต้องตรงกับที่เขียนใน model (belongs_to :user)

  • WHERE "users"."id" IN (1, 2, 3) — IN (…) แปลว่า "เฉพาะแผ่นที่เลขที่เป็นตัวใดตัวหนึ่งในวงเล็บ" · ทั้งประโยค = "ขอแฟ้มทุกช่องจากลิ้นชัก users เฉพาะเลขที่ 1, 2 หรือ 3" — Rails อ่านแฟ้มบทความแล้วรวบเลขผู้เขียนมาให้เอง ซ้ำก็ตัดให้
  • หลังจากนั้น p.user ไม่ไปตู้แล้ว เพราะผู้เขียนทุกคนถูกหยิบมารอไว้แล้ว

ถ้ามีบทความ 100 ชิ้น ก็ยังเป็น 2 รอบ · จำนวนรอบไม่โตตามข้อมูลอีกต่อไป — ต่างจากเดิมที่ 100 ชิ้น = 101 รอบ

🧺 เทียบให้เห็นภาพ — เขียนใบเบิกทีเดียว หยิบมาทั้งตะกร้า

includes(:user) เหมือนเขียนเพิ่มท้ายใบเบิกว่า "พร้อมแฟ้มผู้เขียนของทุกแผ่น" · คนดูแลสต็อกหยิบแฟ้มบทความมาก่อน จดเลขผู้เขียนที่เจอ (1, 2, 3) แล้วเดินไปลิ้นชัก users รอบเดียว หยิบมาใส่ตะกร้าทั้งสามแผ่น · เชฟอ่านบทความแผ่นไหน ก็หยิบผู้เขียนจากตะกร้าข้างตัวได้เลย

ที่ไม่เหมือนกัน: ตะกร้าจริงหยิบของเกินมาก็แค่หนัก · แต่ includes ของที่ไม่ได้ใช้ ก็ยังเดินไปหยิบจริง เสียหนึ่งรอบฟรี ๆ — อย่าใส่ includes เผื่อไว้ทุกที่ ใส่เฉพาะของที่หน้านั้นใช้จริง

includes · preload · eager_load — สามคำ สองวิธี

includes ไม่ใช่คำเดียวที่ทำแบบนี้ได้ · Rails มีวิธีหยิบของที่ผูกกันมาล่วงหน้า สองวิธีจริง ๆ และมีคำสั่งเรียกแต่ละวิธีตรง ๆ · includes คือ "ให้ Rails เลือกวิธีให้"

ประโยคนี้ยาว แต่อ่านแค่สามท่อนก็พอ:

  • Post Eager Load — ป้ายหน้าบรรทัดเปลี่ยนจาก Post Load · และมีบรรทัดเดียว ไม่มี User Load ตามมา
  • SELECT "posts"."id" AS t0_r0, … "users"."name" AS t1_r1, … — ขอทุกช่องของทั้งสองลิ้นชัก · AS t0_r0 คือตั้งชื่อเล่นให้แต่ละช่อง กันไม่ให้ id ของสองลิ้นชักชนกัน (ไม่ต้องอ่าน)
  • FROM "posts" LEFT OUTER JOIN "users" — JOIN = "เอาแฟ้มจากสองลิ้นชักมาวางคู่กันเป็นแผ่นเดียว" · LEFT OUTER = ถึงบทความไหนหาผู้เขียนไม่เจอ ก็ยังเอาบทความนั้นมา (ช่องผู้เขียนว่างไว้)
  • ON "users"."id" = "posts"."user_id" — กติกาการจับคู่: "ผู้ใช้เลขที่ … คู่กับบทความที่ช่อง user_id เป็นเลขเดียวกัน"

preload = คนดูแลสต็อกเดินสองรอบ ได้สองกองมาวางบนโต๊ะ: กองบทความ กับกองผู้เขียน · Rails จับคู่ให้บนโต๊ะเอง · eager_load = ขอให้ห้องเก็บของถ่ายเอกสารแฟ้มบทความเย็บติดกับแฟ้มผู้เขียนมาเป็นแผ่นเดียว เดินรอบเดียว · includes = บอกคนดูแลสต็อกว่า "เลือกวิธีเองเลย"

ที่ไม่เหมือนกัน: ในชีวิตจริง "รอบเดียว" ดูดีกว่าเสมอ · แต่ในฐานข้อมูลไม่แน่ — ถ้าบทความหนึ่งมีคอมเมนต์ 50 อัน แผ่นที่เย็บติดกันจะมีข้อมูลบทความซ้ำ 50 แผ่น (สไลด์หน้า 34) ส่งของซ้ำมาเยอะ · บางครั้งสองรอบเบากว่า

เทียบกับ Go: GORM ก็มีสองแบบเหมือนกัน · db.Preload("User") = แบบ preload (แยกไปสองรอบ) · db.Joins("User") = แบบ eager_load (เอกสาร GORM เรียกว่า Joins Preloading — ใช้ JOIN ไปรอบเดียว) · ต่างกันที่ GORM ไม่มีตัวที่ "เลือกให้เอง" แบบ includes คุณต้องเลือกเองทุกครั้ง

ข้อมูลเยอะ ๆ: find_each — ยกแฟ้มทีละลัง ไม่ยกทั้งตู้

ปัญหานี้คนละเรื่องกับ N+1 แต่มักเจอคู่กัน · Post.all.each = หยิบแฟ้มทุกแผ่นมากองไว้ในหน่วยความจำ (RAM) ทีเดียว แล้วค่อยวน · 6 แผ่นไม่เป็นไร · สไลด์หน้า 36 ยกตัวอย่าง 2 ล้านแถวบนเครื่อง RAM 2 GB — กองไม่พอ โปรแกรมพัง

find_each วนได้เหมือน each แต่หยิบมาทีละชุด · ลองชุดละ 2 แผ่นกับข้อมูลเรา (ผลจริง):

wongnok-blog(dev):001> Post.find_each(batch_size: 2) { |p| puts p.title }

  • batch_size: 2 — ชุดละ 2 แผ่น (ค่าเริ่มต้นคือ 1000 · ใช้ 2 แค่ให้เห็นกับข้อมูล 6 แผ่น)
  • ลัง 1: ORDER BY "posts"."id" ASC LIMIT 2 = "เรียงตามเลขที่น้อยไปมาก เอา 2 แผ่นแรก" → ได้เลขที่ 1, 2
  • ลัง 2: WHERE "posts"."id" > 2 … LIMIT 2 = "เลขที่มากกว่า 2 เอามา 2 แผ่น" — จำเลขสุดท้ายของลังก่อน แล้วต่อจากตรงนั้น
  • ลังสุดท้าย id > 6 ไม่ได้อะไรกลับมา → รู้ว่าหมดแล้ว จบ · ในหน่วยความจำมีแฟ้มไม่เกิน 2 แผ่นตลอดเวลา
  • => nil — ค่าที่ find_each คืนมาเมื่อวนจบ ไม่ต้องสนใจ (ของที่เราอยากเห็นคือชื่อที่ puts พิมพ์ออกมา)

เทียบกับ Go: GORM มี FindInBatches ทำหน้าที่เดียวกัน — db.FindInBatches(&results, 100, func(tx *gorm.DB, batch int) error { … }) = หยิบมาชุดละ 100 แล้วส่งให้ฟังก์ชันของเราทีละชุด

📦 เทียบให้เห็นภาพ — ยกแฟ้มทีละลัง

ต้องตรวจแฟ้มทุกแผ่นในตู้ · all.each = ยกแฟ้มทั้งตู้มากองบนโต๊ะทีเดียว — โต๊ะเล็ก กองไม่พอ ล้ม · find_each = ยกมาทีละลัง ตรวจเสร็จเก็บคืน แล้วยกลังถัดไป · จดไว้ว่าลังที่แล้วจบที่แฟ้มเลขอะไร จะได้ต่อถูก

ที่ไม่เหมือนกัน: ยกทีละลังจริง ๆ คุณเลือกได้ว่าจะไล่ตามวันที่หรือตามชื่อ · แต่ find_each ไล่ตามเลขที่ (id) เสมอ — ถ้าสั่งเรียงแบบอื่นไว้ มันทิ้งให้เลย (ดูกล่องเตือนข้างล่าง)

⚠️ เรียงเองไม่ได้ — ลอง Post.order(views: :desc).find_each(batch_size: 2) { … } ได้ข้อความนี้จริง แล้วลำดับออกมาตามเลขที่เหมือนเดิม:

Scoped order is ignored, use :cursor with :order to configure custom order.
  Post Load (1.7ms)  SELECT "posts".* FROM "posts" ORDER BY "posts"."id" ASC LIMIT 2 /*application='WongnokBlog'*/

= "คำสั่งเรียงที่ใส่มาถูกทิ้ง" · ไม่ใช่ error งานยังทำต่อ — จึงพลาดง่ายถ้าไม่อ่าน log

พี่น้องของมันชื่อ in_batches — แทนที่จะส่งให้ทีละแผ่น มันส่งทั้งลังให้ (เป็นใบเบิกของหนึ่งใบ) · เหมาะกับงานแบบ "แก้ทุกแผ่นในลังนี้ด้วยคำสั่งเดียว" · บทนี้แค่ให้รู้จักชื่อ

merge = รวมโค้ดของเราเข้า branch หลัก (เช่น main) ให้ทั้งทีมใช้ · หัวข้อนี้คือ "ก่อนส่งงานให้ทีม"

ทั้งบทสรุปได้ว่า อ่านโค้ดอย่างเดียวไม่มีทางรู้ — post.user กับ post.title หน้าตาเหมือนกัน · count กับ size ได้ผลเท่ากัน · ที่รู้ได้ทุกครั้งคือ log · ก่อนส่งงานหน้าไหนที่โชว์เป็นรายการ ทำ 4 ข้อนี้:

  1. เปิดหน้านั้นในเบราว์เซอร์ แล้วดู tail -f log/development.log
  2. อ่านบรรทัด Completed … → ดู (N queries, M cached) · ตัวเลขควรไม่โตตามจำนวนแถว (ลองเพิ่มข้อมูลอีกสักแถวแล้วเปิดใหม่ ถ้าตัวเลขขึ้นตาม = N+1)

ตัวเลือกที่ 3 ถูก — 1 + 20 + 20 = 41 · N+1 สองตัวซ้อนกัน (ผู้เขียน กับ จำนวนคอมเมนต์) · ในบรรทัด Completed จะเห็นเป็น (41 queries, …) (ถ้าผู้เขียนซ้ำกันบางตัวจะเป็น cached)

ตัวเลือกที่ 1 คือจำนวนที่ควรจะเป็นหลังแก้แล้ว ไม่ใช่ตอนนี้ · ตัวเลือกที่ 2 ลืมว่า Comment Count ก็ไปตู้เหมือนกัน แค่หน้าตาต่าง · ตัวเลือกที่ 4 สับสน "ใบสั่งจากลูกค้า" (request) กับ "การไปตู้" (query) — ใบสั่งเดียวไปตู้ได้หลายสิบรอบ

จุดที่ต้องจำ: นับทุกบรรทัด … Load / … Count · บรรทัดซ้ำ ๆ ต่างกันแค่เลข = N+1 หนึ่งตัว

หน้าเดียวกันนั้น ต้องโชว์ชื่อผู้เขียนและจำนวนคอมเมนต์ · แบบไหนเหลือ 3 query (บทความ · ผู้เขียน · คอมเมนต์ อย่างละรอบ)?

ตัวเลือกที่ 4 ถูก — ผลจริงในภารกิจ: (3 queries, 0 cached) · คอมเมนต์อยู่ในตะกร้าแล้ว และ size นับจากตะกร้า

ตัวเลือกที่ 1 ลืมหยิบคอมเมนต์มา size เลยไปให้ตู้นับทีละบทความ (ผมลองได้ 8 query) · ตัวเลือกที่ 2 หยิบคอมเมนต์มาแล้วแต่ count ไม่มองตะกร้า ไปตู้ใหม่ทุกครั้ง (ผลจริงในหัวข้อคอมเมนต์ · แย่กว่าเดิม) · ตัวเลือกที่ 3 แก้แค่ผู้เขียน จำนวนคอมเมนต์ยังเป็น N+1

จุดที่ต้องจำ: includes ของที่ใช้ให้ครบทุกตัว · นับของที่ includes มาแล้วใช้ size · แล้วเปิด log ยืนยัน

ถือแฟ้มบทความไว้แล้ว (post = Post.first) · ข้อไหนอธิบายถูกว่าทำไม post.user_id ไม่ขึ้น SQL แต่ post.user ขึ้น?

ตัวเลือกที่ 1 ถูก — บนแฟ้มบทความมีแค่เลขที่ผู้เขียน (user_id = 1) · ชื่อและอีเมลอยู่ในลิ้นชัก users · post.user จึงต้องเดินไปหยิบ (lazy loading)

ตัวเลือกที่ 2 ผิด เพราะ user_id ไม่ได้มาจาก cache แต่มากับแฟ้มตั้งแต่ Post.first · ตัวเลือกที่ 3 ผิด เพราะในหน้าเว็บจริงครั้งแรกก็ไปตู้เหมือนกัน (เห็นใน log ของ server) ความจำช่วยแค่คำถามที่ซ้ำ · ตัวเลือกที่ 4 ผิด เพราะ post.user แค่หาแฟ้มผู้เขียน ไม่ได้ตรวจสิทธิ์อะไร (เรื่องสิทธิ์อยู่ Day 4)

จุดที่ต้องจำ: ช่องบนแฟ้ม = อ่านฟรี · ของที่อยู่ลิ้นชักอื่น = ไปตู้ · ไปตู้ในลูป = N+1

ต้องเขียนงานที่วนแก้บทความทุกชิ้น และสไลด์บอกว่าตารางจริงมี 2 ล้านแถว · ควรวนแบบไหน?

ตัวเลือกที่ 2 ถูก — ดึงชุดละ 1000 (ค่าเริ่มต้น) ด้วย WHERE id > … LIMIT … · ในหน่วยความจำมีแฟ้มไม่เกินหนึ่งชุดตลอด

ตัวเลือกที่ 1 ไปตู้รอบเดียวจริง แต่ยกมาทั้งตู้ 2 ล้านแฟ้มเข้าหน่วยความจำ — โต๊ะล้ม · ตัวเลือกที่ 3 แก้ N+1 ของผู้เขียน ไม่ได้แก้เรื่องจำนวนแถว ยังยกทั้งตู้เหมือนเดิม · ตัวเลือกที่ 4 ไม่ได้ลำดับตามยอดวิว — ผลจริงขึ้น Scoped order is ignored แล้วไล่ตาม id

จุดที่ต้องจำ: N+1 = ไปตู้หลายรอบเกินไป · all.each กับตารางใหญ่ = ยกของมากเกินไปในรอบเดียว · คนละปัญหา คนละทางแก้
