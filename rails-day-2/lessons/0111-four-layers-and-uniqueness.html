4 ชั้นป้องกันข้อมูล — ทำไมกฎในโมเดลยังกันอีเมลซ้ำไม่ได้

~25 นาที (ยาวกว่าบทอื่นนิดหนึ่ง เพราะมีการทดลองจริง 3 อย่าง) · ควรผ่าน บท 108 (migration) และ บท 110 (validation) มาก่อน

บทที่แล้วเราใส่กฎใน model ไว้ตรวจข้อมูลก่อนเก็บ — บทนี้จะพิสูจน์ด้วยมือตัวเองว่ากฎพวกนั้นยังมีรูรั่ว สองรู: มีประตูข้างที่ข้ามการตรวจได้ และคนสองคนกดสมัครพร้อมกันก็ได้อีเมลซ้ำ
อ่านจบแล้วคุณจะรู้ว่าข้อมูลถูกกันได้ 4 ด่าน ด่านไหนทำอะไร · ใส่ กฎที่ตัว database (ห้ามว่าง · ห้ามซ้ำ · ตัวเลขต้องอยู่ในช่วงที่กำหนด — ชื่อจริงของมันคือ NOT NULL · unique index · CHECK เดี๋ยวรู้จักทีละตัว) คู่กับกฎใน model ได้เอง · และพอ AI เขียน uniqueness: true มาให้ คุณจะรู้ว่าต้องถามหาอะไรต่อ

🔁 ทวนก่อนเริ่ม — บทนี้ใช้คำพวกนี้ตลอด ถ้าข้อไหนไม่คุ้นให้กลับไปบทนั้นก่อน

  • validation · validates = กฎใน model ที่คนดูแลสต็อกใช้ตรวจแฟ้มก่อนเก็บ · valid? ถามว่าผ่านไหม · errors.full_messages ขอเหตุผลที่ไม่ผ่านเป็นประโยค (บท 110)
  • save vs save! = ไม่ผ่านแล้วคืน false เงียบ ๆ · ไม่ผ่านแล้วระเบิด (โยน error) — กฎ ! (บท 110)
  • migration · bin/rails db:migrate = ใบสั่งช่างมาดัดแปลงตู้ · สั่งให้ช่างลงมือ (บท 108)
  • SQL ใน console = บรรทัดที่ Rails พิมพ์ให้ดูทุกครั้งที่เดินไปตู้ — สมุดบันทึกการเบิกของ (บท 107)
  • index = สารบัญ/ป้ายแท็บในลิ้นชัก ช่วยให้หาแฟ้มเจอเร็ว (บท 109) — บทนี้จะใช้มันอีกแบบ คือ "กันซ้ำ"

🍜 ข้อมูลตัวอย่าง: ใช้ตาราง users · posts · comments และข้อมูลตัวอย่าง (seeds) ชุดเดียวกับบท 107 (สมชาย · สมหญิง · มานะ และบทความอาหาร 6 ชิ้น) · บทนี้จะแก้ model และเพิ่ม migrationหลายไฟล์ — แนะนำให้ git add . && git commit -m "ก่อนบท 111" ไว้ก่อน จะได้ย้อนกลับได้

ประโยคเดียวของบทนี้

กฎใน model (validation) ไม่ใช่การรับประกัน — ของสำคัญต้องมีกฎที่ตัว database คู่กันเสมอ
นี่คือประโยคหลักข้อ ② ของ Day 2 (สไลด์หน้า 3 และ 59) · ทั้งบทนี้คือการพิสูจน์ประโยคนี้ด้วยผลรันจริง

ทำไมต้องพิสูจน์? เพราะพอเขียน validates :email, uniqueness: true ("อีเมลห้ามซ้ำ") แล้วลองสมัครซ้ำใน console มันก็ฟ้องจริง ๆ — คนส่วนใหญ่เลยเชื่อว่า "กันแล้ว" · บทนี้จะทำให้เห็นว่ามันหลุดได้ ตอนไหน และปิดยังไง

ข้อมูลผิด ๆ ถูกกันได้ 4 ด่าน

ข้อมูลหนึ่งชิ้น (เช่น อีเมลที่ลูกค้ากรอกตอนสมัคร) เดินจากเบราว์เซอร์ไปถึง database ผ่านด่านได้ 4 ด่าน · แต่ละด่านกันได้คนละแบบ — ด่านที่อยู่ใกล้ลูกค้า บริการดี (บอกเร็ว บอกสวย) · ด่านที่อยู่ลึก รับประกันได้จริง (ข้ามไม่ได้)

ลูกค้ากรอกฟอร์มสมัครสมาชิก แล้วกดส่ง │ ▼ ① ป้ายหน้าร้าน HTML: required · type="email" เบราว์เซอร์เตือน "กรอกช่องนี้ก่อน" ทันที · แต่ใครส่งด้วย curl จะไม่ผ่านป้ายนี้เลย │ ▼ ② พนักงานต้อนรับ controller: params.expect(user: [:name, :email]) รับเฉพาะช่องที่อยู่บนแบบฟอร์ม ช่องที่แอบเขียนเพิ่มถูกตัดทิ้ง · ไม่ได้ดูว่าค่าในช่องถูกไหม │ ▼ ③ คนดูแลสต็อก model: validates :email, uniqueness: true ตรวจแล้วบอกเหตุผลเป็นภาษาคน "Email has already been taken" · แต่มีประตูข้าง │ ▼ ④ ตัวตู้ database: NOT NULL · unique index · CHECK · foreign key ใส่ผิดแบบไม่ได้เลย ไม่ว่ามาทางไหน · แต่ตอบเป็น error ภาษาเครื่อง ลูกค้าอ่านไม่รู้เรื่อง │ ▼ แฟ้มเข้าลิ้นชัก users
  • ด่าน ② strong parameters (params.expect) แค่รู้ชื่อไว้ก่อน — บท 117 สอนละเอียด · บทนี้โฟกัสด่าน ① ③ ④
  • ด่าน ④ คำว่า constraint แปลตรง ๆ ว่า "ข้อบังคับ" — คือกฎที่เขียนไว้ในตัวตารางของ database เอง ไม่ใช่ในโค้ด Ruby
  • สี่ชื่อในกล่อง ④ ภาษาคน: NOT NULL = ช่องนี้ห้ามว่าง · unique index = ช่องนี้ห้ามซ้ำกับแผ่นอื่น · CHECK = เงื่อนไขที่เราเขียนเอง เช่น "ต้อง ≥ 0" · foreign key = เลขที่อ้างถึงแฟ้มอื่น ต้องมีแฟ้มนั้นอยู่จริง — บทนี้ได้ลองครบทุกตัว

ใน Go ที่เคยเรียน คุณเคยเห็นทั้งด่าน ③ และ ④ มาแล้วโดยไม่รู้ตัว: binding:"required" ของ Gin (บท 39) คือด่าน ③ — โค้ดเราตรวจเอง · ส่วน gorm:"unique" ใน struct (บท 27) พอสั่ง AutoMigrate GORM จะไปสร้างกฎห้ามซ้ำที่ตัวตาราง — นั่นคือด่าน ④ 

// Go — สองบรรทัดนี้อยู่คนละด่านกัน
Title string `json:"title" binding:"required"`   // ด่าน ③ Gin ตรวจในโค้ด
Email string `gorm:"unique"`                    // ด่าน ④ GORM สร้างกฎในตาราง

ข้อความในเครื่องหมาย `…` ท้ายแต่ละช่องของ struct คือ tag (ป้ายกำกับที่ library อ่าน) · สองบรรทัดหน้าตาเหมือนกัน แต่ binding ถูกอ่านโดย Gin ตอนรับ request · gorm ถูกอ่านโดย GORM ตอนสร้างตาราง

🍽 เทียบให้เห็นภาพ — ร้านอาหารที่มี 4 ด่าน

① ป้ายหน้าร้าน เขียนว่า "กรุณากรอกชื่อในใบสั่ง" — ลูกค้าส่วนใหญ่ทำตาม แต่คนที่เดินเข้าทางหลังร้านไม่เห็นป้ายนี้เลย
② พนักงานต้อนรับ รับเฉพาะช่องที่อยู่บนแบบฟอร์ม ใครแอบเขียน "ขอฟรี" ไว้ขอบกระดาษ ตัดทิ้ง
③ คนดูแลสต็อก ตรวจแฟ้มก่อนเก็บ ไม่ผ่านก็บอกเหตุผลสุภาพ ๆ "ไม่มีชื่อเรื่อง ไม่รับครับ"
④ ตัวตู้ ออกแบบมาให้ใส่แฟ้มผิดแบบไม่ได้ทางกายภาพ — ไม่ว่าใครถือแฟ้มมา ทางประตูไหน ก็ยัดไม่เข้า

ที่ไม่เหมือนกัน: ป้ายหน้าร้านจริงอย่างน้อยก็ติดอยู่ที่ร้านเรา · แต่ด่าน ① ของแอปอยู่ในเบราว์เซอร์ของลูกค้า — เราควบคุมไม่ได้เลย ลูกค้าจะลบป้ายทิ้งก็ได้ ส่วนด่าน ② ③ คือโค้ดของเราเอง
และตัวตู้จริงไม่พูด แต่ตู้ของเรา "พูด" ได้ — แค่พูดเป็นภาษาเครื่อง (PG::UniqueViolation) ที่ลูกค้าอ่านไม่รู้เรื่อง เราจึงยังต้องมีคนดูแลสต็อกไว้แปลเป็นภาษาคน

🗣 ศัพท์ของภาพรวม
validation (application-level)
กฎที่โค้ดของเราตรวจเอง (ด่าน ③) · บอกเหตุผลเป็นภาษาคนได้ แต่เลี่ยงได้ · ถาม senior ได้ว่า "กฎนี้มีแค่ validation หรือมี constraint ที่ DB ด้วย"
database constraint
กฎที่ตัว database บังคับ (ด่าน ④) เช่น NOT NULL · UNIQUE · CHECK · FOREIGN KEY · ข้ามไม่ได้แม้ยิง SQL ตรง · พิมพ์บอก AI ได้ว่า "add a database constraint to match this validation"
defense in depth
แนวคิด "ป้องกันหลายชั้น ชั้นหนึ่งพลาด อีกชั้นยังกันอยู่" · ไม่ได้แปลว่าทุกชั้นต้องเก่งเท่ากัน แต่ละชั้นมีหน้าที่ของมัน

เตรียมแผนกสมัครสมาชิก (ก็อปวางได้เลย)

จะทดลองด่าน ① ได้ ต้องมีฟอร์มก่อน · เพิ่มไฟล์ 3 ไฟล์นี้ในแอป wongnok_blog ของคุณ — route · controller · view แบบเดียวกับ Lab ของ Day 1 (บท 105)

① route — แก้ config/routes.rb ให้มีบรรทัด resources นี้ (บรรทัดอื่นในไฟล์คงไว้ได้):

Rails.application.routes.draw do
  resources :users, only: [:new, :create, :show]
end

resources :users ให้ 8 เส้นแบบบท 101 · only: [...] = "เอาแค่ 3 เส้นนี้" — หน้าฟอร์ม (new) · รับฟอร์ม (create) · หน้าดูผล (show)

② controller — ไฟล์ใหม่ app/controllers/users_controller.rb:

class UsersController < ApplicationController
  def new
    @user = User.new
  end

  def create
    @user = User.new(user_params)
    if @user.save
      redirect_to @user
    else
      render :new, status: :unprocessable_content
    end
  end

  def show
    @user = User.find(params[:id])
  end

  private

  def user_params
    params.expect(user: [:name, :email])
  end
end
  • new — เตรียมแฟ้มเปล่าหนึ่งแผ่นวางบนถาด (@user) ให้ view เอาไปทำฟอร์ม
  • create — สร้างแฟ้มจากของที่ลูกค้ากรอก · if @user.save = ถ้าเก็บได้ พาไปหน้าดูผล (redirect_to @user — Rails แปลง user เป็น URL /users/เลข id ให้เอง) ถ้าเก็บไม่ได้ (คืน false) ให้แสดงฟอร์มเดิมอีกรอบพร้อมเหตุผล
  • status: :unprocessable_content = ตอบกลับด้วยรหัส 422 แปลว่า "ข้อมูลที่ส่งมาใช้ไม่ได้" (รหัส HTTP แบบบท 34) · ชื่อเดียวกับที่บท 110 ใช้ · สไลด์เขียนชื่อเก่า :unprocessable_entity ซึ่งยังได้ 422 แต่ขึ้นคำเตือน deprecated
  • user_params — ด่าน ② · "จากของที่ส่งมา รับเฉพาะ name กับ email ในกลุ่ม user" · private = method ใต้บรรทัดนี้เรียกจากนอก class ไม่ได้ (ทวนบท 102 · ทำไม user_params ต้องมี ละเอียดบท 117)

③ view — ไฟล์ใหม่ app/views/users/new.html.erb (หน้าฟอร์ม) และ app/views/users/show.html.erb (หน้าดูผล):

<h1>สมัครสมาชิก</h1>

<% @user.errors.full_messages.each do |message| %>
  <p class="error"><%= message %></p>
<% end %>

<%= form_with model: @user do |f| %>
  <%= f.text_field :name, required: true %>
  <%= f.email_field :email, required: true %>
  <%= f.submit "สมัคร" %>
<% end %>
<p>สมัครแล้ว: <%= @user.name %> (<%= @user.email %>)</p>
  • ก้อนบน — วนพิมพ์เหตุผลที่ไม่ผ่านทีละบรรทัด (ถ้าไม่มี ก็ไม่พิมพ์อะไร)
  • form_with model: @user — ตัวช่วยสร้างฟอร์มให้ตรงกับ model (ละเอียด Day 3) · ส่งไปที่ POST /users ให้เอง
  • required: true — ด่าน ① · บอกเบราว์เซอร์ว่า "ช่องนี้ห้ามว่าง" · email_field ได้ type="email" ให้ด้วย

ด่าน ① ป้ายหน้าร้าน — เบราว์เซอร์กันได้ curl ข้ามได้

เปิด http://localhost:3000/users/new ในเบราว์เซอร์แล้วกด "สมัคร" ทั้งที่ยังว่าง — เบราว์เซอร์ไม่ยอมส่ง แต่ขึ้นกล่องเตือนใต้ช่อง (เบราว์เซอร์ที่ผมใช้ตรวจ ตั้งภาษาอังกฤษ ขึ้นว่า Please fill out this field. — ของคุณอาจเป็นภาษาไทย) · ผมเช็ค log ของ server แล้ว ไม่มีใบสั่ง POST เข้ามาเลย — ป้ายหน้าร้านทำงานจริง

แต่ป้ายนี้อยู่ในเบราว์เซอร์ · ถ้าส่งด้วยโปรแกรมอื่นที่ไม่อ่าน HTML เช่น curl ก็ไม่มีใครเตือน · ลองส่งอีเมลว่างตรง ๆ หนึ่งบรรทัด: 

$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/users -d "user[name]=ghost" -d "user[email]="
422
  • -d "ชื่อ=ค่า" — ส่งข้อมูลแบบฟอร์ม (curl จะใช้ POST ให้เอง) · user[email]= คืออีเมลว่าง
  • -o /dev/null -w '%{http_code}\n' — ทิ้งหน้าเว็บ พิมพ์แค่รหัสตอบกลับ

ได้ 422 — แต่ไม่ใช่เพราะอีเมลว่าง · ดูใน log ของ server:

Can't verify CSRF token authenticity.
ActionController::InvalidAuthenticityToken (Can't verify CSRF token authenticity.):

Rails ฝังรหัสลับ (authenticity_token) ไว้ในฟอร์มทุกใบ แล้วเช็คว่าใบสั่งที่ส่งกลับมามีรหัสนี้ไหม — กันเว็บอื่นแอบส่งฟอร์มแทนเรา (เรื่องนี้ชื่อ CSRF เคยเห็นในบท 103 · ไม่ใช่การตรวจข้อมูล) · ถ้าเอารหัสจากหน้าฟอร์มมาด้วย ก็ส่งได้ — ใช้สองคำสั่ง:

$ curl -s -i -b jar.txt http://localhost:3000/users -d "authenticity_token=$TOKEN" -d "user[name]=ghost" -d "user[email]="

  • SELECT "users".* FROM "users" WHERE "users"."name" = 'สมชาย' LIMIT 1 — "ขอแฟ้มทุกช่อง (SELECT … *) จากลิ้นชัก users (FROM) เฉพาะแผ่นที่ช่อง name เป็น สมชาย (WHERE) เอาแค่แผ่นเดียว (LIMIT 1)"
  • BEGIN … COMMIT — "เริ่มงานชุดหนึ่ง" … "ยืนยันว่าเก็บจริง" (คือ transaction — อธิบายท้ายบท)
  • INSERT INTO "posts" (…) VALUES (NULL, NULL, …, 1) — "ใส่แฟ้มแผ่นใหม่ลงลิ้นชัก posts ช่องตามลำดับในวงเล็บแรก ค่าตามวงเล็บที่สอง" · ช่องแรก (title) เป็น NULL = ไม่มีค่า (คือ nil ฝั่ง Ruby) · ช่องสุดท้าย (user_id) เป็น 1 = สมชาย · RETURNING "id" = "เก็บเสร็จแล้วบอกเลขที่แฟ้มกลับมาด้วย" (บท 107)
  • ท่อน /*application='WongnokBlog'*/ ท้ายทุกบรรทัด — ป้ายที่ Rails แปะบอกว่าคำสั่งมาจากแอปไหน ไม่ต้องสนใจ

save(validate: false) ไม่ใช่ประตูข้างบานเดียว · เอกสารทางการของ Rails ระบุคำสั่งที่ข้าม validationไว้เป็นรายการ (Rails Guides — Active Record Validations หัวข้อ 1.4) ตัวที่จะเจอบ่อย:

คำสั่งทำอะไรเจอที่ไหนบ่อย
save(validate: false)เก็บโดยไม่ตรวจscript แก้ข้อมูล · โค้ดที่ AI เขียนให้ "ผ่าน" ไว้ก่อน

insert_all · upsert_allใส่หลายแถวทีเดียว ไม่ตรวจนำเข้าข้อมูลจากไฟล์
SQL ตรง ๆไม่ผ่าน Rails เลยเปิด psql (โปรแกรมพิมพ์ SQL ตรง ๆ ของ PostgreSQL) หรือโปรแกรมอื่นที่ต่อ database เดียวกัน

🍽 เทียบให้เห็นภาพ — ประตูหลังร้าน กับลิ้นชักที่มีช่องบังคับ

คนดูแลสต็อกยืนตรวจแฟ้มอยู่หน้าห้องเก็บของ · แต่ร้านมีประตูหลังที่พนักงานบางคนถือแฟ้มเดินเข้าไปเสียบลิ้นชักเองได้เลย ไม่ผ่านโต๊ะตรวจ
ลิ้นชัก posts ทำช่อง "ผู้เขียน" เป็นช่องบังคับไว้ (แฟ้มที่ช่องนี้ว่าง เสียบไม่ลง) แต่ช่อง "ชื่อเรื่อง" ไม่ได้ทำ · แฟ้มไร้ชื่อเรื่องจึงเข้าทางประตูหลังได้ ส่วนแฟ้มไร้ผู้เขียนเข้าไม่ได้ไม่ว่าทางไหน

ที่ไม่เหมือนกัน: ประตูหลังร้านจริงเป็นเรื่องผิดปกติ · ใน Rails คำสั่งพวกนี้ตั้งใจทำไว้ให้ใช้ (เช่น แก้ข้อมูลทีละมาก ๆ ให้เร็ว) ไม่ใช่ช่องโหว่ — ปัญหาคือคนใช้มักลืมว่ามันไม่ผ่านโต๊ะตรวจ

เทียบ Go: ใน GORM ถ้าเขียน SQL เองด้วย db.Exec("INSERT INTO …") ก็ข้ามทุกอย่างในโค้ด Go ไปเหมือนกัน · กฎที่เหลืออยู่คือกฎที่อยู่ในตาราง เช่น tag gorm:"not null" ที่ GORM ใส่ให้ตอนสร้างตาราง (ด่าน ④)

🗣 ศัพท์ของด่าน ③ และ ④
NOT NULL constraint
กฎที่ตารางบอกว่า "ช่องนี้ห้ามเป็น NULL (ไม่มีค่า)" · ใน migration เขียน null: false · พังแล้วได้ ActiveRecord::NotNullViolation · ถาม senior ได้ว่า "คอลัมน์นี้ presence อย่างเดียว หรือมี NOT NULL ด้วย"
skip validations / bypass
คำสั่งที่เก็บลง database โดยไม่รัน validation · พิมพ์บอก AI ได้ว่า "don't use update_column or save(validate: false) here, I want validations to run"

uniqueness: true — กฎที่ดูเหมือนกันอีเมลซ้ำได้

ประตูข้างยังพอเข้าใจได้ — "ก็คนจงใจข้ามนี่" · แต่เรื่องต่อไปน่ากลัวกว่า: ไม่มีใครข้ามอะไรเลย ใช้ save ธรรมดา แต่ข้อมูลก็ยังซ้ำ · ใส่กฎ "อีเมลห้ามซ้ำ" ให้ User ก่อน — เพิ่มบรรทัดสุดท้ายบรรทัดเดียวต่อจากกฎของบท 110 (ไฟล์ app/models/user.rb): 

# app/models/user.rb
class User < ApplicationRecord
  has_many :posts
  has_many :comments

  validates :name, presence: true
  validates :email, presence: true, format: { with: /\A[^@\s]+@[^@\s]+\z/ }
  validates :email, uniqueness: true   # ← บรรทัดใหม่ของบทนี้
end

uniqueness: true = "อีเมลนี้ต้องไม่ซ้ำกับแฟ้มอื่นในลิ้นชัก users" · จะเขียนรวมกับบรรทัดบน (presence: true, format: …, uniqueness: true) ก็ได้ผลเหมือนกัน — แยกบรรทัดไว้ให้เห็นชัดว่าอันไหนใหม่

ปัญหาอยู่ตรงนี้: "ถามตู้" กับ "เก็บแฟ้ม" เป็นสองคำสั่งแยกกัน และมีช่องว่างระหว่างสองคำสั่งเสมอ · ถ้ามีอีกคนแทรกเข้ามาในช่องว่างนั้นพอดี — ทั้งสองคนจะได้คำตอบว่า "ยังไม่มีใครใช้" ทั้งคู่

ร้านมีโต๊ะริมหน้าต่างตัวเดียว · ลูกค้าสองคนโทรเข้ามาพร้อมกัน พนักงานสองคนรับสายคนละเครื่อง
ทั้งคู่เปิดสมุดจองดูพร้อมกัน — "โต๊ะริมหน้าต่างคืนนี้ ว่างครับ" · แล้วทั้งคู่ก็เขียนชื่อลูกค้าของตัวเองลงไป
คืนนั้นลูกค้าสองคนมาถึงโต๊ะเดียวกัน — พนักงานไม่มีใครผิด แต่ระบบ "ดูก่อนแล้วค่อยเขียน" ผิด

ที่ไม่เหมือนกัน: ในร้านจริง พนักงานคนที่สองยังมีโอกาสเห็นว่ามีชื่อเพิ่งเขียนลงไป · ในแอป สองคำขอวิ่งพร้อมกันเร็วระดับมิลลิวินาที ไม่มีใครเห็นใคร
และในเครื่องเรา (คนใช้คนเดียว) แทบไม่เกิดเลย — มันจะโผล่ตอนมีคนใช้จริงเยอะ ๆ หรือตอนลูกค้ากดปุ่ม "สมัคร" สองครั้งรัว ๆ

ถ้าจำบท 24 ของ Go ได้ — นี่คือเรื่องเดียวกับ counter++ ที่สอง goroutine ทำพร้อมกันแล้วตัวเลขหาย: อ่าน → คิด → เขียนกลับ โดยมีคนอื่นแทรกกลางทางได้ · ต่างกันแค่บท 24 แย่งตัวแปรในหน่วยความจำ ส่วนบทนี้แย่งแถวใน database

ลองให้เกิดจริง: สองโปรแกรมสมัครพร้อมกัน

ช่องว่างจริงสั้นแค่เสี้ยววินาที ตาเปล่าจับไม่ทัน · ผมจึงเขียนสคริปต์ที่แทรกการรอ 2 วินาทีไว้ระหว่าง "ตรวจ" กับ "เก็บ" เพื่อขยายช่องว่างให้เห็น · สร้างไฟล์ race.rb ไว้ที่โฟลเดอร์บนสุดของแอป (ที่เดียวกับ Gemfile): 

# race.rb — จำลองคนสองคนสมัครด้วยอีเมลเดียวกันในเวลาเดียวกัน
$stdout.sync = true
name = ARGV[0]
User.after_validation do
  puts "#{name}: ตรวจแล้ว ไม่มีใครใช้อีเมลนี้ → รอ 2 วินาที"
  sleep 2
end

user = User.new(name: name, email: "nan@example.com")
puts "#{name}: save ได้ #{user.save}"
  • $stdout.sync = true — ให้ puts พิมพ์ออกจอทันที (ไม่งั้นโปรแกรมจะเก็บไว้พิมพ์ทีเดียวตอนจบ ลำดับบรรทัดจะดูเพี้ยน)
  • ARGV[0] — คำแรกที่พิมพ์ต่อท้ายคำสั่ง · เราจะส่ง A กับ B ไว้แยกว่าใครเป็นใคร
  • User.after_validation do … end — "ทุกครั้งที่ตรวจเสร็จ ให้ทำสิ่งนี้ก่อนเก็บ" (เรียกว่า callback · เจอละเอียดบท 112) · ใช้แค่แทรก sleep 2 และมีผลเฉพาะตอนรันสคริปต์นี้ ไม่ได้แก้ model
  • user.save — save ธรรมดา ไม่ได้ข้ามอะไรเลย: ตรวจ (SELECT) → รอ 2 วินาที → เก็บ (INSERT)
  • "#{name}: …" — แทรกค่าตัวแปรในข้อความ (บท 91)

  • & ท้ายคำสั่ง = "ปล่อยให้รันไป ไม่ต้องรอ" (สองตัวจึงวิ่งพร้อมกัน) · wait = "รอทุกตัวที่ปล่อยไปให้จบก่อน" · terminal ของคุณอาจพิมพ์บรรทัดอย่าง [1] 12345 เพิ่ม — เป็นเลขงานของ shell ไม่ต้องสนใจ

🗣 ศัพท์ของเรื่องนี้
race condition
ผลลัพธ์ขึ้นกับว่าใครทำเสร็จก่อนใคร · ทดสอบทีละคนผ่านเสมอ แต่ใช้จริงพร้อมกันแล้วพัง · ถาม senior ได้ว่า "ตรงนี้มี race condition ไหม ถ้าสอง request มาพร้อมกัน"
check-then-act
รูปแบบ "ตรวจก่อน แล้วค่อยทำ" ที่เป็นต้นเหตุของ race condition · validates uniqueness คือ check-then-act · พิมพ์บอก AI ได้ว่า "this uniqueness check is check-then-act, how do we make the database enforce it?"

ทางแก้: ให้ตัวตู้เป็นคนตัดสิน — unique index

แก้ race condition ด้วยการตรวจให้ "เร็วขึ้น" ไม่ได้ — ช่องว่างยังอยู่ · ทางแก้คือให้คนที่เก็บแฟ้ม (database) เป็นคนตรวจเอง ในจังหวะเดียวกับที่เก็บ ไม่มีช่องว่างให้ใครแทรก · เครื่องมือที่ database มีให้คือ unique index

index (ภาษาคน) = สารบัญที่ database ทำไว้ให้ช่องหนึ่ง เรียงตามตัวอักษร เพื่อหาเจอเร็วโดยไม่ต้องไล่ทีละแผ่น (บท 109 พูดถึงเรื่องความเร็ว) · unique index = สารบัญที่มีกฎเพิ่มว่า "ชื่อหนึ่งมีได้ช่องเดียว" — ใครจะใส่แฟ้มที่อีเมลซ้ำกับในสารบัญ ตู้ปฏิเสธทันที

🍽 เทียบให้เห็นภาพ — ป้ายแท็บในลิ้นชักที่มีช่องเดียวต่อชื่อ

ลองนึกถึงลิ้นชัก users ที่ติดป้ายแท็บเรียงตามอีเมล หนึ่งแท็บใส่แฟ้มได้แผ่นเดียว
พนักงานสองคนถือแฟ้ม nan@example.com มาพร้อมกัน · คนแรกเสียบลงแท็บได้ · คนที่สองเสียบไม่ลง เพราะแท็บนั้นมีแฟ้มแล้ว — ไม่ต้องมีใครเปิดสมุดตรวจก่อน ตัวลิ้นชักตัดสินเอง ณ วินาทีที่เสียบ

ที่ไม่เหมือนกัน: พนักงานคนที่สองในชีวิตจริงเห็นเองว่าแท็บเต็ม แล้วเดินกลับไปบอกลูกค้าได้ · ในแอป database แค่โยน error กลับมา (ActiveRecord::RecordNotUnique) — ถ้าโค้ดเราไม่รับ ลูกค้าจะเห็นหน้า error (เรื่องนี้แก้ในหัวข้อถัดไป)

สารบัญของคอลัมน์ที่ห้ามมีค่าซ้ำ · database ตรวจตอนเก็บ ไม่มีช่องว่างให้แทรก · ถาม senior ได้ว่า "uniqueness ตัวนี้มี unique index ใน migration รองรับไหม"
ActiveRecord::RecordNotUnique
error ที่ Rails โยนเมื่อตู้ปฏิเสธค่าซ้ำ (เบื้องหลังคือ PG::UniqueViolation ของ PostgreSQL) · พิมพ์บอก AI ได้ว่า "rescue ActiveRecord::RecordNotUnique and show a form error instead of a 500"

ด่านสุดท้ายต้องมีคนรับ — rescue ใน controller (สไลด์หน้า 26)

ตอนนี้ตู้กันอีเมลซ้ำได้แน่นอนแล้ว · แต่ถ้าคนที่สองแพ้การแข่ง ลูกค้าจะได้ error ภาษาเครื่อง — ต้องมีคนรับ error นั้นแล้วแปลเป็นข้อความในฟอร์ม · สไลด์หน้า 26 ให้โค้ด controller ไว้แบบนี้: 

  def create
    @user = User.new(user_params)
    @user.save!
    redirect_to @user
  rescue ActiveRecord::RecordNotUnique
    @user.errors.add(:email, "ถูกใช้ไปแล้ว")
    render :new, status: :unprocessable_entity
  end
  • @user.save! — เก็บแบบมี !: ไม่ผ่านแล้วระเบิด (บท 110)
  • rescue ActiveRecord::RecordNotUnique — "ถ้าระหว่างทางมี error ชนิดนี้ ให้กระโดดมาทำตรงนี้แทน" (rescue แบบบท 96 · เขียนใน def ได้เลยโดยไม่ต้องมี begin)
  • @user.errors.add(:email, "ถูกใช้ไปแล้ว") — เติมเหตุผลเองลงในรายการ error ของช่อง email · view จะพิมพ์ออกมาเป็น Email ถูกใช้ไปแล้ว
  • render :new, status: :unprocessable_entity — แสดงฟอร์มเดิมอีกรอบพร้อมรหัส 422 (ชื่อเก่าของ :unprocessable_content · โค้ดฉบับแก้ข้างล่างใช้ชื่อใหม่)

เอาโค้ดของสไลด์ไปแทน create เดิม (model User ยังมี validates :email, uniqueness: true) · แล้วสมัครด้วยอีเมล somchai@example.com ธรรมดา ๆ คนเดียว ไม่ได้แข่งกับใคร

transaction — ทั้งหมด หรือไม่ทำเลย (และทำไมต้องใช้ !)

บางงานมีหลายขั้นที่ต้องสำเร็จพร้อมกัน เช่น โอนเงิน = หักบัญชีเรา + เพิ่มบัญชีเพื่อน · ถ้าหักแล้วแต่เพิ่มไม่สำเร็จ เงินหายไปเฉย ๆ · transaction คือการบอก database ว่า "คำสั่งชุดนี้ ให้นับเป็นงานเดียว — สำเร็จทั้งหมด หรือยกเลิกทั้งหมด"

  • BEGIN = เริ่มงานชุด · COMMIT = ยืนยัน เก็บจริงทั้งชุด · ROLLBACK = ยกเลิก ย้อนทุกอย่างในชุดกลับเหมือนไม่เคยทำ
  • คุณเห็นสามคำนี้มาตลอดบท เพราะ save ทุกครั้งห่อตัวเองด้วย transaction อยู่แล้ว · ใน Rails เขียนเองได้ด้วย ActiveRecord::Base.transaction do … end (ActiveRecord::Base = แม่ของ ApplicationRecord ที่เห็นในบท 106 · ทุกคำสั่งใน block นี้นับเป็นงานชุดเดียว)
  • กฎของ Rails: ใน block นี้ ถ้ามี error ระเบิดออกมา → ROLLBACK · ถ้าจบปกติ → COMMIT

กลุ่มคำสั่งที่นับเป็นงานเดียว สำเร็จทั้งหมดหรือไม่สำเร็จเลย (atomic = แบ่งครึ่งไม่ได้) · ถาม senior ได้ว่า "สองขั้นนี้ต้องอยู่ใน transaction เดียวกันไหม"
commit · rollback
ยืนยันเก็บจริง · ย้อนกลับทั้งชุด · พิมพ์บอก AI ได้ว่า "use save! / update! inside the transaction so a validation failure triggers a rollback"

Checklist ตรวจงาน AI (และงานตัวเอง)

เวลา AI (หรือเพื่อน หรือตัวคุณเอง) ส่งโค้ด model มา ไล่ถามทีละข้อ:

  1. เห็น uniqueness: true → "แล้ว unique index ใน migration อยู่ไหน" (สไลด์หน้า 26 บอกว่านี่คือคำถามแรก)
  2. เห็น presence: true → "คอลัมน์นี้มี null: false ไหม"
  3. เห็น belongs_to → "migration มี foreign_key: true ไหม"
  4. เห็นกฎตัวเลข (numericality) ที่สำคัญเรื่องเงิน/จำนวน → "มี CHECK constraint ไหม"
  5. เห็น unique index → "controller rescue ActiveRecord::RecordNotUnique ไว้ไหม หรือคนที่แพ้แข่งจะเห็นหน้า error"
  6. เห็น save! ใน controller → "ถ้า validation ไม่ผ่าน ใครรับ RecordInvalid"
  7. เห็น transaction do → "ข้างในใช้ตัวที่มี ! หรือยัง ไม่งั้นไม่ rollback"

ภารกิจ: ใส่คู่ "ห้ามว่าง" ให้ชื่อผู้ใช้

🎯 ภารกิจ 111 · presence + NOT NULL ให้ users.name (~10 นาที)

ตอนนี้ช่อง name ของ users มีกฎ presence ในโค้ดแล้ว (บท 110) แต่ในตู้ยังว่างได้ · ใส่ด่าน ④ ให้ครบคู่ตาม pattern ของบทนี้

  1. ใน console สร้างผู้ใช้ที่ไม่มีชื่อไว้หนึ่งคน (จำลองข้อมูลเก่าที่หลุดเข้ามาแล้ว): User.new(email: "noname@example.com").save(validate: false) → ควรได้ true
  2. สร้าง migration: bin/rails generate migration ChangeUsersNameNotNull แล้วเขียนใน def change ว่า change_column_null :users, :name, false ("ช่อง name ของ users: ห้ามเป็น null")
  3. bin/rails db:migrate — ควรพัง · อ่าน error แล้วเดาว่าเพราะอะไร
  4. ใน console แก้ข้อมูลเก่าให้มีชื่อ (ใบ้: User.where(name: nil) หาแถวที่ชื่อว่าง แล้วต่อด้วย update_all(name: "…") จากตารางประตูข้าง) แล้ว bin/rails db:migrate อีกรอบ จนผ่าน · ดูใน db/schema.rb ว่าบรรทัด t.string "name" เปลี่ยนไปยังไง
  5. ลองประตูข้างอีกรอบ: User.new(email: "ghost2@example.com").save(validate: false) → ตู้ต้องปฏิเสธ
  6. ลองทางปกติ: user = User.new(email: "ghost2@example.com") แล้ว user.save กับ user.errors.full_messages → กฎ presence จากบท 110 ต้องให้ข้อความภาษาคน (ถ้าข้ามบท 110 มา ให้เติม validates :name, presence: true ใน app/models/user.rb ก่อน)

ควรเห็น: ข้อ 3 พัง · ข้อ 4 migrate ผ่าน และ schema.rb มี null: false · ข้อ 5 ได้ ActiveRecord::NotNullViolation · ข้อ 6 ได้ false และ ["Name can't be blank"]

ถ้าเจอ error แปลว่า…

  • PG::NotNullViolation: ERROR: column "name" of relation "users" contains null values ตอน migrate → มีแถวเก่าที่ชื่อว่างอยู่ ตู้ยังตั้งกฎ "ห้ามว่าง" ไม่ได้ (นี่คือข้อ 3 ที่ตั้งใจให้พัง)
  • PG::UniqueViolation: ERROR: duplicate key value violates unique constraint "index_users_on_email" · Key (email)=(…) already exists ตอนทำข้อ 1 หรือ 5 → อีเมลนี้มีในตู้แล้ว (เช่น รันข้อ 1 ซ้ำสองรอบ) — unique index จากบทนี้ทำงาน · เปลี่ยนอีเมลในคำสั่งเป็นอันใหม่

  has_many :comments

Quiz

ข้อ 1 · model มี validates :email, uniqueness: true แต่ ไม่มี unique index · ลูกค้าสองคนกดสมัครด้วยอีเมลเดียวกันในเสี้ยววินาทีเดียวกัน — เกิดอะไรได้?

ตัวเลือกที่ 2 ถูก · การทดลอง race.rb รอบแรกได้อีเมลเดียวกัน 2 แถวจริง — ทั้งคู่ "ถามตู้" ก่อนที่ใครจะ "เก็บแฟ้ม"

ตัวเลือกที่ 1 ถูกแค่ตอนสมัครทีละคน — validation ตรวจจริง แต่ตรวจกับข้อมูล ณ ตอนที่ถาม · ตัวเลือกที่ 3 ผิด — validates อยู่ในโค้ด Ruby ล้วน ๆ ไม่ได้ไปสร้างอะไรในตู้ (ต่างจาก gorm:"unique") · ตัวเลือกที่ 4 ผิด — Rails ไม่รู้เลยว่ามีอีกคำขอวิ่งอยู่ แต่ละคำขอทำงานแยกกัน

จุดที่ต้องจำ: "ตรวจ" กับ "เขียน" เป็นสองจังหวะ มีช่องว่างเสมอ · ปิดช่องว่างได้ที่ database เท่านั้น

ข้อ 2 · ใน ActiveRecord::Base.transaction do … end มีสองบรรทัด: บรรทัดแรก update ผ่าน · บรรทัดที่สอง update (ไม่มี !) ไม่ผ่าน validation — จบแล้วใน database เป็นยังไง?

ตัวเลือกที่ 3 ถูก · การโอนวิวแบบแรกได้ COMMIT — ส้มตำเป็น 540 ข้าวมันไก่ยัง 85

ตัวเลือกที่ 1 คือสิ่งที่อยากให้เป็น แต่ Rails ROLLBACK เฉพาะเมื่อมี error ระเบิด · update คืน false เงียบ ๆ ไม่นับ · ตัวเลือกที่ 2 คือผลของ update! (แบบที่สอง) ไม่ใช่ update · ตัวเลือกที่ 4 ผิด — transaction ไม่ได้ปิด validation · บรรทัดที่สองไม่ผ่านจึงไม่มี SQL ส่งไปเลย

จุดที่ต้องจำ: ใน transaction ใช้ save! · update! · create! เสมอ — "ระเบิด = rollback"

ข้อ 3 · เพิ่ม migration add_index :users, :email, unique: true แล้ว db:migrate พังด้วย could not create unique index … Key (email)=(…) is duplicated — ต้องทำอะไร?

ตัวเลือกที่ 1 ถูก · ในบทนี้หาด้วย User.group(:email).having("COUNT(*) > 1").count ลบแถวเกิน แล้ว migrate ผ่าน

ตัวเลือกที่ 2 ผิด — validation อยู่ในโค้ด ไม่เกี่ยวกับการสร้าง index ในตู้เลย ลบไปก็พังเหมือนเดิม · ตัวเลือกที่ 3 ได้ index ธรรมดาที่ไม่กันซ้ำ — ไม่ได้แก้ปัญหาที่ตั้งใจแก้ · ตัวเลือกที่ 4 ผิด — error บอกชัดว่าข้อมูลในตารางซ้ำ รันกี่รอบก็ซ้ำเท่าเดิม

จุดที่ต้องจำ: ตู้ตั้งกฎใหม่ไม่ได้ ถ้าของที่อยู่ในตู้ตอนนี้ผิดกฎนั้นอยู่แล้ว (ใช้กับ null: false และ CHECK ด้วย — ภารกิจเจอแบบเดียวกัน)

ข้อ 4 · อยากได้กฎ "ยอดวิวห้ามติดลบ" ที่ทั้งข้ามไม่ได้และลูกค้าอ่านเข้าใจ — ควรใส่อะไร?

ตัวเลือกที่ 4 ถูก · ในบทนี้: มีแค่ CHECK → ได้ ActiveRecord::CheckViolation ภาษาเครื่อง · เติม numericality → ได้ Views must be greater than or equal to 0

ตัวเลือกที่ 1 ผิด — update_column · update_all · SQL ตรง ข้ามการตรวจของ model ได้ (ตารางประตูข้าง) · ตัวเลือกที่ 2 กันได้จริง แต่ลูกค้าได้หน้า error แทนข้อความ — ขาดครึ่ง "อ่านเข้าใจ" · ตัวเลือกที่ 3 คือด่าน ① — curl ข้ามได้ด้วยคำสั่งสองบรรทัดแบบที่ทำในบทนี้

จุดที่ต้องจำ: ของสำคัญต้องกัน 2 ชั้น — ด่าน ③ ให้ข้อความสวย + ด่าน ④ ให้การรับประกัน
