ลบบทความแล้วคอมเมนต์ไปไหน — dependent, CASCADE และ counter_cache

~25 นาที (ลองตามใน console หลายรอบ) · ควรผ่าน บท 111 (foreign key · transaction) · บท 112 (callback) · บท 115 (has_many · belongs_to) มาก่อน

ลองลบบทความที่มีคนมาคอมเมนต์ไว้ แล้วคุณจะเจอ error สีแดงทันที — นั่นไม่ใช่บั๊ก แต่เป็นตู้เก็บแฟ้มกำลังปกป้องข้อมูลให้คุณ
อ่านจบแล้วคุณจะอ่าน error นั้นออก · เลือกได้ว่า "ลบบทความแล้วคอมเมนต์ควรเป็นยังไง" จากทางเลือก 4 แบบ โดยรู้ว่าแต่ละแบบยิง SQL อะไรจริง · แถมของเล็ก ๆ อีกสามชิ้น: counter_cache (จดจำนวนคอมเมนต์ไว้บนบทความ ไม่ต้องเดินไปนับทุกครั้ง) · touch (คอมเมนต์เปลี่ยน → บทความรู้ตัวว่ามีอะไรเปลี่ยน) · inverse_of (แค่รู้จักชื่อ)

🔁 ทวนก่อนเริ่ม — คำจากบทก่อน ๆ ที่บทนี้ใช้ตลอด

  • has_many :comments · belongs_to :post (บท 115) — บทความหนึ่งชิ้นมีใบคอมเมนต์หลายใบ · ใบคอมเมนต์แต่ละใบเป็นของบทความหนึ่งชิ้น
  • foreign key (บท 111 · บท 115) — ช่อง post_id บนใบคอมเมนต์ ("เป็นของบทความเลขที่ …") พร้อมกฎของตู้ว่าเลขนั้นต้องมีอยู่จริง
  • transaction (บท 111) — BEGIN … COMMIT = ทำทั้งชุดหรือไม่ทำเลย · ROLLBACK = ยกเลิกทั้งชุด เหมือนไม่เคยเกิด
  • callback (บท 112) — ขั้นตอนอัตโนมัติที่ทำก่อน/หลังเก็บแฟ้มทุกครั้ง
  • migration · db:reset (บท 108) — ใบสั่งช่างดัดแปลงตู้ · ล้างตู้ทิ้งแล้วสร้างใหม่จากแปลน (schema.rb) พร้อมข้อมูลตัวอย่าง

🧰 ตรวจด้วย Ruby 4.0.9 · Rails 8.1.4 · PostgreSQL 17 (สไลด์ใช้ Ruby 4.0.6 · Rails 8.1.3 — รุ่นแก้บั๊กในสายเดียวกัน ใช้แทนกันได้)

🗂 ตัวอย่างในบทนี้ใช้ตาราง users / posts / comments และข้อมูลตัวอย่าง (seeds) ชุดเดียวกับที่สร้างไว้ใน บท 107 · บทความที่ใช้บ่อย: ต้มยำกุ้งน้ำข้น (เลขที่ 1 · มีคอมเมนต์ 2 ใบ) และ ก๋วยเตี๋ยวเรืออยุธยา (เลขที่ 4 · ไม่มีคอมเมนต์)

⚠️ เริ่มบทด้วย bin/rails db:reset หนึ่งครั้ง — ถ้าทำบท 115ครบ ต้มยำกุ้งจะมีป้าย (tags) ติดอยู่ ซึ่งทำให้ทางที่ ①–③ ข้างล่างลบต้มยำกุ้งไม่ผ่าน (ติดลิ้นชัก taggings แทน) · seeds ไม่มีป้าย reset แล้วป้ายหายหมด ผลจะตรงกับในบท (ลิ้นชัก taggings กลับมาคุยกันอีกทีตอนท้ายหัวข้อ "เลือกแบบไหน")

ผลทุกก้อนรันจริงแล้วก็อปมา · เวลา (ms) · วันที่ · เลข 0x… ของคุณจะไม่ตรงกับในบท · บทนี้จะลบข้อมูลหลายรอบ — ลบแล้วอยากได้ข้อมูลคืน ให้สั่ง bin/rails db:reset (ในเครื่องตัวเองเท่านั้น)

อ่าน log ทีละบรรทัด (บรรทัดที่ย่อหน้าเข้าไปคือ SQL ที่ Rails ยิงไปที่ตู้ · คำหน้าสุด เช่น Post Destroy บอกว่างานของใคร):

  • BEGIN — เริ่ม transaction: "งานต่อจากนี้ ทำทั้งชุดหรือไม่ทำเลย"
  • DELETE FROM "posts" WHERE "posts"."id" = 1 — DELETE คือคำสั่ง "ทิ้ง" · แปลว่า "ทิ้งแฟ้มจากลิ้นชัก posts เฉพาะแผ่นที่เลขที่ (id) เป็น 1" · สังเกตว่า Rails ไม่ได้เช็คอะไรก่อนเลย ส่งคำสั่งทิ้งไปตรง ๆ
  • ROLLBACK — ตู้ปฏิเสธ Rails เลยยกเลิกทั้งชุด · ไม่มีอะไรหาย บทความยังอยู่ครบ

🗄 เทียบให้เห็นภาพ — ตู้ที่ไม่ยอมปล่อยแฟ้มที่ยังมีคนอ้างถึง

ใบคอมเมนต์ทุกใบมีช่อง "เป็นของบทความเลขที่ …" เขียนไว้ · ตู้ของร้านเราออกแบบมาพิเศษ — พอมีคนจะดึงแฟ้มบทความเลขที่ 1 ออกไปทิ้ง ตู้จะไม่ยอมปล่อยแฟ้มออกมา (ดึงยังไงก็ไม่ออก) เพราะยังมีใบคอมเมนต์ 2 ใบเขียนเลข 1 อยู่
คนดูแลสต็อก (model) ไม่ได้เป็นคนห้าม — เขาเดินไปดึงตามสั่งเลย แต่ตัวตู้ไม่ยอม

ที่ไม่เหมือนกัน: ตู้จริงที่ดึงแฟ้มไม่ออก คนจะลองงัด หรือเดินไปหาเองว่าใบไหนอ้างอยู่ · ตู้ของ PostgreSQL แค่ปฏิเสธแล้วบอกชื่อลิ้นชักที่อ้างถึง (table "comments") — มันไม่ได้ถามว่าเราอยากให้ทำอะไรกับใบคอมเมนต์ เราต้องบอกเองล่วงหน้า และนั่นคือเรื่องของทั้งบทนี้

เทียบกับ Go: ถ้าเขียน db.Delete(&post) ด้วย GORM (บท 27) กับตารางที่มี foreign key แบบนี้ ก็ถูกตู้ปฏิเสธด้วยกฎเดียวกัน — เพราะคนปฏิเสธคือ PostgreSQL ไม่ใช่ Rails · ภาษาไหนมาต่อตู้นี้ก็โดนกฎเดียวกันหมด (ฝั่ง Go จะได้ error กลับมาเป็นค่า err แทนการระเบิด)

🗣 ศัพท์ของ error ต้นบท
foreign key constraint · ActiveRecord::InvalidForeignKey
กฎของตู้ที่บังคับว่าเลขในช่อง post_id ต้องมีอยู่จริงในลิ้นชัก posts — ทั้งตอนเพิ่มใบลูก และตอนทิ้งแฟ้มแม่ · พิมพ์บอก AI ได้ว่า "destroying a Post raises ActiveRecord::InvalidForeignKey because comments still reference it — what are my options?"
parent · child record (แม่ · ลูก)
แฟ้มที่ถูกอ้างถึง (บทความ) คือแม่ · แฟ้มที่มีช่องชี้ไปหาแม่ (ใบคอมเมนต์ที่มี post_id) คือลูก · ถาม senior ได้ว่า "ตารางนี้ถ้าลบ parent แล้ว child ต้องเป็นยังไง ธุรกิจตัดสินไว้หรือยัง"
orphan record (แฟ้มกำพร้า)
ใบลูกที่แม่หายไปแล้ว ชี้ไปหาเลขที่ไม่มีอยู่จริง · foreign key มีไว้กันไม่ให้เกิดสิ่งนี้ · ถาม senior ได้ว่า "ตารางเก่า ๆ ที่ไม่มี foreign key มี orphan ค้างอยู่เท่าไหร่"

ทีนี้ลองทิ้งบทความ ก๋วยเตี๋ยวเรืออยุธยา (เลขที่ 4) ที่ยังไม่มีใครคอมเมนต์เลย — ตารางเดิม กฎ foreign key เดิม:

post = Post.find_by(title: "ก๋วยเตี๋ยวเรืออยุธยา")
post.comments.count    # => 0
post.destroy

บทเรียน: นี่คือเหตุผลที่บั๊กแบบนี้มักหลุดไปถึงตอนใช้งานจริง — ตอนทดสอบเรามักลบบทความที่เพิ่งสร้าง (ยังไม่มีคอมเมนต์) เลยไม่เคยเห็น error · ทดลองเสร็จแล้วสั่ง bin/rails db:reset ให้บทความกลับมาครบ 6 ชิ้น

สี่ทางเลือก — ภาพรวมก่อนลงมือ

Rails ไม่เดาให้ว่าลบบทความแล้วคอมเมนต์ควรเป็นยังไง เพราะคำตอบขึ้นกับธุรกิจ · เราต้องเลือกเองหนึ่งในสี่แบบนี้ แล้วเขียนบอกไว้ในโค้ด (สามแบบเขียนใน model · หนึ่งแบบเขียนใน migration)

ทิ้งแฟ้มบทความเลขที่ 1 (มีใบคอมเมนต์อ้างอยู่ 2 ใบ) แล้วใบคอมเมนต์… ① dependent: :destroy ทิ้งทีละใบ พร้อมจดบันทึกทุกใบ ← คนดูแลสต็อกทำ (Rails) ② dependent: :delete_all โกยทิ้งทั้งกองในครั้งเดียว ← คนดูแลสต็อกทำ (Rails) ③ on_delete: :cascade ตู้ทิ้งให้เองอัตโนมัติ ← ตัวตู้ทำ (PostgreSQL) ④ dependent: :restrict_with_error ห้ามทิ้งบทความ ถ้ายังมีใบอ้างอยู่ ← คนดูแลสต็อกห้าม (Rails)
🗑 เทียบให้เห็นภาพ — สี่วิธีเก็บกวาดใบคอมเมนต์ก่อนทิ้งแฟ้มบทความ

① คนดูแลสต็อกหยิบใบคอมเมนต์ออกมาทีละใบ ทิ้งทีละใบ และทำ "ขั้นตอนอัตโนมัติ" ของใบนั้นครบ (เช่น จดลงสมุดว่าทิ้งใบไหน) — ละเอียดแต่ช้า
② คนดูแลสต็อกโกยใบคอมเมนต์ทั้งกองของบทความนี้ลงถังทีเดียว ไม่ได้ดูทีละใบ — เร็ว แต่ไม่มีใครจดอะไร
③ ตัวตู้มีกลไกในตัว: พอแฟ้มบทความถูกดึงออก ใบคอมเมนต์ที่อ้างถึงหล่นลงถังเอง — คนดูแลสต็อกไม่รู้ด้วยซ้ำว่ามีอะไรหล่นไป
④ คนดูแลสต็อกปฏิเสธ: "บทความนี้ยังมีคอมเมนต์ ทิ้งไม่ได้" แล้วบอกเหตุผลกลับมา

ที่ไม่เหมือนกัน: ในร้านจริงถ้าทิ้งผิดยังไปคุ้ยถังขยะคืนได้ · ในฐานข้อมูล ① ② ③ ทิ้งแล้วหายถาวร ไม่มีถังให้คุ้ย (ถ้าธุรกิจอยากกู้คืนได้ ต้องออกแบบ "ลบแบบซ่อนไว้" เอง — แบบ DeletedAt ของ GORM ในบท 27)

เราจะลองทีละแบบกับบทความต้มยำกุ้ง แล้วดูว่า Rails ยิง SQL อะไรจริง · ก่อนเริ่ม ให้แปะ callback (ขั้นตอนอัตโนมัติ จากบท 112) ไว้ที่ใบคอมเมนต์ ชั่วคราว — เพื่อให้เห็นด้วยตาว่าแบบไหน "จดบันทึก" แบบไหนไม่จด (เพิ่มแค่บรรทัด after_destroy · กฎอื่นที่คุณเติมไว้จากบทก่อน ๆ คงไว้ตามเดิม): 

# app/models/comment.rb
class Comment < ApplicationRecord
  belongs_to :post
  belongs_to :user

  after_destroy { puts "📝 จดบันทึก: ทิ้งใบคอมเมนต์เลขที่ #{id} แล้ว" }
end
  • after_destroy — callback แบบที่ทำงานหลังจากใบนี้ถูกทิ้ง (ญาติของ after_commit ในบท 112)
  • { puts "…" } — block (บท 93) ที่พิมพ์ข้อความออกจอ · #{id} = แทรกเลขที่ของใบนี้ลงในข้อความ
  • ในงานจริงตรงนี้อาจเป็น "ลบรูปที่แนบมากับคอมเมนต์" หรือ "หักแต้มผู้ใช้" — งานที่ต้องเกิดทุกครั้งที่ใบคอมเมนต์หายไป

ทางที่ ① — dependent: :destroy ทิ้งทีละใบ พร้อมจดบันทึก

บอก Rails ว่า "ก่อนทิ้งบทความ ให้ทิ้งใบคอมเมนต์ของมันให้หมดก่อน แบบทีละใบ" · เติมแค่ท้ายบรรทัด has_many :comments (บรรทัดอื่นในไฟล์ของคุณ เช่น has_many :taggings จากบท 115 คงไว้): 

# app/models/post.rb
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments, dependent: :destroy
end

ทางที่ ③ — on_delete: :cascade ให้ตู้ทิ้งเอง

สองทางแรก Rails เป็นคนลบ · ทางนี้ย้ายงานไปให้ตัวตู้ (PostgreSQL) — เราแก้กฎ foreign key เดิมจาก "ห้ามทิ้งแม่ที่มีลูก" เป็น "ทิ้งแม่แล้วให้ลูกหายตาม" · การแก้กฎของตู้ = แก้โครงตู้ → ต้องเขียน migration (ใบสั่งช่าง บท 108)

เริ่มจากเอา dependent: ออกจาก Post ก่อน (ให้เห็นผลของตู้ล้วน ๆ):

  has_many :comments

แล้วสร้างใบสั่งช่างเปล่า ๆ หนึ่งใบ (ชื่อ migration ตั้งเองได้ ขอให้อ่านแล้วรู้ว่าทำอะไร):

class ChangeCommentsPostForeignKeyToCascade < ActiveRecord::Migration[8.1]
  def change
    remove_foreign_key :comments, :posts
    add_foreign_key :comments, :posts, on_delete: :cascade
  end
end

  • add_foreign_key :comments, :posts, on_delete: :cascade — "ติดกฎใหม่ ที่เวลาทิ้งแฟ้มบทความ ให้ทิ้งใบคอมเมนต์ที่อ้างถึงตามไปด้วย" · on_delete = "เมื่อมีการทิ้ง" · :cascade = "ไหลต่อเป็นทอด ๆ" (แบบน้ำตก)

ตอนพิมพ์ dependent: ผิด Rails จะบอกค่าที่ใช้ได้ทั้งหมดในข้อความ error (ดูภารกิจ) — มีอีกสองค่าที่บทนี้ไม่ได้ลอง: :nullify (ลบช่อง post_id ของลูกให้ว่าง — ใช้กับตารางเราไม่ได้ ผมลองแล้วตู้ฟ้อง NotNullViolation เพราะ post_id ตั้ง null: false ไว้) กับ :destroy_async (ทิ้งทีละใบแบบทางที่ ① แต่ทำทีหลังด้วยงานเบื้องหลัง — รอ Day 3)

บล็อกของเราเลือกอะไร: ลบบทความแล้วคอมเมนต์หายตามได้ · และอยากได้ทั้ง callback และการรับประกันของตู้ → ใช้ทางที่ ① คู่กับ ③ · Rails ลบลูกทีละใบก่อน (callback ทำงาน) · ส่วน cascade ในตู้เป็น "ตาข่ายรองรับ" เผื่อมีใครลบข้ามแอป — เป็นหลักเดียวกับประโยคหลักของวันนี้ข้อ ②: กฎใน model ไม่ใช่การรับประกัน ต้องมีกฎที่ตู้คู่กัน

ทำให้แอปของคุณอยู่ในสภาพนี้ก่อนไปหัวข้อถัดไป (โชว์เฉพาะบรรทัดที่เกี่ยว · กฎอื่นจากบทก่อน ๆ คงไว้):

# app/models/post.rb
class Post < ApplicationRecord
  belongs_to :user
  has_many :comments, dependent: :destroy
  has_many :taggings, dependent: :destroy   # ถ้ามีจากบท 115
  has_many :tags, through: :taggings            # ถ้ามีจากบท 115
end

# app/models/comment.rb — ลบบรรทัด after_destroy ที่ใส่ทดลองออก
class Comment < ApplicationRecord
  belongs_to :post
  belongs_to :user
end

ทุก has_many ที่ชี้มาหาบทความต้องตัดสินใจ ไม่ใช่แค่ comments — ผมลองติดป้าย "เผ็ด" ให้ต้มยำกุ้ง แล้วใส่ dependent: :destroy ให้ comments อย่างเดียว · destroy ยังได้ InvalidForeignKey โดยคราวนี้ท่อน on table "taggings" และคอมเมนต์ 2 ใบไม่หาย (transaction ยกเลิกทั้งชุด) · เติม dependent: :destroy ให้ has_many :taggings แล้วลบได้ — ใบจับคู่หายตาม แต่ตัวป้าย "เผ็ด" ยังอยู่ ใช้กับบทความอื่นต่อได้

migration cascade เก็บไว้ตามเดิม · แล้วสั่ง bin/rails db:reset ให้ได้ข้อมูลครบ 6 บทความ 7 คอมเมนต์

🗣 ศัพท์ของ counter_cache
counter cache
คอลัมน์ที่เก็บจำนวนลูกไว้บนแฟ้มแม่ (posts.comments_count) ให้ Rails บวก/ลบให้เอง · แก้ N+1 ของ COUNT · พิมพ์บอก AI ได้ว่า "add a counter_cache for post.comments, include the migration with default 0 and a backfill"
backfill
การเติมค่าให้แฟ้มเก่าที่มีอยู่ก่อนเพิ่มคอลัมน์ใหม่ · ไม่ทำ = ข้อมูลเก่าผิดเงียบ ๆ · ถาม senior ได้ว่า "คอลัมน์ใหม่นี้ต้อง backfill ไหม ทำใน migration หรือแยกเป็น task" (ตารางใหญ่ ๆ อย่าทำทีเดียวในตอน deploy — เรื่องตู้ค้างจากบท 109)
reset_counters

ข้อ 1 · ต้นบท post.destroy ได้ ActiveRecord::InvalidForeignKey และ log มี DELETE FROM "posts" … ตามด้วย ROLLBACK — ใครเป็นคนไม่ยอมให้ลบ?

ตัวเลือกที่ 3 ถูก · log ยืนยันว่า Rails ส่ง DELETE ออกไปแล้ว ตู้ตอบกลับด้วย PG::ForeignKeyViolation (PG = PostgreSQL) แล้ว Rails จึง ROLLBACK

ตัวเลือกที่ 1 คือสิ่งที่ restrict_with_error ทำ (มีบรรทัด Comment Exists? และไม่มี DELETE) — แต่ต้นบทยังไม่ได้ใส่ · ตัวเลือกที่ 2 ไม่มี nil เกี่ยวเลย error พูดถึง foreign key ตรง ๆ · ตัวเลือกที่ 4 ผิด — ในกล่องทายผลแรกของบท console ลบก๋วยเตี๋ยวเรือได้ปกติ

จุดที่ต้องจำ: error ที่ขึ้นต้นด้วย PG:: = ตู้เป็นคนพูด · ถ้าไม่บอกล่วงหน้าว่าลูกจะเป็นยังไง Rails ไม่เช็คให้ ส่งคำสั่งไปให้ตู้ตัดสินเลย

ข้อ 2 · ใบคอมเมนต์มี callback ที่ต้องลบรูปแนบออกจากที่เก็บไฟล์ทุกครั้งที่ใบนั้นหายไป — ตอนลบบทความ ควรใช้แบบไหน?

ตัวเลือกที่ 1 ถูก · ในบทนี้มีแค่ทางที่ ① ที่เห็นบรรทัด 📝 ขึ้นทุกใบ — เพราะ Rails หยิบใบคอมเมนต์ขึ้นมาเป็น object ทีละใบ callback จึงได้ทำงาน

ตัวเลือกที่ 2 ลบได้เร็ว แต่ไม่มี Comment Load ไม่มี object → ไม่มี 📝 → รูปแนบค้างเป็นขยะ · ตัวเลือกที่ 3 ตู้ลบเองข้างใน log ไม่พูดถึงคอมเมนต์เลย callback ไม่ทำงานแน่นอน · ตัวเลือกที่ 4 ไม่ได้ลบคอมเมนต์ (และไม่ลบบทความด้วย) ไม่ตรงกับโจทย์ที่อยากลบบทความ

จุดที่ต้องจำ: "ลูกมีงานที่ต้องทำตอนหายไปไหม" — มี → :destroy · ยอมจ่ายด้วยจำนวนคำสั่งที่เท่ากับจำนวนลูก

ข้อ 3 · ใช้ on_delete: :cascade และไม่มี dependent: ใน Post · ทิ้งบทความที่มีคอมเมนต์ 2 ใบ — log ของ Rails จะมีบรรทัด DELETE กี่บรรทัด?

ตัวเลือกที่ 4 ถูก · ผลจริงในหัวข้อทางที่ ③ มี DELETE บรรทัดเดียว (DELETE FROM "posts" WHERE "posts"."id" = 1) ตามด้วย COMMIT · แต่คอมเมนต์ลดจาก 7 เหลือ 5 จริง

ตัวเลือกที่ 1 คือหน้าตาของทางที่ ① (:destroy) · ตัวเลือกที่ 2 คือหน้าตาของทางที่ ② (:delete_all) · ตัวเลือกที่ 3 ผิดเพราะคนเริ่มลบยังเป็น Rails — Rails สั่งลบบทความ ตู้แค่ลบลูกตามให้ต่อจากนั้น

จุดที่ต้องจำ: cascade = Rails ไม่รู้เรื่อง · ดู log อย่างเดียวจะไม่รู้เลยว่ามีคอมเมนต์หายไป ต้องดูที่ schema.rb (on_delete: :cascade)

ข้อ 4 · เพิ่มคอลัมน์ comments_count + ใส่ counter_cache: true + backfill เรียบร้อย · loop โชว์จำนวนคอมเมนต์ของบทความ 6 ชิ้น — ใช้ method ไหนแล้ว log มี SQL แค่คำสั่งเดียว (ตอนหยิบบทความ)?

ตัวเลือกที่ 2 ถูก · ผลจริง: loop ที่ใช้ size มีแค่ Post Load บรรทัดเดียว แล้วตัวเลขออกมาครบ 6 บรรทัด

ตัวเลือกที่ 1 — count ไปนับที่ตู้ (COUNT(*)) ทุกครั้ง ไม่สนป้าย ผมลองแล้วได้ 7 คำสั่ง · ตัวเลือกที่ 3 — length ต้องหยิบใบคอมเมนต์ทุกใบขึ้นมาก่อนถึงจะนับในมือได้ ได้ 7 คำสั่งเหมือนกัน (และหนักกว่า) · ตัวเลือกที่ 4 — ป้ายไม่ได้เปลี่ยนพฤติกรรมของ count กับ length

จุดที่ต้องจำ: counter_cache ได้ผลเฉพาะ size · และถ้าลืม backfill size จะตอบ 0 อย่างมั่นใจ

ถามกลับได้เลย

ถ้าตารางของคุณมีลูกหลายชั้น (บทความ → คอมเมนต์ → ไลก์) แล้วไม่แน่ใจว่าแต่ละชั้นควรใช้ dependent แบบไหน — ส่งให้เพื่อน senior หรือ AI สามอย่าง: db/schema.rb · model ทุกตัวที่เกี่ยว · และคำตอบของธุรกิจว่า "ลบแม่แล้วลูกต้องเป็นยังไง" · อย่างสุดท้ายสำคัญที่สุด ไม่มีมันใครก็ตอบแทนไม่ได้
