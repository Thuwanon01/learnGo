เราจะสั่ง scaffold สร้างแผนกให้ทั้งชุด แล้วเติมของที่มันไม่ให้ทีละอย่าง: กฎตรวจแฟ้ม · กฎของตัวตู้ · ผูกกับบทความ · หน้ารายการที่ไม่เดินไปตู้หลายรอบ · ระหว่างทางจะทำให้พังโดยตั้งใจ เพื่อเห็นกับตาว่าด่านไหนกันอะไรได้
อ่านจบแล้วคุณจะตรวจโค้ดที่เครื่อง (หรือ AI) เขียนให้ได้ว่าขาดอะไร และเขียน prompt (ข้อความสั่งงาน AI) ที่บอกครบตั้งแต่รอบแรก

🔁 ทวนก่อนเริ่ม — Lab นี้ใช้คำพวกนี้ตลอด ถ้าข้อไหนไม่คุ้นให้กลับไปบทนั้นก่อน

  • migration = ใบสั่งช่างมาต่อเติมตู้ · bin/rails db:migrate = ให้ช่างลงมือ (บท 108)
  • validation = คนดูแลสต็อกตรวจแฟ้มก่อนเก็บ · errors.full_messages = รายการเหตุผลที่ไม่รับ (บท 110)
  • constraint (เช่น NOT NULL · unique index) = ตัวตู้ที่ออกแบบให้ใส่แฟ้มผิดแบบไม่ได้เลย (บท 111)
  • N+1 = เดินไปตู้ทีละแผ่นหลายสิบรอบ · includes = เขียนใบเบิกทีเดียวหยิบมาทั้งตะกร้า (บท 114)
  • scaffold = ชุดเปิดแผนกสำเร็จรูป ได้ model + migration + route + controller + view ในคำสั่งเดียว (บท 118)

  • db/migrate/…_create_categories.rb — ใบสั่งช่างต่อลิ้นชักใหม่ชื่อ categories (เลขหน้าชื่อไฟล์ของคุณจะต่าง)
  • app/models/category.rb — คนดูแลสต็อกของแผนกนี้
  • route resources :categories — พนักงานต้อนรับได้รายการใหม่ 8 เส้น (บท 101)
  • categories_controller.rb + app/views/categories/*.html.erb — หัวหน้าเชฟกับคนจัดจานของแผนก
  • test/… · *.json.jbuilder — ไฟล์เทส กับแบบจัดจานเป็นข้อมูล JSON · วันนี้ยังไม่แตะ (เทสอยู่ Day 4) · tailwindcss โผล่เพราะเราสร้างแอปด้วย --css=tailwind

# db/migrate/20261104120835_create_categories.rb
class CreateCategories < ActiveRecord::Migration[8.1]
  def change
    create_table :categories do |t|
      t.string :name
      t.string :slug

      t.timestamps
    end
  end
end

# app/models/category.rb
class Category < ApplicationRecord
end
  • t.string :name · t.string :slug — ต่อช่องสองช่องบนแฟ้ม · ไม่มี null: false = ช่องนี้ว่างก็ได้
  • t.timestamps — ต่อช่อง created_at กับ updated_at (เวลาสร้าง · เวลาแก้ล่าสุด) ให้เอง (บท 108)
  • ไม่มี index ที่ slug (index = ป้ายแท็บเรียงตัวอักษรในลิ้นชัก · บท 109) และไม่มีกฎ "ห้ามซ้ำ" = slug ซ้ำกันกี่แผ่นตู้ก็รับ
  • class Category < ApplicationRecord แล้ว end เลย = คนดูแลสต็อกที่ไม่ตรวจอะไรเลย
🍽 เทียบให้เห็นภาพ — ชุดเปิดแผนกใหม่จากแฟรนไชส์

สำนักงานใหญ่ส่งชุดเปิดแผนกมาให้ครบ: ลิ้นชักเปล่าหนึ่งลิ้นชัก · พนักงานต้อนรับที่รู้เส้นทาง · เชฟ · คนจัดจาน · แบบฟอร์มสั่งของ · เปิดร้านได้ทันทีในห้านาที
แต่ชุดนี้ถูกออกแบบให้ใช้ได้กับทุกสาขาทั่วประเทศ — มันไม่รู้ว่าร้านเรามีกฎว่า "หมวดต้องมีชื่อ" "ชื่อ URL ห้ามซ้ำ" "ห้ามทิ้งหมวดที่ยังมีบทความ" กฎพวกนั้นเราต้องติดเอง

ที่ไม่เหมือนกัน: ชุดจากแฟรนไชส์จริงมักมีคู่มือบอกว่า "ต้องตั้งค่าอะไรเพิ่ม" · scaffold ไม่บอกอะไรเลย มันสร้างไฟล์เสร็จแล้วเงียบ — โค้ดที่ได้ดูครบ ใช้ได้จริง จนเราไม่รู้ตัวว่าขาด (เหมือนโค้ดจาก AI ที่บทนี้จะพูดถึงตอนท้าย)

เทียบกับ Go: ฝั่ง Go ไม่มีคำสั่งแบบนี้ — ใน Gin คุณเขียน handler ทีละตัว เขียน struct เอง และเขียน migration ของ goose เอง (บท 31) · ข้อดีคือทุกบรรทัดคุณตั้งใจเขียน · ข้อเสียคือช้า · scaffold กลับกัน: เร็วมาก แต่ทุกบรรทัดที่ได้คือ "ค่าตั้งต้นที่ไม่มีกฎ" ที่เราต้องอ่านเองว่าขาดอะไร

🗣 ศัพท์ของขั้นนี้
scaffold
คำสั่งที่สร้าง model · migration · route · controller · view ของหนึ่งเรื่องให้ครบในคำสั่งเดียว (แปลตรงตัวว่า "นั่งร้าน" — โครงชั่วคราวที่ต้องเติมต่อ) · พิมพ์บอก AI ได้ว่า "this was generated by rails scaffold, list what validations and DB constraints are missing" แล้วให้มันไล่ให้
generator · bin/rails destroy
generator = คำสั่งตระกูล bin/rails generate … ที่เขียนไฟล์ให้ · bin/rails destroy … คือคำสั่งคู่กันที่ลบไฟล์ชุดเดียวกันทิ้ง · ถาม senior ได้ว่า "ทีมเราใช้ scaffold ได้ไหม หรือให้เขียน controller เอง"

สไลด์อ้างว่าผลที่ได้มักเป็น model ที่มี validates presence สองบรรทัด กับ migration ที่ไม่มี constraint อะไรเลย (ผมไม่ได้ลองส่งให้ AI ในบทนี้ — แต่ขั้น 1 เราเห็นแล้วว่า scaffold ให้น้อยกว่านั้นอีก) · เหตุผลง่าย ๆ: prompt บอกแค่รูปร่าง (มีช่องอะไร) ไม่ได้บอกกฎของร้าน · ทั้ง scaffold และ AI ไม่รู้กฎที่เราไม่บอก

📞 เทียบให้เห็นภาพ — โทรสั่งชุดเปิดแผนกจากสำนักงานใหญ่

โทรไปบอกสำนักงานใหญ่ว่า "ส่งชุดแผนกหมวดอาหารมาหน่อย" → ได้ชุดมาตรฐานแบบขั้น 1: ลิ้นชัก เชฟ คนจัดจาน ใช้ได้ทันที · แต่ไม่มีกฎของร้านเราสักข้อ เพราะเราไม่ได้บอก
ถ้าอยากได้แบบที่ร้านเราใช้ ต้องบอกเป็นข้อ ๆ: "แฟ้มไม่มีชื่อห้ามเข้าลิ้นชัก · ป้ายห้ามซ้ำ · ห้ามทิ้งหมวดที่ยังมีบทความ · …" · ยิ่งบอกกฎครบ ยิ่งได้ของถูกตั้งแต่รอบแรก — และเราเอารายการเดียวกันนี้ไว้ตรวจรับของได้ด้วย

ที่ไม่เหมือนกัน: พนักงานสำนักงานใหญ่ที่ดีมักถามกลับว่า "ชื่อหมวดซ้ำได้ไหมครับ" · AI ส่วนใหญ่ไม่ถาม มันเดาค่าที่พบบ่อยแล้วเขียนออกมามั่นใจมาก · และของจากสำนักงานใหญ่มีคนรับผิดชอบ แต่โค้ดจาก AI คนรับผิดชอบคือคนที่กด merge (รวมโค้ดเข้าโปรเจกต์หลัก) — คือเรา · ต้องรันตรวจเองแบบที่ทำมาทั้ง Lab

โจทย์: ก่อนกดเฉลย เขียน prompt ของคุณเองลงในโน้ตหรือแชท — ใช้ทุกอย่างที่เพิ่งทำใน Lab นี้ (ขั้น 1–6) ใส่เงื่อนไขให้มากที่สุด · ไม่จำกัดความยาว · ภาษาไทยได้ · แล้วค่อยเทียบกับตัวอย่าง

ตัวอย่างที่ผมเขียนจากของที่ทำใน Lab นี้ + รายการในสไลด์หน้า 58 (ไม่ได้ลองส่งให้ AI จริงในบทนี้ — เป็นตัวอย่างวิธีเขียน ไม่ใช่สูตรที่รับประกันผล): 

ช่วยเพิ่มหมวดอาหาร (Category) ให้แอป Rails 8.1 ชื่อ wongnok_blog (PostgreSQL)
โดยเริ่มจาก bin/rails generate scaffold Category name:string slug:string แล้วเติมให้ครบตามนี้

กฎของข้อมูล (ต้องมีทั้งใน model และใน migration ทุกข้อ)
1. name กับ slug ห้ามว่าง — validates presence ใน model และ null: false ที่ DB
2. slug ห้ามซ้ำ — validates uniqueness ใน model และ unique index ที่ DB
3. slug รับได้แค่ a-z 0-9 และขีด (-) — ใช้ format validation
4. name ยาวไม่เกิน 80 ตัวอักษร
5. ถ้าไม่ได้กรอก slug ให้สร้างจาก name อัตโนมัติด้วย before_validation
   ระวัง: ฟอร์มส่งช่องว่างมาเป็น "" ไม่ใช่ nil ให้เช็คด้วย blank? ไม่ใช่ ||=
   ถ้าชื่อเป็นภาษาไทยจนสร้าง slug ไม่ได้ ให้ขึ้น error ไม่ใช่บันทึกค่าว่าง

ความสัมพันธ์
6. Category has_many :posts — เพิ่ม category_id ให้ posts แบบว่างได้ (null: true)
   เพราะบทความเดิมยังไม่มีหมวด แต่ต้องมี foreign key และ index
   Post belongs_to :category, optional: true
7. ห้ามลบหมวดที่ยังมีบทความ — dependent: :restrict_with_error
   และแก้ destroy ใน controller ไม่ให้ใช้ destroy! ถ้าลบไม่ได้ให้กลับหน้ารายการพร้อมข้อความ

หน้ารายการ (index)
8. เรียงตามชื่อ · แบ่งหน้าหรืออย่างน้อย limit 50
9. หน้ารายการโชว์จำนวนบทความของแต่ละหมวด — ใช้ includes(:posts) กัน N+1

อื่น ๆ
10. ข้อความ error เป็นภาษาไทยผ่าน i18n (ไฟล์ใน config/locales)
11. ใช้ params.expect ของ Rails 8 ไม่ใช่ require/permit
12. ถ้า migration ไหนจะพังเพราะข้อมูลเก่า (เช่น NOT NULL กับแถวที่เป็น null) ให้เตือนก่อน
    และบอกวิธีจัดการข้อมูลเก่า

ส่งกลับมาเป็น: รายชื่อไฟล์ที่สร้าง/แก้ · โค้ดเต็มของแต่ละไฟล์ · คำสั่งที่ต้องรันตามลำดับ
· และคำสั่งใน bin/rails console ที่ใช้พิสูจน์ว่ากฎแต่ละข้อทำงานจริง
(รวมถึง save(validate: false) ที่ต้องพังที่ชั้น DB)

สามสิ่งที่ทำให้ prompt นี้ต่างจากประโยคเดียวของสไลด์:

  • บอกบริบท — Rails เวอร์ชันไหน DB อะไร มีข้อมูลเก่าอยู่แล้ว (AI จะได้ไม่ใส่ null: false ที่พังแบบภารกิจข้อ 1)
  • บอกกฎเป็นคู่ — ทุกกฎระบุว่าต้องอยู่ทั้ง model และ DB · ข้อ 5 บอกกับดักที่เราเจอเองด้วย
  • บอกวิธีตรวจรับ — ขอคำสั่งพิสูจน์ใน console มาด้วย · เราจะได้รันตรวจแทนการเชื่อว่า "ดูครบแล้ว"

ข้อ 10 (i18n = ระบบแปลข้อความเป็นหลายภาษาของ Rails · ข้อความ can't be blank จะกลายเป็นภาษาไทย) กับการแบ่งหน้าในข้อ 8 เราไม่ได้ทำใน Lab นี้ — ใส่ไว้เพราะสไลด์ขอ · ได้โค้ดกลับมาแล้วต้องรันตรวจเองเหมือนข้ออื่น

กลับมาที่ 3 ประโยคของวัน

ตอนเช้า (สไลด์หน้า 3) ผู้สอนบอกว่าถ้าจำได้แค่ 3 อย่าง ให้จำสามประโยคนี้ · สไลด์หน้า 59 กลับมาถามอีกครั้ง · Lab นี้ทำให้คุณเห็นทั้งสามประโยคกับมือแล้ว:

ประโยคในร้านอาหารเห็นกับมือใน Lab ตรงไหน
① schema เปลี่ยนได้โดยไม่ต้องดับแอป
expand → migrate → contract · เพราะโค้ดกับ DB ไม่มีวันเปลี่ยนพร้อมกันเป๊ะ		 ปรับปรุงร้านโดยไม่ปิดร้าน: ต่อลิ้นชักใหม่ก่อน → ย้ายแฟ้ม → ค่อยรื้อของเก่า ภารกิจข้อ 1–2: category_id ต้องเริ่มแบบ null: true (expand) · เติมหมวดให้บทความ (migrate) · ค่อยขันเป็น NOT NULL ทีหลัง · ขั้น 3: เปลี่ยนตู้ทั้งที่มีแฟ้มเสียค้าง = ช่างไม่ยอม
② validation ใน model ไม่ใช่การรับประกัน
ต้องมี constraint ที่ DB คู่กัน · เพราะ "ตรวจ" กับ "เขียน" เป็นสองคำสั่งแยกกัน		 คนดูแลสต็อกตรวจเก่ง แต่คนเข้าทางหลังร้านเขาไม่เห็น · ลิ้นชักที่ทำร่องไว้กันได้ทุกทาง ขั้น 2: save(validate: false) เข้าตู้ได้ · ขั้น 4: คำสั่งเดียวกันพังที่ DB · และกฎ uniqueness ถามตู้ก่อน (Category Exists?) แล้วค่อยเขียน — สองจังหวะ มีช่องว่างตรงกลาง (บท 111)
③ N+1 ไม่ได้อ่านจากโค้ด อ่านจาก log
includes / preload / eager_load · เพราะ ORM ซ่อน SQL เก่งจนลืมว่าทุกบรรทัดคือการถาม DB		 เดินไปตู้ทีละแผ่นหลายสิบรอบ · ดูจากใบเบิกไม่รู้ ต้องเปิดสมุดบันทึกการเบิกของ ขั้น 6: โค้ด category.posts.size บรรทัดเดียวดูไม่มีพิษภัย · log บอกว่า 5 query · เติม includes เหลือ 3 และไม่โตตามจำนวนหมวด

Checklist ท้ายวัน — ควรเข้าใจอะไรแล้ว

ติ๊กในใจทีละข้อ · ข้อไหนลังเล กลับไปบทนั้น 5 นาทีก่อนเข้า Day 3:

  • ☐ อธิบายได้ว่า Active Record คือ "แฟ้มที่เดินเข้าลิ้นชักเองได้" และต่างจาก Data Mapper ยังไง (106)
  • ☐ สร้าง อ่าน แก้ ลบ ใน console ได้ และแปล SQL ที่ console โชว์เป็นภาษาคนได้ (107)
  • ☐ เขียน migration · migrate · rollback ได้ และรู้ว่า schema.rb คือแปลนตู้ฉบับล่าสุด (108)
  • ☐ รู้ว่า migration แบบไหนอาจทำร้านค้าง และเปลี่ยนชื่อคอลัมน์แบบ expand → migrate → contract (109)
  • ☐ ใส่ validation · อ่าน errors.full_messages · รู้ว่า save กับ save! ต่างกันยังไง (110)
  • ☐ ใส่ constraint คู่กับ validation ทุกครั้ง และอธิบายได้ว่าทำไม uniqueness อย่างเดียวกันซ้ำไม่ได้ (111 + Lab นี้)
  • ☐ รู้ว่า callback เหมาะกับงานแบบไหน และงานไหนควรย้ายออกไป (112)
  • ☐ เปิด log แล้วนับได้ว่าหน้าหนึ่งไปตู้กี่ครั้ง และแก้ N+1 ด้วย includes (113–114)
  • ☐ ผูก belongs_to / has_many ได้ และเลือก dependent จากกฎของธุรกิจ (115–116)
  • ☐ อธิบายได้ว่า params.expect กันอะไร และไม่ได้กันอะไร (117)
  • ☐ อ่านไฟล์ที่ scaffold (หรือ AI) เขียนให้ แล้วบอกได้ว่าขาดอะไร ด้วย checklist 8 ข้อ (118 + Lab นี้)

ตัวเลือกที่ 1 ถูก · ผลจริงในขั้น 6: Post Load … WHERE "posts"."category_id" IN (4, 1, 5) บรรทัดเดียว · ทั้งหน้า 3 queries

ตัวเลือกที่ 2 คือผลก่อนเติม includes (Post Count 3 บรรทัด) · ตัวเลือกที่ 3 ผิดครึ่งเดียว — size ไม่ต้องไปตู้ตอนนับ เพราะบทความอยู่ในมือแล้ว แต่ต้องไปหยิบมาก่อนหนึ่งครั้ง · ตัวเลือกที่ 4 คือหยิบซ้ำซ้อน — หยิบทั้งตะกร้าแล้วยังเดินไปตู้ทีละหมวดอีก ถ้าเป็นแบบนั้น includes ก็ไม่ได้ช่วยอะไร (ผลจริงไม่มีบรรทัดรายหมวดเลย)

จุดที่ต้องจำ: แก้ N+1 แล้วจำนวนครั้งต้องไม่โตตามจำนวนแถว · ตรวจด้วยการนับใน log ไม่ใช่ด้วยการอ่านโค้ด — ประโยคที่ ③

ข้อ 3 · ร้านเปิดอยู่ตลอด ไม่อยากปิดเลย · อยากเปลี่ยนชื่อช่อง name ของ categories เป็น title · ลำดับไหนปลอดภัย?

ตัวเลือกที่ 2 ถูก · นี่คือ expand → migrate → contract จาก บท 109 — ทุกช่วงระหว่างทาง โค้ดเก่าก็ใช้ได้ โค้ดใหม่ก็ใช้ได้

ตัวเลือกที่ 1 มีช่วงที่ตู้เปลี่ยนแล้วแต่แอปยังเป็นโค้ดเก่า → โค้ดเก่าหาช่อง name ไม่เจอ · ตัวเลือกที่ 4 กลับด้านกัน มีช่วงที่โค้ดใหม่หาช่อง title ไม่เจอ (บท 109 อธิบายว่าช่วงนี้หนีไม่พ้น เพราะ migrate กับ restart แอปเกิดคนละจังหวะ) · ตัวเลือกที่ 3 ข้อมูลหายทั้งหมด

จุดที่ต้องจำ: ไม่มี deploy ไหนที่โค้ดกับตู้เปลี่ยนพร้อมกันเป๊ะ — ต้องมีช่วงที่ของเก่ากับของใหม่อยู่ด้วยกันได้ · ประโยคที่ ①

ข้อ 4 · Category มี has_many :posts, dependent: :restrict_with_error · หมวด อาหารไทย มีบทความ 2 ชิ้น · สั่ง thai.destroy — ได้อะไร?

ตัวเลือกที่ 4 ถูก · ผลจริงในภารกิจข้อ 5: thai.destroy → false · thai.errors.full_messages → ["Cannot delete record because dependent posts exist"]

ตัวเลือกที่ 1 คือ dependent: :destroy · ตัวเลือกที่ 2 คือ dependent: :nullify (บท 116) · ตัวเลือกที่ 3 คือ restrict_with_exception — หรือการเรียก destroy! แบบ controller ของ scaffold ซึ่งเราเห็นหน้าแดง RecordNotDestroyed ในภารกิจข้อ 6

จุดที่ต้องจำ: จะเลือก dependent แบบไหน คำตอบมาจากกฎของธุรกิจ ไม่ใช่จาก scaffold หรือ AI · และถ้าใช้ restrict_with_error ต้องเช็คผลของ destroy ใน controller ด้วย
