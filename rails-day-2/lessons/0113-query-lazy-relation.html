Query — ใบเบิกของที่ยังไม่ยื่น จนกว่าจะใช้ข้อมูลจริง

~20–25 นาที (ถ้าลองใน console ตามทุกก้อน) · ควรผ่าน บทเรียน 106 (Active Record · SQL ภาษาคน) และ บทเรียน 107 (ลอง where · first ใน console) มาก่อน

เรื่องที่ทำให้มือใหม่งงที่สุดเรื่องหนึ่งของ Rails: พิมพ์ Post.where(...) แล้ว Rails ยังไม่ได้ไปเอาข้อมูลจากฐานข้อมูลเลย
อ่านจบบทนี้ คุณจะบอกได้ว่าบรรทัดไหน "ไปตู้จริง" บรรทัดไหนยังไม่ไป · เปิดดู SQL ที่แอปยิงจริงจาก log ได้ · และเลือกใช้ count · size · length · exists? · pluck · sum ได้ถูกตัว โดยให้ฐานข้อมูลทำงานให้ แทนที่จะขนข้อมูลมาทั้งหมด

🔁 ทวนก่อนเริ่ม — คำจากบทก่อน ๆ ที่บทนี้ใช้

  • model Post (บท 106) — "คนดูแลสต็อก" ของลิ้นชัก posts · เรียก method ของมัน แล้วมันไปคุยกับฐานข้อมูลให้
  • SQL (บท 106) — ภาษาที่ใช้สั่งตู้เก็บแฟ้ม (ฐานข้อมูล) · Active Record แปลคำสั่ง Ruby เป็น SQL ให้เอง
  • bin/rails console (บท 104, 107) — ครัวทดลองหลังร้าน พิมพ์โค้ดทีละบรรทัดแล้วเห็นผลทันที · เห็น SQL ที่ Rails ยิงด้วย
  • Post.where(...) · first · all (บท 107) — หาแฟ้มตามเงื่อนไข · เอาแผ่นแรก · เอาทั้งหมด
  • log ของ server (บท 100, 104) — ข้อความ Started GET … / Completed 200 OK … ที่ขึ้นทุกครั้งที่มีใบสั่งเข้าร้าน

ทวน SQL ภาษาคน — คำที่จะเห็นทั้งบท

ทั้งบทนี้เราจะอ่าน SQL ที่ Rails ยิงออกไป · ไม่ต้องเขียน SQL เป็น แค่อ่านออกว่ามันขออะไรจากตู้ก็พอ
นี่คือคำทั้งหมดที่จะเจอ (ทวนจากบท 106 และเพิ่มอีกนิด):

คำใน SQLแปลเป็นภาษาคน
SELECT "posts".*ขอทุกช่องของแฟ้ม (* = ทุกช่อง)
SELECT "posts"."title"ขอแค่ช่อง title ช่องเดียว
FROM "posts"จากลิ้นชัก posts
WHERE …เฉพาะแผ่นที่ตรงเงื่อนไขนี้
… AND …"และ" — ต้องตรงทั้งสองเงื่อนไข
ORDER BY … DESC / ASCเรียงตามช่องนี้ · DESC = มากไปน้อย · ASC = น้อยไปมาก
LIMIT 10เอามาไม่เกิน 10 แผ่น
COUNT(*)ไม่ต้องหยิบแฟ้มมา แค่นับให้หน่อยว่ามีกี่แผ่น
SUM(…) · AVG(…)บวกตัวเลขในช่องนี้ของทุกแผ่น · หาค่าเฉลี่ย
GROUP BY …แยกกองตามช่องนี้ก่อน แล้วค่อยนับ/บวกทีละกอง
… AS "ชื่อ"ตั้งชื่อเล่นให้ผลลัพธ์ช่องนั้น (Rails ใส่ไว้ใช้เอง ข้ามได้)
UPDATE … SET …แก้ค่าในช่องนี้ ของทุกแผ่นที่ตรงเงื่อนไข

ลองแปลหนึ่งประโยคเต็ม ๆ:

SELECT "posts".* FROM "posts" WHERE "posts"."published" = TRUE ORDER BY "posts"."views" DESC LIMIT 10

= "ขอแฟ้มทุกช่อง จากลิ้นชัก posts · เฉพาะแผ่นที่ช่อง published เป็นจริง · เรียงตามยอดวิวมากไปน้อย · เอามาไม่เกิน 10 แผ่น"
เครื่องหมาย "…" รอบชื่อเป็นแค่วิธีเขียนชื่อของ PostgreSQL · "posts"."views" อ่านว่า "ช่อง views ของลิ้นชัก posts"

Post.where(...) ไม่ใช่ข้อมูล — มันคือใบเบิกของ

ตอนพิมพ์ Post.where(published: true) หลายคนคิดว่า "Rails ไปเอาบทความที่ published มาให้แล้ว" · ความจริงคือยังไม่ได้ไปเลย
สิ่งที่ where คืนมาคือคำขอที่จดไว้ว่า "อยากได้อะไร" · Rails จะไปตู้จริงก็ต่อเมื่อเราเริ่มใช้ข้อมูล เช่น วนลูปโชว์ หรือนับจำนวน

ประโยชน์ของการออกแบบแบบนี้: เราต่อเงื่อนไขเพิ่มได้ทีละบรรทัด (where แล้ว order แล้ว limit) · Rails รวมทุกอย่างเป็น SQL ประโยคเดียว แล้วไปตู้ครั้งเดียวตอนท้าย · ไม่ใช่ไปตู้ทุกบรรทัด

📝 เทียบให้เห็นภาพ — ใบเบิกของที่ยังเขียนไม่เสร็จ

Post.where(published: true) เหมือนหยิบใบเบิกของมาหนึ่งใบ แล้วเขียนว่า "เอาแฟ้มที่ published แล้ว" · .order(views: :desc) = เขียนต่อว่า "เรียงตามยอดวิว" · .limit(10) = "ขอแค่ 10 แผ่น"
ตลอดเวลาที่ยังเขียนอยู่ ไม่มีใครเดินไปตู้เลย · คนดูแลสต็อกจะเดินไปก็ต่อเมื่อเรา "ยื่นใบ" — คือตอนที่เราต้องการของจริง เช่น จะเอาแฟ้มมาวางเรียงบนจาน (each)

ที่ไม่เหมือนกัน: ใบเบิกของจริงยื่นแล้วก็หมดหน้าที่ · แต่ใบเบิกของ Rails ยื่นซ้ำได้ และบางคำสั่ง (เช่น count) จะเดินไปตู้ใหม่ทุกครั้งที่เรียก แม้เคยยื่นไปแล้ว — เดี๋ยวเห็นจริงในหัวข้อ count vs size

เทียบกับ Go (GORM): GORM ก็ต่อเงื่อนไขทีละท่อนได้เหมือนกัน แต่ต้องปิดท้ายด้วยคำสั่งที่สั่งให้ไปตู้เอง เช่น Find · ตามเอกสาร GORM เรียกคำสั่งพวกนี้ว่า Finisher Methods และบอกว่ามันยิง SQL ทันที: 

// Go + GORM — บรรทัดนี้ไปตู้ทันที เพราะลงท้ายด้วย Find
var posts []Post
db.Where("published = ?", true).Order("views desc").Find(&posts)
# Ruby + Rails — บรรทัดนี้ยังไม่ไปตู้ ไม่มีคำว่า Find ท้าย
posts = Post.where(published: true).order(views: :desc)
  • ฝั่ง Go: Find(&posts) = "ไปตู้เดี๋ยวนี้ แล้วเทแฟ้มที่ได้ใส่ slice posts" · อ่านโค้ดแล้วเห็นชัดว่าไปตู้ตรงไหน
  • ฝั่ง Rails: posts ได้ใบเบิกของ · จะไปตู้ตอนไหนขึ้นกับว่าบรรทัดถัด ๆ ไปเอา posts ไปทำอะไร — อ่านบรรทัดเดียวไม่รู้
  • :desc — symbol (บท 92) แปลว่า "มากไปน้อย"
🗣 ศัพท์ที่เพิ่งเรียนไป
ActiveRecord::Relation (relation)
ชนิดของสิ่งที่ where · order · limit คืนมา = "ใบเบิกของ" ที่ยังไม่ยื่น · ใน console จะเห็นชื่อเต็มว่า Post::ActiveRecord_Relation · พิมพ์บอก AI ได้ว่า “this returns an ActiveRecord::Relation, when does it actually hit the database?”
lazy loading · lazy evaluation
"ขี้เกียจไว้ก่อน" — ยังไม่ทำงานจริงจนกว่าจะต้องใช้ผล · คำว่า hit the database = ไปตู้จริง · ถาม senior ได้ว่า “relation นี้ถูก load ตรงไหน ใน controller หรือใน view”
query chaining · finisher
การต่อคำสั่ง .where.order.limit เป็นสาย · ฝั่ง GORM คำสั่งปิดท้ายที่ไปตู้ (Find · First) เรียกว่า finisher · พิมพ์บอก AI ได้ว่า “in GORM I call Find to execute, what triggers execution in ActiveRecord?”

ทั้งสองอย่างนี้ console ใส่เอง ไม่ใช่ของ where:

  • console มีนิสัยโชว์ผลของทุกบรรทัดหลังเครื่องหมาย => · จะโชว์ใบเบิกของได้ ต้องรู้ก่อนว่าได้แฟ้มอะไร → เลยยื่นใบให้เราเอง
  • pp = "pretty print" คำสั่งพิมพ์สวย ๆ ที่ console ใช้โชว์ผล · loading for pp = "ไปตู้เพราะจะพิมพ์ให้ดู"
  • LIMIT 11 = console ขอแค่ 11 แผ่นพอ เผื่อตารางใหญ่จะได้ไม่ขนมาทั้งลิ้นชัก
  • /*application='WongnokBlog'*/ ท้ายสุด = ป้ายชื่อแอปที่ Rails แปะไว้ท้าย SQL ทุกประโยค · ไม่ต้องสนใจ (เดี๋ยวเจออีกในหัวข้อ log)
  • "views > ?", 100 — เงื่อนไขแบบเขียนเอง · ? คือช่องว่างที่ Rails เอา 100 ไปเติมให้อย่างปลอดภัย (เหมือน ? ใน db.Where ของ GORM)

ในแอปจริง (controller · view) ไม่มีนิสัยนี้ — ไม่มีใครมาโชว์ผลทุกบรรทัด · กับดักนี้มีแค่ใน console
วิธีแก้: ต่อท้ายบรรทัดด้วย ; nil · ; คือ "จบคำสั่งแรก ขึ้นคำสั่งใหม่ในบรรทัดเดียวกัน" · คำสั่งสุดท้ายเป็น nil console เลยโชว์แค่ nil ไม่ต้องยื่นใบเบิกของ

🙋 เทียบให้เห็นภาพ — ผู้ช่วยขี้สงสัยในครัวทดลอง

ครัวทดลอง (console) มีผู้ช่วยคนหนึ่งที่อยากให้คุณเห็นผลทุกอย่างที่เขียน · คุณเพิ่งเขียนใบเบิกของบรรทัดแรก เขาก็วิ่งไปตู้ หยิบแฟ้มมาโชว์ 11 แผ่นทันที · เขียนต่ออีกบรรทัด ก็วิ่งไปอีกรอบ
; nil = บอกผู้ช่วยว่า "ไม่ต้องโชว์ ฉันยังเขียนไม่เสร็จ"

ที่ไม่เหมือนกัน: ผู้ช่วยจริงถ้าไปตู้มาแล้วก็คงวางแฟ้มไว้ให้เราใช้ต่อ · แต่ผู้ช่วยใน console ถ่ายสำเนาใบของเราไปเบิกเอง แล้วทิ้งแฟ้มที่ได้หลังโชว์เสร็จ — ใบตัวจริง (q) ในมือเรายังนับว่า "ไม่เคยยื่น" · พอเราเอาไปใช้จริง Rails ก็ต้องไปตู้อีกรอบอยู่ดี

เทียบกับ Go: Go ไม่มีครัวทดลองแบบนี้ (ต้อง go run ทั้งไฟล์) จึงไม่มีใครมาแอบโชว์ผลให้ · กับดักนี้เป็นของ console ของ Rails ล้วน ๆ

ใบเบิกของยังอยู่ในมือ ถามมันได้ว่าเป็นอะไร และเขียนว่าอะไรไว้บ้าง (ผลจริง ต่อจากเมื่อกี้):

wongnok-blog(dev):005> q.class
=> Post::ActiveRecord_Relation
wongnok-blog(dev):006> q.to_sql
=> "SELECT \"posts\".* FROM \"posts\" WHERE \"posts\".\"published\" = TRUE AND (views > 100) ORDER BY \"posts\".\"created_at\" DESC LIMIT 10"
  • q.class — ชนิดของ q คือ Post::ActiveRecord_Relation = ใบเบิกของของลิ้นชัก posts ไม่ใช่ Array ของบทความ
  • q.to_sql — "อ่านใบเบิกของให้ฟังหน่อย" ได้ SQL ที่จะยิง โดยยังไม่ยิง · \" คือเครื่องหมายคำพูดที่อยู่ใน string (console โชว์แบบนี้ ของจริงคือ ")
  • แปล SQL: "ขอทุกช่องจากลิ้นชัก posts · เฉพาะแผ่นที่ published เป็นจริง และยอดวิวเกิน 100 · เรียงจากสร้างล่าสุดก่อน · ไม่เกิน 10 แผ่น" · สี่บรรทัด Ruby → SQL ประโยคเดียว · created_at = ช่องเวลาที่สร้างแฟ้ม (มาจาก t.timestamps บท 106)

to_sql = ดู SQL ที่ relation จะยิง โดยไม่ยิง · loaded? = relation นี้ไปเอาข้อมูลมาแล้วหรือยัง · ถาม senior ได้ว่า “ก่อนส่ง relation นี้ไป view ผมเช็ค to_sql แล้ว SQL หน้าตาแบบนี้ ถูกไหม”

ยื่นใบเมื่อไหร่ — คำสั่งไหนไปตู้จริง

ตารางนี้สรุปจากผลรันจริงใน console ทุกบรรทัด (เริ่มจาก Post.where(published: true) ที่ยังไม่ยื่น) · ไม่ต้องจำทั้งหมด จำแค่หลัก: อะไรที่ต้องรู้ "ของจริง" = ไปตู้

พิมพ์ไปตู้ไหมSQL ที่เห็นจริง (ภาษาคน)
.where · .order · .limit❌ ไม่ไปแค่เขียนเพิ่มลงใบ
.class · .to_sql❌ ไม่ไปถามเรื่องตัวใบ ไม่ได้ถามเรื่องแฟ้ม
.each { … } · .to_a✅ ไปSELECT "posts".* … = หยิบทุกแผ่นที่ตรงมาวางบนโต๊ะ · to_a แปลงเป็น Array ธรรมดา
.first✅ ไป (ถ้ายังไม่โหลด)… ORDER BY "posts"."id" ASC LIMIT 1 = เรียงตามเลขที่แล้วหยิบแผ่นแรกแผ่นเดียว · ถ้าโหลดแล้วไม่ไปซ้ำ
.count✅ ไป ทุกครั้งSELECT COUNT(*) … = ให้ตู้นับ · เรียกสองครั้งก็ไปสองครั้ง
.any? · .empty? · .exists?✅ ไปSELECT 1 AS one … LIMIT 1 = "มีสักแผ่นไหม" เจอแผ่นแรกก็หยุด

ใน controller เขียนบรรทัดเดียว @posts = Post.where(published: true).order(:views) · ตอนบรรทัดนี้ทำงานเสร็จ Rails ยิง SQL ไปแล้วกี่ครั้ง?

ตัวเลือกที่ 1 ถูก — where กับ order แค่เขียนเพิ่มลงใบเบิกของ · SQL จะโผล่ตอนที่ view เอา @posts ไปวน each

ตัวเลือกที่ 2 ผิดครึ่งเดียว — ถูกที่ "รวมเป็นประโยคเดียว" แต่ประโยคนั้นยังไม่ถูกส่งตอนนี้ · ตัวเลือกที่ 3 ผิด เพราะ Rails ไม่เคยยิงแยกทีละ method · ตัวเลือกที่ 4 ผิด เพราะจำนวนแถวไม่เกี่ยวกับว่าจะยิงหรือไม่ยิง

จุดที่ต้องจำ: where · order · limit = เขียนใบ · each · count · first = ยื่นใบ

size = คนฉลาด: ดูก่อนว่าบนโต๊ะมีแฟ้มกองอยู่ไหม · มี → นับบนโต๊ะ · ไม่มี → โทรถาม

count vs size vs length

อยากรู้แค่ว่า "สมชายมีบทความบ้างไหม" (ไม่ต้องรู้ว่ากี่ชิ้น) · แบบไหนให้ตู้ทำงานน้อยที่สุด?

ตัวเลือกที่ 3 ถูก — SQL จริงคือ SELECT 1 AS one … LIMIT 1 เจอแผ่นแรกก็ตอบ ไม่ต้องหยิบแฟ้ม ไม่ต้องนับต่อ

ตัวเลือกที่ 1 กับ 4 ผิด เพราะหยิบทุกแผ่นของสมชายมาวางบนโต๊ะก่อน (SELECT "posts".*) แค่เพื่อตอบว่ามีหรือไม่ · ตัวเลือกที่ 2 ไม่ได้หยิบแฟ้ม (เป็น COUNT(*)) แต่ตู้ต้องนับให้ครบทุกแผ่นก่อน — ดีกว่า 1 และ 4 แต่ยังทำงานเกินจำเป็น

จุดที่ต้องจำ: ถามว่า "มีไหม" ใช้ exists? · ถาม "กี่ชิ้น" ใช้ count · อย่าขนแฟ้มมาเพื่อตอบคำถามที่ตอบเป็นตัวเลขได้

ใน console พิมพ์ q = Post.where(published: true) (ไม่มี ; nil) แล้วเห็น SQL ที่มี /* loading for pp */ LIMIT 11 · แปลว่าอะไร?

ตัวเลือกที่ 2 ถูก — console ต้องโชว์ผลหลัง => จึงไปตู้เพื่อ "pretty print" (pp) และขอแค่ 11 แผ่นกันตารางใหญ่ · ใน log ของหน้า /posts เห็นชัดว่า controller ที่มี where ไม่ได้ยิง SQL เลย

ตัวเลือกที่ 1 ผิด — ต่อท้าย ; nil แล้ว SQL หายไปเลย พิสูจน์ว่าไม่ใช่ where ที่ยิง · ตัวเลือกที่ 3 ผิด เพราะตารางเรามี 6 แถว แต่ยังได้ LIMIT 11 · ตัวเลือกที่ 4 ผิด เพราะในแอปจริงไม่มี LIMIT 11 โผล่ใน log

จุดที่ต้องจำ: ทดลองเรื่อง "ยิงตอนไหน" ใน console ต้องต่อ ; nil ไม่งั้นจะเห็นภาพผิด

สรุป 3 บรรทัด

  • where · order · limit = เขียนใบเบิกของ · each · count · first · exists? · pluck · sum = ยื่นใบ
  • อยากรู้ว่าหน้าไหนไปตู้กี่รอบ อย่าเดาจากโค้ด — เปิด log ดูบรรทัด (N queries) และ ↳ ที่ชี้ต้นเหตุ (นี่คือทักษะที่บท 114 ใช้หา N+1)
  • ให้ตู้ทำงานแทน: นับด้วย count · ถามว่ามีไหมด้วย exists? · ขอบางช่องด้วย pluck · อย่าขนแฟ้มทั้งลิ้นชักมาทำใน Ruby
