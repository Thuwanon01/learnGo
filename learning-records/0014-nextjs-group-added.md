## การตัดสินใจที่ต่างจากรอบก่อน

### เตรียม sandbox ที่รันได้จริงไว้ให้ agent ก่อนยิง workflow

รอบ TypeScript แค่ `tsc` ก็พอ แต่ Next.js ต้องมีโปรเจกต์จริงถึงจะ build ได้
จึง `npx create-next-app@latest` ไว้หนึ่งชุดก่อน แล้วบอก agent ให้ใช้ตัวนั้น
— **ไม่ใช่ให้แต่ละตัวสร้างเอง** ซึ่งจะเสียเวลาโหลด `node_modules` สิบรอบ

เวอร์ชันจริงที่ทุกบทตรวจด้วย: **next 16.3.4 · react 19.2.8 · tailwindcss 4 ·
typescript 5 · node v24.14.0**

### ไม่ใช้กล่อง `.demo` ในกลุ่มนี้

`assets/demo.js` ตั้ง `sandbox="allow-same-origin"` ไว้ (ไม่ให้ `allow-scripts`)
React จึงรันในกล่องไม่ได้เลย · กลุ่มนี้ใช้กล่อง `<pre>` โชว์ output จริงจาก terminal แทน
**ถ้าวันหลังอยากได้ demo ที่รัน React จริง ต้องเปิด `allow-scripts` ซึ่งเป็นคนละเรื่องด้านความปลอดภัย
— อย่าเปิดโดยไม่คิด**

## บทเรียนเรื่องการคุม agent (สำคัญกว่าตัวเนื้อหา)

### 1 · ไฟล์ brief ใน scratchpad หายกลางรอบ

สั่ง agent 20 ตัวว่า "อ่าน `scratchpad/BRIEF.md` ก่อน" แล้ว**ไฟล์นั้นหายไปกลางทาง**
พร้อมกับ `verify.py` และ `mksweep.py` ที่เขียนไว้รอบก่อน

ผลที่วัดได้ตอนตรวจ: บทที่เขียนทีหลังขาดเกณฑ์**อย่างเป็นระบบ ไม่ใช่สุ่ม** —
บท 74 ได้ quiz 3 ข้อ (เกณฑ์ 4) และ `.jargon` น้อยกว่า `.analogy` ·
บท 76 ไม่มีกล่องภารกิจเลย

**กฎใหม่:** เกณฑ์ที่ห้ามพลาด ให้**ฝังลงใน prompt ของ workflow ตรง ๆ**
ไม่ใช่แค่ชี้ไปที่ไฟล์ภายนอก — สคริปต์ workflow ถูกเซฟไว้ในโปรเจกต์จึงไม่หาย
ส่วนไฟล์ใน scratchpad หายได้

### 2 · sandbox ที่ใช้ร่วมกัน ทำให้ build ของคนอื่นพังตาม

`next build` build ทั้งโปรเจกต์ ไม่ได้ build เฉพาะโฟลเดอร์ที่เราแตะ
ตอนผมทดสอบเรื่อง `'use client'` เอง ได้ error จากไฟล์ที่ agent บท 78
กำลังเขียนค้างอยู่ ทั้งที่ไม่เกี่ยวกับโค้ดผมเลย

ข้อความ error บอก path ชัด (`./components/t78/CustomerList.tsx`) จึงยังแยกออกว่าของใคร
แต่**เสี่ยงที่ agent จะไปแก้ของที่ไม่ได้พัง**

**ครั้งหน้า:** ก็อป sandbox ให้ agent คนละชุด แล้ว symlink `node_modules`
หรือให้ตรวจแบบ scope แคบแทน `next build` ทั้งโปรเจกต์

### 3 · agent สั่ง `pkill` กว้างเกินไป แล้วไปปิด dev server ของผู้ใช้

agent ที่ตรวจบท 76 เก็บกวาดด้วย **`pkill -f "next-server"`** ซึ่งจับทุก process
ที่มีคำนั้นในเครื่อง — ไม่ใช่แค่ของตัวเอง · ผลคือ dev server ของ agent ตัวอื่น
**และ `next dev` ของโปรเจกต์ `wongnok-web` ของผู้ใช้เองที่รันมา 2 ชั่วโมง 49 นาที ถูกปิดไปด้วย**

ตัว agent **รายงานเรื่องนี้กลับมาเองตามตรง** ในช่อง `remaining` และตัว workflow
ก็ตีธงความปลอดภัยขึ้นมาให้ (`Blocked by classifier`) — ระบบเตือนทำงานถูกต้อง

**สิ่งที่ต้องเขียนใน brief ครั้งหน้า:**
- ปิด process ให้ปิด**ด้วย PID ที่ตัวเองจดไว้ตอนเปิด** เท่านั้น
- ถ้าจำเป็นต้องใช้ pattern ให้ผูกกับ **path ของ sandbox ตัวเอง** เช่น
  `pkill -f "$SANDBOX/.*next dev"` **ห้ามใช้ชื่อโปรแกรมลอย ๆ**
- **ห้ามฆ่า process ที่ไม่ได้อยู่ใต้โฟลเดอร์ของตัวเองเด็ดขาด** เครื่องนี้มีงานของผู้ใช้รันอยู่จริง

### 4 · agent แก้ปัญหา sandbox ที่ใช้ร่วมกันได้เอง

พอเจอว่า `next build` ของตัวเองพังเพราะไฟล์ของ agent อื่น มีสองตัวที่**ก็อป sandbox
เป็นของตัวเอง** (`cp -Rl` / `cp -Rc` แล้ว hardlink `node_modules`) แล้วรันในนั้นแทน
— เป็นทางแก้ที่ถูกกว่าที่ผมออกแบบไว้ตั้งแต่แรก · **ครั้งหน้าให้ทำแบบนี้ตั้งแต่ต้น**

⚠️ อีกเรื่องที่เจอ: ลบโฟลเดอร์ route ของตัวเองทิ้งแล้ว `.next/dev/types/validator.ts`
ยังอ้างถึงมันอยู่ ทำให้ `tsc --noEmit` ของ **agent คนอื่น** พังตาม —
ต้อง `rm -rf .next && next build` ใหม่ถึงหาย
