## จุดที่สไลด์ผิด — และมันเป็นข้อที่ผมเคยตอบไม่ได้เมื่อวาน

แบบฝึกหัดหน้า 75–76 ข้อ 6 เฉลยว่า *"ให้ swag สแกนโค้ดใน `internal/` ด้วย"* → `--parseInternal`

ตอนทำ Day 8 ผมเจอเรื่องนี้แล้วแต่**ฟันธงไม่ได้** เลยเขียนไว้ในบันทึก 0002 ว่า "ยังไม่สรุปว่าผิด"
เหตุผลที่ฟันธงไม่ได้ตอนนั้นคือ — **ผมทดสอบด้วยการใส่สอง flag พร้อมกัน**

รอบนี้เปลี่ยนวิธี: **เปลี่ยนทีละ flag** แล้ววัดด้วย `md5`

```
27d4b4c32eba7c375b7cd69a3808fce9    # ไม่ใส่ flag
27d4b4c32eba7c375b7cd69a3808fce9    # --parseInternal            ← เท่ากับข้างบน
e7c184f840b49b6bde994728d8cb1a2e    # --parseDependency
e7c184f840b49b6bde994728d8cb1a2e    # --parseDependency --parseInternal ← เท่ากับข้างบน
```

`--parseInternal` **ไม่เคยเปลี่ยนผลลัพธ์เลยสักชุด** ตัวที่เปลี่ยนชื่อ definition เป็น
`internal_user.*` คือ `--parseDependency` ต่างหาก

ยืนยันซ้ำจากซอร์ส `swaggo/swag` v1.16.6 — `ParseInternal` ถูกอ่านแค่ 2 จุด และทั้งคู่อยู่ใน
`getAllGoFileInfoFromDeps*` คือ**เส้นทางอ่าน dependency**:

```go
golist.go:51    ignoreInternal := pkg.Goroot   && !parser.ParseInternal
parser.go:1868  ignoreInternal := pkg.Internal && !parser.ParseInternal
```

ส่วน `walkWith` (`parser.go:1957`) ที่เดินไฟล์ของโปรเจกต์เรา ข้ามแค่ `vendor`, `docs`,
โฟลเดอร์ที่ขึ้นต้นด้วยจุด และ `--exclude` — **ไม่มีเงื่อนไขคำว่า `internal` อยู่เลย**

ต้นเหตุที่ทุกคนเข้าใจตรงกันผิดคือข้อความช่วยเหลือของ swag เอง:
`Parse go files in internal packages` ซึ่งไม่ได้บอกว่าหมายถึง internal **ของ dependency**

## จุดที่ผมเขียนผิดเอง (อีกครั้ง) — คนละแบบกับคราวที่แล้ว

บันทึก 0009 เล่าว่า brief ที่ผมเขียนให้ agent ผิด แล้ว agent แก้ให้
คราวนี้หนักกว่านั้น — **ของที่ผิดมันขึ้นเว็บไปแล้ว**

บทเรียน 41 เขียนไว้ว่า *"สิ่งที่ `--parseInternal` ทำจริงในเคสนี้คือทำให้ชื่อ definition ยาวขึ้น"*
ซึ่ง**ผิด** เพราะตอนนั้นผมใส่ `--parseDependency --parseInternal` พร้อมกัน เห็นชื่อเปลี่ยน
แล้ว**ยกความดีความชอบให้ flag ผิดตัว**

นี่คือความผิดพลาดแบบคลาสสิก — เปลี่ยนสองตัวแปรพร้อมกันแล้วสรุปว่าตัวไหนเป็นเหตุ
ตลกร้ายคือมันเป็นเรื่องเดียวกับที่คอร์สนี้สอนเรื่อง controlled experiment มาตลอด

แก้แล้วทั้ง 3 ที่: บทเรียน 41 (เขียนหัวข้อใหม่ทั้งก้อน + ใส่กล่องยอมรับว่าเคยเขียนผิด),
cheat sheet Day 8 (แถวในตาราง flag) และภารกิจท้ายบท 41 ที่เคยสั่งให้ผู้เรียน
`diff` ระหว่าง "ไม่ใส่ flag" กับ "ใส่ทั้งสอง flag" — ซึ่งเป็นวิธีที่**ทำให้สรุปผิดแบบเดียวกับผม**
เปลี่ยนเป็นให้รัน 4 แบบแล้วเทียบ `md5`

## brief ของผมผิดอีกจุด แล้ว agent จับได้

ผมเขียนใน brief ว่าให้พิสูจน์ idempotency ด้วยการ *"ยิงซ้ำ 3 ครั้งแล้วดู status code ที่ต่างกัน"*

agent รันจริงแล้วรายงานกลับว่า **มันไม่ต่างกันเลย**

```
##### GOOD: DELETE /users/123  x3 #####     ##### BAD: POST /deleteUser?id=123  x3 #####
call 1 -> HTTP 200                          call 1 -> HTTP 200
call 2 -> HTTP 404                          call 2 -> HTTP 404
call 3 -> HTTP 404                          call 3 -> HTTP 404
```

ถูกของ agent — **idempotency ไม่ใช่พฤติกรรมที่ server สะท้อนออกมาเป็นตัวเลข**
แต่เป็นสัญญาที่ผูกกับตัว method ตาม HTTP spec ซึ่ง client · proxy · ชั้น retry
เอาไปใช้ตัดสินใจว่า "ยิงซ้ำได้ไหม" · บทเรียน 43 จึงเอาความเข้าใจผิดอันนี้
ไปทำเป็น predict-the-output ตรง ๆ แทนที่จะเงียบไว้

ประโยคที่กันไว้ใน brief ทุกครั้ง — *"ถ้าผลจริงต่างจากที่ brief บอก ให้รายงานตามจริง
อย่าดัดให้ตรง brief"* — คือสิ่งเดียวที่ทำให้เรื่องนี้ไม่หลุดขึ้นเว็บ **สองครั้งติดแล้ว**

## ของที่ agent เขียนแล้วผมต้องแก้เอง

agent เขียนบท 43 โดย copy ผลของคำสั่ง `diff` มาว่า:

```
$ diff run1_noflag.json run2_withflag.json
[ok] Files are identical
```

**`diff` ตัวจริงไม่พิมพ์แบบนั้น** — เวลาไฟล์เหมือนกัน `diff` ไม่พิมพ์อะไรเลย
บรรทัด `[ok] Files are identical` มาจาก wrapper ที่ครอบ shell อยู่บนเครื่องนี้

ถ้าปล่อยไป ผู้เรียนที่รันตามจะไม่เห็นข้อความนี้ แล้วนึกว่าตัวเองทำผิด ·
เปลี่ยนไปใช้ `md5` แทนทั้งหมด เพราะ**มันพิมพ์ค่าออกมาให้เห็น**
ต่างจาก `diff` ที่ "เงียบ" ซึ่งหน้าตาแยกไม่ออกจาก "คำสั่งไม่ได้รัน"

บทเรียนสำหรับครั้งหน้า: **ผลรันที่ agent ส่งกลับมา อาจเป็นของจริงแต่เป็นของจริง
"บนเครื่องที่มี wrapper"** ซึ่งไม่เหมือนเครื่องผู้เรียน

## เรื่อง font ทับกัน — bug เดียว กระทบ 33 ไฟล์

ผู้ใช้ส่งภาพหน้าจอมาว่าโค้ดทับข้อความจนอ่านไม่ออก ต้นเหตุอยู่ที่ CSS บรรทัดเดียว:

```css
.compare .side > pre { margin-bottom: 0; height: 100%; }
```

`.side` เป็น grid item ที่ถูกยืดให้สูงเท่าคอลัมน์ข้าง ๆ `height: 100%` ของ `<pre>`
จึงคิดจากความสูงของ `.side` **ทั้งก้อน — รวม `<h4>` ที่อยู่ข้างบนด้วย**
`<pre>` เลยสูงเกินที่ว่างจริงไปเท่ากับความสูงของ `<h4>` แล้วล้นทับข้อความข้างล่าง

แก้ด้วยการเปลี่ยนไปใช้ flex ซึ่งคิดจาก**ที่ว่างที่เหลือ** ไม่ใช่ความสูงทั้งก้อน:

```css
.compare .side { min-width: 0; display: flex; flex-direction: column; }
.compare .side > pre { margin-bottom: 0; flex: 1 1 auto; min-width: 0; }
```

**วิธีตรวจว่าไม่มีที่อื่นเหลืออีก** — ไม่ได้ไล่เปิดดูทีละหน้า แต่เขียนหน้า harness
ที่โหลดทั้ง 53 หน้าใส่ `<iframe>` แล้ววิ่งเช็คทุก element ว่ามันล้นออกนอกกล่องแม่ไหม

ผลลัพธ์ 3 อย่าง:

1. **ยืนยันว่า detector จับ bug นี้ได้จริง** — เอา CSS เก่ากลับมาใส่ทับ แล้ว detector
   รายงานว่าทุก `<pre>` ล้น **39px** พอดี (= ความสูง `<h4>` + margin) ·
   ถ้าไม่ทดสอบขั้นนี้ "ไม่เจอปัญหา" อาจแปลว่า detector เสียก็ได้
2. **จุดที่รายงานมา 6 จุดเป็น false positive ทั้งหมด** — เป็น `<td rowspan>`
   ซึ่งกินพื้นที่เกิน `<tr>` ของมันโดยธรรมชาติ (นับ `td[rowspan]` ได้ 2 กับ 4 ตรงกันเป๊ะ)
3. **เจอ bug ที่สองที่ไม่มีใครรายงาน** — พอลองที่ความกว้าง 380px
   พบว่า `<code>` ชื่อยาว ๆ อย่าง `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE` ตัดบรรทัดไม่ได้
   มันดันขอบขวาจน**ทั้งหน้าเลื่อนแนวนอนได้** สูงสุด 216px ใน 13 หน้า
   แก้ด้วย `overflow-wrap: anywhere` ที่ `code` และกันไม่ให้กระทบบล็อกโค้ดด้วย
   `pre code { overflow-wrap: normal; }` (ในบล็อกโค้ดต้องเลื่อนแนวนอนเหมือนเดิม)

ตรวจซ้ำครบ 3 ความกว้าง (380 · 768 · 1100px) × 53 หน้า — เหลือ 0 จุด
