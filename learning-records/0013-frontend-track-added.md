## การตัดสินใจที่สำคัญ และเหตุผล

### 1 · ฝั่ง Frontend ไม่แบ่งตามวัน เพราะสไลด์ไม่ได้กำกับวันมา

สไลด์ฝั่ง Backend ทุกไฟล์มีคำว่า `Day N` อยู่ในชื่อ ส่วนสองไฟล์นี้ไม่มีเลย
**ทางเลือกที่ไม่เลือก:** ตั้งวันเองว่าเป็น Day 10, Day 11
เพราะถ้าอาจารย์ส่งสไลด์ Go วันที่ 10 มาจริงทีหลัง เลขจะชนกันทันที
และการ "ตั้งวันเอง" คือการเติมข้อมูลที่ไม่มีในต้นฉบับ

**ที่เลือก:** ตั้งชื่อกลุ่มตามชื่อไฟล์สไลด์ตรง ๆ (`fe-html-css`, `fe-ts-fp`)
ผู้เรียนจะหาได้จากชื่อที่เห็นในสไลด์จริง

### 2 · เลขบทเรียนต่อเนื่องทั้งเว็บ ไม่รีเซ็ตตามฝั่ง

ฝั่ง FRONT เริ่มที่ **0056** ไม่ใช่ 0001
เหตุผลไม่ใช่ความสวยงาม แต่เป็นเรื่องข้อมูลพัง: `assets/quiz.js` อ่าน
**เลขสี่หลักจากชื่อไฟล์** ไปใช้เป็นคีย์ของ `localStorage`
ถ้าฝั่ง FRONT เริ่มนับ 0001 ใหม่ คนที่ติ๊ก "เรียนจบ" บทที่ 1 ของ Go ไว้
จะพบว่าบทที่ 1 ของ HTML ถูกติ๊กไปด้วยโดยไม่ได้ทำ

### 3 · สไลด์ที่เป็นภาพ ต้องแปลงเป็นรูปก่อน ห้ามเดาจากหัวข้อ

`pdftotext -layout` ได้ข้อความจาก 74 หน้าแค่ **15 KB** —
เพราะแต่ละหน้ามีแค่หัวข้อ + bullet อังกฤษหนึ่งบรรทัด + คำแปลไทยหนึ่งบรรทัด
ส่วน **โค้ดตัวอย่างทั้งหมดอยู่ในรูป**

→ ต้อง `pdftoppm -jpeg -r 100` แล้วให้คนเขียนบทเปิดรูปอ่านทีละหน้า

**เกณฑ์ที่ใช้ตัดสินครั้งต่อไป:** ข้อความที่แกะได้ **น้อยกว่า ~500 ไบต์ต่อหน้า**
= สไลด์ชุดนั้นเป็นภาพ ต้องแปลงเป็นรูป

### 4 · บท CSS ที่ไม่มีผลลัพธ์ให้ดู คือบทที่พิสูจน์อะไรไม่ได้เลย

กฎของ workspace นี้คือ "ทุกอย่างที่โชว์เป็นผลรัน ต้องรันจริง"
กับ Go แปลว่า `go run` แล้วก็อป output มา — แต่กับ CSS **ผลลัพธ์คือภาพ**
ถ้าเขียนว่า "จะเห็นกล่องเรียงกันแนวนอน" เฉย ๆ ก็เท่ากับแต่งผลลัพธ์ขึ้นมาเอง

จึงทำ component ใหม่: `assets/demo.js` เอาโค้ดชุดเดียวกับที่โชว์ไปเรนเดอร์จริง

**ทำไมต้องเป็น `<iframe>`:** `lesson.css` ตั้งสไตล์ให้ `p` `a` `ul` `button` `input`
ไว้หมดแล้ว ถ้าเรนเดอร์ตัวอย่างในหน้าตรง ๆ มันจะโดนสไตล์ของหน้าทับ
แล้วผู้เรียนจะเห็นผลของ CSS ที่ผสมกันสองชุด — **สอนผิดโดยที่ไม่มีใครรู้**
iframe คือขอบเขตที่ CSS ข้ามไม่ได้จริง ๆ

**ทำไมต้องอยู่ใน `<template>`:** ถ้าวางเนื้อในไว้ตรง ๆ CSS ในกล่องจะรั่วออกมา
ทั้งหน้าทันทีที่ JS ปิด

## กับดักที่เจอตอนทำ (เสียเวลาจริง)

### วัดความสูงของ iframe ตอนที่แม่ยังซ่อนอยู่ ได้ค่ามหาศาล

`.demo:not(.is-live)` เป็น `display:none` (ไว้กันไม่ให้เห็นกล่องเปล่าเมื่อ JS ปิด)
รอบแรกเขียนลำดับเป็น `appendChild` → `classList.add('is-live')`
iframe จึงถูกใส่ตอนแม่ยัง `display:none` → **กว้าง 0px** → ข้อความหนึ่งบรรทัด
ตัดเป็นหลายสิบบรรทัด → วัดความสูงได้ **442px จากข้อความบรรทัดเดียว**

→ ติดคลาส `is-live` **ก่อน** `appendChild` เสมอ

### วัดความสูงจาก `<html>` ทำให้กล่องไม่มีวันหดลง

รอบแรกใช้ `documentElement.getBoundingClientRect().height` ซึ่ง**เท่ากับความสูง
ของ iframe เองเสมอ** (html ยืดเต็ม viewport) → ตั้งค่าใหม่เท่าค่าเดิมทุกครั้ง
→ ต้องวัดจาก `body.scrollHeight`

### `id` ซ้ำข้าม `<template>` ไม่ใช่บั๊ก แต่ตัวตรวจร้อง

บท 58 มีฟอร์มตัวอย่างสองอัน ทั้งคู่ใช้ `id="email"` — ดูเหมือน id ซ้ำ
แต่แต่ละ `<template>` ไปอยู่คนละ iframe = **คนละ document** จึงไม่ชนกันจริง
→ ตัวตรวจต้องนับ id **แยกต่อ template** ไม่งั้นจะร้องผิดทุกบทที่มีฟอร์มสองตัวอย่าง

### พิสูจน์ว่าการ์ดกัน 0px ได้ผลจริง ด้วยการปิดมันออก

auditor ของบท 58 รายงานว่าเปิดหน้าในแท็บที่ pane กว้าง 0 แล้วกล่อง `data-h="180"`
ยืดเป็น **578px** ผมไม่เชื่อทันที เลยทำหน้าทดสอบที่มีกล่อง `.demo` อยู่ในตัวครอบ
`width: 0` แล้ววัดสามรอบ:

| สภาพ | ความสูงที่ได้ |
|---|---|
| ปิดการ์ด (`if (!frame.clientWidth) return`) ออก | **512px** |
| ใส่การ์ดกลับ · ยังกว้าง 0 | 120px (= ค่า `data-h` ที่ตั้งไว้ ไม่ระเบิด) |
| ใส่การ์ดกลับ · แล้วขยายตัวครอบเป็น 100% | **52px** (`ResizeObserver` วัดใหม่ให้) |

**ข้อความเดียวกันทั้งสามรอบ** ต่างกันแค่ว่าตอนวัดมีความกว้างจริงหรือยัง

### เส้นแบ่ง responsive ต้องวัด ไม่ใช่เดา

แถบนำทางมีตัวสลับฝั่งเพิ่มมา ทำให้ของบนแถวบนเยอะขึ้น
วัดจริงที่จอ 1280px: 🏠 32 + ตัวสลับฝั่ง 116 + ปุ่ม Day 1–9 **485** +
ช่องค้นหา 192 + ปุ่มบันทึก 69 = **894px**
จอ 1000px มีที่ให้ 920px → **ชนพอดีเกินไปจนเชื่อไม่ได้**

→ ขยับเส้นแบ่ง "ยุบเป็นปุ่ม ☰" จาก 768px เป็น **1100px**
และต้องขยับ `MQ_NARROW` ของช่องค้นหาตามให้ตรงกัน ไม่งั้น 🔍 กับ ☰ จะโผล่คนละจังหวะ

**หมายเหตุ:** ตัวเลข 485px นี้ต่างจากที่เคยประเมินไว้ (696px) ในรอบทำ navbar
เพราะรอบนั้นวัดที่จอ 768px ซึ่งฟอนต์ถูกย่อคนละขนาด — **ตัวเลขที่วัดคนละเงื่อนไข
เอามาใช้ต่อไม่ได้**

### สร้าง DOM ของทั้งสองฝั่งไว้พร้อมกัน ดีกว่ารื้อสร้างใหม่ตอนกดสลับ

`makeToggle()` เก็บคู่ `{btn, panel}` ไว้ในอาเรย์ `toggles` เพื่อบังคับ "เปิดได้ทีละเมนู"
ถ้ากดสลับฝั่งแล้วรื้อ DOM ทิ้งสร้างใหม่ อาเรย์นั้นจะเหลือ node ที่หลุดจากหน้าไปแล้ว
→ สร้างทั้งสองฝั่งไว้ แล้วซ่อนอันที่ไม่ได้ใช้ด้วย `hidden`
ค่าใช้จ่ายคือปุ่มไม่กี่สิบปุ่ม ซึ่งถูกกว่าบั๊กแบบนั้นมาก

⚠️ `.sn-daysgrp` ใช้ `display:contents` เพื่อให้ปุ่มลูกยังเป็น flex item ของ `.sn-days`
เหมือนเดิม — **ต้องเขียน `[hidden]{display:none}` แยกด้วย** เพราะ `display:contents`
ทับกฎ `[hidden]` ที่เบราว์เซอร์ตั้งไว้ให้

## จุดที่สไลด์ฝั่ง Frontend ผิด หรือชวนเข้าใจผิด

รายละเอียดพร้อมผลรันจริงอยู่ใน [0002](0002-course-slides-have-errors.md)
สรุปที่เจอรอบนี้:

| สไลด์ | หน้า | เรื่อง |
|---|---|---|
| TypeScript | 28 | โค้ดสองก้อนคอมไพล์ไม่ผ่านจริง (`TS18048` · `TS2552` · `TS7006`) |
| TypeScript | 48 | พาดหัวเขียน **SPLICE** แต่โค้ดข้างล่างเรียก `slice` ซึ่งพฤติกรรมตรงข้ามกัน (อันหนึ่งแก้ของเดิม อีกอันไม่แก้) |
| TypeScript | 32 | เขียนว่า "returns a **new array**" แต่ตัวอย่างเป็น `string` และตั้งชื่อตัวแปรเป็นพหูพจน์จนดูเหมือน array |
| TypeScript | 17 | เตือนว่า assert ไป sub-type ที่ไม่ตรงจะมีปัญหา — แต่ `tsc` **เงียบสนิท** ไม่ฟ้องอะไรเลย ปัญหาโผล่ตอน runtime |

## บทเรียนเรื่องวิธีทำงาน

### brief ที่เราเขียนเองผิดได้ และ agent ที่รายงานตามจริงคือของดี

รอบนี้มีสองจุดที่ผมเขียน brief ผิดแล้ว agent ทักกลับมาแทนที่จะทำตาม:

1. brief สั่งให้บท 56 สอน "วิธีเอา CSS มาต่อกับ HTML" แต่เรื่องนั้น
   **ไม่มีในสไลด์หน้า 1–12** เลย (หน้า 13 ขึ้นหัวข้อใหม่แล้ว)
2. brief เขียนว่ากับดักของ `reduce` คือ "ใส่ค่าเริ่มต้นผิด type แล้ว error งง ๆ"
   แต่เคสที่มือใหม่เจอบ่อยที่สุด (`reduce((sum, p) => sum + p, "")`)
   **ไม่ error เลยสักตัว** — มันต่อ string เงียบ ๆ ซึ่งแย่กว่า error

→ ประโยคที่กันไว้ได้คือ **"ถ้าผลจริงต่างจากที่คำถามคาดไว้ ให้รายงานตามจริง
อย่าดัดให้ตรงคำถาม"** ต้องมีในคำสั่งของ agent ทุกครั้ง (กฎเดิมจาก Day 8 ยังใช้ได้)
