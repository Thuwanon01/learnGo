ช่องโหว่ XSS และ N+1 ที่ซ่อนอยู่ใน view

~20 นาที · ควรผ่าน บทเรียน 123 (partial) · บทเรียน 103 (XSS ขั้นต้น) และ บทเรียน 114 (N+1) มาก่อน

view คือที่ที่บั๊กสองแบบชอบซ่อนตัว: บั๊กที่ทำให้คนร้ายรันโปรแกรมในเบราว์เซอร์ของคนอื่นได้ และบั๊กที่ทำให้หน้าเว็บช้าลงทุกครั้งที่มีบทความเพิ่ม
อ่านจบบทนี้ คุณจะรู้ว่าคำไหนใน view ที่ปิดระบบกันภัยของ Rails (raw · html_safe) และค้นหามันได้ในคำสั่งเดียว · จับ N+1 ที่ซ่อนอยู่ใน partial ได้จาก log และจากคำเตือนของ bullet · แล้วแก้ที่ controller บรรทัดเดียว

🔁 ทวนก่อนเริ่ม — คำพวกนี้จะโผล่ในบทนี้

  • XSS · escape (บท 103) — คนร้ายใส่ <script> ไว้ในข้อมูล ให้ไปรันในเบราว์เซอร์คนอื่น · <%= %> กันให้เองด้วยการแปลง < เป็น &lt;
  • partial · render post (บท 123) — แม่พิมพ์ _post.html.erb ที่หน้า index ใช้ซ้ำทีละบทความ · ในแม่พิมพ์เรียกบทความว่า post (ไม่มี @)
  • N+1 · includes (บท 114) — ไปตู้ 1 รอบเอารายการ แล้วไปอีกรอบต่อทุกชิ้น · แก้ด้วยใบเบิกที่บอกล่วงหน้าว่า "หยิบของที่ผูกกันมาด้วย"
  • อ่าน log (บท 113) — … Load = ไปตู้ 1 รอบ · ↳ ไฟล์:บรรทัด = บรรทัดที่สั่ง (ไฟล์ .erb ลบหนึ่ง) · (N queries, M cached) ท้ายใบสั่ง = รวมกี่รอบ

🖥 เปิดค้างไว้: bin/dev หนึ่งหน้าต่าง (เว็บอยู่ที่ localhost:3000) · อีกหน้าต่างไว้พิมพ์คำสั่ง · ผลรันทุกกล่องมาจากเครื่องจริง · เวลา ms · วันที่ · เลข 0x… · id ของบทความ ของคุณอาจไม่ตรงกับในบท

XSS ทวน 30 วินาที — แล้วทำไมต้องลงลึกอีก

บท 103 เห็นแล้วว่าถ้าชื่อบทความเป็น <script>…</script> แล้วหน้าเว็บวางลงไปตรง ๆ เบราว์เซอร์ของทุกคนที่เปิดหน้านั้นจะรันโปรแกรมของคนร้าย · และ <%= %> กันให้แล้วโดยไม่ต้องสั่ง

ที่ต้องลงลึกเพราะ Day 3 เราจะเริ่มให้ AI เขียน view · และมีคำสั้น ๆ ไม่กี่คำที่ปิดระบบกันภัยนี้ได้ ซึ่ง AI (หรือคนที่รีบ) อาจหยิบมาใช้ตอนอยากให้ HTML "โชว์ออกมาสวย ๆ" · บทนี้จะลองของจริงทั้ง 4 แบบในสไลด์หน้า 17 แล้วดูว่าเบราว์เซอร์ได้รับอะไรจริง

แบบ ③ <%= post.title.html_safe %>

แก้บรรทัด 4 เป็น <%= post.title.html_safe %> — ผลจริง:

    <strong class="block font-medium mb-1">Title:</strong>
    <script>alert('XSS!')</script>

เหมือนแบบ ② ทุกตัวอักษร · กล่อง alert เด้งเหมือนกัน (ยืนยันด้วย Chrome แล้ว) · เพราะในโค้ดของ Rails เอง raw คือ to_s.html_safe บรรทัดเดียว — สองคำนี้คือของชิ้นเดียวกัน คนละหน้าตา

⚠️ ชื่อ html_safe หลอกตา — มันไม่ได้ทำให้ HTML ปลอดภัย · มันคือการแปะป้ายว่า "ข้อความนี้ปลอดภัยแล้ว ไม่ต้อง escape" · Rails เชื่อป้ายนั้นทันที ไม่ตรวจอะไรเลย

แบบ ④ <%= sanitize post.title %>

<%= sanitize post.title %>

sanitize แปลว่า "ฆ่าเชื้อ" · ชื่อบทความคือ <script>alert('XSS!')</script> · คิดว่าบนจอจะเห็นอะไร — ว่างเปล่า · ตัวหนังสือทั้งก้อนเหมือนแบบ ① · alert เด้ง · หรืออย่างอื่น?

ผลจริงจาก curl:

    <strong class="block font-medium mb-1">Title:</strong>
    alert('XSS!')

แท็ก <script> ถูกถอดทิ้ง แต่ตัวหนังสือข้างในยังอยู่ · บนจอจึงเห็นคำว่า alert('XSS!') เป็นตัวหนังสือเฉย ๆ · ไม่มีอะไรรัน (Chrome ยืนยันว่าตรงชื่อบทความไม่มีแท็ก script เหลือ และกล่องไม่เด้ง)

สรุปทั้ง 4 แบบ (ผลจริงทุกช่อง):

ใน viewHTML ที่ส่งออกไปบนจอscript รันไหม
<%= post.title %>&lt;script&gt;…ข้อความเต็ม ๆ✅ ไม่รัน
<%= raw post.title %><script>…ว่าง + กล่องเด้ง❌ รัน
<%= post.title.html_safe %><script>…ว่าง + กล่องเด้ง❌ รัน

✉️ เทียบให้เห็นภาพ — ซองใส กับการแกะซอง

คนจัดจาน (view) เอาทุกอย่างที่ลูกค้าเขียนมาใส่ซองใสก่อนวางบนจาน · ใครดูก็อ่านออกว่าเขียนอะไร แต่มันทำงานไม่ได้ — ใบที่เขียนว่า "จุดประทัด" ก็เป็นแค่กระดาษในซอง · raw คือสั่งคนจัดจานว่า "แกะซองออก วางของจริงลงจานเลย" · .html_safe คือแปะสติกเกอร์ "ตรวจแล้ว" บนของชิ้นนั้น — คนจัดจานเห็นสติกเกอร์ก็ไม่ใส่ซองให้ ทั้งที่ไม่มีใครตรวจจริง

ที่ไม่เหมือนกัน: คนจัดจานจริงเห็นประทัดก็คงทักว่า "เอ๊ะ แน่ใจเหรอ" · Rails ไม่ทักเลย ไม่มี error ไม่มีคำเตือนใน log — หน้าเว็บโหลดปกติ 200 OK · คนเดียวที่จะจับได้คือคนอ่านโค้ด

เทียบกับ React (บท 71): {post.title} ใน JSX ก็ escape ให้เองแบบเดียวกับ <%= %> · ถ้าอยากวาง HTML ดิบ React บังคับให้พิมพ์ชื่อยาว ๆ ว่า dangerouslySetInnerHTML — ตั้งชื่อให้ดูอันตรายโดยตั้งใจ · ฝั่ง Rails คำที่ทำหน้าที่นั้นคือ raw กับ html_safe ซึ่งชื่อไม่ได้ฟังดูอันตรายเลย เราจึงต้องจำเอง

🗣 ศัพท์ที่เพิ่งเรียนไป
stored XSS (persistent XSS)
XSS ที่โปรแกรมของคนร้ายถูกเก็บลงฐานข้อมูลแล้วไปรันในเบราว์เซอร์ของทุกคนที่เปิดหน้านั้น (แบบที่เราเพิ่งทำ) · ร้ายแรงเพราะโดนทุกคน ไม่ใช่แค่คนที่กดลิงก์แปลก ๆ · ถาม senior ได้ว่า "ช่องไหนบ้างที่ผู้ใช้พิมพ์เองแล้วเราเอาไปโชว์ให้คนอื่นดู"
raw · html_safe
สองคำที่บอก Rails ว่า "ไม่ต้อง escape ข้อความนี้" · raw x = x.to_s.html_safe · พิมพ์บอก AI ได้ว่า "do not use raw or html_safe on user input; keep ERB's default escaping"

sanitize — คัดแท็กตามรายชื่อที่อนุญาต

แล้วถ้าอยากให้ผู้ใช้ทำตัวหนา หรือใส่ลิงก์ได้ล่ะ? (เช่น คำอธิบายร้านที่มี ตัวหนา) · <%= %> จะ escape ทุกแท็ก ส่วน raw ปล่อยทุกแท็ก — sanitize คือทางกลาง: เก็บแท็กที่อยู่ในรายชื่อที่อนุญาต ถอดที่เหลือทิ้ง

ลองใน console (helper ใน console = กล่องเครื่องมือชุดเดียวกับที่ view ใช้ ยืมมาลองนอกหน้าเว็บได้) — ผลจริง: 

wongnok-blog-all-in-one(dev):001> helper.sanitize('<b>อร่อยมาก</b>')
=> "<b>อร่อยมาก</b>"
wongnok-blog-all-in-one(dev):002> helper.sanitize('<script>alert(1)</script>สวัสดี')
=> "alert(1)สวัสดี"
wongnok-blog-all-in-one(dev):003> helper.sanitize('<a href="/posts" onclick="alert(1)">ร้านอื่น</a>')
=> "<a href=\"/posts\">ร้านอื่น</a>"
  • บรรทัด 1 — <b> (ตัวหนา) อยู่ในรายชื่อ → ผ่านไปทั้งแท็ก
  • บรรทัด 2 — <script> ไม่อยู่ในรายชื่อ → ถอดแท็กทิ้ง เหลือแต่ตัวหนังสือ (แบบเดียวกับแบบ ④ เมื่อกี้)
  • บรรทัด 3 — แท็ก <a> (ลิงก์) ผ่าน และ href (ที่อยู่ลิงก์) ผ่าน · แต่ onclick="…" (คำสั่ง "กดแล้วรันโปรแกรมนี้") ถูกตัดออก · \" คือวิธีที่ console โชว์ " ที่อยู่ในข้อความ ไม่ต้องสนใจ
🌿 เทียบให้เห็นภาพ — คนจัดจานที่ถือรายการของตกแต่งที่อนุญาต

ลูกค้าส่งของตกแต่งจานมาเอง · คนจัดจานถือรายการ "ใบโหระพา · พริกซอย · ผักชี วางได้" · ของที่อยู่ในรายการวางลงจาน · ของนอกรายการ (ประทัด · ไม้ขีด) ดึงออกทิ้ง · กระดาษโน้ตที่ติดมากับประทัดยังวางไว้ให้อ่านได้ — แบบที่ alert(1) ยังเหลือเป็นตัวหนังสือ

ที่ไม่เหมือนกัน: คนจัดจานจริง "ดูออก" ว่าอะไรอันตราย · sanitize ดูไม่ออก มันแค่เทียบกับรายการ · ถ้าเราไปเพิ่ม script ลงรายการเอง (sanitize(x, tags: %w[script])) มันก็ปล่อย <script>alert(1)</script> ผ่านทั้งก้อน (ผมลองแล้ว) · เอกสารของ Rails เตือนตรง ๆ ว่าให้ใช้รายการเริ่มต้นเท่าที่ทำได้

สไลด์หน้า 17 บอกว่า sanitize "ใช้กับ rich text (บ่าย)" — rich text คือช่องที่ผู้ใช้จัดตัวหนา ใส่ลิงก์ได้ เป็นเรื่องของ Day 3 ช่วงบ่าย (ยังไม่มาในชุดนี้) · วันนี้จำแค่ว่า: ไม่ต้องการ HTML จากผู้ใช้ = ใช้ <%= %> ธรรมดา · ต้องการจริง ๆ = sanitize · ไม่มีกรณีไหนที่ควร raw ข้อมูลจากผู้ใช้

🗣 ศัพท์ที่เพิ่งเรียนไป
sanitize · sanitizer
ล้างข้อความ HTML ให้เหลือเฉพาะแท็กและ attribute ที่อนุญาต · ใน Rails คือ helper sanitize · พิมพ์บอก AI ได้ว่า "if HTML from users is needed, use sanitize with the default allowlist, never raw"
allowlist (safe list)
รายชื่อของที่อนุญาต — ไม่อยู่ในรายชื่อ = ไม่ผ่าน (ตรงข้ามกับ denylist ที่ห้ามเฉพาะของที่รู้จัก) · ถาม senior ได้ว่า "โปรเจกต์เราแก้ allowlist ของ sanitize ไว้ไหม เพิ่มอะไรเข้าไปบ้าง"

กฎหนึ่งบรรทัด + หาคำอันตรายด้วยคำสั่งเดียว

ค่าเริ่มต้นของ Rails ปลอดภัย — อันตรายเกิดเมื่อเราตั้งใจพิมพ์ raw หรือ html_safe เอง (สไลด์หน้า 17) · แปลว่าเวลาตรวจโค้ด (ของเพื่อนหรือของ AI) ไม่ต้องไล่อ่านทุกบรรทัด — ค้นหาสองคำนี้ก่อน

ตอนนี้บรรทัด 4 ของ _post.html.erb ยังเป็น sanitize อยู่ · เปลี่ยนกลับเป็น <%= raw post.title %> สักครู่ แล้วค้นด้วย grep — ผลจริง:

แก้ที่ controller ไม่ใช่ที่ view

ทำตามที่ bullet บอก — แก้ app/controllers/posts_controller.rb บรรทัดเดียว (ของเดิมจาก scaffold คือ @posts = Post.all) · แม่พิมพ์ไม่ต้องแตะเลย:

# app/controllers/posts_controller.rb — action index
  def index
    @posts = Post.includes(:category)
  end

ให้ AI ช่วย — แต่ตรวจด้วยของสองอย่างที่เพิ่งเรียน

สไลด์ Day 3 จะให้เราสั่ง AI เขียน view บ่อย ๆ (Lab บท 126) · AI เขียน post.category.name ในแม่พิมพ์โดยไม่ไปเติม includes ที่ controller ได้ง่ายมาก เพราะมันไม่เห็น log ของคุณ · ใส่ข้อห้ามไว้ใน prompt ตั้งแต่แรก (โครง 4 ส่วนจาก บท 121) เช่นท่อน "ห้าม" กับ "เกณฑ์ตรวจรับ": 

ห้าม:
- ใช้ raw หรือ html_safe กับข้อมูลที่ผู้ใช้พิมพ์
- เรียก association ใน partial โดยไม่ includes ที่ controller
เกณฑ์ตรวจรับ:
- grep -rnw "raw\|html_safe" app ไม่เจออะไร
- หน้า /posts ไม่มี Bullet Warnings และ log ขึ้นไม่เกิน 3 queries

แล้วตรวจเองทุกครั้ง อย่าเชื่อคำว่า "เสร็จแล้ว" ของ AI:

  1. รัน grep -rnw "raw\|html_safe" app · เจอ → ถาม "ข้อมูลตรงนี้มาจากไหน"
  2. เปิดทุกหน้าที่ AI แก้ · ดูมุมซ้ายล่างว่ามี Bullet Warnings ไหม · ดู (N queries) ใน log
  3. เจอปัญหา → แปะ log หรือคำเตือนของ bullet ให้ AI ดูตรง ๆ ได้ผลกว่าสั่งลอย ๆ ว่า "ทำให้เร็วขึ้น"

ทดสอบความเข้าใจ

บรรทัดไหนเปิดช่อง XSS ถ้า post.title มาจากที่ผู้ใช้พิมพ์? (ดัดแปลงจาก Quiz A ข้อ 1 สไลด์หน้า 19)

ตัวเลือกที่ 3 ถูก — ผลจริงจาก curl: ทั้งสองแบบส่ง <script> ตัวจริงออกไป และกล่อง alert เด้งใน Chrome · สองคำนี้คือของชิ้นเดียวกัน (raw = to_s.html_safe)

ตัวเลือกที่ 1 กลับด้าน — <%= %> ธรรมดาคือแบบที่ปลอดภัยที่สุด มัน escape ให้ · ตัวเลือกที่ 2 ตัวหนังสือ alert('XSS!') ที่เหลืออยู่ไม่ได้รัน เพราะแท็ก script ถูกถอดแล้ว · ตัวเลือกที่ 4 ผิดเพราะ Rails escape ให้จนกว่าเราจะสั่งให้หยุด — raw/html_safe คือคำสั่งให้หยุด

จุดที่ต้องจำ: ค่าเริ่มต้นปลอดภัย · อันตรายเกิดเมื่อพิมพ์ raw หรือ html_safe เอง → ค้นสองคำนี้ก่อนเสมอ

ส่งข้อความ <a href="/posts" onclick="alert(1)">ร้านอื่น</a> เข้า sanitize แบบไม่ตั้งค่าอะไรเพิ่ม · ได้อะไรออกมา?

ตัวเลือกที่ 2 ถูก — ผลจริงใน console: "<a href=\"/posts\">ร้านอื่น</a>" · รายชื่อที่อนุญาตมีทั้งแท็กและช่องในแท็ก (attribute) · href อยู่ในรายชื่อ onclick ไม่อยู่

ตัวเลือกที่ 1 ลืมว่าตรวจระดับช่องด้วย ไม่ใช่แค่ระดับแท็ก · ตัวเลือกที่ 3 คือสิ่งที่เกิดกับแท็กที่ไม่อยู่ในรายชื่อ เช่น <script> · <a> อยู่ในรายชื่อจึงรอด · ตัวเลือกที่ 4 — sanitize ไม่เคย error มันแค่ถอดของที่ไม่อนุญาตออกเงียบ ๆ

จุดที่ต้องจำ: sanitize = เก็บเฉพาะของในรายชื่อ (allowlist) ถอดที่เหลือ · ใช้เมื่อต้องการ HTML จากผู้ใช้จริง ๆ เท่านั้น

partial นี้ (ดัดแปลงจาก Quiz A ข้อ 3 สไลด์หน้า 19) ถูก render @posts เรียกในหน้ารวม · ข้อไหนบอกปัญหาสองข้อได้ถูก?
<h2><%= @post.title %></h2> · <small><%= @post.category.name %></small>

ตัวเลือกที่ 1 ถูก — ① ในหน้ารวม controller วางแค่ @posts (มี s) บนถาด · @post ไม่มีใครวาง = nil → พัง (บท 123: แม่พิมพ์ควรใช้ของที่ยื่นใส่มือ ไม่ควานหาบนถาด) · ② .category.name ทุกรอบ = เดินไปตู้ทุกบทความ แก้ที่ controller ด้วย includes(:category)

ตัวเลือกที่ 2 — <%= %> escape ให้เสมอ และ partial ใส่แท็กอะไรก็ได้ · ตัวเลือกที่ 3 — @post ไม่เกี่ยวกับ XSS และ raw คือตัวเปิดช่อง XSS ไม่ใช่ตัวแก้ · ตัวเลือกที่ 4 — partial ขึ้นต้นด้วย _ ไม่ใช่ @ · และ includes ต้องอยู่ที่ใบเบิกใน controller ไม่ใช่ใน view

จุดที่ต้องจำ: partial ใช้ตัวแปรที่ยื่นมา (post) · เติมจุดใน partial แล้วไปเช็ค includes ที่ controller

หน้า /posts 30 บทความ log ขึ้น (32 queries, 25 cached) และมีบรรทัด CACHE Category Load เยอะมาก · เพื่อนบอก "cached ตั้ง 25 ตัว ไม่ได้ไปตู้จริง ปล่อยไว้ได้" · ข้อไหนตอบเพื่อนได้ถูก?

ตัวเลือกที่ 4 ถูก — ผลจริงหลังเติม includes(:category): (3 queries, 0 cached) · ความจำ CACHE อยู่แค่ในใบสั่งเดียว และช่วยเฉพาะตอนหมวดซ้ำ · ถ้าหมวดไม่ซ้ำกันเลยก็เดินจริงทุกรอบ

ตัวเลือกที่ 1 — CACHE ไม่ได้แก้ N+1 แค่บังให้ดูเบาลงในข้อมูลชุดนี้ · ตัวเลือกที่ 2 — partial เรียกลิ้นชักอื่นได้ ปัญหาอยู่ที่ใบเบิกไม่ได้บอกล่วงหน้า แก้ที่ controller โดยไม่ต้องตัดข้อมูลที่ผู้ใช้อยากเห็น · ตัวเลือกที่ 3 — ตัวเลขใน log เชื่อได้ดีอยู่แล้ว (มันแยก cached ให้ดูด้วยซ้ำ) ปิด cache ไม่ได้แก้อะไร

จุดที่ต้องจำ: เห็น … Load ซ้ำ ๆ ต่างกันแค่เลข (มี CACHE หรือไม่ก็ตาม) = N+1 → includes ที่ controller
