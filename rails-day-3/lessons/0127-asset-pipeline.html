ไฟล์ CSS และ JS เดินทางยังไง — fingerprinting, Propshaft และ importmap

~20 นาที · ควรผ่าน บทเรียน 126 (Lab Vibe 1) และ บทเรียน 120 (เปิดโปรเจกต์กลางของคอร์ส) มาก่อน

เคยไหม แก้ CSS แล้วกด refresh แต่หน้าเว็บยังหน้าตาเดิม? ปัญหานี้เกิดกับทุกเว็บในโลก · บทนี้เปิดบล็อก B (CSS) ด้วยการตามดูว่าไฟล์ CSS และ JavaScript เดินทางจากโฟลเดอร์ของเราไปถึงเบราว์เซอร์ยังไง
อ่านจบแล้วคุณจะอธิบายได้ว่าทำไมชื่อไฟล์ CSS ในหน้าเว็บมีเลขแปลก ๆ ต่อท้าย · รู้ว่าเลขนั้นช่วยให้ผู้ใช้ไม่เห็นของเก่ายังไง · รู้ว่า bin/rails assets:precompile ทำอะไร · และตอบได้ว่าทำไมโปรเจกต์ Rails 8 ไม่มีโฟลเดอร์ node_modules เหมือนโปรเจกต์ Next.js

🔁 ทวนก่อนเริ่ม — คำจากบทก่อน ๆ ที่บทนี้ใช้

  • layout (บท 103 · 123) — "จานรองมาตรฐาน" ไฟล์ app/views/layouts/application.html.erb ที่ห่อทุกหน้า · ส่วน <head> ของมันคือที่ที่บทนี้จะแกะดู
  • curl (บท 99–105) — ขอหน้าเว็บจาก server แล้วโชว์ HTML ดิบ ๆ ที่เบราว์เซอร์ได้รับจริง · curl -sI = ขอดูแค่ header ไม่เอาเนื้อ (header = "หัวจดหมาย" ข้อมูลกำกับที่ server แนบมาก่อนตัวไฟล์ เช่น ไฟล์นี้ชนิดอะไร ใหญ่เท่าไหร่ — บท 56)
  • Tailwind (บท 72) — เขียนคลาสสั้น ๆ อย่าง text-3xl ใน HTML แล้วเครื่องมือสร้างไฟล์ CSS ให้ · ในแอปนี้ไฟล์ที่สร้างได้คือ app/assets/builds/tailwind.css (สร้างโดย bin/dev หรือ bin/rails tailwindcss:build · ละเอียดในบท 128)
  • npm install · node_modules · npm run build (บท 70) — ฝั่ง Next.js ต้องโหลด library มากองในเครื่องก่อน และมีขั้น build ก่อนขึ้นเครื่องจริง · deploy (บท 109) = เอาโค้ดขึ้นเครื่อง server จริง (production) ให้คนอื่นใช้
  • import … from "…" (บท 63–71) — ดึงโค้ดจากไฟล์อื่นหรือ library อื่นมาใช้ใน JavaScript/TypeScript

asset คืออะไร — ของในร้านที่ไม่ได้ทำใหม่ทุกจาน

หน้าเว็บหนึ่งหน้าไม่ได้มีแค่ HTML · HTML บอกว่ามีอะไรบนหน้า แต่หน้าตามาจากไฟล์ CSS · การขยับได้มาจากไฟล์ JavaScript · และยังมีรูป ฟอนต์ ไอคอนอีก
ไฟล์พวกนี้ที่ไม่ใช่ HTML เรียกรวม ๆ ว่า asset · ต่างจาก HTML ตรงที่ทุกคนได้ไฟล์เดียวกันเป๊ะ ไม่ต้องทำใหม่ต่อคำขอ

เทียบกับร้านอาหาร: HTML คือจานอาหารที่ครัวทำใหม่ทุกออร์เดอร์ (บทความไม่เหมือนกันแต่ละหน้า) · ส่วน asset คือของตกแต่งร้านและเมนูเล่ม — พิมพ์ครั้งเดียว ทุกโต๊ะใช้เล่มเดียวกัน

ในแอปของเรา asset อยู่ตรงนี้:

ไฟล์/โฟลเดอร์คืออะไร
app/assets/stylesheets/application.cssCSS ที่เราเขียนเอง (ตอนนี้มีแต่คอมเมนต์ ยังว่าง)
app/assets/builds/tailwind.cssCSS ที่ Tailwind สร้างให้ จากคลาสใน view · ไม่ได้เก็บใน git · ห้ามแก้มือ (สร้างใหม่ทับทุกรอบ)
app/javascript/JavaScript ของเรา (application.js และโฟลเดอร์ controllers/ ของ Stimulus — บท 134)
app/assets/images/รูปภาพ (ตอนนี้ว่าง)

แล้วเบราว์เซอร์รู้ได้ยังไงว่าต้องไปเอาไฟล์พวกนี้? เพราะ layout เขียนบอกไว้ใน <head> · ดูสองบรรทัดนี้ใน app/views/layouts/application.html.erb: 

<%= stylesheet_link_tag :app, "data-turbo-track": "reload" %>
<%= javascript_importmap_tags %>
  • stylesheet_link_tag :app — helper ที่เขียนแท็ก <link rel="stylesheet"> ให้ ทุกไฟล์ CSS ในแอป (:app = "เอาของแอปทั้งหมด") · ของเรามีสองไฟล์ จึงได้สองบรรทัด
  • "data-turbo-track": "reload" — ป้ายให้ Turbo คอยดูว่าชื่อไฟล์นี้เปลี่ยนไหม ถ้าเปลี่ยนให้โหลดใหม่ทั้งหน้า (Turbo คือตัวที่ทำให้เปลี่ยนหน้าโดยไม่โหลดใหม่ทั้งหน้า — ละเอียดบท 130) · ตอนนี้แค่รู้ว่ามี
  • javascript_importmap_tags — helper ที่เขียนส่วน JavaScript ทั้งหมดให้ (หัวข้อ importmap ท้ายบท)

เปิด server (bin/dev แบบบท 120) แล้วดูว่าเบราว์เซอร์ได้อะไรจริง — ตัดเอาเฉพาะช่วงนั้นของ <head>:

ส่วน <script type="importmap"> · modulepreload · <script type="module"> คือส่วนของ JavaScript · ตอนนี้ข้ามไปก่อน เดี๋ยวแกะทีละบรรทัดในหัวข้อ importmap · … คือบรรทัดที่เราตัดออกให้สั้น

cache ของเบราว์เซอร์ — ลูกค้าประจำที่จำเมนูเล่มเก่า

เบราว์เซอร์ฉลาดพอจะไม่โหลดไฟล์เดิมซ้ำ ๆ · ไฟล์ไหนเคยโหลดแล้ว มันจะเก็บสำเนาไว้ในเครื่อง ครั้งหน้าใช้สำเนาเลย ไม่ต้องรอเน็ต · ที่เก็บสำเนานี้เรียกว่า cache (อ่านว่า "แคช")
เก็บไว้นานแค่ไหน — server เป็นคนบอก ผ่าน header (หัวจดหมาย) ที่แนบมากับไฟล์

ไอเดียเดียวกับ includes ใน Day 2 (บท 114): ของที่หยิบมาแล้ว อย่าเดินไปขอซ้ำ · ต่างกันแค่ includes ลดการเดินไปตู้เก็บแฟ้ม ส่วน cache ลดการเดินไปขอไฟล์จาก server

เราเปิดหน้าเว็บด้วย Chrome จริง แล้ววัดว่าไฟล์ CSS แต่ละไฟล์ต้องโหลดผ่านเน็ตกี่ byte (0 = ไม่ได้โหลดเลย หยิบจากสำเนา):

ครั้งแรก /posts79134,446
ต่อมา /posts/30 (หน้าอื่น แต่ใช้ CSS ชุดเดียวกัน)00

หน้าที่สองไม่โหลด CSS ผ่านเน็ตเลยสักไบต์ · นี่คือสิ่งที่ทำให้เว็บเปิดหน้าถัดไปเร็ว (ตัวเลขรวม header ด้วย จึงมากกว่าขนาดไฟล์นิดหน่อย · ของคุณดูได้ในแท็บ Network ของ DevTools แบบบท 56 คอลัมน์ Size — ไฟล์ที่หยิบจากสำเนาจะขึ้นเป็นคำว่า memory cache หรือ disk cache แทนตัวเลข · ถ้าติ๊ก Disable cache ไว้ จะโหลดใหม่ทุกครั้ง)
แต่ข้อดีนี้มีด้านมืด: ถ้าเราแก้ไฟล์ CSS แล้วชื่อไฟล์ยังเหมือนเดิม เบราว์เซอร์จะคิดว่า "อันนี้มีแล้ว" แล้วใช้สำเนาเก่าต่อไป

📖 เทียบให้เห็นภาพ — ลูกค้าประจำที่จำเมนูเล่มเก่าได้

ลูกค้าประจำมาร้านบ่อยจนจำเมนูได้ขึ้นใจ เลยไม่หยิบเมนูเล่มบนโต๊ะมาเปิดอีก — สั่งจากความจำเลย เร็วดี · วันหนึ่งร้านเปลี่ยนราคาและเพิ่มเมนูใหม่ แต่หน้าปกเมนูเหมือนเดิมทุกอย่าง · ลูกค้าประจำก็ยังสั่งจากความจำ ไม่รู้เลยว่ามีของใหม่

ที่ไม่เหมือนกัน: ลูกค้าคนจริงอาจสังเกตป้ายหน้าร้านหรือถามพนักงานเอง · เบราว์เซอร์ไม่ถามเลย ถ้า server เคยบอกว่า "เก็บไว้ได้หนึ่งปี" มันก็เชื่อตามนั้นหนึ่งปีเต็ม ไม่สนว่าเนื้อในเปลี่ยนไปแล้ว

🗣 ศัพท์ที่เพิ่งเรียนไป
asset
ไฟล์ที่ไม่ใช่ HTML ที่หน้าเว็บต้องใช้: CSS · JavaScript · รูป · ฟอนต์ · ถาม senior ได้ว่า “asset ของโปรเจกต์นี้เสิร์ฟจาก Rails เองหรือผ่าน CDN” (CDN = บริการเก็บไฟล์ไว้หลายประเทศให้โหลดใกล้ ๆ)
browser cache
ที่เบราว์เซอร์เก็บสำเนาไฟล์ที่เคยโหลดไว้ เพื่อไม่ต้องโหลดซ้ำ · พิมพ์บอก AI ได้ว่า “after deploy, users still see the old CSS — is it a browser cache problem?”
Cache-Control header
บรรทัดในหัวจดหมายที่ server บอกเบราว์เซอร์ว่าเก็บสำเนาได้นานแค่ไหน เช่น max-age=31536000 = เก็บได้ 31,536,000 วินาที (หนึ่งปี) · ถาม senior ได้ว่า “ไฟล์ asset ของเราตั้ง Cache-Control ไว้เท่าไหร่”

สามปัญหาที่ asset pipeline มีไว้แก้

asset pipeline คือชื่อรวมของ "ขั้นตอนที่พาไฟล์ asset จากโฟลเดอร์ของเราไปถึงเบราว์เซอร์" · สไลด์หน้า 24 บอกว่ามันเกิดมาเพื่อแก้สามปัญหาที่ทุกเว็บเจอ ไม่ว่าเขียนด้วยภาษาอะไร:

ปัญหาภาษาคนวิธีแก้เดิมตอนนี้ยังสำคัญไหม
1 · cache ตามชื่อแก้ CSS แล้ว deploy แต่ผู้ใช้ยังเห็นของเก่าเป็นวัน (หัวข้อที่แล้ว)fingerprintingสำคัญเสมอ แก้ทางอื่นไม่ได้
2 · ไฟล์เยอะ = ช้าสมัยก่อนโหลดได้ทีละไม่กี่ไฟล์พร้อมกัน 50 ไฟล์ต้องต่อคิวนานbundling = มัดหลายไฟล์เป็นก้อนเดียวน้อยลงมาก
3 · ไฟล์ใหญ่เกินจำเป็นช่องว่าง คอมเมนต์ ชื่อตัวแปรยาว ๆ เบราว์เซอร์ไม่ได้ใช้minify = บีบเอาช่องว่าง/คอมเมนต์ออก · compress = บีบอัดแบบไฟล์ zipน้อยลงมาก

ทำไมข้อ 2–3 สำคัญน้อยลง (แค่รู้ไว้ ไม่ต้องลงลึก):

  • HTTP/2 — "ภาษาที่เบราว์เซอร์คุยกับ server" รุ่นใหม่ ส่งหลายไฟล์พร้อมกันบนสายเดียวได้ ไฟล์เยอะจึงไม่ต้องต่อคิวเหมือนเมื่อก่อน
  • gzip · brotli — วิธีบีบอัดข้อมูลที่ server (หรือตัวกลางหน้า server) ทำให้อัตโนมัติตอนส่ง ไม่ต้องบีบไว้ล่วงหน้าเอง
  • ES module — การเขียน import … from ที่เบราว์เซอร์ทุกตัวเข้าใจเองแล้ว ไม่ต้องมีเครื่องมือมัดรวมให้ก่อน (หัวข้อ importmap)

แต่ข้อ 1 ไม่มีเทคโนโลยีไหนมาช่วย เพราะมันเป็นเรื่องของชื่อ · สไลด์สรุปว่านี่คือเหตุผลที่ Rails 8 ยอมทิ้งเครื่องมือมัดรวมไฟล์ แต่ยังเก็บ fingerprinting ไว้

fingerprinting — เปลี่ยนเนื้อใน ชื่อเปลี่ยนตาม

ทางแก้ข้อ 1 ง่ายจนน่าตกใจ: ถ้าเนื้อไฟล์เปลี่ยน ก็เปลี่ยนชื่อไฟล์ด้วย · ชื่อใหม่ที่เบราว์เซอร์ไม่เคยเห็น = ต้องโหลดใหม่แน่นอน
เลขท้ายชื่อคำนวณจากเนื้อไฟล์ทุกตัวอักษร เรียกว่า hash — คิดว่าเป็น "ลายนิ้วมือของเนื้อไฟล์" ก็ได้: เนื้อเดิมได้เลขเดิมทุกครั้ง · แก้แม้ตัวเดียวได้เลขใหม่ทันที

ที่ไม่เหมือนกัน: เลขรุ่นในร้านจริงคนตั้งเองตามใจ (รุ่น 1, 2, 3) · ในเว็บเลขมาจากเนื้อไฟล์ ล้วน ๆ — แก้แล้วแก้กลับ เลขก็กลับเป็นเลขเดิม · และเมนูเล่มเก่าในร้านต้องมีคนเก็บทิ้ง แต่ไฟล์ชื่อเก่าไม่ต้องมีใครไปลบจากเครื่องผู้ใช้ — แค่ไม่มีหน้าไหนเรียกถึงมันอีก

สไลด์หน้า 25 ให้จำประโยคนี้ไว้: "ไม่ต้องไปลบของเก่า — ให้ key เปลี่ยน แล้วของเก่าจะหมดความหมายไปเอง" · key ในที่นี้คือชื่อไฟล์ · หลักการเดียวกันนี้จะกลับมาอีกครั้งตอนเรียนเรื่อง cache ของหน้าเว็บใน Day 3 ครึ่งหลัง (ยังไม่มาในชุดนี้)

🗣 ศัพท์ที่เพิ่งเรียนไป
fingerprinting · digest
ต่อเลขที่คำนวณจากเนื้อไฟล์ไว้ท้ายชื่อ (application-8b441ae0.css) · เลขนั้นเรียกว่า digest หรือ hash · ถาม senior ได้ว่า “ไฟล์นี้ผ่าน fingerprinting หรือยัง ทำไมชื่อไม่มี digest”
cache busting
ชื่อเรียกเทคนิค "บังคับให้เบราว์เซอร์ทิ้งสำเนาเก่า" ซึ่ง fingerprinting เป็นวิธีที่นิยมที่สุด · พิมพ์บอก AI ได้ว่า “use digest-based cache busting, don't add ?v=123 by hand”
immutable
คำใน Cache-Control ที่บอกว่า "ไฟล์ชื่อนี้ไม่มีวันเปลี่ยนเนื้อ ไม่ต้องถามซ้ำ" · ใช้ได้ปลอดภัยก็ต่อเมื่อชื่อมี digest · ถาม senior ได้ว่า “ไฟล์ที่ไม่มี digest ห้ามตั้ง immutable ใช่ไหม”
key-based cache expiration
ชื่อทางการของประโยค "ให้ key เปลี่ยน แทนการลบของเก่า" · เจอเต็ม ๆ ใน Day 3 ครึ่งหลัง · ถาม senior ได้ว่า “ตรงนี้ใช้ key-based expiration ได้ไหม แทนการสั่งลบ cache”

Propshaft — พนักงานที่ติดเลขรุ่นแล้ววางบนชั้น

คนที่คำนวณลายนิ้วมือ · เสิร์ฟไฟล์ที่ /assets/… · และบอก stylesheet_link_tag ว่าตอนนี้ไฟล์ชื่ออะไร คือ gem ชื่อ Propshaft · เป็นค่าเริ่มต้นของ Rails 8 และทำแค่นั้นจริง ๆ — ไม่มัดรวมไฟล์ ไม่แปลงภาษา ไม่บีบไฟล์

เหตุผลเบื้องหลัง (สไลด์): Sprockets เกิดตอนที่เบราว์เซอร์ทำอะไรเองไม่ค่อยได้ เครื่องมือจึงต้องทำแทนหมด · ทุกวันนี้เบราว์เซอร์ทำเองได้เกือบหมดแล้ว (หัวข้อสามปัญหา) เครื่องมือที่ทำเยอะเลยกลายเป็นภาระแทน

เทียบกับ Next.js (บท 70): งานมัดรวม · บีบ · แปลง TypeScript ทั้งหมดซ่อนอยู่ใน npm run build ที่เครื่องมือของ Next.js ทำให้ · Rails 8 แยกงานออกเป็นชิ้นเล็ก ๆ แล้วให้ Propshaft ถือแค่ชิ้นที่เล็กที่สุด

importmap — JavaScript โดยไม่มี node_modules

ตอนทำ Next.js (บท 70) สิ่งแรกที่ทำคือ npm install แล้วได้โฟลเดอร์ node_modules ก้อนโต · ก่อนขึ้นเครื่องจริงต้อง npm run build ให้เครื่องมือมัด JavaScript ทั้งหมดเป็นก้อน · ในโปรเจกต์ Rails ของเรา: 

$ ls node_modules package.json

ls: package.json: No such file or directory

import "…" แบบไม่มี from = "โหลดไฟล์นั้นมารันเลย" ไม่ได้หยิบตัวแปรอะไรออกมาใช้ · "@hotwired/turbo-rails" ไม่ใช่ที่อยู่ไฟล์ — มันเป็นแค่ชื่อเล่น · เบราว์เซอร์เปล่า ๆ ไม่รู้ว่าชื่อนี้คือไฟล์ไหน · ใน Next.js เครื่องมือ build ไปหาใน node_modules ให้ · ใน Rails 8 ใช้วิธีที่เบราว์เซอร์เข้าใจเอง ชื่อ import map = "สมุดรายชื่อที่บอกเบราว์เซอร์ว่า ชื่อเล่นนี้ → ไฟล์ที่อยู่ตรงไหน"

สมุดนี้เราเขียนที่ config/importmap.rb (ไฟล์จริงของแอป):

# Pin npm packages by running ./bin/importmap

pin "application"
pin "@hotwired/turbo-rails", to: "turbo.min.js"
pin "@hotwired/stimulus", to: "stimulus.min.js"
pin "@hotwired/stimulus-loading", to: "stimulus-loading.js"
pin_all_from "app/javascript/controllers", under: "controllers"
  • pin "application" — จดชื่อ application → ไฟล์ application.js (ไม่มี to: = ชื่อไฟล์เหมือนชื่อเล่น)
  • pin "@hotwired/turbo-rails", to: "turbo.min.js" — ชื่อเล่น @hotwired/turbo-rails → ไฟล์ turbo.min.js (.min = ฉบับที่บีบช่องว่างออกแล้ว)
  • สองบรรทัด @hotwired/stimulus… — แบบเดียวกัน แต่เป็นของ Stimulus (ตัวช่วยเขียน JS เล็ก ๆ ผูกกับ HTML — บท 134)
  • pin_all_from "app/javascript/controllers", under: "controllers" — จดทุกไฟล์ในโฟลเดอร์นั้นทีเดียว โดยขึ้นต้นชื่อเล่นด้วย controllers/ (ใช้ในบท 134)

ไม่มี node_modules ไม่มี package.json ไม่มีขั้น build ของ JSไม่มี tree-shaking (การตัดส่วนของ library ที่เราไม่ได้ใช้ทิ้ง) — ได้ library มาทั้งก้อน

ที่ไม่เหมือนกัน: สมุดรายชื่อไม่ได้ทำให้ของเบาลง — ถ้าชั้นนั้นมีหนังสือหนาพันหน้า ลูกค้าก็ต้องแบกไปทั้งเล่ม แม้จะอ่านแค่หน้าเดียว (ไม่มี tree-shaking) · และสมุดใช้ได้เฉพาะของที่ "หยิบได้เลย" ถ้าต้องปรุงก่อน (TypeScript · JSX) ต้องมีครัวแยกมาช่วย

แบบฝึกหัด

สไลด์หน้า 33 ถามว่า ถ้าเราไม่ทำ fingerprinting เลย แต่ตั้งหัวจดหมายบอกเบราว์เซอร์ว่า "ห้ามเก็บสำเนาไฟล์ CSS" แทน จะเกิดอะไรขึ้น?

ตัวเลือกที่ 2 ถูก — ห้ามเก็บสำเนา = ไม่มีของเก่าค้าง แต่ก็เสียข้อดีของ cache ไปทั้งหมด · ตาราง Chrome ในบทนี้ หน้าที่สองโหลด CSS 0 byte เพราะมีสำเนา · ถ้าห้ามเก็บ ทุกหน้าต้องโหลดใหม่ (34 KB ของ Tailwind ทุกหน้า) server ก็เหนื่อยขึ้น · fingerprinting ได้ทั้งสองอย่าง: เก็บได้นานหนึ่งปี และ ได้ของใหม่ทันทีที่แก้

ตัวเลือกที่ 1 ผิดเพราะสั่งห้ามเก็บแล้ว จะไม่มีสำเนาเก่าให้จำ · ตัวเลือกที่ 3 ผิดเพราะการต่อเลขคือ fingerprinting ที่โจทย์บอกว่าไม่ทำ · ตัวเลือกที่ 4 ผิดเพราะเราวัดแล้วว่าเบราว์เซอร์เก็บสำเนาจริง (0 byte ในหน้าที่สอง)

จุดที่ต้องจำ: ปิด cache = ได้ของใหม่แต่ช้า · cache ยาวโดยไม่มี digest = เร็วแต่ได้ของเก่า · fingerprinting = เร็วและใหม่

ข้อไหนบอกหน้าที่ของ Propshaft ได้ตรงที่สุด?

ตัวเลือกที่ 3 ถูก — Propshaft ทำแค่ fingerprint + เสิร์ฟ (+ ทำตาราง manifest ให้ stylesheet_link_tag รู้ชื่อ) ไม่ทำอย่างอื่น

ตัวเลือกที่ 1 คืองานของ tailwindcss-rails (บท 128) · ตัวเลือกที่ 2 คืองานของ importmap · ตัวเลือกที่ 4 คืองานของ bundler (jsbundling-rails · Vite) หรือ Sprockets สมัยก่อน — Propshaft ตั้งใจไม่ทำ

จุดที่ต้องจำ: Propshaft = เลขรุ่น + เสิร์ฟ · Tailwind = สร้าง CSS · importmap = สมุดชื่อเล่นของ JS

เพื่อนลอง bin/rails assets:precompile ในเครื่องเมื่อวาน · วันนี้แก้ application.css แล้วเปิด server ใหม่ · สีไม่เปลี่ยน และชื่อไฟล์ใน HTML ก็ยังเป็นชื่อเดิม · เกิดจากอะไร?

ตัวเลือกที่ 1 ถูก — คำเตือนตอน precompile บอกไว้ตรง ๆ ว่า "Rails will not serve any changed assets until you delete public/assets/.manifest.json" · เราลองแล้วได้อาการนี้เป๊ะ · แก้ด้วย assets:clobber แล้วอย่าลืม tailwindcss:build

ตัวเลือกที่ 2 ผิดเพราะชื่อใน HTMLยังเป็นชื่อเดิม — ปัญหาอยู่ฝั่ง server ไม่ใช่เบราว์เซอร์ (ถ้าชื่อเปลี่ยน เบราว์เซอร์โหลดใหม่เองอยู่แล้ว) · ตัวเลือกที่ 3 ผิดเพราะ importmap ดูแลแค่ JS ไม่เกี่ยวกับ CSS · ตัวเลือกที่ 4 ผิดเพราะ digest มาจากเนื้อไฟล์ล้วน ๆ (แก้แล้วแก้กลับได้เลขเดิม)

จุดที่ต้องจำ: ชื่อใน HTML ไม่เปลี่ยน = ดูฝั่ง server ก่อน · precompile ในเครื่องแล้วต้อง clobber

โปรเจกต์ไม่มี node_modules แต่ app/javascript/application.js เขียน import "@hotwired/turbo-rails" แล้วทำงานได้ · เพราะอะไร?

ตัวเลือกที่ 4 ถูก — <script type="importmap"> แมปชื่อเล่นไปที่ไฟล์ · ไฟล์นั้นจริง ๆ อยู่ใน gem turbo-rails และ Propshaft เป็นคนเสิร์ฟ (พร้อม digest)

ตัวเลือกที่ 1 คือสิ่งที่ bundler ทำ — importmap ไม่มัดรวม (ไฟล์ส่งแยกกัน เห็นได้จาก modulepreload 7 บรรทัด) · ตัวเลือกที่ 2 ผิดเพราะไฟล์มาจาก server ของเราเอง ที่ /assets/ · npm ไม่เกี่ยวเลย · ตัวเลือกที่ 3 ผิดเพราะ JS รันในเบราว์เซอร์ Ruby ไม่ได้แตะบรรทัดนั้น

จุดที่ต้องจำ: importmap = สมุดชื่อเล่น → ไฟล์ · เบราว์เซอร์อ่านสมุดแล้วโหลดเอง ไม่มีขั้น build

ติดตรงไหน ลองถามผู้สอนหรือ AI ด้วยประโยคในกล่องศัพท์ได้เลย · หรือแปะผล curl -sI ของไฟล์ที่สงสัยแล้วถามว่า "ทำไมไฟล์นี้ cache แบบนี้"
