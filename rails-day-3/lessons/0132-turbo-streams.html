โจทย์ — ส่งครั้งเดียว ต้องเปลี่ยนสามกล่อง

เป้าหมายของบทนี้คือส่วนคอมเมนต์ใต้บทความ หน้าตาแบบนี้ · ตอนกดปุ่ม "ส่งความคิดเห็น" มีสามกล่องในหน้าที่ต้องเปลี่ยน และอยู่คนละที่กัน:

หน้า /posts/30 (นมเย็น) บทความ … แถวปุ่ม แก้ไข / ลบ ← ไม่ต้องขยับ ความคิดเห็น ( 2 ) ← กล่อง ② id="comment_count" ตัวเลขต้องเพิ่ม ┌ id="comments" ────────────────────── │ ทดลอง · ส่งก่อนมีไฟล์ stream │ ต้นกล้า · ชาเย็นร้านนี้หวานกำลังดี │ + คอมเมนต์ใหม่มาต่อท้ายตรงนี้ ← กล่อง ① ต่อท้ายรายการ └───────────────────────────────────── ┌ form id="comment_form" ───────────── │ ชื่อ [ ] ← กล่อง ③ ล้างให้ว่าง │ ความคิดเห็น [ ] [ส่งความคิดเห็น] (หรือโชว์ error ถ้าส่งว่าง) └─────────────────────────────────────

ถ้าใช้ Turbo Frame (บท 131) เราเปลี่ยนได้แค่กรอบเดียว — กรอบที่ฟอร์มอยู่ข้างใน · กล่อง ① กับ ② อยู่นอกกรอบ เลยไม่ขยับ · ถ้าใช้ redirect_to แบบ scaffold ก็ได้ผลถูก แต่ได้ทั้งหน้าใหม่ทั้งที่อยากเปลี่ยนแค่สามจุด · ของที่ตอบโจทย์นี้พอดีชื่อ Turbo Stream · แต่ก่อนจะถึงตรงนั้น ต้องมีคอมเมนต์ให้ส่งก่อน

ทวน Day 2 — สร้าง Comment (พิมพ์ตาม ~5 นาที)

ส่วนนี้ไม่มีเรื่องใหม่ · เป็นท่าเดียวกับที่ทำใน Day 2 ทั้งหมด · คอมเมนต์หนึ่งชิ้นมี ข้อความ (body) · ชื่อคนเขียน (author_name — แอปนี้ยังไม่มีระบบล็อกอิน เลยให้พิมพ์ชื่อเอง ระบบล็อกอินรออยู่ Day 4) · และเป็นของบทความไหน (post)

ขั้น 1 · สร้าง model (คำสั่งตามสไลด์หน้า 52) — รันในโฟลเดอร์โปรเจกต์:

$ bin/rails generate model Comment body:text author_name:string post:references
      invoke  active_record
      create    db/migrate/20261107035534_create_comments.rb
      create    app/models/comment.rb
      invoke    test_unit

post:references = "คอมเมนต์ชี้ไปหาบทความ" → ได้คอลัมน์ post_id + index + foreign key ให้เอง (บท 115) · เลขยาว ๆ หน้าชื่อไฟล์ migration คือเวลาที่คุณรัน ของคุณจะต่าง · ไฟล์ test สองไฟล์ปล่อยไว้ก่อน (เรื่อง test รออยู่ Day 4)

ขั้น 2 · เติม "ห้ามว่าง" ให้ตู้ — เปิดไฟล์ migration ที่เพิ่งได้ เติม , null: false ท้ายบรรทัด body และ author_name:

generator ให้มา

      t.text :body
      t.string :author_name
      t.references :post, null: false, foreign_key: true

หลังแก้

      t.text :body, null: false
      t.string :author_name, null: false
      t.references :post, null: false, foreign_key: true

generator ใส่ null: false ให้แค่บรรทัด references · อีกสองบรรทัดต้องเติมเองก่อน db:migrate · "validation + NOT NULL ต้องมาเป็นคู่" คือกฎข้อเดียวกับบท 111 — validation กันที่หน้าร้าน NOT NULL กันที่ตัวตู้

ไฟล์ทั้งไฟล์หลังแก้ (ของคุณชื่อไฟล์ต่างแค่เลขเวลา):

class CreateComments < ActiveRecord::Migration[8.1]
  def change
    create_table :comments do |t|
      t.text :body, null: false
      t.string :author_name, null: false
      t.references :post, null: false, foreign_key: true

      t.timestamps
    end
  end
end

ขั้น 4 · กฎของคอมเมนต์ + ความสัมพันธ์ — app/models/comment.rb ทั้งไฟล์ (generator เขียน belongs_to ให้แล้ว เราเติม validates สองบรรทัด):

class Comment < ApplicationRecord
  belongs_to :post

  validates :author_name, presence: true, length: { maximum: 50 }
  validates :body, presence: true, length: { maximum: 1000 }
end

แล้วเปิด app/models/post.rb เพิ่มหนึ่งบรรทัดใต้ belongs_to :category:

  has_many :comments, dependent: :destroy
  • validates … presence: true, length: { maximum: 50 } = ห้ามว่าง และยาวไม่เกิน 50 ตัวอักษร (ชื่อคนสั้น ๆ) · ข้อความไม่เกิน 1000 (บท 110)
  • has_many :comments = "บทความหนึ่งมีหลายคอมเมนต์" → ได้ @post.comments มาใช้ (บท 115)
  • dependent: :destroy = ลบบทความแล้วลบคอมเมนต์ของมันตาม · ถ้าไม่ใส่ ตู้จะไม่ยอมให้ลบบทความที่มีคอมเมนต์ (foreign key ฟ้อง — บท 116) · เลือก :destroy เพราะคอมเมนต์ไม่มีความหมายถ้าไม่มีบทความ (ต่างจากหมวดที่ใช้ :restrict_with_error "ห้ามลบถ้ายังมีบทความ")

ทางเข้าของคอมเมนต์ — route ซ้อน และ controller

คอมเมนต์ต้องรู้ว่าเป็นของบทความไหน · เราเลยให้ URL บอกเลขบทความไว้ในตัว: POST /posts/30/comments = "ส่งคอมเมนต์ให้บทความเลข 30" · เปิด config/routes.rb เปลี่ยน resources :posts บรรทัดเดียว ให้เป็นสามบรรทัดนี้ (ท่า "ซ้อนกัน" ของบท 117): 

  resources :posts do
    resources :comments, only: :create
  end
$ bin/rails routes -c comments
       Prefix Verb URI Pattern                        Controller#Action
post_comments POST /posts/:post_id/comments(.:format) comments#create

only: :create = เปิดแค่ประตูเดียว คือ "สร้างคอมเมนต์" (ยังไม่ต้องมีหน้ารวมคอมเมนต์ หน้าแก้ หน้าลบ) · :post_id = ช่องในใบสั่งที่บอกเลขบทความ · ได้ชื่อเล่น post_comments → ใช้เป็น post_comments_path(@post) ได้

ต่อไปคือหัวหน้าเชฟแผนกคอมเมนต์ · ไม่มี generator ให้ — สร้างไฟล์ใหม่ app/controllers/comments_controller.rb แล้วพิมพ์ทั้งไฟล์: 

class CommentsController < ApplicationController
  before_action :set_post

  # POST /posts/1/comments
  def create
    @comment = @post.comments.build(comment_params)

    respond_to do |format|
      if @comment.save
        format.turbo_stream # ใช้ create.turbo_stream.erb
        format.html { redirect_to @post, notice: "เพิ่มความคิดเห็นแล้ว" }
      else
        format.turbo_stream do
          render turbo_stream: turbo_stream.replace("comment_form", partial: "comments/form", locals: { post: @post, comment: @comment }),
                 status: :unprocessable_content
        end
        format.html do
          @comments = @post.comments.order(:created_at)
          render "posts/show", status: :unprocessable_content
        end
      end
    end
  end

  private
    def set_post
      @post = Post.find(params.expect(:post_id))
    end

    def comment_params
      params.expect(comment: [ :author_name, :body ])
    end
end
  • before_action :set_post + set_post = ก่อนทำอะไร หาบทความจากเลขใน URL ก่อน · params.expect(:post_id) = "ต้องมีเลขบทความ" · ไม่มีบทความเลขนั้นได้ 404
  • @post.comments.build(comment_params) = สร้างคอมเมนต์ใหม่ที่ผูกกับบทความนี้ให้แล้ว (เติม post_id เอง) แต่ยังไม่บันทึก
  • comment_params = รับเฉพาะช่อง author_name กับ body · ใครแอบส่ง post_id มาในฟอร์มก็ถูกทิ้ง (strong parameters — บท 117)
  • respond_to do |format| = "ลูกค้าอยากได้คำตอบแบบไหน ก็เตรียมแบบนั้น" · format.html คือแบบหน้าเว็บเต็ม (เหมือน scaffold) · format.turbo_stream คือของใหม่ของบทนี้ — อธิบายละเอียดในสองหัวข้อถัดไป
  • ทางที่ไม่ผ่าน (else) = ส่งฟอร์มเดิมที่มี error กลับไปพร้อมรหัส 422 (รหัส "ข้อมูลไม่ผ่าน" แบบเดียวกับ scaffold ในบท 118) — ดูหัวข้อ "ส่งว่าง" ข้างล่าง
  • format.html do … end ในทาง else = ทางสำรองตอนไม่มี Turbo (เช่นเบราว์เซอร์ปิด JavaScript — ลองในหัวข้อ Accept) · วาดหน้า show เดิมพร้อม error · ต้องเตรียม @comments เองตรงนี้ เพราะหน้า show ใช้ตัวแปรนี้ แต่คำขอนี้ไม่ได้ผ่าน PostsController#show ที่ปกติเตรียมให้
  • # POST /posts/1/comments = คอมเมนต์บอกว่า action นี้รับคำขอแบบไหน (ตามสไตล์ scaffold) · private = method ข้างล่างใช้กันเองในไฟล์นี้ route เรียกตรง ๆ ไม่ได้

หน้าจอ — หน้า show และแม่พิมพ์สองตัว

ถาดหน้าครัวของหน้า show — เปิด app/controllers/posts_controller.rb เติมสองบรรทัดใน def show (เดิมว่าง): 

  def show
    @comments = @post.comments.order(:created_at)
    @comment = Comment.new
  end

@comments = คอมเมนต์ของบทความนี้ เรียงเก่า → ใหม่ (ของใหม่อยู่ล่างสุด ตรงกับ "ต่อท้าย") · @comment = คอมเมนต์เปล่าไว้วาดฟอร์ม

หน้า show — เปิด app/views/posts/show.html.erb เลื่อนไปท้ายไฟล์ · ตอนนี้ท้ายไฟล์หน้าตาแบบนี้ (แถวปุ่ม แก้ไข / กลับ / ลบ แล้วปิดด้วย </div> สองตัว): 

    <%= button_to "ลบบทความ", @post, … %>
  </div>      ← ปิดแถวปุ่ม
                ← ★ วางก้อนใหม่ตรงนี้ (เว้นบรรทัดว่างหนึ่งบรรทัดก่อน)
</div>        ← บรรทัดสุดท้ายของไฟล์ ปิดกล่องใหญ่ทั้งหน้า

ก้อนที่วาง:

  <section class="mt-10 space-y-4">
    <h2 class="text-xl font-bold">
      ความคิดเห็น (<span id="comment_count"><%= @post.comments.count %></span>)
    </h2>

    <div id="comments" class="space-y-3">
      <%= render @comments %>
    </div>

    <%= render "comments/form", post: @post, comment: @comment %>
  </section>
  • สาม id ที่ตัวหนา = ป้ายบนกล่องที่จะถูกสั่งเปลี่ยนทีหลัง (comment_count · comments · และ comment_form ซึ่งอยู่ในแม่พิมพ์ฟอร์ม) · จำสามชื่อนี้ไว้ ใช้ทั้งบท
  • <span> = กล่องเล็กที่ครอบเฉพาะตัวเลข · มีไว้ให้เปลี่ยนแค่ตัวเลขได้โดยไม่แตะคำว่า "ความคิดเห็น"
  • <%= render @comments %> = "ใช้แม่พิมพ์ comments/_comment กับทุกชิ้น" (Rails เดาชื่อแม่พิมพ์จากชนิดของแฟ้ม — บท 123) · ยังไม่มีคอมเมนต์ก็ไม่วาดอะไร
  • <%= render "comments/form", post: @post, comment: @comment %> = ใช้แม่พิมพ์ฟอร์ม (สร้างข้างล่าง) และยื่นของใส่มือสองอย่าง
  • คลาส Tailwind (บท 72): mt-10 = เว้นที่ว่างด้านบน · space-y-4 / space-y-3 = เว้นระยะแนวตั้งระหว่างของข้างใน · text-xl font-bold = ตัวใหญ่ หนา

แม่พิมพ์คอมเมนต์หนึ่งชิ้น — สร้างโฟลเดอร์ app/views/comments/ แล้วสร้างไฟล์ _comment.html.erb: 

<%# locals: (comment:) -%>
<article id="<%= dom_id comment %>" class="card bg-base-100 shadow-sm">
  <div class="card-body p-4 gap-1">
    <p class="text-sm text-base-content/70">
      <span class="font-semibold text-base-content"><%= comment.author_name %></span>
      · <%= time_ago_in_words(comment.created_at) %> ago
    </p>
    <p class="whitespace-pre-line break-words"><%= comment.body %></p>
  </div>
</article>
  • บรรทัด 1 strict locals: แม่พิมพ์นี้รับ comment อย่างเดียว (แบบเดียวกับ _post ในบท 126) · -%> ที่มีขีด = ไม่ทิ้งบรรทัดว่างไว้ใน HTML
  • id="<%= dom_id comment %>" → ได้ comment_1 · comment_2 … ป้ายเลขถ้วยของแต่ละชิ้น (เจอแล้วในบท 131)
  • <%= time_ago_in_words(comment.created_at) %> ago = helper "ผ่านมานานแค่ไหน" ได้แค่ less than a minute ไม่มีคำว่า ago · เลยพิมพ์ ago ต่อท้ายเอง (บท 124)

บท 131 (Frame) เหมือนพนักงานยกถ้วยใหม่มาเปลี่ยนถ้วยเดียวบนโต๊ะ · Turbo Stream เหมือนครัวยื่นใบสั่งงานหลายข้อให้พนักงานเสิร์ฟถือไปที่โต๊ะ: "① วางจานนี้ต่อท้ายแถวจานคอมเมนต์ · ② เปลี่ยนป้ายจำนวนเป็น 2 · ③ เก็บกระดาษสั่งที่เขียนแล้ว วางใบใหม่ที่ว่าง" · พนักงานทำตามทีละข้อ โต๊ะเดิม ผ้าปูเดิม ลูกค้าไม่ต้องลุก · ของที่วางลงโต๊ะครัวจัดจานเสร็จแล้วทุกชิ้น (HTML) พนักงานไม่ได้ปรุงอะไรเอง

ที่ไม่เหมือนกัน: พนักงานคนนี้ไม่ถามกลับ — ถ้าหาโต๊ะ/ป้ายตามที่ใบสั่งเขียนไม่เจอ เขาข้ามข้อนั้นไปเงียบ ๆ ไม่มีใครรู้ (ภารกิจท้ายบทจะเจอกับตัว) · และใบสั่งไปถึงแค่โต๊ะที่สั่ง (แท็บที่กดส่ง) · โต๊ะอื่นที่เปิดหน้าเดียวกันอยู่ไม่รู้เรื่อง (ลองแล้ว: เปิดสองแท็บ ส่งจากแท็บซ้าย แท็บขวายังเป็นตัวเลขเดิมจนกว่าจะรีเฟรช — ทำให้ทุกโต๊ะได้ยินคือบท 133)

เทียบกับ React ที่เพิ่งเรียน (บท 73): ถ้าทำหน้านี้ด้วย React เราจะได้ข้อมูลคอมเมนต์ใหม่มาเป็น JSON แล้วต้องเขียนเองในเบราว์เซอร์ว่า "เติมเข้า state รายการ · บวกตัวนับ 1 · ล้าง state ของฟอร์ม" — สามบรรทัด setXxx(…) และเบราว์เซอร์ต้องจำข้อมูลชุดที่สอง (สมุดจดบนโต๊ะลูกค้า) · แบบ Turbo Stream เบราว์เซอร์ไม่ได้จำอะไรเลย · ตัวเลข 2 มาจาก server นับในตู้ใหม่ทุกครั้ง · นี่คือประโยคหลักข้อ ① ของวัน: ถ้า server เป็นเจ้าของข้อมูลชุดเดียว บั๊ก "ตัวเลขไม่ตรงกัน" ก็ไม่มี

Rails รู้ได้ยังไงว่าต้องตอบเป็นใบสั่งงาน

ใบสั่ง (request) ทุกใบมีบรรทัดข้อมูลแนบหัวกระดาษที่คนใช้เว็บมองไม่เห็น เรียกว่า header · หนึ่งในนั้นชื่อ Accept = "รับคำตอบแบบไหนได้บ้าง เรียงตามที่อยากได้" · ตอนกดส่งฟอร์ม Turbo เป็นคนส่งแทนเบราว์เซอร์ (บท 130) และเขียน Accept ให้เอง · ค่าที่ดักได้จริงใน Chrome: 

Accept: text/vnd.turbo-stream.html, text/html, application/xhtml+xml

ตัวแรก text/vnd.turbo-stream.html = "ขอเป็นใบสั่งงานก่อนนะ" · ถ้าไม่มีค่อยเอาหน้าเว็บ (text/html) · Rails อ่านแล้วจดใน log ว่า Processing by CommentsController#create as TURBO_STREAM → respond_to จึงเลือกทาง format.turbo_stream

เคยเจอแล้วฝั่ง Go: header Accept: application/json ในบท 35 คือของชิ้นเดียวกัน — ตอนนั้น client ขอ JSON · ตอนนี้ Turbo ขอ "ใบสั่งงาน" · ส่วน respond_to ก็คือ "อ่าน Accept แล้วเลือกวิธีตอบ" ที่ Rails ทำให้ แทนที่เราจะต้องเขียน if ดู header เอง

เทียบกับร้านอาหาร

ใบสั่งอาหารมีช่องเล็ก ๆ ให้ติ๊ก "ขอแบบไหน": ☑ ขอเป็นใบสั่งงานให้พนักงานเปลี่ยนของบนโต๊ะ · ☐ ถ้าไม่ได้ เสิร์ฟจานใหม่ทั้งชุด · หัวหน้าเชฟ (respond_to) ดูช่องนี้แล้วเลือกเตรียมให้ตรง — ครัวเดียวกัน ทำอาหารเหมือนกัน (บันทึกคอมเมนต์เหมือนกัน) ต่างกันแค่วิธีเสิร์ฟ

ที่ไม่เหมือนกัน: ลูกค้า (คนที่ใช้เว็บ) ไม่ได้ติ๊กเอง — Turbo ติ๊กให้ · ถ้าเบราว์เซอร์ปิด JavaScript ก็ไม่มี Turbo ไม่มีใครติ๊ก · ใบสั่งไปแบบธรรมดา → Rails เลือก format.html → redirect_to ทั้งหน้า + ข้อความ "เพิ่มความคิดเห็นแล้ว" · ลองแล้วใน Chrome ที่ปิด JavaScript: ส่งได้ คอมเมนต์ขึ้น แค่หน้าโหลดใหม่ทั้งหน้า (log: as HTML · 302 Found) = เว็บยังใช้ได้แม้ JavaScript พัง

Accept header
บรรทัดในใบสั่ง (request) ที่บอกว่ารับคำตอบชนิดไหนได้ · ถาม AI ได้ว่า "request นี้ Accept อะไร ทำไม Rails ถึงตอบเป็น HTML แทน turbo stream"

respond_to
ตัวเลือกวิธีตอบตามชนิดที่ลูกค้าขอ · พูดกับ senior ได้ว่า "create มี respond_to สองทาง: turbo_stream ใช้ template, html ทำ redirect เป็น fallback"

ในไฟล์เราใช้แค่สามคำสั่ง · ของจริงมีแปด (สไลด์หน้า 44 นับ before/after เป็นข้อเดียวเลยได้ 7 แถว) · ทุกตัวในตารางนี้ลองแล้วใน Chromeกับหน้าคอมเมนต์ของเรา:

คำสั่งทำอะไรกับกล่อง targetในร้านอาหารใช้ตอนไหน
appendเติมของใหม่ต่อท้ายข้างในกล่องวางจานใหม่ปลายแถวคอมเมนต์ใหม่ (เรียงเก่า→ใหม่)
prependเติมของใหม่ไว้บนสุดข้างในกล่องวางจานใหม่หัวแถวรายการที่ของใหม่อยู่บน เช่น แจ้งเตือน
replaceเอากล่องทั้งกล่องออก (รวมตัวมันเองและ id) วางของใหม่แทนยกถ้วยทั้งใบออก วางใบใหม่ฟอร์ม · การ์ดที่ถูกแก้ทั้งใบ
updateเปลี่ยนเฉพาะของข้างใน กล่องเดิมอยู่ที่เดิมเทของในถ้วยออก เติมใหม่ ถ้วยเดิมตัวเลข · ข้อความสั้น ๆ
removeลบกล่องทิ้ง (ไม่ต้องมี <template>)เก็บจานออกจากโต๊ะลบคอมเมนต์
before / afterแทรกของใหม่ข้างนอกกล่อง ก่อน / หลังมันวางจานข้าง ๆ ถ้วย ไม่ใส่ในถ้วยข้อความแจ้งเหนือฟอร์ม (ภารกิจ)

คอมเมนต์นั้นหายจากหน้าทันที · กดรีเฟรชแล้วมันกลับมา เพราะ Turbo Stream เปลี่ยนแค่ HTML บนจอ ไม่ได้แตะตู้ — การลบจริงต้องผ่าน controller เสมอ

replace กับ update — ต่างกันคำเดียว แต่พังคนละแบบ

สองคำนี้คนสับสนมากที่สุด · กติกาจำง่าย: ป้าย id ติดอยู่ที่ตัวกล่อง · update เก็บกล่อง (และป้าย) ไว้ เปลี่ยนแค่ของข้างใน · replace ยกกล่องพร้อมป้ายทิ้ง → ของใหม่ต้องมีป้ายเดิมติดมาเอง ไม่งั้นครั้งหน้าหาไม่เจอ

เทียบกับร้านอาหาร

ถ้วยน้ำจิ้มมีป้ายเลข "comment_count" แปะที่ตัวถ้วย · update = เทน้ำจิ้มเก่าออก เติมใหม่ ถ้วยใบเดิม ป้ายยังอยู่ · replace = ยกถ้วยทั้งใบไปล้าง วางของใหม่ลงแทน — ถ้าของใหม่เป็นแค่ "น้ำจิ้มเปล่า ๆ ไม่มีถ้วย" ป้ายก็หายไปกับถ้วยเก่า · ใบสั่งงานรอบหน้าที่เขียนว่า "เปลี่ยนน้ำจิ้มในถ้วย comment_count" พนักงานก็หาไม่เจอ

ที่ไม่เหมือนกัน: ในร้านจริงพนักงานจะเดินกลับมาถามว่า "ถ้วยเบอร์นี้ไม่มีครับ" · Turbo ไม่ถาม ไม่ฟ้อง — console ว่างเปล่า หน้าดูปกติ แค่ตัวเลขค้าง

แก้บรรทัด 3 ของ create.turbo_stream.erb จาก update เป็น replace แบบนี้ (ทดลองชั่วคราว):

<%= turbo_stream.replace "comment_count", @post.comments.count %>

ศัพท์ที่เอาไปคุยต่อได้
replace (outerHTML)
แทนทั้ง element รวมแท็กของมันเอง · ภาษา JavaScript เรียกส่วนนี้ว่า outerHTML · บอก AI ได้ว่า "ฟอร์มมี id บน <form> เองต้องใช้ replace และ partial ต้องคืน id เดิม"
update (innerHTML)
แทนเฉพาะเนื้อข้างใน element · JavaScript เรียกว่า innerHTML · เหมาะกับตัวเลข/ข้อความในกล่องที่มี id อยู่แล้ว
target ไม่มีในหน้า
Turbo ข้ามคำสั่งนั้นไปโดยไม่ฟ้อง · เวลาตัวเลขค้างให้ถามตัวเองก่อนว่า "หลังคำสั่งรอบที่แล้ว id นี้ยังอยู่ในหน้าไหม"

ก่อนกดเฉลย: ข้อ 2 เห็นข้อความสำเร็จไหม เพราะอะไร? ข้อ 3 ส่งสองครั้งแล้วเห็นข้อความกี่กล่อง เพราะอะไร?

ข้อ 2 — ไม่มีข้อความโผล่เลย (ตรวจใน Chrome: ทั้งหน้าไม่มีกล่อง .alert สักกล่อง · Console ว่าง) · แต่คอมเมนต์ต่อท้าย ตัวนับเพิ่ม ฟอร์มว่าง ตามปกติ · เหตุผล: ในหน้าของเราไม่มีกล่องไหนชื่อ id="flash" (layout ของแอปนี้ไม่มี · ข้อความ notice อยู่ในแต่ละหน้าด้วย id="notice" และโผล่เฉพาะตอนมีข้อความ) → พนักงานหาป้ายไม่เจอ ข้ามข้อนี้เงียบ ๆ = "ที่ไม่เหมือนกัน" ของภาพใบสั่งงาน

ข้อ 3 — ข้อความขึ้นเหนือฟอร์ม · ส่งครั้งที่สองได้สองกล่องซ้อนกัน (ผลจริงใน Chrome: ครั้งแรก 1 กล่อง ครั้งที่สอง 2 กล่อง "เพิ่มความคิดเห็นแล้ว") · เพราะ before = "แทรกเพิ่มข้างนอกกล่อง" ทุกครั้งที่ส่ง ไม่ได้แทนของเดิม · กล่อง comment_form ยังมีอยู่เสมอ (ข้อ ③ วางฟอร์มใหม่ที่มี id เดิมกลับมา) จึงหาเจอทุกรอบ

ถ้าอยากให้มีข้อความเดียวเสมอ ทางหนึ่งคือเตรียมกล่องว่างที่มี id ไว้ในหน้า show แล้วใช้ update กับกล่องนั้น · บทนี้ไม่ทำต่อ — เป้าหมายคือเห็นว่าคำสั่งต่างกันให้ผลต่างกัน และ target ต้องมีอยู่จริง

  • ข้อ 3 แล้วข้อความยังไม่ขึ้น — สะกด "comment_form" ผิด (เช่น comments_form) · target ผิดตัวเดียวก็ถูกข้ามเงียบ ๆ เหมือนข้อ 2
  • git status หลังข้อ 4 ยังเห็นไฟล์อื่น — คุณยังไม่ได้ commit งานของบทนี้ก่อนเริ่มภารกิจ · อย่า git restore . ทั้งโฟลเดอร์ จะลบงานทั้งบท · git add . && git commit ก่อน

ทดสอบความเข้าใจ

ผู้ใช้กดส่งคอมเมนต์ แล้วต้องเปลี่ยน 3 จุดในหน้าเฉพาะแท็บของคนที่กดส่ง · ควรใช้อะไร? (ดัดแปลงจาก Quiz C สไลด์หน้า 51)

ตัวเลือกที่ 2 ถูก — หลายกล่อง + เฉพาะคนกด = ใบสั่งงานที่ตอบกลับคำขอของคนนั้น

ตัวเลือกที่ 1 Frame เปลี่ยนได้แค่กรอบเดียว รายการกับตัวนับอยู่นอกกรอบจึงไม่ขยับ · ตัวเลือกที่ 3 broadcast คือส่งให้ทุกคน — เกินโจทย์ (และคือข้อที่สไลด์บอกว่าคนสับสนกับข้อนี้มากที่สุด เรื่องของบท 133) · ตัวเลือกที่ 4 Turbo Drive ได้หน้าใหม่ทั้งหน้าหลัง redirect ไม่ใช่การเปลี่ยนสามจุด

จุดที่ต้องจำ: ถามสองข้อ — เปลี่ยนกี่กล่อง (1 = Frame · หลาย = Stream) และเปลี่ยนให้ใคร (คนกด = ตอบฟอร์ม · ทุกคน = broadcast)

ทำไมบรรทัด "ล้างฟอร์ม" ใน create.turbo_stream.erb ใช้ replace "comment_form" ไม่ใช่ update "comment_form"?

ตัวเลือกที่ 3 ถูก — แม่พิมพ์ _form สร้าง <form id="comment_form"> ใหม่ทั้งใบ · replace เอาใบเก่าออกแล้ววางใบใหม่ (id เดิมติดมา ส่งรอบหน้าก็หาเจอ) · update จะเอาใบใหม่ไปใส่ข้างในใบเก่า (ลองแล้ว: ได้ฟอร์มซ้อนกันสองชั้น)

ตัวเลือกที่ 1 ผิด — update ใส่ HTML อะไรก็ได้ · ตัวเลือกที่ 2 ผิด — ช่องว่างเพราะเราส่ง Comment.new ไปวาด ไม่ใช่เพราะคำสั่ง · ตัวเลือกที่ 4 ผิด — ไม่มีคำสั่งไหนในแปดตัวที่โหลดหน้าใหม่ ยกเว้น refresh

จุดที่ต้องจำ: id อยู่บนกล่องที่จะถูกแทนทั้งก้อน → replace + ของใหม่ต้องมี id เดิม · id อยู่บนกล่องที่แค่เปลี่ยนไส้ → update

Rails รู้ได้ยังไงว่าต้องตอบด้วย create.turbo_stream.erb แทนที่จะ redirect_to?

ตัวเลือกที่ 1 ถูก — ค่าที่ดักได้จริง text/vnd.turbo-stream.html, text/html, application/xhtml+xml · log จึงเขียน as TURBO_STREAM แล้ว respond_to เลือก format.turbo_stream

ตัวเลือกที่ 2 ผิด — ช่องซ่อนในฟอร์มมีแค่ authenticity_token (ดูได้ใน Response) · ตัวเลือกที่ 3 ผิด — ปิด JavaScript แล้วไฟล์ก็ยังอยู่ แต่ Rails ตอบ redirect (ลองแล้ว: as HTML · 302) · ตัวเลือกที่ 4 ผิด — URL จริงคือ /posts/30/comments ไม่มีนามสกุล

จุดที่ต้องจำ: ลูกค้าบอก "ขอแบบไหน" ผ่าน Accept · Turbo ติ๊กให้ · ไม่มี Turbo ก็ได้หน้าเต็มแบบเดิม

หลังส่งคอมเมนต์ ตัวเลขใน ความคิดเห็น (2) มาจากไหน?

ตัวเลือกที่ 4 ถูก — ใน response เห็น <turbo-stream action="update" target="comment_count"><template>2</template> และใน log เห็น Comment Count … SELECT COUNT(*)

ตัวเลือกที่ 1–3 คือการให้เบราว์เซอร์มี "สมุดจดเล่มที่สอง" ซึ่งเป็นสิ่งที่ Hotwire ตั้งใจเลี่ยง · ถ้าคนอื่นเพิ่มคอมเมนต์ระหว่างนั้น การบวกเองจะได้เลขผิด ส่วนการนับจากตู้ได้เลขจริงเสมอ

จุดที่ต้องจำ: server เป็นเจ้าของข้อมูลชุดเดียว เบราว์เซอร์แค่วางสิ่งที่ server จัดจานมาให้ → ไม่มีบั๊ก sync
