broadcast — คอมเมนต์เด้งขึ้นทุกแท็บ และ Turbo เหมาะกับงานแบบไหน

~22 นาที · ควรผ่าน บทเรียน 132 (Turbo Streams · ฟอร์มคอมเมนต์) และ บทเรียน 112 (callback · after_commit) มาก่อน

บท 132 เราส่งคอมเมนต์แล้วหน้าของเราเปลี่ยนทันที · แต่ถ้าเพื่อนเปิดบทความเดียวกันอยู่อีกเครื่อง เขาจะไม่เห็นอะไรเลยจนกว่าจะกด refresh
อ่านจบบทนี้ คุณจะทำให้คอมเมนต์ใหม่เด้งขึ้นเองในทุกแท็บที่เปิดบทความนั้นอยู่ ด้วยโค้ดแค่ 3 บรรทัด · อ่าน log ออกว่าข้อความวิ่งไปถึงใครบ้าง · รู้ว่าบรรทัดที่ดูง่ายนี้มี "ราคา" อะไร · และตอบได้ว่างานแบบไหนควรใช้ Turbo งานแบบไหนไม่ควร

🔁 ทวนก่อนเริ่ม — คำจากบทก่อน ๆ ที่บทนี้ใช้

  • Turbo Stream (บท 132) — "ใบสั่งงานให้พนักงานเสิร์ฟ" หน้าตาแบบ <turbo-stream action="append" target="comments"> = "เอาของในซองไปต่อท้ายกล่องที่ id เป็น comments" · ในบท 132 ใบสั่งนี้มาจาก create.turbo_stream.erb และส่งกลับไปให้แท็บที่กดส่งเท่านั้น
  • dom_id (บท 131) — ตั้งป้ายเลขถ้วยให้ HTML เช่นคอมเมนต์เลข 8 ได้ id="comment_8"
  • callback (บท 112) — กฎ "ทำทุกครั้ง" ที่ติดไว้ข้างตู้ · after_commit = ทำหลังตู้เซ็นรับแฟ้มแล้วเท่านั้น
  • transaction (บท 111) — กล่อง "ทำทั้งหมด หรือไม่ทำเลย" · log เห็นเป็น BEGIN … COMMIT (ยืนยัน) หรือ ROLLBACK (ยกเลิกทั้งกล่อง)
  • หน้า show ของบทความ (บท 132) — มีจุดที่มี id อยู่ 3 จุด: ตัวนับ #comment_count · รายการ #comments · ฟอร์ม #comment_form

🧰 ตรวจด้วย Ruby 4.0.9 · Rails 8.1.4 · turbo-rails 2.0.23 (Turbo 8.0.23) · PostgreSQL 18 (สไลด์และ repo ของอาจารย์ใช้ Ruby 4.0.5–4.0.6 · Rails 8.1.3 — รุ่นแก้บั๊กในสายเดียวกัน)

🗂 โค้ดเริ่มจาก: แอปหลังจบบท 132 (คอมเมนต์ + ฟอร์มที่ตอบด้วย Turbo Stream · ตามไม่ทันดูบท 132) · บทนี้เพิ่มโค้ดจริง 3 บรรทัดแล้วเก็บไว้ (commit ท้ายภารกิจ) · ส่วนการทดลองอื่น ๆ ในบทให้ git restore ทิ้ง · branch day3-c-done ของอาจารย์มีไว้ตามทันได้ แต่หน้าตาไฟล์ต่างจากบทเรียน (ใช้ i18n และข้อมูลคนละชุด)

ผลทุกก้อนรันจริงแล้วก็อปมา · ตัดบรรทัดที่ไม่เกี่ยวเป็น … และตัดคอมเมนต์ SQL /*application=…*/ ท้ายบรรทัดออก · เลขบทความ · เลขคอมเมนต์ · Job ID · เวลา (ms) · ชื่อช่องยาว ๆ ที่ขึ้นต้น Z2lk · ลายเซ็นหลัง -- ของคุณจะไม่ตรงกับในบท

ปัญหา: แท็บอื่นไม่รู้ว่ามีคอมเมนต์ใหม่

ลองนึกภาพ: คุณเปิดบทความ "ราดหน้าหมูหมัก" ไว้สองแท็บ · ส่งคอมเมนต์จากแท็บซ้าย แท็บซ้ายเปลี่ยนทันที (บท 132) · แต่แท็บขวานิ่งสนิท ต้องกด refresh เองถึงจะเห็น

เหตุผลอยู่ที่วิธีคุยของเว็บปกติ (HTTP): เบราว์เซอร์ต้องถามก่อน server ถึงจะตอบ · ถามหนึ่งครั้งได้คำตอบหนึ่งครั้ง แล้วจบ · server ไม่มีทางวิ่งไปบอกแท็บขวาเองได้ เพราะแท็บขวาไม่ได้ถามอะไรอยู่

สิ่งที่เราอยากได้เรียกว่า real-time — ข้อมูลใหม่วิ่งมาหาเราเองทันทีที่เกิด โดยเราไม่ต้องกดอะไร · ทางแก้คือให้เบราว์เซอร์ต่อสายค้างไว้กับ server ตั้งแต่เปิดหน้า · สายแบบนี้ชื่อ WebSocket · ต่อครั้งเดียวแล้วคุยได้สองทาง ใครมีเรื่องก็พูดได้เลย ไม่ต้องรออีกฝั่งถาม

📢 เทียบให้เห็นภาพ — ใบสั่งทีละใบ vs สายที่ต่อค้างไว้

HTTP ปกติเหมือนใบสั่งอาหาร: โต๊ะยื่นใบสั่ง → ครัวทำ → เสิร์ฟจาน → จบ · ครัวไม่เดินไปหาโต๊ะไหนเองถ้าโต๊ะนั้นไม่ได้สั่ง · โต๊ะขวาจะรู้ว่ามีเมนูใหม่ก็ต่อเมื่อยื่นใบสั่งไปถามเอง (กด refresh)

WebSocket เหมือนร้านที่ติดลำโพงเสียงตามสายไว้ทุกโต๊ะ · สายต่อค้างไว้ตลอดที่ลูกค้านั่งอยู่ · พอครัวมีข่าว ประกาศครั้งเดียว ทุกโต๊ะที่เปิดลำโพงได้ยินพร้อมกัน

ที่ไม่เหมือนกัน: เสียงตามสายจริงเป็นทางเดียว (ครัวพูด โต๊ะฟัง) แต่ WebSocket คุยได้สองทาง — แค่ในบทนี้เราใช้ทางเดียว · และโต๊ะที่เพิ่งมานั่งไม่ได้ยินประกาศที่ผ่านไปแล้ว — เขาเห็นคอมเมนต์เก่าได้เพราะตอนเปิดหน้า Rails ดึงจากฐานข้อมูลมาให้ ไม่ใช่เพราะลำโพงเล่นย้อนหลัง

เทียบกับฝั่ง React ที่เพิ่งเรียน: ใน บท 74 การ "เปิด WebSocket" คือตัวอย่างงานที่ต้องเขียนใน useEffect เอง พร้อม cleanup ตอนปิด · ใน Rails บทนี้เราไม่เขียน JavaScript สักบรรทัด — Turbo เปิดและปิดสายให้เอง

🗣 ศัพท์ชุดแรก
real-time
ข้อมูลใหม่ไปโผล่ที่หน้าจอคนอื่นทันทีโดยเขาไม่ต้องกดอะไร · พิมพ์บอก AI ได้ว่า “make new comments appear in real time for everyone viewing the post”
WebSocket
การเชื่อมต่อที่เปิดค้างไว้ระหว่างเบราว์เซอร์กับ server คุยได้สองทาง · ต่างจาก HTTP ที่ถามหนึ่งครั้งตอบหนึ่งครั้ง · ถาม senior ได้ว่า “ตอนขึ้น server จริง WebSocket ต้องตั้งค่าอะไรเพิ่มไหม”
Action Cable
ส่วนของ Rails ที่จัดการ WebSocket ให้ (รับสาย · จำว่าใครฟังช่องไหน · ส่งข้อความ) · เปิดอยู่ที่ path /cable โดยไม่ต้องแก้ routes · ถาม AI ได้ว่า “how does Action Cable know which browser is listening to which stream?”

สองชิ้นที่ต้องมี — คนประกาศ กับ โต๊ะที่เปิดลำโพง

real-time ใน Rails ต้องมีสองฝั่งเสมอ: ฝั่งที่ประกาศ (เกิดคอมเมนต์ใหม่ → ส่งข่าว) กับฝั่งที่ฟัง (หน้าเว็บที่รอรับข่าว) · ขาดฝั่งไหนก็ไม่ทำงาน · เราจะใส่ทีละฝั่ง แล้วดูผลจริงแต่ละขั้น

ชิ้นที่ 1 — คนประกาศ: broadcasts_to :post ใน model

เปิดไฟล์ app/models/comment.rb แล้วเพิ่ม 2 บรรทัดใต้ belongs_to :post พร้อมบรรทัดว่างคั่นก่อน validates ให้หน้าตาเป็นแบบนี้ (บรรทัดคอมเมนต์ # พิมพ์ตามไว้ด้วย ไฟล์จะได้ตรงกับบทเรียน):

class Comment < ApplicationRecord
  belongs_to :post

  # คอมเมนต์ใหม่เด้งขึ้นทุกแท็บที่เปิดหน้าโพสต์นี้ (ส่งต่อให้ job · หลัง commit)
  broadcasts_to :post

  validates :author_name, presence: true, length: { maximum: 50 }
  validates :body, presence: true, length: { maximum: 1000 }
end
  • broadcasts_to — แปลว่า "ทุกครั้งที่คอมเมนต์ถูกสร้าง · แก้ · ลบ ให้ประกาศข่าว" · broadcast = ประกาศถึงทุกคนที่ฟังอยู่
  • :post — "ประกาศในช่องของบทความที่คอมเมนต์นี้อยู่" · Rails เรียก comment.post แล้วใช้บทความนั้นเป็นชื่อช่อง · คอมเมนต์ของบทความ 23 จึงประกาศในช่องของบทความ 23 เท่านั้น คนเปิดบทความ 24 ไม่ได้ยิน
  • ข่าวที่ประกาศตอนสร้างคือใบสั่ง Turbo Stream แบบเดียวกับบท 132: "append คอมเมนต์นี้ ต่อท้ายกล่อง comments" · Rails เดาให้หมด: ใช้ partial comments/_comment (ชื่อตาม model) และ target comments (ชื่อ model แบบพหูพจน์)
  • บรรทัดคอมเมนต์ (ส่งต่อให้ job · หลัง commit) — job คืองานที่ฝากไว้ให้ทำทีหลัง (ละเอียดใน Day 3 Part 2 ซึ่งยังไม่มา) · commit คือจังหวะ COMMIT ที่ตู้เซ็นรับแฟ้ม (บท 111) · ทั้งสองอย่างจะเห็นด้วยตาในหัวข้อ "อ่าน log" ข้างล่าง

ไม่ต้อง restart server — แก้ไฟล์ใน app/ ตอน development Rails โหลดใหม่ให้เอง

ตอนนี้มีแค่คนประกาศ ยังไม่ได้แตะหน้า show เลย · เปิดบทความเดียวกันสองแท็บ ส่งคอมเมนต์จากแท็บซ้าย — แท็บขวาจะเห็นคอมเมนต์ใหม่ไหม?

ไม่เห็น — ผลจริงจาก Chrome สองแท็บ (บทความเลข 30 · สถานะก่อนและหลังกดส่ง 2.5 วินาที):

before B {"marker":"B","count":"0","n":0,"ids":[],"source":false,"connected":null}
after  A {"marker":"A","count":"1","n":1,"ids":["comment_1"],"source":false,"connected":null}

วิธีอ่าน: count = เลขในตัวนับ · n = จำนวนคอมเมนต์ในกล่อง · ids = id ของคอมเมนต์ในกล่อง · source / connected = หน้านี้มี "ลำโพง" หรือยัง และต่อสายติดไหม (เดี๋ยวรู้จัก) · marker = ป้ายที่เราแปะไว้ในหน้าด้วย JavaScript ก่อนกดส่ง ถ้าหน้าโหลดใหม่ป้ายจะหาย — ยังอยู่ทุกรอบ = ไม่มีแท็บไหนโหลดหน้าใหม่

แท็บซ้าย (A) ได้คอมเมนต์จากคำตอบของฟอร์มตามบท 132 · แท็บขวา (B) นิ่ง · (การทดลองแต่ละรอบในบทนี้ใช้บทความคนละเลข ตัวนับจะได้เริ่มที่ 0 ทุกรอบ)

ชิ้นที่ 2 — เปิดลำโพง: turbo_stream_from @post ในหน้า show

เปิด app/views/posts/show.html.erb · หา <section class="mt-10 space-y-4"> (ส่วนความคิดเห็นจากบท 132) แล้วเพิ่ม 2 บรรทัดนี้ (บรรทัดที่สองคือบรรทัดว่าง) เป็นบรรทัดแรกในนั้น:

  <section class="mt-10 space-y-4">
    <%= turbo_stream_from @post %>

    <h2 class="text-xl font-bold">
      ความคิดเห็น (<span id="comment_count"><%= @post.comments.count %></span>)
    </h2>
  • turbo_stream_from @post — "หน้านี้ขอฟังช่องของบทความนี้" · ต้องเป็นของชิ้นเดียวกับที่ model ประกาศ (:post ↔ @post) ไม่งั้นต่างคนต่างอยู่คนละช่อง
  • ใช้ <%= %> (มีเครื่องหมาย =) เพราะมันต้องวางแท็กลงบนจาน — ลืม = แล้วไม่มีลำโพง (บท 122)
  • วางไว้ตรงไหนในหน้าก็ได้ · ที่วางใน <section> เพราะอยู่ใกล้ส่วนที่มันจะเปลี่ยน อ่านแล้วเข้าใจ · แท็กนี้ไม่มีหน้าตาให้เห็นบนจอ

📻 เทียบให้เห็นภาพ — ช่องประกาศของแต่ละเมนู

ร้านมีเสียงตามสายหลายช่อง ช่องละหนึ่งบทความ · broadcasts_to :post คือกฎของครัว: "มีคอมเมนต์ใหม่เมื่อไหร่ ประกาศในช่องของบทความนั้น" · turbo_stream_from @post คือโต๊ะที่หมุนลำโพงไปที่ช่องของบทความที่กำลังดู · ข่าวที่ประกาศเป็นใบสั่งงานแบบเดียวกับบท 132 พนักงานเสิร์ฟ (Turbo) ที่โต๊ะได้ยินแล้วเอาไปจัดจานตามนั้นทันที

ที่ไม่เหมือนกัน: ลำโพงจริงหมุนผิดช่องก็ยังได้ยินเสียงอะไรสักอย่าง · ในเว็บ ถ้าชื่อช่องสองฝั่งไม่ตรงกัน หรือลืมลำโพง ไม่มีเสียงอะไรเลย และไม่มีใครแจ้ง error — ต้องเปิดสองแท็บทดสอบเองถึงจะรู้

ให้ตัวนับในแท็บอื่นขยับด้วย — บรรทัดที่สาม

กลับไปที่ app/models/comment.rb เพิ่มอีก 2 บรรทัดต่อจาก broadcasts_to :post (ก่อนบรรทัดว่าง) · ไฟล์ทั้งไฟล์จะเป็นแบบนี้ (ตรงกับโค้ดของบทเรียนทุกบรรทัด):

class Comment < ApplicationRecord
  belongs_to :post

  # คอมเมนต์ใหม่เด้งขึ้นทุกแท็บที่เปิดหน้าโพสต์นี้ (ส่งต่อให้ job · หลัง commit)
  broadcasts_to :post
  # ตัวนับในแท็บอื่นต้องเปลี่ยนตามด้วย
  after_create_commit -> { broadcast_update_later_to post, target: "comment_count", html: post.comments.count }

  validates :author_name, presence: true, length: { maximum: 50 }
  validates :body, presence: true, length: { maximum: 1000 }
end

แกะบรรทัดยาวทีละท่อน:

  • after_create_commit — callback (บท 112) "หลังตู้เซ็นรับคอมเมนต์ใหม่แล้ว" · เฉพาะตอนสร้าง ไม่รวมแก้/ลบ
  • -> { … } — ก้อนโค้ดที่เก็บไว้รันทีหลัง (Ruby เรียกว่า lambda) · คล้าย block { |x| … } ที่ใช้กับ each แต่ตั้งไว้ก่อน รอ Rails เรียกตอนถึงจังหวะ
  • broadcast_update_later_to post — "ประกาศในช่องของบทความนี้ ให้เปลี่ยนเนื้อใน (update) ของ…" · คำว่า later = ฝากเป็นงานไว้ให้ทำต่อ ไม่ทำตรงนี้ (เดี๋ยวเห็นใน log)
  • post (ไม่มี @) — โค้ดนี้อยู่ใน model ของคอมเมนต์ · post เฉย ๆ จึงแปลว่า "บทความของคอมเมนต์ตัวนี้" (เหมือนเขียน comment.post ใน console) ได้มาจาก belongs_to :post · @post เป็นของ controller/view ใช้ใน model ไม่ได้
  • target: "comment_count" — ของที่จะเปลี่ยนคือ <span id="comment_count"> ที่มีอยู่แล้วตั้งแต่บท 132
  • html: post.comments.count — เนื้อใหม่ = นับคอมเมนต์ของบทความนี้ใหม่จากฐานข้อมูล

⚠️ html: ใส่ของลงใบสั่งตรง ๆ ไม่ใส่ซองใส (ไม่ escape — ทวน XSS บท 125) · เราลองส่ง html: "<b>ตัวหนา</b>" แล้ว log ได้ <template><b>ตัวหนา</b></template> เป็นแท็กจริง · ตัวเลขจาก count ปลอดภัย แต่ห้ามส่งข้อความที่ผู้ใช้พิมพ์ผ่าน html: — ของแบบนั้นให้ใช้ partial ซึ่ง escape ให้เอง

ทดลองรอบที่สาม (บทความเลข 28) — ผลจริง:

after  B {"marker":"B","count":"1","n":1,"ids":["comment_3"],"source":true,"connected":true}

แท็บขวา "count":"1" แล้ว — ตัวนับขยับตาม

ไม่ต้องรัน tailwindcss:build ใหม่ (ไม่มีคลาส CSS ใหม่) และไม่มี gem หรือ migration ใหม่

แท็บที่กดส่งเอง ได้ใบสั่งสองใบ — ทำไมคอมเมนต์ไม่ซ้ำ

มีเรื่องแปลกที่ต้องสังเกต: แท็บซ้ายก็เปิดลำโพงอยู่เหมือนกัน · ตอนกดส่ง มันจึงได้ใบสั่ง "append คอมเมนต์" สองใบ — ใบแรกจากคำตอบของฟอร์ม (create.turbo_stream.erb บท 132) ใบที่สองจากเสียงตามสาย

แท็บซ้ายได้ append คอมเมนต์ใบเดียวกันสองรอบ — ในกล่องจะมีคอมเมนต์กี่อัน? แล้วถ้าลบ id="<%= dom_id comment %>" ออกจาก _comment.html.erb ล่ะ?

ผลจริง — เราดักดูว่ามีอะไรถูกใส่เข้ากล่อง #comments บ้าง (appended) เทียบกับของที่เหลือจริง:

บรรทัดล่าง: comment_3 ถูกใส่เข้ากล่องสองรอบจริง · บรรทัดบน: แต่ในกล่องเหลืออันเดียว ("n":1)

พอลบ id ออกจาก partial ชั่วคราว (ใส่บั๊กกลับเพื่อพิสูจน์):

after  B {"marker":"B","count":"1","n":1,"ids":[""],"source":true,"connected":true}

แท็บซ้าย "n":2 = เห็นคอมเมนต์ซ้ำ 2 อัน (id ว่างทั้งคู่) · แท็บขวาปกติเพราะได้ใบสั่งใบเดียว

เพราะ Turbo มีกฎว่า ถ้าของใหม่มี id ซ้ำกับของที่อยู่ในกล่องแล้ว ให้เอาอันเก่าออกแล้วใส่อันใหม่แทน (เอกสาร Turbo หน้า Streams เขียนไว้ใต้หัวข้อ Append) · ป้ายเลขถ้วย comment_3 จึงช่วยให้ไม่ซ้ำ · ไม่มีป้าย Turbo เทียบไม่ได้ ก็ใส่ทั้งสองอัน
บทเรียน: dom_id ใน partial ไม่ใช่ของประดับ — มันคือสิ่งที่ทำให้ broadcast กับคำตอบฟอร์มอยู่ด้วยกันได้ · อย่าลืม git restore app/views/comments/_comment.html.erb ถ้าลองตาม

ราคาที่ 2 — model รู้จัก view

ปกติคนดูแลสต็อก (model) ไม่ยุ่งกับการจัดจาน (view) · แต่ broadcasts_to ทำให้ model ไปเรียก partial comments/_comment เอง · ผลที่สไลด์เตือน: เปลี่ยนชื่อ partial แล้ว model พังโดยไม่รู้ตัว · test ของ model ต้อง render HTML ด้วยจึงช้าลง (เรื่อง test อยู่ Day 4)

ทางเลือกที่สไลด์เสนอ: ไม่ใส่ใน model แต่ให้ controller เป็นคนสั่งประกาศ หลังบันทึกสำเร็จ — seed/console ไม่โดนลูกหลง เพราะไม่ได้ผ่าน controller · หน้าตาประมาณนี้ (เราลองเรียกคำสั่งนี้จาก runner แล้วได้ Broadcasting to จริง · บทเรียนไม่ได้เปลี่ยนไปใช้แบบนี้ ไม่ต้องพิมพ์ตาม · สไลด์เขียน broadcast_append_to ซึ่งทำ HTML และประกาศทันทีในคำขอ · ตรงนี้ใช้รุ่น _later_ ให้ส่งต่อให้ job ตามหลักเดียวกับ broadcasts_to): 

# ใน CommentsController#create หลัง @comment.save สำเร็จ (ตัวอย่างเท่านั้น)

  • Turbo::StreamsChannel — "ตัวประกาศ" ตัวเดียวกับที่ broadcasts_to ใช้อยู่เบื้องหลัง แต่คราวนี้เราเรียกเองตรง ๆ
  • broadcast_append_later_to(@post, …) — ประกาศ append ในช่องของ @post · later = ฝากเป็นงาน · บอก target · partial · locals เองทั้งหมด (ไม่มีการเดาให้)

ข้อดี: อ่าน controller แล้วรู้เลยว่าใครสั่งประกาศ · ข้อเสีย: ทุกที่ที่สร้างคอมเมนต์ (เช่นหน้า admin ในอนาคต) ต้องจำใส่เอง · ไม่มีคำตอบเดียว — สไลด์สรุปว่า "ความสะดวกบรรทัดเดียวมีราคาเสมอ แค่ต้องรู้ว่าราคาคืออะไร"

ทำไมต้องหลัง commit — และ later: true ในสไลด์

broadcasts_to และบรรทัดตัวนับของเราใช้ after_*_commit ทั้งหมด · ทวนบท 112: ถ้าประกาศตอน after_save (ก่อน COMMIT) แล้ว transaction ถูกยกเลิก ทุกแท็บจะเห็นคอมเมนต์ที่ไม่มีอยู่จริง — เหมือนส่งไลน์บอกลูกค้าก่อนตู้เซ็นรับ · เราลองสร้างคอมเมนต์ใน transaction แล้วสั่ง raise ActiveRecord::Rollback (คำสั่ง "ยกเลิกทั้งกล่อง" ของ transaction): log มี BEGIN → ROLLBACK และไม่มี Enqueued สักบรรทัด = ไม่ประกาศของที่ถูกยกเลิก ✅

⚠️ สไลด์หน้า 46 และ 52 ให้เขียน broadcasts_to :post, later: true · ใน turbo-rails 2.0.23 ที่เราใช้ broadcasts_to ไม่มีตัวเลือก later: · ใส่แล้วไม่ error แต่ไม่มีผลอะไร (มันใช้ job ให้อยู่แล้วตอนสร้างและแก้ — เห็น Enqueued ใน log ข้างบน) · บทเรียนจึงไม่ใส่ — รายละเอียดท้ายบท

morphing และ data-turbo-permanent — refresh ทั้งหน้าแบบไม่สะดุด

สไลด์หน้า 47 พูดถึงอีกความสามารถหนึ่งของ Turbo 8 (รุ่นที่เราใช้) ซึ่งไม่ได้อยู่ในโค้ดของบทเรียน แต่ควรรู้จัก · ก่อนอื่นต้องรู้จัก page refresh = Turbo โหลดหน้าเดิมซ้ำ · เกิดบ่อยตอนส่งฟอร์มแล้ว server พากลับมาหน้าเดิม (redirect) หรือตอน server ประกาศว่า "ทุกคนโหลดหน้านี้ใหม่" (คำสั่ง broadcasts_refreshes_to — อีกทางเลือกแทน broadcasts_to ไม่ได้ใช้ในบทนี้)

ปกติ Turbo เปลี่ยนทั้ง <body> (บท 130) → หน้าเลื่อนกลับไปบนสุด ช่องที่กำลังพิมพ์หลุด · ถ้าใส่ 2 บรรทัดนี้ใน <head> ของ layout Turbo จะเทียบหน้าเก่ากับหน้าใหม่ทีละชิ้น แล้วแก้เฉพาะจุดที่ต่าง (เรียกว่า morphing): 

<meta name="turbo-refresh-method" content="morph">     <%# refresh แบบเทียบแล้วแก้เฉพาะที่ต่าง %>
<meta name="turbo-refresh-scroll" content="preserve">  <%# refresh แล้วไม่เลื่อนกลับบนสุด %>

และถ้ามีชิ้นไหนที่ห้ามแตะเด็ดขาด (เช่นเครื่องเล่นเพลงที่กำลังเล่น) ให้ติด data-turbo-permanent พร้อม id:

<div id="player" data-turbo-permanent>
  <audio controls src="…"></audio>
</div>

เปิดหน้า morph แล้ว · กำลังพิมพ์คอมเมนต์ค้างไว้ (ยังไม่กดส่ง) แล้วหน้าเกิด refresh — ข้อความที่พิมพ์ค้างจะอยู่ไหม?

เราทดลองบนหน้าบทความ (ใส่ meta ชั่วคราว · พิมพ์ในช่องความคิดเห็น · เลื่อนจอลง · สั่ง refresh ด้วย Turbo.session.refresh(location.href) ใน Chrome) — ผลจริง:

refresh แบบปกติเหมือนพนักงานยกของบนโต๊ะออกหมดแล้ววางชุดใหม่ · morph เหมือนพนักงานถือรายการใหม่มาเทียบกับโต๊ะทีละจาน จานไหนเหมือนเดิมไม่แตะ จานไหนต่างค่อยเปลี่ยน ลูกค้าแทบไม่รู้สึก · data-turbo-permanent คือป้าย "ของลูกค้า ห้ามเก็บ" ที่วางบนแก้วของเขาเอง

ที่ไม่เหมือนกัน: พนักงานจริงเห็นกระดาษที่ลูกค้าเขียนค้างไว้ก็คงไม่ลบ · morph ไม่รู้ว่าอะไรคือ "ของที่ลูกค้ากำลังทำ" มันทำให้ตรงกับรายการใหม่เป๊ะ ๆ · ต้องติดป้าย permanent เองทุกชิ้นที่อยากให้รอด

🎯 ภารกิจ: เปิดสองหน้าต่างวางข้างกัน แล้วพิมพ์ (~10 นาที)

  1. ถ้ายังไม่ได้ทำตามบท: แก้ app/models/comment.rb ให้ตรงกับไฟล์เต็มในหัวข้อ "ให้ตัวนับในแท็บอื่นขยับด้วย" และเพิ่ม <%= turbo_stream_from @post %> ในหน้า show ตามหัวข้อ "ชิ้นที่ 2"
  2. เปิด server ด้วย bin/dev (ถ้ายังไม่ได้เปิด)
  3. เปิดสองหน้าต่างเบราว์เซอร์ (ไม่ใช่สองแท็บในหน้าต่างเดียว — จะได้เห็นพร้อมกัน) ไปที่ http://localhost:3000/posts/1 ทั้งคู่ แล้ววางซ้าย–ขวา
  4. พิมพ์ชื่อและความคิดเห็นในหน้าต่างซ้าย กดส่ง · มองหน้าต่างขวา
  5. ดู terminal ที่รัน bin/dev หาบรรทัด Broadcasting to และนับ transmitting
  6. ถ้าทุกอย่างถูก: git add . && git commit -m "hotwire: broadcast คอมเมนต์ทุกแท็บ"

ควรเห็น: หน้าต่างขวามีคอมเมนต์ใหม่ต่อท้าย และเลขใน "ความคิดเห็น (…)" เพิ่มขึ้น 1 เองโดยไม่ต้องกด refresh · หน้าต่างซ้ายมีคอมเมนต์อันเดียว · log มี Broadcasting to 2 บรรทัด (รายการ · ตัวนับ) และแต่ละอันตามด้วย transmitting 2 บรรทัด (สองหน้าต่าง)

ถ้าเจออาการนี้ แปลว่า…

  • หน้าต่างขวาไม่ขยับ · log มี Broadcasting to แต่ไม่มี transmitting → หน้า show ยังไม่มี turbo_stream_from หรือพิมพ์เป็น <% %> (ไม่มี =) · แก้แล้วกด refresh ทั้งสองหน้าต่าง
  • คอมเมนต์ขึ้นในหน้าต่างขวา แต่ตัวนับยังเป็นเลขเดิม → ยังไม่ได้เพิ่มบรรทัด after_create_commit … comment_count …
  • หน้าต่างซ้ายมีคอมเมนต์ซ้ำ 2 อัน → _comment.html.erb ไม่มี id="<%= dom_id comment %>" แล้ว · git restore app/views/comments/_comment.html.erb
  • ลองสร้างคอมเมนต์จาก bin/rails console แล้วไม่เด้ง → ปกติ ไม่ใช่บั๊ก · development ใช้ adapter async ซึ่งได้ยินกันแค่ใน server ตัวเดียว

Quiz

1. ส่งคอมเมนต์จากแท็บ A แล้วแท็บ B ไม่ขยับ · ใน log เห็น Broadcasting to Z2lk… แต่ไม่มี transmitting เลย · สาเหตุที่น่าจะเป็นที่สุดคือ?

ตัวเลือกที่ 1 ผิด เพราะเห็น Broadcasting to แปลว่า model ประกาศแล้ว · ตัวเลือกที่ 2 ผิด เพราะ broadcasts_to ใช้ after_*_commit ให้เองอยู่แล้ว และต่อให้ใช้ after_save ข่าวก็ยังถูกส่ง ไม่ได้หาย · ตัวเลือกที่ 4 ผิด เพราะ development โหลดไฟล์ใน app/ ใหม่ให้เอง (เราทดลองทั้งบทโดยไม่ restart) · ตัวเลือกที่ 3 ถูก: transmitting คือการส่งถึงลำโพงแต่ละตัว ไม่มีเลย = ไม่มีลำโพง

จุดที่ต้องจำ: real-time ต้องมีสองฝั่ง — คนประกาศ (model) กับคนฟัง (turbo_stream_from ใน view) · ขาดฝั่งฟังแล้วพังเงียบ

2. (ดัดแปลงจากสไลด์หน้า 51) "เพิ่มคอมเมนต์แล้วหน้าเราเปลี่ยน 3 จุด" (บท 132) กับ "คนอื่นเพิ่มคอมเมนต์แล้วหน้าเราขึ้นเอง" (บทนี้) ใช้ Turbo Stream ทั้งคู่ · ต่างกันตรงไหน?

ตัวเลือกที่ 1 ผิด เพราะทั้งคู่เป็นใบสั่ง <turbo-stream> ที่เป็น HTML เหมือนกัน (เห็นใน log) · ตัวเลือกที่ 3 ผิด เพราะทั้งสองทางใช้คำสั่งได้เหมือนกัน — บทนี้เองก็ broadcast ทั้ง append และ update · ตัวเลือกที่ 4 สลับกัน: แบบที่สองต่างหากที่ต้องมี turbo_stream_from · แบบแรกเป็นคำตอบของฟอร์มจึงไม่ต้องฟังอะไร · ตัวเลือกที่ 2 ถูก: ของข้างในเหมือนกัน ต่างแค่ทางที่มันเดินทางมา

จุดที่ต้องจำ: Turbo Stream คือ "ใบสั่งงาน" · ส่งได้สองทาง — เป็นคำตอบของคำขอ (ถึงคนที่ถามคนเดียว) หรือ broadcast ผ่าน WebSocket (ถึงทุกคนที่ฟังช่องนั้น)

3. ทำไมการประกาศคอมเมนต์ใหม่ต้องเกิดหลัง COMMIT (after_commit) ไม่ใช่ตอน after_save?

ตัวเลือกที่ 2 ผิด เพราะ after_save เกิดก่อน after_commit ไม่ได้ช้ากว่า · ตัวเลือกที่ 3 ผิด เพราะ after_save ใช้กับ model ไหนก็ได้ · ตัวเลือกที่ 4 ผิด เพราะ WebSocket ไม่รู้จักฐานข้อมูลเลย ใครสั่งส่งมันก็ส่ง · ตัวเลือกที่ 1 ถูก: เราลอง ROLLBACK แล้วไม่มีการประกาศ เพราะ after_commit ไม่ทำงานเมื่อกล่องถูกยกเลิก

จุดที่ต้องจำ: เรื่องที่ออกไปนอกร้าน (ประกาศ · อีเมล) ทำหลังตู้เซ็นรับเท่านั้น — ส่งออกไปแล้วดึงกลับไม่ได้

4. งานไหนไม่เหมาะจะทำด้วย Turbo มากที่สุด?

ตัวเลือกที่ 1 เหมาะ — เปลี่ยนเป็นครั้งคราว ข้อมูลอยู่ที่ server (เหมือนคอมเมนต์ในบทนี้) · ตัวเลือกที่ 2 เหมาะ — กฎตรวจอยู่บน server ส่งฟอร์มที่มี error กลับมาแทนที่ (บท 132) · ตัวเลือกที่ 3 เหมาะ — ทุกสองสามวินาที server ตามทัน · ตัวเลือกที่ 4 ไม่เหมาะ: ต้องตอบสนองตามมือทุกเสี้ยววินาที รอ server ไม่ได้ และหน้าจอไม่ได้มาจาก HTML ของ server

จุดที่ต้องจำ: Turbo เหมาะเมื่อ server เป็นคนตัดสินหน้าจอและรอสักครู่ได้ · งานที่ต้องตอบทุกการขยับของมือ ใช้ JavaScript ฝั่งเบราว์เซอร์

💬 ถามกลับได้เลย — เช่น "ถ้าอยากให้คอมเมนต์ใหม่ขึ้นบนสุดแทนต่อท้าย ต้องแก้ตรงไหน" หรือ "ถ้าลบคอมเมนต์ ตัวนับในแท็บอื่นจะลดไหม" (ใบ้: ดูว่า broadcasts_to ทำอะไรตอนลบ และบรรทัดตัวนับของเราเป็น after_create_commit)
