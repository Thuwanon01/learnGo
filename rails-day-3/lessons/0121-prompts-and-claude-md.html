สไลด์พูดไว้ดีมาก: สามส่วนล่าง (ข้อกำหนด · ห้าม · เกณฑ์ตรวจรับ) ไม่ใช่งานเพิ่ม — มันคือเนื้อหาที่เพิ่งเรียนในบล็อกนั้น แค่เขียนลงไฟล์ · ถ้าเขียนส่วนไหนไม่ออก แปลว่าเรื่องในบล็อกนั้นยังไม่เข้าใจ ให้ย้อนกลับไปอ่าน ไม่ใช่ไปถาม AI ให้เขียนแทน

🧾 เทียบให้เห็นภาพ — ใบสั่งงานครัวที่พิมพ์ช่องไว้ตายตัว

ใบสั่งงานที่พิมพ์ช่องไว้แล้ว "เมนู · วิธีทำ · ห้ามใส่ (ลูกค้าแพ้) · ชิมผ่านเมื่อ…" · คนเขียนเห็นทันทีว่าลืมกรอกช่องไหน · และช่อง "ชิมผ่านเมื่อ…" คือสิ่งที่หัวหน้าใช้ตรวจจานก่อนเสิร์ฟ

ที่ไม่เหมือนกัน: ใบสั่งงานจริงเขียนครั้งเดียวทิ้ง · ไฟล์ prompt ของเราถูกแก้ซ้ำเรื่อย ๆ ทุกครั้งที่ AI พลาดแบบใหม่ · และคนที่ต้องติ๊กเกณฑ์ตรวจรับทีละข้อคือเรา ไม่ใช่ AI

🗣 ศัพท์ของ 4 ส่วน
goal · requirements · constraints
ชื่อภาษาอังกฤษของ เป้าหมาย · ข้อกำหนด · ห้าม · constraint = "ข้อจำกัด/สิ่งที่ห้ามทำ" · พิมพ์บอก AI ได้ว่า "Goal: … Requirements: … Constraints: do NOT add a migration"
acceptance criteria
"งานนี้ถือว่าเสร็จเมื่อ…" เขียนเป็นข้อที่ตรวจได้จริง (เคยเจอในบท 119) · ถาม senior ได้ว่า "acceptance criteria ของ ticket นี้คืออะไร ผมจะได้รู้ว่าเสร็จเมื่อไหร่"

# บริบทของโปรเจค wongnok_blog

## Stack

- Ruby 4.0.5 / Rails 8.1.3 / PostgreSQL 18
- Propshaft + importmap  (ห้ามใช้ Sprockets, ห้ามแนะนำ npm หรือ node_modules)

  ห้ามสร้าง tailwind.config.js — Tailwind v4 ไม่อ่านไฟล์นั้น
- Solid Queue / Solid Cache / Solid Cable

## รูปแบบโค้ด

- ข้อความที่ผู้ใช้เห็นเป็นภาษาไทย ผ่าน i18n
- ใช้ params.expect ไม่ใช่ params.require(...).permit(...)
- ตั้งชื่อตาม convention ของ Rails เสมอ
- ห้ามมี `<script>` ใน view

  • ที่เหลือเป็นของ Part 2 กับ Day 4 · ตอนนี้แค่รู้ว่ามีอยู่: Solid Queue (งานเบื้องหลัง) · Solid Cache (cache) · Active Storage (ระบบแนบไฟล์/รูป) · -> MinIO = เก็บไฟล์ไว้ที่ "โกดังเก็บไฟล์" ที่ docker เปิดให้ในบท 120 (S3-compatible = ใช้วิธีคุยแบบเดียวกับบริการเก็บไฟล์ S3 ของ Amazon) · Minitest กับ RSpec = เครื่องมือเขียน test สองยี่ห้อ โปรเจกต์นี้ใช้ตัวแรก
  • @plugin ในบรรทัด daisyUI เป็นคำสั่งในไฟล์ CSS ของ Tailwind (บท 128) · ไม่ใช่ @ แบบดึงไฟล์ที่จะเจอในหัวข้อ CLAUDE.md ข้างล่าง
  • ทำไมต้องบอก stack? เพราะ AI ไม่รู้ว่าโปรเจกต์เราใช้อะไร มันจะเดาจากสิ่งที่พบบ่อยในอินเทอร์เน็ต · เช่น Rails รุ่นเก่าใช้ Sprockets (ระบบส่งไฟล์ CSS/JS รุ่นก่อน Propshaft) · Tailwind รุ่นเก่าใช้ tailwind.config.js
  • สังเกตคำว่า "ห้าม" ในวงเล็บและบรรทัด tailwind.config.js — เป็นของรุ่นเก่าที่ AI มีโอกาสเดามาใส่ · สไลด์หน้า 5 บอกว่าไฟล์แบบนี้ "โตขึ้นทุกครั้งที่เจอ AI ทำพลาด" — ข้อห้ามพวกนี้คือหน้าตาของกฎที่เกิดแบบนั้น
  • ## รูปแบบโค้ด = กติกาการเขียน · params.expect คือท่าของ Rails 8 ที่เรียนในบท 117 · ห้าม <script> ใน view จะเข้าใจเหตุผลตอนเจอ Stimulus ในบท 134
  • i18n = ระบบแปลข้อความของ Rails (เขียนข้อความแยกไว้ในไฟล์ภาษา) · บทเรียนของเราไม่ใช้ i18n เขียนภาษาไทยตรง ๆ ใน view · บท 126 จะพาแก้บรรทัดนี้ให้ตรงกับโค้ดจริง — เป็นตัวอย่างแรกของ "เจอไม่ตรงแล้วแก้ไฟล์"

## กฎที่ห้ามลืม  (จากวันก่อน)

1. validates uniqueness ต้องมี unique index ที่ DB คู่เสมอ
2. validates presence ต้องมี NOT NULL ที่ DB คู่เสมอ
3. คอลัมน์ที่ใช้ค้นหาหรือเป็น foreign key ต้องมี index
4. ระบุ dependent: ของทุก association เสมอ และเลือกจากกฎธุรกิจ
5. ตรงที่วน each ต้องมี includes
6. index action ต้องมี limit หรือ pagination
7. migration ต้องไม่ล็อกตารางที่มีข้อมูลเยอะ — ใช้ expand-contract
8. strong parameters ไม่ใช่ authorization — แยกให้ออก

## รูปแบบการตอบ

- บอกชื่อไฟล์ทุกไฟล์ที่แก้หรือสร้าง

ดูหลักฐานใน repo เดียวกันเลย · กฎข้อ 6 ใน 00-context.md บอกว่า "index action ต้องมี limit หรือ pagination" แต่โค้ดตอนนี้คือ:

# app/controllers/posts_controller.rb (branch day3-start)
  # GET /posts or /posts.json
  def index
    @posts = Post.all
  end

Post.all ไม่มี limit · กฎในไฟล์ไม่ได้แก้โค้ดให้เอง และไม่ได้ห้ามใครเขียนโค้ดผิดกฎ (โค้ดนี้มาจาก scaffold — เราจะแก้ด้วยการแบ่งหน้าในบท 126) · AI ก็เหมือนกัน: อ่านกฎแล้ว ส่วนใหญ่ทำตาม แต่บางครั้งยังพลาด

แล้วกฎที่พลาดไม่ได้จริง ๆ ไปอยู่ไหน? สไลด์ตอบว่า test หรือ CI · repo นี้มีของพวกนี้อยู่แล้วบางส่วน:

  • CI (continuous integration) = เครื่องของ GitHub ที่รันตรวจโค้ดให้อัตโนมัติ · ไฟล์ .github/workflows/ci.yml สั่งให้มันทำงานทุกครั้งที่เปิด pull request (คำขอรวมโค้ดจาก branch หนึ่งเข้าอีก branch) หรือ push (ส่งโค้ดขึ้น GitHub) เข้า main
  • หนึ่งในขั้นของ CI คือ bin/rails db:test:prepare test = รัน test ทั้งหมด · test ไม่ผ่าน = GitHub ขึ้นกากบาทแดง (การเขียน test คือ Day 4)
  • gem ที่ดักให้จริง — Gemfile มี strong_migrations (บรรทัด 70) ที่หยุด migration อันตรายได้ทันที = เวอร์ชันบังคับของกฎข้อ 7 (รู้จักแล้วในบท 109) · และ bullet (บรรทัด 72) ที่เตือนเรื่อง N+1 = ผู้ช่วยของกฎข้อ 5 (ใช้จริงในบท 125)

เทียบกับ TypeScript: comment ที่เขียนว่า // ห้ามส่ง null มาตรงนี้ คือคำแนะนำ — คนอ่านอาจข้าม · ส่วน type ที่ไม่รับ null แล้ว tsc ฟ้อง error (บท 63–68) คือการบังคับ · CLAUDE.md อยู่ฝั่ง comment · test/CI อยู่ฝั่ง type

🚰 เทียบให้เห็นภาพ — ป้าย "กรุณาล้างมือ" กับประตูครัวที่ต้องสแกนมือก่อนเปิด

ป้าย "กรุณาล้างมือก่อนเข้าครัว" ช่วยได้เยอะ คนส่วนใหญ่ทำตาม · แต่วันที่ยุ่ง ๆ ก็มีคนลืม · ถ้าเรื่องนี้พลาดไม่ได้จริง ร้านจะติดประตูที่เปิดเมื่อสแกนมือที่ล้างแล้วเท่านั้น — ใครจะลืมก็เข้าไม่ได้
CLAUDE.md = ป้าย · test/CI/gem ที่ดัก = ประตูที่ล็อก

ที่ไม่เหมือนกัน: ประตูจริงกันได้ทันทีที่หน้าครัว · test/CI ส่วนใหญ่จับได้หลังโค้ดถูกเขียนแล้ว (ตอนรัน test · ตอน push) ไม่ได้หยุด AI ตอนพิมพ์ · และประตูจริงตรวจได้แค่เรื่องเดียว (ล้างมือ) — test ตรวจได้เฉพาะเรื่องที่เราเขียน test ไว้ เรื่องที่ไม่มี test ก็กลับไปพึ่งป้ายเหมือนเดิม

🗣 ศัพท์เรื่องคำแนะนำกับการบังคับ
guidance vs enforcement
guidance = คำแนะนำที่หวังให้ทำตาม (CLAUDE.md · comment) · enforcement = กลไกที่ไม่ผ่านก็ไปต่อไม่ได้ (test · CI · type checker · gem ที่ดัก) · ถาม senior ได้ว่า "กฎนี้สำคัญพอจะต้องมี test/CI จับไหม หรือแค่เขียนไว้ใน CLAUDE.md พอ"
CI (continuous integration)
ระบบที่รันตรวจโค้ดอัตโนมัติทุกครั้งที่ push หรือเปิด pull request · repo นี้ใช้ GitHub Actions (บริการ CI ของ GitHub · ตั้งค่าใน .github/workflows/ci.yml) · พิมพ์บอก AI ได้ว่า "this rule must not regress — write a test for it so CI fails if someone breaks it"

1. อยากให้ Claude Code รู้ว่า DB ทดลองในเครื่องคุณอยู่พอร์ต 55432 (เพื่อนในทีมใช้พอร์ตอื่น) ควรเขียนไว้ที่ไหน?

ตัวเลือกที่ 3 ถูก · ค่านี้เป็นของโปรเจกต์นี้ และเป็นของเราคนเดียว — ตรงกับ CLAUDE.local.md พอดี · และ repo ของคอร์สกันไว้ใน .gitignore บรรทัด 40

ตัวเลือกที่ 1 และ 2 ผิด — สองไฟล์นี้เข้า git · พอร์ตของเราจะไปปนกับของเพื่อน AI ในเครื่องเพื่อนจะต่อผิดพอร์ต · ตัวเลือกที่ 4 ผิด — ไม่หลุดเข้า git จริง แต่ไฟล์นี้ใช้กับทุกโปรเจกต์ โปรเจกต์อื่นไม่ได้ใช้พอร์ตนี้

จุดที่ต้องจำ: ถามสองคำถาม — ใช้กับโปรเจกต์ไหน (ทุกอัน/อันนี้) · ใครต้องรู้ (ทั้งทีม/เราคนเดียว) · แล้วจะรู้เองว่าไฟล์ไหน

2. เครื่องหมาย @ ในสองที่นี้ต่างกันยังไง: บรรทัด @prompts/00-context.md ใน CLAUDE.md กับการพิมพ์ @prompts/01-views.md ทำตามไฟล์นี้ ในช่องแชท?

ตัวเลือกที่ 2 ถูก · @ ใน CLAUDE.md คือ import — เนื้อไฟล์ถูกโหลดตอนเริ่มทุก session · @ ในช่องแชทคือยื่นไฟล์ให้ดูเฉพาะงานนี้

ตัวเลือกที่ 1 ผิด — @ ในช่องแชทไม่ได้แก้ไฟล์ไหน จึงไม่มีอะไรติดไปถึง session หน้า เปิดแชทใหม่ก็ต้องพิมพ์ใหม่ · ตัวเลือกที่ 3 ผิด — เอกสารบอกว่าไฟล์ที่ import ถูกโหลดเข้ามาพร้อม CLAUDE.md เลย ไม่ได้รอ AI ตัดสินใจเปิด · ตัวเลือกที่ 4 ผิด — การพิมพ์ในแชทไม่ได้แก้ไฟล์ CLAUDE.md ให้ ถ้าอยากให้ถาวรต้องสั่งหรือแก้ไฟล์เอง

จุดที่ต้องจำ: ของที่ใช้ทุกงาน → import ใน CLAUDE.md · ของที่ใช้บางงาน → @ ในช่องแชทตอนจะใช้

3. 00-context.md มีกฎ "index action ต้องมี limit หรือ pagination" แต่ AI ยังเขียน @posts = Post.all มาให้ ข้อสรุปไหนถูกที่สุด?

ตัวเลือกที่ 1 ถูก · ทั้งสไลด์และเอกสารพูดตรงกันว่าไฟล์พวกนี้เป็นคำแนะนำ ไม่ใช่การบังคับ · หน้าที่ของเราคือติ๊กเกณฑ์ตรวจรับเอง และเรื่องที่พลาดไม่ได้ให้ test/CI จับ

ตัวเลือกที่ 2 ผิด — โหลดแล้วก็ยังพลาดได้ (เช็กว่าโหลดไหมด้วย /context ไม่ใช่เดาจากผลงาน) · ตัวเลือกที่ 3 ผิด — 46 บรรทัดยังห่างจาก ~200 มาก ลบกฎดี ๆ ทิ้งไม่ได้แก้ปัญหา · ตัวเลือกที่ 4 ผิด — เอกสารบอกว่าไฟล์ต่าง ๆ ถูกเอามาต่อกัน ไม่มีไฟล์ไหนชนะไฟล์ไหน และกฎทีมควรอยู่ที่ทีมเห็น

จุดที่ต้องจำ: CLAUDE.md = ป้าย · test/CI = ประตูที่ล็อก · AI ทำผิดกฎ = เรื่องปกติที่ต้องตรวจเจอ ไม่ใช่ระบบพัง

4. เพื่อนเสนอให้ใส่ @prompts/01-views.md · @prompts/02-styling.md · @prompts/03-hotwire.md ลงใน CLAUDE.md "AI จะได้รู้ทุกอย่างตลอด" ทำไมไม่ควรทำ?

ตัวเลือกที่ 4 ถูก · import = โหลดทุก session · ไฟล์รายบล็อกใช้เฉพาะตอนทำบล็อกนั้น จึงควรเรียกด้วย @ ในช่องแชทตอนจะใช้ · ไฟล์ที่ import ยังนับรวมในงบ ~200 บรรทัดด้วย

ตัวเลือกที่ 1 ผิด — import ได้หลายไฟล์ และไฟล์ถูกเอามาต่อกัน ไม่ทับกัน · ตัวเลือกที่ 2 ผิด — prompts/ เข้า git อยู่แล้วโดยตั้งใจ (ทีมใช้ร่วมกัน) · ตัวเลือกที่ 3 ผิด — ไฟล์ที่โหลดเป็นข้อมูลประกอบ AI ไม่ได้ลงมือทำเองจนกว่าเราจะสั่งงาน

จุดที่ต้องจำ: CLAUDE.md เก็บเฉพาะของที่จริงทุกงาน (stack · กฎถาวร · คำสั่งที่ใช้บ่อย) · ที่เหลือเรียกเมื่อใช้
