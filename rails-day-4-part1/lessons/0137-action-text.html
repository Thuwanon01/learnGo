Action Text — ช่องเนื้อหาแบบ rich text ที่มากับ Rails

~30 นาที (บทนี้ติดตั้งของจริงและแก้ 10 กว่าไฟล์ — ยาวกว่าบทปกติ) · ควรผ่าน บทเรียน 136 (allowlist · sanitize ตอนโชว์) · บทเรียน 109 (expand-contract) และ บทเรียน 125 (XSS · N+1 ใน view) มาก่อน

บท 136 เราประกอบ rich text เองด้วยมือเพื่อดูกลไก · บทนี้ติดตั้งของสำเร็จรูปที่มากับ Rails ชื่อ Action Text ให้ช่องเนื้อหาของบทความมีปุ่ม B ลิงก์ และรายการ
อ่านจบบทนี้ คุณจะติดตั้ง Action Text ได้ · รู้ว่าเนื้อหาไปอยู่ตารางไหน และทำไมค้นด้วย WHERE body ไม่ได้ · ย้ายเนื้อหา 30 บทความเดิมมาครบโดยไม่ลบของเก่า (expand) · และกัน N+1 ตัวใหม่ที่ Action Text แอบพามา — จบบทด้วย commit

🔁 ทวนก่อนเริ่ม — คำพวกนี้จะโผล่ในบทนี้

  • allowlist · sanitize ตอนโชว์ (บท 136) — เก็บเฉพาะแท็กที่อยู่ในรายการที่อนุญาต ถอดที่เหลือ · ทำตอนแสดงผลทุกครั้ง ไม่ใช่ตอนบันทึก · ช่อง plain text ไว้ค้นหาโดยไม่มีชื่อแท็กปน
  • expand-contract (บท 109) — เปลี่ยนโครงตารางทีละเฟส: ทำของใหม่ก่อน → ย้ายข้อมูล (backfill) ในงานแยก → ค่อยลบของเก่ารอบหลัง
  • before_save · private (บท 112) — สั่งให้ทำอะไรก่อนบันทึกทุกครั้ง ทั้งตอนสร้างและตอนแก้
  • N+1 · includes · bullet (บท 114 · บท 125) — เดินไปตู้ทีละแผ่น vs ใบเบิกทีเดียวทั้งตะกร้า · ดู (N queries) ท้ายบรรทัด Completed ใน log
  • params.expect (บท 117) — รายชื่อช่องในฟอร์มที่ controller ยอมรับ

Action Text คืออะไร — และบทนี้จะทำ 6 ขั้น

Action Text คือชิ้นส่วนที่มากับ Rails ให้ช่องเนื้อหามีปุ่มจัดรูปแบบ (ตัวหนา ลิงก์ หัวข้อ รายการ) แล้วเก็บผลเป็น HTML ให้ · ตอนโชว์มัน sanitize ให้เองทุกครั้ง แบบที่บท 136 สอน · เราจึงไม่ต้องประกอบเองอีก

ช่องพิมพ์ที่มีปุ่มนั้นเรียกว่า editor · ตัวที่มากับ Action Text ชื่อ Trix (โปรแกรม JavaScript ที่วาดแถบปุ่มและช่องพิมพ์ในเบราว์เซอร์) · (ถ้าได้ยินชื่อ Lexxy — เป็น editor ตัวใหม่ที่เป็น gem แยก ไม่ได้ติดมากับ Rails 8.1.4 · บทนี้ใช้ Trix)

🎂 เทียบให้เห็นภาพ — ชุดแต่งหน้าเค้กสำเร็จรูป

บท 136 ร้านทำทุกอย่างเองด้วยมือ: ทำกระดาษให้ลูกค้าเขียนข้อความหน้าเค้ก · หาที่เก็บใบสั่ง · จดรายการตัวตกแต่งที่อนุญาต · ตรวจตอนจัดจาน · Action Text คือชุดสำเร็จรูปกล่องเดียวที่มีครบ: กระดาษพร้อมปุ่มตัวหนา (editor) · ลิ้นชักเก็บใบสั่ง (ตาราง) · คนตรวจตอนจัดจาน (sanitize)

ที่ไม่เหมือนกัน: ชุดสำเร็จรูปจริงแกะกล่องแล้วใช้ได้เลย · Action Text ยังต้องปรับให้เข้ากับร้านเรา — ย้ายเนื้อหา 30 บทความเดิมเข้าลิ้นชักใหม่ · จัด CSS ให้เข้ากับ Tailwind · กันการเดินไปลิ้นชักทีละแผ่น · ซึ่งก็คือเนื้อหาเกือบทั้งบทนี้

ทีละบรรทัด (append = ต่อท้ายไฟล์เดิม · create = สร้างไฟล์ใหม่):

  • Installing JavaScript dependencies — แค่หัวข้อ ไม่ได้ดาวน์โหลดอะไร · installer จะเรียก yarn/bun (ตัวติดตั้ง package ของ JavaScript แบบเดียวกับ npm) เฉพาะโปรเจกต์ที่มี package.json · โปรเจกต์เราใช้ importmap (บท 127) ไม่มีไฟล์นี้ จึงข้ามไป
  • application.js + importmap.rb — เพิ่มบรรทัดโหลด Trix กับตัวเชื่อม Trix ↔ Rails · ทั้งคู่ชี้ไฟล์ที่อยู่ใน gem ของ Rails ไม่ใช่ CDN (ดูข้างล่าง)
  • actiontext.css — หน้าตาของแถบปุ่มและเนื้อหา (440 บรรทัด) · เดี๋ยวขั้น 5 ต้องย้ายที่ ไม่งั้นชนกับ Tailwind
  • _blob.html.erb — แม่พิมพ์ของรูป/ไฟล์ที่แนบในเนื้อหา (เรื่องไฟล์เริ่มบท 138) · _content.html.erb — กรอบ <div class="trix-content"> ที่ห่อเนื้อหาทุกครั้งที่โชว์
  • railties:install:migrations — คำสั่งที่ installer เรียกต่อเอง: ก็อปไฟล์ migration ที่มากับ gem มาใส่ db/migrate/ ของเรา (ยังไม่สร้างตาราง) · ได้มา 2 ไฟล์ · ไฟล์แรกเป็นของ Active Storage (ระบบเก็บไฟล์ของ Rails — บท 138) เพราะรูปที่แนบในเนื้อหาต้องเก็บด้วยระบบนั้น
  • rich_texts.yml — ไฟล์ข้อมูลตัวอย่างสำหรับ test (มีแต่ comment ไม่มีผลอะไร · เรื่อง test อยู่ Part 2)

ขั้น 2 · เนื้อหาไม่ได้อยู่ในตาราง posts

เปิด db/schema.rb (ไฟล์ที่สรุปโครงทุกตาราง — บท 108) หาตารางใหม่:

  create_table "action_text_rich_texts", force: :cascade do |t|
    t.string "name", null: false
    t.text "body"
    t.string "record_type", null: false
    t.bigint "record_id", null: false
    t.datetime "created_at", null: false
    t.datetime "updated_at", null: false
    t.index ["record_type", "record_id", "name"], name: "index_action_text_rich_texts_uniqueness", unique: true
  end
  • body — ตัว HTML ของเนื้อหา (ชื่อคอลัมน์บังเอิญตรงกับชื่อช่องที่เราจะตั้ง แต่คนละที่กัน)
  • name — ชื่อช่อง เช่น "body" · เผื่อ model หนึ่งมี rich text หลายช่อง (เช่น เนื้อหา + บทสรุป)
  • record_type + record_id — เนื้อหานี้เป็นของแถวไหน ในตารางไหน เช่น "Post" + 5 = บทความเลข 5
  • index … unique: true — กันไม่ให้แถวเดียวกันมีช่องชื่อเดียวกันซ้ำสองอัน (index ไม่ซ้ำ — บท 111)

ต่างจากที่เคยเห็นตรงไหน? ตาราง comments ของเรามีคอลัมน์ post_id (บท 115) — รู้อยู่แล้วว่าชี้ไปตาราง posts · ตารางนี้ชี้ได้ทุกตาราง จึงต้องเก็บสองช่อง: ชื่อ model (record_type) กับเลขแถว (record_id) · การชี้แบบนี้เรียกว่า polymorphic (แปลตรง ๆ ว่า "รับได้หลายแบบ")

คำว่า polymorphic เคยผ่านตาในชื่อ polymorphic_path (บท 117) แต่การเก็บแบบสองช่องนี้เพิ่งเจอครั้งแรก · บท 138 จะเจออีกที่ตาราง active_storage_attachments ซึ่งมี record_type + record_id แบบเดียวกัน

🗄 เทียบให้เห็นภาพ — ลิ้นชักกลาง "ข้อความยาว" ใบเดียวของทุกแผนก

แฟ้มบทความในลิ้นชัก posts ไม่มีที่เขียนเนื้อหายาว ๆ แล้ว · เนื้อหาไปอยู่ลิ้นชักกลาง "ข้อความยาว" ที่ทุกแผนกใช้ร่วมกัน · ทุกแผ่นในลิ้นชักกลางติดป้ายว่า "ของแผนกไหน · แฟ้มเลขที่เท่าไร · ช่องอะไร" เช่น "แผนกบทความ · แฟ้ม 5 · เนื้อหา"

ที่ไม่เหมือนกัน: ลิ้นชักจริง พนักงานเห็นป้ายแล้วรู้ว่าแผนกนั้นมีจริงไหม · ฐานข้อมูลตรวจไม่ได้ว่า record_type + record_id ชี้ไปแถวที่มีอยู่จริง (ไม่มี foreign key แบบ post_id — เพราะชี้ได้หลายตาราง) · Rails เป็นคนดูแลให้แทน เช่นลบบทความแล้วลบแผ่นในลิ้นชักกลางตามให้

บอก model ว่าบทความมีช่อง rich text ชื่อ body — เปิด app/models/post.rb เติม 2 บรรทัดใต้ has_many :comments (ส่วนอื่นยังไม่แตะ):

  • ไม่ต้องเขียน migration เพิ่มคอลัมน์ body ในตาราง posts — ตารางกลางมีอยู่แล้ว

ขั้น 3 · แผนย้ายข้อมูล — expand ก่อน ยังไม่ลบ description

เนื้อหา 30 บทความอยู่ใน description ต้องย้ายไป body · นี่คือการย้ายข้อมูลจริงแบบที่บท 109 สอน · ข้อกำหนดของสไลด์หน้า 14 เขียนชัดว่า รอบนี้ห้ามลบคอลัมน์ description — เพิ่มของใหม่ก่อน ย้ายข้อมูล แล้วปล่อยของเก่าไว้ ค่อยลบรอบหน้า

ร้านเปลี่ยนมาเขียนเนื้อหาบนกระดาษในลิ้นชักกลาง · แต่ช่อง "เนื้อหา" บนแฟ้มเดิมยังอยู่ และสั่งพนักงานว่า "ช่วงนี้เขียนทั้งสองที่" · ถ้าระบบใหม่มีปัญหาแล้วต้องถอยกลับไปใช้คู่มือเก่า แฟ้มทุกแผ่นยังมีข้อมูลครบ · พอมั่นใจแล้วค่อยประกาศเลิกใช้ช่องเดิม แล้วลบรอบหน้า

ที่ไม่เหมือนกัน: พนักงานจริงลืมเขียนที่สองได้ · ในโค้ด "เขียนสองที่" คือ callback บรรทัดเดียวที่ทำให้ทุกครั้งที่บันทึก ไม่มีวันลืม · แต่ถ้ามีใครแก้ข้อมูลด้วย SQL ตรง ๆ (ไม่ผ่าน model) callback ก็ไม่ทำงาน — สองช่องจะไม่ตรงกัน

แล้วแก้ model ทั้งไฟล์ เป็นแบบนี้ — app/models/post.rb:

class Post < ApplicationRecord
  belongs_to :category
  has_many :comments, dependent: :destroy
  # เนื้อหาแบบ rich text เก็บในตาราง action_text_rich_texts (ไม่ได้อยู่ในตาราง posts)
  has_rich_text :body

  validates :title, presence: true, length: { maximum: 120 }
  validates :body, presence: true

  # ทุกครั้งที่บันทึก: เก็บข้อความล้วนของ body ไว้ใน plain_text (ไว้ค้นหาทีหลัง)
  # และเขียนลง description ด้วย (expand-contract: คอลัมน์เก่ายังอยู่ เขียนทั้งสองช่องไปก่อน)
  before_save :copy_body_to_plain_text

  scope :recent, -> { order(created_at: :desc) }

  private
    def copy_body_to_plain_text
      self.plain_text = body.to_plain_text
      self.description = plain_text
    end
end
  • validates :body, presence: true — แทน validates :description เดิม · ตอนนี้ช่องที่ผู้ใช้ต้องกรอกคือ body
  • before_save :copy_body_to_plain_text — ก่อนบันทึกทุกครั้ง เรียก method ข้างล่าง (บท 112)
  • body.to_plain_text — ถอดแท็กทิ้ง เหลือตัวหนังสือล้วน (แบบ strip_tags ในบท 136 · ขึ้นบรรทัดใหม่ยังเป็น \n) → เก็บลง plain_text
  • self.description = plain_text — เขียนลงช่องเก่าด้วย (= "เขียนทั้งสองที่") · เหตุผลที่สองคือคอลัมน์ description ในฐานข้อมูลตั้งไว้ว่าห้ามว่าง (null: false) · ถ้าไม่เติมให้ บทความใหม่จะบันทึกไม่ได้

ขั้น 4 · ย้าย 30 บทความเดิมด้วย rake task

กฎจากบท 109: การย้ายข้อมูลอยู่ในงานแยก ไม่ใช่ในไฟล์ migration · งานแยกแบบหนึ่งคือ rake task = คำสั่งที่เราเขียนเพิ่มเอง แล้วรันด้วย bin/rails ชื่องาน · ให้ generator สร้างโครงให้ (posts = กลุ่มของงาน · backfill_body = ชื่องาน): 

$ bin/rails generate task posts backfill_body
      create  lib/tasks/posts.rake

ไฟล์ที่ได้เป็นงานเปล่า ๆ (desc "TODO" + task backfill_body: :environment do … end) · เขียนทับทั้งไฟล์เป็น — lib/tasks/posts.rake:

namespace :posts do
  desc "ย้าย description (ข้อความล้วน) ไปเป็น body (rich text) ให้บทความที่ยังไม่มี body — รันซ้ำได้"
  task backfill_body: :environment do
    # เลือกเฉพาะบทความที่ยังไม่มีแถวใน action_text_rich_texts → รันรอบสองจะไม่ทับของที่ย้ายแล้ว
    Post.where.missing(:rich_text_body).find_each do |post|
      # escape ก่อน: ถ้าใน description มีคำว่า <script> ให้โชว์เป็นตัวอักษร ไม่กลายเป็นแท็ก
      text = ERB::Util.html_escape(post.description)
      # ขึ้นบรรทัดใหม่ → <br> แบบเดียวกับที่ Trix เก็บ
      post.update!(body: "<div>#{text.gsub(/\r?\n/, "<br>")}</div>")
    end

    puts "บทความทั้งหมด #{Post.count} · ยังไม่มี body #{Post.where.missing(:rich_text_body).count}"
  end
end
  • namespace :posts + task backfill_body: — ได้ชื่อคำสั่ง posts:backfill_body · desc = คำอธิบายที่โชว์ใน bin/rails -T · :environment = โหลดแอปก่อน (ไม่งั้นใช้ Post ไม่ได้)
  • where.missing(:rich_text_body) — "บทความที่ยังไม่มีแผ่นในลิ้นชักกลาง" (rich_text_body คือชื่อ has_one ที่ has_rich_text :body สร้างให้) · ทำให้รันซ้ำได้: รอบสองไม่เหลือใครให้ย้าย
  • find_each — วนทีละกองแทนโหลดทั้งตารางเข้าหน่วยความจำ (บท 114)
  • ERB::Util.html_escape — ใส่ซองใสแบบเดียวกับ <%= %> · description เดิมเป็นตัวหนังสือล้วน ถ้าในนั้นมีคำว่า <b> ต้องโชว์เป็นตัวอักษร ไม่ใช่กลายเป็นตัวหนาหลังย้าย
  • gsub(/\r?\n/, "<br>") — เปลี่ยนการขึ้นบรรทัดใหม่เป็นแท็ก <br> (/…/ = รูปแบบที่จะค้น · \r?\n = ขึ้นบรรทัดใหม่ทั้งแบบ Windows และ Mac)
  • update! — บันทึกผ่าน model → before_save ทำงาน → plain_text ถูกเติมไปพร้อมกัน · ! = พังให้เห็นถ้าบันทึกไม่ได้ (บท 107)

เทียบกับของที่รู้: rake task คล้าย "scripts" ใน package.json ฝั่ง Next.js ที่สั่งด้วย npm run ชื่อ — เป็นงานที่ตั้งชื่อไว้ แล้วใครในทีมก็สั่งด้วยชื่อเดียวกันได้ · ต่างกันตรงที่ rake task โหลดแอปทั้งตัว (:environment) จึงใช้ model ได้เลย
