Rich text — ให้ผู้ใช้จัดตัวหนาได้ โดยไม่เปิดช่องให้รัน JavaScript

~25 นาที · ควรผ่าน บทเรียน 125 (XSS · sanitize) และจบ Day 3 (บทเรียน 135) มาก่อน

บทความในเว็บของเราตอนนี้เป็นตัวหนังสือล้วน · ถ้าอยากให้คนเขียนทำตัวหนา ใส่ลิงก์ได้ เราต้องยอมรับ HTML จากผู้ใช้ — ซึ่งเป็นประตูเดียวกับที่คนร้ายใช้ฝังโปรแกรม
อ่านจบบทนี้ คุณจะอธิบายได้ว่าทำไม "รายการของที่อนุญาต" ปลอดภัยกว่า "รายการของที่ห้าม" · ใช้ sanitize ใน view ให้เหลือแค่แท็กที่ต้องการ · รู้ว่าทำไม Rails ตรวจตอนโชว์ ไม่ใช่ตอนบันทึก · และรู้ว่าควรเก็บเนื้อหาเป็น HTML หรือ Markdown ก่อนไปติดตั้งของจริงในบท 137

🔁 ทวนก่อนเริ่ม — คำพวกนี้จะโผล่ในบทนี้

  • XSS · escape (บท 125) — คนร้ายฝังโปรแกรมไว้ในข้อมูล ให้ไปรันในเบราว์เซอร์คนอื่น · <%= %> กันให้เองด้วยการใส่ซองใส (แปลง < เป็น &lt;)
  • raw · html_safe (บท 125) — สองคำที่แกะซองออก ปิดระบบกันภัย · ห้ามใช้กับของที่ผู้ใช้พิมพ์
  • sanitize (บท 125) — ทางกลาง: เก็บแท็กที่อยู่ในรายชื่อที่อนุญาต ถอดที่เหลือทิ้ง · ลองใน console ด้วย helper.sanitize(...)
  • params.expect (บท 117) — บอกว่าช่องไหนในฟอร์มรับได้ ช่องที่ไม่อยู่ในรายชื่อถูกทิ้ง · จำไว้ เดี๋ยวจะเห็นว่าเป็นหลักการเดียวกัน
  • curl (บท 125) — เปิดหน้าเว็บจากเทอร์มินัล เห็น HTML ที่เบราว์เซอร์ได้รับจริง

rich text คือข้อความที่มีรูปแบบ — ตัวหนา ตัวเอียง ลิงก์ หัวข้อ รายการข้อ ๆ · นึกถึงช่องเขียนอีเมลใน Gmail หรือ Google Docs ที่มีปุ่ม B I ด้านบน · กดปุ่ม B แล้วพิมพ์ ข้อความก็หนาทันที

เบื้องหลังปุ่มพวกนั้นคือ HTML · กดตัวหนา = editor (ช่องพิมพ์แบบมีปุ่ม) แอบเขียน <strong>อร่อย</strong> ให้ · แปลว่าถ้าเว็บเรามี rich text เราต้องเก็บ HTML ที่มาจากผู้ใช้ แล้วเอาไปโชว์ให้คนอื่นดู

🎂 เทียบให้เห็นภาพ — ข้อความบนหน้าเค้กที่ลูกค้าเขียนเอง

ร้านเรารับทำเค้กที่ลูกค้าเขียนข้อความบนหน้าเค้กเอง · ข้อความธรรมดา (ช่อง title เดิม) เราเขียนให้ตามที่สั่งทุกตัวอักษร · แต่ลูกค้าอยากได้มากกว่านั้น: "คำว่าอร่อยขอตัวใหญ่สีทอง" — นี่คือ rich text · ถ้าเรายอมให้ลูกค้าเอาของตกแต่งมาวางเองได้ทุกอย่าง วันหนึ่งจะมีคนเอาประทัดมาวาง แล้วเค้กชิ้นนั้นถูกเสิร์ฟให้ทุกโต๊ะ

ที่ไม่เหมือนกัน: คนกินเค้กยังมองเห็นประทัดแล้วหยิบออกได้ · เบราว์เซอร์ไม่ดูเลย มันทำตาม HTML ทุกคำสั่งทันที และหน้าเว็บหน้าเดียวถูกเปิดโดยคนนับร้อย — ของต้องห้ามหนึ่งชิ้นจึงโดนทุกคนที่เปิดหน้านั้น

เทียบกับ React (บท 125 เล่าไว้): {post.title} ใน JSX escape ให้เองเหมือน <%= %> · จะโชว์ HTML ของผู้ใช้ได้ต้องพิมพ์ dangerouslySetInnerHTML — โลก React ก็เจอคำถามเดียวกับบทนี้ทุกเว็บที่มี rich text

allowlist กับ blocklist — ผิดแบบไหนเจ็บกว่า

มีสองวิธีเขียน "กฎว่าอะไรผ่าน":

  • blocklist (รายการของที่ห้าม) — บอกว่าอะไรห้ามผ่าน ที่เหลือผ่านหมด · เช่น "ห้าม <script>"
  • allowlist (รายการของที่อนุญาต) — บอกว่าอะไรผ่านได้ ที่เหลือโดนถอดหมด · เช่น "ผ่านได้แค่ strong em a p"

ร้านเค้กมีสองแบบ · ร้าน A ติดป้ายรายการของห้ามใส่: "ห้ามประทัด ห้ามไม้ขีด" — ลูกค้าเอาพลุมา ไม่อยู่ในป้าย พนักงานก็ใส่ให้ · ร้าน B ถือรายการตัวตกแต่งที่ร้านอนุญาต: "เม็ดน้ำตาล ช็อกโกแลตชิพ ตัวอักษรสีทอง" — ของที่ไม่อยู่ในรายการไม่ใส่ ไม่ว่ามันคืออะไร · ร้าน B ไม่ต้องรู้จักพลุก็กันพลุได้ ร้าน A ต้องรู้จักของอันตรายทุกชนิดในโลก

ที่ไม่เหมือนกัน: ของนอกรายการในร้านจริงถูกปัดทิ้งทั้งชิ้น · sanitize ถอดแค่แท็กแต่ตัวหนังสือข้างในยังอยู่ (บท 125: <script>alert(1)</script> เหลือ alert(1)) · และมันตรวจทีละ "ส่วนประกอบ" ด้วย — รับ img แต่แกะ onerror ที่ติดมาออก เหมือนรับช็อกโกแลตแต่แกะไส้ที่ไม่อนุญาตทิ้ง

เทียบของที่รู้แล้ว — หลักการเดียวกันเจอมาแล้วหลายรอบ (สไลด์หน้า 4): params.expect (บท 117) = บอกว่าช่องไหนในฟอร์มรับได้ · <%= %> (บท 103/125) = escape ทุกอย่างแล้วค่อยยกเว้นเป็นจุด · วันนี้ sanitize = บอกว่าแท็กไหนผ่านได้ · บท 140 จะบอกว่าไฟล์ชนิดไหนรับได้ — ทั้งหมดคือ allowlist

ทดสอบความเข้าใจ

ทีม A กรอง rich text ด้วย allowlist แต่ลืมใส่ em · ทีม B ใช้ blocklist (ห้าม script กับ iframe) แต่ลืม onerror · ข้อไหนถูก?

ตัวเลือกที่ 3 ถูก — allowlist ลืมของ = ของนั้นถูกถอดทิ้ง (แบบที่ <h2> หายในภารกิจ) feature ขาด เห็นเอง · blocklist ลืมของ = ของนั้นผ่าน (แบบที่ <img onerror> ผ่าน gsub ไปทั้งก้อน) คนร้ายเห็นก่อน

ตัวเลือกที่ 1 — ลืมเท่ากันแต่ผลไม่เท่ากัน คือหัวใจของหัวข้อนี้ · ตัวเลือกที่ 2 — แท็กนอกรายการถูกถอดทิ้ง ไม่ได้หลุดออกไป เหลือแค่ตัวหนังสือ · ตัวเลือกที่ 4 — "ที่รู้จัก" คือปัญหา · ลองแล้วว่าแค่ <sc<script>ript> ก็หลบตัวกรองแบบลบคำได้

จุดที่ต้องจำ: allowlist ผิด = feature ขาด (เราเห็น) · blocklist ผิด = ระบบถูกเจาะ (เราไม่เห็น) → เลือก allowlist เสมอ

มีบทความเก่า 500 ชิ้นบันทึกไว้แล้ว บางชิ้นมี <img src="x" onerror="…"> · วันนี้เราเพิ่ม sanitize ใน view · เกิดอะไรกับบทความเก่า?

ตัวเลือกที่ 1 ถูก — sanitize กรองระหว่างทางออกไปหน้าเว็บทุกครั้ง · เราเห็นแล้วว่าหน้าเว็บไม่มี onerror แต่ Post.find(31).description ยังมีครบ

ตัวเลือกที่ 2 — ไม่ต้อง migrate นี่คือข้อดีของการตรวจตอนโชว์ · ตัวเลือกที่ 3 — sanitize ไม่เคยเขียนกลับลงฐานข้อมูล · ตัวเลือกที่ 4 — คือผลของการกรองตอนบันทึก ซึ่ง Rails ไม่ได้ทำ

จุดที่ต้องจำ: ตรวจตอนโชว์ = แก้กฎแล้วของเก่าปลอดภัยทันที · แต่ของสกปรกยังอยู่ใน DB

ทีมมือถือดึง /posts/31.json แล้วเอา description ไปวางเป็น HTML บนจอ · ผู้ใช้แอปโดน alert ทั้งที่หน้าเว็บของเรา sanitize แล้ว · เพราะอะไร?

ตัวเลือกที่ 4 ถูก — ผลจริงจาก curl: JSON มี onerror=\"alert(1)\" ครบ · show.json.jbuilder ไม่ผ่าน _post.html.erb ที่เราใส่ sanitize

ตัวเลือกที่ 1 — JSON แปลง < เป็น \u003c จริง แต่นั่นเป็นแค่วิธีเขียน อ่านกลับมาก็ได้ < เหมือนเดิม (ลองด้วย JSON.parse แล้ว) · ปัญหาไม่ได้อยู่ที่การแปลงตัวอักษร · ตัวเลือกที่ 2 — sanitize ไม่เคยเขียนลง DB · ของดิบอยู่ในนั้นมาตั้งแต่บันทึก · ตัวเลือกที่ 3 — cookie ไม่เกี่ยว ทั้งสองทางอ่านแถวเดียวกันในฐานข้อมูล

จุดที่ต้องจำ: จุดที่ปลอดภัยคือ "render ผ่าน Rails view" เท่านั้น · ทุกทางส่งออกอื่นต้องกรองเอง

ช่องค้นหาของเว็บใช้ description ILIKE '%strong%' แล้วเจอบทความที่บนจอไม่มีคำนี้เลย · แก้แบบไหนตรงจุดที่สุด?

ตัวเลือกที่ 2 ถูก — คำว่า strong มาจากชื่อแท็ก · strip_tags ให้ "น้ำแกงเข้มข้น ดูร้านอื่นที่หน้ารวม" ที่ไม่มีแท็กปน · เก็บแบบนี้ไว้อีกช่องแล้วค้นจากช่องนั้น (บท 137)

ตัวเลือกที่ 1 — Markdown ก็มีสัญลักษณ์ปน (** · [ ](…)) และยังแทรก HTML ดิบได้ด้วย · ตัวเลือกที่ 3 — ปัญหาไม่ได้อยู่ที่ผู้ใช้ แท็ก <strong> มาจากการกดปุ่ม B เอง · ตัวเลือกที่ 4 — sanitize เป็น helper ของ Rails ทำงานใน Ruby ตอนโชว์ ไม่ใช่คำสั่งของฐานข้อมูล

จุดที่ต้องจำ: เก็บ HTML = ต้องมีช่อง plain text แยกไว้ค้นหา
