signed URL และ direct upload — แอปออกใบอนุญาต ไม่ได้แบกไฟล์เอง

~25 นาที · ควรผ่าน บทเรียน 138 (MinIO · Active Storage · รูปปก) มาก่อน · บทนี้ไม่เพิ่มโค้ดใหม่ — เปิดดูข้างในของที่บท 138 ติดตั้งไว้

บท 138 รูปปกขึ้นจอได้แล้ว · บทนี้ดูว่าไฟล์วิ่งทางไหน — และทำไมทางที่ถูกคือไม่ผ่าน Rails
อ่านจบบทนี้ คุณจะอ่าน URL ของรูปที่มี X-Amz-Signature ออกว่าแต่ละท่อนคืออะไร · รู้ว่ามันหมดอายุเมื่อไหร่และหมดแล้วเห็นอะไร · ชี้ใน Network ได้ว่าตอนอัปรูปไฟล์ไปหา MinIO ตรง ๆ ส่วน Rails ได้แค่รหัส · เลือกได้ว่าเมื่อไหร่ให้ Rails บอกทาง (redirect) เมื่อไหร่ให้ Rails ส่งไฟล์เอง (proxy) · และรู้ว่าลบรูปแล้วต้องเช็คอะไรก่อนบอกเจ้าของว่า "ลบแล้ว"

🔁 ทวนก่อนเริ่ม — คำพวกนี้จะโผล่ในบทนี้

  • object storage · bucket · MinIO (บท 138) — โกดังรับฝากของนอกร้าน · bucket wongnok-dev คือห้องหนึ่งในโกดัง ตั้งเป็น private (ห้ามคนนอกเข้า) · MinIO พูด "ภาษาเดียวกับ S3 ของ Amazon"
  • blob · attachment (บท 138) — blob = ใบรับฝาก (ชื่อไฟล์ ขนาด ชนิด และ key = เลขช่องเก็บในโกดัง) · attachment = ป้ายว่าของชิ้นนี้ของแฟ้มไหน (โพสต์เลขอะไร ช่อง cover)
  • direct_upload: true · ActiveStorage.start() (บท 138) — สองบรรทัดที่เปิดไว้ในฟอร์มกับ application.js · บทนี้ดูว่ามันทำอะไรจริง
  • 302 · location: (บท 102) — คำตอบที่บอกว่า "ของไม่อยู่ที่นี่ ไปเอาที่ location" · เบราว์เซอร์เดินตามเอง · curl ไม่เดินตาม
  • DevTools แท็บ Network (บท 130) — รายการทุกคำขอที่เบราว์เซอร์ยิงออกไป · CORS (บท 39 ฝั่ง Go) — เบราว์เซอร์ถามเว็บปลายทางก่อนว่า "ยอมให้หน้าเว็บจากที่อื่นส่งของมาไหม"

ประโยคเดียวของบทนี้: แอปออกใบอนุญาต ไม่ได้แบกไฟล์เอง

ตอนนี้ไฟล์รูปอยู่ใน MinIO แล้ว · คำถามต่อไปคือใครเป็นคนขนไฟล์ระหว่างเบราว์เซอร์กับ MinIO · ถ้าให้ Rails ขนเอง รูปขนาด 600 KB ที่คนเปิดดู 1,000 ครั้ง = Rails ต้องอ่านไฟล์จาก MinIO แล้วส่งต่อ 600 MB

ระหว่างส่ง Rails ต้องกันคนรับคำขอไว้หนึ่งคนจนกว่าจะส่งเสร็จ · และ Rails มีคนรับคำขอจำกัด (Puma = โปรแกรมที่รับคำขอแทน Rails · ไฟล์ config/puma.rb ของเราตั้งไว้ 3 คน) · ถ้าคนรับคำขอทุกคนกำลังขนรูป คนที่แค่อยากเปิดหน้าบทความก็ต้องรอคิว

ทางที่ Active Storage ใช้คือ Rails ไม่ขนไฟล์ แต่ออก "ใบอนุญาต" ให้เบราว์เซอร์ไปคุยกับ MinIO เอง · ใช้สองทิศ:

ขาออก — มีคนเปิดดูรูป เบราว์เซอร์ ──① ขอรูป────────────────────▶ Rails (:3000) เบราว์เซอร์ ◀─② 302 + URL ที่เซ็นแล้ว───── Rails (Rails แค่เซ็นชื่อ ไม่แตะไฟล์) เบราว์เซอร์ ──③ ดึงไฟล์ตรง────────────────▶ MinIO (:9000) ขาเข้า — มีคนอัปรูป (direct upload) เบราว์เซอร์ ──① ขอใบอนุญาต (ชื่อ ขนาด ลายนิ้วมือไฟล์)──▶ Rails เบราว์เซอร์ ◀─② URL ที่เซ็นแล้ว สำหรับส่งไฟล์───────── Rails เบราว์เซอร์ ──③ ส่งไฟล์ตรง──────────────────────────▶ MinIO เบราว์เซอร์ ──④ ส่งฟอร์ม (มีแค่รหัสของไฟล์)─────────▶ Rails
🍜 เทียบกับร้านอาหาร

ร้านของเราฝากของไว้ที่โกดังรับฝากของนอกร้าน (MinIO) · ถ้าให้พนักงานเดินไปแบกของจากโกดังมาให้ลูกค้าทุกครั้ง หน้าร้านจะไม่มีคนรับออเดอร์ · ร้านจึงทำแค่ออกบัตรผ่านที่มีลายเซ็นของร้านให้ลูกค้าเดินไปที่โกดังเอง · คนเฝ้าโกดังตรวจลายเซ็นบนบัตรได้เองโดยไม่ต้องโทรถามร้าน · บัตรเขียนไว้ว่าใช้ได้ 5 นาที และใช้กับของชิ้นเดียวที่ระบุไว้

ที่ไม่เหมือนกัน: บัตรผ่านจริงมักมีชื่อคนถือ คนเฝ้าดูหน้าก่อนให้เข้า · URL ที่เซ็นแล้วไม่มีชื่อใคร — ใครถือ URL ก็เปิดได้ภายใน 5 นาที (ส่งต่อในแชตก็เปิดได้) · และ "ตรวจลายเซ็นเอง" ของ MinIO คือการคำนวณทางคณิตศาสตร์ด้วยรหัสลับที่ร้านกับโกดังรู้ร่วมกัน ไม่ใช่การดูลายมือ

เทียบของที่รู้: ถ้าเคยทำ JWT ใน บท 49 (Go) — คือไอเดียเดียวกัน: ข้อมูลที่เซ็นแล้ว + มีเวลาหมดอายุ ฝั่งที่รับตรวจลายเซ็นเองได้โดยไม่ต้องถามฐานข้อมูล · ต่างกันแค่ JWT เป็น "บัตรที่บอกว่าคุณเป็นใคร" ส่วน URL ที่เซ็นแล้วเป็น "บัตรที่บอกว่าเปิดไฟล์นี้ได้"

อ่าน URL ที่เซ็นแล้วทีละท่อน

ท่อนแปลเป็นภาษาคน
/wongnok-dev/16r6iq…ห้อง wongnok-dev · ช่องเก็บเลข 16r6iq… (= key ของ blob สุ่มมาตอนอัป · ไม่ใช่ชื่อ cover.jpg)
response-content-disposition · response-content-typeสั่ง MinIO ว่าตอนส่งไฟล์ ให้บอกเบราว์เซอร์ว่า "นี่คือรูป jpeg ชื่อ cover.jpg · เปิดโชว์ในหน้า (inline) ไม่ต้องดาวน์โหลด"
X-Amz-Algorithmวิธีคำนวณลายเซ็น (มาตรฐานของ S3 ชื่อ Signature Version 4) · MinIO พูดภาษา S3 จึงใช้ชื่อขึ้นต้น X-Amz- (Amz = Amazon)
X-Amz-Credential"ใครเซ็น" — minioadmin คือ access key id (ชื่อผู้ใช้ของโกดัง) + วันที่ + us-east-1 (ค่า region ที่เขียนไว้ใน config/storage.yml บท 138 · S3 จริงใช้บอกว่าโกดังอยู่ประเทศไหน) · รหัสลับ (secret) ไม่อยู่ใน URL
X-Amz-Dateเวลาที่เซ็น · T031855Z = 03:18:55 เวลาสากล (Z) = 10:18:55 เวลาไทย (บวก 7 ชั่วโมง) — ตรงกับบรรทัด date: ของคำตอบ 302
X-Amz-Expires=300ใช้ได้ 300 วินาทีนับจาก X-Amz-Date = 5 นาที
X-Amz-SignedHeaders=hostลายเซ็นครอบหัวคำขอตัวไหนด้วย · ตรงนี้แค่ host (= ต้องเรียกที่ localhost:9000 เท่านั้น)
X-Amz-Signatureลายเซ็น · คำนวณจากทุกท่อนด้านบน + รหัสลับของ MinIO ที่อยู่ใน credentials ของเรา (บท 138)

MinIO รู้รหัสลับตัวเดียวกัน · พอได้คำขอ มันคำนวณลายเซ็นซ้ำจากทุกท่อนในคำขอ · ถ้าตรงกับ X-Amz-Signature = ร้านออกบัตรนี้จริงและไม่มีใครแก้ตัวอักษรสักตัว · แล้วค่อยเช็คว่ายังไม่หมดเวลา

คนที่ได้ URL นี้ไปอยากเปิดได้นานขึ้น · เลยแก้ X-Amz-Expires=300 เป็น X-Amz-Expires=86400 (1 วัน) แล้วเปิดทันที (ยังไม่ถึง 5 นาที) · -w '\n[%{http_code}]\n' = ให้ curl พิมพ์เลข status ในวงเล็บเหลี่ยมตอนจบ:

$ curl -s "http://localhost:9000/wongnok-dev/16r6iq…&X-Amz-Expires=86400&X-Amz-SignedHeaders=host&X-Amz-Signature=…" -w '\n[%{http_code}]\n'

(การแก้ URL เล่นแบบนี้ ทำได้กับแอปในเครื่องตัวเองเท่านั้น · ห้ามลองกับเว็บหรือ storage ของคนอื่น)

ได้รูป และเปิดได้ 1 วัน · ได้รูปแต่ยังหมดใน 5 นาที · หรือไม่ได้อะไรเลย?

ถ้าเปิด bucket ให้ทุกคนอ่านได้ ก็ไม่ต้องเซ็นอะไร URL สั้นกว่า · สไลด์หน้า 10 ให้เหตุผลที่ไม่ทำ 4 ข้อ เล่าเป็นภาษาคน:

  1. URL หลุดแล้วเก็บคืนไม่ได้ — สไลด์ยกตัวอย่างว่า URL ไปโผล่ใน log · ใน referrer (หัวคำขอที่บอกเว็บปลายทางว่ามาจากหน้าไหน) · ในแชต · ของ public เปิดได้ตลอด · ของที่เซ็นแล้วหลุดไปก็ตายใน 5 นาที
  2. ลบในแอปแล้วแต่ไฟล์ยังเปิดได้ — ลบข้อมูลใน DB แล้วลืมลบไฟล์ = คนที่จำ URL ไว้ยังเปิดได้ตลอดกาล (หัวข้อท้ายบทจะเห็นว่าเรื่องนี้เกิดกับเราได้แม้ bucket ไม่ public)
  3. ของส่วนตัวกลายเป็นของสาธารณะเงียบ ๆ — วันหนึ่งมีคนอัปใบเสร็จ/บัตรประชาชนเข้า bucket เดียวกัน ไม่มีใครรู้ว่ามันเปิดให้โลกดู
  4. เครื่องมือค้นหาเก็บไปได้ — Google อาจเก็บไฟล์ที่ไม่ควรถูกค้นเจอไปขึ้นผลค้นหา
