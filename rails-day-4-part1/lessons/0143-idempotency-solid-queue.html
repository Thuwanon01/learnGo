🔁 ทวนก่อนเริ่ม — บทนี้ใช้คำพวกนี้

  • at-least-once (บท 142) — คิวที่ไม่ยอมให้งานหาย ต้องยอมให้งานซ้ำ (worker ทำเสร็จแต่ตายก่อนบอกคิว → คิวแจกใบงานเดิมอีกรอบ)
  • perform_later · worker · async (บท 142) — แขวนใบงานแล้วกลับทันที · worker คือโปรแกรมที่หยิบใบงานไปทำ · async เก็บใบงานในหน่วยความจำ ปิดโปรแกรมแล้วหาย
  • idempotency (Go บท 36) — PUT ยิงซ้ำได้ผลเดิม · POST ยิงซ้ำได้ของเบิ้ล
  • migration ปลอดภัย (บท 109) — add_column พร้อม default ไม่ต้องเขียนทุกแผ่น · index ใช้ algorithm: :concurrently คู่กับ disable_ddl_transaction! · strong_migrations ดักท่าอันตรายก่อนถึงตู้ · การเติมข้อมูลแถวเดิม (backfill) อยู่ใน rake task ไม่ใช่ใน migration
  • ช่องว่างระหว่าง "ตรวจ" กับ "เก็บ" (บท 111) — สองโปรแกรมตรวจพร้อมกัน ผ่านทั้งคู่ แล้วเก็บซ้ำ · unique index ที่ตัวตู้คือด่านสุดท้ายที่กันได้จริง

3 ท่าที่ใช้จริง — ทำให้ job รันซ้ำแล้วไม่พัง

สไลด์หน้า 19 สรุปไว้ 3 ท่า · เรียงจาก "ดีที่สุดถ้าทำได้" ไปจนถึง "ท่าสุดท้ายเมื่อไม่มีอะไรให้ดู":

ท่าทำยังไงเหมาะกับ
1 · ธรรมชาติของงานเขียนงานเป็น "ตั้งค่าให้เป็น" หรือ "คำนวณใหม่จากของจริง" แทน "บวกเพิ่มจากค่าเดิม"ดีที่สุด ถ้าออกแบบได้ — ไม่ต้องตรวจอะไรเลย
2 · guard สถานะดูสถานะในตารางก่อน · ทำไปแล้วก็ไม่ทำงานที่มีสถานะให้ดู · สไลด์อ้างว่าใช้ได้ 90% ของงาน · บทนี้ใช้ท่านี้
3 · idempotency key + unique indexตั้งชื่อเฉพาะให้งานแต่ละชิ้น จดลงตาราง · ตู้ไม่ยอมให้ชื่อซ้ำงานที่ไม่มีสถานะให้ดู เช่น ส่งอีเมล · ใช้จริงในบท 144

ตัวอย่างสั้น ๆ ของแต่ละท่า — ยังไม่ต้องพิมพ์ เป็นตัวอย่างสมมติทั้งก้อน (คอลัมน์ comments_count · ตาราง JobRun · method send_the_email ยังไม่มีในแอป ตั้งชื่อขึ้นมาให้อ่านง่าย):

# ท่า 1 — ซ้ำได้: นับใหม่จากของจริงทุกครั้ง (รันกี่รอบก็ได้เลขเท่าจำนวนความเห็นจริง)
post.update!(comments_count: post.comments.count)
# ท่า 1 — ซ้ำแล้วพัง: บวกเพิ่มจากค่าเดิม (รันสามรอบ = +3)
post.update!(comments_count: post.comments_count + 1)

# ท่า 2 — guard: ดูสถานะก่อน ทำไปแล้วก็ออกเลย
return if post.published?
post.update!(status: :published, published_at: Time.current)

# ท่า 3 — key: จดชื่อเฉพาะของงานลงตาราง ที่คอลัมน์ key มี unique index
key = "notify-#{post.id}-#{follower.id}"
JobRun.create!(key: key)   # ชื่อนี้มีแล้ว → ตู้ปฏิเสธ (error) → ไม่ไปส่งซ้ำ
send_the_email
  • ท่า 1 — คุณเจอมาแล้วโดยไม่รู้ตัว: find_or_create_by! ใน seeds (บท 120) "หาก่อน ไม่มีค่อยสร้าง" รันซ้ำแล้วไม่เบิ้ล
  • ท่า 2 — return if … คือ "ถ้า … ก็ออกจาก method เลย" · บรรทัดเดียวที่เปลี่ยน job ธรรมดาให้ซ้ำได้
  • ท่า 3 — ใช้เมื่องานไม่ทิ้งร่องรอยให้ดู · อีเมลส่งออกไปแล้วไม่มีช่องไหนในตาราง posts บอกได้ว่า "ส่งให้คนนี้แล้ว" จึงต้องสร้างตารางจดเอง · และต้องเป็น unique index (ด่าน ④ ของบท 111) ไม่ใช่แค่ exists? ในโค้ด เพราะสอง worker อาจตรวจพร้อมกันแล้วผ่านทั้งคู่ — ช่องว่างเดียวกับที่บท 111 เจอ

ท่า 2 = ดูป้ายก่อนทำ · ใบงาน "เปิดร้าน" เขียนกำกับว่า "ถ้าป้ายเป็น 'เปิด' อยู่แล้ว ไม่ต้องทำอะไร" · คนที่หยิบใบงานซ้ำมาเห็นป้ายก็วางใบงานลง

ท่า 3 = สมุดจดเลขใบงานที่ทำแล้ว · งาน "ส่งข้าวกล่องให้คุณสมชาย" ไม่มีป้ายให้ดู · ร้านเลยมีสมุดเล่มหนึ่ง ใครจะออกไปส่งต้องเขียนเลขใบงานลงสมุดก่อน ถ้าเลขนี้มีอยู่แล้ว = มีคนส่งไปแล้ว ไม่ต้องไป

ที่ไม่เหมือนกัน: สมุดกระดาษ สองคนเขียนเลขเดียวกันพร้อมกันได้ (ต่างคนต่างเปิดดูแล้วไม่เห็น) · unique index ของตู้ไม่ยอมให้แผ่นที่สองเข้าลิ้นชักเลย — คนที่ช้ากว่าเสี้ยววินาทีได้ error กลับไป นี่คือเหตุที่ท่า 3 ต้องพึ่งตู้ ไม่ใช่โค้ด

ศัพท์ที่เอาไปคุยต่อได้
guard (guard clause)
บรรทัดตรวจเงื่อนไขต้น method ที่ "ออกก่อน" ถ้าไม่ควรทำ · พิมพ์บอก AI ได้ว่า "add a state guard so the job is a no-op when the post is already published"
idempotency key
ชื่อเฉพาะของงานหนึ่งชิ้น ใช้ตรวจว่าเคยทำแล้วหรือยัง · คำเดียวกับหัว Idempotency-Key ที่ client ส่งมากับ POST ใน Go บท 36
unique constraint
กฎที่ตัวตู้ "ห้ามซ้ำ" (สร้างด้วย unique index) · ใน Rails ชนแล้วได้ ActiveRecord::RecordNotUnique · ถาม senior ได้ว่า "อันนี้กันซ้ำที่ DB หรือแค่ในโค้ดครับ"

Active Job คือหน้ากาก · Solid Queue คือคิวที่อยู่ในตาราง Postgres

Active Job คือชุดเครื่องมือเขียน job ที่มากับ Rails — ApplicationJob · perform · perform_later ที่ใช้ในบท 142 ทั้งหมดมาจากมัน · สไลด์หน้า 20 เรียกมันว่า "หน้ากาก": โค้ด job ของเราหน้าตาเหมือนเดิม ไม่ว่าข้างหลังจะเก็บใบงานไว้ที่ไหน

ตัวที่อยู่ข้างหลังคือ adapter (ตัวเสียบ — บท 142) · บท 142 ใช้ async (ใบงานอยู่ในหน่วยความจำ ปิดโปรแกรมแล้วหาย) · บทนี้เปลี่ยนเป็น Solid Queue = adapter ที่เก็บใบงานเป็นแถวในตาราง Postgres · เปลี่ยน adapter ด้วย config บรรทัดเดียว ไม่ต้องแก้ job

ทำไมเป็น Solid Queue: เป็น adapter ค่าเริ่มต้นของ Rails 8 (production ของเราตั้ง :solid_queue ไว้แล้ว) · ไม่ต้องติดตั้งโปรแกรมคิวเพิ่ม (เช่น Redis — บท 32 ของ Go) · แบบฐานข้อมูลก้อนเดียวที่เราจะตั้งในขั้น 3 สำรองข้อมูล (backup) ครั้งเดียวได้ทั้งข้อมูลและใบงานที่ค้าง · และเปิดดูคิวด้วย SQL ได้

ที่แลกมา: สไลด์อ้างว่ารับงานต่อวินาทีได้น้อยกว่าคิวบน Redis แต่พอสำหรับงานส่วนใหญ่

Active Job = แบบฟอร์มใบงานมาตรฐานของร้าน · เชฟกรอกแบบเดียวกันเสมอ (ชื่องาน + เลขแฟ้ม) · adapter = ที่แขวนใบงาน — บท 142 คือโน้ตในกระเป๋าเสื้อเชฟ · บทนี้คือลิ้นชักหนึ่งในตู้แฟ้มเดิม ที่ร้านกันไว้เป็นกระดานแขวนใบงาน

ปิดครัว (ปิด server) แล้วตู้แฟ้มยังอยู่ · ใบงานในลิ้นชักก็ยังอยู่ · พนักงานหลังร้าน (โปรแกรม bin/jobs) มาถึงเมื่อไรก็หยิบไปทำต่อได้

ที่ไม่เหมือนกัน: พนักงานจริงเห็นใบงานใหม่ทันทีที่แขวน · bin/jobs ต้องคอยเปิดลิ้นชักดูเป็นรอบ ๆ (ไฟล์ config/queue.yml ของเราตั้งไว้ทุก 1 วินาที) · และถ้าไม่มีพนักงานมาเลย ใบงานก็นอนในลิ้นชักเงียบ ๆ ไม่มีใครเตือน

เทียบกับ Go (บท 26 worker pool): channel jobs = คิว แต่อยู่ในหน่วยความจำของโปรแกรมเดียวกัน — ตรงกับ async · Solid Queue ย้าย "channel" ไปเป็นตารางในฐานข้อมูล worker จึงเป็นอีกโปรแกรมหนึ่ง และอยู่คนละเครื่องกับเว็บก็ได้

ขั้น 1 · บทความมีสถานะ — migration สองไฟล์

ตอนนี้บทความทุกชิ้นโชว์ทันทีที่บันทึก · เราต้องการ 3 สถานะ: ร่าง (ยังไม่โชว์) · ตั้งเวลา (รอถึงเวลา) · เผยแพร่แล้ว · และเวลาอีกสองช่อง: scheduled_at = เวลาที่อยากให้ออก · published_at = เวลาที่ออกจริง

1.1 สร้างไฟล์ migration (หน้าต่างที่สอง):

$ bin/rails generate migration AddPublishingToPosts status:string scheduled_at:datetime published_at:datetime
      invoke  active_record
      create    db/migrate/20261110034656_add_publishing_to_posts.rb

Rails เขียน add_column มาให้ 3 บรรทัด · เปิดไฟล์นั้นแล้วแก้ทั้งไฟล์เป็น:

class AddPublishingToPosts < ActiveRecord::Migration[8.1]
  # expand: เพิ่มคอลัมน์อย่างเดียว ไม่ UPDATE แถวเดิมทีละแถว (Postgres 11+ เก็บ default ไว้ที่ตัวตาราง ไม่เขียนทับทุกแถว)
  def change
    # บทความเดิมทุกแถวถือว่าเผยแพร่แล้ว → ใส่ default "published" ตอนเพิ่มคอลัมน์
    add_column :posts, :status, :string, null: false, default: "published"
    # จากนี้ไปบทความใหม่เริ่มเป็นฉบับร่าง
    change_column_default :posts, :status, from: "published", to: "draft"
    add_column :posts, :scheduled_at, :datetime
    # published_at ของบทความเดิม เติมด้วย rake task (bin/rails posts:backfill_published_at)
    add_column :posts, :published_at, :datetime
  end
end
  • status, :string — เก็บสถานะเป็นคำ ("draft") ไม่ใช่ตัวเลข · เปิดตารางดูด้วย SQL แล้วอ่านรู้เรื่องทันที
  • null: false, default: "published" — ห้ามว่าง · และแถวเดิม 30 แถวได้ค่า "published" ทันที โดยไม่ต้องเขียนทีละแถว (บท 109: Postgres จดค่าเริ่มต้นไว้ที่ตัวตาราง)
  • change_column_default … from: "published", to: "draft" — เปลี่ยนค่าเริ่มต้นทันทีหลังเพิ่ม · แถวเดิมยังเป็น published · แถวที่สร้างหลังจากนี้ได้ draft · ใส่ from: ไว้ให้ Rails รู้วิธีย้อนกลับ (rollback)
  • ทำไมไม่ตั้ง default เป็น "draft" แล้วเขียนงานเปลี่ยน "draft → published" ทีหลัง: งานนั้นรันซ้ำไม่ได้ — รันอีกรอบวันหน้าจะไปเผยแพร่ร่างจริงของผู้ใช้ด้วย · ท่าสองจังหวะนี้ไม่มีงานแบบนั้นเลย
  • scheduled_at · published_at — :datetime = วันที่ + เวลา · ว่างได้ (ร่างไม่มีเวลา)

class AddPublishingIndexesToPosts < ActiveRecord::Migration[8.1]
  # concurrently = สร้าง index โดยไม่ล็อกการเขียนตาราง posts (ต้องอยู่นอก transaction)
  disable_ddl_transaction!

  def change
    # ตัวกวาดทุกนาทีค้น "ถึงเวลาแล้วหรือยัง" ด้วย scheduled_at
    add_index :posts, :scheduled_at, algorithm: :concurrently
    # หน้ารวมเรียงบทความตามเวลาเผยแพร่
    add_index :posts, :published_at, algorithm: :concurrently
  end
end
  • index ของ scheduled_at — บท 144 จะมีตัวกวาดที่ถามตู้ทุกนาทีว่า "ใครถึงเวลาแล้วบ้าง" · index = ป้ายแท็บข้างลิ้นชัก หาได้โดยไม่ต้องเปิดทุกแฟ้ม

ขั้น 2 · model รู้จักสถานะ และเติม published_at ให้บทความเดิม

ตู้มีคอลัมน์แล้ว แต่ model ยังไม่รู้ว่า status มีได้แค่ 3 คำ · Rails มีเครื่องมือชื่อ enum (ย่อจาก enumeration = "รายการค่าที่เลือกได้") ประกาศครั้งเดียว ได้ทั้งการตรวจค่า และคำถามสำเร็จรูปอย่าง post.draft? · Post.published

2.1 เปิด app/models/post.rb · เพิ่มสามจุด · บรรทัดของเดิม (has_one_attached · validates :title · validates :body · scope :recent) ใส่ไว้ให้ดูตำแหน่ง ที่เหลือคือของใหม่:

  has_one_attached :cover

  # สถานะเก็บเป็นคำ (string) อ่านใน SQL ได้ตรง ๆ · ได้ scope ฟรี: Post.draft / Post.scheduled / Post.published
  # validate: true = ส่งค่าแปลก ๆ มาจากฟอร์ม → ได้ error ในฟอร์ม ไม่ใช่หน้า error
  enum :status, { draft: "draft", scheduled: "scheduled", published: "published" }, validate: true

  validates :title, presence: true, length: { maximum: 120 }
  validates :body, presence: true
  validates :scheduled_at, presence: true, if: :scheduled?
  # published ได้ทางเดียวคือ PublishPostJob (ตั้ง published_at ให้) · ฟอร์มส่ง status=published มาเองจะติดข้อนี้
  validates :published_at, presence: true, if: :published?
  # ตรวจเฉพาะตอนแนบรูปใหม่ …   (บรรทัดเดิม)
  …
  scope :recent, -> { order(created_at: :desc) }
  # หน้ารวม: เฉพาะที่เผยแพร่แล้ว ใหม่สุดก่อน
  scope :latest_published, -> { published.order(published_at: :desc) }
  • enum :status, { draft: "draft", … } — ชื่อในโค้ด (ซ้าย) กับคำที่เก็บในตู้ (ขวา) ตรงกัน · ได้ของฟรี: post.scheduled? (ถาม) · Post.draft (ค้นเฉพาะร่าง) · Post.not_published (ทุกอย่างที่ยังไม่เผยแพร่ — ขั้น 5 ใช้)
  • validate: true — ค่าที่ไม่อยู่ในรายการกลายเป็นข้อความ error ในฟอร์ม · ไม่ใส่ = Rails โยน error ทั้งหน้า
  • validates :scheduled_at, presence: true, if: :scheduled? — ถ้าเลือก "ตั้งเวลา" ต้องกรอกเวลาด้วย · if: = กฎนี้ใช้เฉพาะบางกรณี
  • validates :published_at, … if: :published? — เผยแพร่แล้วต้องมีเวลาเผยแพร่ · ทำให้ฟอร์มแอบส่ง status=published มาเองไม่ได้ เพราะฟอร์มไม่มีช่อง published_at
  • scope :latest_published — คำถามสำเร็จรูปของหน้ารวม แบบเดียวกับ scope :recent ที่สร้างในบท 126

2.2 บทความเดิม 30 ชิ้นเป็น published แล้ว แต่ published_at ยังว่าง · เติมด้วย rake task (บท 109: การเติมข้อมูลไม่อยู่ในไฟล์ migration) · เปิด lib/tasks/posts.rake ที่มี task backfill_body จากบท 137 อยู่แล้ว · พิมพ์ต่อท้าย ก่อน end บรรทัดสุดท้าย:


  desc "เติม published_at ให้บทความที่เผยแพร่แล้วแต่ยังไม่มีเวลาเผยแพร่ (ใช้เวลาที่สร้าง) — รันซ้ำได้"
  task backfill_published_at: :environment do
    # เลือกเฉพาะแถวที่ยังว่าง → รันรอบสองไม่ทับของเดิม · ทีละ 1,000 แถว ไม่ล็อกทั้งตาราง
    Post.published.where(published_at: nil).in_batches(of: 1000) do |posts|
      posts.update_all("published_at = created_at")
    end

    puts "เผยแพร่แล้ว #{Post.published.count} · ยังไม่มี published_at #{Post.published.where(published_at: nil).count}"
  end
  • Post.published.where(published_at: nil) — นี่คือท่า 2 (guard) ในรูปของคำค้น: เลือกเฉพาะแถวที่ยังไม่ได้ทำ
  • in_batches(of: 1000) — แบ่งทีละ 1,000 แถว (บท 109) · update_all("published_at = created_at") — ให้ตู้ก็อปเวลาที่สร้างมาใส่เองในคำสั่งเดียว ไม่โหลดแฟ้มมาทีละแผ่น

อย่าใช้ bin/rails generate task posts … — ไฟล์ posts.rake มีอยู่แล้ว generator จะถามว่าจะเขียนทับไหม · ตอบ Y แล้ว task backfill_body หายทั้งก้อน

ขั้น 3 · ติดตั้ง Solid Queue ในฐานข้อมูลก้อนเดิม

แอปที่สร้างด้วย Rails 8 มีไฟล์ของ Solid Queue ติดมาแล้ว: config/queue.yml (ตั้งค่า worker) · bin/jobs (คำสั่งเปิด worker) · db/queue_schema.rb (แบบของตารางคิว) · แต่ development ยังไม่ได้ใช้เลย

ส่วน production.rb มีบรรทัด connects_to ที่สั่งให้คิวไปอยู่ในฐานข้อมูลอีกก้อนหนึ่ง (ตู้แฟ้มใบที่สอง) · README ของ Solid Queue แนะนำแบบแยกก้อน แต่เราเลือกก้อนเดียวกับข้อมูล เพราะ compose ของเรามี Postgres ก้อนเดียว ตั้งค่าน้อยกว่า

README มีหัวข้อ "Single database configuration" รองรับแบบก้อนเดียว 3 ข้อ: ① ก็อป queue_schema.rb เป็น migration · ② ลบ connects_to จาก production · ③ migrate

# เผยแพร่บทความที่ตั้งเวลาไว้ เมื่อถึงเวลาแล้ว
# ห้ามสมมติว่ารันครั้งเดียว: กดปุ่มซ้ำ · retry · สอง worker หยิบงานพร้อมกัน → รันกี่รอบผลต้องเหมือนรอบเดียว
class PublishPostJob < ApplicationJob
  queue_as :default

  # รับแค่ id แล้วโหลดสดจาก DB: ได้สถานะ/เวลาล่าสุดเสมอ (ไม่ใช่ค่าเก่าตอนเข้าคิว)
  def perform(post_id)
    post = Post.find(post_id)

    # with_lock = SELECT ... FOR UPDATE แล้วโหลดแถวใหม่: worker ตัวที่สองต้องรอตัวแรกเสร็จก่อน
    # แล้วเห็นว่า published ไปแล้ว → ไม่ทำซ้ำ
    post.with_lock do
      # guard สถานะ: เผยแพร่แล้ว เป็นฉบับร่าง หรือยังไม่ถึงเวลา (ผู้ใช้เลื่อนเวลาออกไป) → ไม่ทำอะไร
      if post.scheduled? && post.scheduled_at <= Time.current
        post.update!(status: :published, published_at: Time.current)
      end
    end
  end
end
  • queue_as :default — generator ใส่มาให้ = แขวนใบงานไว้ที่กระดานชื่อ default · worker ของเราฟังทุกกระดานอยู่แล้ว (queues: "*" ใน config/queue.yml) ไม่ต้องแก้
  • def perform(post_id) + Post.find(post_id) — ใบงานจดแค่เลข id · worker ไปหยิบแฟ้มจากตู้เองตอนจะทำ · ได้ของล่าสุดเสมอ: ถ้าผู้ใช้เปลี่ยนใจกลับเป็นร่างหลังกดปุ่ม job จะเห็นว่าเป็นร่างแล้ว · ถ้าจดสถานะลงใบงานไปด้วย worker จะทำตามข้อมูลเก่าตอนแขวน
  • if post.scheduled? && post.scheduled_at <= Time.current — guard (ท่า 2) · && = "และ" · Time.current = เวลาตอนนี้ตามโซนเวลาของแอป (ใน Rails ใช้ตัวนี้แทน Time.now) · <= = "น้อยกว่าหรือเท่ากับ" คือเวลาที่ตั้งไว้มาถึงหรือเลยมาแล้ว · รวมกันได้ว่า ทำเฉพาะเมื่อ "ตั้งเวลาไว้ และ ถึงเวลาแล้ว" · กันได้ 3 กรณี: เผยแพร่ไปแล้ว (ใบงานซ้ำ) · เป็นร่าง · ผู้ใช้เลื่อนเวลาออกไปหลังแขวนใบงาน (สไลด์เขียนแค่ return if post.published? ซึ่งกันได้กรณีแรกกรณีเดียว)
  • post.update!(status: :published, published_at: Time.current) — ที่เดียวในแอปที่ตั้ง published_at · ! = บันทึกไม่ผ่านให้พังดัง ๆ (job พังแล้วบท 144 จะสอนให้ลองใหม่)
  • post.with_lock do … end — ดูหัวข้อถัดไป

with_lock — สอง worker หยิบใบงานซ้ำพร้อมกัน

guard มีช่องโหว่แบบเดียวกับบท 111: ถ้าสอง worker ถือใบงานเดียวกันในเวลาเดียวกัน ทั้งคู่ตรวจแล้วเห็นว่า "ยัง scheduled" ทั้งคู่ แล้วเผยแพร่ทั้งคู่ · เกิดได้จริงเมื่อมีใบงานซ้ำในคิว (กดปุ่มสองที · retry = ลองทำใหม่หลังพัง) และ worker ทำหลายใบพร้อมกัน (ของเราตั้งไว้ 3 ใบพร้อมกัน — threads: 3 ใน config/queue.yml · thread ≈ goroutine ของ Go)

with_lock คือการล็อกแถว: เปิด transaction (บท 111) แล้วขอแฟ้มแผ่นนี้แบบ "ห้ามคนอื่นแก้จนกว่าฉันจะเสร็จ" (SQL: SELECT … FOR UPDATE) พร้อมโหลดค่าล่าสุดมาใหม่ · ล็อกปล่อยตอน COMMIT (จบ transaction) · worker ตัวที่สองต้องรอจนถึงตอนนั้น · พอได้แฟ้มก็เห็นว่า published แล้ว guard จึงไม่ทำอะไร

ตัวเลือกที่ 1 ผิด — ทั้งคู่ตรวจในเสี้ยววินาทีเดียวกัน ตอนนั้นยังไม่มีใครเผยแพร่ · ตัวเลือกที่ 3 ผิด — การแก้แถวเดียวกันสองครั้งไม่ใช่ error ตัวที่สองแค่รอแล้วเขียนทับ · ตัวเลือกที่ 4 ผิด — ใบงานซ้ำในคิวเกิดได้จาก retry หรือกดปุ่มสองที (ลองแล้ว: กดสองทีขณะปิด worker ได้ใบงาน 2 ใบ worker ทำพร้อมกัน แต่มี UPDATE แค่ครั้งเดียวเพราะ with_lock)

ตัวเลือกที่ 1 ถูก — ระหว่างแขวนกับทำอาจห่างกันเป็นนาที (worker ปิดอยู่) · ผู้ใช้อาจถอนกลับเป็นร่าง หรือเลื่อนเวลา · guard ตรวจกับของล่าสุดถึงจะถูก
