Background jobs — งานที่ผู้ใช้ไม่ควรรอ และทำไม "ทำพอดีครั้งเดียว" ไม่มีจริง

~20 นาทีอ่าน + ทดลองตามอีก ~10 นาที · ควรผ่าน บท 141 (จบบล็อก D) · Day 2 บท 112 (callback) · และ Go บท 21 · บท 26 มาก่อน

ตอนนี้ถ้าการกด "บันทึก" ต้องส่งอีเมล ย่อรูป และอื่น ๆ ไปด้วย ผู้ใช้จะยืนรอหน้าขาวจนครบทุกอย่าง · บทนี้จะทำให้หน้าค้าง 9 วินาทีให้เห็นกับตา แล้วแก้ให้เหลือราว 0.1 วินาทีด้วย background job
อ่านจบแล้วคุณจะ ตัดสินได้ว่างานไหนควรให้ผู้ใช้รอ งานไหนไม่ควร · สร้าง job และสั่ง perform_later ได้ · อธิบายได้ว่าทำไมงานในคิว หายได้หรือซ้ำได้ แต่รับประกัน "พอดีครั้งเดียว" ไม่ได้ — ประโยคข้อ ② ใน "3 ประโยคของวัน" ที่บท 136 บอกให้จำ

🔁 ทวนก่อนเริ่ม — บทนี้ใช้คำพวกนี้

  • log ของ request — บรรทัด Started POST … ถึง Completed 302 Found in …ms คือหนึ่งใบสั่งอาหาร · ตัวเลข ms คือลูกค้ายืนรอนานแค่ไหน (Day 2–3)
  • callback (บท 112) — โค้ดที่ Rails เรียกเองตอนบันทึก · กฎในบทนั้น: callback ควรดูแลแค่แฟ้มของตัวเอง งานที่ต้องคุยกับคนอื่น (อีเมล ระบบอื่น) ให้คิดก่อนว่าควรอยู่ใน callback จริงไหม · และบอกว่าอีเมลแจ้งผู้ติดตาม "ฝากให้ job ส่งทีหลัง"
  • goroutine (Go บท 21) — go f() แยกงานไปทำพร้อมกัน · main จบ = goroutine ที่ค้างตายหมดแบบเงียบ ๆ
  • worker pool (Go บท 26) — งานกองรวมใน channel jobs แล้วมีคนงานหลายตัวมาหยิบไปทำ
  • idempotency (Go บท 36) — ยิงซ้ำกี่ครั้งผลก็เหมือนเดิม · และ find_or_create_by! ใน seeds (บท 120) ที่รันซ้ำแล้วข้อมูลไม่เบิ้ล

ลองทำให้หน้าค้างเอง — งาน 9 วินาทีใน request เดียว

สไลด์หน้า 16 ยกตัวอย่าง action create ที่บันทึกบทความแล้วทำต่ออีกสามอย่าง: ส่งอีเมลแจ้งผู้ติดตาม (3 วิ) · ส่งเข้าระบบค้นหา (2 วิ) · ย่อรูปปก (4 วิ) · แอปเรายังไม่มีทั้งสามอย่าง เลยจำลองด้วย sleep (สั่งให้โปรแกรมหยุดรอ N วินาที) — ความช้าเท่ากัน แค่ไม่ได้ทำงานจริง

ขั้น 1 · เปิด app/controllers/posts_controller.rb หา action create แล้วเติมสามบรรทัด sleep ใต้ if @post.save:

  def create
    @post = Post.new(post_params)

    respond_to do |format|
      if @post.save
        sleep 3 # จำลอง: ส่งอีเมลแจ้งผู้ติดตาม
        sleep 2 # จำลอง: ส่งเข้าระบบค้นหา
        sleep 4 # จำลอง: ย่อรูปปก
        format.html { redirect_to @post, notice: "สร้างบทความแล้ว" }
        # … บรรทัดที่เหลือเหมือนเดิม
  • บรรทัด sleep 3 — หยุดรอ 3 วินาที แทน "ส่งอีเมล" · อีกสองบรรทัดเหมือนกัน รวม 9 วินาที
  • ทั้งสามบรรทัดอยู่หลัง @post.save — บทความถูกบันทึกลงตู้เรียบร้อยก่อนจะเริ่มรอ
  • และอยู่ก่อน redirect_to — ผู้ใช้จะยังไม่ได้หน้าถัดไปจนกว่าจะรอครบ

ยังไม่ต้องลบ sleep · หัวข้อถัดไปจะย้ายมันไปอยู่ที่ใหม่ · ถ้าคุณกดบันทึกซ้ำเพราะคิดว่าเว็บค้าง จะได้บทความ "ทดลองงานช้า" สองชิ้น — ปล่อยไว้ ภารกิจท้ายบทพาลบ

เส้นแบ่ง — "ถ้างานนี้ยังไม่เสร็จ ผู้ใช้เห็นหน้าถัดไปได้ไหม"

สไลด์หน้า 16 ให้คำถามข้อเดียวไว้ตัดสินทุกงานที่อยู่ใน action:

  • ได้ → ไม่ต้องให้ผู้ใช้รอ · ส่งไปทำเบื้องหลัง
  • ไม่ได้ → ต้องทำให้เสร็จใน request (ในใบสั่งนี้) ก่อนตอบ
งานยังไม่เสร็จ ผู้ใช้เห็นหน้าถัดไปได้ไหมไปไหน
บันทึกบทความลงตู้ไม่ได้ — หน้าถัดไปคือหน้าบทความ ยังไม่มีบทความก็ไม่มีอะไรให้ดูใน request
ตรวจว่าหัวข้อไม่ว่าง (validation)ไม่ได้ — ต้องรู้ก่อนว่าจะโชว์หน้าบทความหรือโชว์ errorใน request
ส่งอีเมลแจ้งผู้ติดตามได้ — ช้าไป 5 วินาทีก็ไม่มีใครรู้เบื้องหลัง
ส่งเข้าระบบค้นหาได้ — ค้นเจอช้าไปไม่กี่วินาทีไม่มีใครเดือดร้อนเบื้องหลัง
ย่อรูปปกหลายขนาดได้ — หน้าบทความโชว์รูปเดิมไปก่อนได้เบื้องหลัง

ทวนบท 112: ตอนเรียน callback เราได้กฎว่า "callback ควรดูแลแค่แฟ้มของตัวเอง" · และบอกว่าอีเมลแจ้งผู้ติดตาม "ฝากให้ job ส่งทีหลัง" แต่ยังไม่ได้เล่าว่า job คืออะไร (บท 112 เขียนว่า "เรื่องของ Day 3" — ของจริงมาถึงตอนนี้) · job คือปลายทางของคำว่า "ฝาก" นั่นเอง

สไลด์ให้เหตุผลข้อที่สองด้วย: งานที่อยู่ใน job พังแล้วลองใหม่ได้ · งานที่อยู่ใน request พังแล้วหายไปเลย · ประโยคนี้จริงเมื่อคิวเก็บงานไว้ถาวรและตั้งให้ลองใหม่ — สองอย่างที่บท 143–144 จะตั้ง · ในบทนี้คุณจะเห็นว่ายังไม่จริง

background job คืออะไร — ใบงานหลังร้าน

background job คือ "งานที่จดไว้ให้ทำทีหลัง" · controller ไม่ทำเอง แค่เขียนใบงานแขวนไว้ แล้วตอบผู้ใช้ทันที · จะมีโปรแกรมอีกตัวมาหยิบใบงานไปทำตอนว่าง โดยไม่มีผู้ใช้คนไหนยืนรอ

ที่แขวนใบงานเรียกว่า คิว (queue = แถวรอ ใครมาก่อนได้ทำก่อน) · โปรแกรมที่มาหยิบใบงานไปทำเรียกว่า worker (คนงาน)

เทียบกับร้านอาหาร

ลูกค้าสั่งข้าวผัด (request) · หัวหน้าเชฟผัดเสร็จ ยกจานให้ลูกค้า (response) — จบสำหรับลูกค้า · แต่ร้านยังมีงานที่ต้องทำต่อ: ล้างกระทะ · โทรสั่งวัตถุดิบ · ส่งข้าวกล่องไปบ้านลูกค้าอีกคน

เชฟไม่ทำเองตอนนั้น แค่เขียนใบงานหลังร้านแขวนไว้บนกระดาน (คิว) แล้วกลับไปรับออเดอร์ต่อ · พนักงานหลังร้าน (worker) เดินมาหยิบใบงานไปทำทีละใบ

ที่ไม่เหมือนกัน: ร้านจริงถ้าไม่มีพนักงานหลังร้าน ใบงานก็แขวนอยู่เฉย ๆ ไม่มีใครทำ — กับ Rails ก็เป็นแบบนั้นจริงในบท 143 (ต้องเปิด worker แยก) · แต่ในบทนี้ Rails ยังใช้ทางลัดที่ให้ "หัวหน้าเชฟพกผู้ช่วยติดตัวมาเอง" (หัวข้อหลังจากนี้) · และพนักงานในร้านจริงจำได้ว่าทำอะไรไปแล้ว ส่วน worker จำอะไรไม่ได้นอกจากที่เขียนบนใบงาน

เทียบกับ Go (บท 26 worker pool): channel jobs ที่กองงานไว้ = คิว · goroutine ที่วนรับงานจาก jobs = worker · ความต่างคือ worker pool ของ Go อยู่ในโปรแกรมเดียวกับคนส่งงาน · คิวของจริงที่ใช้ใน production (บท 143) อยู่นอกโปรแกรมเว็บ — ต่างกันตรงนี้แหละที่ทำให้งานไม่หาย

ศัพท์ที่เอาไปคุยต่อได้
background job
งานที่แยกออกจาก request ไปทำทีหลัง ผู้ใช้ไม่ต้องรอ · ถาม senior ได้ว่า "งานนี้ควรอยู่ใน request หรือทำเป็น background job ครับ"
queue (คิว)
ที่เก็บงานที่รอทำ เรียงตามลำดับ · คำที่ได้ยินบ่อย: "job ค้างในคิว" = ใบงานแขวนอยู่ ยังไม่มีใครหยิบ
worker
โปรแกรมที่หยิบงานจากคิวไปทำ · "worker ล่ม" = ไม่มีใครทำงาน ใบงานกองสูงขึ้นเรื่อย ๆ
enqueue
เอางานเข้าคิว (แขวนใบงาน) · พิมพ์บอก AI ได้ว่า "move the email sending out of the request and enqueue a background job instead"

  queue_as :default

  def perform(post_id)
    post = Post.find(post_id)
    sleep 3 # จำลอง: ส่งอีเมลแจ้งผู้ติดตาม
    sleep 2 # จำลอง: ส่งเข้าระบบค้นหา
    sleep 4 # จำลอง: ย่อรูปปก
    Rails.logger.info "งานหลังร้านของบทความ #{post.id} เสร็จแล้ว"
  end
end
  • < ApplicationJob — สืบทอดจากแม่แบบของ job ทุกตัวในแอป (เหมือน model สืบจาก ApplicationRecord) · แม่แบบนี้มาจาก Active Job = ชุดเครื่องมือทำ job ที่มากับ Rails (บท 143 เล่าต่อ)
  • queue_as :default — แขวนใบงานไว้บนกระดานชื่อ default · แอปเล็ก ๆ ใช้กระดานเดียวพอ
  • def perform(post_id) — สิ่งที่ worker ทำเมื่อหยิบใบงานนี้ไป · ชื่อ perform บังคับ
  • Post.find(post_id) — ใบงานจดแค่เลข id ของบทความ worker ต้องไปหยิบแฟ้มจากตู้เอง (ทำไมจดแค่เลข — บท 143)
  • sleep สามบรรทัด — ย้ายมาจาก controller ตรง ๆ
  • Rails.logger.info "…" — เขียนหนึ่งบรรทัดลง log ตอนทำครบ · เราจะใช้บรรทัดนี้เป็นหลักฐานว่างานเสร็จจริง

ขั้น 3 · ให้ controller แขวนใบงานแทนทำเอง — กลับไปที่ create ลบ sleep สามบรรทัด ใส่บรรทัดเดียวแทน:

ก่อน — ทำเองใน request

        sleep 3 # จำลอง: ส่งอีเมล…
        sleep 2 # จำลอง: ส่งเข้า…

  • (@post.id) — ของที่ส่งไปจะกลายเป็น post_id ใน perform
  • บรรทัดนี้อยู่หลัง save สำเร็จเท่านั้น — บันทึกไม่ผ่านก็ไม่มีใบงาน (ไม่มีอีเมลเรื่องบทความที่ไม่มีอยู่จริง)

ตอนนี้ใบงานแขวนอยู่ที่ไหน — Async คือคิวในหน่วยความจำ

เราไม่ได้ตั้งค่าคิวเลย แต่ job ก็ทำงาน · ถามแอปได้ว่าตอนนี้ใช้คิวแบบไหน (หน้าต่างที่สอง): 

$ bin/rails runner 'p ActiveJob::Base.queue_adapter_name'
"async"

bin/rails runner '…' = รันโค้ด Ruby หนึ่งบรรทัดในแอปแล้วจบ (ไม่ต้องเปิด console) · p = พิมพ์ค่าออกมา · ActiveJob::Base = แม่แบบตัวบนสุดของ job ทุกตัว (:: อ่านว่า "ที่อยู่ใน") · ได้ "async" · adapter คือ "ตัวเสียบ" ที่บอกว่าใบงานไปเก็บที่ไหน · development ถ้าไม่ตั้งอะไร ได้ async · ส่วน config/environments/production.rb (ค่าตั้งของ production = เครื่องจริงที่ผู้ใช้ใช้) ของเรามีบรรทัดนี้อยู่แล้ว: 

  # Replace the default in-process and non-durable queuing backend for Active Job.
  config.active_job.queue_adapter = :solid_queue

คอมเมนต์บรรทัดบนบอกนิสัยของ async ไว้สองคำ: in-process (อยู่ใน process เดียวกับเว็บ — ตัวโปรแกรมที่กำลังรันอยู่ตัวเดียวกัน) และ non-durable (ไม่ทนทาน — ไม่ได้เขียนเก็บลงที่ไหน) · เอกสาร Rails เขียนตรง ๆ ว่า ถ้า process ดับหรือเครื่องรีเซ็ต งานที่ค้างอยู่หายหมด (ดูลิงก์ท้ายบท)

เทียบกับร้านอาหาร

async เหมือนหัวหน้าเชฟจดใบงานลงกระดาษโน้ตในกระเป๋าเสื้อ แล้วพาผู้ช่วยติดตัวมาเองยืนทำอยู่ข้าง ๆ ในครัวเดียวกัน · สะดวก ไม่ต้องติดกระดาน ไม่ต้องจ้างพนักงานหลังร้าน

แต่ถ้าปิดครัว (หยุด server) เชฟเดินออก — โน้ตกับผู้ช่วยหายไปพร้อมกัน ใบงานที่ยังไม่เสร็จไม่มีใครรู้ว่าเคยมี · บท 143 จะเปลี่ยนเป็น Solid Queue = ติดกระดานไว้ในตู้แฟ้ม (ตารางใน PostgreSQL) ปิดครัวแล้วกระดานยังอยู่

ที่ไม่เหมือนกัน: ผู้ช่วยของ async ไม่ได้มีคนเดียว — เป็นกลุ่มคนงานหลายคนในโปรแกรมเดียวกัน (ทำหลายใบงานพร้อมกันได้) · และ "ปิดครัว" ในโลกจริงไม่ได้เกิดแค่ตอนคุณกด Ctrl+C — ทุกครั้งที่ deploy (เอาเวอร์ชันใหม่ขึ้นเครื่องจริง) server ถูกปิดแล้วเปิดใหม่ นั่นคือเหตุที่ production ห้ามใช้ async

เทียบกับ Go (บท 21): async ก็คือ go f() ดี ๆ นี่เอง · ถ้าใน handler ของ Gin เราเขียน (ตัดมาสองบรรทัด ไม่ใช่ไฟล์เต็ม): 

go sendEmail(post.ID) // แยกไปส่งอีเมล ไม่รอ
c.JSON(201, post)     // ตอบผู้ใช้ทันที

ผู้ใช้ได้คำตอบเร็วเหมือนกัน · แต่กฎของบท 21 ยังอยู่: โปรแกรมจบ = goroutine ที่ค้างตายเงียบ ๆ · และถ้า sendEmail พัง ไม่มีใครลองใหม่ให้ · go f() แก้ปัญหา "ผู้ใช้ต้องรอ" ได้ แต่ไม่ได้แก้ "งานหาย" — สิ่งที่คิวจริงต้องมีคือที่เก็บใบงานที่อยู่นอกโปรแกรม

ศัพท์ที่เอาไปคุยต่อได้
perform_later
สั่งให้ job ไปเข้าคิว ทำทีหลัง แล้วกลับมาทันที · คู่กับ perform ที่เป็นตัวงานจริง · log ฝั่งคนสั่งขึ้น Enqueued · ฝั่งคนทำขึ้น Performing / Performed
queue adapter
ตัวเสียบที่กำหนดว่าคิวจริงอยู่ที่ไหน (ในหน่วยความจำ · ในฐานข้อมูล · ใน Redis) · โค้ด job ไม่ต้องแก้เมื่อเปลี่ยน adapter · ถาม senior ได้ว่า "production เราใช้ queue adapter ตัวไหนครับ"
async adapter (in-process)
adapter ค่าเริ่มต้นของ development · ทำ job ด้วยคนงานในโปรแกรมเว็บเอง · restart แล้วงานค้างหาย · พิมพ์บอก AI ได้ว่า "don't rely on the async adapter in production, jobs are lost on restart"
durable
"ทนทาน" = เก็บงานไว้ในที่ที่รอดจากการปิดเปิดโปรแกรม (เช่น ตารางในฐานข้อมูล) · คิวที่ durable คือสิ่งที่บท 143 ตั้ง

ถึงตรงนี้คิดว่าแก้ได้แล้ว: แค่เปลี่ยนไปใช้คิวที่ durable งานก็ไม่หาย · ไม่หาย — แต่ได้ปัญหาใหม่มาแทน · ครึ่งหลังของบทว่าด้วยเรื่องนี้

exactly-once ไม่มีจริง — เลือกได้แค่ "อาจหาย" หรือ "อาจซ้ำ"

ใบงานหนึ่งใบต้องผ่านสองฝั่ง: คิว (ที่แขวนใบงาน) กับ worker (คนทำ) · สองฝั่งนี้คุยกันผ่านเครือข่ายหรือฐานข้อมูล ซึ่งขาดได้ และ worker ตายได้ทุกเมื่อ · คำถามคือ: คิวจะขีดฆ่าใบงาน (ถือว่าจบ) ตอนไหน — ก่อน worker ทำ หรือหลัง worker ทำ · มีแค่สองทาง (สไลด์หน้า 17):

at-most-once
"ไม่เกิน 1 ครั้ง"		at-least-once
"อย่างน้อย 1 ครั้ง"		exactly-once
"พอดี 1 ครั้ง"
ลำดับขีดฆ่าใบงานออกจากคิวก่อน แล้วค่อยทำทำให้เสร็จก่อน แล้วค่อยบอกคิวว่าเสร็จสองฝั่งต้องรู้ตรงกันเป๊ะทุกครั้ง
worker ตายกลางทางใบงานถูกฆ่าไปแล้ว → งานหายคิวยังไม่ได้ยินว่าเสร็จ → แจกใหม่ → งานซ้ำทำไม่ได้ เมื่อสายขาดได้หรือ worker ตายได้
เหมาะกับงานที่หายได้ เช่น นับคลิกค่าเริ่มต้นของคิวเกือบทุกตัว (สไลด์อ้าง)ไม่มีอยู่จริง

แล้วที่คนชอบพูดว่า "ระบบเรา exactly-once" คืออะไร · สไลด์ตอบว่า at-least-once + งานที่ทำซ้ำแล้วผลเหมือนเดิม — คิวส่งซ้ำได้ แต่ทำซ้ำแล้วไม่มีอะไรเสีย ผลรวมเลยดูเหมือนทำครั้งเดียว

เทียบกับร้านอาหาร

ใบงาน "ส่งข้าวกล่องไปบ้านคุณสมชาย" แขวนบนกระดาน · พนักงานส่งของหยิบไป ส่งถึงมือแล้ว เดินกลับมาจะติ๊กกระดานว่าเสร็จ — แต่เป็นลมล้มไปก่อนติ๊ก · พนักงานคนใหม่มาเห็นใบงานยังไม่ติ๊ก ก็หยิบไปส่งอีกรอบ · คุณสมชายได้ข้าวสองกล่อง = at-least-once · ถ้าร้านเปลี่ยนกฎเป็น "ติ๊กก่อนออกจากร้าน" แล้วพนักงานเป็นลมกลางทาง — กระดานบอกว่าเสร็จ แต่คุณสมชายไม่ได้ข้าวเลย = at-most-once

ที่ไม่เหมือนกัน: ในร้านจริงคุณสมชายโทรมาบอกได้ว่า "ได้แล้ว อย่าส่งอีก" · ในระบบจริงไม่มีใครโทรมาบอก — อีเมลที่ส่งออกไปแล้วเรียกคืนไม่ได้ · และคนใหม่ไม่ได้รู้ว่าคนเก่าเป็นลม เขาแค่เห็นว่านานเกินกำหนดแล้วยังไม่ติ๊ก (คิวรอจนหมดเวลา)

ศัพท์ที่เอาไปคุยต่อได้
at-most-once
รับประกันว่าไม่ซ้ำ แต่อาจหาย · ใช้กับงานที่หายได้ไม่เป็นไร
at-least-once
รับประกันว่าไม่หาย แต่อาจซ้ำ · ถาม senior ได้ว่า "คิวเราเป็น at-least-once ใช่ไหมครับ job ต้อง idempotent ทุกตัวหรือเปล่า"
exactly-once (delivery)
"ส่งพอดีครั้งเดียว" — เมื่อเครือข่ายขาดได้ ทำไม่ได้จริง · ถ้าเห็นเครื่องมือไหนโฆษณาคำนี้ ให้ถามว่า "หมายถึง at-least-once บวก dedup (กรองของซ้ำ) หรือ idempotency ใช่ไหม"
ack (acknowledge)
สัญญาณที่ worker บอกคิวว่า "ทำเสร็จแล้ว ขีดฆ่าได้" = การติ๊กกระดาน · คำถามทั้งหัวข้อนี้คือ "ack ก่อนทำ หรือหลังทำ"

worker ตายตอนไหน งานถึงซ้ำ — ช่องว่างที่ปิดไม่ได้

ไล่ตามเวลาแบบสไลด์หน้า 18 · คิวแบบ at-least-once (ทำก่อน แล้วค่อยบอกคิว) · ใบงานคือ "ส่งอีเมลแจ้งผู้ติดตาม":

t1 คิวส่งใบงานให้ worker t2 worker ส่งอีเมลออกไปแล้ว ┐ t3 worker กำลังจะบอกคิวว่าเสร็จ ┘ ← ช่องว่าง: งานทำไปแล้ว แต่ยังไม่มีใครรู้ t4 worker ตาย (deploy · หน่วยความจำเต็ม · เครื่องดับ) t5 คิวรอจนหมดเวลา → คิดว่างานยังไม่เสร็จ t6 คิวส่งใบงานเดิมให้ worker ตัวใหม่ t7 ลูกค้าได้อีเมลฉบับที่สอง
  • ช่องว่างระหว่าง t2 กับ t3 ปิดไม่ได้ — "ส่งอีเมล" กับ "บอกคิว" เป็นสองการกระทำ ต่อให้เขียนโค้ดเร็วแค่ไหน ระหว่างกลางก็กว้างกว่าศูนย์เสมอ · worker ตายพอดีตรงนั้น = ซ้ำ
  • t4 ไม่ใช่เรื่องไกลตัว — deploy ทุกครั้งคือการปิด worker เก่าแล้วเปิดตัวใหม่ · ระบบที่ deploy วันละหลายรอบเจอจังหวะนี้แน่นอนสักวัน

สลับลำดับก็ไม่ช่วย: ถ้าบอกคิวว่าเสร็จก่อน (t3 ขึ้นมาก่อน t2) แล้ว worker ตายตรงกลาง — คิวคิดว่าเสร็จ แต่อีเมลไม่เคยออก · เราแค่ย้ายจากปัญหา "ซ้ำ" ไปเป็นปัญหา "หาย" · เลือกได้แค่ว่าจะเจ็บทางไหน

ซ้ำได้ไม่เป็นไร

"ตั้งสถานะบทความเป็นเผยแพร่แล้ว" · รันครั้งเดียวหรือสิบครั้ง ผลเหมือนเดิม — เหมือนพลิกป้ายหน้าร้านเป็น "เปิด" ซ้ำ ป้ายก็ยังเป็น "เปิด"

ฝั่งขวาคือ idempotent — คำเดียวกับที่เจอใน Go บท 36 (PUT ยิงซ้ำได้ POST ยิงซ้ำแล้วได้ของเบิ้ล) และ find_or_create_by! ใน seeds · แต่ "ส่งอีเมล" ไม่มีทางทำให้เป็นแบบฝั่งขวาโดยธรรมชาติ — ส่งสองครั้งก็สองฉบับ · 3 ท่าที่ใช้จริงในการทำให้ job แบบนี้ซ้ำได้ คือเรื่องของบท 143

ทดสอบความเข้าใจ

ใน action create ของบทความ งานไหนควรย้ายไปเป็น background job?

ตัวเลือกที่ 3 ถูก — อีเมลยังไม่ออก ผู้ใช้ก็เห็นหน้าบทความได้ตามปกติ

ตัวเลือกที่ 1 ผิด — ไม่มีบทความในตู้ หน้าถัดไปก็ไม่มีอะไรให้ดู (และจริง ๆ ใช้แค่ไม่กี่ ms — log บอก ActiveRecord: 9.4ms) · ตัวเลือกที่ 2 ผิด — ต้องรู้ผลก่อนว่าจะโชว์หน้าบทความหรือโชว์ error · ตัวเลือกที่ 4 ผิด — redirect ต้องรู้ URL ตอนตอบ จะทำทีหลังไม่ได้

จุดที่ต้องจำ: ถามว่า "ถ้างานนี้ยังไม่เสร็จ ผู้ใช้เห็นหน้าถัดไปได้ไหม" · ได้ = ส่งเข้า job · ไม่ได้ = ทำใน request

development ใช้ adapter async · job กำลังทำได้ครึ่งทาง แล้วคุณกด Ctrl+C ที่ bin/dev แล้วเปิดใหม่ · เกิดอะไรขึ้น?

ตัวเลือกที่ 2 ถูก — ภารกิจพิสูจน์แล้ว: ไม่มีบรรทัด "เสร็จแล้ว" · เปิดใหม่ 25 วินาทีไม่มี [ActiveJob] · แต่บทความอยู่

ตัวเลือกที่ 1 ผิด — async เก็บใบงานในหน่วยความจำ ปิดโปรแกรมแล้วไม่มีที่ไหนจำ · ตัวเลือกที่ 3 ผิด — บทความ COMMIT ไปแล้วก่อนแขวนใบงาน สองเรื่องนี้ไม่ผูกกัน · ตัวเลือกที่ 4 ผิด — log บอก waiting for requests to finish คือรอ request ไม่ใช่ job (และ log ยังขึ้น Performed … in 2158.22ms ทั้งที่งานไม่ครบ)

จุดที่ต้องจำ: async = go f() ของ Rails · เร็ว ใช้ง่าย แต่โปรแกรมดับ = งานหาย → ห้ามใช้ใน production

คิวแบบ at-least-once · worker ส่งอีเมลสำเร็จ แล้วดับไปก่อนบอกคิวว่าเสร็จ · ผลคืออะไร?

ตัวเลือกที่ 4 ถูก — คือ t2 → t4 → t7 ในแผนภาพ · ช่องว่างระหว่าง "ทำแล้ว" กับ "บอกแล้ว" ปิดไม่ได้

ตัวเลือกที่ 1 ผิด — อีเมลออกไปแล้วตั้งแต่ t2 การยืนยันกับคิวไม่เกี่ยวกับอีเมล · ตัวเลือกที่ 2 ผิด — คิวรู้แค่ว่ายังไม่มีใครบอกว่าเสร็จ ไม่รู้ว่าข้างนอกเกิดอะไร · ตัวเลือกที่ 3 ผิด — อีเมลที่ส่งออกไปแล้วเรียกคืนไม่ได้ (ที่ไม่เหมือนกันของภาพพนักงานส่งของ)

จุดที่ต้องจำ: at-least-once = ไม่หายแต่อาจซ้ำ · คิวเกือบทุกตัวเลือกแบบนี้ → job ต้องทนการทำซ้ำได้

เพื่อนเสนอว่า "งั้นให้ worker บอกคิวว่าเสร็จก่อน แล้วค่อยส่งอีเมล จะได้ไม่ซ้ำ" · ข้อไหนอธิบายถูก?

ตัวเลือกที่ 1 ถูก — สลับลำดับ = เปลี่ยนจาก at-least-once เป็น at-most-once · ย้ายปัญหาจาก "ซ้ำ" ไปเป็น "หาย"

ตัวเลือกที่ 2 ผิด — ช่องว่างยังอยู่ แค่ย้ายไปอยู่อีกฝั่ง · ตัวเลือกที่ 3 ผิด — คิวได้ยินว่าเสร็จแล้วจึงไม่แจกซ้ำ ปัญหาคือหาย ไม่ใช่ซ้ำ · ตัวเลือกที่ 4 ผิด — ลำดับนี้เป็นเรื่องการออกแบบคิว ไม่ใช่กฎบังคับของ Rails · ประเด็นคือไม่ว่าลำดับไหน "พอดีครั้งเดียว" ก็ไม่มี

จุดที่ต้องจำ: เลือกได้แค่ว่าจะเจ็บทางไหน · งานที่หายไม่ได้ → ยอมซ้ำ แล้วออกแบบให้ "ซ้ำแล้วไม่เป็นไร" (บท 143)
