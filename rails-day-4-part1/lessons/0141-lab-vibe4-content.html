## เป้าหมาย

เปลี่ยน description เป็น rich text แก้ไขได้
เพิ่มรูปปกให้โพสต์ เก็บใน MinIO และโชว์รูปย่อในหน้า index

## ข้อกำหนด

- ใช้ Action Text สำหรับเนื้อหา (has_rich_text :body)
- ย้ายข้อมูลเดิมจาก description มา body
  ใช้ท่า expand-contract ไม่ลบคอลัมน์เก่าในรอบนี้
  (ย้ายด้วย rake task ที่รันซ้ำได้ ไม่ใช่ใน migration · escape ข้อความเดิมก่อนเป็น HTML)
- รูปปกใช้ Active Storage -> service minio
- เปิด direct_upload: true
- validate ชนิดไฟล์ (png/jpeg/webp) และขนาด <= 5MB
- index ใช้ variant resize_to_limit [400,300]
- controller ต้องมี with_attached_cover
  และ with_rich_text_body
- เพิ่มคอลัมน์ plain_text สำหรับค้นหาภายหลัง

## ห้าม

- raw หรือ html_safe กับ body ที่ไหนก็ตาม
- ตั้ง bucket เป็น public
- เชื่อ content_type ที่ client ส่งมาอย่างเดียว
- เขียน access key ลง storage.yml ตรง ๆ
- ลบคอลัมน์ description ในรอบนี้

แปลว่า ถ้าก๊อป src ไปทดสอบ คุณจะรอ 5 นาทีแล้วเห็นรูปยังขึ้น แล้วสรุปผิดว่า "ลายเซ็นไม่หมดอายุ" · เกณฑ์ข้อ 3 ต้องทดสอบด้วยตัว :9000

🎫 เทียบให้เห็นภาพ — ใบบอกทางของร้าน vs บัตรผ่านเข้าโกดัง

URL :3000 = ใบบอกทางที่ร้านแจก "อยากได้ของชิ้นนี้ ถามเคาน์เตอร์ร้าน" — ใครถือมาเมื่อไหร่ เคาน์เตอร์ก็เขียนบัตรผ่านใบใหม่ให้ทุกครั้ง · URL :9000 = บัตรผ่านเข้าโกดังที่มีลายเซ็นหมดอายุใน 5 นาที — ยามโกดังดูแค่ลายเซ็นกับเวลา ไม่สนว่าคุณเป็นใคร (หน้าต่าง incognito ไม่มี cookie ก็เข้าได้) · เลยเวลาแล้วยามไม่ให้เข้า

ที่ไม่เหมือนกัน: เคาน์เตอร์ร้านจริงมักถามว่า "คุณเป็นใคร" ก่อนออกบัตร · ของเราตอนนี้ไม่ถามเลย ใครมีใบบอกทางก็ได้บัตรใหม่ไปเรื่อย ๆ — เพราะแอปยังไม่มีระบบ login (มาใน Part 2) · ข้อ 3 จึงพิสูจน์ได้แค่ว่า "บัตรผ่านหมดอายุจริง" ไม่ได้พิสูจน์ว่า "รูปเป็นความลับ"

ถูกล้างแล้ว ทั้งที่มี raw — แท็ก <script> หายเหลือแค่ตัวหนังสือ alert(1) · onerror หายจาก <img> · เพราะ body.to_s ผ่าน sanitize ของ Action Text ก่อนแล้ว (ตรวจตอนจัดจาน · บท 136) · raw แค่บอกว่า "ไม่ต้อง escape อีก" กับของที่ล้างมาแล้ว

แล้วทำไมยังห้าม? บรรทัดแรกของผลคือของดิบในตาราง — ยังมี script ครบ · ถ้าวันหนึ่งมีคน (หรือ AI) เปลี่ยน to_s เป็นของดิบ เช่น raw @post.body.body.to_html raw จะปล่อย script เข้าอีเมลทันที · raw ที่ไม่มีประโยชน์ = ซองที่ถูกแกะรอไว้ · เขียน <%= @post.body %> ได้ผลเท่ากันและไม่เปิดช่องนี้

ส่วนบรรทัดที่สอง render json: { body: @post.body.to_s } (API = ช่องที่ส่งข้อมูลเป็น JSON ให้แอปมือถือ) — ผมรันจริงกับบทความที่ใส่ HTML อันตรายแบบเดียวกัน (รันใน runner เป็น { body: post.body.to_s }.to_json ซึ่งคือสิ่งที่ render json: ทำ) · ได้ 2 อย่างที่ควรรู้:

  • ได้ HTML ที่ล้างแล้วเหมือนในอีเมล ห่อด้วยกล่อง trix-content — แอปมือถือต้องเอา HTML ไปวาดเอง · และใน development ยังติด comment บอกที่อยู่ไฟล์ในเครื่อง server มาด้วย ซึ่งไม่ควรไปถึงลูกค้า
  • ถ้าแอปมือถือแค่โชว์ข้อความ ใช้ post.body.to_plain_text แทน — ผลจริงได้ "สูตรเด็ด ตัวหนา" (ทิ้งทั้งแท็กและเนื้อใน script) · API ของเราตอนนี้ (_post.json.jbuilder) ส่ง description ซึ่งเป็นข้อความล้วนอยู่แล้ว (บท 137)
✉️ เทียบให้เห็นภาพ — ซองใสที่ถูกตรวจมาแล้ว

body.to_s = คนจัดจานเอาข้อความหน้าเค้กมาเทียบรายการตัวตกแต่งที่ร้านอนุญาต ทิ้งของที่ไม่อยู่ในรายการแล้ว · raw = บอกพนักงานเสิร์ฟว่า "ไม่ต้องใส่ซองใสอีก ยกไปเลย" · วันนี้ปลอดภัยเพราะของผ่านการตรวจมาแล้ว — แต่ป้าย "ยกไปเลย" ติดอยู่ที่ช่องเสิร์ฟ ไม่ได้ติดที่ของ วันไหนมีคนเอาของที่ยังไม่ตรวจมาวางช่องนี้ มันก็ถูกยกไปเลยเหมือนกัน

ตัวเลือกที่ 2 คิดว่า raw ปิด sanitize — ไม่จริง มันแค่ไม่ escape ซ้ำ · ตัวเลือกที่ 3 ผิด — อีเมลถูกสร้างได้ปกติ · ตัวเลือกที่ 4 ผิดสองจุด — แท็กถูกถอดทิ้ง (sanitize) ไม่ใช่แปลงเป็นตัวหนังสือ (escape) และยังต้องแก้เพราะผิดข้อห้ามข้อ 1

จุดที่ต้องจำ: ปลอดภัยวันนี้เพราะบังเอิญ ≠ ปลอดภัยโดยการออกแบบ · ไม่มีเหตุผลต้องใช้ raw กับ body เลย

ข้อ 4 · ตรวจเกณฑ์ข้อ 6 ผ่าน (ไฟล์ปลอมถูกปฏิเสธ 422) · แต่เปิด MinIO console ยังเห็นไฟล์ขนาด 38.0 B อยู่ใน bucket · หมายความว่าอะไร?

ตัวเลือกที่ 3 ถูก · Network: PUT 200 … :9000 เกิดก่อน POST 422 /posts · ใน console ของ Rails ActiveStorage::Blob.unattached ได้ [["fake.png", "image/png", 38]] = ใบรับฝากที่ไม่มีป้ายผูกกับบทความไหน

ตัวเลือกที่ 1 ผิด — ถ้าผูกแล้วจะไม่อยู่ใน unattached และหน้าจะ redirect ไม่ใช่ 422 · ตัวเลือกที่ 2 ผิด — MinIO ไม่รู้เรื่อง validation ของ Rails เลย ไม่มีใครลบให้ · ตัวเลือกที่ 4 ผิด — Network มี PUT ครั้งเดียวต่อการกดบันทึก
