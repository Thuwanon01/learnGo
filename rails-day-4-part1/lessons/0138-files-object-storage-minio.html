ไฟล์ไม่ควรอยู่ในแอป — object storage, MinIO และ Active Storage

บทนี้เราจะให้บทความมีรูปปก · คำถามแรกไม่ใช่ "เขียนโค้ดยังไง" แต่เป็น "ไฟล์ควรไปอยู่ที่ไหน"

ตอนนี้ไฟล์ที่อัปโหลดไปอยู่ไหน

ในบท 137 ถ้าคุณกดปุ่มคลิปของ Trix แล้วแนบรูป รูปนั้นไปอยู่ในโฟลเดอร์ storage/ ของโปรเจกต์ · เพราะ Rails ตั้งค่าเริ่มต้นไว้แบบนี้: 

# config/environments/development.rb (ตอนเริ่มบท)
  # Store uploaded files on the local file system (see config/storage.yml for options).
  config.active_storage.service = :local

# config/storage.yml (ตอนเริ่มบท · ตัดมาเฉพาะส่วนนี้)
local:
  service: Disk
  root: <%= Rails.root.join("storage") %>
  • service = :local — "ไฟล์ที่ผู้ใช้อัปมา ให้ใช้ที่เก็บชื่อ local"
  • local: → service: Disk — ที่เก็บชื่อ local คือดิสก์ของเครื่องนี้ · root: = โฟลเดอร์ storage/ ในโปรเจกต์ (<%= %> ในไฟล์ yml คือ ERB แบบเดียวกับใน view · Rails คำนวณให้เป็นที่อยู่เต็มของโฟลเดอร์)

ตอนผมลองอัปรูปด้วยค่านี้ ไฟล์ไปโผล่ที่ storage/65/er/65eryelme20ify18xoi0sa9d1z7e — อยู่ในโฟลเดอร์ของแอป บนเครื่องที่รันแอป · บนโน้ตบุ๊กเราไม่มีปัญหา · แต่พอเอาแอปขึ้นให้คนใช้จริง (production) จะพังสี่แบบ (สไลด์หน้า 8):

เหตุการณ์เกิดอะไรกับไฟล์ใน storage/
restart · deploy ใหม่production มักรัน Rails ในกล่องแยก (container) แบบเดียวกับที่เรารัน Postgres · deploy (เอาโค้ดใหม่ขึ้น) = สร้างกล่องใหม่จากแม่แบบ แล้วทิ้งกล่องเก่า → โฟลเดอร์ในกล่องเริ่มจากศูนย์ รูปหายหมด
scale (เปิดแอปหลายเครื่องช่วยกันรับคน)ผู้ใช้อัปรูปผ่านเครื่อง A → ไฟล์อยู่ใน A เครื่องเดียว · คนที่เปิดหน้าเดียวกันแล้วไปตกเครื่อง B หรือ C เห็นรูปพัง
backupสำรองฐานข้อมูลแล้ว แต่ไฟล์อยู่อีกที่ ต้องจำไปสำรองแยก · กู้คืนทีหนึ่งต้องกู้สองที่ให้ตรงกัน
ไฟล์ใหญ่วิ่งผ่าน Railsตลอดเวลาที่ไฟล์กำลังส่งเข้ามา Rails ต้องมีคนคอยรับหนึ่งคน · server ของเราตอนเปิดพิมพ์ Min threads: 3 Max threads: 3 = รับงานพร้อมกันได้ 3 งาน · สไลด์ยกตัวอย่างว่า 10 คนอัปไฟล์ 500 MB พร้อมกัน = คนรับงานหมด คนที่แค่จะอ่านบทความก็เปิดเว็บไม่ได้

ใน Go บท 44 คุณเจอ 12-Factor ข้อ III (config) มาแล้ว · ข้อที่เกี่ยวกับบทนี้คือ ข้อ VI: แอปต้องไม่เก็บของที่ต้องอยู่ถาวรไว้กับตัว — ของแบบนั้นให้ไปอยู่ในบริการข้างนอก แบบที่ข้อมูลบทความไปอยู่ใน Postgres

🍳 เทียบให้เห็นภาพ — วางของฝากของลูกค้าไว้ในครัว

ลูกค้าฝากรูปปกไว้กับร้าน แล้วพนักงานเอาไปวางในครัว · วันหนึ่งครัวรีโนเวท (deploy) ช่างรื้อทุกอย่างแล้วสร้างครัวใหม่ตามแบบ → ของฝากหาย · พอร้านเปิดสามสาขา (scale) ของฝากอยู่ครัวสาขาเดียว ลูกค้าไปอีกสาขาก็ไม่เจอ · และระหว่างที่พนักงานต้อนรับแบกกล่องใหญ่ของลูกค้าเข้าครัว เขาก็รับออเดอร์โต๊ะอื่นไม่ได้

ที่ไม่เหมือนกัน: ร้านจริงรีโนเวทปีละครั้ง และช่างอาจเก็บของไว้ให้ · แอปจริง deploy ได้วันละหลายรอบ และกล่องใหม่ไม่มีอะไรจากกล่องเก่าติดมาเลย ทุกครั้ง ไม่มีใครเก็บของให้

เทียบกับที่รู้: แอป Go ใน บท 27 ก็ไม่เก็บบทความไว้ในตัวโปรแกรม แต่ส่งไป Postgres ด้วย GORM · ปิดเปิดโปรแกรม Go ใหม่ ข้อมูลยังอยู่ · บทนี้ทำแบบเดียวกันกับไฟล์

🗣 ศัพท์ที่เพิ่งเรียนไป
stateless process
โปรแกรมที่ไม่เก็บของถาวรไว้กับตัว ปิดทิ้งแล้วเปิดใหม่กี่ตัวก็ได้ไม่เสียอะไร (12-Factor ข้อ VI) · ถาม senior ได้ว่า "แอปเรา stateless หรือยัง มีอะไรเขียนลงดิสก์ของ container บ้าง"
backing service
บริการข้างนอกที่แอปเรียกใช้ผ่านเครือข่าย เช่น Postgres หรือที่เก็บไฟล์ (12-Factor ข้อ IV) · สลับตัวได้แค่แก้ config · พิมพ์บอก AI ได้ว่า "treat file storage as a backing service; never write uploads to the container's disk"
scale out · horizontal scaling
เพิ่มจำนวนเครื่องที่รันแอปตัวเดียวกันเพื่อรับคนได้มากขึ้น · ทำได้ก็ต่อเมื่อแอป stateless · ถาม senior ได้ว่า "ถ้าเรา scale out เป็น 3 เครื่องตอนนี้ อะไรจะพังก่อน"

object storage — โกดังเก็บไฟล์ที่พูดภาษา S3

object storage คือที่เก็บไฟล์ที่อยู่บนเครือข่าย · แอปส่งไฟล์ไปทั้งก้อน พร้อมบอกชื่อที่จะใช้เรียกคืน · อยากได้คืนก็ขอด้วยชื่อนั้น · มันไม่ได้อยู่ในเครื่องที่รันแอป → deploy กี่รอบ เปิดกี่เครื่อง ทุกเครื่องเห็นไฟล์ชุดเดียวกัน

  • bucket — กล่องใหญ่ที่ตั้งชื่อไว้ เก็บไฟล์ได้ไม่จำกัด · แอปเราจะใช้ bucket ชื่อ wongnok-dev
  • object — ไฟล์หนึ่งชิ้นใน bucket · key = ชื่อที่ใช้เรียกมัน (เหมือนเลขที่ใบฝากของ)
  • S3 — บริการ object storage ของ Amazon · ชุดคำสั่งที่ใช้คุยกับมันกลายเป็นภาษากลาง หลายเจ้าเลยพูดภาษาเดียวกัน (เรียกว่า S3-compatible)
  • MinIO — โปรแกรม object storage ที่พูดภาษา S3 และรันในเครื่องเราได้ · ตอนพัฒนาใช้ MinIO · ตอนขึ้นจริงจะเปลี่ยนไปใช้ S3 ก็แค่แก้ config ไม่ต้องแก้โค้ด

MinIO อยู่ใน compose.yaml ของ repo ตั้งแต่บท 120 แล้ว · ดูส่วนของมัน (ไม่ต้องแก้):

# compose.yaml (ส่วนของ minio)
  minio:
    image: pgsty/silo
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: minioadmin
      MINIO_ROOT_PASSWORD: minioadmin
    ports: ["9000:9000", "9001:9001"]
    volumes: ["miniodata:/data"]
  • image: pgsty/silo — ตัวโปรแกรม · หน้า login ของมันเขียนว่า "MinIO fork maintained by PGSTY" = MinIO ฉบับที่อีกทีมดูแลต่อ ใช้งานเหมือนกัน · ชื่อบนหน้าจอจะเป็น SILO
  • command: server /data … — สั่งให้เก็บไฟล์ไว้ที่ /data ในกล่อง · --console-address ":9001" = เปิดหน้าเว็บจัดการที่ประตู 9001
  • MINIO_ROOT_USER · MINIO_ROOT_PASSWORD — ชื่อและรหัสของผู้ดูแลสูงสุด · minioadmin เป็นค่าทดลองในเครื่อง ห้ามใช้กับระบบจริง
  • ports — 9000 = ประตูที่โปรแกรมคุยกัน (ภาษา S3 · Rails และเบราว์เซอร์จะส่งไฟล์มาที่นี่) · 9001 = หน้าเว็บ console ให้คนกดดู
  • volumes: miniodata:/data — เก็บ /data ไว้นอกกล่อง (แบบ pgdata ของ Postgres บท 120) · MinIO เองก็เป็นกล่อง แต่ปิดเปิดใหม่แล้วไฟล์ไม่หายเพราะบรรทัดนี้
🏬 เทียบให้เห็นภาพ — โกดังรับฝากของนอกร้าน

ร้านเลิกวางของฝากในครัว แล้วไปเช่าโกดังรับฝากของนอกร้าน · ครัวรีโนเวทกี่รอบ ของในโกดังก็อยู่ · ร้านเปิดสามสาขา ทุกสาขาไปเบิกจากโกดังเดียวกัน · ในโกดังแบ่งเป็นห้อง (bucket) · ของแต่ละชิ้นมีเลขที่ใบฝาก (key) · บริษัทโกดังหลายเจ้าใช้แบบฟอร์มฝาก-เบิกแบบเดียวกัน (ภาษา S3) ร้านจะย้ายเจ้าก็ไม่ต้องสอนพนักงานใหม่ · MinIO คือโกดังจำลองหลังบ้านเรา ที่ใช้แบบฟอร์มเดียวกันเป๊ะ ไว้ซ้อมก่อนไปเช่าของจริง

ที่ไม่เหมือนกัน: โกดังจริงอยู่ไกล ไปทีกินเวลา · object storage อยู่บนเครือข่าย ส่งไฟล์ไปกลับในเสี้ยววินาที · และโกดังจริงเปิดกล่องแก้ของข้างในได้ · object storage แก้ไฟล์ครึ่งชิ้นไม่ได้ ต้องส่งชิ้นใหม่ไปแทนทั้งชิ้น

เทียบกับที่รู้: MinIO เป็นกล่องหนึ่งใน compose.yaml แบบเดียวกับ postgres ของบท 120 · Postgres รับแถวข้อมูลทางประตู 5432 · MinIO รับไฟล์ทั้งก้อนทางประตู 9000 · ทั้งคู่อยู่นอกแอป Rails ปิดเปิดแอปกี่รอบของก็ยังอยู่

🗣 ศัพท์ที่เพิ่งเรียนไป
object storage · object · key
ที่เก็บไฟล์บนเครือข่าย · ไฟล์หนึ่งชิ้น · ชื่อที่ใช้เรียกไฟล์ · ถาม senior ได้ว่า "ไฟล์ที่ผู้ใช้อัปโหลดของระบบเราเก็บใน object storage ตัวไหน bucket อะไร"
bucket
กล่องใหญ่ที่ตั้งชื่อไว้เก็บ object · มักแยก bucket ตาม environment เช่น wongnok-dev กับของ production · พิมพ์บอก AI ได้ว่า "use a separate private bucket per environment"
S3-compatible · MinIO
บริการที่พูดภาษาเดียวกับ Amazon S3 · MinIO เป็นตัวที่รันเองได้ เหมาะกับเครื่อง dev · พิมพ์บอก AI ได้ว่า "we use MinIO locally as an S3-compatible store; configure Active Storage's S3 service with a custom endpoint"

เปิดโกดัง แล้วสร้างห้อง wongnok-dev

bucket ไม่มีใครสร้างให้ · เราสร้างผ่านหน้าเว็บ console ของ MinIO:

  1. เปิด http://localhost:9001 · เจอหน้า login ที่มีโลโก้ SILO ใต้โลโก้เขียน "OBJECT STORAGE CONSOLE" · ช่อง Username พิมพ์ minioadmin · ช่อง Password พิมพ์ minioadmin (ค่าจาก compose.yaml) → ปุ่ม Login · จะไปหน้า Overview
  2. เมนูซ้าย Buckets → ปุ่ม Create bucket (มุมขวาบน) → หน้า "Create Bucket"
  3. ช่อง Bucket Name* พิมพ์ wongnok-dev (ตรงตัวอักษร เดี๋ยวต้องใส่ชื่อนี้ใน config) · Versioning · Object Locking · Quota ปล่อย Off → ปุ่ม Create Bucket
  4. หน้าจอเด้งไปที่ห้องใหม่ ขึ้นว่า "This location is empty, please try uploading a new file" = ห้องว่าง พร้อมใช้

แท็บ Summary ของ bucket จะเขียน Access Policy: private = คนนอกเปิดไฟล์ในห้องนี้ตรง ๆ ไม่ได้ ต้องมีใบอนุญาตจากแอปเท่านั้น · ค่าเริ่มต้นนี้แหละที่เราต้องการ

⚠️ อย่าเปลี่ยน bucket เป็น public แม้จะทำให้รูปขึ้นง่ายกว่า — ใครเดาชื่อไฟล์ได้ก็เปิดได้หมด · บท 139 จะเห็นว่าแอปออก "ใบอนุญาตชั่วคราว" ให้เบราว์เซอร์แทน

Active Storage — ระบบบัตรรับฝากของร้าน

Active Storage คือส่วนของ Rails ที่ทำสามอย่างให้: ส่งไฟล์ไปเก็บ (ในเครื่องหรือโกดังไหนก็ได้ตาม config) · จดลงฐานข้อมูลว่าไฟล์อะไรเป็นของบทความไหน · และสร้างลิงก์ให้เบราว์เซอร์เปิดไฟล์ได้ · สไลด์หน้า 9 สั่งให้ติดตั้งด้วยคำสั่งนี้ — ลองพิมพ์ดู: 

$ bin/rails active_storage:install
$ bin/rails db:migrate
$ git status --short
$

เงียบทั้งสามคำสั่ง (ผลจริง ไม่ใช่ตัดออก) · เพราะบท 137 ตอน action_text:install มันก็อป migration ของ Active Storage มาให้แล้ว (ไฟล์ db/migrate/…_create_active_storage_tables.active_storage.rb · เลขหน้าชื่อไฟล์ของคุณต่างจากของผม) และ migrate ไปแล้ว · ดูตารางที่มันสร้างใน db/schema.rb (ตัดมาเฉพาะสองตารางหลัก): 

# db/schema.rb
  create_table "active_storage_attachments", force: :cascade do |t|
    t.string "name", null: false
    t.string "record_type", null: false
    t.bigint "record_id", null: false
    t.bigint "blob_id", null: false
    t.datetime "created_at", null: false
    t.index ["blob_id"], name: "index_active_storage_attachments_on_blob_id"
    t.index ["record_type", "record_id", "name", "blob_id"], name: "index_active_storage_attachments_uniqueness", unique: true
  end

  create_table "active_storage_blobs", force: :cascade do |t|
    t.string "key", null: false
    t.string "filename", null: false
    t.string "content_type"
    t.text "metadata"
    t.string "service_name", null: false
    t.bigint "byte_size", null: false
    t.string "checksum"
    t.datetime "created_at", null: false
    t.index ["key"], name: "index_active_storage_blobs_on_key", unique: true
  end

(บรรทัด t.index … unique: true = กฎ "ห้ามซ้ำ" ระดับฐานข้อมูลแบบ unique index ของบท 111 · ที่เหลือเป็นหน้าตาปกติของ schema.rb)

active_storage_blobs — หนึ่งแถว = ไฟล์หนึ่งชิ้น (blob = "ก้อนข้อมูล"):

  • key — ชื่อของไฟล์ในโกดัง · Rails สุ่มให้ · unique: true = ห้ามซ้ำ
  • filename — ชื่อเดิมที่ผู้ใช้อัปมา เช่น khaosoi.jpg · content_type — ชนิดไฟล์ เช่น image/jpeg (บท 140 จะเห็นว่าเชื่อช่องนี้ไม่ได้)
  • metadata — ข้อมูลเสริม เช่นกว้าง × ยาวของรูป · byte_size — ขนาดเป็นไบต์
  • service_name — ไฟล์นี้อยู่โกดังไหน (local หรือ minio)
  • checksum — ลายนิ้วมือของไฟล์ คำนวณจากเนื้อไฟล์ · ไว้ตรวจว่าไฟล์ไม่เพี้ยนระหว่างส่ง

active_storage_attachments — หนึ่งแถว = ป้ายบอกว่าไฟล์ไหนเป็นของใคร:

  • name — ชื่อช่อง เช่น "cover" (รูปปก)
  • record_type + record_id — ของแฟ้มไหน เลขที่เท่าไร เช่น "Post" + 1 · นี่คือ polymorphic แบบเดียวกับ action_text_rich_texts ของบท 137 · ตารางเดียวใช้ได้กับทุก model
  • blob_id — ชี้ไปแถวใน active_storage_blobs

ตารางที่สาม active_storage_variant_records (ไม่ได้ตัดมาโชว์) ใช้จดรูปย่อ — รอบท 140 · สังเกตว่าไม่มีตารางไหนเก็บตัวไฟล์ · ฐานข้อมูลเก็บแค่ข้อมูลเกี่ยวกับไฟล์ ตัวไฟล์อยู่ในโกดัง

🎫 เทียบให้เห็นภาพ — ระบบบัตรรับฝากของร้าน

ทุกครั้งที่ของเข้าโกดัง ร้านออกใบรับฝาก (blob): เลขที่ฝาก ชื่อของ ขนาด ฝากไว้โกดังไหน แล้วเก็บใบนี้ในตู้แฟ้ม · แยกจากนั้นมีป้ายติดแฟ้ม (attachment): "รูปปกของแฟ้มบทความเลขที่ 1 → ดูใบรับฝากเลข 1" · เพราะใบรับฝากกับป้ายแยกกัน ใบเดียวจึงถูกป้ายหลายอันชี้มาได้

ที่ไม่เหมือนกัน: ร้านจริงให้ลูกค้าถือใบรับฝากกลับบ้าน · ที่นี่ทั้งใบและป้ายอยู่ในตู้แฟ้มของร้าน (ฐานข้อมูล) ลูกค้าไม่ได้ถืออะไร · และเลขที่ฝากของจริงมักเรียง 1 2 3 · ของ Active Storage เป็นตัวอักษรสุ่ม ใครก็เดาเลขของคนอื่นไม่ได้

เทียบกับที่รู้: คล้าย has_many :comments (บท 115) ที่เก็บคอมเมนต์แยกตาราง แล้วจดว่าเป็นของบทความไหน · ต่างกันตรงที่ Active Storage ใช้สองตารางนี้ร่วมกันทุก model ไม่ต้องสร้างตารางใหม่ต่อ model

ติดตั้งตัวพูดภาษา S3 — gem aws-sdk-s3

Active Storage รู้ว่าต้องทำอะไร แต่พูดภาษา S3 เองไม่เป็น · ต้องมี gem ของ Amazon ที่รวมคำสั่งคุยกับ S3 ไว้ให้ · เปิด Gemfile แล้วพิมพ์ต่อท้ายไฟล์: 

# Gemfile (ต่อท้ายไฟล์)

# Active Storage ต่อ MinIO/S3 · require: false เพราะ Active Storage require เองตอนใช้ service S3
gem "aws-sdk-s3", "~> 1.238", require: false
  • "~> 1.238" — ใช้รุ่น 1.238 ขึ้นไป แต่ไม่ถึง 2.0
  • require: false — ไม่ต้องโหลดตอนเปิดแอป · Active Storage จะโหลดเองตอนต้องคุยกับ S3

เครื่องผมมี gem ครบแล้ว (รันแบบ --local = ใช้ของในเครื่อง) · ของคุณจะมีบรรทัด Fetching … · Installing … ก่อน (Gemfile.lock ได้ gem เพิ่ม 8 ตัว: aws-sdk-s3 กับอีก 7 ตัวที่มันต้องใช้) · เลขรุ่นใน Gemfile.lock ของคุณอาจใหม่กว่าของผม (ผมได้ aws-sdk-s3 (1.238.0)) เพราะ bundler หยิบรุ่นล่าสุดที่เข้ากับ "~> 1.238" — ไม่เป็นไร · ลงท้ายด้วย Bundle complete! = ผ่าน

กุญแจโกดังห้ามเขียนลงไฟล์ — Rails credentials

Rails ต้องมีชื่อผู้ใช้กับรหัสของ MinIO ถึงจะส่งไฟล์ได้ · ถ้าเขียนลง config/storage.yml ตรง ๆ ไฟล์นั้นขึ้น Git → ทุกคนที่เห็น repo ได้กุญแจโกดังไปด้วย (Go บท 44 สอนเกณฑ์ไว้แล้ว: "เปิด repo เป็น public ตอนนี้ได้ไหม")

ทางของ Rails เรียกว่า credentials: เก็บรหัสในไฟล์ที่เข้ารหัสแล้ว (.yml.enc · commit ได้ อ่านไม่ออก) คู่กับไฟล์กุญแจถอดรหัส (.key · ห้าม commit) · repo นี้มี config/credentials.yml.enc ของอาจารย์อยู่แล้ว แต่เราไม่มีกุญแจของมัน → เราสร้างชุดแยกสำหรับ development ของเราเอง 

$ EDITOR=nano bin/rails credentials:edit --environment development
  • EDITOR=nano — บอกว่าจะเปิดไฟล์ด้วยโปรแกรมแก้ข้อความในเทอร์มินัลชื่อ nano (บน macOS คำสั่งนี้เปิดโปรแกรม pico ที่หน้าตาและปุ่มเหมือนกัน หัวจอจะเขียนว่า PICO ไม่ต้องตกใจ) · ใช้ VS Code ได้ด้วย EDITOR="code --wait" (--wait สำคัญ ไม่งั้นมันปิดทันทีแล้วไม่ได้บันทึกอะไร)
  • credentials:edit — ถอดรหัสไฟล์ ให้แก้ แล้วเข้ารหัสกลับตอนปิด · --environment development = ทำชุดของ development

ภาพรวมก่อนลงมือ: ① model บอกว่าบทความมีรูปปก → ② controller ยอมรับช่องรูปปก → ③ ฟอร์มมีช่องเลือกไฟล์ → ④ เปิด JavaScript ที่ส่งไฟล์ขึ้นโกดัง → ⑤ หน้าบทความโชว์รูป · แต่ละขั้นแก้ไฟล์เดียว ยกเว้นขั้น ④ ที่แก้สองไฟล์

① model — app/models/post.rb เพิ่มสองบรรทัดต่อจาก has_rich_text :body:

  has_one_attached :cover

② controller — app/controllers/posts_controller.rb ใน method post_params เพิ่ม :cover ในรายชื่อ (บท 117 · ไม่เพิ่ม = Rails ทิ้งช่องนี้):

ทดสอบความเข้าใจ

แอปเก็บรูปไว้ใน storage/ แล้วทีมเพิ่มเครื่องรันแอปเป็น 3 เครื่องช่วยกันรับคน · ผู้ใช้บ่นว่า "รูปปกขึ้นบ้างไม่ขึ้นบ้าง" · เพราะอะไร?

ตัวเลือกที่ 2 ถูก — ฐานข้อมูลมีเครื่องเดียวทุกเครื่องเห็นตรงกัน แต่ storage/ เป็นโฟลเดอร์ของแต่ละเครื่อง · คนที่เปิดหน้าแล้วไปตกเครื่องที่ไม่ใช่เครื่องที่รับอัปโหลดจะไม่เจอไฟล์

ตัวเลือกที่ 1 — Active Storage ไม่ได้บีบอัดรูปตอนเก็บ ไฟล์เป็นแบบที่อัปมา · ตัวเลือกที่ 3 — แถว blob ถูกจดถูกต้อง ปัญหาคือตัวไฟล์ไม่อยู่ในเครื่องที่ถูกถาม · ตัวเลือกที่ 4 — ถ้าเบราว์เซอร์จำรูปไว้ รูปจะขึ้น ไม่ใช่หาย

จุดที่ต้องจำ: ของถาวรต้องอยู่นอกตัวแอป (12-Factor ข้อ VI) · ไฟล์ไปโกดังกลาง ข้อมูลไปฐานข้อมูลกลาง

ใน bucket ไฟล์ชื่อ l79czbrb5id3zw723b3nbxrllau6 · แล้วชื่อ khaosoi.jpg ที่ผู้ใช้อัปมาถูกเก็บไว้ที่ไหน?

ตัวเลือกที่ 4 ถูก — blob คือใบรับฝาก จดทั้ง key (ชื่อในโกดัง) และ filename (ชื่อเดิม) ไว้แถวเดียวกัน · console เห็น filename: "khaosoi.jpg" คู่กับ key: "l79c…"

ตัวเลือกที่ 1 — ชื่อใน bucket คือ key ล้วน ไม่มีส่วนที่ซ่อน · ตัวเลือกที่ 2 — has_one_attached ไม่สร้างคอลัมน์ ไม่มี migration · ตาราง posts ไม่มีช่อง cover · ตัวเลือกที่ 3 — attachment จดแค่ "ของใคร ช่องไหน ชี้ blob ไหน" (name · record_type · record_id · blob_id) ไม่มีชื่อไฟล์

จุดที่ต้องจำ: โกดังเก็บตัวไฟล์ใต้ชื่อสุ่ม · ฐานข้อมูลเก็บ "ข้อมูลเกี่ยวกับไฟล์" (blob) กับ "ไฟล์นี้ของใคร" (attachment)

เพื่อน clone repo ไปแล้วอัปรูปปกไม่ได้ เด้ง Status: 500 และ log มี MissingCredentialsError · วิธีไหนแก้ถูกทางที่สุด?

ตัวเลือกที่ 1 ถูก — เพื่อนได้ .yml.enc มากับ Git แล้ว ขาดแค่กุญแจ · ส่งกุญแจแบบที่ Rails แนะนำ (ที่เก็บรหัสของทีม ไม่ใช่แชตกลุ่ม) แล้ว Rails อ่านรหัสได้ทันที

ตัวเลือกที่ 2 — กุญแจขึ้น Git = ใครเห็น repo ก็ถอดรหัสได้ทุกอย่าง เท่ากับไม่ได้เข้ารหัส · ตัวเลือกที่ 3 — รหัสโผล่ในไฟล์ที่ commit แบบตัวหนังสือธรรมดา คือสิ่งที่บทนี้หลีกเลี่ยง · ตัวเลือกที่ 4 — ผมลองแล้ว: Rails สร้างกุญแจใหม่ให้ แล้วฟ้อง Couldn't decrypt config/credentials/development.yml.enc. Perhaps you passed the wrong key? เพราะกุญแจใหม่ไม่ใช่ตัวที่ล็อกไฟล์นั้น

จุดที่ต้องจำ: .yml.enc ขึ้น Git ได้ · .key ห้ามขึ้น และต้องส่งให้ทีมแยกทางอย่างปลอดภัย

แก้ development.rb เป็น :minio แล้ว แต่อัปรูปเสร็จ ใน bucket ไม่มีไฟล์ใหม่ กลับมีโฟลเดอร์ใหม่ใน storage/ · เพราะอะไร?

ตัวเลือกที่ 3 ถูก — ไฟล์ใน config/environments/ ถูกอ่านครั้งเดียวตอนเปิด server · ผมลองแล้ว blob ถูกจด service_name: "local" จนกว่าจะเปิด server ใหม่

ตัวเลือกที่ 1 — private แปลว่าคนนอกเปิดไม่ได้ · console ล็อกอินด้วยผู้ดูแลเห็นทุกไฟล์ · ตัวเลือกที่ 2 — service: ใน model มีจริงแต่ไม่บังคับ ไม่ใส่ก็ใช้ค่าจาก config · ของเราไม่ใส่และไฟล์ไปโกดังได้ · ตัวเลือกที่ 4 — direct upload ส่งจากเบราว์เซอร์ไปที่เก็บตามที่ server ตั้งค่าอยู่ตอนนั้นทีเดียว ไม่มีขั้นย้ายทีหลัง

จุดที่ต้องจำ: แก้อะไรใน config/ หรือ Gemfile → ปิดเปิด server ใหม่เสมอ · เช็คด้วย blob.service_name
