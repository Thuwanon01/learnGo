## ข้อกำหนด

- เพิ่ม status (draft/scheduled/published) + scheduled_at
  + published_at พร้อม index ที่ scheduled_at
  (โพสต์เดิมทั้งหมดเป็น published · เติม published_at ด้วย rake task ที่รันซ้ำได้ ไม่ใช่ใน migration)
- ใช้ Solid Queue · เพิ่ม jobs: bin/jobs ใน Procfile.dev
  (development ใช้ DB เดียวกับข้อมูล: ตาราง solid_queue_* มาจาก migration ไม่ต้องตั้ง connects_to)
- PublishPostJob ต้อง idempotent ด้วย guard สถานะ
  และต้องมี unique constraint ที่ DB กันสอง worker ชนกัน
  (guard สถานะอยู่ใน with_lock · unique index (post_id, follower_id) ของตารางที่จดว่าส่งอีเมลหาใครแล้ว)
- ใช้ท่า recurring job กวาดทุกนาที ไม่ใช่ wait_until
  (เพราะผู้ใช้แก้เวลาได้)
  (config/recurring.yml ต้องมี key development: ไม่งั้น bin/jobs ไม่กวาดในเครื่องเรา)
- retry_on พร้อม backoff แบบถ่างออก
- discard_on RecordNotFound
- ส่งเฉพาะ id เข้า job ห้ามส่งก้อนข้อมูล
- อีเมลใน development เขียนลงไฟล์ tmp/mails (delivery_method :file) ไม่ต้องลง service เพิ่ม

🍽 เทียบให้เห็นภาพ — ป้ายหน้าร้าน กับ สมุดจดเลขใบงาน

ใบงาน "เปิดร้านแล้วโทรบอกลูกค้าประจำ 3 คน" ถูกยื่นซ้ำ 3 ใบ · พนักงานมีตัวกันสองอย่าง: (1) ดูป้ายหน้าร้านก่อน — ป้ายเขียน "เปิดแล้ว" ก็ไม่ต้องไปพลิกป้ายใหม่ (= guard สถานะ) · (2) สมุดจดเลขใบงาน — ก่อนโทรหาใคร ต้องเขียนชื่อคนนั้นลงสมุดก่อน ถ้าชื่อมีอยู่แล้วเขียนซ้ำไม่ได้ ก็ไม่ต้องโทร (= จองแถว + unique index)

การทดลอง ก = ไม่ดูป้าย พลิกป้ายใหม่ทุกครั้ง → เวลาเปิดร้านบนป้ายเปลี่ยนไปเรื่อย ๆ แต่ลูกค้ายังไม่โดนโทรซ้ำ (สมุดยังกัน) · การทดลอง ข = เลิกเขียนสมุด → ลูกค้าโดนโทร 3 รอบ ทั้งที่สมุดยังมีชื่อครบ 3 คนจากรอบแรก ดูจากสมุดเลยเหมือนไม่มีอะไรผิด

ที่ไม่เหมือนกัน: สมุดของร้านจริงสองคนเขียนพร้อมกันได้ · "สมุด" ของเราคือ unique index ใน Postgres ที่ให้เขียนชื่อเดียวกันได้คนเดียวเสมอ แม้ worker สองตัวมาพร้อมกันในเสี้ยววินาทีเดียว — ตัวที่สองต้องรอ แล้วได้ error ว่าซ้ำ (บท 144) · และการ "โทร" (ส่งอีเมล) อยู่ในก้อนเดียวกับการเขียนสมุด: ส่งพัง = ลบชื่อออกจากสมุดให้ด้วย

🗣 ศัพท์ของข้อ 3–4
durable queue (คิวที่ทนทาน)
คิวที่เก็บใบงานในที่ที่ไม่หายเมื่อ process ตาย (ของเราคือตารางใน Postgres) · ตรงข้ามกับคิวในหน่วยความจำ · ถาม senior ได้ว่า "คิวของระบบนี้ durable ไหมครับ ถ้า worker ตายตอน deploy งานหายไหม"
polling (กวาดเป็นรอบ) vs delayed job (ตั้งเวลาล่วงหน้า)
polling = ตัวกวาดถาม DB ทุกนาทีว่ามีอะไรถึงเวลา · delayed job = แขวนใบงานไว้กับเวลาที่ระบุตอนบันทึก (wait_until) · polling ทนการแก้เวลากว่า แลกกับช้าได้ถึง 1 นาที · พิมพ์บอก AI ได้ว่า "Use a recurring job that polls the DB every minute instead of wait_until, because users can change the scheduled time."
