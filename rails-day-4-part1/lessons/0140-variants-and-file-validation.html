ย่อรูป ตรวจไฟล์จากเนื้อจริง และไฟล์กำพร้า

~25 นาที · ควรผ่าน บทเรียน 138 (รูปปก · MinIO) · บทเรียน 139 (direct upload) และ บทเรียน 125 (N+1 ใน view · bullet) มาก่อน

บท 138 ให้บทความมีรูปปกได้แล้ว แต่ยังมีสามเรื่องที่ทุกโปรเจกต์ที่รับไฟล์ต้องทำ (สไลด์หน้า 12): รูปปกขนาดเต็มใหญ่เกินไปสำหรับการ์ดเล็ก ๆ · ใครจะส่งไฟล์อะไรมาก็ได้แค่ตั้งชื่อลงท้าย .png · และไฟล์ที่อัปขึ้นไปแล้วแต่ไม่ได้ใช้ ค้างอยู่ในโกดังตลอดไป
อ่านจบบทนี้ คุณจะทำรูปย่อด้วย variant และดูได้ว่ามันถูกสร้างตอนไหน · แก้ N+1 ที่รูปปกพามาด้วย with_attached_cover · พิสูจน์ด้วยไฟล์ปลอมของตัวเองว่าโค้ดตรวจไฟล์ในสไลด์ไม่พอ แล้วเปลี่ยนเป็นตรวจจากเนื้อไฟล์ · และนับ/เก็บกวาดไฟล์กำพร้าได้

🔁 ทวนก่อนเริ่ม — คำพวกนี้จะโผล่ในบทนี้

  • blob · attachment (บท 138) — blob = ใบรับฝาก (แถวในตาราง active_storage_blobs: ชื่อไฟล์ ขนาด ชนิด และ key = ชื่อของในโกดัง) · attachment = ป้ายว่าใบรับฝากใบนี้เป็นของแฟ้มไหน (ตาราง active_storage_attachments) · ตัวไฟล์จริงอยู่ใน MinIO
  • direct upload (บท 139) — ตอนกดบันทึก เบราว์เซอร์ขอใบอนุญาตจาก Rails ก่อน แล้วเอาไฟล์ไปฝาก MinIO เอง · ฟอร์มส่งให้ Rails แค่รหัสของไฟล์
  • N+1 · includes · bullet (บท 114 · บท 125) — เดินไปตู้ทีละแผ่น vs ใบเบิกทีเดียวทั้งตะกร้า · bullet = ผู้ช่วยที่ตะโกนบอกใน log
  • validation (บท 110) — กฎใน model ที่ต้องผ่านก่อนบันทึก · ไม่ผ่าน = ไม่บันทึก + ข้อความใน errors
  • console (บท 107) — bin/rails console คุยกับแอปทีละบรรทัด

รูปต้นฉบับใหญ่เกินไปสำหรับการ์ด — variant

รูปที่ผู้ใช้อัปมักใหญ่มาก (รูปจากมือถือกว้างหลายพันพิกเซล หนักหลาย MB) · ถ้าการ์ดในหน้ารวมใช้ไฟล์ต้นฉบับ ผู้ใช้ต้องโหลดรูปใหญ่ 10 รูปเพื่อดูภาพเล็ก ๆ 10 ภาพ · ทางแก้คือทำรูปย่อ — ไฟล์ใหม่ที่เล็กลง ทำจากรูปเดิม แล้วให้การ์ดใช้ไฟล์นั้น

Active Storage ทำรูปย่อให้เองด้วยคำสั่ง variant (แปลว่า "แบบหนึ่งของของชิ้นเดิม") · เราไม่ต้องเก็บไฟล์ย่อเอง ไม่ต้องเพิ่มคอลัมน์ · สั่งแค่ใน view ว่า "ขอแบบย่อไม่เกิน 400×300" — ครั้งแรกที่มีคนขอ Rails ย่อแล้วเก็บไว้ใน MinIO · ครั้งต่อไปหยิบอันเดิม

🔪 เทียบให้เห็นภาพ — หั่นชิ้นพอดีคำจากวัตถุดิบเดิม

รูปต้นฉบับคือปลาทั้งตัวที่ลูกค้าเอามาฝากไว้ในโกดัง · หน้าบทความเดี่ยวเสิร์ฟทั้งตัวได้ · แต่การ์ดในหน้ารวมเป็นจานเล็ก ต้องการแค่ชิ้นพอดีคำ · ครั้งแรกที่มีโต๊ะสั่ง คนครัวไปหยิบปลาจากโกดังมาหั่น แล้วเอาชิ้นที่หั่นแล้วไปเก็บในโกดังด้วย · โต๊ะต่อไปสั่งเมนูเดิม ไม่ต้องหั่นใหม่ หยิบชิ้นเดิมได้เลย · ปลาทั้งตัวยังอยู่ครบ วันหลังอยากได้ชิ้นขนาดอื่นก็หั่นจากตัวเดิมได้อีก

ที่ไม่เหมือนกัน: ร้านจริงหั่นเตรียมไว้ตั้งแต่ก่อนเปิดร้าน · Rails ไม่หั่นล่วงหน้า รอให้มีคนขอครั้งแรกก่อน — ลูกค้าคนแรกเลยรอนานกว่าคนอื่น (ส่วน Rails รู้ได้ยังไงว่าชิ้นไหนหั่นแล้ว เดี๋ยวเห็นใน log ในหัวข้อ "ครั้งแรกหั่น ครั้งต่อไปหยิบ")

เทียบของที่รู้: ถ้าเคยใช้ <Image> ของ Next.js — มันทำแบบเดียวกัน คือย่อรูปตอนมีคนขอครั้งแรกแล้วเก็บไว้ · และอีกเดี๋ยวจะเห็นว่า "สูตรการย่อ" ถูกฝังอยู่ใน URL ของรูป แบบเดียวกับเลขรุ่นบนชื่อไฟล์ CSS (fingerprinting บท 127)

  • image_tag … — helper ที่สร้างแท็ก <img> (บท 124) · ส่งรูปปกให้มันได้ตรง ๆ แบบที่บท 138 ทำในหน้าเดี่ยว
  • post.cover.variant(…) — "ขอรูปปกแบบย่อ" · ยังไม่ย่ออะไรตอนนี้ แค่จดสูตรไว้
  • resize_to_limit: [ 400, 300 ] — สูตร: ย่อให้กว้างไม่เกิน 400 และสูงไม่เกิน 300 โดยรักษาสัดส่วน (รูป 1600×1000 ได้ 400×250 ไม่ใช่ 400×300) · รูปที่เล็กกว่านี้อยู่แล้วไม่ถูกขยาย · เว้นวรรคใน [ 400, 300 ] เพราะ rubocop (ตัวตรวจรูปแบบโค้ดที่โปรเจกต์ติดมา) ชอบแบบนี้ สไลด์เขียนชิดก็ทำงานเหมือนกัน
  • alt: "" — รูปตกแต่ง ไม่มีคำบรรยาย (โปรแกรมอ่านจอจะข้ามไป) · rounded-box = มุมมนของ daisyUI (บท 128)
  • self-start — คลาส Tailwind สำคัญ: การ์ดของ daisyUI เรียงของในแนวตั้งแล้วยืดทุกชิ้นให้เต็มความกว้าง · ไม่ใส่ = รูป 400px ถูกยืดเป็น 720px แตก ๆ (วัดจริงใน Chrome) · ใส่แล้วรูปกว้างตามจริง 400px · ถ้าใส่แล้วรูปยังกว้างเต็มการ์ด = ตัว build CSS ใน bin/dev ไม่ได้เปิดอยู่ (คลาส Tailwind ใหม่ต้องถูก build ก่อนถึงจะมีผล · บท 128)
  • if post.cover.attached? — โชว์เฉพาะบทความที่มีรูป · บทความไม่มีรูปไม่ต้องมีแท็กรูปเปล่า ๆ (if ท้ายบรรทัด = "ทำบรรทัดนี้ก็ต่อเมื่อ…")

ตรวจจากเนื้อไฟล์ — magic bytes

ไฟล์รูปทุกชนิดมีลายเซ็นประจำตัวอยู่ไม่กี่ byte แรกของไฟล์ ที่โปรแกรมสร้างรูปเขียนไว้เสมอ · เรียกกันว่า magic bytes · ดูด้วยตาได้ (ใช้รูปจริงในเครื่องคุณสักรูป ก็อปมาเป็น tmp/real.png) · ผลจริง:

$ file tmp/fake.png tmp/real.png

tmp/real.png: PNG image data, 1600 x 1000, 8-bit grayscale, non-interlaced

  • 8950 4e47 … / .PNG.... — ลายเซ็นของไฟล์ PNG ทุกไฟล์บนโลก (ตัว . คือ byte ที่พิมพ์ออกมาเป็นตัวอักษรไม่ได้)
  • hello th — ไฟล์ปลอมขึ้นต้นด้วยตัวหนังสือ ไม่มีลายเซ็นของรูปชนิดไหนเลย

📦 เทียบให้เห็นภาพ — ฉลากที่ลูกค้าเขียนเอง vs เปิดดูของข้างใน

ลูกค้าเอากล่องมาฝาก เขียนฉลากเองว่า "ปลา" (นามสกุล .png · content_type ที่เบราว์เซอร์ส่งมา) · โค้ดของสไลด์คือพนักงานที่อ่านฉลากแล้วเชื่อ · วิธีที่ถูกคือแง้มฝากล่องดู — ปลาทุกตัวมีหน้าตาของปลา (magic bytes) ปลอมฉลากได้ แต่ปลอมของข้างในยากกว่ามาก

ที่ไม่เหมือนกัน: เราแง้มดูแค่ปากกล่อง (ไม่กี่ KB แรก) ไม่ได้รื้อทั้งกล่อง · คนร้ายที่ตั้งใจจริงทำไฟล์ที่หัวเป็น PNG ถูกต้องแต่ท้ายไฟล์ซ่อนของอื่นได้ · การตรวจนี้กัน "ของผิดชนิด" ได้ ไม่ได้รับประกันว่าไฟล์ปลอดภัย 100% · OWASP (กลุ่มที่ทำคู่มือความปลอดภัยเว็บที่คนทั้งวงการใช้ — เจออีกใน Part 2) จึงแนะนำให้ทำหลายชั้น เช่นจำกัดขนาด เก็บไฟล์ไว้คนละเครื่องกับแอป และสแกนไวรัสถ้าทำได้

method แรก cover_must_be_small_image — ตัวตัดสิน:

  • cover_head — เรียก method ที่สอง ได้ต้นไฟล์ 4 KB เป็นข้อความ (4 KB = 4,096 byte มากพอให้เห็นลายเซ็นทุกชนิดที่เรารับ)
  • StringIO.new(…) — ห่อข้อความให้หน้าตาเหมือนไฟล์ (Marcel อยากได้ของที่ "อ่านได้แบบไฟล์")
  • Marcel::MimeType.for(…) — ส่งแค่เนื้อ ไม่ส่งชื่อ ตามกฎเมื่อกี้ → ได้ชนิดจริงเก็บใน real_type
  • errors.add(…) unless real_type.in?(COVER_TYPES) — unless = "ถ้าไม่" · ชนิดจริงไม่อยู่ในรายการ → แปะข้อความผิด · ข้อความเดียวกับของสไลด์
  • บรรทัดขนาด — เหมือนสไลด์ แค่เขียนบรรทัดเดียว · comment บอกเหตุผลว่าทำไมขนาดเชื่อได้ ทั้งที่ชนิดเชื่อไม่ได้: บท 139 เห็นแล้วว่าใบอนุญาตที่ Rails เซ็นให้เบราว์เซอร์ล็อกขนาดไฟล์ไว้ (X-Amz-SignedHeaders=content-length;…) ส่งไฟล์ขนาดไม่ตรง MinIO ไม่รับ

method ที่สอง cover_head — ไปเอาต้นไฟล์มา ซึ่งอยู่ได้ 3 ที่ จึงมี 3 กิ่ง:

  • if cover.byte_size.zero? → "" — ไฟล์ว่าง 0 byte: ไม่มีอะไรให้อ่าน ตอบข้อความว่าง (Marcel จะบอก "ไม่รู้จัก" → ถูกปฏิเสธ) · ไม่มีกิ่งนี้ การขอช่วง byte จากไฟล์ว่างใน MinIO จะ error
  • elsif cover.blob.persisted? — elsif = "ไม่งั้นถ้า…" · persisted? = ใบรับฝากถูกบันทึกแล้ว = มาทาง direct upload (ใบรับฝากเกิดตอนขอใบอนุญาต และไฟล์อยู่ใน MinIO แล้ว) → download_chunk(0...4.kilobytes) โหลดแค่ช่วง byte ที่ 0 ถึง 4,095 ไม่โหลดทั้งไฟล์ (0...4096 สามจุด = ไม่รวมตัวท้าย)
  • else — แนบไฟล์จากโค้ดตรง ๆ (ใน console หรือ test) ไฟล์ยังอยู่ในมือ ยังไม่ขึ้น MinIO · กิ่งนี้หน้าเว็บไม่ได้ใช้ พิมพ์ตามได้เลย ไม่ต้องจำทุกคำ — อ่านทีละบรรทัดได้ว่า:
    • attachment_changes["cover"].attachable — ของที่กำลังจะแนบ (method ภายในของ Active Storage — ยังไม่มีทางทางการให้อ่านไฟล์ก่อนอัป)
    • io = io[:io] if io.is_a?(Hash) — ถ้าแนบมาแบบ { io: ไฟล์, filename: … } ให้หยิบตัวไฟล์ออกมา
    • io.rewind — กรอกกลับไปต้นไฟล์ (เหมือนกรอเทป) · read(4.kilobytes) — อ่าน 4 KB
    • .tap { io.rewind } — อ่านเสร็จแล้วกรอกลับอีกรอบ ไม่งั้นตอนอัปจริงจะเริ่มอ่านจากกลางไฟล์

✅ กิ่ง else ผมลองจริงใน console แล้ว: แนบ tmp/fake.png ด้วย post.cover.attach(io: File.open(…), filename: "fake.png") → ได้ ["Cover รองรับเฉพาะ PNG, JPEG, WebP"] และรูปเดิมใน DB ไม่ถูกแทน

purge · purge_later
purge = ลบป้าย + ใบรับฝาก + ไฟล์ + รูปย่อ เดี๋ยวนั้น · purge_later = ส่งเป็นงานเบื้องหลัง (Active Job) คืนผลทันที · พิมพ์บอก AI ได้ว่า "use purge_later in request paths so the user does not wait for storage deletes"

📍 ตรวจก่อนไปต่อ: git status --short ต้องเห็นไฟล์ที่ถูกแก้ 5 ไฟล์พอดี — app/controllers/posts_controller.rb · app/models/post.rb · app/views/posts/_form.html.erb · app/views/posts/_post.html.erb · config/application.rb · ใน post.rb ต้องไม่เหลือ cover_is_valid ของสไลด์ · ไฟล์ใน tmp/ ไม่โผล่ (git ไม่สนโฟลเดอร์นี้) · แล้ว commit ได้ เช่น git commit -am "รูปย่อ + ตรวจรูปปกจากเนื้อไฟล์"

ทดสอบความเข้าใจ

(ดัดแปลงจาก Recap case 2 สไลด์หน้า 13) หน้ารวมโชว์รูปย่อของรูปปก และข้อความล้วนของเนื้อหา rich text ในการ์ดทุกใบ · controller เขียน Post.includes(:category).limit(20) · ควรเติมอะไรไม่ให้เกิด N+1?

ตัวเลือกที่ 3 ถูก — ผลจริงในบทนี้: ไม่มี with_attached_cover ได้ 17 query (ป้ายทีละบทความ + ใบรับฝากทีละใบ) · ใส่แล้ว + ปิด track_variants เหลือ 6 · ส่วน with_rich_text_body กันเนื้อหา rich text ทีละบทความ (บท 137)

ตัวเลือกที่ 1 สับสนระหว่างตัวไฟล์ (อยู่ใน MinIO) กับป้าย/ใบรับฝาก (อยู่ใน DB) — N+1 เกิดที่ DB · ตัวเลือกที่ 2 — cover ไม่ใช่ชื่อความสัมพันธ์จริง ลองแล้วได้ Association named 'cover' was not found on Post (ชื่อจริงคือ cover_attachment) · ตัวเลือกที่ 4 — ย้ายที่เรียกไม่ได้ลดจำนวนครั้งที่ไปตู้ ปัญหาอยู่ที่ใบเบิกไม่ได้บอกล่วงหน้า

จุดที่ต้องจำ: ไฟล์แนบ = ความสัมพันธ์ใน DB เหมือน association อื่น · หน้ารวมที่โชว์ไฟล์แนบต้องมี with_attached_* แล้วดูว่าจำนวน query ใน log ไม่โตตามข้อมูล

ทำไมโค้ดในสไลด์ที่ตรวจ cover.content_type.in?(%w[image/png image/jpeg image/webp]) จึงปล่อยไฟล์ข้อความที่ตั้งชื่อ fake.png ผ่านไปได้?

ตัวเลือกที่ 1 ถูก — log จริง: "content_type" => "image/png" มากับใบขอ direct upload ของเบราว์เซอร์ และ Marcel ที่ได้ชื่อไฟล์ไปด้วยตอบ "image/png" · ให้แค่เนื้อ Marcel ตอบ "application/octet-stream"

ตัวเลือกที่ 2 — validation รันจริง (ตอน PATCH) โค้ดตัวจริงของเราปฏิเสธได้ด้วย 422 · ปัญหาคือข้อมูลที่โค้ดของสไลด์ใช้ตัดสิน · ตัวเลือกที่ 3 — content_type ถูกจดลง DB ตั้งแต่ INSERT INTO "active_storage_blobs" ตามที่เบราว์เซอร์บอก MinIO ไม่ได้ยุ่ง · ตัวเลือกที่ 4 — validation รันทุกข้อ (ภารกิจได้ 2 ข้อความพร้อมกัน) และในสไลด์ตรวจชนิดก่อนขนาดด้วยซ้ำ

จุดที่ต้องจำ: ชื่อไฟล์ นามสกุล content_type = สิ่งที่ client อ้าง · ชนิดจริงต้องดูจากเนื้อไฟล์ (magic bytes) โดยไม่บอกชื่อไฟล์ให้ตัวตรวจ

ลูกค้าคนที่สองเปิดหน้ารวม หลังจากคนแรกเปิดไปแล้ว (โค้ดตอนจบบท) · ตอนเบราว์เซอร์ขอรูปย่อของบทความ 30 Rails ทำอะไร?

ตัวเลือกที่ 4 ถูก — log ครั้งที่สอง: Checked if file exists at key: variants/… (yes) → Generated URL → 302 · ไม่มี Downloaded/Uploaded · 46ms → 8ms

ตัวเลือกที่ 1 — ไม่จดลงตาราง ≠ ไม่จำ · ชิ้นย่อยังอยู่ใน MinIO Rails แค่ถามโกดังแทนการเปิดสมุด · ตัวเลือกที่ 2 — ถ้าทำแบบนั้นก็ไม่ต้องมี variant · ผู้ใช้ได้ไฟล์เล็ก 400×250 จริง · ตัวเลือกที่ 3 — เราปิด track_variants แล้ว ตารางนั้นไม่ถูกใช้ และตาราง DB ไม่เคยเก็บตัวไฟล์ เก็บแค่ข้อมูลของไฟล์

จุดที่ต้องจำ: variant ทำครั้งแรกตอนมีคนขอ แล้วเก็บใน storage ใช้ซ้ำ · คนแรกรอ คนต่อไปเร็ว

ผู้ใช้อัปไฟล์ปลอมผ่านฟอร์ม (direct upload) แล้วได้กล่องแดง 422 · ตอนนี้ไฟล์ปลอมนั้นอยู่ที่ไหน?

ตัวเลือกที่ 2 ถูก — ผลจริง: ActiveStorage::Blob.unattached.count → 2 และ exist? ใน MinIO → [true, true] · direct upload ส่งไฟล์และสร้างใบรับฝากก่อนฟอร์มถึง model

ตัวเลือกที่ 1 — ROLLBACK ยกเลิกแค่สิ่งที่ทำใน transaction ของ PATCH · ใบรับฝากถูก COMMIT ไปตั้งแต่ใบสั่ง direct_uploads ก่อนหน้า และ MinIO ไม่รู้จัก transaction ของ Postgres · ตัวเลือกที่ 3 — direct upload ไม่ผ่านเซิร์ฟเวอร์ Rails เลย ไฟล์ไปที่ MinIO ตรง ๆ · ตัวเลือกที่ 4 — ไม่มีป้าย (Attachment Create ไม่เกิด) บทความยังไม่มีรูปปก

จุดที่ต้องจำ: direct upload + validation ไม่ผ่าน = ไฟล์กำพร้า · ต้องมีงานไล่ unattached ที่อายุเกินกำหนดแล้ว purge_later
