ขั้น 1 — ผู้ติดตาม: ตาราง followers

ผู้ติดตาม = คนที่อยากได้อีเมลเมื่อมีบทความใหม่ · เก็บแค่อีเมลพอ · บทนี้ไม่ทำหน้าสมัคร (หัวใจของบทคือ job) — ใส่รายชื่อ 3 คนผ่าน seeds · ชื่อตรงกับผู้ใช้ที่จะมาในบล็อก G (somchai · malee · boss)

  • ไฟล์ใน test/ สองไฟล์ ปล่อยไว้ตามที่ generator สร้าง ยังไม่แตะ (เรื่อง test เป็นของบล็อก J)

เปิด migration ที่เพิ่งได้ (db/migrate/…_create_followers.rb) แก้ให้เป็นแบบนี้ — เติม , null: false กับคอมเมนต์หนึ่งบรรทัด:

class CreateFollowers < ActiveRecord::Migration[8.1]
  def change
    create_table :followers do |t|
      t.string :email, null: false

      t.timestamps
    end
    # อีเมลซ้ำไม่ได้ (คู่กับ validates uniqueness ใน model)
    add_index :followers, :email, unique: true
  end
end
  • null: false — ตู้ไม่ยอมเก็บแถวที่ไม่มีอีเมล (ชั้น DB · บท 111)
  • add_index … unique: true — generator เขียนให้แล้วจาก :uniq · เราแค่เติมคอมเมนต์ข้างบน

  normalizes :email, with: ->(email) { email.strip.downcase }

  validates :email, presence: true, uniqueness: true, format: { with: URI::MailTo::EMAIL_REGEXP }

  • has_many :post_notifications — ประกาศไว้ก่อนว่าคนหนึ่งมี "บันทึกการส่ง" ได้หลายแถว · ตารางนี้จะสร้างในขั้น 3 (ตอนนี้ยังไม่มีใครเรียกใช้ จึงยังไม่พัง)
  • normalizes :email, with: ->(email) { … } — strip ตัดช่องว่างหัวท้าย · downcase ทำเป็นตัวเล็ก · ทำก่อนเก็บและก่อนค้นทุกครั้ง
  • format: { with: URI::MailTo::EMAIL_REGEXP } — รูปแบบอีเมลที่ Ruby มีมาให้ (มาตรฐานเดียวกับช่อง <input type="email"> ของเบราว์เซอร์)

ขั้น 2 — อีเมลใน Rails: ActionMailer

ActionMailer คือส่วนของ Rails ที่ทำอีเมล · หน้าตาเหมือน controller + view ที่คุ้นแล้ว: มี method (เหมือน action) เตรียมข้อมูล แล้วมี view วาดเนื้ออีเมล · ต่างกันตรงที่ผลลัพธ์ไม่ได้กลับไปที่เบราว์เซอร์ แต่ถูกส่งออกไปเป็นจดหมาย

เทียบกับร้านอาหาร

ปกติคนจัดจาน (view) วางอาหารบนจานแล้วเสิร์ฟที่โต๊ะลูกค้าที่สั่ง · mailer คือคนจัดจานชุดเดิม แต่ใส่กล่องส่งไปรษณีย์ไปบ้านคนที่ไม่ได้มานั่งในร้าน · แม่พิมพ์ (ERB) เขียนแบบเดียวกัน · คนสั่งให้ทำคือพนักงานหลังร้าน (job) ไม่ใช่ลูกค้าที่โต๊ะ

ที่ไม่เหมือนกัน: ส่งออกไปแล้วเรียกคืนไม่ได้ (ส่งซ้ำ = ลูกค้าได้สองกล่องจริง ๆ) · และที่อยู่บนกล่องต้องเขียนเต็ม — ลิงก์ในอีเมลต้องเป็น post_url (มีชื่อโดเมน) ไม่ใช่ post_path เพราะอีเมลไม่ได้เปิดจากในร้าน ไม่รู้ว่า "ร้านเรา" อยู่ที่ไหน

เทียบของที่รู้: ใน Go ต้องประกอบเองด้วย html/template + ไลบรารีส่งเมล · ใน Next.js มักเรียก service ภายนอก · Rails มีมาในกล่อง และใช้ ERB/helper ชุดเดียวกับหน้าเว็บ (Day 3)

แทนทั้งไฟล์ app/mailers/post_mailer.rb:

class PostMailer < ApplicationMailer
  # อีเมลแจ้งผู้ติดตามว่ามีบทความใหม่ · เรียกจาก PublishPostJob เท่านั้น (ไม่ส่งใน callback ของ model)
  # ลิงก์สร้างตอนส่ง ไม่รับ URL หรือ token ที่สร้างไว้ก่อนเข้าคิว
  def published
    @post = params[:post]
    @follower = params[:follower]

    mail to: @follower.email, subject: "บทความใหม่: #{@post.title}"
  end
end
  • params[:post] — ของที่ยื่นมาตอนเรียก PostMailer.with(post: …, follower: …) (เห็นในขั้น 4) · ชื่อเหมือน params ของ controller แต่ไม่ได้มาจากฟอร์ม
  • @post @follower — ตัวแปร @ ส่งต่อให้ view ได้ เหมือน controller
  • mail to: …, subject: … — ประกอบซองจดหมาย: ผู้รับ หัวเรื่อง · ผู้ส่งมาจาก ApplicationMailer (from@example.com ที่ Rails ใส่ไว้ — ในเครื่องเราไม่เป็นไร)

ขั้น 3 — สมุดจดว่าส่งใครไปแล้ว: ตาราง post_notifications

ท่าที่ใช้คือท่าที่ 3 ของบท 143: กุญแจกันซ้ำ + unique index · กุญแจในที่นี้คือคู่ (บทความ, ผู้รับ) · และใช้ลำดับ"จองก่อนส่ง": เขียนแถวลงสมุดก่อน → เขียนได้ = ได้สิทธิ์ส่ง · เขียนไม่ได้เพราะมีอยู่แล้ว = มีคนส่งไปแล้ว ข้าม

เทียบกับร้านอาหาร

หลังร้านมีสมุดจดใบงานที่ทำแล้ววางข้างประตู · พนักงานส่งของต้องเขียน "จานนี้ → บ้านเลขที่นี้" ลงสมุดก่อนออกไปส่ง · สมุดเล่มนี้พิเศษ: ถ้ามีบรรทัดเดียวกันอยู่แล้ว ปากกาเขียนไม่ติด → พนักงานรู้ทันทีว่ามีคนส่งไปแล้ว ไม่ต้องออกไป · ถ้าออกไปแล้วส่งไม่สำเร็จ (บ้านปิด) กลับมาลบบรรทัดนั้นทิ้ง รอบหน้าจะได้มีคนส่งใหม่

เปิด app/jobs/publish_post_job.rb · ก) แก้คอมเมนต์สองบรรทัดบนสุดเป็น:

    # แจ้งทุกรอบที่บทความเผยแพร่แล้ว (ไม่ใช่แค่รอบที่เพิ่งเปลี่ยนสถานะ):
    # รอบก่อนพังกลางทาง → retry รอบนี้ส่งต่อให้คนที่ยังไม่ได้ · คนที่ได้แล้วถูกกันด้วย unique index

  private
    # เฉพาะคนที่ติดตามก่อนเวลาเผยแพร่: รันซ้ำทีหลังจะไม่ส่งบทความเก่าไปหาคนที่เพิ่งมาติดตาม
    def notify_followers(post)
      Follower.where(created_at: ..post.published_at).find_each do |follower|
        notify(post, follower)
      end
    end

    def notify(post, follower)
      PostNotification.transaction do
        # จองก่อนส่ง: ใส่แถว (post, follower) ได้ = ได้สิทธิ์ส่ง
        PostNotification.create!(post: post, follower: follower)
        # ส่งพังอยู่ใน transaction → แถวที่จองถูกยกเลิกด้วย → retry รอบหน้าส่งใหม่ ไม่หายเงียบ
        PostMailer.with(post: post, follower: follower).published.deliver_now
      end
    rescue ActiveRecord::RecordNotUnique
      # มีแถวอยู่แล้ว = ส่งไปแล้ว (รอบก่อน หรือ worker อีกตัว) → ข้าม
    end
end

  • notify_followers(post) if post.published? — อยู่นอกบล็อก with_lock · ทำทุกรอบที่บทความเผยแพร่แล้ว ไม่ใช่แค่รอบที่เพิ่งเปลี่ยนสถานะ · เพราะถ้ารอบแรกส่งได้ครึ่งเดียวแล้วพัง รอบ retry ต้องส่งต่อให้คนที่เหลือ (ถ้าเขียน return if post.published? แบบสไลด์หน้า 19–20 คนที่เหลือจะไม่ได้อีเมลเลย)
  • private — method ข้างล่างเรียกได้จากในคลาสเท่านั้น · ย่อหน้าเข้าไปอีกขั้นตามสไตล์ของ Rails
  • where(created_at: ..post.published_at) — ..x = "ไม่เกิน x" (SQL <=) · เอาเฉพาะคนที่ติดตามก่อนบทความออก · ไม่งั้นรันซ้ำพรุ่งนี้ คนที่เพิ่งมาติดตามจะได้อีเมลบทความเก่า
  • find_each — วนทีละแถว แต่ดึงจากตู้ทีละ 1,000 (ผู้ติดตามเป็นแสนก็ไม่กินหน่วยความจำ)
  • PostNotification.transaction do … end — สองบรรทัดข้างในสำเร็จพร้อมกัน หรือยกเลิกพร้อมกัน

เมื่อ job พัง — retry_on กับ discard_on

job ที่ส่งอีเมลพังได้สองแบบที่ต่างกันมาก · แบบที่ปัญหาอาจหายเอง — เซิร์ฟเวอร์อีเมลต่อไม่ติดชั่วคราว ยุ่งอยู่ · รอแล้วลองใหม่ก็น่าจะผ่าน · แบบที่ลองใหม่ไปก็เท่านั้น — บทความถูกลบไปแล้วก่อนถึงคิว · ลองอีกร้อยรอบก็หาไม่เจอ · สไลด์หน้า 21 สรุปว่า retry กับ discard ต่างกันที่ความหวัง

และถ้าลองใหม่ ต้องเว้นระยะให้ห่างขึ้นเรื่อย ๆ · ถ้าเซิร์ฟเวอร์อีเมลป่วยอยู่แล้ว job เป็นพันตัวลองใหม่ทุกวินาที = รุมกระหน่ำคนป่วยจนไม่มีวันฟื้น

เทียบกับร้านอาหาร

พนักงานหลังร้านโทรสั่งของจากซัพพลายเออร์ แล้วสายไม่ว่าง → วางสาย รอ 3 วินาทีโทรใหม่ · ยังไม่ว่าง รอ 18 วินาที · แล้ว 1 นาทีครึ่ง · แล้วราว 4 นาที (retry + backoff) · ครบ 5 ครั้งยังไม่ติด → แปะใบงานไว้ที่กระดาน "งานติดปัญหา" ให้ผู้จัดการมาดู · แต่ถ้าใบงานเขียนว่า "ส่งของให้โต๊ะ 12" แล้วลูกค้าโต๊ะ 12 ยกเลิกไปแล้ว → ฉีกใบงานทิ้งเลย ไม่ต้องโทรสักครั้ง (discard)

ที่ไม่เหมือนกัน: พนักงานจริงฟังเสียงแล้วรู้ว่า "สายไม่ว่าง" หรือ "เบอร์นี้ยกเลิกแล้ว" · job ไม่รู้เอง — เราต้องบอกล่วงหน้าเป็นชื่อ error ทีละชื่อ · error ที่เราไม่ได้ระบุ = ไม่ลองใหม่ ไม่ทิ้ง ไปกองที่กระดาน "งานติดปัญหา" ทันที

เปิด app/jobs/publish_post_job.rb เพิ่มใต้บรรทัด queue_as :default (เว้นบรรทัดว่างคั่นตามนี้):

  queue_as :default

  # ส่งอีเมลไม่ผ่านแบบชั่วคราว (เซิร์ฟเวอร์อีเมลต่อไม่ติด / ยุ่ง) → ลองใหม่ เว้นระยะถ่างออกเรื่อย ๆ
  # (ประมาณ 3 วิ · 18 วิ · 83 วิ · 258 วิ) · retry ได้อย่างปลอดภัยเพราะ job นี้รันซ้ำได้
  retry_on Net::OpenTimeout, Net::SMTPServerBusy, wait: :polynomially_longer, attempts: 5
  # บทความถูกลบไปก่อนถึงคิว → ลองใหม่กี่รอบก็ไม่เจอ ทิ้งงานไปเลย
  discard_on ActiveRecord::RecordNotFound

  # รับแค่ id แล้วโหลดสดจาก DB: ได้สถานะ/เวลาล่าสุดเสมอ (ไม่ใช่ค่าเก่าตอนเข้าคิว)
  • Net::OpenTimeout — ต่อเซิร์ฟเวอร์ไม่ติดภายในเวลาที่รอ · Net::SMTPServerBusy — เซิร์ฟเวอร์อีเมลตอบว่า "ยุ่งอยู่ ลองใหม่ทีหลัง" · ทั้งคู่เป็น error ที่ไลบรารีส่งอีเมลของ Ruby โยนออกมา
  • wait: :polynomially_longer — สูตรเว้นระยะของ Rails: (ครั้งที่ลอง)⁴ + 2 วินาที บวกสุ่มเพิ่มไม่เกิน 15% ให้ job ที่พังพร้อมกันไม่ลองพร้อมกันอีก (ตารางข้างล่าง)
  • attempts: 5 — รวมรอบแรกด้วย = ทำรอบแรก + ลองใหม่อีก 4 · ครั้งที่ 5 ยังพัง → ไปอยู่ตาราง solid_queue_failed_executions
  • discard_on ActiveRecord::RecordNotFound — error ที่ Post.find โยนเมื่อหาไม่เจอ → ทิ้งงาน เขียน log หนึ่งบรรทัด จบ

ไฟล์ทั้งไฟล์ตอนนี้ต้องเป็นแบบนี้ (เทียบทีละบรรทัดได้):

# เผยแพร่บทความที่ตั้งเวลาไว้ เมื่อถึงเวลาแล้ว แล้วส่งอีเมลแจ้งผู้ติดตาม
# ห้ามสมมติว่ารันครั้งเดียว: กดปุ่มซ้ำ · ตัวกวาดส่งซ้ำ · retry · สอง worker หยิบงานพร้อมกัน → รันกี่รอบผลต้องเหมือนรอบเดียว
class PublishPostJob < ApplicationJob
  queue_as :default

  # ส่งอีเมลไม่ผ่านแบบชั่วคราว (เซิร์ฟเวอร์อีเมลต่อไม่ติด / ยุ่ง) → ลองใหม่ เว้นระยะถ่างออกเรื่อย ๆ
  # (ประมาณ 3 วิ · 18 วิ · 83 วิ · 258 วิ) · retry ได้อย่างปลอดภัยเพราะ job นี้รันซ้ำได้
  retry_on Net::OpenTimeout, Net::SMTPServerBusy, wait: :polynomially_longer, attempts: 5
  # บทความถูกลบไปก่อนถึงคิว → ลองใหม่กี่รอบก็ไม่เจอ ทิ้งงานไปเลย
  discard_on ActiveRecord::RecordNotFound

  # รับแค่ id แล้วโหลดสดจาก DB: ได้สถานะ/เวลาล่าสุดเสมอ (ไม่ใช่ค่าเก่าตอนเข้าคิว)
  def perform(post_id)
    post = Post.find(post_id)

    # with_lock = SELECT ... FOR UPDATE แล้วโหลดแถวใหม่: worker ตัวที่สองต้องรอตัวแรกเสร็จก่อน
    # แล้วเห็นว่า published ไปแล้ว → ไม่ทำซ้ำ
    post.with_lock do
      # guard สถานะ: เผยแพร่แล้ว เป็นฉบับร่าง หรือยังไม่ถึงเวลา (ผู้ใช้เลื่อนเวลาออกไป) → ไม่ทำอะไร
      if post.scheduled? && post.scheduled_at <= Time.current
        post.update!(status: :published, published_at: Time.current)
      end
    end

    # แจ้งทุกรอบที่บทความเผยแพร่แล้ว (ไม่ใช่แค่รอบที่เพิ่งเปลี่ยนสถานะ):
    # รอบก่อนพังกลางทาง → retry รอบนี้ส่งต่อให้คนที่ยังไม่ได้ · คนที่ได้แล้วถูกกันด้วย unique index
    notify_followers(post) if post.published?
  end

  private
    # เฉพาะคนที่ติดตามก่อนเวลาเผยแพร่: รันซ้ำทีหลังจะไม่ส่งบทความเก่าไปหาคนที่เพิ่งมาติดตาม
    def notify_followers(post)
      Follower.where(created_at: ..post.published_at).find_each do |follower|
        notify(post, follower)
      end
    end

    def notify(post, follower)
      PostNotification.transaction do
        # จองก่อนส่ง: ใส่แถว (post, follower) ได้ = ได้สิทธิ์ส่ง
        PostNotification.create!(post: post, follower: follower)
        # ส่งพังอยู่ใน transaction → แถวที่จองถูกยกเลิกด้วย → retry รอบหน้าส่งใหม่ ไม่หายเงียบ
        PostMailer.with(post: post, follower: follower).published.deliver_now
      end
    rescue ActiveRecord::RecordNotUnique
      # มีแถวอยู่แล้ว = ส่งไปแล้ว (รอบก่อน หรือ worker อีกตัว) → ข้าม
    end
end

ศัพท์ที่เอาไปคุยต่อได้
transient error vs permanent error
error ชั่วคราว (ลองใหม่มีหวัง) กับ error ถาวร (ลองใหม่ไร้ประโยชน์) · ถาม senior ได้ว่า "error ตัวนี้นับเป็น transient ไหมครับ ควร retry_on หรือ discard_on"
exponential / polynomial backoff
เว้นระยะลองใหม่ให้ห่างขึ้นเรื่อย ๆ · Rails ใช้ :polynomially_longer · พิมพ์บอก AI ได้ว่า "retry_on Net::OpenTimeout ด้วย polynomially_longer ไม่เกิน 5 ครั้ง"
jitter
ระยะรอที่สุ่มเพิ่มเล็กน้อย ให้ job ที่พังพร้อมกันไม่ลองใหม่พร้อมกันจนรุมเซิร์ฟเวอร์ซ้ำ (thundering herd)
failed execution / dead letter
ใบงานที่ลองครบแล้วยังพัง เก็บไว้ให้คนตรวจ · ระบบคิวอื่นเรียก dead letter queue

deploy ตอน job กำลังรัน — SIGTERM และใบงานที่กลับเข้าคิว

deploy (เอาโค้ดเวอร์ชันใหม่ขึ้นเครื่องจริง) ต้องปิดโปรแกรมเก่าก่อนเสมอ · ระบบจะส่ง SIGTERM ไปบอก worker ว่า "เก็บของ กำลังจะปิด" (เหมือน Go บท 25) · worker ที่ดีหยุดรับงานใหม่ แล้วพยายามทำงานในมือให้จบ · ถ้าไม่จบในเวลาที่ให้ งานนั้นถูกแขวนกลับเข้าคิว → ตัวใหม่หยิบไปทำใหม่ตั้งแต่ต้น

กลับเข้าคิว = ถูกทำซ้ำ = idempotency ต้องทำงานตรงนี้แหละ (สไลด์หน้า 21)

ที่ไม่เหมือนกัน: พนักงานจริงจำได้ว่าทำไปถึงไหนแล้ว · job เริ่มใหม่ตั้งแต่บรรทัดแรก ไม่รู้ว่ารอบก่อนทำอะไรไปบ้าง (เว้นแต่ใช้ Continuations ข้างล่าง) · และถ้าโดนดึงปลั๊กกะทันหัน (เครื่องดับ · kill -9) ไม่มีใครได้แขวนใบงานคืน — Solid Queue จะย้ายใบนั้นไปกองงานล้มเหลว ไม่ทำใหม่เอง (README ของ Solid Queue · หัวข้อ "Jobs interrupted by non-graceful process death")

เครื่องที่ตรวจลองให้ดู (ไม่ต้องทำตาม) ด้วย job ทดลองที่ทำงาน 20 วินาที (ไฟล์ชั่วคราว ลบทิ้งหลังทดลอง):

# ทดลองเท่านั้น: งานยาว 20 วินาที

    20.times { |i| sleep 1 }
    logger.info "งานยาว: เสร็จ"
  end
end

งานยาวมาก — Active Job Continuations (แค่รู้จัก)

Rails 8.1 เพิ่มทางเลือกให้ job ยาว ๆ (เช่น ไล่แก้บทความแสนแถว) แบ่งเป็นขั้น และจดว่าทำถึงแถวไหนแล้ว · โดนปิดกลางทาง กลับมาทำต่อจากจุดเดิม ไม่ต้องเริ่มใหม่ · ตัวอย่างของสไลด์หน้า 21 (ไม่ต้องพิมพ์ — แอปเราไม่มีคอลัมน์ indexed และไม่มี method send_report · ตรวจแล้วว่า ActiveJob::Continuable, step, step.cursor, step.advance!(from:) มีจริงใน Rails 8.1.4): 

class BackfillJob < ApplicationJob
  include ActiveJob::Continuable

  def perform
    step :mark_posts do |step|
      Post.find_each(start: step.cursor) do |p|
        p.update!(indexed: true)
        step.advance!(from: p.id)
      end
    end
    step :send_report
  end
end
  • step :mark_posts do |step| — ขั้นที่ 1 · step.cursor = "ทำถึงแถวไหนแล้ว" (รอบแรกว่าง = เริ่มต้น) · step.advance!(from: p.id) = จดว่าทำถึงแถวนี้แล้ว และเป็นจุดที่ยอมให้หยุดได้
  • step :send_report — ขั้นที่ 2 · เรียก method ชื่อเดียวกัน · ทำเมื่อขั้นที่ 1 จบ
  • แอปเรายังไม่มีงานยาวขนาดนั้น · PublishPostJob ทำเสร็จในไม่ถึงหนึ่งวินาที ใช้ "ทนการทำซ้ำ" ก็พอ

graceful shutdown
ปิดอย่างสุภาพ: หยุดรับงานใหม่ ทำงานในมือให้จบ แล้วค่อยปิด · ถาม senior ได้ว่า "deploy ของเราให้เวลา worker graceful shutdown กี่วินาทีครับ"
shutdown timeout
เวลาที่ยอมรอก่อนบังคับปิด · Solid Queue ค่าเริ่มต้น 5 วินาที (SolidQueue.shutdown_timeout)
claimed / released job
ใบงานที่ worker ถืออยู่ / ถูกปล่อยคืนเข้าคิว · ตาราง solid_queue_claimed_executions
job continuation
job ที่แบ่งขั้นและจดความคืบหน้า กลับมาทำต่อได้ · พิมพ์บอก AI ได้ว่า "ทำ backfill เป็น ActiveJob::Continuable ใช้ step กับ cursor"

กฎเขียน job 5 ข้อ — เทียบกับโค้ดของเรา

สไลด์หน้า 21 ให้กฎ 5 ข้อ · ใช้เป็น checklist ตรวจ job ทุกตัว รวมถึงที่ AI เขียนให้ (Lab บท 145 จะใช้):

กฎเพราะในโค้ดเรา
① job ต้องสั้น — งานยาวแตกเป็นหลาย job หรือใช้ stepสั้น = โดนตัดกลางคันน้อย · ทำซ้ำก็เสียไม่มากตัวกวาด (ขั้นถัดไป) ไม่เผยแพร่เอง แตกเป็น PublishPostJob หนึ่งตัวต่อบทความ
② ส่ง id อย่าส่งก้อนข้อมูลใหญ่หรือไฟล์ข้อมูลในใบงานเก่าตั้งแต่ตอนเข้าคิว · id แล้วโหลดสดได้ค่าล่าสุดperform_later(post.id) · Post.find(post_id)
③ อย่าส่งของที่หมดอายุได้ เช่น signed URL หรือ tokenรอคิวนานหรือ retry ทีหลัง ของหมดอายุไปแล้ว (บท 139)mailer สร้าง post_url ตอนส่ง ไม่รับลิงก์ที่ทำไว้ก่อน
④ สมมติเสมอว่าจะรันซ้ำ และรันช้ากว่าที่คิดat-least-once · retry · deploypost_notifications + unique index · guard เช็ก "ถึงเวลาหรือยัง" ณ ตอนที่รันจริง
⑤ job ที่เขียนลง DB ต้องมี guard ทุกตัวรอบซ้ำต้องไม่เขียนทับของที่ถูกแล้วif post.scheduled? && post.scheduled_at <= Time.current

งานตามเวลา — ตั้งนาฬิกาปลุก หรือ เดินตรวจทุกนาที

ถึงตอนนี้ job ส่งอีเมลได้แล้ว แต่ใครจะสั่ง job ตอนถึงเวลา? สไลด์หน้า 22 ให้สองท่า · ท่า A: ตอนบันทึกบทความ แขวนใบงานพร้อมเวลานัด PublishPostJob.set(wait_until: post.scheduled_at).perform_later(post.id) — ใบงานนอนรอในคิวจนถึงเวลา · ท่า B: มี job อีกตัวทำงานทุกนาที ค้นในตู้ว่าบทความไหนถึงเวลาแล้ว แล้วส่งต่อให้ PublishPostJob

ท่า B ทนกว่า · ท่า A ถ้าผู้ใช้เลื่อนเวลา ใบงานเก่ายังนัดเวลาเดิม (ไปถึงแล้ว guard บอก "ยังไม่ถึง" → ไม่ทำ → เวลาใหม่ไม่มีใครมา) · ถ้าคิวถูกล้าง ใบงานหายพร้อมกัน · ท่า B อ่านเวลาล่าสุดจากตู้ทุกรอบ รอบนี้พลาด รอบหน้าก็เจอ

เทียบกับร้านอาหาร

ท่า A = ตอนรับออเดอร์จัดเลี้ยง ติดนาฬิกาปลุกไว้ที่ใบงานแต่ละใบ "ดังตอนบ่ายสอง" · ลูกค้าโทรมาเลื่อนเป็นบ่ายสาม — นาฬิกาเดิมยังดังบ่ายสอง ไม่มีใครตั้งใหม่ · ท่า B = มีพนักงานเดินดูสมุดออเดอร์ทุกนาที "ออเดอร์ไหนถึงเวลาแล้วบ้าง" · ลูกค้าเลื่อนเวลา ก็แค่แก้ในสมุด รอบหน้าพนักงานเห็นเวลาใหม่เอง

ที่ไม่เหมือนกัน: พนักงานเดินตรวจไม่มีวันเบื่อ แต่ก็ละเอียดได้แค่นาที (ตั้ง 10:30 จะออกช่วง 10:30:00–10:30:01 ไม่ใช่วินาทีที่ 30) · และถ้าพนักงานคนนี้ไม่ได้มาทำงาน (worker ปิด) ช่วงนั้นไม่มีใครเดินตรวจย้อนหลังให้ — แต่ออเดอร์ยังอยู่ในสมุด พอเขากลับมารอบแรกก็เจอเอง (ภารกิจท้ายบทพิสูจน์)

เทียบของที่รู้: ใน Go ต้องเขียน goroutine ที่วนรอบ + time.Sleep(time.Minute) เอง (บท 21) หรือพึ่ง cron ของเครื่อง · Solid Queue มีตัว Scheduler (คนเดินตรวจตามเวลา) อยู่ใน bin/jobs แล้ว แค่บอกในไฟล์ว่าจะให้ทำอะไรเมื่อไร

แทนทั้งไฟล์ app/jobs/publish_scheduled_posts_job.rb:

# ตัวกวาด: config/recurring.yml สั่งให้รันทุกนาที · หาบทความที่ถึงเวลาแล้ว ส่งต่อให้ PublishPostJob ทีละบทความ
# ไม่ใช้ PublishPostJob.set(wait_until: scheduled_at) ตอนบันทึก เพราะผู้ใช้แก้เวลาได้
# (งานที่ตั้งไว้กับเวลาเก่าจะค้างในคิว) ตัวกวาดอ่านเวลาล่าสุดจาก DB ทุกรอบ
# รอบนี้พลาด รอบหน้าก็กวาดเจออีก · ส่งซ้ำก็ไม่เป็นไร เพราะ PublishPostJob รันซ้ำได้
class PublishScheduledPostsJob < ApplicationJob
  queue_as :default

  def perform
    Post.scheduled.where(scheduled_at: ..Time.current).find_each do |post|
      # แยกงานต่อบทความ + ส่งแค่ id: บทความหนึ่งพังไม่ลากบทความอื่น retry เฉพาะตัวที่พัง
      PublishPostJob.perform_later(post.id)
    end
  end
end
  • Post.scheduled — scope ที่ enum สร้างให้ (บท 143) = WHERE status = 'scheduled' · where(scheduled_at: ..Time.current) = เวลานัดไม่เกินตอนนี้
  • perform ไม่รับอะไรเลย — ตัวกวาดไม่ต้องรู้ล่วงหน้าว่าจะเจอบทความไหน
  • บทความเดียวกันอาจถูกส่งเข้าคิวสองรอบ (เช่นรอบที่แล้วยังทำไม่เสร็จ) — ไม่เป็นไร เพราะ PublishPostJob รันซ้ำได้

config/recurring.yml — บอก Scheduler ว่าให้ทำอะไรเมื่อไร

ไฟล์นี้ Rails สร้างมาให้แล้ว · เปิดดูจะเห็นตัวอย่างที่ comment ไว้ และงานหนึ่งตัวใต้ production: · ลองทำตามสไลด์หน้า 22 ก่อน — เพิ่มงานของเราใต้ production::
