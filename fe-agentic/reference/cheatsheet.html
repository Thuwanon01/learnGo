1 · Chat · Code · Cowork — งานแบบไหนใช้ตัวไหน

ทั้งสามตัวใช้โมเดล Claude คิดเหมือนกัน ที่ต่างคือมือของมันเอื้อมไปถึงอะไรได้บ้าง · กฎหยาบ ๆ: ผลลัพธ์เป็น “ความรู้” → Chat · ผลลัพธ์เป็น “ไฟล์ที่เปลี่ยน” หรือ “ผลรันคำสั่ง” → Code

ลักษณะงานตัวที่เหมาะเพราะอะไร
ถามแนวคิด · ขอคำอธิบาย · เทียบสองวิธีChatผลลัพธ์คือความเข้าใจ ไม่ต้องแตะไฟล์
ถามเรื่องโค้ดชิ้นเล็กที่ก็อปไปวางได้ทั้งก้อนChatบริบทพอดีกับที่วาง · ไม่มีอะไรในเครื่องเปลี่ยน
งานเขียนทั่วไป (อีเมล · สรุป · แปล)Chatไม่เกี่ยวกับโปรเจกต์
แก้ bug ที่ต้องไล่หลายไฟล์ · แก้ build / tsc / eslint errorCodeต้องค้นไฟล์จริงและรันคำสั่งตรวจซ้ำ
เพิ่ม feature · refactor ที่กระทบหลายไฟล์Codeแก้ได้ครบทุกจุดแล้วรัน build ยืนยันเอง · ก่อนสั่งควรมี git commit ไว้ย้อนกลับได้
ทำความเข้าใจโปรเจกต์ที่เพิ่งได้มาCode (โหมด Plan หรือ Manual)อ่านไฟล์จริงได้ทั้งโปรเจกต์ · ใช้โหมดที่ไม่แก้อะไรก่อน
งานหลายขั้นข้ามไฟล์และเครื่องมือ ผลงานเป็นเอกสาร (deck · spreadsheet · research) แล้วกลับมาตรวจทีหลังCowork ตามคำโปรยในสไลด์หน้า 7: ให้เป้าหมาย แล้วกลับมาตรวจงาน · สไลด์มีแค่ภาพหน้าเว็บภาพเดียว บทเรียนจึงไม่ลงรายละเอียดเกินนี้

วงจรที่ agent วนเองมีชื่อในเอกสารทางการว่า agentic loop: gather context (ค้นไฟล์ · อ่าน error) → take action (แก้ไฟล์ · รันคำสั่ง) → verify results (รัน build / test ซ้ำ) → ยังไม่เสร็จก็วนใหม่ · ทุกลูกศรคือการตัดสินใจของ AI ไม่ใช่ของคุณ — นี่คือเหตุผลที่ต้องมี workflow 5 ขั้น (หัวข้อ 3)

2 · โหมดสิทธิ์ — ดูก่อนพิมพ์

ใน VS Code เปลี่ยนที่ตัวบอกโหมดใต้ช่องพิมพ์ · ใน CLI กด Shift+Tab · คำถามที่ต้องถามตัวเองก่อนสั่งงานทุกครั้ง: “ตอนนี้อยู่โหมดไหน”

โหมด (ชื่อใน VS Code)ทำอะไรได้โดยไม่ถามเหมาะกับ
Planอ่าน · เขียนแผน แล้วไม่แก้ไฟล์โค้ดจนกว่าคุณจะอนุมัติแผน (ถ้าบัญชีใช้โหมด Auto ได้ คำสั่ง shell ที่ classifier อนุมัติก็รันได้เพื่อสำรวจ)สำรวจโปรเจกต์ก่อนแก้ · ใช้ครั้งแรก
Manualอ่านไฟล์ · ค้นหา · คำสั่งอ่านอย่างเดียวชุดหนึ่ง เช่น ls cat git status · แก้ไฟล์ · npm install · rm · curl · wget ต้องถามอยากเห็นทุกการกระทำ · โค้ดที่ไม่ไว้ใจ
Edit automaticallyแก้ไฟล์ได้เลย รวมคำสั่งจัดการไฟล์ mkdir touch mv cpคุณนั่งรีวิวโค้ดที่มันแก้ไปด้วย
Autoเกือบทุกอย่าง โดยมีโมเดลอีกตัว (classifier) ตรวจแทนและบล็อกสิ่งที่เห็นว่าไม่ปลอดภัยงานยาวที่ไม่อยากถูกถามบ่อย
⚠ สองเรื่องที่ต้องรู้ก่อนกดอนุญาตครั้งแรก

โหมดเริ่มต้นอาจไม่ใช่โหมดที่ถามก่อน — เอกสารระบุว่าบนแพ็กเกจ Pro · Max · Team โหมดเริ่มต้นคือ Auto · ลองครั้งแรกให้เปลี่ยนเป็น Plan หรือ Manual ก่อน

“Yes, and don't ask again” กับคำสั่ง shell = เขียนกฎถาวรลง .claude/settings.local.json ที่รากของ git repo (ต่อคำสั่ง ต่อ repo) ครั้งหน้าเปิดใหม่ก็ไม่ถาม · ส่วนอนุญาตแก้ไฟล์จำแค่จนจบ session · ดูและลบกฎได้ที่ /permissions · กฎตรวจตามลำดับ deny → ask → allow

3 · ตาราง 5 ขั้น Explore → Plan → Code → Evaluate → Commit

สไลด์หน้า 12 นิยาม agentic workflow ว่า “An AI-driven process where autonomous systems use reasoning, planning, and tool use to execute multi-step tasks dynamically” · เส้นประย้อนกลับของ diagram บอกว่า Evaluate ไม่ผ่าน → กลับไปขั้นที่เหมาะ (Plan หรือ Code) แล้ววนใหม่

ขั้นทำอะไร (ถอดจากสไลด์)ต้องตอบได้ก่อนไปขั้นถัดไปคำเตือน · ประโยคที่ใส่ใน prompt
1 · Explore
หน้า 14		 Like a researcher, gather context before touching anything · อ่านไฟล์ที่เกี่ยว ค้นทั้งโปรเจกต์ เข้าใจ pattern · convention · dependency · เป้าหมายคือ mental model ยังไม่ใช่เขียนโค้ด ของที่จะแก้อยู่ไฟล์ไหน · ของคล้าย ๆ กันเขียนแบบไหน · มีของนี้อยู่แล้วหรือยัง · ใครใช้อยู่ (แก้แล้วกระทบใคร) · อ่าน package.json กับ AGENTS.md แล้วหรือยัง read … Do not edit anything yet. · ตัวอย่าง “Add dark mode” — โปรเจกต์ shadcn มีชุดสีโหมดมืดอยู่แล้วครึ่งทาง ข้าม Explore = สร้างซ้ำซ้อน
2 · Plan
หน้า 15		 Decide the approach before implementing · แตกงานเป็นขั้น · ระบุไฟล์ที่เปลี่ยน · คาด edge case และ trade-off ไฟล์ไหนเปลี่ยน กี่ไฟล์ · ทางเลือกที่ตัดทิ้งเพราะอะไร · ตรวจยังไงว่าเสร็จ · คนอื่นอ่านจบในนาทีเดียวแล้วแย้งได้ไหม “A good plan is reviewable by someone who can catch a bad direction before written code.” · show me which files you will change … STOP and wait for my approval · งานเล็กที่อธิบาย diff ได้ประโยคเดียว ข้ามได้ (ตามเอกสาร Claude Code)
3 · Code
หน้า 16		 Execute the plan · แก้ตาม convention ที่เจอตอน Explore diff ตรงกับแผนไหม · มีอะไรนอกแผนเข้ามาหรือเปล่า “Implement what was planned rather than improvising a new scope mid-stream.” · implement only the approved plan · เจอของที่อยากแก้ระหว่างทาง → จดเป็นงานถัดไป
4 · Evaluate
หน้า 17		 Verify the work is CORRECT — Run tests, lint, type-check, execute the code, and review the diff. tsc · eslint · build ผ่านครบ · รันจริงแล้วเห็นผล · diff --stat ตรงแผน · ย้อนเทียบโจทย์ตั้งต้นทีละข้อแล้ว ⚠ “Should check the original requirements.” · “If FAILURES here should be loop back to Code” · แผนผิดตั้งแต่ต้น → กลับไป Plan · re-check every item in Requirements and Examples, one by one
5 · Commit
หน้า 18		 Write a clear commit message describing the change, and record the work. ข้อความบอกว่าเปลี่ยนอะไรและตรวจด้วยอะไร · add เฉพาะไฟล์ที่ตั้งใจ ⚠ “Only reached after Eval passes.” — ไม่มีเครื่องมือไหนบังคับให้ เป็นวินัยล้วน ๆ · only after step 4 fully passes, commit …
✅ ตัวอย่างที่เดินครบ 5 ขั้นในบท 87 — เพิ่ม variant="success" ให้ Button 
$ git diff --stat
 app/globals.css          | 6 ++++++
 app/page.tsx             | 2 ++
 components/ui/button.tsx | 1 +
 3 files changed, 9 insertions(+)

แผนบอก 3 ไฟล์ · --stat ขึ้น 3 ไฟล์ 9 บรรทัด = ตรงแผน · ถ้าเห็นไฟล์ที่ไม่อยู่ในแผนโผล่มา (เช่น package-lock.json ทั้งที่ไม่ได้ลงแพ็กเกจ) หยุดถามก่อน commit

4 · คำสั่งตรวจในขั้น Evaluate / Commit

ทุกคำสั่งในตารางนี้บท 87–89 รันจริง · โปรเจกต์นี้ package.json มีแค่ dev · build · start · lint — ไม่มี test ขั้น Evaluate จึงพึ่ง type-check · lint · build · และ “รันจริงแล้วดูผล”

อยากรู้อะไรพิมพ์ผ่านหน้าตาแบบไหน · ที่ต้องรู้
type ถูกไหม npx tsc --noEmit; echo "rc=$?" ผ่าน = ไม่พิมพ์อะไรเลย เหลือแค่ rc=0 · พัง = rc=2 · จับพิมพ์ชื่อ variant ผิดได้ พร้อมบอก Did you mean '"success"'?
tsc ฟ้อง LayoutProps ทั้งที่ไม่ได้แตะ npx next typegen ขึ้น ✓ Types generated successfully แล้ว error นั้นหาย · type นี้ Next.js สร้างไว้ใน .next/types/ ตอน dev/build · โปรเจกต์ที่เพิ่ง clone ยังไม่มี
แพตเทิร์นอันตราย / สไตล์ npx eslint .; echo "rc=$?" ผ่าน = rc=0 เงียบ ๆ · ไม่ได้ตรวจ type — ได้ rc=0 ทั้งตอนพิมพ์ "sucess" ผิด และตอนลืมใส่ HARD ใน Record<RecipeLevel, string>
ประกอบทั้งโปรเจกต์ได้จริง npx next build ผ่าน = จบด้วยตาราง Route (app) · อ่านจนบรรทัดสุดท้าย — ✓ Compiled successfully ขึ้นก่อน แล้วค่อยพังที่ Running TypeScript ... → Failed to type check.
รันจริงแล้วเห็นผลจริง npx next dev -p 387
curl -s http://localhost:387/ | grep -o '<button[^>]*>บันทึกแล้ว</button>'		 ยืนยันว่า class bg-success อยู่บนปุ่มใน HTML ที่ server ส่งมาจริง
Tailwind สร้าง CSS ของ class นั้นจริงไหม grep -rho '\.bg-success[^{]*{[^}]*}' .next/static เจอ = .bg-success{background-color:var(--success)} · ลืมเพิ่ม token ใน globals.css → grep rc=1 ทั้งที่ tsc · eslint · build ได้ rc=0 หมด
แก้ไปกี่ไฟล์ ตรงแผนไหม · แตะไฟล์ต้องห้ามไหม git diff --stat ตัวเดียวในชุดที่จับ “แอบแก้ components/ui/” ได้ — ลองแก้ badge.tsx แล้ว tsc · eslint · build ผ่านหมด มีแค่ --stat ที่โชว์ components/ui/badge.tsx | 2 +-
หาคนที่ใช้ component อยู่ (เสี่ยง regression ไหม) grep -rn "components/ui/button" app components; echo "rc=$?" rc=1 = ไม่เจอเลย ยังไม่มีใคร import · เป็นคำสั่งของขั้น Explore ที่ใช้ประเมินผลกระทบ
commit เฉพาะที่ตั้งใจ git add app/globals.css app/page.tsx components/ui/button.tsx ระบุชื่อไฟล์ ไม่ใช่ git add . · git commit -am ใช้ได้เฉพาะหลังเพิ่งดู diff --stat ยืนยันแล้ว
ข้อความ commit สองชั้น git commit -m "feat(button): add success variant" -m "… checked: tsc --noEmit, eslint ., next build" บรรทัดแรกสั้น อ่านใน git log --oneline รู้เรื่อง · ย่อหน้าล่างบอกรายละเอียดและตรวจด้วยอะไร

5 · ตาราง 6 หลักของ prompt (สไลด์หน้า 20)

สามข้อแรก (บท 88) ลดจำนวนสิ่งที่ AI ต้องเดา · สามข้อหลัง (บท 89) จัดวางเนื้อหา · กำหนดหน้าตาผลลัพธ์ · และทำอะไรต่อเมื่อยังไม่ตรง · ทุกคำถามที่คุณไม่ได้ตอบใน prompt AI ตอบแทนคุณ — และส่วนใหญ่ไม่ถามกลับ

#หลักใส่อะไรเพิ่มตัวอย่างสั้น (Bad → Good จากสไลด์)

# รอบที่ 1 — prompt แรก (หัวข้อ Markdown + ตัวอย่างในแท็ก XML)
# Role
You are a senior Next.js engineer who follows existing project conventions strictly.

# Context
- Next.js App Router project "Wongnok", TypeScript, Tailwind, shadcn/ui.

  and renders `RecipeCard` from `@/components/RecipeCard`.
- Convention: `components/` = pure presentational, `containers/` = stateful composition.

# Task
Add a "search by recipe name" input and an empty state to the All Recipes page.

# Requirements
- Filter while typing. Case-insensitive. Trim spaces before matching.
- Match on `name` only.
- Empty input shows all recipes.
- No match shows: No recipes match your search
- Keep `RecipeCard` presentational — put state and filtering in `RecipeList`.
- Do not change `RECIPES_MOCK_DATA`, `RecipeCard`'s props, or any other page.

# Examples
<examples>

input: "beef"        → only "Beef Wellington"
input: "  BEEF "     → same as "beef"
input: "pizza"       → empty state: No recipes match your search
</examples>

# Steps
1. Explore: read RecipeList.tsx, recipes.ts, RecipeCard, and app/recipes/page.tsx. Do not edit anything yet.
2. Plan: think step by step, then show me which files you will change, and why,
   plus any edge case you see. STOP and wait for my approval.
3. Code: implement only the approved plan.
4. Evaluate: run `npx tsc --noEmit`, `npx eslint .`, `npx next build`, and fix any failure.
   Then re-check every item in Requirements and Examples, one by one.
5. Commit: only after step 4 fully passes, commit with a clear conventional message.

# Output
When done, reply with exactly 3 sections:
1. Files changed — one line per file
2. Checks — tsc / eslint / build: pass or fail
3. Requirements — each requirement with ✅ or ❌
