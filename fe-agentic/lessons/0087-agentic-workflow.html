Agentic workflow คืออะไร

สไลด์หน้า 12 นิยามไว้ประโยคเดียว:

An AI-driven process where autonomous systems use reasoning, planning, and tool use to execute multi-step tasks dynamically

แปลเป็นภาษาคน: ให้ AI ทำงานหลายขั้นต่อกันเองได้ — ไม่ใช่ถามหนึ่งคำ ตอบหนึ่งก้อน แล้วคุณเอาไปก็อปวางเอง
แต่เป็น AI ที่คิด (reasoning) · วางแผน (planning) · หยิบเครื่องมือมาใช้เอง (tool use — เปิดไฟล์ · ค้นโค้ด · รันคำสั่งใน terminal) แล้วปรับตัวตามผลที่ได้ (dynamically — รันแล้ว error ก็อ่าน error แล้วแก้ต่อ)

สไลด์หน้าเดียวกันวาดขั้นตอนนั้นไว้เป็น 5 กล่องเรียงกัน เริ่มจากคำขอของผู้ใช้ (ตัวอย่างในสไลด์คือ "Add dark mode to the app") แล้วมีเส้นประย้อนกลับจากขั้นที่ 4:

USER REQUEST "Add dark mode to the app" │ ▼ ┌───────────┐ ┌────────┐ ┌────────┐ ┌────────────┐ ┌──────────┐ │ 1 EXPLORE │──▶│ 2 PLAN │──▶│ 3 CODE │──▶│ 4 EVAL │──▶│ 5 COMMIT │ └───────────┘ └────────┘ └────────┘ └────────────┘ └──────────┘ ▲ ▲ │ ▲ │ │ EVALUATION PASSED? │ │ │ ├───── YES ──────┘ │ └───── NO ─────┤ └────────────────── NO ─────┘ "Return to the appropriate step and iterate"

เส้นล่างสุดคือหัวใจของทั้งบท — Evaluate ไม่ผ่าน ห้ามเดินหน้าไป Commit ต้องย้อนกลับไปแก้ แล้วตรวจใหม่ทั้งชุด วนจนกว่าจะผ่าน

ภาพในสไลด์หน้า 12 มีหัวเรื่องว่า “AGENTIC WORKFLOW by Claude Code” พร้อมคำโปรยว่า “Claude Code works like an agent that understands your goal, thinks, acts, and delivers production-ready changes.” — Claude Code ทำงานเหมือน agent ที่เข้าใจเป้าหมาย คิด ลงมือ แล้วส่งงานที่พร้อมใช้จริง · แต่ละกล่องมีคำสรุปสั้น ๆ ใต้ชื่อขั้น (ถอดตามจริง):

ขั้นคำสรุปใต้ชื่อกล่องแปล
1 EXPLOREUnderstand the codebase and contextเข้าใจโค้ดและบริบท
2 PLANBreak down the task and create a planแตกงานแล้ววางแผน
3 CODEImplement the planลงมือตามแผน
4 EVALEvaluate the changes and resultsประเมินสิ่งที่เปลี่ยนและผลลัพธ์
5 COMMITDeliver clean, reviewable changesส่งงานที่สะอาด รีวิวได้

แถวล่างของภาพชื่อ WHY THIS WORKS สรุปว่าทำไมห้าขั้นนี้ได้ผล: Context First (Understand deeply before changing anything) · Planned Execution (Reduce mistakes by thinking ahead) · Iterative Improvement (Continuously refine until it's right) · Quality Focused (Evaluation ensures reliability and maintainability) · Transparent & Reviewable (Clear plan, clean diff, meaningful commits)
และปิดท้ายว่า “Explore → Plan → Code → Eval → Commit — Claude Code follows this agentic workflow to ship better software, faster.”

⚠️ สไลด์สองหน้าพูดเรื่องลูปไม่ตรงกันนิดเดียว — แต่สำคัญ

สไลด์หน้า 17 เขียนว่า “If FAILURES here should be loop back to Code” — ย้อนไป Code
สไลด์หน้า 12 (ภาพ diagram) ลากเส้นประ NO ไปสองที่ คือกล่อง Plan และกล่อง Code พร้อมคำว่า “Return to the appropriate step and iterate”
สองหน้านี้ไม่ได้ขัดกัน หน้า 17 พูดถึงกรณีที่พบบ่อยที่สุด (โค้ดผิด → แก้โค้ด) ส่วนหน้า 12 ครอบกรณีที่แผนผิดตั้งแต่ต้นด้วย — แก้โค้ดกี่รอบก็ไม่ผ่าน เพราะทางที่เลือกไม่ถูก ต้องกลับไปวางแผนใหม่

🔧 เทียบกับของจริง

นึกถึงช่างซ่อมบ้านที่ดี ที่คุณเรียกมาเพราะ “ก๊อกในครัวน้ำหยด”
ช่างดีจะไม่ถอดก๊อกทันที — เขาเดินดูก่อน (ท่อเป็นแบบไหน ยี่ห้ออะไร วาล์วปิดน้ำอยู่ตรงไหน) → บอกคุณก่อนว่าจะทำอะไร (“เปลี่ยนซีลยาง ไม่ต้องเปลี่ยนทั้งก๊อก ค่าของ 80 บาท”) → ลงมือตามที่บอก → เปิดน้ำทดสอบ ดูว่ายังหยดไหม ตรงอื่นรั่วเพิ่มไหม → ผ่านแล้วค่อยเขียนใบงานส่งมอบว่าทำอะไรไป
ห้าขั้นนั้นคือ Explore · Plan · Code · Evaluate · Commit เป๊ะ ๆ

ที่ไม่เหมือนกัน: ช่างจริงเปิดน้ำแล้วเห็นด้วยตาทันทีว่ายังหยดไหม แต่โค้ด “ดูเหมือนเสร็จ” ได้ทั้งที่ยังพัง — ปุ่มขึ้นจอสวยแต่ type ผิด · build ผ่านแต่ไม่ตรงโจทย์
และช่างจริงเหนื่อยเป็น จึงไม่อยากทำซ้ำ · agent ไม่เหนื่อย จึงพร้อมจะเดินต่อเรื่อย ๆ แม้ทางผิด ถ้าไม่มีขั้นตรวจที่ให้ผล “ผ่าน/ไม่ผ่าน” แบบชัด ๆ มันจะหยุดตอนที่คิดว่าเสร็จ ไม่ใช่ตอนที่เสร็จจริง

🗣 ศัพท์ที่เพิ่งเรียนไป
agent / agentic
ระบบ AI ที่ไม่ได้แค่ตอบข้อความ แต่ลงมือทำหลายขั้นเอง ตัดสินใจเองว่าขั้นต่อไปคืออะไร · Claude Code คือ coding agent — มันเปิดไฟล์ รันคำสั่ง แก้โค้ดในเครื่องคุณได้ · ถาม senior ได้ว่า “งานนี้ให้ agent ทำทั้งวงได้ไหม หรือควรคุมทีละขั้น”
tool use
การที่ AI เรียกใช้เครื่องมือภายนอก เช่น อ่านไฟล์ · ค้นโค้ด · รัน npx tsc · นี่คือสิ่งที่ทำให้ agent “เห็นผลจริง” ได้ ไม่ต้องเดา · พิมพ์บอก AI ได้ว่า “run the type-check yourself and show me the output”
feedback loop / iterate
วงจร “ทำ → ตรวจ → เอาผลตรวจมาแก้ → ตรวจใหม่” · คำว่า iterate ในสไลด์หมายถึงการวนรอบนี้ · ประโยคที่ใช้บ่อย: “iterate until tsc, eslint and next build all pass”

ขั้น 1 · Explore — เก็บบริบทก่อนแตะอะไร

สไลด์หน้า 14 มีสามข้อ (ถอดตามจริง):

  • “Like a researcher, gather context before touching anything.” — ทำตัวเป็นนักวิจัย เก็บบริบทก่อนแตะอะไรทั้งนั้น
  • “Read the relevant files, search the codebase, understand existing patterns, conventions, and dependencies.” — อ่านไฟล์ที่เกี่ยว ค้นทั้งโปรเจกต์ ทำความเข้าใจแพตเทิร์น ธรรมเนียมการเขียน และของที่พึ่งพากันอยู่
  • “The goal is a mental model of what exists and how it works, not writing code yet.” — เป้าหมายคือภาพในหัวว่ามีอะไรอยู่แล้วและมันทำงานยังไง ยังไม่ใช่การเขียนโค้ด

diagram หน้า 12 แตกเป็นรายการงานย่อย: Read README and docs · Explore project structure · Search for relevant files and code · Understand existing patterns and conventions · Review tests and configs · เป้าหมาย: Build a mental model of the project.

ลองกับงานจริง: “เพิ่มปุ่มสีเขียวสำหรับสถานะสำเร็จ”

ก่อนแก้อะไร ผมเปิดโปรเจกต์ดูสี่คำถาม — Button อยู่ไหน · variant ที่มีอยู่แล้วเขียนแบบไหน · สีมาจากไหน · มีใครใช้ Button อยู่แล้วบ้าง (จะได้รู้ว่าแก้แล้วกระทบใคร):

สี่บรรทัดคำสั่งนี้ให้ภาพในหัวครบพอจะวางแผนได้:

  • variant ของ Button เป็นรายการใน cva(...) — มี default · outline · secondary · ghost · destructive · link แต่ละตัวคือสตริง class ของ Tailwind · แปลว่าเพิ่ม variant = เพิ่มหนึ่งบรรทัดในรายการนี้
  • สีไม่ได้เขียนตรง ๆ เช่น bg-red-600 แต่ใช้ชื่อสี (token) อย่าง bg-destructive ซึ่งไปโยงกับตัวแปร CSS ใน app/globals.css สองชุด — บรรทัด 66 สำหรับโหมดสว่าง · บรรทัด 101 สำหรับโหมดมืด · นี่คือ convention ของโปรเจกต์ ถ้าเราเขียน bg-green-600 ตรง ๆ โค้ดก็ทำงาน แต่จะผิดธรรมเนียม และโหมดมืดจะไม่เปลี่ยนสีตาม
  • rc=1 ของ grep แปลว่าไม่เจอเลย — ยังไม่มีไฟล์ไหน import Button · เพิ่ม variant ใหม่จึงไม่มีทางทำหน้าเดิมพัง

และอีกสองไฟล์ที่ควรเปิดในขั้นนี้เสมอ: package.json (สคริปต์ที่มีคือ dev · build · start · lint — ไม่มี test ขั้น Evaluate จึงต้องพึ่ง type-check · lint · build) และ AGENTS.md ที่ create-next-app รุ่นนี้สร้างมาให้ ซึ่งเขียนเตือน agent ไว้ตรง ๆ ว่า “This is NOT the Next.js you know” ให้ไปอ่านเอกสารใน node_modules/next/dist/docs/ ก่อนเขียนโค้ด — ไฟล์นี้มีไว้ให้ agent อ่านในขั้น Explore โดยเฉพาะ

โปรเจกต์นี้มี dark mode อยู่แล้วครึ่งทาง — globals.css มีชุดสีโหมดมืดทั้งก้อน (บรรทัด 86 .dark { ... }) และ Button มี class dark: อยู่ 4 บรรทัด
ที่ยังไม่มีคือตัวสลับโหมด (ไม่มีแพ็กเกจอย่าง next-themes) และไม่มีใครใส่ class dark ให้ <html>

agent ที่ข้าม Explore มีโอกาสสูงที่จะเขียนระบบสีโหมดมืดขึ้นใหม่ทั้งชุด ซ้อนกับของเดิม — โค้ดอาจ build ผ่านด้วย แต่ตอนนี้โปรเจกต์มีสองระบบที่ตีกันเอง
ส่วน agent ที่ Explore ก่อนจะรู้ว่างานจริงเล็กกว่าที่คิดมาก: “ทำปุ่มสลับ แล้วใส่/ถอด class dark ที่ <html>” · คำขอเดียวกัน แต่งานคนละขนาด — รู้ได้จากการอ่านเท่านั้น

ขั้น 2 · Plan — ตัดสินใจก่อนลงมือ และให้คนรีวิวได้

สไลด์หน้า 15 (ถอดตามจริง):

  • “Decide the approach before implementing.” — เลือกวิธีให้ได้ก่อนลงมือ
  • “Break the task into steps, identify which files change, and anticipate edge cases and trade-offs.” — แตกงานเป็นขั้น · ระบุว่าไฟล์ไหนจะเปลี่ยน · คาดการณ์ edge case และสิ่งที่ต้องแลก
  • “A good plan is reviewable by someone who can catch a bad direction before written code.” — แผนที่ดีคือแผนที่คนอื่นอ่านแล้วจับได้ว่าไปผิดทาง ตั้งแต่ก่อนมีโค้ดสักบรรทัด

diagram หน้า 12: Identify what needs to be changed · Determine affected files and dependencies · Consider edge cases and impacts · Create a step-by-step implementation plan · เป้าหมาย: Have a clear, safe plan before writing code.

นี่คือแผนที่ผมเขียนจริงก่อนแตะโค้ด (เขียนเอง ไม่ใช่ output ของ AI):

งาน: เพิ่ม Button variant "success" (ปุ่มเขียว สถานะสำเร็จ) ขั้นตอน 1. app/globals.css เพิ่ม token --success / --success-foreground ทั้งโหมดสว่าง (:root) และโหมดมืด (.dark) แล้วโยง --color-success ใน @theme inline (ตาม convention เดียวกับ --destructive) 2. components/ui/button.tsx เพิ่มบรรทัด success ใน variants หน้าตาแบบเดียวกับ default: พื้นทึบ + hover จางลง 3. app/page.tsx ใช้ <Button variant="success"> หนึ่งปุ่มเพื่อทดสอบ ไฟล์ที่เปลี่ยน: 3 ไฟล์ · ไม่แตะ size · ไม่แตะ variant เดิม edge case / trade-off - โหมดมืดต้องอ่านออก → สีตัวอักษรโหมดมืดใช้สีเข้ม (ตรงข้ามกับโหมดสว่าง) - ทางเลือกที่ตัดทิ้ง: เขียน bg-green-600 ตรง ๆ ใน button.tsx เร็วกว่า 1 ไฟล์ แต่ผิด convention และโหมดมืดไม่เปลี่ยนสี ตรวจยังไงว่าเสร็จ npx tsc --noEmit · npx eslint . · npx next build ผ่านหมด เปิดหน้าเว็บจริงแล้วเห็น class bg-success บนปุ่ม

สังเกตว่าแผนนี้สั้นพอให้คนอ่านจบในหนึ่งนาที และมีจุดที่ reviewer แย้งได้จริง — เช่น senior อาจบอกว่า “ไม่ต้องทำโหมดมืดตอนนี้ ทีมยังไม่เปิดใช้” ซึ่งจะตัดงานไปครึ่งหนึ่ง ตั้งแต่ก่อนมีโค้ด — นี่คือความหมายของ reviewable ในสไลด์

เอกสารทางการของ Claude Code พูดเรื่องเดียวกันนี้ไว้ ในหัวข้อ Explore first, then plan, then code — แนะนำให้ใช้ plan mode (กด Shift+Tab จนแถบสถานะขึ้น ⏸ plan mode on) ซึ่ง agent จะอ่านไฟล์และเสนอแผนได้ แต่แก้ไฟล์ไม่ได้จนกว่าคุณจะอนุมัติ

สามอย่างที่ทำให้ commit นี้ “clean” ตามสไลด์:

  • git diff --stat ก่อน add — ตัวเลข 3 ไฟล์ 9 บรรทัดตรงกับแผน ถ้าเห็นไฟล์ที่ไม่อยู่ในแผนโผล่มา (เช่น package-lock.json เปลี่ยนทั้งที่ไม่ได้ลงแพ็กเกจ) ให้หยุดถามก่อน
  • git add ระบุชื่อไฟล์ ไม่ใช่ git add . — คุมได้ว่า commit มีแค่สิ่งที่ตั้งใจ

git รับไปเฉย ๆ ไม่มีคำเตือนสักคำ — git เก็บ “ไฟล์หน้าตาแบบนี้” ไม่ได้สนว่าโค้ดถูกหรือผิด
คำเตือน “Only reached after Eval passes” ในสไลด์จึงไม่มีเครื่องมือไหนบังคับให้ (ถ้าไม่ได้ตั้ง hook หรือ CI ไว้) — มันเป็นวินัยของคุณหรือของ agent ล้วน ๆ

type-check ตรวจว่าค่าแต่ละตัวมีชนิดตรงกับที่ประกาศ (tsc) · lint ตรวจแพตเทิร์นอันตรายและสไตล์ (eslint) · คนละเรื่องกัน ผ่านอันหนึ่งไม่ได้แปลว่าผ่านอีกอัน · พิมพ์บอก AI ได้ว่า “run both tsc --noEmit and eslint, lint passing is not enough”
exit code (rc)
ตัวเลขที่คำสั่งคืนตอนจบ · 0 = สำเร็จ · ไม่ใช่ 0 = มีปัญหา · tsc กับ eslint ที่ผ่านจะไม่พิมพ์อะไรเลย จึงต้อง echo "rc=$?" ดูเอง · agent ก็อ่านตัวเลขนี้เพื่อตัดสินใจว่าจะวนกลับไป Code หรือไปต่อ
regression
ของที่เคยทำงานได้ แล้วพังเพราะงานใหม่ของเรา · diagram หน้า 12 เขียนว่า Ensure no regressions · ขั้น Explore ที่ grep หาคนใช้ Button อยู่ ก็คือการประเมินความเสี่ยงเรื่องนี้ล่วงหน้า · ถาม senior ได้ว่า “แก้ตรงนี้แล้วมีหน้าไหนเสี่ยง regression บ้าง”
scope creep
งานที่ค่อย ๆ บวมเกินที่ตกลงกันไว้ทีละนิด — สิ่งที่สไลด์หน้า 16 เรียกว่า improvising a new scope mid-stream · บอก AI ได้ว่า “stick to the plan, list anything else you notice as follow-ups instead of doing it”

ข้ามขั้นนี้แล้วเกิดอะไร

ตารางสรุปจากตัวอย่างในบทนี้ — ทุกช่องมาจากสิ่งที่เห็นจริงข้างบน:

ข้ามขั้นอาการที่จะเจอเห็นในบทนี้ตรงไหน
1 · Explore ทำของที่มีอยู่แล้วซ้ำ · เขียนผิด convention ของโปรเจกต์ · แก้แล้วกระทบไฟล์ที่ไม่รู้ว่ามีคนใช้ “Add dark mode” — โปรเจกต์มีชุดสีโหมดมืดอยู่แล้ว · ถ้าไม่เจอ --destructive จะเขียน bg-green-600 ตรง ๆ แล้วโหมดมืดไม่เปลี่ยนสี
2 · Plan ไม่มีใครจับทางผิดได้จนโค้ดเสร็จแล้ว · ไม่มีเกณฑ์ว่า “เสร็จ” คืออะไร ขั้น Evaluate จึงไม่รู้จะเทียบกับอะไร แผนระบุ 3 ไฟล์ + วิธีตรวจ — ทำให้ตอน git diff --stat รู้ทันทีว่า 3 ไฟล์ 9 บรรทัด “ตรงแผน”
3 · Code ตามแผน
(ด้นสดแทน)		 diff บวม คนรีวิวหาบรรทัดสำคัญไม่เจอ · ถ้าพังก็ไม่รู้ว่าพังเพราะส่วนไหน ข้อความ “To get started…” ใน page.tsx ที่ชวนลบ แต่ไม่อยู่ในแผน
4 · Evaluate commit ของพังเข้า history · คนถัดไป pull แล้ว build ไม่ผ่าน branch skip-eval — git รับ "sucess" ไปเฉย ๆ แต่ tsc ได้ rc=2
4 · Evaluate
(ตรวจไม่ครบชุด)		 เชื่อเครื่องมือตัวเดียวที่ไม่ได้ครอบเรื่องนั้น eslint ได้ rc=0 ทั้งที่ type ผิด · next build ขึ้น ✓ Compiled successfully ก่อนพัง
5 · Commit งานดีแต่ไม่มีบันทึก · ย้อนกลับไม่ได้ · คนอื่นไม่รู้ว่าเปลี่ยนอะไรและตรวจด้วยอะไร ย่อหน้า checked: tsc --noEmit, eslint ., next build ในข้อความ commit

ภารกิจ — เดินครบ 5 ขั้นด้วยตัวเอง

🎯 เพิ่ม variant success ให้ Badge

ต่อจาก commit feat(button): add success variant ข้างบน ในโปรเจกต์ของคุณเอง (บท 79–85) · ทำทีละขั้น และจดสิ่งที่ได้ของแต่ละขั้นลงกระดาษก่อนไปขั้นถัดไป:

  1. Explore — Badge อยู่ไฟล์ไหน · variant ที่คล้ายกันที่สุดเขียนยังไง · token --success มีอยู่แล้วหรือยัง · มีใครใช้ Badge อยู่ไหม
  2. Plan — เขียนแผนไม่เกิน 10 บรรทัด: ไฟล์ที่เปลี่ยน · หน้าตาแบบไหน (พื้นทึบหรือพื้นจาง) · ตรวจยังไงว่าเสร็จ
  3. Code — ทำตามแผน ห้ามแตะอะไรนอกแผน
  4. Evaluate — รัน tsc --noEmit · eslint . · next build ครบทั้งสาม แล้วเทียบกับแผน
  5. Commit — git diff --stat ก่อน แล้ว commit พร้อมข้อความที่บอกว่าตรวจด้วยอะไร

ถ้าใช้ Claude Code ทำ ให้สั่งทีละขั้นแล้วอ่านสิ่งที่มันทำก่อนอนุญาตขั้นถัดไป — เป้าหมายคือคุณต้องบอกได้ทุกจุดว่ามันอยู่ขั้นไหน

Explore — ผลจริงบนโปรเจกต์เดียวกัน (หลัง commit ของ Button):

$ grep -rn "components/ui/badge" app components; echo "rc=$?"
rc=1

ยังไม่มีใครใช้ Badge → ไม่เสี่ยง regression · เปิด components/ui/badge.tsx จะเห็นว่าโครงเหมือน Button (cva + รายการ variants) และ variant destructive ของ Badge เป็นแบบพื้นจาง (bg-destructive/10 text-destructive) ไม่ใช่พื้นทึบ · token --success มีแล้วจาก commit ก่อน

Plan — 2 ไฟล์: เพิ่ม success ใน badge.tsx แบบพื้นจางตามแพตเทิร์น destructive ของ Badge · ใช้ <Badge variant="success"> ใน page.tsx หนึ่งจุด · ไม่เพิ่ม token ใหม่ (ใช้ของเดิม)

Code — บรรทัดที่เพิ่มใน badge.tsx:

        success:
          "bg-success/10 text-success dark:bg-success/20 [a]:hover:bg-success/20",

ลองตอบดู

โจทย์คือ “ปุ่มสีเขียวบนหน้ายืนยันการชำระเงิน” · agent เพิ่ม variant แล้ววางปุ่มไว้หน้าแรก · tsc · eslint · next build ผ่านหมด — ความผิดพลาดนี้ควรถูกจับได้ที่ไหน?

ตัวเลือกที่ 3 ถูก · สไลด์หน้า 17 เขียนคำเตือนไว้ตรง ๆ ว่า “Should check the original requirements.” และ diagram หน้า 12 ใส่ Validate requirements ไว้ในขั้น Eval
ตัวเลือกที่ 4 ผิด เพราะเครื่องมือตรวจแค่ว่าโค้ดถูกหลักภาษา ไม่รู้ว่าโจทย์ขออะไร — ในบทนี้เราเห็นแล้วว่า class บนปุ่มถูกแต่ถ้าลืม token ปุ่มก็ไม่มีสี และไม่มีเครื่องมือไหนฟ้อง · ตัวเลือกที่ 1 ผิดเพราะ Explore อ่านไฟล์ที่เกี่ยว ไม่ใช่ทุกไฟล์ และมันเกิดก่อนมีโค้ด จึงจับความผิดของโค้ดไม่ได้ · ตัวเลือกที่ 2 ผิดเพราะสไลด์หน้า 18 บอกว่า Commit “Only reached after Eval passes” — ถึงตอนนั้นควรตรวจเสร็จแล้ว
จุดที่ต้องจำ: เครื่องมือผ่าน = โค้ดถูกหลัก · ตรงโจทย์หรือเปล่า ต้องเปิดโจทย์เทียบเอง

ในรอบที่ 1 ที่จงใจพิมพ์ variant="sucess" ผิด — คำสั่งไหนไม่ฟ้องอะไรเลย?

ตัวเลือกที่ 2 ถูก · ผลจริงคือ npx eslint . ได้ rc=0 ไม่พิมพ์อะไรเลย
ตัวเลือกที่ 1 ผิด — tsc จับได้พร้อมบอก Did you mean '"success"'? เพราะ cva ทำให้ variant มี type เป็นรายการสตริงที่แน่นอน ไม่ใช่ string อะไรก็ได้ · ตัวเลือกที่ 3 ผิด — next build ขึ้น ✓ Compiled successfully จริง แต่ยังไม่จบ มันไปพังต่อที่ Running TypeScript แล้วจบด้วย Failed to type check. · ตัวเลือกที่ 4 ผิดเพราะ eslint ไม่ฟ้อง
จุดที่ต้องจำ: lint กับ type-check คนละเรื่อง — เหมือน go vet กับ go build · รันครบชุดทุกครั้ง

Evaluate ไม่ผ่านเพราะ tsc ฟ้องว่าพิมพ์ชื่อ variant ผิด · แผนเดิมยังถูกต้องทุกข้อ — ขั้นต่อไปที่ถูกคืออะไร?

ตัวเลือกที่ 1 ถูก · สไลด์หน้า 17: “If FAILURES here should be loop back to Code” และแผนยังถูก จึงไม่ต้องย้อนไปถึง Plan (diagram หน้า 12 ให้ย้อนไป “the appropriate step” ซึ่งกรณีนี้คือ Code)
ตัวเลือกที่ 2 ผิดเพราะย้อนไกลเกินเหตุ ปัญหาไม่ได้อยู่ที่ความเข้าใจโปรเจกต์ · ตัวเลือกที่ 3 ผิดตรง ๆ กับคำเตือนหน้า 18 “Only reached after Eval passes” — และเราเห็นแล้วว่า git ไม่ห้ามให้ · ตัวเลือกที่ 4 ฟังดูประหยัดเวลา แต่การแก้รอบใหม่อาจทำอย่างอื่นพังได้ (เช่นแก้แล้วเผลอลบ import) ต้องตรวจครบชุดใหม่
จุดที่ต้องจำ: ไม่ผ่าน → กลับไปขั้นที่ต้นเหตุอยู่ → แก้ → ตรวจใหม่ทั้งชุด

ระหว่างเพิ่ม variant success ตามแผน agent เห็นว่าหน้าแรกยังเป็นหน้าตัวอย่างของ create-next-app เลยเขียนหน้าแรกใหม่ทั้งหน้าให้สวยขึ้นด้วย — ผิดหลักข้อไหน?

ตัวเลือกที่ 4 ถูก · สไลด์หน้า 16: “Implement what was planned rather than improvising a new scope mid-stream.”
ตัวเลือกที่ 2 ผิดเพราะ “build ผ่าน” ไม่ได้แปลว่าควรทำ — diff จาก 9 บรรทัดจะบวมเป็นหลายสิบ คนรีวิวไม่ได้ขอ และหาบรรทัดสำคัญไม่เจอ · ตัวเลือกที่ 3 แยก commit ได้จริง แต่แก้ปลายเหตุ งานนั้นไม่ควรเกิดขึ้นในรอบนี้ตั้งแต่แรก เพราะไม่ผ่านการวางแผนและรีวิว · ตัวเลือกที่ 1 ผิดเพราะปัญหาไม่ใช่อ่านไม่พอ แต่คือทำเกินที่ตกลง
จุดที่ต้องจำ: เจอของที่อยากแก้ระหว่างทาง → จดเป็นงานถัดไป · ไม่ยัดเข้างานปัจจุบัน

ถามกลับได้เลย

ถ้าคุณลองให้ Claude Code ทำงานแล้วบอกไม่ได้ว่ามันอยู่ขั้นไหน — เอาสิ่งที่มันพิมพ์ออกมาทั้งก้อนมาคุยได้ เราจะไล่ด้วยกันว่าตรงไหนคือ Explore ตรงไหนมันข้าม Plan ไป และมันรันตรวจครบชุดจริงหรือแค่บอกว่าตรวจแล้ว
หรือถ้า tsc ฟ้อง error ที่ไม่ได้มาจากโค้ดที่คุณแก้ (แบบ LayoutProps ในบทนี้) ก็เอาข้อความมาได้เลย
