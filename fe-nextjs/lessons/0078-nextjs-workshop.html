ก่อนพิมพ์บรรทัดแรก — 5 คำถามที่โจทย์ไม่ได้ตอบ

นี่คือส่วนที่สำคัญที่สุดของบทนี้ อ่านให้จบก่อนเปิดเอดิเตอร์
จดคำตอบของคุณลงกระดาษก่อน แล้วค่อยไปดูว่าโค้ดในสไลด์เลือกทางไหน — ถ้าคุณเลือกต่างจากสไลด์ นั่นไม่ผิด แต่คุณต้องรู้ตัวว่าเลือก

คำถามทางเลือกที่เป็นไปได้โค้ดในสไลด์เลือกทางไหน
1 · ค้นตอนไหน กรองทุกครั้งที่พิมพ์ตัวอักษร · หรือรอกดปุ่ม “ค้นหา” / กด Enter กรองทันทีที่พิมพ์ (onChange) — ไม่มีปุ่มเลย
2 · ตัวพิมพ์เล็กใหญ่ นับ · ไม่นับ ไม่นับ (โจทย์บอกตรง ๆ ว่า case-insensitive)
3 · ช่องว่างหัวท้าย ตัดทิ้งก่อนค้น (trim) · เอาไปค้นตรง ๆ เอาไปค้นตรง ๆ — ไม่มี trim
4 · ค้นไม่เจอ โชว์ข้อความบอก · โชว์พื้นที่ว่าง ๆ · โชว์ทุกคนเหมือนเดิม พื้นที่ว่าง ไม่มีข้อความอะไรเลย
5 · ค้นจากอะไร เฉพาะชื่อ · ชื่อ+รหัส · ชื่อ+รหัส+อายุ เฉพาะ name เท่านั้น
🍜 เทียบกับของจริง

โจทย์บรรทัดครึ่งนี้เหมือนเดินเข้าร้านแล้วสั่งว่า “ขอข้าวผัดจานนึง”
ร้านทำให้ได้แน่ ๆ และคุณก็ได้ข้าวผัดจริง ๆ แต่คนทำต้องตัดสินใจแทนคุณอีกสิบอย่าง: ใส่ไข่ไหม · เผ็ดแค่ไหน · หมูหรือไก่ · มาพร้อมมะนาวไหม
คุณไม่ได้พูดสักคำ แต่พอจานมาถึงแล้วไม่ถูกใจ คุณจะรู้สึกว่า “ร้านทำผิด” ทั้งที่ร้านไม่ได้ทำผิดอะไรเลย — คุณแค่ไม่ได้บอก

ที่ไม่เหมือนกัน: ร้านข้าวผัดถามกลับได้ทันที และคุณชิมคำแรกก็รู้เลยว่าไม่ตรง
แต่ซอฟต์แวร์ “ชิมไม่ออก” — โปรแกรมที่ค้นตอนพิมพ์กับโปรแกรมที่ค้นตอนกดปุ่ม หน้าตาบนสกรีนช็อตเหมือนกันเป๊ะ ต่างกันตอนใช้จริงเท่านั้น และไม่มี compiler ตัวไหนบนโลกฟ้องให้ · นี่คือเหตุผลที่ต้องถามก่อน ไม่ใช่ถามหลังส่งงาน

ภารกิจ 1 — วางลูกค้าทั้ง 25 คนลงหน้าเว็บก่อน (ยังไม่ต้องค้น)

อย่าเพิ่งเขียนช่องค้นหา · งานแรกคือทำให้ข้อมูลโผล่บนจอให้ได้ก่อน ถ้าขั้นนี้ยังไม่ผ่าน การค้นก็ไม่มีอะไรให้ค้น

🎯 ภารกิจข้อ 1

  1. สร้าง components/CustomerList/customers.json วางข้อมูล 25 คนลงไป
  2. สร้าง components/CustomerList/CustomerList.tsx ที่ import ไฟล์ JSON แล้ววาดการ์ดทุกใบด้วย .map()
  3. สร้าง app/customers/page.tsx ที่เรียก <CustomerList />
  4. รัน npx next build ให้ผ่าน แล้วเปิด npx next dev ดูว่ามีการ์ด 25 ใบจริง
// components/CustomerList/CustomerList.tsx
import customers from "./customers.json";

const CustomerList = () => {
  return (
    <div className="grid grid-cols-6 gap-2">
      {customers.map((customer) => (
        <div key={customer.id} className="border p-2 text-center">
          <p>{customer.name}</p>
          <p>age: {customer.age}</p>
        </div>
      ))}
    </div>
  );
};

export default CustomerList;

สามอย่างที่ต้องสังเกต:

  • import customers from "./customers.json" ใช้ได้เลยเพราะ tsconfig.json ที่ create-next-app สร้างให้ เปิด "resolveJsonModule": true ไว้อยู่แล้ว — TypeScript อ่านไฟล์ JSON แล้วเดา type ให้เองด้วย ไม่ต้องประกาศ type Customer ก็ได้
  • key={customer.id} — ห้ามลืม (predict ข้างล่างจะโชว์ให้ดูว่าลืมแล้วเกิดอะไร)
  • ยังไม่ต้องใส่ "use client" เพราะขั้นนี้ยังไม่มี hook สักตัว

App Router ถือว่าทุกไฟล์เป็น Server Component โดยปริยาย — คุณไม่ได้เขียนอะไรผิด แต่คุณไม่ได้เขียนอะไรบางอย่างที่ต้องเขียน
วิธีแก้คือใส่บรรทัดนี้เป็นบรรทัดแรกสุดของไฟล์ (ก่อน import ทุกตัว): 

"use client";

import { useMemo, useState, type ChangeEvent } from "react";

สังเกต Import trace ท้าย error — Next.js บอกเส้นทางให้ครบว่า ไฟล์ที่ผิดคือ CustomerList.tsx และมันถูกลากเข้ามาโดย page.tsx
ใส่ "use client" ที่ CustomerList.tsx พอ ไม่ต้องไปใส่ที่ page.tsx — ยิ่งใส่ไว้ใกล้ปลายทางเท่าไหร่ ส่วนที่ยังรันบน server ก็ยิ่งเหลือมาก

📦 เทียบกับของจริง

"use client" คือสติกเกอร์ที่แปะหน้ากล่องพัสดุว่า “เปิดที่ปลายทางเท่านั้น”
ของในโรงงาน (server) แกะดูได้ ตรวจได้ ห่อเสร็จส่งเป็นกล่องสำเร็จรูปไปเลย แต่ของบางอย่าง — อะไรที่ต้องตอบสนองคนที่ถือมันอยู่ เช่น ช่องพิมพ์ ปุ่มกด — ต้องไปแกะที่บ้านลูกค้า (browser) ถึงจะทำงานได้

ที่ไม่เหมือนกัน: สติกเกอร์บนกล่องจริงติดผิดแล้วของยังส่งถึง แค่คนแกะงง
แต่ "use client" ลืมแปะแล้ว build ไม่ผ่านเลย — ซึ่งเป็นข่าวดี
และที่ต่างกว่านั้น: สติกเกอร์นี้ติดเชื้อลงล่าง — ไฟล์ที่ติด "use client" จะลาก component ทุกตัวที่มัน import ให้กลายเป็นฝั่ง client ตามไปด้วยหมด · เพราะงั้นอย่าแปะไว้บนสุดของต้นไม้ แปะให้ใกล้ใบที่ต้องการมันจริง ๆ

🎯 ภารกิจข้อ 2

  1. ใส่ "use client" บรรทัดแรกของ CustomerList.tsx
  2. เก็บคำค้นด้วย useState("")
  3. เขียนฟังก์ชันกรอง: ถ้าคำค้นเป็นค่าว่างให้คืนทุกคน · ถ้าไม่ว่างให้กรองด้วย includes แบบไม่สนตัวพิมพ์เล็กใหญ่
  4. ห่อผลกรองด้วย useMemo ที่ผูกกับคำค้น
  5. ผูก <input> เข้ากับ state (value + onChange) โดยพิมพ์ type ของ event ให้ถูกต้อง
  6. รัน npx next build และ npx tsc --noEmit ให้ผ่านทั้งคู่

นี่คือโค้ดตามสไลด์หน้า 59 (สไลด์โชว์ถึงบรรทัด 33 ส่วน JSX ที่เหลือผมเขียนต่อให้ตรงกับภาพหน้า 58):

"use client";

import { useMemo, useState, type ChangeEvent } from "react";
import customers from "./customers.json";

const CustomerList = () => {
  const [search, setSearch] = useState("");

  const filterCustomer = (search: string) => {
    if (search !== "") {
      const searchValue = search.toLocaleLowerCase();
      return customers.filter((customer) => {
        const customerName = customer.name.toLocaleLowerCase();
        return customerName.includes(searchValue);
      });
    }
    return [...customers];
  };

  const customerData = useMemo(() => {
    return filterCustomer(search);
  }, [search]);

  const handleSearch = (event: ChangeEvent<HTMLInputElement>) => {
    const value = event.target.value;
    setSearch(value);
  };

  return (
    <>
      <input
        type={"text"}
        className={"border"}
        value={search}
        onChange={handleSearch}
      />
      <div className="grid grid-cols-6 gap-2">
        {customerData.map((customer) => (
          <div key={customer.id} className="border p-2 text-center">
            <p>{customer.name}</p>
            <p>age: {customer.age}</p>
          </div>
        ))}
      </div>
    </>
  );
};

export default CustomerList;

สามจุดในเฉลยที่ควรหยุดถาม

1 · ทำไมต้อง [...customers] ไม่ใช่ customers เฉย ๆ

บรรทัด return [...customers]; คืนสำเนาใหม่ของกองข้อมูล ไม่ใช่ตัวเดิม
ในโค้ดชุดนี้มันยังไม่จำเป็น เพราะเราแค่เอาไป .map() อ่านอย่างเดียว
แต่มันเป็นนิสัยที่ถูก: ถ้าวันหนึ่งมีใครเติม .sort() ต่อท้าย customers ตัวจริงที่ import มาจาก JSON จะโดนเรียงใหม่ถาวรทั้งไฟล์ และมันจะไม่กลับมาเป็นลำดับเดิมจนกว่าจะรีเฟรชหน้า (sort แก้ของเดิม — เรื่องนี้อยู่ใน บท 68 ข้อ 2)

2 · toLocaleLowerCase() ต่างจาก toLowerCase() ยังไง

สไลด์ใช้ toLocaleLowerCase() · คนส่วนใหญ่เขียน toLowerCase() · ผลรันจริงบน node v24.14.0 บนเครื่องนี้:

สองบรรทัดแรกได้เท่ากัน — บนเครื่องนี้ สองอันนี้ไม่ต่างกันเลย
บรรทัดที่สามคือเหตุผลที่มันมีอยู่: ถ้า locale เป็นตุรกี ตัว I ใหญ่ จะกลายเป็น ı (ไม่มีจุด) ไม่ใช่ i — แปลว่า “Isabella” จะหาไม่เจอถ้าผู้ใช้พิมพ์ “i”

⚠️ อย่าจำว่า “toLocaleLowerCase ดีกว่า”

สำหรับการค้นหา คนส่วนใหญ่แนะนำให้ใช้ toLowerCase() ต่างหาก เพราะมันให้ผลเหมือนกันทุกเครื่องทุก locale — คุณจะได้ไม่เจอบั๊กที่ “ทำงานปกติบนเครื่องผม แต่พังบนเครื่องลูกค้าที่ตั้งภาษาตุรกี”
toLocaleLowerCase() เหมาะกับตอนแสดงผลให้คนอ่าน มากกว่าตอนเปรียบเทียบ
ในบทนี้ผมคงไว้ตามสไลด์ทุกตัวอักษร เพื่อให้เทียบกับสไลด์ได้ตรง ๆ แต่ให้รู้ไว้ว่ามีจุดนี้อยู่

3 · useMemo ตรงนี้จำเป็นจริงไหม

ตอบตรง ๆ: ในโจทย์ขนาดนี้ ไม่จำเป็น เขียน const customerData = filterCustomer(search); เฉย ๆ ก็ได้ผลเหมือนกัน และไม่มีใครวัดความต่างได้กับข้อมูล 25 แถว

useMemo เริ่มคุ้มเมื่อสองเงื่อนไขนี้เกิดพร้อมกัน: (ก) การคำนวณแพงจริง (กรองข้อมูลหลักหมื่นแถว) หรือ (ข) ผลลัพธ์ถูกส่งเป็น prop ให้ component ลูกที่ห่อด้วย React.memo ซึ่งจะ re-render ทุกครั้งถ้าได้ array ตัวใหม่

เช็คของจริงก่อนเถียง: next.config.ts ของโปรเจกต์นี้ เป็นค่าเริ่มต้นล้วน ๆ ไม่ได้เปิด React Compiler ไว้ — แปลว่าบนโปรเจกต์นี้ useMemo / useCallback ยังต้องเขียนเองอยู่ ไม่มีตัวช่วยใส่ให้อัตโนมัติ (รายละเอียดอยู่ใน บท 75)

เขียน CustomerSearchV2 ที่ตัดสินใจสามข้อนี้ต่างจากสไลด์:

  1. ค้นตอนกดปุ่ม / กด Enter ไม่ใช่ตอนพิมพ์ — แปลว่าต้องมี state สองตัว: ตัวที่เก็บสิ่งที่กำลังพิมพ์ กับตัวที่เก็บสิ่งที่ค้นไปแล้ว
  2. trim() ก่อนค้น — เคาะ space แล้วต้องเท่ากับไม่ได้พิมพ์อะไร
  3. ค้นไม่เจอต้องมีข้อความบอก พร้อมบอกจำนวนที่เจอเสมอ
  4. รัน npx next build · npx tsc --noEmit · npx eslint ให้ผ่านทั้งสามตัว
"use client";

import { useMemo, useState, type ChangeEvent, type FormEvent } from "react";
import customers from "./customers.json";

type Customer = { id: string; name: string; age: number };

function filterByName(list: Customer[], keyword: string): Customer[] {
  const needle = keyword.trim().toLocaleLowerCase();
  if (needle === "") return list;
  return list.filter((c) => c.name.toLocaleLowerCase().includes(needle));
}

export default function CustomerSearchV2() {
  const [draft, setDraft] = useState("");   // สิ่งที่กำลังพิมพ์
  const [query, setQuery] = useState("");   // สิ่งที่กดค้นไปแล้ว

  const results = useMemo(() => filterByName(customers, query), [query]);

  const handleChange = (event: ChangeEvent<HTMLInputElement>) => {
    setDraft(event.target.value);
  };

  const handleSubmit = (event: FormEvent<HTMLFormElement>) => {
    event.preventDefault();      // กัน browser รีโหลดหน้าทิ้ง state
    setQuery(draft);
  };

  return (
    <section>
      <form onSubmit={handleSubmit}>
        <input type="text" value={draft} onChange={handleChange}
               placeholder="พิมพ์ชื่อลูกค้า" className="border px-2 py-1" />
        <button type="submit" className="border px-3 py-1">ค้นหา</button>
      </form>

      <p>พบ {results.length} คน</p>

      {results.length === 0 ? (
        <p>ไม่พบลูกค้าที่ชื่อมีคำว่า &quot;{query.trim()}&quot;</p>
      ) : (
        <ul>
          {results.map((customer) => (
            <li key={customer.id}>{customer.name} — age: {customer.age}</li>
          ))}
        </ul>
      )}
    </section>
  );
}

🗣 ศัพท์ที่เพิ่งเรียนไป
Client Component / Server Component
ใน App Router ทุกไฟล์เป็น Server Component จนกว่าจะแปะ "use client" · Server Component แตะ useState/useEffect ไม่ได้เลย แลกกับการที่มันไม่ต้องส่ง JavaScript ไปให้ browser · ถาม senior ได้ว่า “อันนี้ต้องเป็น client component จริงไหม หรือดันขอบเขตลงไปได้อีก” คำถามนี้คือคำถามที่ทำให้เว็บเบาลงจริง ๆ
directive ("use client", "use server")
สตริงเปล่า ๆ ที่วางเป็นบรรทัดแรกสุดของไฟล์ แล้วมีความหมายพิเศษกับตัวแปลโค้ด · มันไม่ใช่ import ไม่ใช่ฟังก์ชัน · วางผิดตำแหน่ง (เช่นหลัง import) เท่ากับไม่ได้วาง
prerender / hydration
Next.js สร้าง HTML ชุดแรกไว้ตั้งแต่ตอน build (prerender) แล้วพอถึง browser ค่อยเอา JavaScript มา “เสียบปลั๊ก” ให้กดได้พิมพ์ได้ (hydration) · เพราะงั้นหน้า /t78 ถึงขึ้น ○ (Static) ในตาราง build ทั้งที่ข้างในเป็น client component — 25 การ์ดอยู่ใน HTML ตั้งแต่วินาทีแรก ผู้ใช้เห็นก่อน JS โหลดเสร็จด้วยซ้ำ
controlled input
<input> ที่ค่าถูกบังคับด้วย state (value={search}) แทนที่จะให้ browser จำเอง · ถ้าใส่ value แล้วลืม onChange ช่องจะพิมพ์ไม่ได้เลย และ React จะเตือนใน console · บอก AI ได้ว่า “make this a controlled input”
🗣 ศัพท์สำหรับคุยเรื่องโจทย์ ไม่ใช่เรื่องโค้ด
derived state (สถานะที่คำนวณออกมา)
ผลกรอง customerData ไม่ใช่ state — มันคำนวณจาก search ได้เสมอ · กฎง่าย ๆ: อะไรที่คำนวณจาก state อื่นได้ อย่าเก็บเป็น state ซ้ำ เพราะคุณจะต้องคอยจำอัปเดตให้มันสองที่ แล้ววันหนึ่งจะลืม · ถาม senior ว่า “ตัวนี้ควรเป็น state หรือเป็น derived”
empty state
หน้าจอตอนที่ “ไม่มีอะไรให้แสดง” — ค้นไม่เจอ · ยังไม่มีข้อมูล · โหลดไม่สำเร็จ · เป็นสิ่งที่โจทย์แทบไม่เคยเขียนถึง และเป็นสิ่งที่คนตรวจงานสังเกตเป็นอย่างแรก · ถามคนออกโจทย์ตรง ๆ ว่า “empty state ให้แสดงอะไร”
debounce
หน่วงไม่ให้ทำงานทุกครั้งที่มีเหตุการณ์ รอจนเงียบครบเวลาที่กำหนดค่อยทำทีเดียว · คู่กับคำว่า throttle (จำกัดว่าทำได้ไม่เกิน N ครั้งต่อวินาที) · พิมพ์บอก AI ว่า “debounce the search input by 300ms” ได้เลย
acceptance criteria
รายการเงื่อนไขที่ตกลงกันไว้ว่า “แบบไหนถึงเรียกว่าเสร็จ” · ตารางคำถาม 5 ข้อข้างบนคือการเปลี่ยนโจทย์บรรทัดครึ่งให้กลายเป็น acceptance criteria · ประโยคที่ใช้ได้จริงในที่ทำงาน: “ขอ acceptance criteria ของเคสค้นไม่เจอหน่อยครับ”

วงจร 6 ขั้นในสไลด์หน้า 70 คือคำอธิบายที่ตรงที่สุดของสิ่งที่เกิดขึ้นใน Customer Search ของเรา:

ลองตอบดู

ลืมใส่ "use client" แล้ว npx next build พัง — error ชี้ไปที่ไฟล์ไหน?

ตัวเลือกที่ 3 ถูก · error จริงขึ้นต้นว่า ./components/t78/CustomerList.tsx:1:19 แล้วชี้ลูกศรไปที่คำว่า useState ในบรรทัด import พอดี
Next.js ยังพิมพ์ Import trace ต่อท้ายให้ด้วย ซึ่งไล่จาก CustomerList.tsx ขึ้นไปหา page.tsx — อ่านสองบรรทัดนั้นแล้วจะรู้ทันทีว่าต้องไปแปะ "use client" ที่บรรทัดบนของ trace (ไฟล์ที่ import hook เข้ามาจริง) ไม่ใช่บรรทัดล่างที่เป็นหน้าเว็บที่เรียกมัน

ในโค้ดของสไลด์ (ไม่มี trim) ผู้ใช้เคาะ space bar หนึ่งครั้ง จะเห็นลูกค้ากี่คน จาก 25?

ตัวเลือกที่ 2 ถูก และเหตุผลสำคัญกว่าตัวเลข · ผลรันจริงคือ search=" " -> 25 คน
ตัวเลือกที่ 3 ได้ตัวเลขถูกแต่เหตุผลผิด — โค้ดเทียบด้วย !== ตรง ๆ " " ไม่เท่ากับ "" จึงเข้าไปกรองจริง ๆ แล้วบังเอิญตรงทุกคน เพราะทุกชื่อในไฟล์เป็น “ชื่อ เว้นวรรค นามสกุล”
ความต่างนี้สำคัญตอนข้อมูลเปลี่ยน: ถ้ามีลูกค้าชื่อเดี่ยวไม่มีนามสกุล คนนั้นจะหายไปทันทีที่ผู้ใช้เผลอเคาะ space — ซึ่งเป็นบั๊กที่หาสาเหตุยากมาก

ตาราง next build ขึ้นว่า ○ /t78 (Static) ทั้งที่ CustomerList ติด "use client" — แปลว่าอะไร?

ตัวเลือกที่ 4 ถูก · พิสูจน์ได้ด้วย curl ซึ่งไม่รัน JavaScript เลย — ยังนับ age: NN ได้ 25 อัน แปลว่าการ์ดอยู่ใน HTML ตั้งแต่แรก
"use client" ไม่ได้แปลว่า “ห้ามเรนเดอร์บน server” แต่แปลว่า “ต้องส่ง JavaScript ตัวนี้ไปให้ browser ด้วย เพราะมันต้องตอบสนองผู้ใช้”
ผลคือได้ทั้งสองอย่าง: เห็นเนื้อหาทันที (จาก HTML ที่ prerender ไว้) แล้วพิมพ์ค้นหาได้เมื่อ JS โหลดเสร็จ (hydration)

โค้ดตามสไลด์ · ผู้ใช้พิมพ์ zz ซึ่งไม่ตรงกับใครเลย — ผู้ใช้จะเห็นอะไรบนหน้าจอ?

ตัวเลือกที่ 3 ถูก · ผลรันจริงคือ search="zz" -> 0 คน แล้วโค้ดของสไลด์ .map() บน array ว่าง ซึ่งได้ผลลัพธ์เป็น “ไม่มีอะไร” — ไม่ error (ตัดตัวเลือกที่ 4 ออก) แต่ก็ไม่มีข้อความอะไรบอกผู้ใช้เลย
นี่ไม่ใช่บั๊ก เพราะโจทย์ไม่ได้บอกว่าต้องแสดงอะไร · มันคือ ช่องว่างในโจทย์ที่ถูกเติมด้วยความเงียบ
เวอร์ชัน V2 ในภารกิจข้อ 3 เติมข้อความ ไม่พบลูกค้าที่ชื่อมีคำว่า "zz" เข้าไป — ต่างกันแค่สามบรรทัด แต่ต่างกันคนละเรื่องในสายตาผู้ใช้

เอาไปต่อยอด

ถ้ายังมีแรง ลองเพิ่มทีละอย่างในเวอร์ชันของคุณเอง แล้วรัน next build ทุกครั้ง:

  • ค้นจาก id ได้ด้วย — พิมพ์ c003 แล้วต้องเจอ Sophia Martinez (ตอนนี้ยังไม่เจอ ผลรันจริงคือ search="c003" -> 0 คน)
  • แยกส่วนกรองออกเป็น custom hook useCustomerSearch() ตามกฎสี่ข้อใน บท 77
  • เติม useDebounce 300ms ให้เวอร์ชันค้นตอนพิมพ์
  • ไฮไลต์ตัวอักษรที่ตรงกับคำค้นในชื่อลูกค้า — ข้อนี้จะทำให้คุณเจอกับดักใหม่: ตำแหน่งที่ตรงกันต้องหาจากชื่อตัวจริง ไม่ใช่จากชื่อที่แปลงเป็นตัวพิมพ์เล็กแล้ว

ถามกลับได้เลย

ถ้าคุณเลือกคำตอบของคำถาม 5 ข้อต่างจากในบทนี้ แล้วโค้ดออกมาหน้าตาไม่เหมือนกันเลย — นั่นคือผลลัพธ์ที่ถูกต้องของบทนี้ ไม่ใช่ความผิด
เอาโค้ดของคุณมาคุยได้ พร้อมบอกว่าคุณเลือกทางไหนในแต่ละข้อและเพราะอะไร
ถ้า next build พังแล้วอ่าน error ไม่ออก ก็เอาข้อความ error ทั้งก้อนมาเลย โดยเฉพาะบรรทัด Import trace ซึ่งมักบอกคำตอบไว้แล้ว
