useMemo และ useCallback — จำผลลัพธ์ไว้ ไม่ต้องคิดใหม่ทุกครั้ง

~25 นาที · ต้องผ่านบท 73 (useState) และ 74 (useEffect) มาก่อน · บทนี้ยาวกว่าปกติเพราะสองในสามของเนื้อหาคือ "เมื่อไหร่ที่ไม่ควรใช้"

สองตัวนี้เป็น hook ที่ถูกใส่ผิดที่บ่อยที่สุดในโค้ด React ทั้งโลก เพราะชื่อมันฟังดูเหมือน "ปุ่มเร่งความเร็ว" ที่ใส่แล้วดีขึ้นเสมอ — ซึ่งไม่จริง
ความจริงคือมันต่างกันแค่เรื่องเดียว: useMemo จำค่า ส่วน useCallback จำฟังก์ชัน · จบแค่นั้น ที่เหลือเหมือนกันหมด
และความจริงข้อที่สองที่แสบกว่า: useCallback ที่ใส่ไว้เฉย ๆ โดยที่ลูกไม่ได้ห่อ React.memo คือโค้ดที่ไม่ทำอะไรเลย นอกจากทำให้ไฟล์ยาวขึ้น

1 · ก่อนอื่น: React วาดใหม่ทั้งตัว ทุกครั้งที่ state เปลี่ยน

นี่คือรากของทั้งบท ถ้าข้อนี้ไม่แน่น อีกสิบหัวข้อข้างล่างจะกลายเป็นการท่องจำทันที

ตอนคุณกด setCount(1) ในบท 73 สิ่งที่ React ทำคือ เรียกฟังก์ชัน component ของคุณใหม่ทั้งฟังก์ชัน ตั้งแต่บรรทัดแรกถึงบรรทัดสุดท้าย
ไม่ได้แก้เฉพาะตัวเลขบนจอ · ไม่ได้ "อัปเดตแค่ส่วนที่เปลี่ยน" ในระดับโค้ด — โค้ดในตัว component ถูกรันซ้ำหมด

แปลว่าทุกบรรทัดแบบนี้ ถูกทำใหม่ทุกครั้งที่วาด:

function TodoList({ todos, tab }) {
  const visible = filterTodos(todos, tab);   // ← คำนวณใหม่ทุกครั้ง
  const handleClick = () => {};             // ← สร้างฟังก์ชันก้อนใหม่ทุกครั้ง
  // ...
}

ปกติไม่เป็นไร เพราะงานพวกนี้เร็วมาก · แต่มันเริ่มเป็นเรื่องเมื่อ

  • filterTodos ทำงานกับข้อมูลหลักหมื่นแถว → ช้าจนรู้สึกได้
  • ค่าที่คำนวณได้ถูกส่งเป็น prop ให้ลูก → ลูกเห็น "ของใหม่" ทุกครั้งเลยวาดใหม่ตาม

useMemo กับ useCallback เกิดมาเพื่อสองเคสนี้ เท่านั้น

2 · useMemo — จำ "ค่า" ที่คำนวณได้

สไลด์หน้า 44 เขียนไว้สั้นมากว่า "Cache the result of a calculation between re-renders" — แปลตรงตัวคือ เก็บผลลัพธ์ของการคำนวณไว้ใช้ข้ามการวาด

const cachedValue = useMemo(() => {
  // calculate value
}, [dependencies])

สไลด์หน้า 45 แยกชิ้นส่วนไว้ 3 อย่าง ซึ่งตรงกับของจริงทุกตัว:

ชิ้นส่วนสไลด์เรียกว่าพูดแบบภาษาคน
cachedValue Value ผลลัพธ์ที่ได้จากการเรียกฟังก์ชันคำนวณ — ไม่ใช่ตัวฟังก์ชัน
() => {…} Calculation Function ฟังก์ชันที่ไม่รับอาร์กิวเมนต์ และต้อง return ค่าออกมา
[dependencies] Dependencies ค่าทุกตัวในตัว component ที่ถูกใช้ข้างในการคำนวณ ต้องใส่ให้ครบ

ตัวอย่างของสไลด์หน้า 45–46 คือ TodoList:

const TodoList = ({ todos, tab }) => {
  const visibleTodos = useMemo(() => {
    return filterTodos(todos, tab);
  }, [todos, tab]);

  return (
    <ul>
      {visibleTodos.map(todo => <li key={todo.id}>{todo.text}</li>)}
    </ul>
  );
};

แผนภาพหน้า 46 สรุปลำดับไว้ว่า Tab changed → Recalculate function → Re-render
อ่านให้ดี — มันบอกว่า "คำนวณใหม่" เกิดขึ้นเฉพาะตอน dependency เปลี่ยน ส่วน "วาดใหม่" เกิดได้บ่อยกว่านั้นเยอะ

ของจริง: กดปุ่มที่ไม่เกี่ยวข้อง แล้วดูว่ามันคำนวณใหม่ไหม

ผมสร้างไฟล์นี้ในโปรเจกต์ Next.js จริง (components/MemoDemo.tsx) แล้วรัน:

'use client';

import { useMemo, useState } from 'react';
import { bump } from './counter';   // ตัวนับเล็ก ๆ ที่ผมเขียนเอง

function slowSum(n: number): number {
  console.log(`[คำนวณ] รอบที่ ${bump('calc')} · n=${n}`);
  let total = 0;
  for (let i = 0; i < n; i += 1) total += i;
  return total;
}

export default function MemoDemo() {
  const [n, setN] = useState(1000);
  const [tick, setTick] = useState(0);

  const sum = useMemo(() => slowSum(n), [n]);   // ผูกไว้กับ n ตัวเดียว

  return (
    <div>
      <p>sum={sum} tick={tick}</p>
      <button onClick={() => setN(v => v + 1000)}>เปลี่ยน n</button>
      <button onClick={() => setTick(v => v + 1)}>tick +1</button>
    </div>
  );
}

เปิดหน้าเว็บ แล้วกดปุ่มตามลำดับนี้ · นี่คือ console จริง (ผมแทรกบรรทัด ##### ไว้เองเพื่อคั่นจังหวะ):

[คำนวณ] รอบที่ 1 · n=1000
[คำนวณ] รอบที่ 2 · n=1000
##### B · กด tick +1 (state ที่ไม่เกี่ยวกับ n) #####
##### C · กด เปลี่ยน n #####
[คำนวณ] รอบที่ 3 · n=2000
[คำนวณ] รอบที่ 4 · n=2000

ระหว่างบรรทัด B กับ C ว่างเปล่า — กด tick +1 แล้ว component ถูกวาดใหม่จริง (ตัวเลข tick บนจอเปลี่ยนเป็น 1) แต่ slowSum ไม่ถูกเรียกเลย เพราะ n ยังเป็น 1000 เท่าเดิม
พอกด "เปลี่ยน n" เท่านั้นแหละ มันถึงคำนวณใหม่ — และค่าที่ได้บนจอคือ sum=1999000 ซึ่งคือผลรวม 0 ถึง 1999 จริง ๆ

ทำไม log ขึ้นซ้ำสองบรรทัดทุกครั้ง? ไม่ใช่บั๊กของคุณ — ตอน next dev Next เปิด React Strict Mode ไว้ให้ ซึ่งจงใจเรียกฟังก์ชัน component สองรอบ เพื่อจับโค้ดที่มีผลข้างเคียงแอบแฝง
ตอน next build ผมเห็น log ขึ้นรอบเดียว ในเทอร์มินัล
ดังนั้นเวลาอ่าน console ในโหมด dev ให้ดู "เพิ่มขึ้นหรือไม่เพิ่ม" ไม่ใช่ตัวเลขดิบ

🎯 เทียบให้เห็นภาพ

useMemo คือกระดาษทดที่จดคำตอบข้อยากไว้
ครูให้ทำโจทย์เดิมซ้ำ ๆ ทั้งคาบ — ครั้งแรกคุณคิดจริง แล้วจดคำตอบไว้ข้างโจทย์ ครั้งต่อ ๆ ไปคุณแค่เหลือบดูว่า "โจทย์ยังเป็นตัวเลขชุดเดิมไหม" ถ้าใช่ก็ลอกคำตอบเดิมส่งเลย
"ตัวเลขชุดเดิมไหม" นั่นแหละคือ [dependencies]

ที่ไม่เหมือนกัน: กระดาษทดจริงเก็บคำตอบได้หลายข้อพร้อมกัน แต่ useMemo เก็บได้ค่าเดียว คือค่าล่าสุดเท่านั้น
ถ้า dependency วิ่งกลับไปกลับมา n=1000 → n=2000 → n=1000 มันจะคำนวณใหม่ทั้งสามครั้ง ไม่ได้จำค่าของ 1000 ไว้รอ — ใครคิดว่ามันเป็นตารางแคชย้อนหลังได้ จะประหลาดใจตอนโปรไฟล์

3 · useCallback — จำ "ฟังก์ชัน" ไม่ใช่ค่า

สไลด์หน้า 48 เขียนว่า "Caches a function definition between component re-renders"
สังเกตคำว่า definition — มันไม่เรียกฟังก์ชันของคุณ มันแค่เก็บก้อนฟังก์ชันนั้นไว้ 

const cachedFn = useCallback(() => {
  // function
}, [dependencies])

ตัวอย่างของสไลด์หน้า 49–50:

const ProductPage = ({ productId, referrer }) => {
  const handleSubmit = useCallback(
    (orderDetails) => {
      post(`/product/${productId}/buy`, { referrer, orderDetails });
    },
    [productId, referrer],
  );

  return <ShippingForm onSubmit={handleSubmit} />;
};

ต่างจาก useMemo ตรงที่ฟังก์ชันข้างในนี้ รับอาร์กิวเมนต์ได้ (orderDetails) เพราะมันคือฟังก์ชันที่จะถูกเรียกทีหลัง ตอนคนกดปุ่ม ไม่ใช่ฟังก์ชันที่ React เรียกให้ตอนนี้

ทำไมต้อง "จำฟังก์ชัน" ในเมื่อโค้ดข้างในเหมือนเดิมทุกครั้ง

เพราะ JavaScript ตัดสินว่าฟังก์ชันสองก้อน "เท่ากัน" หรือไม่ จากว่ามันเป็นก้อนเดียวกันในหน่วยความจำหรือเปล่า ไม่ใช่จากเนื้อโค้ดข้างใน
เขียน () => {} สองครั้ง = ได้ของสองก้อนที่ไม่เท่ากัน แม้จะพิมพ์เหมือนกันเป๊ะ

ตัวช่วยก่อน — seeFn เก็บก้อนฟังก์ชันลง Set แล้วคืนจำนวนก้อนที่ไม่ซ้ำกัน (Set ตัดของซ้ำด้วยกฎเดียวกับ === พอดี) · อยู่ใน components/counter.ts ไฟล์เดียวกับ bump:

const seen = new Map<string, Set<unknown>>();

export function seeFn(label: string, fn: unknown): number {
  let s = seen.get(label);
  if (!s) {
    s = new Set<unknown>();
    seen.set(label, s);
  }
  s.add(fn);
  return s.size;
}

แล้วไฟล์ที่ใช้พิสูจน์จริง (components/IdentityDemo.tsx):

'use client';

import { useCallback, useMemo, useState } from 'react';
import { seeFn } from './counter';

export default function IdentityDemo() {
  const [tick, setTick] = useState(0);

  const plain   = () => {};                        // ไม่ห่ออะไรเลย
  const cached  = useCallback(() => {}, []);        // ห่อด้วย useCallback
  const viaMemo = useMemo(() => () => {}, []);     // ห่อด้วย useMemo แต่คืนฟังก์ชัน

  console.log(
    `[Identity] tick=${tick}` +
    ` · plain มีก้อนที่ไม่ซ้ำกัน ${seeFn('plain', plain)} ก้อน` +
    ` · cached มีก้อนที่ไม่ซ้ำกัน ${seeFn('cached', cached)} ก้อน` +
    ` · viaMemo มีก้อนที่ไม่ซ้ำกัน ${seeFn('viaMemo', viaMemo)} ก้อน`,
  );

  return <button onClick={() => setTick(v => v + 1)}>identity tick +1</button>;
}

ลูกที่ห่อ React.memo ก็เหมือนยามหน้าตึกที่จำได้แค่ "เลขกล่องพัสดุ"
ทุกครั้งที่คุณเดินมาส่งของ ยามจะดูเลขกล่อง ถ้าเลขเดิมเขาก็โบกมือให้ผ่าน ไม่ต้องยกเข้าไปใหม่
ปัญหาคือคุณเปลี่ยนกล่องใหม่ทุกเช้า ทั้งที่ของข้างในชิ้นเดิม — ยามเลยเห็นเลขไม่ซ้ำสักวัน แล้วสั่งยกเข้าไปใหม่ทุกวัน
useCallback คือการใช้กล่องใบเดิมซ้ำ

ที่ไม่เหมือนกัน: ยามจริงเปิดกล่องดูข้างในได้ถ้าอยากตรวจ แต่ JavaScript เปิดดูไม่ได้เลย — มันไม่มีวิธีถามว่า "ฟังก์ชันสองก้อนนี้ทำงานเหมือนกันไหม" ทำได้แค่ถามว่า "เป็นก้อนเดียวกันหรือเปล่า"
เพราะฉะนั้นอย่าคิดว่า React "ฉลาดพอจะรู้ว่าโค้ดเหมือนเดิม" — มันไม่รู้ และไม่มีวันรู้

🗣 ศัพท์ที่เพิ่งเรียนไป
memoization
เทคนิค "จำผลลัพธ์ของอินพุตชุดเดิมไว้ ไม่คำนวณซ้ำ" — เป็นที่มาของชื่อ useMemo และ React.memo · ถาม senior ได้ว่า "ตรงนี้ควร memoize ไหม หรือปล่อยให้คำนวณใหม่ไปเลยก็ได้" คำถามนี้จะได้คำตอบตรงกว่าถามว่า "ทำยังไงให้เร็วขึ้น"
re-render (วาดใหม่)
การที่ React เรียกฟังก์ชัน component ของคุณใหม่ทั้งฟังก์ชัน · คนละเรื่องกับการที่หน้าจอเปลี่ยนจริง — วาดใหม่แล้วผลออกมาเหมือนเดิม React ก็ไม่แตะ DOM เลย · พิมพ์บอก AI ได้ว่า "why does this component re-render when X changes" จะได้คำตอบที่ตรงจุดกว่าบอกว่า "หน้าเว็บกระตุก"
referential equality (การเท่ากันโดยอ้างอิง)
กฎที่ว่า object · array · function สองก้อนจะ "เท่ากัน" ก็ต่อเมื่อเป็นก้อนเดียวกัน ไม่ใช่ "หน้าตาเหมือนกัน" · ผมรัน node -e 'console.log((()=>{}) === (()=>{}))' ได้ false จริง · ถาม senior ได้ว่า "prop ตัวนี้เสีย referential equality ทุก render ใช่ไหม" — เป็นประโยคที่บอกอาการได้ครบในบรรทัดเดียว
dependency array

5 · กับดักที่ 1 — useCallback ที่ลูกไม่ได้ห่อ React.memo คือโค้ดที่ไม่ทำอะไรเลย

นี่คือความเข้าใจผิดที่แพงที่สุดของบทนี้ และเป็นเหตุผลที่โค้ดจำนวนมากเต็มไปด้วย useCallback โดยไม่ได้เร็วขึ้นแม้แต่นิดเดียว

useCallback ทำได้อย่างเดียวคือทำให้ prop ที่ส่งลงไปเป็นก้อนเดิม
แต่ ลูกจะสนใจว่า prop เป็นก้อนเดิมหรือไม่ ก็ต่อเมื่อมันถูกห่อด้วย React.memo
ลูกธรรมดา ๆ ที่ไม่ได้ห่อ จะวาดใหม่ทุกครั้งที่พ่อวาดใหม่ ไม่ว่า prop จะเปลี่ยนหรือไม่

ไฟล์ที่ผมใช้พิสูจน์ (components/CallbackDemo.tsx) — ลูกสองตัว ต่างกันแค่ห่อกับไม่ห่อ:

'use client';

import { memo, useCallback, useState } from 'react';
import { bump } from './counter';

// ลูกคนที่ 1 — ไม่ห่ออะไรเลย
function ChildPlain({ onPing }: { onPing: () => void }) {
  console.log(`[ChildPlain] วาดใหม่ครั้งที่ ${bump('plain')}`);
  return <button onClick={onPing}>ChildPlain</button>;
}

// ลูกคนที่ 2 — ห่อด้วย React.memo
const ChildMemo = memo(function ChildMemoInner({ onPing }: { onPing: () => void }) {
  console.log(`[ChildMemo] วาดใหม่ครั้งที่ ${bump('memo')}`);
  return <button onClick={onPing}>ChildMemo</button>;
});

export default function CallbackDemo() {
  const [count, setCount] = useState(0);
  const onPing = useCallback(() => {}, []);   // ← ก้อนเดิมตลอด

  console.log(`[Parent] วาดใหม่ count=${count}`);

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>+1 (count = {count})</button>
      <ChildPlain onPing={onPing} />
      <ChildMemo  onPing={onPing} />
    </div>
  );
}

6 · กับดักที่ 2 — dependency array ผิด แล้วได้ค่าเก่าค้าง

กับดักข้อ 1 ทำให้โค้ดไม่เร็วขึ้น (น่ารำคาญแต่ไม่พัง)
ข้อนี้ทำให้ตัวเลขบนหน้าเว็บผิด ซึ่งแย่กว่ากันเยอะ และหายากกว่าเยอะ 

'use client';

import { useMemo, useState } from 'react';

export default function StaleDemo() {
  const [a, setA] = useState(1);
  const [b, setB] = useState(1);

  const bad  = useMemo(() => a + b, [a]);      // ใช้ b แต่ไม่ได้ใส่ b
  const good = useMemo(() => a + b, [a, b]);   // ใส่ครบ

  return (
    <div>
      <p>a={a} b={b} bad={bad} good={good}</p>
      <button onClick={() => setA(v => v + 1)}>a +1</button>
      <button onClick={() => setB(v => v + 1)}>b +1</button>
    </div>
  );
}

เริ่มที่ a=1 b=1 · กด b +1 สองครั้ง แล้วค่อยกด a +1 หนึ่งครั้ง
bad กับ good จะแสดงเลขอะไรในแต่ละจังหวะ? (ระวังจังหวะสุดท้าย มันไม่ตรงกับที่คนส่วนใหญ่เดา) 

เริ่มต้น          : a=1 b=1 bad=2 good=2
กด b +1           : a=1 b=2 bad=2 good=3
กด b +1 อีกครั้ง  : a=1 b=3 bad=2 good=4
กด a +1           : a=2 b=3 bad=5 good=5

สองจังหวะกลาง bad ค้างอยู่ที่ 2 ทั้งที่ b ขยับไปถึง 3 แล้ว — เพราะ [a] ไม่เปลี่ยน React จึงคืนค่าที่จำไว้ให้ ไม่เรียกฟังก์ชันคำนวณเลย

จังหวะสุดท้ายคือส่วนที่โหดที่สุด: พอ a ขยับ bad กระโดดจาก 2 ไป 5 ข้ามค่า 3 กับ 4 ไปเลย
บนหน้าเว็บจริง อาการนี้จะออกมาเป็น "ตัวเลขไม่อัปเดต แล้วอยู่ดี ๆ ก็เด้งไปค่าที่ถูก" ซึ่งสืบยากมาก เพราะตอนคุณเปิดดู มันมักจะถูกไปแล้ว

7 · กับดักที่ 3 — ใส่ให้ทุกอย่างแล้วช้าลง

ความรู้สึกแรกของทุกคนหลังอ่านสองหัวข้อบนคือ "งั้นใส่มันทุกที่เลยดีกว่า ปลอดภัยไว้ก่อน"
อย่าทำ และเหตุผลไม่ใช่เรื่องสไตล์ แต่เป็นเรื่องต้นทุนที่มีอยู่จริง

useMemo หนึ่งบรรทัด ทำให้เกิดงานพวกนี้ ทุกครั้งที่วาด แม้ตอนที่มันคืนค่าเก่า:

  1. สร้างก้อนฟังก์ชันใหม่ที่ส่งเข้าไป — ข้อนี้ผมพิสูจน์แล้วในหัวข้อ 3 (คอลัมน์ plain ที่ไต่จาก 1 ถึง 6) · useMemo แค่ไม่เรียกมัน แต่มันถูกสร้างไปแล้ว
  2. สร้างอาร์เรย์ dependency ใหม่ — [a, b] คืออาร์เรย์ก้อนใหม่ทุกครั้ง
  3. เทียบทีละช่องกับของรอบก่อน
  4. จองที่เก็บค่าเก่าไว้ตลอดอายุของ component

ถ้าการคำนวณข้างในเป็นแค่ a + b — งานสี่ข้อข้างบนแพงกว่าการบวกเลขเอง แถมยังบวกภาระให้คนอ่านโค้ดอีกต่างหาก

ลำดับที่ควรทำ (เรียงจากบนลงล่าง อย่าข้ามขั้น)

  1. เขียนแบบไม่ใส่ก่อนเสมอ — โค้ดที่อ่านง่ายชนะโค้ดที่ "อาจจะเร็วกว่า"
  2. เจอปัญหาจริง (หน้าสะดุด · พิมพ์แล้วช้า) แล้วค่อยเปิดดู
  3. วัดก่อนแก้ — ใช้ React DevTools Profiler หรือ console.log นับรอบแบบในบทนี้
  4. รู้แล้วว่าใครคือตัวปัญหา ค่อยใส่ useMemo / useCallback + React.memo ตรงจุดนั้น
  5. วัดซ้ำ ว่าดีขึ้นจริง ถ้าไม่ดีขึ้น ให้ถอดออก

ข้อ 5 คือข้อที่คนข้ามมากที่สุด · โค้ดที่ใส่ไว้แล้วไม่มีใครกล้าถอดออก คือหนี้ที่กองเพิ่มขึ้นทุกสัปดาห์

มีข้อยกเว้นข้อเดียวที่ควรใส่ตั้งแต่ต้น — เวลาค่านั้นเป็น object หรือ array ที่ต้องส่งเป็น prop ให้ component ที่ห่อ React.memo หรือต้องใส่ใน dependency array ของ useEffect
สองกรณีนี้ไม่ได้ทำเพื่อ "ความเร็ว" แต่ทำเพื่อ ความถูกต้อง — ไม่ใส่แล้ว useEffect จะยิงทุกรอบไม่หยุด (บท 74 มีตัวอย่างลูปไม่รู้จบให้ดูแล้ว)

8 · เรื่องที่สไลด์ไม่ได้บอก — 'use client' กับ hook สองตัวนี้

ใน App Router ของ Next.js ทุกไฟล์ใน app/ เป็น Server Component โดยปริยาย จนกว่าคุณจะเขียน 'use client' ไว้บรรทัดบนสุด
ตำราส่วนใหญ่จะสรุปสั้น ๆ ว่า "ใช้ hook = ต้องใส่ 'use client'" — ผมลองจริงแล้วไม่ตรงทั้งหมด จึงเขียนตามที่รันได้จริง

ทดสอบความเข้าใจ

1. ข้อไหนอธิบาย "ความต่างระหว่าง useMemo กับ useCallback" ได้ตรงที่สุด?

ตอบตัวเลือกที่ 2 · ต่างกันแค่ "จำค่า" กับ "จำฟังก์ชัน" จบแค่นั้นจริง ๆ ถึงขนาดที่ useCallback(fn, deps) เขียนเป็น useMemo(() => fn, deps) แล้วได้ผลเหมือนกันเป๊ะ — ผมรันพิสูจน์ไว้ในหัวข้อ 3 แล้ว (คอลัมน์ viaMemo ค้างที่ 1 ก้อนเท่ากับ cached)

ตัวเลือกที่ 1 ผิดเพราะไม่เกี่ยวกับความหนักเบาของงาน · ตัวเลือกที่ 3 ผิดสองชั้น — ทั้งคู่ใช้ได้ทั้งสองฝั่ง (ผมเปิด export ของ React ฝั่ง server ให้ดูในหัวข้อ 8) · ตัวเลือกที่ 4 ผิดเพราะทั้งคู่รับ dependency array เหมือนกันทุกประการ
จุดที่ต้องจำ: useMemo จำค่า useCallback จำฟังก์ชัน — ต่างกันแค่นี้จุดเดียว

2. พ่อมี const onPing = useCallback(() => {}, []) แล้วส่งให้ลูกที่ไม่ได้ห่อ React.memo · กดปุ่มให้พ่อวาดใหม่ 2 รอบ ลูกจะเป็นยังไง?

ตอบตัวเลือกที่ 3 · console จริงในหัวข้อ 5 แสดงชัดว่า ChildPlain ไต่ต่อไป 3 · 4 · 5 · 6 หลังกดปุ่มสองครั้ง ทั้งที่ onPing เป็นก้อนเดิมเป๊ะ ส่วน ChildMemo ในหน้าเดียวกันหยุดนิ่งที่ 2

ตัวเลือกที่ 1 คือความเข้าใจผิดที่บทนี้ตั้งใจมาแก้โดยตรง · ตัวเลือกที่ 2 ผิดเพราะ React ไม่ได้จำอะไรให้เองเลยถ้าคุณไม่สั่ง · ตัวเลือกที่ 4 ผิด — ผมรัน npx next build แล้วผ่านเงียบ ๆ ไม่มีใครเตือนสักคำ นี่แหละคือเหตุผลที่โค้ดแบบนี้อยู่รอดในโปรเจกต์จริงได้นานเป็นปี
จุดที่ต้องจำ: useCallback ที่ไม่มี React.memo รออยู่ปลายทาง คือโค้ดที่ไม่ทำอะไรเลย

3. const bad = useMemo(() => a + b, [a]); โดยเริ่มที่ a=1 b=1 · กด b +1 สองครั้ง (จน b=3) แล้วกด a +1 หนึ่งครั้ง · bad จะเป็นเท่าไหร่ในแต่ละจังหวะ?

ตอบตัวเลือกที่ 1 · ค่าที่อ่านจากหน้าเว็บจริงคือ bad=2 → bad=2 → bad=2 → bad=5
ตอน a เปลี่ยน React ถึงเรียกฟังก์ชันคำนวณใหม่ แล้วมันไปหยิบ b ตัวล่าสุด (3) มาบวก จึงได้ 2 + 3 = 5 ทันที โดยไม่เคยผ่าน 3 กับ 4 เลย

ตัวเลือกที่ 2 ผิดเพราะนั่นคือพฤติกรรมของ good ที่ใส่ [a, b] ครบ — ถ้า bad เดินตามนั้นได้ก็แปลว่า dependency array ไม่มีความหมายอะไรเลย · ตัวเลือกที่ 3 ผิดตรงที่มันไม่ได้ "ล็อกถาวร" — พอ [a] ขยับเมื่อไหร่ก็คำนวณใหม่ทันที · ตัวเลือกที่ 4 ผิด — ไม่มี error ตอนรันเลย มีแค่ warning ของ eslint (react-hooks/exhaustive-deps) และ npx next build ก็ยังผ่าน
จุดที่ต้องจำ: dependency ขาดไม่ได้ทำให้โปรแกรมพัง แต่ทำให้ตัวเลขผิดเงียบ ๆ แล้วเด้งกลับมาถูกเองตอนที่ dependency ตัวอื่นขยับ

4. ไฟล์ app/page.tsx ที่ไม่มี 'use client' แล้วเรียก useMemo อย่างเดียว (ไม่มี useState) — เกิดอะไรขึ้นตอนเปิดหน้านั้น?

ตอบตัวเลือกที่ 4 · ผมรันแล้วได้ HTTP 200 · หน้าแสดง total = 2 ปกติ และ npx next build ยังทำเป็นหน้า static (○) ให้ด้วยซ้ำ
เพราะ build ฝั่ง server ของ React 19.2.8 มี useMemo · useCallback · useId อยู่ในรายการ export จริง (ผมเปิดดูมาให้แล้วในหัวข้อ 8) — ที่ไม่มีคือ useState กับ useEffect

แต่ ไม่มีประโยชน์ เพราะ Server Component วาดครั้งเดียวต่อ request ไม่มีรอบถัดไปให้จำ · ตัวเลือกที่ 1 ผิดเพราะเหมารวมว่า "hook ทุกตัว" · ตัวเลือกที่ 2 ผิด — Next ไม่เคยเติม directive ให้ใครทั้งนั้น · ตัวเลือกที่ 3 ผิดเพราะ build ผ่านฉลุย · ตัวที่พังคือ useState เท่านั้น และ error ก็ชี้ลูกศรไปที่คำว่า useState ตรง ๆ
จุดที่ต้องจำ: เส้นแบ่ง server/client ไม่ได้ขีดที่คำว่า "hook" แต่ขีดที่ "ต้องจำอะไรข้ามการวาดไหม" — useState ต้อง ส่วน useMemo ไม่ต้อง

💬 ติดตรงไหนถามได้ — ถ้ารันตามในบทแล้วได้ผลไม่ตรงกับที่เขียนไว้ ให้ส่งมาสามอย่าง: โค้ดที่รัน · คำสั่งที่ใช้ · และ console ทั้งก้อน (อย่าตัดให้เหลือบรรทัดเดียว — ลำดับของ log คือเบาะแสหลัก)
และคำถามที่คุ้มที่สุดที่ถามได้กับบทนี้คือ "ตรงนี้ควรใส่ useMemo หรือควรย้าย state ลงไปให้ลึกกว่านี้แทน" — เพราะคำตอบที่ถูกบ่อยที่สุดคือ "ย้าย state" ไม่ใช่ "ใส่ memo"
