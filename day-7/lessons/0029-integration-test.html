จุดที่คนสับสนบ่อยคือคิดว่า integration test = "เทสที่ช้า" ซึ่งไม่ใช่นิยามของมัน นิยามคือ "เทสที่ไม่ mock รอยต่อ"
บทที่ 28 คุณ mock UserRepository เพื่อเทส service — รอยต่อ service ↔ repository ถูกปิดด้วยของปลอม บทนี้เราจะเปิดมันออก แล้วให้ repository คุยกับ PostgreSQL ตัวจริง

ไม่แพงสุด ไม่ถูกสุด — นี่คือเหตุผลที่มันอยู่ชั้นกลาง
ตัวเลขจริงจากเครื่องผม (อยู่ในหัวข้อ 8): unit test ที่ mock ไว้ทำงานใน 1.251ms ส่วน integration test ต้องรอ container ขึ้นก่อน ~1.03s — ต่างกันประมาณ 820 เท่า
ราคานี้ทำให้จ่ายครั้งเดียวได้ — แต่ยังไม่ใช่ในบทนี้ บทนี้เราจะเปิด container ใหม่ทุกเทสก่อน เพื่อให้เห็นราคาเต็ม ๆ ด้วยตาตัวเอง (หัวข้อ 8) ส่วนวิธีแชร์ container ตัวเดียวให้ทั้ง package จนเหลือจ่ายครั้งเดียว เป็นของบทเรียน 30

2 · หัวใจของบทนี้ — mock ที่ผ่านฉลุยทั้งที่ SQL ผิด

สมมติคุณเขียน method นี้ต่อจาก repository ในบทเรียน 27 โดยลืมไปว่าตาราง users ของคุณไม่มี column ชื่อ city: 

// internal/repository/user_repository.go
func (r *UserRepository) SearchByCity(ctx context.Context, city string) ([]model.User, error) {
    var users []model.User
    err := r.db.WithContext(ctx).
        Raw("SELECT * FROM users WHERE city = ?", city).
        Scan(&users).Error
    if err != nil {
        return nil, err
    }
    return users, nil
}

ก่อนไปต่อ ขอแนะนำเครื่องมืออีกตัวก่อน — go-sqlmock
บท 28 คุณใช้ mockery ปลอม interface ของ repository (ชั้นบนของ repository) แต่คราวนี้เราอยากดูว่า repository ตัวจริงที่ยิง SQL ออกไปนั้นถูกหรือผิด จึงต้องปลอมตัว database เอง ที่อยู่ใต้ repository
นั่นคือหน้าที่ของ go-sqlmock: มันสร้าง *sql.DB ปลอมขึ้นมารอรับ SQL ที่โค้ดของเรายิงออกไป แล้วเอาไปเทียบกับ regex ที่เราเขียนดักไว้ (regex = รูปแบบข้อความที่บอกว่า "ข้อความหน้าตาแบบไหนถือว่าตรง" เช่น .* แปลว่าอะไรก็ได้)
ถ้าตรงกับที่ดักไว้ มันก็คืนแถวข้อมูลที่เราเป็นคนป้อนให้มันเอง 

# ติดตั้งเพิ่ม 1 บรรทัด
go get github.com/DATA-DOG/go-sqlmock
// setup: เอา *sql.DB ปลอม ยัดเข้า GORM แทน postgres จริง
sqlDB, mock, err := sqlmock.New()
require.NoError(t, err)
defer sqlDB.Close()

gdb, err := gorm.Open(postgres.New(postgres.Config{Conn: sqlDB}), &gorm.Config{})
require.NoError(t, err)
repo := repository.NewUserRepository(gdb)   // repository ตัวเดิมจากบท 27
// unit test ด้วย go-sqlmock — mock database ทั้งตัว
rows := sqlmock.NewRows([]string{"id", "name", "email", "age", "created_at"}).
    AddRow(7, "Ploy", "ploy@example.com", 28, time.Now())

mock.ExpectQuery(`SELECT \* FROM users WHERE city = .*`).WillReturnRows(rows)

users, err := repo.SearchByCity(context.Background(), "Bangkok")
t.Logf("MOCK RESULT: len=%d first=%s", len(users), users[0].Name)

ตาราง users ไม่มี column city จริง ๆ — go test ตัวนี้ PASS หรือ FAIL?

PASS — และผ่านแบบไม่มีคำเตือนอะไรเลย:

    unitmock_test.go:73: => mocked unit test is GREEN even though column `city` does not exist

go-sqlmock จับคู่ SQL ด้วย regex แล้วคืน rows ที่เราป้อนให้ มันไม่มี SQL parser และไม่รู้จัก schema ของคุณเลยแม้แต่นิดเดียว
คุณเขียน regex ว่า SELECT \* FROM users WHERE city = .* มันก็แค่ match แล้วคืนของที่คุณเตรียมไว้ — คุณกำลังเทสว่า "regex ที่ผมเขียน ตรงกับ string ที่ผมเขียน"

ทีนี้เอา ฟังก์ชันตัวเดียวกันเป๊ะ ไปยิง PostgreSQL ของจริง
ระวังอ่านผิด: เทสตัวล่างก็ขึ้น PASS เหมือนกัน แต่คนละความหมายกัน — ตัวล่างผมเขียนว่า require.Error(t, err) คือ คาดหวังว่าต้องได้ error มันจึง PASS ก็ต่อเมื่อ postgres ด่ากลับมาจริง
สรุปสั้น ๆ: mock PASS = บั๊กหลุด · postgres จริง PASS = จับบั๊กได้ 

=== RUN   TestSearchByCity_CaughtByRealPostgres

--- PASS: TestSearchByCity_CaughtByRealPostgres (1.07s)

❌ สิ่งที่ mock ตรวจได้

"logic ของเราเรียกถูกไหม" — เรียกกี่ครั้ง · ส่ง argument อะไร · แปลงผลลัพธ์ถูกไหม · จัดการ error ที่คืนมาถูกไหม
ทั้งหมดนี้อยู่ในหัวของเราฝ่ายเดียว

✅ สิ่งที่มีแต่ DB จริงตรวจได้

"SQL ใช้ได้กับ schema จริงไหม" — column มีอยู่จริงไหม · ตารางชื่อถูกไหม · constraint ทำงานไหม · type ตรงไหม · migration ครบไหม
ทั้งหมดนี้เป็นสัญญากับระบบอื่น

🍜 เทียบให้เห็นภาพ — ซ้อมสั่งอาหารกับเพื่อน แล้วค่อยไปสั่งที่ร้านจริง

สมมติคุณจะไปสั่งอาหารร้านหนึ่ง แล้วอยากซ้อมก่อน จึงชวนเพื่อนมาเล่นเป็นพนักงาน
แต่เมนูที่เพื่อนถืออยู่ คือเมนูที่คุณเขียนขึ้นเองเมื่อกี้ และคุณบอกบทเพื่อนไว้ด้วยว่า “ถ้าฉันสั่งข้าวผัดปู ให้ตอบว่ามีนะ”
คุณสั่ง เพื่อนตอบว่า “มีครับ” แล้วยกจานสมมติมาให้ — ซ้อมผ่านฉลุย ทั้งที่ร้านจริงไม่เคยมีเมนูนี้อยู่เลย

พอไปที่ร้านจริง พนักงานเปิดเมนูจริงแล้วบอกว่า “เมนูนี้ไม่มีค่ะ” — จบ รู้ทันที
· ซ้อมกับเพื่อน = เทสที่ mock ตัว database ไว้ (go-sqlmock)
· ไปสั่งที่ร้านจริง = เทสที่ยิง PostgreSQL ตัวจริง
· ประโยค column "city" does not exist ก็คือ “เมนูนี้ไม่มีค่ะ” นั่นเอง

ที่ไม่เหมือนกัน: เพื่อนคุณยังพอรู้ว่าร้านนั้นขายอะไรอยู่บ้าง แต่ go-sqlmock ไม่รู้จักตารางของคุณเลยสักนิด — มันเทียบแค่ข้อความ SQL กับ regex ที่คุณเขียนเอง อย่าเผลอคิดว่ามัน “พอจะเช็ค SQL ให้ได้บ้าง” เพราะมันเช็คไม่ได้เลยจริง ๆ
ส่วนการซ้อมก็ไม่ใช่เรื่องเสียเปล่า มันยังตรวจได้ว่าคุณสั่งครบไหม นับจานถูกไหม ทอนเงินถูกไหม ซึ่งเป็นเรื่องของฝั่งคุณล้วน ๆ
และร้านจริงต้องรอคิว (~1.03s เทียบกับ 1.251ms ตอนซ้อม) คุณจึงซ้อมเป็นร้อยรอบได้ แต่เดินเข้าร้านจริงเป็นร้อยรอบไม่ไหว

ใช้ทั้งคู่ คนละหน้าที่: mock สำหรับ business logic (1.25ms ต่อเทส เอาไปวนหลายร้อยเคสได้) · container สำหรับ SQL/schema/constraint
กฎง่าย ๆ: ทุกอย่างที่เป็น "สัญญากับ database" ต้องมี integration test — column, ตาราง, constraint, type, migration

🗣 ศัพท์ที่เพิ่งเรียนไป

คำพวกนี้คือชื่อที่วงการใช้เรียกสิ่งที่คุณเพิ่งเข้าใจไป — ใช้คำให้ตรง แล้วคำตอบจาก senior หรือจาก AI จะตรงตาม

unit test
เทส “ชิ้นเดียว” — ของรอบข้างปลอมหมด = การซ้อมกับเพื่อน · เวลาคุยให้พูดว่า “ตัวนี้เป็น unit test นะ repository ถูก mock ไว้” อีกฝ่ายจะรู้ทันทีว่าเทสนี้ไม่ได้แตะ database
integration test
เทส “รอยต่อ” ระหว่างโค้ดเรากับของจริงอีกระบบหนึ่ง = การไปสั่งที่ร้านจริง
นิยามของมันคือ “ไม่ mock รอยต่อ” ไม่ใช่ “เทสที่ช้า” — ที่ช้าเป็นแค่ผลพลอยได้
mock
ของปลอมที่เราเขียนบทให้มันตอบ และตรวจด้วยว่าถูกเรียกตามบทหรือเปล่า (นั่นคือหน้าที่ของ ExpectQuery ข้างบน) · ถ้าแค่คืนค่าที่เตรียมไว้เฉย ๆ ไม่ตรวจการเรียก วงการเรียกว่า stub
go-sqlmock คือ mock ของ ตัว database ส่วน mockery ในบท 28 คือ mock ของ interface
เวลาถามให้ระบุชั้นให้ชัด: “เทสนี้ mock ที่ชั้นไหน — interface หรือ database”
schema
“แปลนของฐานข้อมูล” — ว่ามีตารางอะไร แต่ละตารางมี column ชื่ออะไร ชนิดไหน
mock ไม่รู้จัก schema ของคุณเลย ฐานข้อมูลจริงเท่านั้นที่รู้
constraint
“กฎที่ database บังคับไว้เอง” เช่น ห้าม email ซ้ำ — ในบทนี้คือ unique index ที่ AutoMigrate สร้างจาก tag gorm:"uniqueIndex"
(ฝั่ง postgres ตัว unique index กับ unique constraint เป็นคนละของกันในทางเทคนิค แต่บังคับกฎเหมือนกัน และข้อความ error ก็ขึ้นว่า violates unique constraint เหมือนกัน) · โค้ดฝั่งเราลืมเช็คได้ แต่ database ไม่ลืม
migration
ขั้นตอนแก้โครงตารางให้ตรงกับโค้ดรุ่นใหม่ (เพิ่ม column, สร้างตาราง) · ประโยคที่ได้ยินบ่อยคือ “ลืมรัน migration” = โค้ดใหม่แล้ว แต่ตารางยังเป็นของเก่า
SQLSTATE
รหัส error 5 ตัวอักษรมาตรฐานของ SQL เช่น 42703 · เวลาไปถามใครให้ยกรหัสไปด้วย: “เจอ SQLSTATE 42703 ตอน query users” จะสื่อกว่าพูดว่า “DB error”

3 · nil slice ที่คืนจากหลังบ้าน — [] หรือ null

คำถามคลาสสิก: repository ที่ query แล้วไม่เจอแถวเลย คืนอะไรออกมา แล้วพอ json.Marshal ต่อ frontend ได้อะไร
คำตอบไม่ใช่ขาวดำ — ขึ้นกับว่าคุณใช้ทางไหนอ่านข้อมูล ผมรันทั้ง 5 กรณีบน postgres จริง: 

// 1. GORM Find เข้า nil slice
var a []model.User
db.WithContext(ctx).Where("age >= ?", 18).Find(&a)

// 2. GORM Find เข้า make([]T,0)
b := make([]model.User, 0)
db.WithContext(ctx).Where("age >= ?", 18).Find(&b)

// 3. GORM Raw + Scan เข้า nil slice
var c []model.User
db.WithContext(ctx).Raw("SELECT * FROM users WHERE age >= ?", 18).Scan(&c)

// 4. database/sql เขียน loop เอง
var users []model.User   // nil slice
for rows.Next() { ... users = append(users, u) }

อ่านตารางนี้ยังไง
len(s) == 0 ตรวจไม่ได้ว่า slice เป็น nil หรือเปล่า — nil slice กับ empty slice มี len เท่ากันคือ 0 ต่างกันที่ s == nil และต่างกันที่ encoding/json มองคนละอย่าง
ที่น่าสนใจคือ GORM Find ไม่คืน nil เลย ต่อให้คุณส่ง var users []T ที่เป็น nil เข้าไป — มัน reflect (ส่องดูโครงสร้างตัวแปรตอนโปรแกรมกำลังรัน) แล้ว allocate (จองที่ในหน่วยความจำ) slice ให้เอง ปัญหา null จึงไม่เกิดบนเส้นทางนี้
ปัญหาเกิดจริงกับ Raw().Scan() และ repository ที่เขียน rows.Next() เอง — ซึ่งเป็นสองทางที่คุณจะใช้เมื่อ query ซับซ้อนเกิน GORM

🧺 เทียบให้เห็นภาพ — ตะกร้าเปล่า กับ ไม่ได้หยิบตะกร้ามาเลย

คุณเดินออกจากซูเปอร์มาแบบไม่ได้ซื้ออะไรเลย ซึ่งเป็นไปได้ 2 แบบ:
· ถือตะกร้าเปล่ามา — มีตะกร้าอยู่ แต่ในนั้นไม่มีของ
· ไม่ได้หยิบตะกร้ามาเลย — ไม่มีแม้แต่ตะกร้า
ถ้านับจำนวนของ ทั้งสองแบบได้ 0 ชิ้น เท่ากันเป๊ะ — นี่คือเหตุผลที่ len(s) == 0 แยกสองกรณีนี้ไม่ออก

แต่พอต้องบอกคนอื่นว่าเป็นยังไง มันคนละประโยคกันชัดเจน
· ตะกร้าเปล่า → JSON ออกมาเป็น [] (มีลิสต์อยู่ แค่ยังไม่มีของในลิสต์)
· ไม่มีตะกร้า → JSON ออกมาเป็น null (ไม่มีลิสต์เลย)
ฝั่ง frontend ที่เตรียมโค้ดไว้วนลูปในลิสต์ พอเจอ null ก็จะพัง เพราะมันไม่มีอะไรให้วน

ที่ไม่เหมือนกัน: ในชีวิตจริง ไม่มีตะกร้าก็ใส่ของไม่ได้ — แต่ใน Go nil slice ยัง append ใส่ของได้ตามปกติ ไม่ต้อง make ก่อนก็ได้ ไม่พังแน่นอน
ความต่างของสองแบบนี้มีผลจริง 3 ที่: ตอนเช็ค s == nil · ตอนแปลงเป็น JSON · และตอนเทียบใน test — reflect.DeepEqual (ตัวที่ require.Equal ในบท 17 ใช้ข้างใน) มองว่า nil slice กับ empty slice ไม่เท่ากัน ทั้งที่ len เท่ากันและหน้าตาเหมือนกัน — require.Equal(t, []model.User{}, users) จะ FAIL ถ้า users เป็น nil slice

วิธีแก้เหมือนกันทั้งสองกรณี คือประกาศด้วย users := make([]model.User, 0) แทน var users []model.User แล้ว append ต่อ — append ทำงานกับ empty slice ได้ปกติ ผลคือ frontend ได้ [] เสมอ ไม่ต้องเขียน if (data === null) ทุกหน้า

⚠️ นี่คือเหตุผลว่าทำไมเรื่องนี้ต้องอยู่ในบท integration test
ถ้าคุณ mock ไว้ คุณเลือกเองว่าจะให้ mock คืน nil หรือ empty slice — เทสจึงยืนยันแค่สิ่งที่คุณสมมติไว้ ไม่ได้ยืนยันว่า GORM ทำอะไรจริง
คำตอบข้างบนทุกบรรทัดมาจากการรันกับ postgres จริง

🗣 ศัพท์ที่เพิ่งเรียนไป
nil slice
“ไม่มีตะกร้า” — slice ที่ประกาศด้วย var users []User เฉย ๆ ยังไม่มีตัวลิสต์จริง ๆ
เวลาถามให้พูดว่า “ตรงนี้เป็น nil slice หรือ empty slice” จะสื่อกว่าถามว่า “ทำไมมันว่าง”

บรรทัดนี้แหละคือความต่างระหว่าง "เทสผ่าน" กับ "เทสผ่านบ้างไม่ผ่านบ้าง" ผมเปิด source ของ v0.44.0 มาดูว่ามันทำอะไร: 

func BasicWaitStrategies() testcontainers.CustomizeRequestOption {
	return testcontainers.WithAdditionalWaitStrategy(
		// First, we wait for the container to log readiness twice.
		// This is because it will restart itself after the first startup.
		wait.ForLog("database system is ready to accept connections").WithOccurrence(2),
		// Then, we wait for docker to actually serve the port on localhost.
		// For non-linux OSes like Mac and Windows, Docker or Rancher Desktop will have to start a separate proxy.
		// Without this, the tests will be flaky on those OSes!
		wait.ForListeningPort("5432/tcp"),
	)
}

error 2 บรรทัดข้างบนคืออาการ 2 แบบนี้ แต่ต้องอ่านให้ครบทั้งคู่ก่อนสรุป เพราะ localhost มีได้หลายที่อยู่ และ pgx ไล่ลองทีละอัน:
· [::1] (ฝั่ง IPv6) ได้ connection refused = ไม่มีใครฟังอยู่ตรงนั้นจริง ๆ — ที่อยู่ IPv6 ของ Docker บน macOS/Windows มักต่อไม่ติดแบบนี้อยู่แล้ว ต่อให้ container พร้อมสนิทแล้วก็ตาม
· 127.0.0.1 (ฝั่ง IPv4) ได้ unexpected EOF = ต่อติดแล้ว แต่ถูกตัดสายกลางคัน — บรรทัดนี้ต่างหากคือปัญหาจริง แปลว่ามีของอยู่จริง แต่คุณไปเร็วเกินไป
สังเกตว่า port เป็น 32800 เหมือนกันทั้งสองบรรทัด — ไม่ใช่ “กดเบอร์ผิด” และไม่ใช่ container ยังไม่ขึ้น ทั้งสองบรรทัดจึงหายไปพร้อมกันด้วยการแก้ทางเดียวกัน คือ “รอให้พร้อมก่อน” (พอฝั่ง IPv4 ต่อติด pgx ก็ใช้อันนั้นต่อได้เลย ไม่ฟ้องอะไรออกมาอีก)

ที่ไม่เหมือนกัน: คนวางสายเพราะไม่อยากคุย แต่ postgres ตัดสายเพราะมันปิดตัวเองเพื่อเปิดใหม่หลังเตรียมฐานข้อมูลเสร็จ ซึ่งเป็นขั้นตอนปกติของมัน ไม่ใช่การปฏิเสธและไม่ใช่ความผิดพลาด

connection refused / unexpected EOF

เวลาเจอทั้งคู่พร้อมกันจาก localhost ให้ดู port ก่อน — ถ้าเลข port เท่ากัน แปลว่าไม่ได้ต่อผิดที่
DSN / mapped port
DSN = ที่อยู่เต็ม ๆ ของ database ในบรรทัดเดียว · mapped port = port บนเครื่องคุณที่ Docker จับคู่ให้กับ port ในตัว container
ประโยคที่ใช้ได้จริง: “เอา DSN จาก ConnectionString() นะ อย่า hardcode port”

ทดสอบความเข้าใจ

1. unit test ที่ mock ด้วย go-sqlmock ตรวจอะไรไม่ได้?

go-sqlmock จับคู่ SQL ด้วย regex แล้วคืน rows ที่เราป้อนให้ — ไม่มี parser ไม่รู้จัก schema
ผมรันฟังก์ชันที่ query WHERE city = ? ทั้งที่ตารางไม่มี column นี้: mock บอก len=1 first=Ploy PASS ส่วน postgres จริงบอก ERROR: column "city" does not exist (SQLSTATE 42703)
อีกสามข้อ mock ตรวจได้หมด เพราะเป็นเรื่องของ logic ฝั่งเราล้วน ๆ ไม่ใช่สัญญากับ database

2. GORM Find() เข้า var users []User แล้วไม่เจอแถวเลย JSON ออกมาเป็นอะไร?

ผลจริงจาก container: GORM Find, var []T, 0 rows → len=0 isNil=false json=[] และ make([]T,0) ก็ได้เหมือนกันเป๊ะ — GORM reflect แล้ว allocate ให้ ไม่ว่าคุณส่งอะไรเข้าไป
ตัวเลือกที่ 3 ("[] เพราะ encoding/json แปลง nil slice เป็น array ว่าง") เดาคำตอบถูกแต่เหตุผลผิด — encoding/json แปลง nil slice เป็น null ต่างหาก พิสูจน์ได้จากบรรทัด GORM Raw+Scan → isNil=true json=null ในหัวข้อ 3
ตัวเลือกที่ 1 และ 2 ผิดทั้งคู่เพราะเชื่อว่า slice ยังเป็น nil อยู่หลัง Find — ผลจริงบอกว่า isNil=false ทั้งกรณี var และ make ตัวเลือกที่ 2 ยังผิดซ้ำตรงที่คิดว่าวิธีประกาศตัวแปรเป็นตัวชี้ขาด ทั้งที่ตัวชี้ขาดจริงคือทางที่ใช้อ่าน (Find เทียบกับ Raw().Scan())
ปัญหา null จึงเกิดเฉพาะกับ Raw().Scan() และ database/sql ที่เขียน rows.Next() เอง

3. ทำไม BasicWaitStrategies() ถึงรอ log บรรทัดเดิม 2 ครั้ง?

คอมเมนต์ใน source ของ v0.44.0 เขียนไว้ตรง ๆ: "we wait for the container to log readiness twice. This is because it will restart itself after the first startup."
log ครั้งแรกออกตอน initdb เสร็จ ตอนนั้น postgres ยังฟังแค่ unix socket ยังไม่เปิด TCP แล้วมันก็ shutdown แล้ว start ใหม่
ถ้ารอครั้งเดียวแล้วรีบต่อ จะได้ unexpected EOF ใน ~3.6ms
ส่วนเงื่อนไขที่สอง (ForListeningPort) ต่างหากที่แก้เรื่อง docker proxy บน macOS/Windows

4. เขียน DSN ด้วย port 5432 ตายตัว อันตรายที่สุดตรงไหน?

ถ้าไม่มีอะไรฟังที่ 5432 คุณจะได้ connection refused ทั้ง [::1] และ 127.0.0.1 — เทสแดง ซึ่งยังโชคดี
กรณีเลวร้ายคือเครื่อง dev มี postgres ของตัวเองรันอยู่ที่ 5432: เทสผ่าน แต่ไป AutoMigrate และ TRUNCATE ทับ database ที่คุณใช้ทำงานจริง
ผมเห็น port ที่ถูกสุ่มมา 15 ค่า (32769 – 32812) ไม่ซ้ำเลย — ใช้ ConnectionString() หรือ MappedPort() เสมอ
