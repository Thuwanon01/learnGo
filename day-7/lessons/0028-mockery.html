บทเรียน 28 · Day 7 · Mockery

Mockery — เลิกเขียน mock ด้วยมือ

~17 นาที · ต้องมี: บทเรียน 10 (interface), บทเรียน 17 (testify), บทเรียน 27 (layout + repository)

ตั้งแต่บทเรียน 15 มา คุณจ่ายค่าผ่านทางเดิมทุกครั้งที่อยากเทส service: ประกาศ interface · รับ dependency ทางพารามิเตอร์ · แล้วนั่งเขียน struct ปลอมขึ้นมาเอง
บทนี้เอาขั้นที่สามออก — แต่ไม่ใช่เพราะ "ประหยัดบรรทัด" อย่างที่มักเคลมกัน ตัวเลขจริงบอกตรงข้าม และเหตุผลที่แท้จริงดีกว่านั้นเยอะ

1 · ทบทวน: ราคาที่เราจ่ายมาตลอดบท 15–17

สูตรที่ใช้มาตั้งแต่ บทเรียน 15 จนถึง บทเรียน 17 มีสามชิ้นเสมอ: 

  1) interface            2) DI                  3) mock เขียนมือ

  type UserRepository    func NewService(         type FakeUserRepository struct {
      interface {            repo UserRepository      GetByIDFunc  func(...) ...
      GetByID(...)       ) *Service {                 GetByIDCalls []int
      Save(...)              ...                      ...
      CountActive()      }                        }
  }                                               func (f *Fake) GetByID(...) {...}
       ▲                        ▲                 func (f *Fake) Save(...)    {...}
       │                        │                 func (f *Fake) CountActive(){...}
  โค้ดจริงพึ่งพา            เทสยัดของปลอม                     ▲
  "สัญญา" ไม่ใช่ตัวจริง        เข้ามาแทนได้         ชิ้นนี้เราพิมพ์เองทุกตัวอักษร

ชิ้นที่ 1 กับ 2 เป็นการออกแบบ — เราได้ประโยชน์จากมันตรง ๆ (บทเรียน 10)
ชิ้นที่ 3 ไม่ใช่การออกแบบ มันคืองานถอดแบบ — อ่าน interface แล้วพิมพ์ struct ที่มี method ชื่อเดียวกัน signature เดียวกัน ครบทุกตัว ถ้าพิมพ์ตกไปตัวหนึ่ง compiler ก็ฟ้องว่าไม่ implement interface

นี่คือ mock เขียนมือของ interface ที่มีแค่ 3 method:

// mock เขียนมือ: struct + field เก็บค่า return + field เก็บ arg ที่ถูกเรียก
type FakeUserRepository struct {
    GetByIDFunc     func(id int) (*User, error)
    GetByIDCalls    []int
    SaveFunc        func(u *User) error
    SaveCalls       []*User
    CountActiveFunc func() int
    CountActiveHits int
}

func (f *FakeUserRepository) GetByID(id int) (*User, error) {
    f.GetByIDCalls = append(f.GetByIDCalls, id)
    if f.GetByIDFunc == nil {
        return nil, nil
    }
    return f.GetByIDFunc(id)
}

func (f *FakeUserRepository) Save(u *User) error {
    f.SaveCalls = append(f.SaveCalls, u)
    if f.SaveFunc == nil {
        return nil
    }
    return f.SaveFunc(u)
}

func (f *FakeUserRepository) CountActive() int {
    f.CountActiveHits++
    if f.CountActiveFunc == nil {
        return 0
    }
    return f.CountActiveFunc()
}

35 บรรทัด · 3 method · pattern เดียวกันเป๊ะทั้งสามอัน (บันทึก arg → เช็ค nil → เรียก func)
เพิ่ม method ที่ 4 ในวันหลัง = กลับมาพิมพ์ pattern เดิมอีกรอบ

2 · ความเจ็บปวดที่แท้จริงไม่ใช่ "เยอะ" แต่คือ "มันเงียบ"

ถ้าปัญหามีแค่ "พิมพ์เยอะ" มันก็แค่น่าเบื่อ ไม่ถึงกับอันตราย
แต่ mock เขียนมือมีรูโหว่ที่ใหญ่กว่านั้นมาก — ลองอ่านเทสข้างล่างนี้ก่อน 

// mock เขียนมือ: GetByIDFunc คืน user id 7 เสมอ
func TestManual_WrongArgSilentlyPasses(t *testing.T) {
    repo := &FakeUserRepository{
        GetByIDFunc: func(id int) (*User, error) {
            return &User{ID: 7, Name: "Somchai"}, nil
        },
    }
    svc := NewService(repo)
    got, err := svc.DisplayName(999) // ควรจะเรียกด้วย 7 แต่เรียก 999
    if err != nil {
        t.Fatal(err)
    }
    if got != "Mr. Somchai" {
        t.Fatalf("got %q", got)
    }
    // ไม่มี assert เรื่อง arg
}

โค้ดเรียก repository ด้วย id 999 ทั้งที่ตั้งใจจะเทส id 7 — เทสนี้ผ่านหรือตก?

ผ่านสบาย ๆ:

=== RUN   TestManual_WrongArgSilentlyPasses
--- PASS: TestManual_WrongArgSilentlyPasses (0.00s)
PASS
ok  	example.com/manual/user	0.435s

เพราะ GetByIDFunc คืนค่าเดิมไม่ว่าใครส่ง id อะไรมา mock เขียนมือไม่รู้จักคำว่า "คาดหวัง" มันรู้จักแค่ "คืนค่านี้"
ถ้าอยากให้จับได้ ต้องเขียน assert เรื่อง argument เองทุกครั้ง — นั่นคือเหตุผลที่ field GetByIDCalls []int ถึงมีอยู่ในโค้ดหัวข้อ 1 แต่มีไว้เฉย ๆ ไม่ได้แปลว่ามีคนใช้

นี่คือบั๊กที่ไม่มีใครเห็น — โค้ด production ส่ง id ผิด เทสยังเขียว CI ยังผ่าน
เก็บความรู้สึกนี้ไว้ แล้วไปดูหัวข้อ 8 ว่า mockery เจอกรณีเดียวกันแล้วทำอะไร

⚠️ รูโหว่ที่สองคือชื่อ method ที่เป็น string — testify แบบดั้งเดิมตั้ง expectation ด้วย mock.On("GetByID", 7) ซึ่งชื่อ method อยู่ในเครื่องหมายคำพูด compiler ไม่ได้ตรวจอะไรให้เลย พิมพ์ "GetById" (d เล็ก) ก็ยังคอมไพล์ผ่าน แล้วไปพังตอนรันเป็นข้อความยาว ๆ ที่มือใหม่อ่านไม่ออก

7 · รัน mockery แล้วรู้ได้ยังไงว่าสำเร็จ

คำตอบที่คนส่วนใหญ่ใช้คือ exit code — และมันใช้ไม่ได้กับเครื่องมือตัวนี้

❌ log แบบนี้ = ไม่ได้อะไรเลย

INF Starting mockery config-file=...
INF Parsing configured packages...
INF Done parsing configured packages.
EXITCODE=0

"Done" + exit 0 แต่ไม่มีไฟล์ mock เกิดขึ้นเลย

✅ log แบบนี้ = สำเร็จจริง

INF Parsing configured packages...
INF Done parsing configured packages.
INF adding interface to collection
    interface=UserRepository
INF Executing template file=.../mocks_test.go
INF Writing template to file file=.../mocks_test.go

บรรทัด adding interface to collection คือหลักฐานเดียว

⚠️ กับดักที่ร้ายที่สุดของบทนี้ — ผมทดลอง 3 แบบ: (ก) ชี้ที่ module root ที่ไม่มีไฟล์ .go (ข) ชี้ที่ example.com/shop/repository ที่ไม่มีอยู่จริง (ค) ชี้ที่ github.com/vektra/doesnotexist123 ที่ไม่มีในโลก

8 · mock ที่ได้ออกมา หน้าตาเป็นยังไง

ไฟล์ที่ generate มา 193 บรรทัด ขึ้นต้นด้วยบรรทัดที่บอกชัดว่าอย่าไปแก้: 

// Code generated by mockery; DO NOT EDIT.
// github.com/vektra/mockery
// template: testify

package user

import (
    mock "github.com/stretchr/testify/mock"
)

// NewMockUserRepository creates a new instance of MockUserRepository. It also
// registers a testing interface on the mock and a cleanup function to assert
// the mocks expectations.
func NewMockUserRepository(t interface {
    mock.TestingT
    Cleanup(func())
}) *MockUserRepository {
    mock := &MockUserRepository{}
    mock.Mock.Test(t)

    t.Cleanup(func() { mock.AssertExpectations(t) })

    return mock
}

type MockUserRepository struct {
    mock.Mock
}
✅ ของฟรีชิ้นที่ 1 — ไม่ต้องเขียน AssertExpectations เองแล้ว

บรรทัด t.Cleanup(func() { mock.AssertExpectations(t) }) อยู่ใน constructor
แปลว่าทุกเทสที่สร้าง mock ด้วย NewMockUserRepository(t) จะถูกตรวจให้อัตโนมัติตอนจบเทส ว่า expectation ที่ตั้งไว้ถูกเรียกครบไหม
ถ้าคุณเคยพิมพ์ defer repo.AssertExpectations(t) ตามสไตล์ v2 — ใน v3 เป็นการเรียกซ้ำโดยไม่จำเป็น
นี่คือ t.Cleanup ตัวเดียวกับที่คุณเจอใน บทเรียน 15

ถัดมาคือ method จริงที่ implement interface ให้:

func (_mock *MockUserRepository) GetByID(id int) (*User, error) {
    ret := _mock.Called(id)

    if len(ret) == 0 {
        panic("no return value specified for GetByID")
    }
    ...
}

และชั้น EXPECT() ที่เป็นพระเอกของ v3: 

func (_m *MockUserRepository) EXPECT() *MockUserRepository_Expecter {
    return &MockUserRepository_Expecter{mock: &_m.Mock}
}

// GetByID is a helper method to define mock.On call
//   - id int
func (_e *MockUserRepository_Expecter) GetByID(id any) *MockUserRepository_GetByID_Call {
    return &MockUserRepository_GetByID_Call{Call: _e.mock.On("GetByID", id)}
}

func (_c *MockUserRepository_GetByID_Call) Return(user *User, err error) *MockUserRepository_GetByID_Call {
    _c.Call.Return(user, err)
    return _c
}

func (_c *MockUserRepository_GetByID_Call) RunAndReturn(run func(id int) (*User, error)) *MockUserRepository_GetByID_Call {
    _c.Call.Return(run)
    return _c
}
✅ ของฟรีชิ้นที่ 2 — ชื่อ method กลับมาให้ compiler ตรวจ

ดูบรรทัดในสุด: _e.mock.On("GetByID", id)
EXPECT() คือ syntactic sugar ที่ห่อ mock.On("ชื่อ method", args...) เอาไว้ — string ยังอยู่ แต่ย้ายไปอยู่ในไฟล์ที่เครื่องสร้าง ไม่ใช่ไฟล์ที่คุณพิมพ์
ฝั่งที่คุณเขียนกลายเป็น repo.EXPECT().GetByID(7) ซึ่งเป็น method จริง → พิมพ์ชื่อผิดคือ compile error
ส่วน .Return(user *User, err error) เป็น type-safe เต็มตัว ใส่ประเภทผิดไม่ผ่านตั้งแต่ compile

ทำไม argument ของ EXPECT().GetByID(id any) ถึงเป็น any ไม่ใช่ int?
เพราะต้องเปิดช่องให้ส่ง mock.Anything และ mock.MatchedBy(...) เข้าไปได้ (บทเรียน 17) ซึ่งไม่ใช่ int
แลกกันตรงนี้: ยืดหยุ่นเรื่อง matcher แต่ไม่ได้ type-check ฝั่ง argument

📊 คุณค่าจริงที่วัดได้คือ assertion ที่ได้ฟรี

เทียบเคสเดียวกันตรง ๆ — โค้ดส่ง argument ผิด: 

mock เขียนมือ  →  --- PASS  (บั๊กหลุดออก production)
mockery       →  Diff: 0: FAIL:  (int=8) != (int=7)

เพราะ mock เขียนมือต้องเขียน assert เรื่อง argument เองทุกครั้ง (ต้องมี field GetByIDCalls []int + if เช็คอีกราว 4 บรรทัดต่อ method) ส่วน mockery ได้มาพร้อม EXPECT() และได้ AssertExpectations อัตโนมัติจาก t.Cleanup ใน constructor

เลือกยังไงแบบไม่โม้:
✅ ยิ่ง interface มี method เยอะ + ยิ่งต้อง assert argument ละเอียด mockery ยิ่งคุ้ม — ซึ่งคือ repository ทุกตัวที่คุณจะเขียนหลัง บทเรียน 27
⚖️ interface 1–2 method ที่แค่ stub ค่า return เฉย ๆ เขียนมือยังคุ้มกว่า เพราะไม่ต้องแบก config + toolchain + ขั้นตอน "อย่าลืมรัน mockery" ในทีม

ทดสอบความเข้าใจ

1. ใน mockery v3 คำสั่งที่ใช้ generate mock คืออะไร?

mockery --help แสดง subcommand ทั้งหมดแค่ 6 ตัว — completion · help · init · migrate · showconfig · version ไม่มี generate และไม่มี build
พิมพ์ตามนิสัย v2 จะได้ Error: unknown command "generate" for "mockery" exit 1
บรรทัด Usage: mockery [flags] คือคำตอบ: root command คือ ตัว generate
ส่วน init สร้างแค่ .mockery.yml ไม่ได้ generate mock ให้

2. รัน mockery แล้ว log จบที่ Done parsing configured packages. exit code 0 แต่ไม่มีไฟล์ mock — แปลว่าอะไร?

exit code ของ mockery v3.7.3 เชื่อไม่ได้ — ผมทดสอบ 3 แบบ (module root ที่ไม่มีไฟล์ .go · package ที่ไม่มีอยู่จริง · package ที่ไม่มีในโลก) ได้ exit 0 ทั้งสามกรณี ไม่ error สักอัน
หลักฐานเดียวที่เชื่อได้คือบรรทัด INF adding interface to collection ... interface=<ชื่อ>
สาเหตุที่พบบ่อยสุด: mockery init สร้าง config ชี้ module root มาให้ แต่ interface อยู่ใน sub-package → เติม recursive: true ใต้ packages.<module>.config

3. เทสตกด้วยบรรทัด Diff: 0: FAIL: (int=8) != (int=7) — อ่านว่าอะไร?

เลข 0 ข้างหน้าคือ index ของ argument (ตัวแรก)
ซ้ายคือค่าที่โค้ดส่งมาจริง ขวาคือค่าที่เราตั้งไว้ใน EXPECT()/On()
testify จับคู่ call ด้วยการเทียบ argument ทุกตัวแบบตรงเป๊ะ ไม่ตรง = mock: Unexpected Method Call แล้ว panic หยุดเทสทันที
ตัวเลือกเรื่องจำนวนครั้งผิด — กรณีนั้นข้อความจะเป็น The method has been called over 1 times. ซึ่งหน้าตาต่างกันชัดเจน

4. ทำไมเทสในหัวข้อ 9 ถึงไม่มี defer repo.AssertExpectations(t) เลยสักบรรทัด?

ใน NewMockUserRepository(t) ที่ generate ออกมามีบรรทัดนี้อยู่: t.Cleanup(func() { mock.AssertExpectations(t) })
เป็น t.Cleanup ตัวเดียวกับที่เรียนไปในบทเรียน 15 — ทำงานอัตโนมัติตอนเทสจบ ไม่ว่าจะจบแบบ pass หรือ fail
นี่คือความต่างสำคัญจาก v2 · ถ้ายังพิมพ์ defer AssertExpectations ตามนิสัยเดิม จะกลายเป็นเรียกซ้ำโดยไม่จำเป็น
และเพราะมันทำงานเสมอนี่เอง กับดัก "ตั้งแล้วไม่ถูกเรียก" ถึงฟ้องได้ ทั้งที่เราไม่ได้เขียน assert อะไรเลย

  10. ท้าทาย 2: เปลี่ยน filename เป็น mocks.go แล้วเขียนเทสใน package อื่นที่ใช้ mock ตัวนี้
    รันครั้งแรกจะเจอ redeclared in this block — รู้อยู่แล้วว่าทำไม แก้เลย
