Goose — เปลี่ยน schema แบบย้อนกลับได้

~18 นาที · ต้องมี: บทเรียน 27 (GORM + AutoMigrate)

ในบทเรียน 27 คุณใช้ db.AutoMigrate(&Product{}) แล้วตารางก็โผล่มาเอง — สะดวกมาก
บทนี้จะพาไปดูว่า ความสะดวกนั้นแลกมาด้วยอะไร ด้วยการทดลองจริง 5 แบบบน PostgreSQL แล้วค่อยมาดูว่า goose แก้เรื่องไหนให้บ้าง
จุดที่ต้องเข้าใจให้ได้ในบทนี้มีจุดเดียว: ตารางชื่อ goose_db_version เก็บอะไรไว้บ้าง เพราะทุกกับดักในบทนี้อธิบายได้จากตารางนั้นตารางเดียว

⚙️ เตรียมเครื่องก่อนเริ่ม — ทำให้ครบ 4 ข้อนี้ ไม่งั้นจะติดกลางทาง

1) ต้องมี Docker เปิดอยู่ + ต่อ internet ได้ (บทนี้ต้องโหลด image และ go install จาก network)

2) เปิด PostgreSQL ขึ้นมาหนึ่งตัว — บทนี้ผูก port 55433 ไว้ที่เครื่องเรา (ไม่ใช่ 5432 ตามปกติ) เพื่อไม่ให้ชนกับ Postgres ตัวอื่นที่อาจเปิดอยู่แล้ว

docker run -d --name pg-shop \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=shopdb \
  -p 55433:5432 \
  postgres:16

# เช็คว่าขึ้นแล้วจริง
docker exec -it pg-shop psql -U postgres -d shopdb -c 'SELECT 1;'

3) psql คืออะไร — เป็นโปรแกรม command line ของ PostgreSQL ไว้พิมพ์ SQL ใส่ DB ตรง ๆ บทนี้ใช้มันตรวจผลตลอด ถ้าเครื่องคุณยังไม่มี ไม่ต้องติดตั้ง ใช้ตัวที่อยู่ใน container ได้เลย โดยแทน psql ทุกที่ในบทนี้ด้วย:

docker exec -it pg-shop psql -U postgres -d shopdb

คำสั่งที่ขึ้นต้นด้วย backslash คือคำสั่งของ psql เอง ไม่ใช่ SQL: \dt = ดูรายชื่อตาราง · \d ชื่อตาราง = ดูโครงสร้างตาราง · \df = ดูรายชื่อ function · \q = ออก

4) หลัง go install ต้องพิมพ์ goose ได้ — ถ้าขึ้น command not found แปลว่า $GOPATH/bin ยังไม่อยู่ใน PATH ให้เพิ่มบรรทัดนี้ใน ~/.zshrc แล้วเปิด terminal ใหม่:

export PATH="$PATH:$(go env GOPATH)/bin"

1 · migration กับ seed ต่างกันตรงไหน

migrationseed
เปลี่ยนอะไรโครงสร้าง — ตาราง · คอลัมน์ · index · constraint · triggerข้อมูล — แถวที่อยู่ในตาราง
ตัวอย่าง SQLCREATE TABLE · ALTER TABLE · CREATE INDEXINSERT INTO
ต้องรันกี่ครั้งครั้งเดียวต่อ databaseแล้วแต่ว่าเป็นข้อมูลชนิดไหน

📘 3 คำนี้จะใช้ทั้งบท รู้จักกันก่อน (ใน AutoMigrate คุณไม่เคยเห็นเพราะ GORM ทำให้เงียบ ๆ)
index = สารบัญของตาราง สร้างไว้ให้ค้นหาคอลัมน์นั้นเร็วขึ้น เช่นสร้าง index บน name แล้ว WHERE name = 'Mouse' จะเร็วขึ้นมาก · ไม่เปลี่ยนข้อมูล เปลี่ยนแค่ความเร็ว
constraint = กฎที่ DB บังคับกับข้อมูล เช่น NOT NULL (ห้ามว่าง) · UNIQUE (ห้ามซ้ำ) · PRIMARY KEY ถ้าข้อมูลผิดกฎ DB จะปฏิเสธไม่ยอมบันทึกให้
trigger = โค้ดที่ DB สั่งรันเองอัตโนมัติทุกครั้งที่มีการ insert/update/delete แถว เช่นให้อัปเดตคอลัมน์ updated_at ให้เองโดยที่ Go ไม่ต้องสั่ง

แต่คำว่า "seed" ในโลกจริงหมายถึงสองอย่างที่ต่างกันคนละเรื่อง และนี่คือจุดที่คนสับสนที่สุด:

✅ master data — เป็น migration

ข้อมูลที่ระบบขาดไม่ได้ เช่น ตาราง categories ที่มี ELEC / BOOK / FOOD
ทุก environment ต้องมีเหมือนกันเป๊ะ · ต้องอยู่ใน git · ต้องรันครั้งเดียว
→ เขียนเป็นไฟล์ migration ปกติ

❌ ข้อมูลทดสอบ — ไม่ใช่ migration

user ปลอม 100 คน สินค้า mock สำหรับเล่นในเครื่องตัวเอง
ไม่ควรโผล่ไปที่ production เด็ดขาด และรันซ้ำได้ไม่จำกัด
→ แยกเป็นสคริปต์ต่างหาก อยู่นอก goose

💡 ประโยคที่ต้องจำ: "migration เปลี่ยน schema · seed ใส่ข้อมูล" ถูกแค่ครึ่งเดียว
ที่ถูกกว่าคือ migration = "การเปลี่ยนแปลงที่ต้องเกิดขึ้นครั้งเดียวและต้องเกิดเหมือนกันทุกเครื่อง" ไม่ว่าสิ่งที่เปลี่ยนจะเป็นโครงสร้างหรือข้อมูล
เดี๋ยวหัวข้อ 8 จะพิสูจน์ให้ดูว่า INSERT ธรรมดา ๆ ที่ไม่มีอะไรกันข้อมูลซ้ำเลย ก็รันซ้ำแล้วข้อมูลไม่ซ้ำ — เพราะอะไร
(ON CONFLICT DO NOTHING คือท่อนที่ต่อท้าย INSERT ของ Postgres แปลว่า "ถ้าแถวนี้ชนของเดิมอยู่แล้ว ก็ข้ามไปเงียบ ๆ อย่าเพิ่ง error" — เป็นวิธีมาตรฐานที่คนใช้กันข้อมูลซ้ำ แต่หัวข้อ 8 จะให้ดูว่าในโลกของ goose เราไม่ต้องใช้มันเลย)

2 · ทำไมห้าม migrate ด้วยมือ

"ก็แค่เข้า psql แล้วพิมพ์ ALTER TABLE เอง จะยากอะไร" — มันยากตรงสองข้อนี้: 

   1) DB ที่คุณกำลังจะแก้ มีข้อมูลของคนอื่นอยู่แล้ว

เครื่องมือ migration แก้สองข้อนี้ด้วยวิธีเดียวกัน: เปลี่ยนคำสั่ง SQL ให้กลายเป็น "ไฟล์ที่อยู่ใน git" แล้วให้ database จำเองว่ารันไฟล์ไหนไปแล้วบ้าง
พอเป็นไฟล์ ก็ได้ของแถมมาสองอย่าง: รีวิวได้ก่อน merge และ เขียนวิธีย้อนกลับติดไว้ในไฟล์เดียวกัน

3 · AutoMigrate ของบทเรียน 27 ทำอะไรไม่ได้บ้าง

ก่อนจะไปที่ goose ต้องตอบให้ได้ก่อนว่า ทำไมของที่มีอยู่แล้วถึงไม่พอ
ผมเปิด PostgreSQL 16 ขึ้นมาหนึ่งตัว แล้วรัน AutoMigrate จริง 5 รอบ รอบละ struct ที่ต่างกันนิดเดียว 

// step1 — รันครั้งแรก สร้างตาราง แล้ว insert Keyboard 1200 กับ Mouse 590
type Product struct {
    ID    uint   `gorm:"primaryKey"`
    Name  string `gorm:"not null"`
    Price float64
}

// step2 — เปลี่ยนชื่อ field จาก Price เป็น Cost แล้วรัน AutoMigrate อีกที
type Product struct {
    ID    uint   `gorm:"primaryKey"`
    Name  string `gorm:"not null"`
    Cost  float64
    Stock int
}

db.AutoMigrate(&Product{})

หลังรัน step2 — ตาราง products มีคอลัมน์อะไรบ้าง และราคา 1200 / 590 ไปอยู่ที่ไหน? 

AutoMigrate step2 OK

ได้คอลัมน์ cost ว่างเปล่ามาเพิ่ม ส่วน price ยังอยู่ที่เดิมพร้อมข้อมูลครบ
ไม่มี error ไม่มี warning — พิมพ์ OK ด้วยซ้ำ แต่โค้ดที่อ่าน Cost จะเห็นค่าว่างหมด

สาเหตุ: AutoMigrate เทียบ struct กับ schema แล้ว "เติมสิ่งที่ขาด" อย่างเดียว
มันไม่มีทางรู้ว่า cost คือ price ที่เปลี่ยนชื่อ หรือเป็นคอลัมน์ใหม่จริง ๆ — เพราะมันไม่มีประวัติให้ดู เห็นแค่ "ตอนนี้ DB เป็นแบบนี้ struct เป็นแบบนี้"

ผมไล่ทดลองต่อจนครบ นี่คือสิ่งที่ AutoMigrate ทำได้และทำไม่ได้ ทั้งหมดยืนยันด้วยการรันจริง:

สถานการณ์ผลจริง
สร้างตารางใหม่ · เพิ่ม field ใหม่✅ ทำให้ครบ
เปลี่ยน type ของคอลัมน์เดิม (int → string)✅ ทำได้จริง — เปลี่ยน Stock int เป็น Stock string ได้ stock | text · และถ้าใส่ tag gorm:"size:20" บน Name ก็ได้ name | character varying(20) (character varying(20) = ข้อความยาวไม่เกิน 20 ตัวอักษร)
เปลี่ยนชื่อ field❌ สร้างคอลัมน์ใหม่ ทิ้งของเก่าไว้ ข้อมูลไม่ตามมา
ลบ field ออกจาก struct❌ คอลัมน์ยังอยู่ตลอดไป — เอกสาร GORM ระบุเองว่าจะไม่ลบคอลัมน์ที่ไม่ได้ใช้
เพิ่ม gorm:"not null" บนคอลัมน์เดิม❌ พิมพ์ OK · exit 0 · แต่ไม่ทำอะไรเลย — Nullable ยังว่าง
มี version table ให้รู้ว่า DB ไหนอยู่สถานะไหน❌ ไม่มีเลย — \dt เห็นแค่ products ตารางเดียว

⚠️ ข้อที่อันตรายที่สุดคือข้อ "เพิ่ม not null"
คุณเติม tag เข้าไป โค้ดคอมไพล์ผ่าน AutoMigrate บอก OK โค้ดฝั่ง Go จึงเชื่อว่า field นี้ไม่มีวันว่าง แต่ DB ยังรับ NULL ได้อยู่
ข้อมูลสกปรกไหลเข้าเงียบ ๆ แล้วไปโผล่เป็น nil pointer ตอนอ่านออกมาอีกทีหนึ่ง

และเมื่อ AutoMigrate ตัดสินใจผิด คุณไม่มีทางย้อน เพราะไม่มีที่ไหนบันทึกไว้ว่ามันทำอะไรไป ลองดูตอนที่มันเจอข้อมูลแปลงไม่ได้ (คอลัมน์ stock เป็น text แล้วมีคำว่า ten อยู่ พอเปลี่ยน struct กลับเป็น int): 

2026/08/18 19:54:58 /..../step5/main.go:20 ERROR: invalid input syntax for type bigint: "ten" (SQLSTATE 22P02)
[3.165ms] [rows:0] ALTER TABLE "products" ALTER COLUMN "stock" TYPE bigint USING "stock"::bigint
AutoMigrate ERROR: ERROR: invalid input syntax for type bigint: "ten" (SQLSTATE 22P02)

สังเกตบรรทัดกลาง — ALTER TABLE ... USING "stock"::bigint คือ SQL ที่ GORM แต่งขึ้นเองตอน runtime โดยไม่มีใครเคยเห็นมาก่อน
นี่คือความต่างที่แท้จริง: migration ของ goose คือ "สคริปต์ที่รีวิวได้ก่อน merge" ส่วน AutoMigrate คือ "SQL ลึกลับที่เกิดตอนแอป start"
แอปตัวนี้พังตอน boot บน production โดยที่ไม่มีใครเคยเห็น ALTER บรรทัดนั้นในโค้ดรีวิวเลยสักครั้ง

goose เป็น CLI แยกต่างหาก ไม่ใช่ library ที่ import เข้าโปรเจกต์ — binary ไปอยู่ที่ $GOPATH/bin เหมือนเครื่องมือ Go ตัวอื่น ๆ
ก่อนใช้ต้องบอกมันสามอย่าง: driver อะไร · ต่อ DB ไหน · ไฟล์อยู่โฟลเดอร์ไหน ซึ่งวิธีที่สบายที่สุดคือไฟล์ .env ที่ goose อ่านให้เองอัตโนมัติ

GOOSE_DRIVER=postgres
GOOSE_DBSTRING=postgres://postgres:secret@localhost:55433/shopdb?sslmode=disable
GOOSE_MIGRATION_DIR=./migrations

ก้อนที่ซ้ำคือทั้งก้อน ไม่ใช่แค่สอง address — สังเกต ; ตรงกลางที่เชื่อมข้อความ failed to connect to … สองอันเข้าด้วยกัน

🕐 ทำไมเลขในชื่อไฟล์ไม่ตรงกับนาฬิกาบนจอ?
ตอนรันคำสั่งนี้นาฬิกาเครื่องคือ 19:50 (เวลาไทย) แต่ชื่อไฟล์เขียนว่า ...125033 คือ 12:50:33 UTC
goose ตั้งชื่อด้วย timestamp UTC รูปแบบ YYYYMMDDHHMMSS เสมอ เพื่อให้ไฟล์ของคนที่อยู่คนละโซนเวลาเรียงลำดับถูกต้อง เมื่อ merge เข้ามาในโฟลเดอร์เดียวกัน
ส่วนตัวเลข 2026/08/18 19:50:33 ที่นำหน้าทุกบรรทัด คือ prefix ของ log ซึ่งใช้เวลาเครื่อง — บรรทัดเดียวมีสองโซนเวลาปนกัน อย่าเพิ่งคิดว่าตัวเองอ่านผิด

ถ้าทีมเล็กและอยากได้เลขอ่านง่าย มี flag -s (sequential) ให้: 

$ goose -s create init sql
2026/08/18 19:53:42 Created new file: migrations/00001_init.sql
$ goose -s create add_users sql
2026/08/18 19:53:42 Created new file: migrations/00002_add_users.sql

อ่านง่ายกว่าจริง แต่แลกมาด้วยความเสี่ยง: สองคนสร้างไฟล์พร้อมกันในคนละ branch จะได้เลขเดียวกัน แล้วชน conflict ตอน merge — ทีมใหญ่จึงใช้ timestamp

5 · โครงไฟล์ migration — annotation ที่ต้องพิมพ์เอง

ไฟล์ที่ goose create สร้างให้ มีแค่นี้จริง ๆ:

-- +goose Up
SELECT 'up SQL query';

-- +goose Down
SELECT 'down SQL query';

⚠️ ไม่มี StatementBegin / StatementEnd มาให้ในไฟล์ — สไลด์หลายชุดเขียนเหมือนว่าเป็นของที่มาพร้อม template ความจริงคือมี annotation แค่ 2 ตัว (Up กับ Down) ที่เหลือต้องพิมพ์เองเฉพาะตอนที่ต้องใช้

ทีนี้มาดูว่าแต่ละ annotation ทำอะไร:

annotationหน้าที่ต้องมีไหม
-- +goose UpSQL ต่อจากนี้คือส่วนที่รันตอน goose upต้องมี ไม่งั้น parse ไม่ผ่าน
-- +goose DownSQL ที่รันตอน goose down เพื่อย้อนกลับควรมีทุกไฟล์ (ดูกับดัก 3 ในหัวข้อ 9)
-- +goose StatementBegin / StatementEndบอก goose ว่า block นี้เป็น statement เดียว ห้ามตัดที่ ;เฉพาะ block ที่มี ; อยู่ข้างใน
-- +goose NO TRANSACTIONไม่ต้องห่อไฟล์นี้ด้วย transactionเฉพาะคำสั่งที่ Postgres ห้ามอยู่ใน transaction

ไฟล์แรกจริง ๆ ของโปรเจกต์เรา:

-- 20260818125033_create_products_table.sql
-- +goose Up
CREATE TABLE products (
    id         BIGSERIAL PRIMARY KEY,
    name       TEXT NOT NULL,
    price      NUMERIC(10,2) NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- +goose Down
DROP TABLE products;

สังเกตว่า ทุกอย่างที่ Up ทำ Down ต้องมีคำสั่งย้อนคู่กัน — สร้างตารางคู่กับลบตาราง เพิ่มคอลัมน์คู่กับลบคอลัมน์ สร้าง index คู่กับลบ index

เมื่อไหร่ที่ต้องใช้ StatementBegin

ผมเขียน trigger ที่อัปเดต updated_at อัตโนมัติแบบตรงไปตรงมา — SQL ชุดนี้ copy ไปวางใน psql รันผ่านฉลุย แต่ goose up พัง: 

2026/08/18 19:51:38 goose run: ERROR 20260818125138_add_updated_at_trigger.sql: failed to run SQL migration:
failed to execute SQL query "CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger AS $$\nBEGIN\n    NEW.updated_at = now();":
ERROR: unterminated dollar-quoted string at or near "$$
BEGIN
    NEW.updated_at = now();" (SQLSTATE 42601)

อ่าน error ให้ดี — SQL ที่ goose ส่งไปที่ DB จบลงที่ NEW.updated_at = now(); พอดี
เพราะ goose แบ่ง statement ด้วยการมอง ; แบบง่าย ๆ มันไม่รู้จัก dollar-quoted string ($$) ของ Postgres เลยตัด function ขาดครึ่งกลางตัว 

-- 20260818125138_add_updated_at_trigger.sql
-- +goose Up
ALTER TABLE products ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT now();

-- +goose StatementBegin      ← ครอบเฉพาะ block ที่มี ; อยู่ข้างใน
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN
    NEW.updated_at = now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
-- +goose StatementEnd

CREATE TRIGGER trg_products_updated_at
BEFORE UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

-- +goose Down
DROP TRIGGER trg_products_updated_at ON products;
DROP FUNCTION set_updated_at();
ALTER TABLE products DROP COLUMN updated_at;
2026/08/18 19:51:54 OK   20260818125138_add_updated_at_trigger.sql (3.77ms)
2026/08/18 19:51:54 goose: successfully migrated database to version: 20260818125138

ครอบแค่ block ที่จำเป็นพอ — ALTER TABLE กับ CREATE TRIGGER ในไฟล์เดียวกัน ไม่ต้องครอบเลย เพราะไม่มี ; ซ่อนอยู่ข้างใน
ครอบทุก statement ก็ไม่ผิด แต่ไฟล์จะรกเปล่า ๆ
กฎง่าย ๆ: เห็น $$ เมื่อไหร่ (function · DO block) ครอบเมื่อนั้น

7 · เปิดตาราง goose_db_version — จุดที่ทำให้เข้าใจทั้งบท

ทุกอย่างในบทนี้ตัดสินด้วยตารางเดียว มาดูกันว่ามันเก็บอะไรบ้าง: 

$ psql -c '\d goose_db_version'

                                  Table "public.goose_db_version"

------------+-----------------------------+-----------+----------+----------------------------------

 is_applied | boolean                     |           | not null |

🔑 อ่านตารางนี้แล้วจะเดาพฤติกรรม goose ได้ทุกกรณี

มีแค่ 4 คอลัมน์ — และสิ่งที่ไม่มี สำคัญกว่าสิ่งที่มี
❌ ไม่มี checksum ของไฟล์ (checksum = ตัวเลขสั้น ๆ ที่คำนวณจากเนื้อไฟล์ ถ้าเนื้อไฟล์เปลี่ยนแม้แต่ตัวอักษรเดียว ตัวเลขนี้จะเปลี่ยนตาม เครื่องมือบางตัวเก็บค่านี้ไว้ตอนรัน เพื่อจับได้ทันทีว่าไฟล์ถูกแก้ทีหลัง)
❌ ไม่มี SQL ที่รันไป
❌ ไม่มีชื่อไฟล์ด้วยซ้ำ — เก็บแค่ตัวเลขหน้าไฟล์

เท่ากับว่าคำถามเดียวที่ goose ตอบได้คือ "เลข version นี้เคยรันไปแล้วหรือยัง"
มันไม่มีทางรู้ว่าไฟล์ที่เคยรันไปนั้น ตอนนี้ หน้าตายังเหมือนเดิมไหม

ย้อนกลับไปดูหัวข้อ 7: goose_db_version เก็บแค่ version_id ไม่มี checksum ของไฟล์ goose จึงเทียบได้แค่ "เลขนี้เคยรันยัง" ไม่มีทางรู้ว่าเนื้อไฟล์เปลี่ยนไปแล้ว

(ถ้าเผลอแก้แล้วแต่ยังไม่ push และเป็นเครื่องตัวเองเครื่องเดียว → goose down ก่อน แล้วค่อยแก้ แล้ว up ใหม่)
เครื่องมืออื่นอย่าง Flyway/Liquibase เก็บ checksum ไว้ จึง fail ให้เห็นทันที — goose ไม่มี ต้องอาศัยวินัยของทีมล้วน ๆ

-- +goose Up
ALTER TABLE products ADD COLUMN stock INTEGER NOT NULL DEFAULT 0;

-- +goose Down
ALTER TABLE products DROP COLUMN stock;

⚠️ goose รายงาน OK ทุกบรรทัด ไม่มี error สักตัว — แต่ 42 กับ 7 หายไปตลอดกาล
goose down ไม่ใช่ undo และไม่ใช่ snapshot — มันคือ "รัน SQL ที่อยู่ใน block Down" เท่านั้น
คุณเขียนว่า DROP COLUMN มันก็ DROP COLUMN ซึ่งทำลายข้อมูลถาวร พอ up ใหม่ ADD COLUMN ... DEFAULT 0 ก็เติมศูนย์ให้ทุกแถว
สรุป: rollback ย้อนได้แค่ schema ไม่เคยย้อน ข้อมูล

ในทางปฏิบัติจึงมีกฎ 3 ข้อ:

สถานการณ์ทำยังไง
อยากย้อน migration บน productionอย่าใช้ down — เขียนไฟล์ migration ใหม่ที่แก้ไปข้างหน้า (forward-only)
จะลบคอลัมน์จริง ๆแยกเป็น 2 deploy: รอบแรกเลิกใช้คอลัมน์นั้นในโค้ด · รอบสอง (หลัง backup) ค่อย DROP
ต้องย้อนได้จริงแบบมีข้อมูลDown ต้อง copy ข้อมูลไปตารางสำรองก่อน DROP
✅ แล้ว down มีไว้ทำอะไร

มีไว้ใช้ตอนกำลังพัฒนาในเครื่องตัวเอง — เขียนไฟล์ผิด down แก้ up ใหม่ วนไปจนพอใจ
และมีไว้เป็นเอกสาร: การบังคับตัวเองให้เขียน Down ทุกไฟล์ ทำให้คุณต้องคิดตั้งแต่ตอนเขียนว่า "ถ้าอันนี้พัง จะย้อนยังไง" — ซึ่งบางทีคำตอบคือ "ย้อนไม่ได้" และนั่นคือข้อมูลที่มีค่าที่สุด

กับดัก 3 — ลืมเขียน block Down

ถ้าไฟล์มีแต่ -- +goose Up แล้วสั่ง goose down คุณอาจคิดว่ามันจะฟ้อง — เปล่าเลย: 

$ goose down
2026/08/18 19:53:29 EMPTY 20260818130000_no_annotation.sql (1.71ms)
EXIT=0

$ psql -c '\dt'
 public | goose_db_version | table | postgres
 public | t1               | table | postgres      ← ตารางยังอยู่!
(2 rows)

$ psql -c 'SELECT * FROM goose_db_version;'
 id | version_id | is_applied |           tstamp
----+------------+------------+----------------------------
  1 |          0 | t          | 2026-08-18 12:53:29.160615
(1 row)                                          ← แต่แถว version หายไปแล้ว

ตอนนี้ DB จริงกับ version table ไม่ตรงกัน — ตาราง t1 มีอยู่ แต่ goose คิดว่ายังไม่เคยสร้าง
พอสั่ง up เพื่อกู้สถานการณ์: 

2026/08/18 19:53:36 goose run: ERROR 20260818130000_no_annotation.sql: failed to run SQL migration:
failed to execute SQL query "CREATE TABLE t1 (id int);": ERROR: relation "t1" already exists (SQLSTATE 42P07)
EXIT=1

ติดหล่มสมบูรณ์: up ก็พัง down ก็ไม่ช่วย ทางออกเดียวคือเข้าไป DROP TABLE t1; ด้วยมือ แล้วค่อย goose up ใหม่
→ เขียน Down เสมอ แม้จะเป็นแค่ DROP TABLE บรรทัดเดียว

โบนัส — ข่าวดีข้อเดียวของบทนี้

ถ้า migration พังกลางไฟล์ ไม่มี state ค้าง เพราะ goose ห่อแต่ละไฟล์ไว้ใน transaction เดียว ทั้งคำสั่งที่เปลี่ยนโครงสร้าง (เรียกรวม ๆ ว่า DDL = คำสั่งกลุ่ม CREATE / ALTER / DROP) และการ INSERT ลง goose_db_version อยู่ใน transaction เดียวกัน
แปลว่าถ้าพังกลางทาง Postgres จะย้อนคืนให้หมดทั้งชุด เหมือนไม่เคยรันเลย
ตอนที่ไฟล์ trigger พังเพราะลืม StatementBegin ผมเช็คทันทีหลังจากนั้น: 

$ goose version
2026/08/18 19:51:44 goose: version 20260818125035     ← ยังอยู่ที่ไฟล์ก่อนหน้า

$ psql -c '\df'
                       List of functions
 Schema | Name | Result data type | Argument data types | Type
--------+------+------------------+---------------------+------
(0 rows)                                              ← function ไม่ถูกสร้างเลย

แก้ไฟล์แล้วรัน goose up ใหม่ได้เลย ไม่ต้องตามเก็บกวาดอะไร
แต่ข้อนี้เป็นจริงเฉพาะ Postgres (และ MySQL InnoDB) ที่ DDL อยู่ใน transaction ได้ — MySQL รุ่นที่ DDL auto-commit ห้ามเหมารวม

🔧 ข้อยกเว้น: CREATE INDEX CONCURRENTLY
คำสั่งนี้มีไว้สร้าง index บนตารางใหญ่โดยไม่ล็อกตาราง แต่ Postgres ห้ามมันอยู่ใน transaction: 

2026/08/18 19:55:42 goose run: ERROR 00002_concurrent_index.sql: failed to run SQL migration:
failed to execute SQL query "CREATE INDEX CONCURRENTLY idx_items_sku ON items (sku);":
ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block (SQLSTATE 25001)

ทางแก้คือใส่ -- +goose NO TRANSACTION เป็นบรรทัดแรกของไฟล์ (ก่อน -- +goose Up) → OK 00002_concurrent_index.sql (2.79ms)
แลกมาด้วยว่าไฟล์นั้นไม่มี rollback อัตโนมัติแล้ว พังกลางทางต้องตามเก็บเอง → ใส่ statement เดียวต่อไฟล์เท่านั้น

10 · goose ทำสิ่งที่ AutoMigrate ทำไม่ได้ยังไง

ปิดวงกลับไปที่หัวข้อ 3 — ผมเอา DB ตัวเดียวกันที่ GORM สร้างไว้ มาให้ goose จัดการต่อ แล้วสั่งเปลี่ยนชื่อคอลัมน์ที่ AutoMigrate ทำไม่ได้: 

-- 00001_rename_price_to_unit_price.sql
-- +goose Up
ALTER TABLE products RENAME COLUMN price TO unit_price;

-- +goose Down
ALTER TABLE products RENAME COLUMN unit_price TO price;

❌ AutoMigrate เปลี่ยนชื่อ

 id |   name   | price | cost
----+----------+-------+------
  1 | Keyboard |  1200 |
  2 | Mouse    |   590 |

ได้คอลัมน์ใหม่ว่าง ๆ · ของเก่ายังอยู่ · ข้อมูลไม่ตามมา

✅ goose RENAME COLUMN

 id |   name   | unit_price
----+----------+------------
  1 | Keyboard |       1200
  2 | Mouse    |        590

คอลัมน์เดิมเปลี่ยนชื่อ · ข้อมูลติดไปด้วย · down ย้อนชื่อกลับได้

ไม่ใช่เพราะ goose ฉลาดกว่า — แต่เพราะ goose ให้คุณเขียน SQL เอง คุณเป็นคนเดียวที่รู้ว่า cost คือ price ที่เปลี่ยนชื่อ ไม่ใช่คอลัมน์ใหม่ และ goose แค่ทำให้ความรู้นั้นกลายเป็นไฟล์ที่รีวิวได้ · เก็บใน git ได้ · รันเหมือนกันทุกเครื่อง

🤝 ใช้ทั้งคู่พร้อมกันได้ไหม? ได้ และหลายทีมทำแบบนี้: ให้ goose เป็นเจ้าของ schema แต่เพียงผู้เดียว · ใช้ GORM แค่ query ไม่เรียก AutoMigrate เลย
ส่วน struct ของ GORM ก็ยังต้องแก้ให้ตรงกับ schema เอง — ไม่มีใครซิงก์ให้อัตโนมัติ ถ้าไม่ตรงจะรู้ตอน query แล้ว error เท่านั้น (เป็นอีกเหตุผลที่ต้องมี integration test — บทถัดไป)

ทดสอบความเข้าใจ

1. ตาราง goose_db_version เก็บอะไรไว้บ้าง?

เปิดดูจริงมี 4 คอลัมน์: id · version_id · is_applied · tstamp
ไม่มี checksum ไม่มี SQL ไม่มีแม้แต่ชื่อไฟล์ — เก็บแค่ตัวเลขหน้าไฟล์
ข้อ 2 คือสิ่งที่ Flyway/Liquibase ทำ แต่ goose ไม่ทำ → เป็นสาเหตุโดยตรงที่แก้ไฟล์ที่ apply แล้ว goose ตรวจไม่เจอ · ข้อ 1 กับ 4 ไม่มีอะไรมาเก็บได้ในตาราง 4 คอลัมน์

2. แก้ไฟล์ที่ up ไปแล้ว เพิ่ม INSERT อีกหนึ่งบรรทัด แล้วรัน goose up ใหม่?

ผลจริง: goose: no migrations to run. current version: 20260818125201 · EXIT=0
แม้แต่ goose validate ก็ EXIT=0 เพราะมันตรวจแค่ syntax ไม่ได้เทียบกับ DB
ข้อ 2 คือพฤติกรรมของ Flyway ที่มี checksum · ข้อ 1 และ 3 เป็นไปไม่ได้เพราะ goose ไม่เปิดไฟล์นั้นอ่านด้วยซ้ำ เมื่อเห็นว่า version_id อยู่ในตารางแล้ว
อันตรายจริงคือ DB เพื่อนที่ยังว่างจะได้ 4 แถว ส่วนของคุณค้างที่ 3 แถว — แตกกันเงียบ ๆ

3. Up คือ ADD COLUMN stock DEFAULT 0 · Down คือ DROP COLUMN stock — สั่ง down แล้ว up ใหม่ ข้อมูล stock เป็นอะไร?

ก่อน down มี 42 กับ 7 · หลัง down แล้ว up ใหม่ ได้ 0 ทั้งสองแถว และ goose พิมพ์ OK ทุกบรรทัด ไม่มี error เลย
goose down คือการรัน SQL ใน block Down เท่านั้น ไม่ใช่ snapshot ไม่ใช่ undo
ไม่ใช่ NULL เพราะ Up ระบุ NOT NULL DEFAULT 0 → ทุกแถวได้ค่า default
ข้อ 4 ผิดชัดเจน: goose ไม่มีกลไกตรวจว่า SQL ของคุณอันตรายไหม มันแค่รันตามที่เขียน

4. เปลี่ยนชื่อ struct field จาก Price เป็น Cost แล้วรัน AutoMigrate?

ผลจริง: ตารางมีทั้ง price (1200, 590) และ cost (ว่าง) — พิมพ์ AutoMigrate step2 OK ไม่มี error
AutoMigrate เติมสิ่งที่ขาดอย่างเดียว มันไม่มีประวัติให้ดู จึงไม่มีทางรู้ว่า cost คือ price ที่เปลี่ยนชื่อ
ข้อ 4 ผิดเพราะเอกสาร GORM ระบุเองว่า จะไม่ลบคอลัมน์ที่ไม่ได้ใช้ (กันข้อมูลหาย)
สิ่งที่ต้องทำจริงคือ ALTER TABLE products RENAME COLUMN price TO unit_price; ผ่าน goose ซึ่งพิสูจน์แล้วว่าข้อมูลอยู่ครบและ down ย้อนชื่อกลับได้

🛠️ ภารกิจ — ทำ migration ชุดแรกของโปรเจกต์คุณเอง

ต่อยอดจากภารกิจบทเรียน 27 — โปรเจกต์ที่มี internal/repository และ AutoMigrate อยู่
เป้าหมายวันนี้: ย้ายความรับผิดชอบเรื่อง schema จาก GORM มาที่ goose ให้หมด

  1. เปิด PostgreSQL ใน Docker แล้ววาง .env ที่รากโปรเจกต์ (GOOSE_DRIVER · GOOSE_DBSTRING · GOOSE_MIGRATION_DIR)
    ทดสอบว่าตั้งถูกด้วย goose status — ต้องขึ้น Pending ไม่ใช่หน้า usage
  2. สร้าง migration 3 ไฟล์ ด้วย goose create <ชื่อ> sql ทีละไฟล์:
    ① สร้างตาราง ② เพิ่มคอลัมน์ ③ เพิ่ม index
    ทุกไฟล์ต้องมี Down ที่ย้อนได้จริง
    ถ้ายังไม่เคยเขียน SQL 3 แบบนี้ นี่คือหน้าตาของมัน (แก้ชื่อตาราง/คอลัมน์เป็นของโปรเจกต์คุณ): 
    -- ① สร้างตาราง
CREATE TABLE products (id BIGSERIAL PRIMARY KEY, name TEXT NOT NULL);
DROP TABLE products;                              -- คู่ Down

-- ② เพิ่มคอลัมน์
ALTER TABLE products ADD COLUMN stock INTEGER NOT NULL DEFAULT 0;
ALTER TABLE products DROP COLUMN stock;           -- คู่ Down

-- ③ เพิ่ม index
CREATE INDEX idx_products_name ON products (name);
DROP INDEX idx_products_name;                     -- คู่ Down
    รู้ได้ยังไงว่าทำถูก: goose status ต้องขึ้น Pending ครบ 3 บรรทัด และ goose validate ต้อง exit 0
  3. goose up แล้วเปิด SELECT * FROM goose_db_version; ดู
    มีกี่แถว · เลข version_id ตรงกับอะไร
  4. goose down หนึ่งครั้ง แล้วเปิดตารางเดิมดูอีกที — แถวหายไป หรือ is_applied เปลี่ยนเป็น f?
  5. เขียน seed master data เป็น migration (ไม่ต้องใส่ ON CONFLICT) แล้วรัน goose up 3 รอบติดกัน — นับแถวว่าซ้ำไหม แล้วอธิบายให้ได้ว่าทำไม
  6. ปิด AutoMigrate ในโค้ดแอป ให้เหลือแค่ gorm.Open อย่างเดียว
    รันแอป — ยังทำงานได้ไหม? ถ้าลืมสร้างตารางไหนใน migration จะรู้ตอนไหน?
  7. ท้าทาย 1 — trigger: เขียน migration ที่สร้าง function set_updated_at() พร้อม trigger โดยยังไม่ใส่ StatementBegin รันดูให้เห็น error เต็ม ๆ ก่อน แล้วค่อยใส่ครอบ
  8. ท้าทาย 2 — ทำลาย DB ตัวเองให้ดู: แก้ไฟล์ seed ที่ up ไปแล้ว เพิ่มอีกหนึ่งแถว แล้วรัน goose up · goose validate
    จากนั้นสร้าง database เปล่าตัวใหม่ขึ้นมา (จำลองว่าเป็นเครื่องเพื่อน) แล้วชี้ GOOSE_DBSTRING ไปที่นั่น รัน goose up 
    # สร้าง database เปล่าชื่อ shopdb2 ใน container เดิม
docker exec -it pg-shop psql -U postgres -c 'CREATE DATABASE shopdb2;'

# แก้ .env ให้ชี้ไปที่ตัวใหม่ (เปลี่ยนแค่ชื่อ database ท้าย URL)
# GOOSE_DBSTRING=postgres://postgres:secret@localhost:55433/shopdb2?sslmode=disable

goose up
    รู้ได้ยังไงว่าทำถูก: SELECT count(*) FROM categories; บน shopdb กับ shopdb2 ต้องได้เลขไม่เท่ากัน ทั้งที่ไฟล์ใน git ชุดเดียวกันเป๊ะ
    เทียบจำนวนแถวสอง DB แล้วเขียนกฎของทีมคุณเองหนึ่งบรรทัดว่าจะกันเรื่องนี้ยังไง
  9. ท้าทาย 3: ลองลบ block -- +goose Down ออกจากไฟล์หนึ่ง แล้วสั่ง goose down — ได้คำว่าอะไร exit เท่าไหร่ แล้วสั่ง goose up ต่อทันที เกิดอะไรขึ้น และจะกู้ยังไง?

แอปยังรันได้ปกติ — ตราบใดที่ schema ตรงกับ struct
เพราะ AutoMigrate ไม่ได้เกี่ยวกับการ query เลย มันแค่พยายามแก้ schema ตอน start

แต่ถ้าลืมสร้างคอลัมน์ไหนใน migration คุณจะไม่รู้ตอน start — คุณจะรู้ตอนมี request แรกวิ่งเข้ามาแล้ว query พังกลาง production
นี่คือข้อแลกเปลี่ยนที่ต้องรับให้ได้: ปิด AutoMigrate = ย้ายจุดที่พังจาก "ตอน deploy" ไปเป็น "ตอนมี traffic"

ทางแก้ไม่ใช่เปิด AutoMigrate กลับ แต่คือ เขียน integration test ที่รันบน schema จริง แล้วยิงทุก query ของ repository ให้ครบ — ถ้า struct ไม่ตรง schema เทสจะแดงตั้งแต่ใน CI ก่อนถึง production · เป็นเนื้อหาของบทถัดไป

💬 ข้อ 3 กับข้อ 4 คือสองข้อที่ผมอยากให้ทำที่สุด — เพราะถ้าคุณเห็นด้วยตาตัวเองว่าตารางนั้นมีแค่ 4 คอลัมน์ และ down คือการลบแถวทิ้ง คุณจะเดาพฤติกรรมของ goose ได้เองทุกกรณีโดยไม่ต้องท่อง รวมถึงกับดักที่บทนี้ยังไม่ได้พูดถึง
มีอะไรที่ลองแล้วผลไม่เหมือนในบท ส่งมาได้เลย — โดยเฉพาะถ้าคุณใช้ MySQL แทน Postgres เพราะเรื่อง transaction ต่างกันมาก
บทถัดไป: ทำให้ Redis เข้ามาอยู่ระหว่างแอปกับ database โดยไม่ทำให้ข้อมูลเพี้ยน
