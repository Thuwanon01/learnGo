2 · sync.Once — เปิดครั้งเดียว ใช้ทั้ง package

ใน บทเรียน 24 คุณเรียนว่า package sync มีไว้ประสานงานระหว่าง goroutine
sync.Once คืออีกตัวในตระกูลเดียวกัน สัญญาของมันสั้นมาก: โค้ดใน Do(f) จะรันแค่ครั้งเดียวตลอดอายุของ process ต่อให้ถูกเรียกพร้อมกันจากหลาย goroutine ก็ตาม — คนที่มาทีหลังจะรอจนตัวแรกทำเสร็จ

🫖 เทียบให้เห็นภาพ — กาต้มน้ำร้อนกลางออฟฟิศ

ออฟฟิศมีกาต้มน้ำร้อนตั้งไว้ตัวเดียว คนแรกที่อยากชงกาแฟตอนเช้าคือคนที่กดต้ม
คนที่สอง สาม สี่ ที่เดินมาทีหลังไม่ต้องต้มใหม่ กดน้ำใส่แก้วแล้วเดินกลับโต๊ะได้เลย
ถ้าบังเอิญเดินมาถึงพร้อมกันตอนน้ำยังไม่เดือด ก็แค่ยืนรอข้าง ๆ ไม่มีใครไปกดต้มซ้ำอีกกา

container ในเทสก็คือกาน้ำใบนี้ · เทสตัวแรกที่ขอใช้ DB เป็นคนจ่ายค่าต้ม (~1 วินาที) ส่วนเทสตัวที่ 2 เป็นต้นไปมารับของที่ร้อนอยู่แล้ว (~2 มิลลิวินาที)

ที่ไม่เหมือนกัน: ถ้ากาน้ำเสีย คนที่สองเดินไปกดต้มเองใหม่ได้ แต่ sync.Once ไม่ยอมรันซ้ำให้เด็ดขาด ต่อให้ครั้งแรกพัง — ตรงกับย่อหน้าใต้โค้ดข้างล่างที่บอกว่าต้องเก็บ sharedErr ไว้เอง 

var (
    sharedOnce sync.Once
    sharedCtr  *tcpostgres.PostgresContainer
    sharedDB   *gorm.DB
    sharedDSN  string
    sharedErr  error
    SharedBoot time.Duration
)

// SharedDB คืน DB ที่ใช้ร่วมกันทั้ง process โดย boot container แค่ครั้งเดียว
func SharedDB(t *testing.T) (*gorm.DB, string) {
    t.Helper()  // ทำให้ error ชี้ไปที่เทสที่เรียก ไม่ใช่ชี้มาที่ฟังก์ชันนี้ — หัวข้อ 6 จะพิสูจน์ให้ดู
    sharedOnce.Do(func() {
        ctx := context.Background()
        var d time.Duration
        sharedCtr, d, sharedErr = StartPostgres(ctx)
        SharedBoot = d
        if sharedErr != nil {
            return
        }
        sharedDB, sharedDSN, sharedErr = OpenGorm(ctx, sharedCtr)
        log.Printf("[sync.Once] container booted in %v dsn=%s", d, sharedDSN)
    })
    if sharedErr != nil {
        t.Fatalf("shared container failed: %v", sharedErr)
    }
    return sharedDB, sharedDSN
}

จุดที่คนมักพลาด: ต้องเก็บ sharedErr ไว้นอก Do
เพราะถ้า container พังในการเรียกครั้งแรก Do จะไม่รันซ้ำให้เทสตัวที่สอง — เทสตัวที่สองต้องรู้ว่า "ตัวแรกพังไปแล้ว" จาก error ที่เก็บไว้ ไม่งั้นมันจะได้ nil แล้ว panic แทน

🗣 ศัพท์ที่เพิ่งเรียนไป

คำพวกนี้คือคำที่วงการใช้เรียกสิ่งที่คุณเพิ่งเข้าใจไป — ใช้ให้ตรงคำ แล้วคำตอบที่ได้จาก senior หรือจาก AI จะตรงขึ้นมาก

sync.Once
“กาน้ำใบเดียวของออฟฟิศ” — โค้ดใน Do ของ Once ตัวนั้น ๆ รันครั้งเดียวจบ · ขอบเขตคือต่อหนึ่งตัวแปร ไม่ใช่ต่อทั้ง process — ประกาศ sync.Once สองตัว ก็รันได้สองครั้งใน process เดียว (คนละตัวแปร = คนละโควตา) · เวลาถามให้พูดว่า “ห่อ boot ไว้ใน sync.Once แล้ว แต่มันยัง boot ซ้ำอยู่” จะสื่อกว่าถามว่า “ทำไม container เปิดหลายตัว”
process
“โปรแกรม 1 ตัวที่กำลังรันอยู่” · สั่ง go test ./test/integration หนึ่งครั้ง = 1 process · พอ process ตาย ตัวแปรที่ sync.Once เก็บไว้ก็หายไปทั้งหมด รอบหน้าเริ่มนับหนึ่งใหม่
ระวัง — go test ./... คือ 1 process ต่อ 1 package ดังนั้น container ที่ share ด้วย sync.Once จะแยกกันคนละใบต่อ package ไม่ใช่ใบเดียวทั้ง repo
lazy / eager
lazy = “ขี้เกียจ” สร้างของตอนมีคนขอใช้จริง · eager = “ใจร้อน” สร้างทิ้งไว้ก่อนเผื่อมีคนใช้ · ประโยคที่เอาไปใช้ได้เลย: “ตรงนี้ boot แบบ eager หรือ lazy” (หัวข้อ 4 จะใช้สองคำนี้เต็ม ๆ)
shared fixture
“ของกลางที่เทสหลายตัวใช้ร่วมกัน” เช่น container ตัวนี้ · ถามว่า “fixture ตัวนี้ share กันทั้ง package หรือแยกต่อเทส” senior จะเข้าใจทันทีว่าคุณถามอะไร
overhead
“ค่าโสหุ้ย” — เวลาที่หมดไปกับการเตรียมของ ไม่ใช่เนื้องานจริง · 760 มิลลิวินาทีต่อเทสในหัวข้อ 1 คือ overhead ล้วน ๆ

🔑 เทียบให้เห็นภาพ — ยามที่ถือกุญแจตึก

ตึกออฟฟิศมีคนถือกุญแจอยู่คนเดียว เช้ามาเปิดประตู เย็นรอจนคนสุดท้ายเดินออกแล้วค่อยล็อก
ระหว่างวันพนักงานเข้าออกกี่คนก็ได้ แต่ไม่มีใครมีสิทธิ์ล็อกประตูตอนบ่ายสอง เพราะยังมีคนอื่นทำงานอยู่ข้างใน

TestMain คือยามคนนั้น · m.Run() คือ “ทั้งวันทำงาน” ที่เทสทุกตัวรันอยู่ข้างใน
นี่คือเหตุผลที่ Terminate ไปแปะไว้ในเทสตัวใดตัวหนึ่งไม่ได้ — เท่ากับให้พนักงานคนหนึ่งล็อกประตูทิ้งเพื่อนที่เหลือไว้ข้างใน

ที่ไม่เหมือนกัน: ยามเดินไล่ปิดไฟทีละห้องก่อนกลับบ้านได้ แต่ os.Exit คือการสับเบรกเกอร์ลงทันที — งานที่ฝากไว้ด้วย defer จะไม่ได้ทำเลยสักอย่าง ตามที่กล่องเตือนข้างล่างจะบอก 

func TestMain(m *testing.M) {
    code := m.Run()          // ← เทสทุกตัวใน package รันตรงบรรทัดนี้
    testutil.TerminateShared()  // ← cleanup หลังเทสจบครบแล้ว
    fmt.Printf("[TestMain] shared container boot time = %v\n", testutil.SharedBoot)
    os.Exit(code)             // ← ส่งผลแพ้ชนะออกไปเป็น exit code
}
บรรทัดเกิดอะไรขึ้น
m.Run()รันเทสทุกตัวใน package นี้จนจบ แล้วคืนค่า exit code (0 = ผ่านหมด)
cleanupต้องอยู่หลัง m.Run() เพราะก่อนหน้านั้นยังมีเทสใช้ของอยู่
os.Exit(code)ทำให้ go test และ CI (เครื่องกลางที่ build + รันเทสให้อัตโนมัติเมื่อโค้ดเข้า repo) รู้ว่าผ่านหรือไม่ผ่าน

⚠️ ทำไม cleanup ต้องอยู่ก่อน os.Exit — ห้ามใช้ defer
os.Exit ฆ่า process ทันทีโดยไม่รัน defer ที่ค้างอยู่ (กฎเดียวกับที่คุณเรียนใน บทเรียน 08)
ถ้าเขียน defer testutil.TerminateShared() ไว้บนสุดแล้วปิดท้ายด้วย os.Exit(code) → ฟังก์ชัน cleanup จะไม่ถูกเรียกเลย
นี่คือที่เดียวใน Go ที่ "เขียน defer ไว้ก่อนเพื่อความปลอดภัย" กลายเป็นคำแนะนำที่ผิด

5 · testify suite — SetupSuite ไม่ใช่ SetupTest

ใน บทเรียน 17 คุณใช้ testify แค่ฝั่ง assert/require — package suite คืออีกครึ่งที่ยังไม่ได้แตะ มันให้ struct หนึ่งตัวถือ state ร่วม (db, repo, ctx) แล้วมี hook ให้แขวนงานเตรียมของ
มีกติกา 3 ข้อที่ต้องรู้ก่อนอ่านโค้ดข้างล่าง:
1. บรรทัด suite.Suite ที่เขียนลอย ๆ ไม่มีชื่อ field คือการฝัง struct ของ testify เข้ามาในของเรา ผลคือ struct ของคุณได้ method ของ testify ติดมาฟรี ตัวที่ใช้บ่อยที่สุดคือ s.T() ซึ่งคืน *testing.T ของเทสที่กำลังรันอยู่ตอนนั้น เอาไว้ส่งต่อให้ฟังก์ชันที่ต้องการ *testing.T เช่น testutil.SharedDB(s.T())
2. เฉพาะ method ที่ชื่อขึ้นต้นด้วย Test เท่านั้นที่จะถูกรันเป็นเทส ถ้าตั้งชื่อว่า CreateAndGet เฉย ๆ จะไม่มีอะไรเกิดขึ้นและไม่มี error ฟ้องเลย — เทสหายไปเงียบ ๆ แล้วขึ้น PASS
3. testify ไม่ได้ถูก go test เห็นเอง ต้องมีเทสธรรมดา 1 ตัว (func TestUserRepoSuite(t *testing.T)) เรียก suite.Run(t, new(UserRepoSuite)) เป็นประตูเข้า อย่างที่เห็นบรรทัดสุดท้ายของโค้ด 

type UserRepoSuite struct {
    suite.Suite
    db   *gorm.DB
    dsn  string
    repo *repository.UserRepository
    ctx  context.Context
}

// SetupSuite — รันครั้งเดียวทั้ง suite: ขอ container ที่ share ไว้
func (s *UserRepoSuite) SetupSuite() {
    if testing.Short() {
        s.T().Skip("skipping integration suite in -short mode")
    }
    s.ctx = context.Background()
    s.db, s.dsn = testutil.SharedDB(s.T())
    s.repo = repository.NewUserRepository(s.db)
}

// SetupTest — รันก่อนทุกเทส: ล้างตาราง ไม่ต้องเปิด container ใหม่
func (s *UserRepoSuite) SetupTest() {
    testutil.TruncateUsers(s.T(), s.db)
}

func TestUserRepoSuite(t *testing.T) {
    suite.Run(t, new(UserRepoSuite))
}
🍲 เทียบให้เห็นภาพ — ร้านชาบู: งานก่อนเปิดร้าน กับ งานระหว่างเปลี่ยนโต๊ะ

ร้านชาบูมีงาน 2 จังหวะที่ไม่เหมือนกันเลย
· ก่อนเปิดร้านตอนเช้า — ติดตั้งเตา ต่อแก๊ส เปิดตู้แช่ ต้มน้ำซุปหม้อใหญ่ ทำครั้งเดียวจบ ทั้งวันไม่ต้องทำซ้ำ
· ตอนลูกค้าโต๊ะหนึ่งลุก ก่อนโต๊ะถัดไปนั่ง — เก็บจาน เช็ดโต๊ะ เปลี่ยนน้ำจิ้ม ทำทุกโต๊ะ และต้องทำ ไม่งั้นลูกค้าใหม่เจอคราบของคนเก่า

SetupSuite = งานก่อนเปิดร้าน (ขอ container, gorm.Open) · SetupTest = งานเช็ดโต๊ะระหว่างลูกค้า (TRUNCATE)
สลับที่กันเมื่อไหร่พังทันที: ต้มซุปใหม่ทุกโต๊ะ = ช้ามาก · เช็ดโต๊ะแค่ตอนเช้า = โต๊ะที่สองเจอของเก่าค้าง

ที่ไม่เหมือนกัน: ลูกค้าร้านชาบูเข้ามาตามคิวที่จองไว้ แต่ testify เรียงเทสตามตัวอักษรของชื่อ method ไม่ใช่ตามลำดับที่คุณเขียนในไฟล์ (กล่องทายผลถัดไปจะพิสูจน์ให้ดู) — จึงห้ามเขียนเทสที่พึ่งพา “โต๊ะก่อนหน้า” เด็ดขาด

“ตาข่ายรองรับ” — ของสำรองที่ช่วยไว้ตอนพลาด ไม่ใช่แผนหลัก · ประโยคที่ senior ชอบพูด: “อย่าออกแบบโดยพึ่ง safety net”

8 · กับดักที่เหลือ

8.1 Run คืน error พร้อมกับ container ที่ไม่ใช่ nil

บทที่แล้วสอนรูปแบบ cleanup ที่ถูกไปแล้ว ตรงนี้คือหลักฐานว่าทำไมมันสำคัญ — เมื่อ wait strategy (กติกาที่บอกว่าจะถือว่า container พร้อมใช้เมื่อไหร่ เช่น รอจนเห็น log บรรทัดหนึ่ง) รอจนหมดเวลา Run คืนทั้ง error และ container ที่ start ไปแล้วจริง ๆ: 

    waittimeout_test.go:28: VERBATIM wait-timeout error: run postgres: generic container: start container: started hook: wait until ready: "this log line will never appear" matched 0 times, expected 1
        context deadline exceeded
    waittimeout_test.go:29: returned container is nil? false
    waittimeout_test.go:31: container id = 6116d6c24184482b076d1c70a39046ad846920da81381698a84b52b9070ccca9
    waittimeout_test.go:37: TerminateContainer: <nil> (cleaned up)

❌ leak ทุกครั้งที่ wait timeout

ctr, err := tcpostgres.Run(ctx, ...)
if err != nil {
    t.Fatal(err)   // ออกก่อนถึง defer
}
defer ctr.Terminate(ctx)

t.Fatal จบเทสทันที บรรทัด defer ไม่เคยถูกรัน → container ที่ start แล้วค้าง

✅ defer ก่อนเช็ค err

ctr, err := tcpostgres.Run(ctx, ...)
defer func() {
    _ = testcontainers.TerminateContainer(ctr)
}()
if err != nil {
    t.Fatal(err)
}

TerminateContainer เป็น nil-safe — ผมทดสอบแล้วส่ง typed nil เข้าไปก็คืน <nil> ไม่ panic

8.3 sync.Once กับ t.Parallel() — เตือนไว้ก่อน

sync.Once เองปลอดภัยกับหลาย goroutine อยู่แล้วโดยธรรมชาติ (บทเรียน 24)
แต่ TruncateUsers ใน SetupTest ไม่ปลอดภัย — ถ้าเทสสองตัวรันขนานกันบน DB เดียวกัน ตัวหนึ่งจะล้างตารางกลางคันของอีกตัว
ข้อจำกัดข้อนี้ผมยังไม่ได้พิสูจน์ด้วยการรันจริง จึงไม่มี output มาให้ดู — เอาไว้เป็นข้อควรระวังว่าถ้าจะใช้ t.Parallel() ต้องแยก schema (ชุดตารางที่แยกกันอยู่คนละกลุ่มใน DB เดียวกัน) หรือแยกตารางต่อเทส ไม่ใช่ใช้ TRUNCATE ร่วมกัน

ทดสอบความเข้าใจ

1. ทำไม go test -short ของแบบ lazy ถึงได้ boot time = 0s แต่แบบ eager ยังเสีย 1.047s?

TestMain ทำงานก่อนเทสทุกตัว — โค้ดที่ boot container ไว้ตรงนั้นจะรันเสมอ ไม่ว่า flag จะเป็นอะไร (วัดได้ 1.673s ทั้งที่ทุกเทส SKIP)
ส่วน lazy ย้าย boot ไปอยู่ใน sync.Once ที่ถูก trigger จากในตัวเทส เมื่อทุกเทส t.Skip ก็ไม่มีใครเรียก Do → ไม่แตะ Docker เลย (0.353s)
ข้อ 1 ผิดเพราะ -short เป็นแค่ flag ที่คุณต้องเช็คเอง testcontainers ไม่รู้จักมัน · ข้อ 4 ผิดเพราะไม่มี container ค้าง Ryuk เก็บกวาดตั้งแต่ 10 วินาทีหลัง process ตาย

2. AutoMigrate และ TRUNCATE TABLE users ควรอยู่ที่ไหนใน testify suite?

SetupSuite = ของแพงที่ใช้ซ้ำได้ (container, gorm.Open, AutoMigrate) · SetupTest = ของถูกที่ต้องสดใหม่ทุกครั้ง (TRUNCATE, seed)
ข้อ 1 กลับหัวกลับหาง: TRUNCATE ครั้งเดียวต้นเทส แปลว่าเทสตัวที่สองเห็นข้อมูลที่ตัวแรกทิ้งไว้ → เทสพึ่งพาลำดับ ซึ่งอันตรายมากเพราะ testify รันตามตัวอักษร ไม่ใช่ลำดับที่เขียน
ข้อ 3 ทำให้จ่ายค่า DDL ทุกเทสโดยไม่จำเป็น · ข้อ 4 คือไม่มีอะไรล้างตารางเลย

3. เทสจบแล้วลืม Terminate โดยไม่ได้ปิด Ryuk — docker ps จะเห็นอะไร?

ผม poll ดูจริง: t+9s ยังเห็น running_pg=1 · t+10s ได้ running_pg=0 all_pg=0
all_pg มาจาก docker ps -a — ค่า 0 พิสูจน์ว่าถูกลบจริง ไม่ใช่แค่ stop (ข้อ 2 จึงผิด) และ dangling volume วัดได้ delta 0 คือ anonymous volume ถูกเก็บด้วย
ข้อ 3 จะจริงก็ต่อเมื่อตั้ง TESTCONTAINERS_RYUK_DISABLED=true ซึ่งผมทดสอบแยกแล้วได้ Up 28 seconds
อย่างไรก็ตาม ยังต้องเขียน Terminate เสมอ — Ryuk คือ safety net ไม่ใช่แผนหลัก

4. ทำไมต้องวาง defer cleanup ไว้ก่อนบรรทัดเช็ค err ของ Run?

ผมวัดจริง: ตอน wait strategy timeout ได้ returned container is nil? false พร้อม container id ยาว ๆ — แปลว่าของถูกสร้างและ start ไปแล้ว แค่ wait ไม่ผ่าน
t.Fatal(err) จบเทสทันทีที่บรรทัดนั้น defer ที่เขียนไว้ข้างล่างไม่เคยถูกลงทะเบียน → container ค้าง
และต้องใช้ testcontainers.TerminateContainer(ctr) ไม่ใช่ ctr.Terminate(ctx) เพราะกรณี image tag ผิดจะได้ returned container is nil? true — ตัวแรก nil-safe ตัวหลังไม่

    รันด้วย go test -run TestLeak -v ./test/leak/ จากนั้นเปิดอีกเทอร์มินัลดู docker ps ทันทีที่เทสจบ แล้วดูซ้ำอีกครั้งตอนวินาทีที่ 15
    ถูกแล้วคือ: ครั้งแรกยังเห็น postgres:16-alpine สถานะ Up ค้างอยู่ (นี่คือตัวที่ leak) · ครั้งที่สองหายไปแล้วเพราะ Ryuk ตามเก็บให้ — ซึ่งแปลว่าถ้าใครไปปิด Ryuk มันจะค้างถาวร
