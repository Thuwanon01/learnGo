1 · สองเครื่องมือ สองคำถาม

ก่อนลงมือ แยกให้ออกก่อนว่าสองอย่างนี้ตอบคำถามคนละแบบ:

  • debugger ตอบคำถาม "ตอนที่โค้ดบรรทัดนี้กำลังจะทำงาน ตัวแปรแต่ละตัวมีค่าอะไร?" — คุณต้องมีโค้ดที่กำลังวิ่งอยู่ (เช่น request ที่เข้ามา) แล้วสั่งให้มันหยุดค้างไว้
  • bin/rails console ตอบคำถาม "ถ้าฉันเรียก method นี้กับข้อมูลจริง จะได้อะไร?" — ไม่ต้องมี request ไม่ต้องเปิด server · แค่เปิดแอปขึ้นมาแล้วพิมพ์ Ruby ใส่ทีละบรรทัด

เทียบกับของที่คุณใช้มาแล้ว:

GoTypeScript / NodeRuby / Rails
ตัวหยุดโค้ด delve (dlv) · ไม่ได้มากับ go — go help ของ Go 1.26.5 ไม่มีคำสั่ง debug และเครื่องที่ใช้ตรวจไม่มี dlv จนกว่าจะติดตั้งเพิ่ม node inspect (ในเทอร์มินัล) หรือ node --inspect (ต่อกับ Chrome DevTools) · มากับ node gem debug (โปรแกรมชื่อ rdbg) · rails new ใส่ไว้ใน Gemfile ให้แล้ว
สั่งหยุดจากในโค้ด ตั้ง breakpoint ผ่าน dlv หรือ IDE debugger; — เป็น keyword ของภาษา debugger — เป็น method ธรรมดา ที่ gem debug เติมให้ (หัวข้อ 3 จะเห็นว่าทำไมเรื่องนี้สำคัญ)
REPL ที่โหลดแอปทั้งตัว ไม่มีใน go node เปิด REPL ได้ แต่ได้แค่ภาษาเปล่า ๆ ไม่โหลดโปรเจกต์ให้ bin/rails console — model · ฐานข้อมูล · route · helper มาครบ

เรื่องน่ารู้: node inspect ใช้ตัวอักษร n s c ชุดเดียวกับ debugger ของ Ruby (ที่จะเจอในหัวข้อ 2) — ผมเปิด help ของมันดูจริง ได้บรรทัดเหล่านี้:

2 · debugger ตัวแรก — สคริปต์ Ruby ล้วน ไม่มี Rails

เริ่มจากที่เล็กที่สุดก่อน เพื่อจะได้เห็นแค่ debugger ไม่มีอะไรของ Rails มาปน
ไฟล์ shout.rb (สร้างที่ไหนก็ได้): 

# shout.rb
require "debug"

def shout(name)
  msg = name.upcase
  msg + "!"
end

greeting = "hello"
debugger
result = shout(greeting)
puts result

มีของใหม่แค่สองบรรทัด: require "debug" โหลด gem เข้ามา · debugger บอกว่า "มาถึงตรงนี้แล้วหยุด เปิดช่องให้ฉันพิมพ์"
รันด้วย ruby shout.rb ตามปกติ — โปรแกรมไม่จบ แต่ค้างอยู่แบบนี้: 

$ ruby shout.rb

     4|   msg = name.upcase
     5|   msg + "!"
     6| end
     7|
     8| greeting = "hello"
=>   9| debugger

    11| puts result
=>#0	<main> at shout.rb:9
(rdbg)

อ่านจอนี้ทีละส่วน:

  • => 9| — ลูกศรชี้บรรทัดที่หยุดอยู่
  • =>#0 <main> at shout.rb:9 — ตอนนี้อยู่ใน "ชั้น" ไหนของการเรียกฟังก์ชัน · <main> แปลว่ายังอยู่นอกทุก method
  • (rdbg) — prompt ของ debugger รอคุณพิมพ์

ที่ prompt นี้คุณพิมพ์ได้สองแบบ: คำสั่งของ debugger (ตารางข้างล่าง) หรือโค้ด Ruby อะไรก็ได้ เช่น greeting.length แล้วจะได้ผลทันที
คำสั่งสี่ตัวที่สไลด์หน้า 67 ให้มา คำอธิบายคัดจาก help ในตัว debugger เอง:

พิมพ์help ของจริงบอกว่าภาษาคน
nStep over. Resume the program until next line. ไปบรรทัดถัดไป · ถ้าบรรทัดนี้เรียก method ก็รัน method นั้นจบทั้งก้อน ไม่เข้าไปดู
sStep in. Resume the program until next breakable point. ถ้าบรรทัดนี้เรียก method ให้มุดเข้าไปข้างใน method นั้น
cResume the program. ปล่อยให้วิ่งต่อตามปกติ (จนกว่าจะเจอ debugger ตัวถัดไป)
infoShow information about current frame (local/instance variables and defined constants). ขอดูตัวแปรทั้งหมดที่มองเห็นจากตรงนี้ในทีเดียว

สามอย่างที่ควรสังเกต:

  • ข้อความ # command · # next command ที่ต่อท้ายสิ่งที่คุณพิมพ์ ไม่ใช่สิ่งที่ผมพิมพ์เพิ่ม — debugger เขียนเป็นตัวจาง ๆ ให้เอง เพื่อบอกว่ามันเข้าใจว่าคุณสั่งคำสั่ง ไม่ใช่โค้ด Ruby
  • info ครั้งแรกเห็น result = nil ทั้งที่บรรทัด 10 ยังไม่รัน · Ruby จองชื่อตัวแปรไว้ตั้งแต่อ่านไฟล์ ค่าเริ่มเลยเป็น nil (ทวนเรื่อง nil ได้ที่บทเรียน 94)
  • หลัง s มีสองชั้น: #0 คือใน shout · #1 คือคนที่เรียกมันมา · และบอกค่า argument ให้ด้วย name="hello"

ตอนนี้หยุดอยู่ที่บรรทัด 4 ใน shout (ลูกศรชี้ที่ msg = name.upcase) แล้วพิมพ์:

(rdbg) info

ตัวแปร msg จะมีค่าอะไร — "HELLO" หรืออย่างอื่น?

ผลรันจริง — msg ยังเป็น nil:

(rdbg) info    # command
%self = main
name = "hello"
msg = nil

เพราะลูกศรชี้บรรทัดที่ "กำลังจะรัน" ไม่ใช่บรรทัดที่ "รันไปแล้ว" · ต้องกด n อีกครั้งให้บรรทัด 4 ทำงานก่อน แล้วถามใหม่: 

(rdbg) n    # next command
…
=>   5|   msg + "!"
…
(rdbg) info    # command
%self = main
name = "hello"
msg = "HELLO"
(rdbg) c    # continue command
HELLO!

นี่คือกับดักอันดับหนึ่งของคนเพิ่งใช้ debugger ทุกภาษา — เห็นค่าเป็น nil แล้วตกใจว่าโค้ดพัง ทั้งที่แค่ยังไม่ได้รันบรรทัดนั้น · c ตัวสุดท้ายปล่อยให้โปรแกรมวิ่งต่อจนพิมพ์ HELLO! แล้วจบ

⏸ เทียบให้เห็นภาพ — กดหยุดหนังแล้วดูทีละเฟรม

debugger คือปุ่ม pause ที่คุณฝังไว้ในหนังล่วงหน้า · พอหนังเล่นมาถึงฉากนั้น ภาพจะค้าง แล้วคุณทำได้สี่อย่าง: n = เลื่อนไปทีละฉาก · s = ซูมเข้าไปในฉากย่อยที่ตัวละครเพิ่งเดินเข้าไป · info = ขอรายชื่อตัวละครทุกตัวในฉากพร้อมของที่ถืออยู่ · c = เล่นต่อ
เทียบกับ puts: เหมือนถ่ายรูปไว้ล่วงหน้าแค่บางมุม ถ้ามุมที่อยากเห็นไม่ได้ถ่ายไว้ ต้องกลับไปถ่ายหนังใหม่ทั้งเรื่อง

ที่ไม่เหมือนกัน: หนังที่ถูก pause ไม่มีใครรอ แต่โปรแกรมที่ถูกหยุดมีคนรออยู่จริง — หัวข้อถัดไปจะเห็นว่า request ที่ค้างใน debugger ทำให้ฝั่งเบราว์เซอร์หมุนติ้วไป 23 วินาที · และอีกข้อ: ตอน pause คุณพิมพ์โค้ดใหม่แทรกลงไปได้ (เช่น greeting.length) ซึ่งหนังทำไม่ได้ · โค้ดที่แทรกนั้นรันจริง ถ้ามันไปแก้ข้อมูล ข้อมูลก็เปลี่ยนจริง

🗣 ศัพท์ที่เพิ่งเรียนไป
breakpoint
จุดที่สั่งให้โปรแกรมหยุด · ใน Ruby คือบรรทัด debugger (หรือชื่อเล่น binding.break · binding.b) · พิมพ์บอก AI ได้ว่า “I put a debugger breakpoint in the controller, here is the info output” แล้วแปะผล info ให้มันดู ได้คำตอบตรงกว่าการเล่าเป็นคำพูด
step over / step into
n กับ s · ต่างกันแค่ตอนบรรทัดนั้นเรียก method — over ข้ามไป · into มุดเข้าไป · ถาม senior ได้ว่า “ตรงนี้ควร step into หรือ step over — โค้ดข้างในเป็นของเราหรือของ library” เพราะ step into เข้าไปในโค้ดของ Rails จะหลงอยู่ในนั้นนาน
frame / backtrace
"ชั้น" ของการเรียก method ที่เรียงซ้อนกันอยู่ (#0 คือชั้นที่หยุดอยู่ #1 คือคนที่เรียกมันมา) · ทั้งกองเรียกว่า backtrace · ดูทั้งกองด้วยคำสั่ง bt · ถาม senior ได้ว่า “frame #1 มาจากไหน ทำไม method นี้ถูกเรียก”
rdbg
ชื่อโปรแกรมของ gem debug · prompt (rdbg) ที่เห็นมาจากชื่อนี้ · rdbg --help มีโหมดอื่นอีก เช่น -A (attach เข้าโปรเซสที่รอ debugger อยู่) · วันแรกไม่ต้องใช้ แค่รู้ว่าเวลาคนพูด "rdbg" คือตัวเดียวกับ debugger

ข้อ 1 · debugger หยุดอยู่ที่บรรทัด result = shout(greeting) และคุณอยากเห็นทีละบรรทัดว่าข้างใน shout ทำอะไร ต้องพิมพ์อะไร?

ตัวเลือกที่ 2 ถูก — s (step in) พาเข้าไปหยุดที่บรรทัดแรกของ shout พร้อมโชว์ name="hello"

ตัวเลือกที่ 1 ผิด เพราะ n คือ step over — ผมรันจริงแล้ว มันรัน shout จบทั้งก้อน แล้วไปหยุดที่ puts result โดย info บอก result = "HELLO!" เลย ไม่ได้เห็นข้างใน · ตัวเลือกที่ 3 ผิด เพราะ c ปล่อยให้วิ่งจนจบ ได้ HELLO! แล้วโปรแกรมปิดไป · ตัวเลือกที่ 4 ผิด เพราะ info แค่ดู ไม่ได้เดิน — ลูกศรยังอยู่ที่เดิม

จุดที่ต้องจำ: n = ข้ามหัว method · s = มุดเข้า method · ต่างกันแค่ตอนบรรทัดนั้นมีการเรียก method

3 · debugger ใน Rails จริง — โค้ดสไลด์หน้า 67

ทีนี้เอาไปใส่ในแอปจริง · method index ตามสไลด์หน้า 67 ทุกตัวอักษร (สไลด์โชว์แค่ def index … end · ผมห่อด้วย class PostsController ให้เป็นไฟล์ที่รันได้จริง · route resources :posts, only: [:index] กับ view app/views/posts/index.html.erb ที่วนพิมพ์ชื่อโพสต์ ทำตามแบบในบทเรียน 101–103): 

# app/controllers/posts_controller.rb
class PostsController < ApplicationController
  def index
    @posts = Post.all
    debugger        # <- หยุดตรงนี้
    render :index
  end
end

สังเกตว่าไม่มี require "debug" เหมือนตอนสคริปต์ล้วน · เพราะ Gemfile ที่ rails new สร้างให้มีบรรทัดนี้อยู่แล้ว (ที่บทเรียน 98อ่าน Gemfile ไปทีละบรรทัด): 

group :development, :test do
  # See https://guides.rubyonrails.org/debugging_rails_applications.html#debugging-with-the-debug-gem
  gem "debug", platforms: %i[ mri windows ], require: "debug/prelude"
  …
end

require: "debug/prelude" แปลว่า "ตอนแอปบูต โหลดแค่ ชื่อ debugger ไว้ก่อน ตัว debugger เต็ม ๆ ค่อยโหลดตอนมีคนเรียกจริง" · และสังเกต group :development, :test — ไม่มี production (จำไว้ อีกเดี๋ยวใช้)

ตัวเลือกที่ 3 ถูก — log บอกตรง ๆ ว่า Blocked hosts: www.example.com · แก้ด้วย app.host! "localhost" หรือส่ง headers: { "Host" => "localhost" } แล้วได้ 200 จริง

ตัวเลือกที่ 1 ผิด เพราะ app ไม่ต้องใช้ server เลย (ผมยิงได้ 200 ทั้งที่ไม่มี server เปิดอยู่) · ตัวเลือกที่ 2 ผิด เพราะถ้า route ไม่มีจะได้ 404 ไม่ใช่ 403 · console โหลด route ให้ตั้งแต่บูต · ตัวเลือกที่ 4 ผิด เพราะยิงจาก console ใน development ได้ — ยิงซ้ำหลัง host! ใน session เดิมก็ผ่าน

จุดที่ต้องจำ: เจอ 403 จาก app.get ให้นึกถึง Host ก่อนอย่างอื่น · 403 ≠ 404

🗣 ศัพท์ที่เพิ่งเรียนไป
transaction / rollback
transaction คือ "ก้อนงาน" ที่ฐานข้อมูลรับประกันว่าจะสำเร็จทั้งก้อนหรือไม่เกิดเลย · COMMIT = ยืนยัน · rollback = ยกเลิกทั้งก้อน · --sandbox คือ transaction ใหญ่ครอบทั้ง session · Day 2 จะเจอคำนี้อีกเยอะ · ถาม senior ได้ว่า “อันนี้ต้องห่อ transaction ไหม ถ้าพังครึ่งทางข้อมูลจะเป็นยังไง”
sequence
ตัวนับเลข id อัตโนมัติของ PostgreSQL · ไม่ถอยตาม rollback จึงทำให้ id กระโดดได้ · พิมพ์บอก AI ได้ว่า “Postgres sequence gaps after rollback — is this expected?” (คำตอบคือ ใช่ ปกติ)
environment (RAILS_ENV)
ชุด config ที่แอปใช้ — development · test · production · -e คือการเลือกชุด · ถาม senior ได้ว่า “ทีมเราเข้า console ของ production ยังไง ต้องขอสิทธิ์ใคร มีบังคับ sandbox ไหม” คำตอบนี้ต้องรู้ก่อนวันที่ต้องแก้ข้อมูลกลางดึก
dbconsole / psql
dbconsole แค่เปิดโปรแกรมอื่นให้ โดยกรอกชื่อ DB / user / host จาก database.yml · โปรแกรมนั้น (psql) ต้องติดตั้งเอง · พิมพ์บอก AI ได้ว่า “rails dbconsole says Couldn't find database client: psql — how do I install only the client on macOS”

ข้อ 4 · ในตารางมี 4 แถว id สูงสุดคือ 4 · เปิด bin/rails console --sandbox สร้างโพสต์ใหม่ (ได้ id 5) แล้ว exit · จากนั้นนับแถว และสร้างโพสต์ใหม่นอก sandbox จะเป็นยังไง?

ตัวเลือกที่ 1 ถูก — ผมรันจริง: ออกจาก sandbox แล้ว Post.count ได้ 4 · โพสต์ที่สร้างหลังจากนั้นได้ id 6

ตัวเลือกที่ 2 ผิดครึ่งเดียว — จำนวนแถวถอยจริง แต่ตัวนับ id ของ PostgreSQL ไม่ถอยตาม transaction · ตัวเลือกที่ 3 ผิด เพราะใน sandbox create! ไม่ได้ COMMIT จริง แค่ทำ SAVEPOINT ใน transaction ใหญ่ที่เปิดไว้ตั้งแต่ต้น · ตัวเลือกที่ 4 ผิด เพราะ exit สั่ง rollback ให้เอง — ข้อความตอนเปิดบอกไว้แล้วว่า rolled back on exit

จุดที่ต้องจำ: sandbox คืนข้อมูลครบ แต่ไม่คืนเลข id · และอย่าเปิดค้างนาน

Day 2 (Active Record · PostgreSQL · CRUD) จะใช้ console หนักมาก — แทบทุกเรื่องจะเริ่มจาก "พิมพ์ใน console ดูว่าได้ SQL อะไร" · บทนี้แค่ต้องการให้คุณเปิด–ออก–อ่าน prompt–อ่าน SQL ที่โผล่มาได้คล่องมือ ส่วน Post.where · find · association ทั้งหลาย รอวันพรุ่งนี้

🎯 ภารกิจ — ลองเครื่องมือทั้งสองชิ้นกับ wongnok_blog ของคุณเอง

  1. ถ้ายังไม่มี model Post: bin/rails g model Post title:string แล้ว bin/rails db:migrate
  2. เปิด bin/rails console สร้างโพสต์ 3 อันด้วย Post.create! · จดหน้าตา prompt ของคุณไว้ (ชื่อแอปอะไร · env สีอะไร)
  3. เพิ่ม route resources :posts, only: [:index] · controller ตามสไลด์หน้า 67 (มี debugger) · view ที่วนพิมพ์ post.title
  4. รัน bin/rails server เปิด /posts ในเบราว์เซอร์ · ในเทอร์มินัลของ server พิมพ์ info แล้วตอบให้ได้ว่า ตัวแปรตัวไหนเป็นของคุณ · ลอง n หนึ่งครั้ง แล้ว c · สังเกตเลข Completed 200 OK in …ms
  5. เปิด bin/rails console --sandbox สั่ง Post.destroy_all · exit · เปิด console ปกตินับใหม่
  6. พิสูจน์ว่าสะอาดก่อน commit: ลบบรรทัด debugger ออก แล้วรัน bin/rubocop --only Lint/Debugger ให้ได้ no offenses detected · และใน console ยิง app.get "/posts", headers: { "Host" => "localhost" } ให้ได้ 200

ทำครบแล้วตอบก่อนกดเฉลย: ทำไมข้อ 4 เลข Completed … in …ms ถึงสูงผิดปกติ และถ้าลบ debugger แล้วยิงใหม่ เลขนี้จะเหลือประมาณเท่าไร?

เลขสูงเพราะ request ถูกนับเวลารวมช่วงที่ค้างอยู่ใน debugger — ตั้งแต่เข้า controller จนกด c · ของผมได้ Completed 200 OK in 23675ms ทั้งที่งานจริงใช้ไม่กี่สิบ ms · พอลบ debugger แล้วยิงผ่าน app.get ได้ Completed 200 OK in 56ms (ของคุณจะต่างไปบ้าง แต่ควรอยู่หลักสิบถึงร้อย ms)

ผลที่ควรเห็นในแต่ละข้อ (จากเครื่องที่ใช้ตรวจ):

  • ข้อ 2 — prompt wongnok-blog(dev):001> · dev สีน้ำเงิน
  • ข้อ 4 — info โชว์ตัวแปร @_… ของ Rails ยาวเหยียด · ของคุณมีแค่ @posts (เป็น ActiveRecord::Relation) · n พาไปบรรทัด render :index
  • ข้อ 5 — ถ้านับใน sandbox หลัง destroy_all จะได้ 0 · ออกมานับใหม่ได้เท่าเดิม
  • ข้อ 6 — ผลจริงของผม:
