จาก bin/rails server ถึง HTML — ลำดับการ boot, วงจร request และ MVC

~25 นาที · ควรผ่าน บทเรียน 98 (rails new · โครงสร้าง) และ บทเรียน 99 (naming convention) มาก่อน · ถ้าลืม middleware ของ Gin ทวนได้ที่ บทเรียน 39

ตอนเขียน Go คุณเห็นทุกอย่างกับตา: main() สร้าง router · ลง route · ใส่ middleware · แล้วสั่ง r.Run()
พอมา Rails คุณพิมพ์ bin/rails server บรรทัดเดียว แล้วเว็บก็ขึ้นเลย — ไม่มี main() ให้อ่าน หลายคนเลยรู้สึกว่า Rails เป็นกล่องดำ
บทนี้จะเปิดกล่องนั้นตามสไลด์หน้า 49–53: ไฟล์ไหนถูกอ่านก่อนหลังตอน boot · request หนึ่งตัวเดินผ่านอะไรบ้างกว่าจะกลายเป็น HTML · และ Model / View / Controller แบ่งงานกันยังไง
ผมไม่ได้แค่อ่านสไลด์แล้วเล่าต่อ — ผมแปะป้ายลงในไฟล์ config ทุกไฟล์แล้วเปิด server จริงดูว่าป้ายไหนโผล่ก่อน และเจอจุดที่ของจริงไม่ตรงกับสไลด์ — ลำดับ boot (หัวข้อ 2) · CSRF ที่สไลด์จัดไว้ใน middleware (หัวข้อ 6) · และ status 422 ที่สไลด์สองหน้าเขียนไม่ตรงกัน (หัวข้อ 7)

1 · พิมพ์ bin/rails server แล้วเกิดอะไรขึ้น — 7 ขั้นของสไลด์หน้า 49

ก่อนที่ server จะตอบ request แรกได้ มันต้องเตรียมตัวก่อน — โหลด gem · ตั้งค่า · เตรียมตาราง route · แล้วค่อยเปิดพอร์ตรอ ขั้นตอนนี้เรียกว่า boot
ใน Go คุณเขียนขั้นตอนนี้เองทั้งหมดใน main() · ใน Rails มันกระจายอยู่ในโฟลเดอร์ config/ ทีละไฟล์ แต่ละไฟล์ทำหน้าที่เดียว สไลด์หน้า 49 เรียงไว้แบบนี้:

#ไฟล์สไลด์บอกว่าบรรทัดสำคัญในไฟล์จริง
1config.ruจุดเริ่มจริง — บอก Rack ว่าแอปคืออะไร run Rails.application
2config/boot.rbตั้ง Bundler ให้โหลด gem ตาม Gemfile.lock require "bundler/setup"
3config/application.rbโหลด Rails แต่ละชิ้นที่เราใช้ + ตั้งค่าระดับแอป require "rails/all" · config.load_defaults 8.1
4config/environments/*.rbทับค่าเฉพาะ environment ที่กำลังรัน config.eager_load = false (development)
5config/initializers/*.rbรันไฟล์ทั้งหมดเรียงตามชื่อ 4 ไฟล์ที่ rails new สร้างให้
6config/routes.rbโหลดตาราง route ทั้งหมดเข้าหน่วยความจำ Rails.application.routes.draw do
7พร้อมรับ requestPuma เปิดพอร์ต 3000 port ENV.fetch("PORT", 3000) ใน config/puma.rb

อย่าเชื่อตารางนี้เพราะมันอยู่ในสไลด์ — เปิดไฟล์จริงดูทีละไฟล์ (ผมตัดคอมเมนต์ออกบางไฟล์ ไม่ได้แก้โค้ด):

① config.ru — ทั้งไฟล์มีแค่นี้

# This file is used by Rack-based servers to start the application.

require_relative "config/environment"

run Rails.application
Rails.application.load_server

สังเกตบรรทัดที่ 3: มัน require ไฟล์ config/environment — ไฟล์ที่ไม่มีในสไลด์ (เดี๋ยวหัวข้อ 2 จะเห็นว่ามันสำคัญแค่ไหน) · ส่วน run Rails.application คือการบอก Rack ว่า "แอปของฉันคือก้อนนี้ request มาเมื่อไหร่ให้ส่งเข้าก้อนนี้"

② config/boot.rb — ทั้งไฟล์

ENV["BUNDLE_GEMFILE"] ||= File.expand_path("../Gemfile", __dir__)

require "bundler/setup" # Set up gems listed in the Gemfile.
require "bootsnap/setup" # Speed up boot time by caching expensive operations.

bundler/setup ทำให้ require ทุกตัวหลังจากนี้เห็นเฉพาะ gem และเวอร์ชันที่ล็อกไว้ใน Gemfile.lock — เป้าหมายเดียวกับ go.mod + go.sum ที่ทำให้ go build ทุกเครื่องได้ dependency ชุดเดียวกัน (รายละเอียดว่า lock ของ Ruby เก็บอะไรบ้างอยู่ใน บทเรียน 98) · ส่วน bootsnap แค่ cache ให้ boot เร็วขึ้น (สไลด์ไม่ได้พูดถึง)

③ config/application.rb — ตัดคอมเมนต์ออก

require_relative "boot"

require "rails/all"

Bundler.require(*Rails.groups)

module WongnokBlog
  class Application < Rails::Application
    config.load_defaults 8.1
    config.autoload_lib(ignore: %w[assets tasks])
  end
end

สามบรรทัดที่ต้องรู้จัก: require "rails/all" โหลด Rails ทุกชิ้น (Active Record · Action Controller · Action View …) · Bundler.require โหลดทุก gem ใน Gemfile ให้อัตโนมัติ (เฉพาะกลุ่มของ environment ที่รันอยู่ · ใน Go ต้อง import ทีละตัว) · และ class Application < Rails::Application คือ "ตัวแอป" ที่ config.ru สั่ง run นั่นเอง (< คือ inheritance ที่เรียนใน บทเรียน 95)

④ config/environment.rb — ไฟล์ที่สไลด์ข้ามไป ทั้งไฟล์มีแค่นี้

# Load the Rails application.
require_relative "application"

# Initialize the Rails application.
Rails.application.initialize!

initialize! คือปุ่มสตาร์ทตัวจริง — ขั้น ④ และ ⑤ ของสไลด์ (environments กับ initializers) เกิดขึ้นข้างในการเรียกบรรทัดนี้

⑤ config/environments/development.rb — 10 บรรทัดแรก

require "active_support/core_ext/integer/time"

Rails.application.configure do
  # Settings specified here will take precedence over those in config/application.rb.

  # Make code changes take effect immediately without server restart.
  config.enable_reloading = true

  # Do not eager load code on boot.
  config.eager_load = false

คอมเมนต์บรรทัดที่ 4 พูดเรื่องเดียวกับสไลด์: ค่าในไฟล์นี้ทับค่าใน application.rb · ไฟล์ production.rb ตั้งสองค่าเดียวกันนี้กลับด้าน (enable_reloading = false · eager_load = true) — จำ eager_load ไว้ หัวข้อ 2 จะได้ใช้

☕ เทียบให้เห็นภาพ — เช็คลิสต์เปิดร้านกาแฟตอนเช้า

ก่อนเปิดประตูรับลูกค้า บาริสต้าต้องทำตามลำดับ: ติดป้ายหน้าร้านว่าร้านนี้คือร้านอะไร (config.ru) · เช็ควัตถุดิบให้ตรงใบสั่งของ (boot.rb + Gemfile.lock) · ตั้งเครื่องชงตามมาตรฐานแบรนด์ (application.rb) · ปรับตามกฎของสาขานี้ เช่นสาขาทดลองเปิดเมนูลับ (environments/*.rb) · ทำงานเตรียมย่อยทีละข้อตามลำดับในเช็คลิสต์ (initializers/*.rb) · ติดเมนูหน้าเคาน์เตอร์ (routes.rb) · แล้วค่อยเปิดประตู (Puma เปิดพอร์ต)

ที่ไม่เหมือนกัน: เช็คลิสต์ร้านกาแฟเป็นรายการเรียงตรง ๆ ทำข้อ 1 จบแล้วค่อยข้อ 2 · แต่ไฟล์ของ Rails เรียกต่อกันเป็นทอด ๆ ด้วย require (config.ru เรียก environment.rb ที่เรียก application.rb ที่เรียก boot.rb) — ลำดับที่ "เปิดไฟล์" กับลำดับที่ "โค้ดในไฟล์ได้รันจริง" จึงไม่ใช่ลำดับเดียวกัน · และการติดเมนู (routes) ใน development ไม่ได้เกิดก่อนเปิดประตู หัวข้อถัดไปพิสูจน์ให้ดู

🗣 ศัพท์ที่เพิ่งเรียนไป
boot
ช่วงที่แอปเตรียมตัวก่อนพร้อมรับ request · ถ้าแอปเปิดช้า คนจะพูดว่า "boot ช้า" · ถาม senior ได้ว่า “ถ้าจะใส่โค้ดที่ต้องรันครั้งเดียวตอน boot ทีมนี้ใส่ไว้ใน initializer หรือที่อื่น”
Rack · config.ru
Rack คือข้อตกลงกลางระหว่าง web server (เช่น Puma) กับเว็บแอป Ruby ทุกตัว · config.ru คือไฟล์ที่บอก server ว่า "แอปคือก้อนไหน" · เทียบกับ Go คือ interface http.Handler ที่ทุก router ต้องทำตาม · พิมพ์ถาม AI ได้ว่า “explain the Rack interface: call(env) returning status, headers, body”
Bundler · Gemfile.lock
Bundler คือตัวจัดการ gem · Gemfile.lock ล็อกเวอร์ชันทุก gem ให้ตรงกันทุกเครื่อง (รุ่นที่ล็อกแบบ package-lock.json + checksum แบบ go.sum ในไฟล์เดียว ตามที่บทเรียน 98 เปิดดู) · ถาม senior ได้ว่า “Gemfile.lock ต้อง commit ไหม” — สำหรับแอป คำตอบคือต้อง
environment (RAILS_ENV)
โหมดที่แอปกำลังรัน: development · test · production · แต่ละโหมดมีไฟล์ใน config/environments/ ของตัวเอง · พิมพ์บอก AI ได้ว่า “this setting should only apply in production, put it in config/environments/production.rb”
initializer
ไฟล์ใน config/initializers/ ที่ Rails รันให้ครั้งเดียวตอน boot เรียงตามชื่อไฟล์ · เป็นที่ตั้งค่า gem ต่าง ๆ · คอมเมนต์บรรทัดแรกของ inflections.rb เตือนไว้เองว่า Be sure to restart your server when you modify this file. — แก้ initializer ต้อง restart server
Puma
web server ที่ Rails ใช้เป็นค่าเริ่มต้น · เป็นตัวที่เปิดพอร์ตแล้วรับ request จริง · ตั้งค่าที่ config/puma.rb

// main.go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

type GreetingsHandler struct {
	visits int
}

func (h *GreetingsHandler) Index(w http.ResponseWriter, r *http.Request) {
	h.visits++
	fmt.Fprintf(w, "handler %p visits: %d", h, h.visits)
}

func main() {
	h := &GreetingsHandler{} // สร้างครั้งเดียวตอน start
	mux := http.NewServeMux()
	mux.HandleFunc("GET /hello", h.Index)

	for i := 0; i < 3; i++ {
		rec := httptest.NewRecorder()
		mux.ServeHTTP(rec, httptest.NewRequest("GET", "/hello", nil))
		fmt.Println(rec.Body.String())
	}
}

controller ของ Rails เหมือนใบคำร้องเปล่าที่เคาน์เตอร์ — ลูกค้าทุกคนหยิบใบใหม่ กรอกเฉพาะเรื่องของตัวเอง ยื่นเสร็จพนักงานก็เก็บเข้าแฟ้ม ไม่มีใครเห็นสิ่งที่ลูกค้าคนก่อนกรอก · handler struct ของ Go เหมือนไวท์บอร์ดแผ่นเดียวหน้าเคาน์เตอร์ — ทุกคนเขียนลงแผ่นเดียวกัน ถ้าสองคนเขียนพร้อมกันก็ทับกันมั่ว

5 · implicit render — ไม่เขียน render แต่ได้ HTML ทั้งหน้า

ดู controller ในหัวข้อ 4 อีกที: ไม่มีบรรทัดไหนสั่งให้ส่งอะไรกลับไปเลย · ใน Go ถ้า handler ไม่เขียนอะไรลง w เลย (func(w http.ResponseWriter, r *http.Request) {}) ผลรันจริงด้วย httptest คือ status=200 body="" — ได้หน้าเปล่า · แต่ Rails มีกติกา: ถ้า action จบโดยไม่ได้ render หรือ redirect_to อะไรเลย ให้ไปหา view ที่ชื่อตรงกับ controller และ action เอง — เรียกว่า implicit render

Controller คือพนักงานเสิร์ฟ — รับออเดอร์จากโต๊ะ (request) · เดินไปบอกครัว · ยกชามมาเสิร์ฟ · ไม่ได้ลวกเส้นเอง · Model คือครัว — รู้สูตร รู้ว่าวัตถุดิบไหนหมด รู้ว่า "เส้นใหญ่แห้งไม่ใส่ผัก" ทำได้ไหม · ครัวไม่เคยเห็นหน้าลูกค้า (ไม่รู้จัก HTTP) · View คือการจัดชามก่อนเสิร์ฟ — วางผักโรยกระเทียมให้ดูน่ากิน แต่ไม่ได้ตัดสินว่าจะใส่อะไร

ที่ไม่เหมือนกัน: ในร้านจริง คนจัดชามอาจเดินเข้าครัวไปหยิบลูกชิ้นเพิ่มเองได้ · แต่ใน Rails View เดินเข้าครัวได้จริงด้วย (ERB เขียน Post.where(...) ได้ และมันทำงาน!) — ไม่มีอะไรห้าม เป็นแค่ข้อตกลงที่ทีมต้องรักษาเอง · ข้อนี้คือเหตุผลที่สไลด์เรียกมันว่าเส้นที่คนข้ามบ่อยที่สุด

🗣 ศัพท์ของ MVC
MVC (Model–View–Controller)
รูปแบบการแบ่งโค้ดเป็นสามส่วนตามหน้าที่ · ถาม senior ได้ว่า “ทีมนี้ยอมให้ logic อยู่ใน controller ได้แค่ไหน หรือต้องย้ายไป model / service object” — แต่ละทีมขีดเส้นไม่เท่ากัน
skinny controller, fat model
คำขวัญที่ชาว Rails ใช้บ่อย = controller บาง ๆ (ประสานงานอย่างเดียว) กฎธุรกิจไปอยู่ใน model · ตรงกับคำว่า "ควรบางที่สุด" ในสไลด์หน้า 52 · พิมพ์บอก AI ได้ว่า “refactor this to skinny controller, move the business rule into the model”
business logic / กฎธุรกิจ
กฎที่ยังเป็นจริงแม้จะไม่มีเว็บ เช่น "โพสต์ต้องมีชื่อเรื่อง" · ทดสอบง่าย ๆ ว่าถ้าย้ายไปทำเป็น CLI กฎนี้ยังต้องมีไหม — ถ้าต้องมี มันคือของ Model
instance variable (เป็นสะพาน C → V)
@posts ที่ตั้งใน action จะอ่านได้ใน view ของ action นั้น · ตัวแปร local ไม่ข้ามไป · ถาม AI ได้ว่า “why can the view see @posts but not a local variable posts”

กฎตัดสินจากสไลด์หน้า 52 ใช้ได้เกือบทุกครั้ง: ข้อมูลและกฎของธุรกิจ → Model · เกี่ยวกับ HTTP, params, session, redirect → Controller · หน้าตาล้วน ๆ → View · ลองใช้ดู:

5.  scope :published, -> { where.not(published_at: nil) }

#อยู่ที่เหตุผล
1M"โพสต์ต้องมีชื่อเรื่อง" เป็นกฎธุรกิจ · เป็นจริงแม้ไม่มีเว็บ
2Cparams มาจาก URL/HTTP — Model ห้ามรู้จัก
3Vหน้าตาล้วน ๆ แค่หยิบ @name มาแสดง
4Credirect_to คือคำสั่ง HTTP (ตอบ 303 ให้ browser ไปหน้าอื่น)
5Mนิยามว่า "โพสต์ที่เผยแพร่แล้ว" คืออะไร = กฎธุรกิจ + รู้จัก DB
6Vสร้างลิงก์บนหน้า (ผลจริง: <a href="/posts/1/edit">แก้ไข</a>)
7Cเลือกว่าจะ render view ไหนด้วย status อะไร = งานของคนประสานงาน
8V แต่ผิดที่มี query อยู่ใน view — ข้ามเส้นที่สไลด์หน้า 52 เตือน · ย้ายเงื่อนไขไปเป็นบรรทัดที่ 5 (scope ใน M) แล้วให้ C เขียน @posts = Post.published · view เหลือแค่ <% @posts.each do |post| %>

ผมรันทุกบรรทัดใน sandbox แล้ว (สร้าง model Post ชั่วคราว) — ทุกบรรทัดทำงานได้ (บรรทัดที่ 4 curl ได้ 303 ไปที่ /posts · บรรทัดที่ 7 ได้ 422) รวมถึงบรรทัดที่ 8 ซึ่ง render ออกมาเป็น <h2>ข้าวซอย</h2> ได้ตามปกติ · นั่นคือปัญหา: Rails ไม่ฟ้องเวลาโค้ดอยู่ผิดชั้น คุณต้องรู้เอง · ถ้าบรรทัดนี้ถูกก็อปไปอีก 3 หน้า แล้ววันหนึ่งความหมายของ "เผยแพร่แล้ว" เปลี่ยน คุณต้องไล่แก้ 3 view · แต่ถ้าอยู่ใน scope แก้ที่เดียวจบ

เจอบรรทัด <% Post.where.not(published_at: nil).each do |post| %> ใน index.html.erb — หน้าเว็บแสดงผลถูกต้อง แต่ควรแก้ยังไง?

ตัวเลือกที่ 1 ถูก · "โพสต์ที่เผยแพร่แล้ว" เป็นกฎธุรกิจ → Model · การเลือกว่าหน้านี้แสดงโพสต์ชุดไหน → Controller · view เหลือแค่วนแสดง @posts (ตรงกับภาพสไลด์หน้า 53 ทุกขั้น)

ตัวเลือกที่ 2 แก้ผิดทาง — ให้ Controller ทำ HTML ก็ข้ามเส้นอีกเส้น (C ไปทำงานของ V) · ตัวเลือกที่ 3 ครึ่งจริงครึ่งหลอก: view query ได้จริง แต่ไม่ได้เร็วกว่า (SQL ตัวเดียวกัน) และสไลด์บอกตรง ๆ ว่า "ไม่ควรมี query อยู่ในนี้" · ตัวเลือกที่ 4 ผิด — routes.rb จับคู่ URL กับ action อย่างเดียว ไม่ได้แตะข้อมูล · จุดที่ต้องจำ: โค้ดที่ทำงานได้ไม่ได้แปลว่าอยู่ถูกชั้น — กฎ → M · HTTP → C · หน้าตา → V
