2 · ทายก่อนลงมือ: สลับลำดับ route แล้วเกิดอะไร

ขั้นที่ 4 ของ Lab สั่งว่า “เพิ่ม route /about/:id แล้วลองสลับลำดับดูว่าเกิดอะไร” · สไลด์หน้า 59 สอนไว้ว่า Rails ไล่จากบนลงล่าง และหยุดที่เส้นแรกที่ match · ลองเอาความรู้นั้นมาทายก่อน (ผมเพิ่ม action ชื่อ member ไว้รับ /about/:id — ชื่อนี้ผมตั้งเอง สไลด์ไม่ได้กำหนด) 

# แบบ A — /about อยู่บน
get "/about",     to: "pages#about"
get "/about/:id", to: "pages#member"

# แบบ B — สลับสองบรรทัด
get "/about/:id", to: "pages#member"
get "/about",     to: "pages#about"

เปิด /about กับ /about/7 — แบบ B ได้ผลต่างจากแบบ A ตรงไหน?

ไม่ต่างกันเลยสักบรรทัด · ผลรันจริง ยิงห้า URL กับทั้งสองแบบ:

--- แบบ A (/about อยู่บน)
/about               <p>Hello PEA</p> [200]
/about/7             <p>id = 7 (String)</p> [200]
/about/nan           <p>id = nan (String)</p> [200]
/about/              <p>Hello PEA</p> [200]
/about/7?name=Nan    <p>id = 7 (String)</p> [200]
--- แบบ B (/about/:id อยู่บน)
/about               <p>Hello PEA</p> [200]
/about/7             <p>id = 7 (String)</p> [200]
/about/nan           <p>id = nan (String)</p> [200]
/about/              <p>Hello PEA</p> [200]
/about/7?name=Nan    <p>id = 7 (String)</p> [200]

เหตุผล: /about/:id ต้องมีอะไรสักอย่างต่อท้าย /about/ ถึงจะ match · ส่วน /about ไม่มีอะไรต่อท้าย → ไม่มี URL ไหนเลยที่สองเส้นนี้แย่งกัน ลำดับจึงไม่มีผล (สังเกต /about/ ที่มี / ปิดท้าย ก็ยังเข้า about ทั้งสองแบบ)

ถ้าคุณทาย “แบบ B จะพัง” ไม่ต้องรู้สึกแย่ — ผมเองตอนวางโจทย์บทนี้ก็คาดว่าจะเห็นอะไรเปลี่ยน
“ลำดับสำคัญ” จริงเฉพาะเมื่อมีสองเส้นที่ match URL เดียวกันได้ · หัวข้อถัดไปจะทำให้มันชนกันจริง ๆ

ทำให้ชนกันจริง: เพิ่ม /about/team

เพิ่มเส้นที่เจาะจง (static segment) ไว้ใต้เส้นที่กว้างกว่า — แบบเดียวกับ /posts/popular ในสไลด์หน้า 59: 

# config/routes.rb
get "/about",      to: "pages#about"
get "/about/:id",  to: "pages#member"
get "/about/team", to: "pages#team"     # ← อยู่ล่าง :id
$ curl ... (ผลจริง)
/about         <p>Hello PEA</p> [200]
/about/7       <p>id = 7 (String)</p> [200]
/about/team    <p>id = team (String)</p> [200]      # ← ไม่ได้หน้า team

# log ของ server ตอนเปิด /about/team
Started GET "/about/team" for 127.0.0.1 at 2026-11-01 00:16:14 +0700
Processing by PagesController#member as */*
  Parameters: {"id" => "team"}

/about/team ตกไปที่ member โดย params[:id] เป็นสตริง "team" · หน้า team ไม่มีวันถูกเรียก และไม่มีอะไรเตือนเลย — แม้แต่ตาราง bin/rails routes ก็โชว์เส้นนี้ปกติ: 

$ bin/rails routes -c pages
    Prefix Verb URI Pattern           Controller#Action
     about GET  /about(.:format)      pages#about
           GET  /about/:id(.:format)  pages#member
about_team GET  /about/team(.:format) pages#team

ย้ายเส้น team ขึ้นไปไว้เหนือ :id แล้วยิงใหม่: 

/about         <p>Hello PEA</p> [200]
/about/7       <p>id = 7 (String)</p> [200]
/about/team    <p>this is the team page</p> [200]

กฎที่ใช้ได้จริง: เส้นที่เจาะจงไว้บน เส้นที่กว้างไว้ล่าง (ตรงกับฝั่ง “ถูก” ของสไลด์หน้า 59) · และถ้าสองเส้นไม่มีทางแย่ง URL เดียวกันได้ จะเรียงยังไงก็ได้

📮 เทียบกับของจริง

routes.rb เหมือนกระดาษกฎแผ่นเดียวของพนักงานคัดแยกจดหมาย ที่อ่านจากบนลงล่าง เจอข้อแรกที่เข้าก็โยนซองลงช่องนั้นทันที ไม่อ่านข้อที่เหลือ
กฎข้อ 1 “ซองจ่าหน้า ฝ่ายบุคคล / ชื่อใครก็ได้ → ช่อง A” · กฎข้อ 2 “ซองจ่าหน้า ฝ่ายบุคคล / หัวหน้าฝ่าย → ช่อง B” → จดหมายถึงหัวหน้าฝ่ายลงช่อง A หมด เพราะ “หัวหน้าฝ่าย” ก็เป็น “ชื่อใครก็ได้” แบบหนึ่ง
แต่ถ้ากฎสองข้อคือ “ซองที่ไม่มีชื่อผู้รับ” กับ “ซองที่มีชื่อผู้รับ” — ไม่มีซองไหนเข้าได้ทั้งสองข้อ จะเขียนข้อไหนก่อนก็ได้ผลเหมือนกัน (นี่คือ /about กับ /about/:id)

ที่ไม่เหมือนกัน: พนักงานจริงทำงานไปเดือนนึงแล้วเห็นว่าช่อง B ว่างตลอด ก็จะเอะใจแล้วถามหัวหน้า
Rails ไม่เอะใจ — ไม่เตือนตอน boot ไม่เตือนใน bin/rails routes ไม่เตือนตอนมี request เข้า · เส้นที่ถูกบังจะนั่งเงียบอยู่ในไฟล์ไปตลอด จนกว่าจะมีคนสงสัยว่าทำไมหน้า team ไม่เคยขึ้น
และพนักงานอ่านแค่หน้าซอง แต่ Rails ดูทั้ง HTTP method กับ path — GET /posts กับ POST /posts คือคนละกฎ (สไลด์หน้า 54)

🗣 ศัพท์เรื่องลำดับ route
dynamic segment · static segment
ส่วนของ path ที่ขึ้นต้นด้วย : (เช่น :id) คือ dynamic — รับค่าอะไรก็ได้แล้วใส่ลง params · ส่วนที่เป็นตัวอักษรตายตัว (เช่น team) คือ static · ถาม senior ได้ว่า “เส้นนี้มี dynamic segment ที่บัง static route ข้างล่างอยู่หรือเปล่า”
first match wins
กฎของ Rails router: เส้นแรกที่ match ชนะ เส้นที่เหลือไม่ถูกดูต่อ · คำนี้ใช้คุยได้กับ router แทบทุกตัว แต่อย่าเหมาว่าทุก framework เป็นแบบนี้ — พิมพ์ถาม AI ได้ว่า “Does this router use first-match or most-specific-match?” ก่อนจะย้ายความรู้นี้ไปใช้กับ framework อื่น
shadowed route (เส้นที่ถูกบัง)
เส้นที่ไม่มีวันถูกเรียกเพราะมีเส้นข้างบนกินหมด เช่น /about/team ใต้ /about/:id · เป็นคำที่คนใช้คุยกัน ไม่ใช่ชื่อ error ใน Rails (เพราะ Rails ไม่ฟ้อง) · บอก AI ได้ว่า “check my routes.rb for shadowed routes”
recognize_path
เมธอดที่ถาม router ตรง ๆ ว่า URL นี้จะไปไหน ไม่ต้องเปิด server · ใช้ใน console ได้: Rails.application.routes.recognize_path("/posts/popular") (ผลจริงอยู่ใน quiz ข้อ 4 ข้างล่าง) · เร็วกว่าเดาจากการอ่านไฟล์มาก

error ห้าตัวนี้เหมือนตราประทับบนพัสดุตีกลับ ที่บอกว่าส่งไม่ถึงเพราะอะไร:
(ก) “ไม่มีผู้รับชื่อนี้ในระบบ” — คนเขียนจ่าหน้าผิด (routes.rb) · (ข) “บ้านเลขที่ถูก แต่คนในบ้านชื่อไม่ตรงทะเบียน” · (ค) “ชื่อผู้รับถูก แต่ไม่มีบ้านเลขที่นี้” · (ง) “ผู้รับอยู่ แต่ไม่มีแผนกที่ระบุ — หมายถึงแผนกนี้หรือเปล่า?” · (จ) “ผู้รับอยู่ รับเรื่องแล้ว แต่ไม่มีของจะส่งกลับ”
คนที่อ่านตราประทับเป็น จะรู้ทันทีว่าต้องแก้จ่าหน้า หรือต้องโทรถามผู้รับ

ที่ไม่เหมือนกัน: ตราประทับของไปรษณีย์จริงคนละแบบก็คนละข้อความ แต่ Rails ใช้ตราเดียวกัน (MissingController) กับ (ก) และ (ค) ทั้งที่ผิดคนละไฟล์ — ต้องอ่านชื่อ constant ต่อท้ายถึงจะแยกได้

🗣 ศัพท์สำหรับคุยเรื่อง error
constant (ใน Ruby)
ชื่อที่ขึ้นต้นด้วยตัวพิมพ์ใหญ่ · ชื่อ class ก็เป็น constant — นั่นคือเหตุผลที่ error บอกว่า uninitialized constant PageController ไม่ใช่ “class not found” · พิมพ์ถาม AI ได้ว่า “Why does Rails say uninitialized constant for a controller that exists?”
autoloading · Zeitwerk
Rails ไม่ให้คุณเขียน require เอง · มันเดาไฟล์จากชื่อ constant ด้วยตัวโหลดชื่อ Zeitwerk (PagesController → pages_controller.rb) · ชื่อไม่ตรงกฎ = หาไม่เจอ · ถาม senior ได้ว่า “รัน bin/rails zeitwerk:check ใน CI ด้วยไหมครับ”
stack trace (backtrace)
รายการว่า error เกิดขึ้นระหว่างที่โค้ดไหนเรียกโค้ดไหนอยู่ · บรรทัดบนสุดคือจุดที่พัง บรรทัดล่างคือจุดเริ่ม · เวลาส่งให้ AI หรือ senior ให้ส่งบรรทัดชื่อ error + ข้อความ + 5–10 บรรทัดแรกของ trace ไม่ต้องส่งทั้งกอง
404 · 406 · 500 · 204
status ที่ Rails เลือกให้ error แต่ละแบบ (ทบทวนจากบทฝั่ง Go บท 34) · 500 = โค้ดฝั่งเราพัง · 404 = หาสิ่งที่ขอไม่เจอ · 406 = มีของ แต่ไม่มีในรูปแบบที่ขอ · 204 = สำเร็จแต่ไม่มีเนื้อหา · บอกเพื่อนในทีมได้ว่า “ได้ 204 ตอน curl แต่ 406 ในเบราว์เซอร์ น่าจะลืม view”

5 · กับดักเล็กสองตัวที่ Lab ไม่ได้บอก

/about?name= ได้ “Hello ” ไม่ใช่ “Hello PEA”

โค้ดตามสไลด์หน้า 60 คือ params[:name] || "PEA" · พอส่ง ?name= ที่ไม่มีค่า params[:name] ได้ สตริงว่าง "" ไม่ใช่ nil
และใน Ruby "" เป็นค่าจริง (เหมือน 0 — quiz ข้อ 2 ข้างล่าง) → || ไม่ไปหยิบ "PEA" → ได้ Hello ตามด้วยความว่างเปล่า · คนที่มาจาก TypeScript จะพลาดตรงนี้แน่ ๆ เพราะใน TS "" || "PEA" ได้ "PEA"

แก้ด้วย presence จาก Active Support (บท 94):

def about
  @name = params[:name].presence || "PEA"
end

3.days.ago ตอบเป็น UTC ไม่ใช่เวลาไทย

ตอนผมรัน นาฬิกาเครื่องคือ 1 พ.ย. 2026 00:17 (+07:00) · ย้อนไป 3 วันควรได้ 29 ต.ค. 00:17 เวลาไทย · แต่ console ตอบว่า 2026-10-28 17:17:51.188270000 UTC +00:00
มันเป็นเวลาเดียวกัน แค่บอกเป็นโซน UTC (ลบ 7 ชั่วโมง เลยตกไปเป็นวันที่ 28) — เพราะแอปที่ rails new สร้างใช้ time zone เป็น UTC โดยปริยาย: 

$ bin/rails runner 'p Time.zone.name; p 3.days.ago.class'

ActiveSupport::TimeWithZone

ไม่ใช่บั๊ก แต่ถ้าคุณเอา 3.days.ago ไปโชว์ให้ผู้ใช้ไทยดูตรง ๆ จะเห็นวันที่ผิดไปหนึ่งวันในบางช่วงของวัน · เรื่องตั้ง time zone ของแอปเก็บไว้ทีหลัง ตอนนี้แค่รู้ว่าค่าเริ่มต้นคือ UTC · และสังเกตบรรทัดที่สอง: ผลเป็น ActiveSupport::TimeWithZone ไม่ใช่ Time ธรรมดาของ Ruby — days กับ ago เป็น method ที่ Active Support เติมให้ Integer ตามที่สไลด์หน้า 37 เล่าไว้ (บท 97)

6 · Quiz ท้ายวัน (สไลด์หน้า 70–71)

สี่ข้อนี้ถอดมาจากสไลด์ตรง ๆ (ในสไลด์ให้ตอบ A–D ในแชท) · ผมรันพิสูจน์เฉลยทุกข้อก่อนใส่ — ผลจริงอยู่ในคำอธิบายหลังตอบ

ข้อ 1 · get "/hello", to: "greetings#index" → Rails จะไปหา view ที่ไฟล์ไหน?

ตัวเลือกที่ 2 ถูก · ผมพิสูจน์ด้วยการวางไฟล์ view ไว้ทีละที่ตามตัวเลือกทั้งสี่ แล้ว curl /hello · ตัวเลือกที่ 1, 3, 4 ได้ 204 (คือหาไฟล์ไม่เจอ — ดูหัวข้อ 4 ข้อ (จ)) · มีแค่ตัวเลือกที่ 2 ที่ได้ 200 พร้อม comment <!-- BEGIN app/views/greetings/index.html.erb ใน HTML
และถ้าลบไฟล์ทิ้งแล้วเปิดด้วยเบราว์เซอร์ หน้า error ของ Rails 8.1.4 เฉลยให้เองว่า “should have a corresponding view template in a file named app/views/greetings/index.html.erb”
ตัวเลือกที่ 1 เอาชื่อ URL (/hello) ไปตั้งชื่อไฟล์ — แต่ Rails ไม่สน URL เลย สนแค่ "greetings#index" · ตัวเลือกที่ 3 ใช้ชื่อ controller แต่ลืมว่า action คือชื่อไฟล์ ในโฟลเดอร์ ของ controller · ตัวเลือกที่ 4 ผิดสองชั้น: ใช้ชื่อ URL และอยู่นอก app/views/

จุดที่ต้องจำ: "controller#action" → app/views/controller/action.html.erb · URL ไม่เกี่ยวกับชื่อไฟล์ view เลย — เปลี่ยน /hello เป็น /hi ไฟล์ view ก็ยังเป็นตัวเดิม

ข้อ 2 · ใน Ruby if 0 จะเข้าเงื่อนไขไหม?

ตัวเลือกที่ 2 ถูก · ผลรันจริงบน Ruby 4.0.9 เทียบกับ node v24: 

$ ruby q2.rb       # if 0 ... else ... end
เข้า if
$ node -e 'if (0) { console.log("เข้า if") } else { console.log("ไม่เข้า") }'
ไม่เข้า

ใน Ruby มี falsy แค่ nil กับ false · !!0 ได้ true · !!"" ก็ได้ true (สไลด์หน้า 26 · บท 94)
ตัวเลือกที่ 1 คือกับดักของคนมาจาก TypeScript ตรง ๆ · ตัวเลือกที่ 3 ผิด — Ruby ไม่ error (ถ้ารันด้วย ruby -w จะมีแค่คำเตือน warning: literal in condition แล้วก็ยังเข้า if อยู่ดี) · ตัวเลือกที่ 4 ผิด — กติกา “มีแค่ nil กับ false ที่เป็นเท็จ” เขียนไว้ในเอกสารทางการของภาษา ไม่ได้เปลี่ยนตามเวอร์ชัน

จุดที่ต้องจำ: ใน Ruby 0 · "" · [] เป็นจริงทั้งหมด · อยากเช็คว่าเป็นศูนย์ใช้ .zero? · อยากเช็คว่าว่างใช้ .blank? / .presence (คือตัวแก้กับดักในหัวข้อ 5)

ข้อ 3 · posts.map(&:title) เท่ากับข้อไหน?

ตัวเลือกที่ 1 ถูก · ผมรันทั้งห้าแบบกับ posts สองตัว (Struct ที่มี title): 

p posts.map(&:title)              # => ["Hello Rails", "Draft"]
p posts.map { |p| p.title }       # => ["Hello Rails", "Draft"]
p posts.map { |p| :title }        # => [:title, :title]
p posts.select { |p| p.title }    # => [#<struct Post title="Hello Rails", published=true>, #<struct Post title="Draft", published=false>]
posts.title                       # NoMethodError: undefined method 'title' for an instance of Array

ตัวเลือกที่ 2 คืน symbol :title ตัวเดิมซ้ำทุกรอบ — ไม่ได้เรียก method · ตัวเลือกที่ 3 คืน post ทั้งตัว ที่ title เป็นค่าจริง (ซึ่งก็คือทุกตัว เพราะสตริงเป็นจริงเสมอ) ไม่ใช่รายการ title · ตัวเลือกที่ 4 เรียก title บน Array ซึ่งไม่มี method นี้ (บท 92 · สไลด์หน้า 21)

จุดที่ต้องจำ: &:ชื่อ = “เรียก method ชื่อนี้กับสมาชิกทุกตัว” · ใช้ได้เมื่อ block ทำแค่เรียก method ตัวเดียวโดยไม่ส่งอาร์กิวเมนต์

ข้อ 4 · route สองเส้นเรียงแบบนี้ — get "/posts/:id" → show แล้วบรรทัดถัดมา get "/posts/popular" → popular · เปิด /posts/popular จะเข้า action ไหน?

ตัวเลือกที่ 2 ถูก · ผลรันจริงในแอป Rails ตัวเดียวกับ Lab:

$ curl http://127.0.0.1:4105/posts/popular
show id=popular

$ bin/rails runner 'p Rails.application.routes.recognize_path("/posts/popular")'
{controller: "posts", action: "show", id: "popular"}

ตัวเลือกที่ 1 คือสิ่งที่ควรจะเป็น แต่ Rails ไม่ได้เลือกเส้นที่เจาะจงที่สุด — มันเลือกเส้นแรก · ตัวเลือกที่ 3 ผิด — server boot ปกติ bin/rails routes ก็ไม่เตือน · ตัวเลือกที่ 4 ผิด — หนึ่ง request เข้าได้ action เดียว พอเจอเส้นแรกที่ match ก็หยุด

จุดที่ต้องจำ: เส้นแรกที่ match ชนะ และไม่มีใครเตือน · เส้นที่เจาะจงไว้บน เส้นที่มี :id ไว้ล่าง · ถ้าสองเส้นไม่มีทางแย่ง URL เดียวกัน (เช่น /about กับ /about/:id) ลำดับไม่มีผล
