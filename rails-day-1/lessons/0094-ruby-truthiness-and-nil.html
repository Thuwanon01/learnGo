Truthiness และ nil — 0 เป็นจริง, present? blank? และ ||=

~22 นาที · ควรผ่าน บทเรียน 93 (method ที่ลงท้ายด้วย ?) มาก่อน

คำถามง่าย ๆ ข้อเดียว — "ค่านี้นับว่าจริงไหม" — Go, TypeScript และ Ruby ตอบไม่เหมือนกันเลย
Go ไม่ยอมตอบ (compile ไม่ผ่าน) · TypeScript ถือว่า 0 กับ "" เป็นเท็จ · ส่วน Ruby ถือว่าทุกอย่างเป็นจริง ยกเว้น nil กับ false
สไลด์หน้า 26 เรียกเรื่องนี้ว่า "จุดที่คนมาจาก TypeScript เจ็บที่สุด" — เพราะเขียนผิดแล้ว ไม่มี error ไม่มี warning แค่หน้าเว็บโชว์ "มีคนดู 0 ครั้ง" เฉย ๆ
บทนี้จะรันให้ดูทีละค่า แล้วต่อด้วยเครื่องมือที่ Ruby กับ Rails ให้มารับมือกับ nil: &. · .nil? · ||= (ที่มีกับดักเรื่อง false) · และ blank? present? presence ที่ Ruby เปล่า ๆ ไม่มี

ทุกกล่องผลรันในบทนี้ก็อปมาจากเครื่องจริง · ไฟล์ TypeScript ผ่าน tsc --noEmit --strict ก่อน แล้วรันด้วย node ไฟล์.ts (node 24 รัน .ts ได้ตรง ๆ) · ตัวอย่างที่ต้องใช้ Active Support รันด้วย ruby -ractive_support/all ไฟล์.rb ซึ่งคือการโหลดส่วนเสริมของ Rails เข้ามาใน Ruby เปล่า ๆ

1 · คำถามเดียว สามภาษา สามคำตอบ

เวลาเขียน if count โดยไม่มี == 0 หรือ > 0 ต่อท้าย ภาษาต้องตัดสินใจเองว่า "count ตัวนี้ นับว่าจริงหรือเท็จ" · การตัดสินใจนี้มีชื่อเรียกว่า truthiness และแต่ละภาษาตั้งกฎไม่เหมือนกัน

เริ่มจากภาษาที่คุณรู้จักดีที่สุด — Go ไม่เล่นเกมนี้เลย ถ้าเงื่อนไขไม่ใช่ bool ก็ compile ไม่ผ่าน (เหมือนที่เห็นใน บทเรียน 2 ว่า Go เข้มเรื่อง type แค่ไหน): 

package main

import "fmt"

func main() {
	count := 0
	if count {
		fmt.Println("มีคนดู")
	}
}
$ go run main.go
# command-line-arguments
./main.go:7:5: non-boolean condition in if statement

สไลด์หน้า 26 สรุปฝั่ง Go ไว้ว่า "ยาว แต่ไม่มีทางพลาด" — ต้องเขียน if x != 0 · if s != "" · if err != nil ให้ชัดทุกครั้ง
ทีนี้ลองของจริงของ Ruby กับ TypeScript ด้วยค่าแปดตัวชุดเดียวกัน 

# predict.rb
values = [nil, false, 0, "", " ", [], "false", "0"]

values.each do |v|
  if v
    puts "#{v.inspect.ljust(8)} เข้า if"
  else
    puts "#{v.inspect.ljust(8)} ไม่เข้า"
  end
end

ก่อนกดเฉลย จดลงกระดาษ: ค่าแปดตัวนี้ ตัวไหนเข้า if ตัวไหนไม่เข้า ใน Ruby?
แล้วถ้าเป็น TypeScript (null แทน nil) คำตอบจะต่างกันตรงไหนบ้าง?

ผลรันจริงทั้งสองภาษา วางเทียบกัน:

ฝั่ง TypeScript ใช้ค่าแปดตัวชุดเดียวกัน (เปลี่ยน nil เป็น null) ผ่าน tsc --noEmit --strict แล้วรันด้วย node: 

// predict.ts
const values: unknown[] = [null, false, 0, "", " ", [], "false", "0"];
for (const v of values) {
  if (v) {
    console.log(`${JSON.stringify(v).padEnd(8)} เข้า if`);
  } else {
    console.log(`${JSON.stringify(v).padEnd(8)} ไม่เข้า`);
  }
}

ต่างกันอยู่ สองแถวพอดี: 0 กับ "" — TypeScript ปัดตกทั้งคู่ Ruby ให้ผ่านทั้งคู่
ที่หลายคนทายผิดคือ [] — อาร์เรย์ว่างเป็นจริงทั้งสองภาษา · และ " " (มีช่องว่างหนึ่งตัว) ก็จริงทั้งสองภาษา เพราะมันไม่ใช่สตริงว่าง — จำแถวนี้ไว้ หัวข้อ 5 จะกลับมาใช้

สรุปเป็นตารางเดียวตามสไลด์หน้า 26 (แก้ตัวเลขฝั่ง TypeScript ให้ตรงกับที่รันจริงแล้ว — ดูกล่องเตือนข้างล่าง):

GoTypeScriptRuby
ค่าที่นับว่าเท็จ (falsy) ไม่มีเรื่องนี้ · if รับแค่ bool false 0 -0 0n "" null undefined NaN nil กับ false เท่านั้น
0compile ไม่ผ่านเท็จจริง
""compile ไม่ผ่านเท็จจริง
[]compile ไม่ผ่านจริงจริง
วิธีเขียนที่ปลอดภัย if x != 0 if (x !== 0) if x.positive? · if x.zero? (หัวข้อ 2)

⚠️ สไลด์หน้า 26 เขียนหัวคอลัมน์ TypeScript ว่า "falsy 6 ตัว" แต่ลิสต์มาแค่ 5 ตัว (0 "" null undefined NaN) — ขาด false ตัวที่ชัดที่สุดไป
และถ้านับให้ครบจริง ๆ JavaScript มีค่า falsy มากกว่า 6 ตัวด้วย — รันจริงด้วย Boolean(): 

$ node -e 'for (const v of [false, 0, -0, 0n, "", null, undefined, NaN]) console.log(String(v).padEnd(10), Boolean(v))'
false      false
0          false
0          false
0          false
           false
null       false
undefined  false
NaN        false

(แถวที่ 3 กับ 4 คือ -0 และ 0n ซึ่ง String() พิมพ์ออกมาเป็น 0 ทั้งคู่ · แถวที่ 5 คือสตริงว่างเลยไม่เห็นอะไร)
ประเด็นหลักของสไลด์ยังถูกต้องเต็มที่: ฝั่ง Ruby มีแค่ 2 ตัว และ 0 "" [] เป็นจริงหมด

📦 เทียบให้เห็นภาพ — ยามหน้าหอพักที่เช็คพัสดุ

ลองนึกถึงยามหน้าหอสองคนที่ต้องตอบคำถามว่า "ห้องนี้มีพัสดุมาไหม"
ยาม Ruby ดูแค่ว่ามีกล่องวางอยู่หน้าห้องไหม · กล่องเปล่า ("") กล่องที่ข้างในเขียนเลข 0 (0) ก็ยังเป็นกล่อง → "มี" · จะตอบว่า "ไม่มี" ก็ต่อเมื่อไม่มีกล่องเลย (nil) หรือมีป้ายเขียนชัด ๆ ว่า "ไม่มี" (false)
ยาม TypeScript ชอบเปิดดูข้างใน — กล่องเปล่า กล่องที่เขียนเลข 0 เขาตอบว่า "ไม่มี" ด้วย
ยาม Go ไม่ตอบเลย ถ้าคุณไม่ถามมาเป็นประโยคใช่/ไม่ใช่ชัด ๆ เช่น "มีกล่องมากกว่า 0 ใบไหม"

ที่ไม่เหมือนกัน: ยาม TypeScript ไม่ได้เปิดกล่องทุกชนิด — [] (อาร์เรย์ว่าง) เขาก็ถือว่า "มี" เหมือนยาม Ruby ทั้งที่ข้างในว่างเปล่า · เพราะฉะนั้นอย่าจำว่า "TS ดูว่าข้างในว่างไหม" ให้จำรายชื่อ falsy ในตารางข้างบนแทน · และในโลกจริง false ก็ไม่ใช่ "ป้าย" แต่เป็นค่าจริง ๆ ตัวหนึ่ง เหมือน true

🗣 ศัพท์ที่เพิ่งเรียนไป
truthiness
กฎของภาษาว่าค่าที่ไม่ใช่ boolean จะ "นับว่าจริงหรือเท็จ" เมื่อเอาไปใส่ใน if · พิมพ์บอก AI ได้ว่า “I come from TypeScript — check this Ruby code for places that rely on 0 or empty string being falsy” ได้ผลกว่าการถามว่า "โค้ดนี้มีบั๊กไหม" เพราะ AI จะรู้ว่าต้องมองหาอะไร
truthy / falsy
คำคุณศัพท์ของสองคำบน · ใน Ruby falsy มีแค่ nil กับ false ที่เหลือ truthy หมด · ถาม senior ได้ว่า “ทีมนี้ยอมให้เขียน if count ลอย ๆ ไหม หรือต้องเขียน count.positive? ให้ชัด” คำตอบต่างกันไปแต่ละทีม ถามไว้ก่อนดีกว่าโดนแก้ใน code review
nil
ค่า "ไม่มีอะไร" ของ Ruby ตัวเดียว (ไม่มีแยก null กับ undefined แบบ TS) · เป็น object จริง ๆ ของคลาส NilClass · เวลาเห็น error undefined method '…' for nil ให้ถาม AI ว่า “where can this value become nil” ไม่ใช่ “how to fix NoMethodError”

2 · บั๊กที่ไม่มีใครเตือน: if @post.views

สไลด์หน้า 26 ยกตัวอย่างที่เจอใน Rails จริง: บทความมีคอลัมน์ views (จำนวนครั้งที่มีคนเปิดดู) แล้วอยากโชว์ป้าย "มีคนดู" เฉพาะบทความที่มีคนดูแล้ว
คนที่มาจาก TypeScript จะเขียนออกมาแบบนี้โดยไม่คิด เพราะใน TS มันใช้ได้ (บทความยังไม่มี model จริง — Active Record รออยู่ Day 2 — เลยจำลองด้วย Struct ไปก่อน): 

# views.rb
Post = Struct.new(:title, :views)
post = Post.new("ข้าวมันไก่ประตูน้ำ", 0)

if post.views
  puts "แสดงป้าย: มีคนดู #{post.views} ครั้ง"
end

if post.views.positive?
  puts "positive?: มีคนดูแล้ว"
else
  puts "positive?: ยังไม่มีใครดู"
end

p post.views.zero?
p 5.positive?
p 0.positive?
$ ruby views.rb
แสดงป้าย: มีคนดู 0 ครั้ง
positive?: ยังไม่มีใครดู
true
true
false

บรรทัดแรกของผลคือบั๊ก — หน้าเว็บโชว์ "มีคนดู 0 ครั้ง" เพราะ 0 เป็นจริงใน Ruby
ทางแก้ตามสไลด์คือถามให้ชัดด้วย method ที่ลงท้ายด้วย ? (ที่เรียนใน บทเรียน 93 ว่าคืนค่า true/false):

  • views.positive? — มากกว่า 0 ไหม (ใช้กับ "มีคนดูแล้ว")
  • views.zero? — เท่ากับ 0 ไหม (ใช้กับ "ยังไม่มีใครดู")

⚠️ สไลด์เขียนว่า if @post.views "จริงเสมอ" — จริงเสมอยกเว้นตอนเป็น nil · และถ้า views เป็น nil ได้ (เช่นคอลัมน์ในฐานข้อมูลไม่ได้ตั้งค่าเริ่มต้นไว้) .positive? จะพังแทน: 

$ ruby nilpos.rb          # views = nil แล้วเรียก views.positive?
nilpos.rb:2:in '<main>': undefined method 'positive?' for nil (NoMethodError)

views.positive?
     ^^^^^^^^^^

ทางที่ดีคือทำให้คอลัมน์นับจำนวนแบบนี้ไม่มีวันเป็น nil (ตั้ง default เป็น 0 ตอนสร้างตาราง — เรื่องของ Day 2) หรือถ้ายังไม่แน่ใจ ใช้ views.to_i.positive? (nil.to_i ได้ 0 — รันแล้ว) · ภารกิจท้ายบทจะได้ลองเอง

3 · รับมือ nil: &. กับ .nil?

ใน Rails คุณจะเจอ nil บ่อยมาก — หา user ไม่เจอ · ฟอร์มไม่ได้ส่งช่องนั้นมา · ความสัมพันธ์ยังไม่ได้ผูก
ปัญหาคือ เรียก method ใส่ nil แล้วพังทันที · Ruby เลยมีเครื่องมือสองชิ้นในตัว (สไลด์หน้า 27 ครึ่งบน): 

User = Struct.new(:name)

user = User.new("Somchai")
p user&.name

user = nil
p user&.name
p user&.name&.upcase
p user.nil?
$ ruby safe.rb
"Somchai"
nil
nil
true

user&.name อ่านว่า "ถ้า user ไม่ใช่ nil ก็เรียก .name · ถ้าเป็น nil ก็ได้ nil กลับมาเลย ไม่พัง" — คือ user?.name ของ TypeScript นั่นเอง แค่เปลี่ยนเครื่องหมายจาก ?. เป็น &. (เพราะ ? ใน Ruby ถูกจองไว้ให้ชื่อ method อย่าง nil? แล้ว)
ถ้าไม่ใส่ & จะเจอ error ที่คุณจะเห็นบ่อยที่สุดตลอดชีวิตการเขียน Rails: 

$ ruby safe.rb           # เพิ่มบรรทัดที่ 10: user.name ตอน user เป็น nil
"Somchai"
nil
nil
true
safe.rb:10:in '<main>': undefined method 'name' for nil (NoMethodError)

user.name
    ^^^^^
อยากได้GoTypeScriptRuby
เรียกต่อเมื่อไม่ว่าง if u != nil { n = u.Name } u?.name u&.name
เช็คว่าว่างไหม u == nil u == null (จับทั้ง null และ undefined) u.nil?

มีจุดเล็ก ๆ ที่ทำให้ &. ต่างจาก "ค่าเท็จ": &. ข้ามให้แค่ nil ไม่ข้าม false · และ .nil? ก็ตอบ true แค่กับ nil ตัวเดียว: 

$ ruby safe2.rb          # user = false แล้ว p user&.name
safe2.rb:2:in '<main>': undefined method 'name' for false (NoMethodError)

p user&.name
      ^^^^^^
$ ruby -e 'p "".nil?, false.nil?'
false
false

นี่คือเหตุผลที่ !x กับ x.nil? ไม่ใช่ของเดียวกัน — !false เป็นจริง แต่ false.nil? เป็นเท็จ · ถ้าตั้งใจถามว่า "ไม่มีค่า" ให้ใช้ .nil? · ถ้าตั้งใจถามว่า "เป็นเท็จ" ค่อยใช้ !

🚪 เทียบให้เห็นภาพ — กดกริ่งเฉพาะห้องที่มีคนอยู่

user.name คือเดินไปเคาะประตูถามชื่อเลย — ถ้าห้องว่าง (nil) คุณก็ยืนงงอยู่หน้าห้อง (โปรแกรมพัง)
user&.name คือมองไฟห้องก่อน ถ้าห้องมืดก็เดินกลับมาพร้อมคำตอบว่า "ไม่มีใคร" (nil) ไม่ต้องเคาะให้เสียเรื่อง
user.nil? คือแค่มองไฟอย่างเดียว ไม่ได้ถามอะไรต่อ — ได้คำตอบใช่/ไม่ใช่

ที่ไม่เหมือนกัน: ในชีวิตจริง ห้องที่มีป้าย "ไม่อยู่" (false) คุณก็คงไม่เคาะ · แต่ &. เคาะ — มันมองเห็นแค่ห้องที่ว่างจริง ๆ (nil) เท่านั้น แล้วก็พังตามผลรันข้างบน · และการ "เดินกลับมามือเปล่า" อาจแค่เลื่อนปัญหาออกไป ถ้าโค้ดถัดไปเอา nil นั้นไปใช้ต่อโดยไม่เช็คอีกที

🗣 ศัพท์ที่เพิ่งเรียนไป
safe navigation operator (&.)
ชื่อทางการในเอกสาร Ruby · คนเรียกเล่น ๆ ว่า lonely operator · เทียบได้กับ optional chaining (?.) ของ TS · ถาม senior ได้ว่า “ตรงนี้ควรใช้ &. หรือควรทำให้ค่าไม่มีวันเป็น nil ตั้งแต่ต้น” — การโรย &. ทุกจุดมักแปลว่ายังไม่รู้ว่า nil มาจากไหน
NoMethodError
error ที่เกิดเมื่อเรียก method ที่ object ไม่มี · แบบที่เจอบ่อยสุดคือ undefined method '…' for nil · พิมพ์บอก AI ได้ว่า “trace back where this variable got nil, don't just add &.” จะได้คำตอบที่แก้ต้นเหตุ ไม่ใช่แค่ปิดอาการ

4 · ||= — ใส่ค่าให้เฉพาะตอนยังไม่มี (และกับดักเรื่อง false)

count ||= 0 อ่านว่า "ถ้า count ยังเป็นค่าเท็จอยู่ ก็ใส่ 0 ให้ · ถ้ามีค่าแล้วก็ปล่อยไว้"
คำว่า "ค่าเท็จ" ตรงนี้คือกฎเดียวกับหัวข้อ 1 — แปลว่า nil หรือ false และตรงคำว่า false นี่แหละที่เป็นกับดัก 

# orq.rb
count = nil
count ||= 0
p count

สไลด์เทียบ ||= กับ ??= ของ TypeScript — แม่นแค่ไหน

สไลด์หน้า 27 เขียนไว้ว่า ||= เทียบได้กับ x ??= 0 ของ TS — ใกล้ แต่ไม่เท่ากันพอดี · ผมรันฝั่ง TypeScript ทั้ง ??= และ ||= ให้ดู: 

// nq.ts (ผ่าน tsc --noEmit --strict)
let x: boolean = false;
x ??= true;
console.log("??= :", x);

let y: boolean = false;
y ||= true;
console.log("||= :", y);

let n: number = 0;
n ??= 99;
console.log("??= 0 :", n);

let m: number = 0;
m ||= 99;
console.log("||= 0 :", m);

||= : true

||= 0 : 99

(ใส่เมื่อ falsy ทุกตัว)		Ruby ||=
(ใส่เมื่อ nil/false)
nil / nullใส่ค่าใหม่ใส่ค่าใหม่ใส่ค่าใหม่
0คงไว้ใส่ค่าใหม่คงไว้
""คงไว้ใส่ค่าใหม่คงไว้
falseคงไว้ใส่ค่าใหม่ใส่ค่าใหม่

อ่านตารางแล้วจะเห็นว่า Ruby ||= อยู่ตรงกลาง: เรื่อง 0 กับ "" มันเหมือน ??= (คงไว้) · แต่เรื่อง false มันเหมือน ||= ของ TS (เขียนทับ)
สรุปสั้น ๆ: สไลด์เทียบกับ ??= ถูกในเคส nil 0 "" แต่ผิดเคส false · ถ้าตัวแปรเป็น boolean อย่าใช้ ||= ใส่ค่าเริ่มต้น ให้เขียน x = true if x.nil? แทน

บรรทัด Go ในสไลด์ไม่มีความหมาย

สไลด์หน้า 27 เทียบ ||= กับ Go ไว้ว่า // Go: if x == 0 { x = 0 } — อ่านดี ๆ จะเห็นว่า "ถ้า x เป็น 0 ก็ตั้งให้เป็น 0" ไม่ได้เปลี่ยนอะไรเลย (รันจริงก็ได้ 0 เหมือนเดิม) · น่าจะตั้งใจเขียนอย่างอื่นแต่พิมพ์ผิด
ใน Go ตัวแปร int เป็น 0 ตั้งแต่ประกาศอยู่แล้ว (zero value) · ที่ใกล้ ||= จริง ๆ คือการเช็ค nil ของ map หรือ pointer แล้วค่อยใส่ค่าเริ่มต้น: 

package main

import "fmt"

func main() {
	// ตามสไลด์: ไม่มีผลอะไรเลย เพราะถ้า x เป็น 0 ก็ตั้งให้เป็น 0 อีกรอบ
	x := 0
	if x == 0 {
		x = 0
	}
	fmt.Println("slide:", x)

	// ที่ใกล้ ||= จริง ๆ: เช็ค nil แล้วค่อยใส่ค่าเริ่มต้น
	var cache map[string]int
	if cache == nil {
		cache = map[string]int{}
	}
	cache["views"]++
	fmt.Println("map:", cache)

	var limit *int
	if limit == nil {
		v := 20
		limit = &v
	}
	fmt.Println("pointer:", *limit)
}
$ go run main.go
slide: 0
map: map[views:1]
pointer: 20

ที่จะเจอบ่อยที่สุด: @current_user ||= User.find_by(...)

สไลด์หน้า 27 บอกว่าจะเจอ ||= บ่อยมากในรูปนี้ · ท่านี้มีชื่อเรียกว่า memoization = "คำนวณครั้งแรกแล้วจำผลไว้ ครั้งต่อไปหยิบของที่จำไว้มาใช้เลย"
ในหนึ่ง request หน้าเว็บอาจถาม current_user สิบครั้ง (ใน controller, ใน view, ใน helper) ถ้าไม่จำไว้ก็ยิง SQL ไปฐานข้อมูลสิบรอบ · @current_user เป็นตัวแปรของ object (@ = instance variable — รายละเอียดอยู่บทเรียน 95) จึงอยู่ได้ตลอดอายุของ object นั้น
ผมจำลองฐานข้อมูลด้วย puts เพื่อให้เห็นว่ายิง query กี่ครั้ง (ยังไม่ใช่ Active Record จริง): 

# memo.rb
class FakeDB
  def self.find_user(id)
    puts "  -> SELECT * FROM users WHERE id = #{id.inspect}"
    id == 1 ? "Somchai" : nil
  end
end

class PageController
  def initialize(session_user_id)
    @session_user_id = session_user_id
  end

  def current_user
    @current_user ||= FakeDB.find_user(@session_user_id)
  end
end

puts "login แล้ว (id = 1):"
c = PageController.new(1)
3.times { c.current_user }

puts "ยังไม่ login (id = nil):"
c = PageController.new(nil)
3.times { c.current_user }

แต่ตอนยังไม่ login ผลของการค้นคือ nil → ||= เห็นค่าเท็จ → คิดว่ายังไม่เคยหา → ยิงใหม่ทุกครั้ง · กับดักเดียวกับ false ในหัวข้อนี้ แค่มาในรูป nil
ถ้าอยากจำ "ผลว่าไม่เจอ" ไว้ด้วย ต้องเช็คว่าเคยตั้งค่าตัวแปรแล้วหรือยัง แทนการเช็คว่าค่าเป็นจริงไหม: 

# memo2.rb — เหมือน memo.rb ทุกบรรทัด ยกเว้น current_user ที่เปลี่ยนเป็นแบบนี้
  def current_user
    return @current_user if defined?(@current_user)
    @current_user = FakeDB.find_user(@session_user_id)
  end

ในงานจริง หน้าที่ไม่มีคน login มีไม่กี่หน้า query เกินมาสองสามครั้งอาจไม่ใช่เรื่องใหญ่ · แต่ถ้าสิ่งที่ memo ไว้คือการเช็คสิทธิ์ที่คืน true/false (เช่น @admin ||= check_admin) ทุกคนที่ไม่ใช่ admin จะโดนคำนวณซ้ำทุกครั้ง — จำไว้ว่า ||= จำได้แค่ค่าที่เป็นจริง

📝 เทียบให้เห็นภาพ — โพสต์อิทแปะจอ

@current_user ||= User.find_by(...) เหมือนจดเบอร์โทรลูกค้าที่ต้องโทรบ่อยลงโพสต์อิทแปะข้างจอ · ครั้งแรกต้องเปิดแฟ้มหา (ยิง query) · ครั้งต่อไปเหลือบมองโพสต์อิทพอ
กฎของ ||= คือ "ถ้าโพสต์อิทว่าง ค่อยเปิดแฟ้ม"

ที่ไม่เหมือนกัน: คนจริงที่เปิดแฟ้มแล้วไม่เจอ จะจดลงโพสต์อิทว่า "ไม่มีในแฟ้ม" แล้วไม่เปิดซ้ำ · แต่ ||= จดคำว่า "ไม่มี" ไม่เป็น — ได้ nil หรือ false มาก็เหมือนโพสต์อิทยังว่าง แล้วเปิดแฟ้มใหม่ทุกรอบ (ผลรันข้างบน) · และโพสต์อิทของจริงอยู่ข้ามวันได้ แต่ @current_user ใน controller อยู่แค่หนึ่ง request — request ถัดไปเริ่มจากโพสต์อิทว่างใหม่

🗣 ศัพท์ที่เพิ่งเรียนไป
abbreviated assignment (||=)
ชื่อในเอกสาร Ruby ของการกำหนดค่าแบบย่อ · คนในวงการเรียก ||= ว่า or-equals · ถาม senior ได้ว่า “ตัวแปรนี้เป็น false ได้ไหม ถ้าได้ ||= ตรงนี้จะเขียนทับมัน” — เป็นคำถามรีวิวโค้ดที่ดูเป็นมืออาชีพมาก
nullish coalescing (?? / ??=)
ชื่อของตัวดำเนินการฝั่ง TS ที่ดูแค่ null/undefined · Ruby ไม่มีตัวที่ตรงกันเป๊ะ · พิมพ์บอก AI ได้ว่า “translate this TS ??= to Ruby — note the value can be false” ไม่งั้น AI มักแปลเป็น ||= ตรง ๆ
memoization
คำนวณครั้งแรกแล้วเก็บผลไว้ในตัวแปร ครั้งต่อไปคืนของที่เก็บไว้ · ใน Ruby มักเห็นเป็น @x ||= … · ถาม senior ได้ว่า “method นี้ memoize ไว้ ถ้าผลเป็น nil จะยิงซ้ำไหม ต้องใช้ defined? หรือเปล่า”

5 · blank? · present? · presence — ของที่ Rails เติมให้

สไลด์หน้า 27 กล่องขวาบนให้เหตุผลไว้ดีมาก: ฟอร์มบนเว็บส่ง "" มา ไม่ได้ส่ง nil และ " " ที่ผู้ใช้เผลอเคาะ space ก็ควรนับว่าว่าง — แต่ตามตารางหัวข้อ 1 ทั้ง "" และ " " เป็นจริงใน Ruby
Ruby เปล่า ๆ มี empty? ให้ แต่มันนับแค่สตริงยาว 0 ตัว ช่องว่างไม่นับ · และ blank? ไม่มีใน Ruby เปล่า ๆ เลย:

  • " ".empty? เป็น false แต่ " ".blank? เป็น true — blank? นับช่องว่าง แท็บ ขึ้นบรรทัดใหม่ ว่าเป็น "ว่าง" ด้วย
  • 0.blank? เป็น false — ตัวเลขไม่เคย blank · 0 คือค่าที่ผู้ใช้ตั้งใจกรอก ไม่ใช่ "ไม่ได้กรอก"
  • present? คือ !blank? ตามที่สไลด์เขียนไว้ — มีไว้ให้อ่านง่าย ไม่ต้องเขียน ! นำหน้า

presence — ค่าเริ่มต้นให้ช่องค้นหา

x.presence คืน x เองถ้า x present · คืน nil ถ้า x blank
ประโยชน์ของมันคือเอาไปต่อกับ || ได้ เพราะ nil เป็นเท็จ — สไลด์ยกตัวอย่าง params[:q].presence || "default" · ผมรันเทียบกับ params[:q] || "default" เฉย ๆ โดยจำลอง params ด้วย Hash ก่อน:

  b = params[:q].presence || "default"
  puts "#{params.inspect.ljust(14)} ||: #{a.inspect.ljust(10)} presence ||: #{b.inspect}"
end

🧾 เทียบให้เห็นภาพ — เจ้าหน้าที่รับใบสมัคร

นึกถึงใบสมัครกระดาษที่มีช่อง "ชื่อเล่น"
nil = ใบสมัครรุ่นเก่าที่ไม่มีช่องนี้ · "" = มีช่องแต่ไม่ได้เขียน · " " = ขีดเส้นว่าง ๆ ไว้

ที่ไม่เหมือนกัน: ถ้าช่องเป็น "จำนวนบุตร" แล้วมีคนกรอก 0 เจ้าหน้าที่คนจริงอาจมองว่า "ไม่มี" · แต่ 0.blank? เป็น false — สำหรับ Active Support ตัวเลขไม่เคยว่าง · และ blank? ไม่ได้ตัดช่องว่างทิ้ง — " ramen " ยัง present อยู่และมีช่องว่างหัวท้ายติดไปด้วย

🗣 ศัพท์ที่เพิ่งเรียนไป
Active Support
gem ส่วนหนึ่งของ Rails ที่เติม method ให้คลาสพื้นฐาน (blank? · 3.days.ago · ฯลฯ) · ส่วนที่เติมให้คลาสของ Ruby เรียกว่า core extensions · ถาม AI ได้ว่า “is this method plain Ruby or Active Support?” ทุกครั้งที่เจอ method ที่ไม่แน่ใจ — สำคัญมากถ้าโค้ดนั้นจะไปรันนอก Rails
blank / present
blank = nil · false · สตริงที่มีแต่ช่องว่าง · collection ว่าง · present = ตรงข้าม · พิมพ์บอก AI ได้ว่า “treat whitespace-only input as missing — use presence” จะได้โค้ดที่จัดการฟอร์มถูกตั้งแต่แรก
presence
คืนตัวเองถ้า present · คืน nil ถ้า blank · ใช้คู่กับ || เพื่อใส่ค่าเริ่มต้น · ถาม senior ได้ว่า “ช่องนี้ควร strip ก่อน presence ไหม” — เพราะ presence ไม่ตัดช่องว่างหัวท้ายให้

6 · สรุป: ถามให้ตรงกับที่อยากรู้

7 · ภารกิจ: แก้บั๊กสามจุด

สร้างไฟล์ task.rb แล้ววางโค้ดข้างล่างทั้งก้อน · ฟังก์ชันสามตัวข้างบนมีบั๊กตัวละจุด — ทุกจุดคือเรื่องที่เรียนในบทนี้ · ส่วน "ตัวตรวจ" ข้างล่างห้ามแก้ 

# task.rb — โค้ดตั้งต้น (มีบั๊ก 3 จุด)

def view_badge(views)

  end

def search_term(params)
  params[:q] || "ทั้งหมด"
end

def apply_defaults(settings)
  settings[:notify] ||= true
  settings
end

# ---- ตัวตรวจ ห้ามแก้ ----
FAILED = []

def check(label, actual, expected)
  if actual == expected
    puts "ผ่าน  #{label}"
  else
    puts "พัง   #{label}: ได้ #{actual.inspect} แต่ควรได้ #{expected.inspect}"
    FAILED << label
  end
end

check "views 12",  view_badge(12),  "ดูแล้ว 12 ครั้ง"
check "views 0",   view_badge(0),   "ยังไม่มีคนดู"
check "views nil", view_badge(nil), "ยังไม่มีคนดู"

check "q ramen", search_term({ q: "ramen" }), "ramen"
check "q ว่าง",  search_term({ q: "" }),      "ทั้งหมด"
check "q space", search_term({ q: "   " }),   "ทั้งหมด"
check "ไม่มี q", search_term({}),             "ทั้งหมด"

check "notify ไม่ได้ตั้ง", apply_defaults({}),                { notify: true }
check "notify ปิดไว้",    apply_defaults({ notify: false }), { notify: false }

puts(FAILED.empty? ? "ผ่านทุกข้อ" : "ยังพัง #{FAILED.size} ข้อ")
exit(1) unless FAILED.empty?

  2. แก้เฉพาะฟังก์ชันสามตัวข้างบน (ตัวละบรรทัดก็พอ) จนรันแล้วขึ้น ผ่านทุกข้อ

def view_badge(views)

ลองตอบดู

post.views เป็น 0 แล้วโค้ด if post.views โชว์ป้าย "มีคนดู 0 ครั้ง" — แก้ยังไงถึงตรงที่สุด?

ตัวเลือกที่ 2 ถูก · 0.positive? ได้ false (รันจริงในหัวข้อ 2) จึงไม่โชว์ป้าย
ตัวเลือกที่ 1 ผิดเพราะ 0 ไม่ใช่ nil → !0.nil? เป็นจริง ป้ายยังขึ้นเหมือนเดิม · ตัวเลือกที่ 3 ผิดเพราะ 0.blank? เป็น false → 0.present? เป็น true (ตัวเลขไม่เคย blank) · ตัวเลือกที่ 4 แก้ผิดปัญหา — &. กันแค่ post เป็น nil ส่วน views ที่เป็น 0 ก็ยังเป็นจริงอยู่ดี
จุดที่ต้องจำ: อยากรู้เรื่องตัวเลข ให้ถามด้วย method ของตัวเลข (positive? zero?) อย่าพึ่ง truthiness

โค้ด TypeScript let on = false; on ??= true; ได้ on เป็น false · ถ้าแปลเป็น Ruby ข้อไหนให้ผลเหมือนกัน?

ตัวเลือกที่ 4 ถูก · false.nil? เป็น false (รันจริงในหัวข้อ 3) จึงไม่เขียนทับ — ตรงกับ ??= ที่ดูแค่ null/undefined
ตัวเลือกที่ 1 คือกับดักหลักของบท — รันจริง x = false; x ||= true ได้ true · ตัวเลือกที่ 2 false || true ได้ true แล้วเอาไปเขียนทับ — รันจริงได้ true · ตัวเลือกที่ 3 unless on แปลว่า "ถ้า on เป็นเท็จ" ซึ่ง false เป็นเท็จ ก็ได้ true เหมือนกัน
จุดที่ต้องจำ: สไลด์เทียบ ||= กับ ??= — ใช้ได้กับ nil 0 "" แต่ไม่ใช่กับ false

ผู้ใช้เคาะ space สามทีในช่องค้นหาแล้วกดค้น · Rails ได้ params[:q] เป็น " " · params[:q] || "default" ได้อะไร?

ตัวเลือกที่ 1 ถูก · ผลรันจริงจาก curl 'http://localhost:4294/search?q=+++' คือ || ได้ " "
ตัวเลือกที่ 2 ผิดเพราะ Rails ไม่ได้ตัดช่องว่างให้ — params[:q] = " " มาครบสามตัว · ตัวเลือกที่ 3 ผิดเพราะใน Ruby มีแค่ nil กับ false ที่เป็นเท็จ · ตัวเลือกที่ 4 ผิดเพราะ key q ถูกส่งมา (ค่า nil เกิดเฉพาะตอนไม่มี q ใน URL เลย)
จุดที่ต้องจำ: ค่าจากฟอร์มให้ใช้ params[:q].presence || "default" — presence เปลี่ยน "" และ " " เป็น nil ก่อน

method current_user ข้างในเขียนว่า @current_user ||= User.find_by(id: session[:user_id]) · ผู้ใช้ยังไม่ login แล้วหน้าเว็บเรียก current_user 3 ครั้ง · ยิง query กี่ครั้ง?

ตัวเลือกที่ 3 ถูก · ผลรันจริงของ memo.rb ฝั่ง "ยังไม่ login" มีบรรทัด SELECT สามบรรทัด
ตัวเลือกที่ 1 ผิดเพราะ ||= ไม่ได้ดู session — มันดูแค่ @current_user ซึ่งยังเป็น nil จึงเรียกฝั่งขวาทุกครั้ง · ตัวเลือกที่ 2 จะถูกก็ต่อเมื่อผลเป็นค่าจริง (กรณี login แล้ว) · ตัวเลือกที่ 4 ผิดเพราะ find_by หาไม่เจอจะคืน nil ไม่ได้โยน error (รันจริงใน bin/rails runner: User.find_by(id: 999) ได้ nil ส่วน User.find(999) โยน ActiveRecord::RecordNotFound — รายละเอียดรอ Day 2)
จุดที่ต้องจำ: ||= จำได้แค่ค่าที่เป็นจริง — ผล nil/false จะถูกคำนวณใหม่ทุกครั้ง · ถ้าต้องจำด้วยให้ใช้ defined?

ถามกลับได้เลย

ถ้ายังสับสนว่าเมื่อไหร่ใช้ nil? เมื่อไหร่ใช้ blank? — ลองเอาค่าที่สงสัยมาถามว่า "ค่านี้มาจากไหน" (ฐานข้อมูล? ฟอร์ม? ตัวแปรที่ยังไม่ได้ตั้ง?) แล้วเทียบกับตารางในหัวข้อ 6
หรือถ้าคุณเคยเขียน TypeScript ที่พึ่ง if (x) เยอะ ๆ เอาโค้ดมาแปลเป็น Ruby ด้วยกันได้ — จุดที่น่าสนใจที่สุดมักเป็นบรรทัดที่ ไม่ต้องแก้ แต่ความหมายเปลี่ยนเงียบ ๆ
