1 · ERB — HTML ที่มีช่องให้ Ruby เติม (สไลด์หน้า 64)

ไฟล์ view ของ Rails นามสกุล .html.erb — อ่านจากขวาไปซ้าย: "ไฟล์นี้ให้ ERB ประมวลผลก่อน แล้วได้ผลเป็น HTML"
หน้าตามันคือ HTML ธรรมดาเกือบทั้งไฟล์ มีแค่บางจุดที่เจาะ "ช่อง" ไว้ให้ Ruby ทำงาน ช่องพวกนี้มีแค่ 3 แบบ และต่างกันที่ตัวอักษรตัวเดียวหลัง <%:

แท็กทำอะไรผลไปถึง browser ไหม
<%= … %> รันโค้ด Ruby แล้วพิมพ์ผลลงไปตรงนั้น — และ escape ให้อัตโนมัติ (หัวข้อ 4) ✅ ผลลัพธ์ไปถึง
<% … %> รันโค้ด Ruby เฉย ๆ ไม่พิมพ์ — ใช้กับ if · each · end ❌ ตัวมันไม่ไป แต่ HTML ที่มันครอบอยู่ไปได้
<%# … %> comment — Ruby ไม่รันเลย ❌ ไม่ไปแม้แต่ตัวอักษรเดียว

ถ้าคุณเคยเขียน JSX ในบท Next.js มาแล้ว นี่คือของเดียวกันแค่คนละไวยากรณ์ · Go ก็มีแม่แบบ HTML แบบนี้ใน standard library ชื่อ html/template:

อยากทำGo (html/template)TypeScript (JSX)Ruby (ERB)
พิมพ์ค่า {{.Title}} {post.title} <%= @post.title %>
เงื่อนไข {{if .Published}}…{{end}} {published && <p>…</p>} <% if @post.published? %>…<% end %>
comment ที่ไม่ไปถึง browser {{/* … */}} {/* … */} <%# … %>

มาดูของจริง — ผมเขียน view ตามสไลด์หน้า 64 แล้วเติม comment แบบ HTML ปกติ (<!-- -->) ไว้เทียบด้วยหนึ่งบรรทัด · controller ตั้งค่า @post = Post.new(title: "ข้าวมันไก่ร้านดัง", published: true): 

<%# app/views/demo/erb.html.erb %>
<h1><%= @post.title %></h1>
<% if @post.published? %>
  <p>เผยแพร่แล้ว</p>
<% end %>
<%# นี่คือ comment ไม่ออกไปถึง browser %>
<!-- นี่คือ comment ของ HTML -->

curl หน้านี้แล้ว HTML ที่ได้มีกี่บรรทัด? comment ตัวไหนรอดไปถึง browser? (บรรทัดแรกของไฟล์ที่ผมเขียนบอกชื่อไฟล์ไว้ก็เป็น <%# เหมือนกัน — นับด้วย)

(ตัดเฉพาะส่วนใน <main>)

--><h1>ข้าวมันไก่ร้านดัง</h1>

<!-- END app/views/demo/erb.html.erb -->

เนื้อจริงมีแค่ 3 บรรทัด: <h1> · <p> · และ comment แบบ HTML · comment <%# หายไปทั้งสองบรรทัด · บรรทัด <% if %> กับ <% end %> ก็หายไปทั้งบรรทัด ไม่ทิ้งแม้แต่บรรทัดว่าง

ยืนยันด้วย grep ให้ชัด ๆ ว่าคำว่า "ไม่ออกไปถึง" ไม่อยู่ใน response เลย (นับรวม comment <%# ใน layout ของ Rails เองด้วย เช่น Enable PWA manifest): 

$ curl -s http://localhost:3000/erb | grep -c -e 'ไม่ออกไปถึง' -e 'Enable PWA' -e 'manifest'
0
$ curl -s http://localhost:3000/erb | grep 'comment'
<!-- นี่คือ comment ของ HTML -->

แล้ว BEGIN / END สองบรรทัดนั่นมาจากไหน? ผมไม่ได้เขียน — Rails ใส่ให้เองเฉพาะตอน development เพราะไฟล์ config/environments/development.rb ที่ rails new สร้างมี config.action_view.annotate_rendered_view_with_filenames = true ไว้บอกว่า "HTML ท่อนนี้มาจากไฟล์ไหน" · มีประโยชน์มากตอนหาว่าหน้าเว็บมาจากไฟล์ไหน แต่ฝั่ง test ตั้งเป็น comment ปิดไว้ (# config.action_view.annotate… ใน config/environments/test.rb) ส่วน production.rb ไม่มีบรรทัดนี้เลย

⚠️ กับดักสองตัวที่มือใหม่เจอวันแรก — รันจริงทั้งคู่

1. ลืม = — เขียน <p>ลืม =: <% @post.title %></p> ได้ <p>ลืม =: </p> · ไม่มี error ค่าแค่หายไปเฉย ๆ เพราะ <% คือ "รันแต่ไม่พิมพ์"

2. ใส่ = เกินที่บรรทัด each: 

<ul>
<%= ["ข้าวซอย", "ส้มตำ"].each do |menu| %>   <%# ← มี = %>
  <li><%= menu %></li>
<% end %>
</ul>

<ul>

  <li>ข้าวซอย</li>

  <li>ส้มตำ</li>
[&quot;ข้าวซอย&quot;, &quot;ส้มตำ&quot;]</ul>

รายการออกมาครบ แต่มีขยะ ["ข้าวซอย", "ส้มตำ"] ต่อท้าย — เพราะ each คืนค่า array ตัวเดิม (บท 93 ข้อ "method คืนค่าบรรทัดสุดท้าย") แล้ว <%= ก็พิมพ์ค่านั้นออกมาตามหน้าที่ · แก้โดยเอา = ออกที่บรรทัด each แล้วได้ <ul> ที่มีแค่ <li> สองตัวสะอาด ๆ · กติกาจำง่าย: บรรทัดที่ "ควบคุม" (if · each · end) ใช้ <% · บรรทัดที่ "อยากเห็นค่า" ใช้ <%= (ข้อยกเว้นเดียวที่เจอใน Day 1 คือ <%= form_with … do |f| %> ซึ่งตั้งใจให้คืน HTML ของฟอร์มทั้งก้อน — หัวข้อ 3)

🧰 เทียบให้เห็นภาพ — จดหมายเวียนที่มีช่องเติมชื่อ

นึกถึงจดหมายเชิญงานที่พิมพ์ส่งลูกค้าร้อยคน ต้นฉบับมีฉบับเดียว แต่มีช่องว่างให้เติม:
· <%= %> คือช่อง "เรียนคุณ ______" — เติมชื่อแล้วชื่อปรากฏบนกระดาษ
· <% %> คือคำสั่งถึงคนพิมพ์ เช่น "ถ้าเป็นลูกค้า VIP ให้พิมพ์ย่อหน้านี้ด้วย" — คำสั่งไม่ได้ถูกพิมพ์ลงจดหมาย แต่ย่อหน้าที่มันคุมอยู่อาจถูกพิมพ์
· <%# %> คือโน้ตดินสอที่ขอบต้นฉบับ "เช็คชื่อสะกดกับฝ่ายขายก่อน" — ลบทิ้งก่อนส่งทุกฉบับ
· ส่วน <!-- --> คือโน้ตที่พิมพ์ด้วยหมึกขาวบนกระดาษขาว — มองไม่เห็นก็จริง แต่ติดไปถึงมือลูกค้า ใครเอาไปส่องไฟ (กด View Source) ก็อ่านออก

ที่ไม่เหมือนกัน: คำสั่งถึงคนพิมพ์จดหมายทำได้แค่ "ใส่/ไม่ใส่ย่อหน้า" แต่ในช่อง <% %> คุณเขียน Ruby อะไรก็ได้ทุกอย่าง — คิวรีฐานข้อมูล ลบข้อมูล ส่งอีเมล ก็รันได้หมด ERB ไม่ห้าม · เพราะฉะนั้นคนที่ต้องห้ามคือคุณเอง: งานคิดให้อยู่ใน controller/model · view ทำแค่ "จัดหน้า" (เหตุผลเดียวกับที่บท 100 แยก MVC)

🗣 ศัพท์ที่เพิ่งเรียนไป
ERB (Embedded Ruby)
ระบบแม่แบบที่ฝัง Ruby ลงในข้อความ · Rails 8.1.4 ใช้ตัวประมวลผลชื่อ Erubi อยู่เบื้องหลัง · ถาม senior ได้ว่า "ทีมเราใช้ ERB ล้วนหรือมี ViewComponent / Phlex ด้วย" — บางทีมเลิกเขียน ERB ตรง ๆ แล้ว
output tag · <%= %>
แท็กที่พิมพ์ผลลัพธ์ (และ escape ให้) · พิมพ์บอก AI ได้ว่า "this ERB line uses an output tag on a block-returning call, so the array gets printed — switch it to an execution tag" เวลาเจอขยะ [...] ต่อท้ายรายการแบบกับดักข้อ 2
execution tag · <% %>
แท็กที่รันโค้ดแต่ไม่พิมพ์ · ใช้กับ if · each · end
ERB comment · <%# %>
comment ที่ถูกตัดทิ้งฝั่ง server ไม่ไปถึง browser · เป็นที่เดียวใน view ที่ควรเขียนโน้ตภายในทีม — เขียนใน <!-- --> = ประกาศให้ทุกคนที่กด View Source อ่าน

2 · layout — กรอบที่ครอบทุกหน้า กับ yield ตัวเดียวกับบท 97

สังเกตไหมว่าในหัวข้อ 1 ผมเขียน view แค่ไม่กี่บรรทัด แต่ HTML ที่ curl ได้มี <!DOCTYPE html> · <head> · <title>Wongnok Blog</title> ครบ — ของพวกนั้นมาจาก layout: ไฟล์ที่ครอบทุกหน้าให้อัตโนมัติ
สไลด์หน้า 64 ย่อ layout ไว้ 8 บรรทัด · นี่คือไฟล์จริงทั้งไฟล์ที่ rails new wongnok_blog --database=postgresql --css=tailwind สร้างให้ (Rails 8.1.4 · ไม่ได้แก้อะไร): 

<%# app/views/layouts/application.html.erb — ของจริงจาก rails new %>
<!DOCTYPE html>
<html>
  <head>
    <title><%= content_for(:title) || "Wongnok Blog" %></title>
    <meta name="viewport" content="width=device-width,initial-scale=1">
    <meta name="apple-mobile-web-app-capable" content="yes">
    <meta name="application-name" content="Wongnok Blog">
    <meta name="mobile-web-app-capable" content="yes">
    <%= csrf_meta_tags %>
    <%= csp_meta_tag %>

    <%= yield :head %>

    <%# Enable PWA manifest for installable apps (make sure to enable in config/routes.rb too!) %>
    <%#= tag.link rel: "manifest", href: pwa_manifest_path(format: :json) %>

    <link rel="icon" href="/icon.png" type="image/png">
    <link rel="icon" href="/icon.svg" type="image/svg+xml">
    <link rel="apple-touch-icon" href="/icon.png">

    <%# Includes all stylesheet files in app/assets/stylesheets %>
    <%= stylesheet_link_tag :app, "data-turbo-track": "reload" %>
    <%= javascript_importmap_tags %>
  </head>

  <body>
    <main class="container mx-auto mt-28 px-5 flex">
      <%= yield %>
    </main>
  </body>
</html>

อ่านแบบภาษาคน — ไม่ต้องจำทุกบรรทัด จำแค่สามจุดนี้:

  1. <%= yield %> ใน <main> คือ "รู" ที่ view ของแต่ละ action จะถูกเอามาวาง · สไลด์เขียนไว้ตรง <body> เลย แต่ไฟล์จริงห่อด้วย <main class="…"> ที่มี class ของ Tailwind ไว้แล้ว (เพราะเราสั่ง --css=tailwind) — เวลาหน้าเว็บของคุณมีขอบบน mt-28 แปลก ๆ ให้มาดูที่บรรทัดนี้
  2. <%= csrf_meta_tags %> คือ token กัน CSRF ที่หัวข้อ 4 จะพูดถึง — มันอยู่ในทุกหน้าเพราะอยู่ใน layout
  3. stylesheet_link_tag :app — สไลด์เขียน "application" แต่ไฟล์จริงใช้ :app ซึ่งแปลว่า "ทุกไฟล์ CSS ใน app/assets" · ผลจริงคือได้ สอง <link>: application-8b441ae0.css กับ tailwind-c917166a.css · ถ้าใช้ "application" ตามสไลด์จะได้แค่ตัวแรก (ผมลองแล้วในหัวข้อ 3) Tailwind จะหายทั้งเว็บ

ทีนี้ประโยคสำคัญของสไลด์หน้า 64: "yield ตัวเดียวกับที่เจอในสไลด์ block" · ในบท 97 หัวข้อ 2.1 คุณเขียน layout จิ๋วด้วย Ruby ล้วนไปแล้ว — method layout พิมพ์หัว → yield ให้ block พิมพ์ไส้ → พิมพ์ท้าย · Rails ทำแบบนั้นจริง ๆ ไม่ได้เปรียบเปรย · นี่คือบรรทัดจริงใน source ของ Rails ที่เรียก layout (actionview-8.1.4/lib/action_view/renderer/template_renderer.rb บรรทัด 76–77): 

view.view_flow.set(:layout, yield(layout))
layout.render(view, locals) { |*name| view._layout_for(*name) }

บรรทัดแรก render view ของ action ก่อน แล้วเก็บผลไว้ในช่องชื่อ :layout · บรรทัดที่สองเรียก layout พร้อมส่ง block ติดไปด้วย — พอ layout เจอ <%= yield %> ก็ไปเรียก block นั้น ซึ่งคืน HTML ของ view ที่ render ไว้แล้วกลับมา · ลำดับนี้เห็นใน log จริงด้วย:

view เสร็จก่อน (Rendered demo/erb…) แล้ว layout ถึงเสร็จ — ข้อนี้สำคัญกว่าที่คิด: เพราะ view ทำงานก่อน view จึงฝากของขึ้นไปให้ layout ได้ เช่นเขียน <% content_for :title, "ข้าวมันไก่" %> ใน view แล้ว <title> ใน layout ก็จะเปลี่ยนตาม (นั่นคือบรรทัด content_for(:title) || "Wongnok Blog" · yield :head ก็กลไกเดียวกัน — รายละเอียดรอ Day 3)

3.1 · image_tag "logo.png" — ถ้ายังไม่มีไฟล์จะเกิดอะไร

บรรทัด <%= image_tag "logo.png", alt: "PEA" %> ในสไลด์ดูไม่มีพิษภัย แต่โปรเจกต์ที่ rails new สร้างให้ไม่มีไฟล์ logo.png · app/assets/images/ มีแค่ .keep · ผมลองใส่บรรทัดนี้บรรทัดเดียวใน view แล้ว curl: 

$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/img
500
$ tail log/development.log

Caused by: Propshaft::MissingAssetError (The asset 'logo.png' was not found in the load path.)

ทั้งหน้าพังเป็น 500 ไม่ใช่แค่รูปแตก · browser เห็นหน้า error สีแดงหัวข้อ Propshaft::MissingAssetError in Demo#img (Demo#img คือ action ทดลองของผม) · ต่างจากการเขียน <img src="/logo.png"> เองที่หน้ายังขึ้นแต่รูปแตกเงียบ ๆ — ผลดีคือรู้ตัวตั้งแต่ตอน dev ไม่ใช่ไปเจอรูปแตกตอนขึ้น production
พอวางไฟล์ PNG ไว้ที่ app/assets/images/logo.png แล้ว curl ใหม่: 

<img alt="PEA" src="/assets/logo-d6ac8881.png" />

ได้ชื่อไฟล์ที่มี digest ต่อท้ายเหมือน CSS — และนี่คือเหตุผลที่ห้ามเขียน /assets/logo.png เองตรง ๆ: ชื่อไฟล์จริงเปลี่ยนทุกครั้งที่รูปเปลี่ยน มีแค่ helper ที่รู้ชื่อล่าสุด

เขียน <a href="/posts/1"> เองคือเขียนที่อยู่บนซองด้วยลายมือ — ส่งได้ แต่ถ้าวันหนึ่งผู้รับย้ายบ้าน (แก้ URL ใน routes.rb) คุณต้องไล่แก้ซองทุกใบเอง และถ้าเผลอเขียนตัวอักษรแปลก ๆ ลงไป (<script>) ก็ไม่มีใครกรองให้
helper คือซองที่เคาน์เตอร์พิมพ์จ่าหน้าให้จากสมุดที่อยู่กลาง (route) — พิมพ์ที่อยู่ล่าสุดเสมอ · ตัวอักษรแปลก ๆ ถูกแปลงให้ปลอดภัย (escape) · และถ้าเป็นซองลงทะเบียน (form_with) ก็แปะสติกเกอร์รหัสยืนยัน (CSRF token) ให้เอง

ที่ไม่เหมือนกัน: เคาน์เตอร์ไปรษณีย์ที่หาที่อยู่ไม่เจอจะแค่บอกว่า "ไม่มีในระบบ" แล้วคุณเขียนเองต่อได้ · แต่ image_tag ที่หาไฟล์ไม่เจอทำให้ทั้งหน้าพังเป็น 500 (หัวข้อ 3.1) ไม่มีทางเลี่ยงไปเขียนเอง · และ helper ไม่ได้พิมพ์ซองครั้งเดียวแล้วเก็บไว้ — มันถูกเรียกใหม่ทุกครั้งที่ render หน้า (ผมลองเปลี่ยนเนื้อไฟล์ logo.png ระหว่างที่ server เปิดอยู่ curl รอบถัดไปได้ชื่อใหม่ logo-c933a130.png ทันที ไม่ต้อง restart)

4 · ความปลอดภัยที่ได้ตั้งแต่วันแรก (สไลด์หน้า 66)

สไลด์หน้า 66 บอกว่า Rails เปิดของกันภัยไว้ก่อน สี่อย่าง · ผมพิสูจน์ทีละอย่าง และมีสองอย่างที่รายละเอียดจริงต่างจากที่สไลด์เขียน

4.1 · XSS — <%= %> escape ให้เสมอ

XSS (Cross-Site Scripting) คือการที่ผู้ไม่หวังดีใส่ <script> ลงในข้อมูล เช่นตั้งชื่อร้านอาหารว่า <script>…</script> · ถ้าเว็บเอาชื่อนั้นไปพิมพ์ลงหน้าเว็บตรง ๆ browser ของทุกคนที่เปิดหน้านั้นจะรันสคริปต์ของเขา — ขโมย cookie ได้ กดปุ่มแทนได้
วิธีกันคือ escape: เปลี่ยน < เป็น &lt; · > เป็น &gt; ฯลฯ browser จะแสดงเป็นตัวอักษร แทนที่จะตีความเป็นแท็ก 

# app/controllers/demo_controller.rb
def xss
  @name = "<script>alert(1)</script>"
  @shop = %q(Tom & "Jerry's")
end
<%# app/views/demo/xss.html.erb %>
<p><%= @name %></p>
<p><%= raw @name %></p>
<p><%= @name.html_safe %></p>
<p><%== @name %></p>
<p><%= @shop %></p>

ห้าบรรทัดนี้ บรรทัดไหนบ้างที่ <script> ไปถึง browser เป็นแท็กจริง (= สคริปต์ถูกรัน)? แล้วบรรทัดสุดท้าย & กับเครื่องหมายคำพูดจะออกมาหน้าตายังไง? 

$ curl -s http://localhost:3000/xss   (ส่วนใน <main> · ตัด comment BEGIN/END ออก)
<p>&lt;script&gt;alert(1)&lt;/script&gt;</p>
<p><script>alert(1)</script></p>
<p><script>alert(1)</script></p>
<p><script>alert(1)</script></p>
<p>Tom &amp; &quot;Jerry&#39;s&quot;</p>

มีแค่บรรทัดแรกที่ปลอดภัย · อีกสามบรรทัดถัดมา (raw · .html_safe · <%==) ส่ง <script> ไปถึง browser เป็นแท็กจริง — สามวิธีนี้คือการเปิดช่องเองทั้งหมด (<%== สไลด์ไม่ได้พูดถึง แต่มันคือ raw แบบตัวสั้น ต้องระวังเท่ากัน)

บรรทัดสุดท้าย: สไลด์บอกว่า escape < > & · ผลจริงทำมากกว่านั้น — " กลายเป็น &quot; และ ' กลายเป็น &#39; ด้วย (กันไม่ให้ค่าหลุดออกจาก attribute เช่น value="…") · บนหน้าจอผู้ใช้ยังเห็น Tom & "Jerry's" ปกติ

แล้ว html_safe ทำอะไรกับ string จริง ๆ? มันไม่ได้ตรวจหรือทำความสะอาดอะไรเลย — แค่คืน object ชนิดใหม่ที่มีป้ายติดว่า "ปลอดภัยแล้ว ไม่ต้อง escape": 

$ bin/rails runner (ผลจาก p ทีละบรรทัด)
s = "<script>alert(1)</script>"
p s.html_safe?              # => false
p s.html_safe.html_safe?    # => true
p raw(s).class              # => ActiveSupport::SafeBuffer

ทั้งสามภาษาที่คุณรู้มีกติกาเดียวกันเป๊ะ: escape เป็นค่าเริ่มต้น · จะเปิดช่องต้องเขียนชื่อน่ากลัว ๆ เอง (ผมรันจริงทั้งสามฝั่งด้วยค่า <script>alert(1)</script> เดียวกัน):

🛂 เทียบให้เห็นภาพ — เครื่องสแกนกระเป๋าที่สนามบิน กับสติกเกอร์ "ตรวจแล้ว"

<%= %> คือเครื่องสแกนที่ทุกกระเป๋าต้องผ่าน ไม่มีข้อยกเว้น — ไม่ว่าข้อมูลจะมาจากไหน
html_safe / raw คือสติกเกอร์ "ตรวจแล้ว" ที่คุณติดเองได้ — กระเป๋าที่ติดสติกเกอร์จะเดินอ้อมเครื่องสแกน · ปัญหาคือไม่มีใครตรวจว่าคนติดสติกเกอร์ตรวจจริงหรือเปล่า (html_safe? แค่อ่านสติกเกอร์ ไม่ได้เปิดกระเป๋า)
เพราะฉะนั้นกฎคือ: ติดสติกเกอร์ได้เฉพาะกระเป๋าที่คุณแพ็กเองกับมือ (HTML ที่คุณเขียนเองในโค้ด) ห้ามติดให้กระเป๋าคนแปลกหน้า (ข้อมูลจากผู้ใช้ · params · ฐานข้อมูล)

ที่ไม่เหมือนกัน: เครื่องสแกนจริงเจอของอันตรายแล้วยึดทิ้ง · แต่ escape ไม่ได้ทิ้งอะไรเลย — มันแปลง <script> ให้เป็นตัวอักษรธรรมดา ผู้ใช้ยังเห็นคำว่า <script>alert(1)</script> ครบทุกตัวบนจอ แค่ browser ไม่รันมัน · ถ้าอยากตัดแท็กทิ้งจริง ๆ (เช่นยอมให้ <b> แต่ตัด <script>) นั่นเป็นงานของ helper อีกตัวชื่อ sanitize

4.2 · CSRF token — Rails ปฏิเสธฟอร์มที่ไม่ได้มาจากเว็บเรา

CSRF (Cross-Site Request Forgery) คือการหลอกให้ browser ของคุณ (ที่ login ค้างไว้) ส่งฟอร์มไปที่เว็บเราจากเว็บอื่น — เช่นเว็บของคนร้ายมีปุ่มที่แอบ POST ไป /posts/1 ให้ลบโพสต์ของคุณ · cookie ของคุณติดไปด้วยอัตโนมัติ เว็บเราจึงคิดว่าคุณกดเอง
วิธีกันคือ: ทุกฟอร์มที่เว็บเราสร้างจะมีรหัสลับ (authenticity_token) ซ่อนไว้ · เว็บคนร้ายอ่านรหัสนั้นไม่ได้ · request ไหนไม่มีรหัสที่ถูก Rails ปฏิเสธ
คุณเคยเจอแนวคิดเดียวกันแล้วในบท 50 — ค่า state ของ OAuth2 มีไว้กัน CSRF เหมือนกัน

token มาให้สองที่ — ใน <head> ทุกหน้า (จาก csrf_meta_tags ใน layout) และในทุกฟอร์มของ form_with:

$ curl -s http://localhost:3000/erb | grep csrf
    <meta name="csrf-param" content="authenticity_token" />
<meta name="csrf-token" content="N4c2BykwTZy9DdXtH3CFMUQMWlomLHcJnQmnEW0V98nd5NtY-5kL_XPQqzNQ5jXCoJ9pO8XDlbAcsgR9eM4I5w" />

ทีนี้ลองเป็นคนร้าย — ยิง POST ตรง ๆ ไม่มี token:

$ curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3000/posts -d 'post[title]=hack'
422
$ tail log/development.log
Started POST "/posts" for ::1 at 2026-11-01 00:13:46 +0700
Processing by PostsController#create as */*
  Parameters: {"post" => {"title" => "hack"}}
Can't verify CSRF token authenticity.
Completed 422 Unprocessable Content in 0ms (ActiveRecord: 0.0ms (0 queries, 0 cached) | GC: 0.0ms)

ActionController::InvalidAuthenticityToken (Can't verify CSRF token authenticity.):

ถูกปฏิเสธด้วย 422 ทั้งที่ PostsController ของผมไม่ได้เขียนอะไรเรื่องนี้เลย · DELETE /posts/1 แบบไม่มี token ก็ได้ 422 เหมือนกัน (สไลด์เขียนว่า "ทุก POST" — จริง ๆ คือทุก request ที่ไม่ใช่ GET/HEAD)
แล้วถ้าทำตัวเป็น browser จริง — เก็บ cookie ไว้ · หยิบ token จาก <meta> · ส่งกลับไปพร้อมกัน: 

$ curl -s -c jar.txt http://localhost:3000/helpers | grep -o 'name="csrf-token" content="[^"]*"'
# เอาค่า content ไปใส่เป็น TOKEN
$ curl -s -b jar.txt -X POST http://localhost:3000/posts \
    --data-urlencode "authenticity_token=$TOKEN" --data-urlencode 'post[title]=ข้าวซอย'
สร้างแล้ว: ข้าวซอย

⚠️ เรื่องที่ผมเจอเองตอนทดลอง: รอบแรกผมหยิบ token จากฟอร์มแก้ไขในหน้า /helpers (ฟอร์มที่ชี้ไป PATCH /posts/1) มาใช้ส่ง POST /posts — โดนปฏิเสธ 422 ทั้งที่มี token และ cookie ครบ · เพราะ Rails 8.1.4 เปิด per_form_csrf_tokens ไว้ (เช็คด้วย ActionController::Base.per_form_csrf_tokens ได้ true) — token ในฟอร์มผูกกับ URL + method ของฟอร์มนั้น เอาไปใช้กับฟอร์มอื่นไม่ได้ · token ใน <meta> เป็นตัวกลางที่ใช้ได้ทุกที่ (Turbo และ JavaScript ใช้ตัวนี้)

4.3 · SQL injection — where(title: x) ปลอดภัย · ต่อ string เองไม่ปลอดภัย

ประโยคในสไลด์: Post.where(title: params[:q]) ปลอดภัย "ยกเว้นเราไปต่อ string เอง" · (เรื่อง Active Record เต็ม ๆ รอ Day 2 · ตรงนี้ดูแค่ว่ากันได้จริงไหม) ลองกับค่าคลาสสิกของ SQL injection: 

# sql.rb — รันด้วย bin/rails runner sql.rb (ในฐานข้อมูลมี Post อยู่ 1 แถว)
ActiveRecord::Base.logger = ActiveSupport::Logger.new($stdout)   # ให้ SQL ที่รันพิมพ์ออกจอ
q = "x' OR '1'='1"
p Post.where(title: q).count
p Post.where("title = '#{q}'").count

ไม่มีโพสต์ไหนชื่อ x' OR '1'='1 เลย · สองบรรทัดนี้นับได้เท่าไหร่?

$ bin/rails runner sql.rb   (ตัดรหัสสีของ terminal ออก)
  Post Count (2.1ms)  SELECT COUNT(*) FROM "posts" WHERE "posts"."title" = 'x'' OR ''1''=''1' /*application='WongnokBlog'*/
0
  Post Count (1.2ms)  SELECT COUNT(*) FROM "posts" WHERE (title = 'x' OR '1'='1') /*application='WongnokBlog'*/
1

แบบ hash ได้ 0 — ถูกต้อง ไม่มีโพสต์ชื่อนั้น · Rails ใส่ ' ซ้อนเป็น '' ให้ ทั้งก้อนจึงเป็น "ข้อความ" ก้อนเดียว
แบบต่อ string เองได้ 1 — เงื่อนไขกลายเป็น OR '1'='1' ซึ่งจริงเสมอ ได้ทุกแถวในตาราง ถ้าเป็นหน้า login นี่คือเข้าได้โดยไม่ต้องรู้รหัสผ่าน

⚠️ จุดที่ไม่ตรงกับสไลด์: สไลด์บอกว่า "ใช้ bind parameter ให้อัตโนมัติ" · แต่ log ใน development ข้างบนไม่มี $1 — ค่าถูก escape แล้วฝังลงใน SQL ตรง ๆ · สาเหตุคือ config/environments/development.rb ที่ rails new สร้างเปิด config.active_record.query_log_tags_enabled = true (คือตัวที่เติม /*application='WongnokBlog'*/ ท้าย SQL) และ Rails 8.1.4 ปิด prepared statement เมื่อเปิดตัวนี้ (เช็คได้: Post.connection.prepared_statements ได้ false) · ผมลองตั้งเป็น false แล้วรันใหม่ log กลายเป็น WHERE "posts"."title" = $1 [["title", "x' OR '1'='1"]] — bind parameter จริงตามสไลด์ · ทั้งสองแบบปลอดภัยเท่ากัน แค่อย่าตกใจถ้าเปิด log แล้วไม่เจอ $1

4.4 · security header — มีจริง แต่ไม่ได้มาจาก middleware

$ curl -sI http://localhost:3000/erb   (เก็บเฉพาะบรรทัดแรก · header ความปลอดภัย · content-type — ที่เหลืออย่าง link · vary · etag · cache-control · set-cookie · x-request-id · x-runtime · server-timing ตัดออก)
HTTP/1.1 200 OK
x-frame-options: SAMEORIGIN
x-xss-protection: 0
x-content-type-options: nosniff
x-permitted-cross-domain-policies: none
referrer-policy: strict-origin-when-cross-origin
content-type: text/html; charset=utf-8

สามตัวที่สไลด์พูดถึง (X-Frame-Options · X-Content-Type-Options · Referrer-Policy) มีจริงครบ และแถมอีกสองตัว · ภาษาคน: SAMEORIGIN = เว็บอื่นเอาหน้าเราไปฝังใน <iframe> ไม่ได้ (กันหลอกให้กดปุ่มที่ซ่อนอยู่) · nosniff = ห้าม browser เดาชนิดไฟล์เอง · x-xss-protection: 0 = ปิดตัวกรอง XSS รุ่นเก่าของ browser ที่สร้างปัญหามากกว่าช่วย (Rails ตั้งใจปิด)

⚠️ จุดที่ไม่ตรงกับสไลด์: สไลด์เขียนว่า header ชุดนี้ "ตั้งมาให้แล้วใน default middleware stack" · ของจริงเป็นค่า config.action_dispatch.default_headers ที่ถูกแปะตอนสร้าง response ของ controller (ActionDispatch::Response.create ใน source ของ actionpack-8.1.4) ไม่ใช่ middleware · ผลที่ตามมาเห็นได้จริง: curl -sI http://localhost:3000/icon.png (ไฟล์ใน public/ ที่ไม่ผ่าน controller) ได้แค่ last-modified · content-type · content-length — ไม่มี header ความปลอดภัยสักตัว · และ Content-Security-Policy ไม่ได้เปิดมาให้ (ไฟล์ config/initializers/content_security_policy.rb เป็น comment ทั้งไฟล์ · csp_meta_tag ใน layout จึงไม่พิมพ์อะไรออกมา)

ประโยคปิดของสไลด์หน้า 66 สำคัญที่สุดในบทนี้ — สไลด์เรียกมันว่า "ด้านที่ดีที่สุดของ Omakase" (Rails เลือกของให้ครบชุดแบบ "แล้วแต่เชฟ" ที่บท 90 เล่าไว้): ของพวกนี้ถูกเปิดไว้ก่อน แต่ถ้าเราปิดมันโดยไม่รู้ตัว จะไม่มีใครเตือน · ปิดง่ายแค่ไหน? raw คำเดียว · "#{q}" หนึ่งคู่ปีกกา — ทั้งคู่ไม่มี error ไม่มี warning ตอนรัน (มีเครื่องมือหนึ่งที่ช่วยได้บางส่วน อยู่ในเฉลยภารกิจ)

🗣 ศัพท์ที่เพิ่งเรียนไป
XSS · escape · html_safe / SafeBuffer
XSS = ยัดสคริปต์ผ่านข้อมูล · escape = แปลงอักขระพิเศษให้เป็นตัวอักษร · html_safe = ป้าย "ไม่ต้อง escape" บน ActiveSupport::SafeBuffer · เวลาเจอ raw หรือ html_safe ใน PR ให้ถาม senior ว่า "ค่านี้มาจากผู้ใช้ได้ไหม" — คำถามเดียวนี้จับ XSS ได้เกือบหมด
CSRF · authenticity_token
CSRF = หลอก browser ให้ส่งฟอร์มจากเว็บอื่น · authenticity_token = รหัสที่พิสูจน์ว่าฟอร์มมาจากเว็บเรา · เจอ ActionController::InvalidAuthenticityToken ให้บอก AI ว่า "the request is missing the CSRF token; the form was not built with form_with, or the token is from a different form" — อย่ายอมรับคำแนะนำให้ปิด protect_from_forgery เพื่อให้ผ่าน
SQL injection · bind parameter
SQL injection = ข้อมูลกลายเป็นคำสั่ง SQL · bind parameter = ส่งค่าแยกจากคำสั่ง ($1) · พิมพ์บอก AI ได้ว่า "never interpolate params into where strings; use hash conditions or ? placeholders"
security headers · default_headers
header ที่สั่ง browser ให้เข้มงวดขึ้น · Rails ตั้งไว้ใน config.action_dispatch.default_headers · ถาม senior ได้ว่า "ใน production เรามี CSP ไหม ตั้งที่ Rails หรือที่ reverse proxy" — เพราะ Rails ไม่ได้เปิดให้

5 · ภารกิจ — หน้าทักทายที่พิสูจน์ความปลอดภัยด้วย curl

🎯 ภารกิจ

ในโปรเจกต์ wongnok_blog ของคุณ (จากบท 98) ทำหน้า /hello?name=… ที่:

  1. เพิ่ม route get "hello" => "pages#hello" · สร้าง PagesController#hello ที่ตั้ง @name จาก params[:name] ถ้าว่างให้เป็น "แขก" (ใช้ .presence จากบท 94)
  2. view มี: comment <%# บรรทัดแรกที่ห้ามโผล่ใน browser · <h1>สวัสดี …</h1> · บรรทัดที่ใช้ pluralize บอกว่าชื่อยาวกี่ตัวอักษร · และฟอร์มค้นหาด้วย form_with url: hello_path, method: :get
  3. พิสูจน์ด้วย curl สี่ข้อ: (ก) ส่ง name=<script>alert(1)</script> แล้ว <h1> ถูก escape · (ข) comment <%# ไม่อยู่ใน response (grep -c ได้ 0) · (ค) header x-frame-options มีจริง · (ง) ฟอร์ม GET มีหรือไม่มี authenticity_token? เปลี่ยนเป็น method: :post แล้วนับใหม่
  4. ลองทำผิดโดยตั้งใจ: เปลี่ยน <%= @name %> เป็น <%= raw @name %> แล้วดูผล (ก) อีกครั้ง — จากนั้นแก้กลับ
# config/routes.rb (เพิ่มบรรทัดนี้)
get "hello" => "pages#hello"

# app/controllers/pages_controller.rb
class PagesController < ApplicationController
  def hello
    @name = params[:name].presence || "แขก"
  end
end
<%# app/views/pages/hello.html.erb — บรรทัดนี้ห้ามโผล่ใน browser %>
<h1>สวัสดี <%= @name %></h1>
<p>ชื่อนี้ยาว <%= pluralize(@name.length, "character") %></p>
<%= form_with url: hello_path, method: :get do |f| %>
  <%= f.text_field :name %>
  <%= f.submit "ทักทาย" %>
<% end %>

ผลรันจริง (%3C = < · %3E = > · %2F = / ที่ต้อง encode ใน URL):

# (ก) escape
$ curl -s 'http://localhost:3000/hello?name=%3Cscript%3Ealert(1)%3C%2Fscript%3E' | grep -o '<h1>.*</h1>'
<h1>สวัสดี &lt;script&gt;alert(1)&lt;/script&gt;</h1>

# (ข) comment ไม่หลุด
$ curl -s http://localhost:3000/hello | grep -c 'ห้ามโผล่'
0

# (ค) header
$ curl -sI http://localhost:3000/hello | grep -i x-frame
x-frame-options: SAMEORIGIN

# (ง) token ในฟอร์ม — method: :get
$ curl -s http://localhost:3000/hello | grep -c 'name="authenticity_token"'
0
# (ง) เปลี่ยนเป็น method: :post แล้วนับใหม่
$ curl -s http://localhost:3000/hello | grep -c 'name="authenticity_token"'
1

ข้อ (ง) คือคำตอบที่หลายคนทายผิด: ฟอร์ม GET ไม่มี token เพราะ GET ต้องเป็น request ที่อ่านอย่างเดียว ไม่เปลี่ยนข้อมูล (บท 36 เรื่อง safe method) จึงไม่ต้องกัน CSRF · ระวังด้วยว่าต้อง grep name="authenticity_token" ทั้งก้อน — ถ้า grep แค่ authenticity_token จะไปเจอ <meta name="csrf-param" content="authenticity_token"> ใน <head> แทน
ไม่ส่ง name เลยจะได้ <h1>สวัสดี แขก</h1> กับ ชื่อนี้ยาว 3 characters — "แขก".length เป็น 3 เพราะ Ruby นับตามตัวอักษร (แ · ข · ก) ส่วนชื่อ <script>alert(1)</script> ได้ 25 characters

ข้อ 4 — เปลี่ยนเป็น raw แล้วรัน (ก) ซ้ำ:

<h1>สวัสดี <script>alert(1)</script></h1>

ไม่มี error · หน้าโหลดปกติ · แต่ใครส่งลิงก์นี้ให้เพื่อนก็รันสคริปต์ในเครื่องเพื่อนได้ — นี่คือ "ปิดโดยไม่รู้ตัว จะไม่มีใครเตือน" ของสไลด์ · ตัวช่วยที่ rails new ใส่มาให้แล้วใน Gemfile คือ Brakeman (เครื่องมือสแกนช่องโหว่จากโค้ด) · ผมรันตอนที่ยังเป็น raw อยู่: 

$ bin/brakeman -q --no-pager   (ตัดเฉพาะส่วน Warnings)
== Warnings ==

Confidence: High
Category: Cross-Site Scripting
Check: CrossSiteScripting
Message: Unescaped parameter value
Code: params[:name]
File: app/views/pages/hello.html.erb
Line: 2

จับได้แม่นถึงบรรทัด · แก้กลับเป็น <%= @name %> แล้วรันใหม่ได้ No warnings found · แต่ Brakeman ไม่ได้จับทุกอย่าง — raw @name ในหน้า /xss ของผมที่ค่ามาจาก string ในโค้ดตรง ๆ ไม่ถูกเตือน เพราะมันดูออกว่าค่าไม่ได้มาจากผู้ใช้ · การเขียนเทสอัตโนมัติแบบจริงจังรอ Day 4

ตัวเลือกที่ 1 คือหน้าที่ของ sanitize ไม่ใช่ html_safe · ตัวเลือกที่ 2 กลับด้าน — มันทำให้ไม่ถูก escape · ตัวเลือกที่ 3 ผิด — ผลรันทั้งหมดในบทนี้เป็น development และ html_safe ก็เปิดช่องจริง · จุดที่ต้องจำ: html_safe / raw / <%== คือ "ฉันรับผิดชอบเอง" — ใช้ได้กับ HTML ที่คุณเขียนเองในโค้ดเท่านั้น ห้ามใช้กับค่าที่ผู้ใช้ส่งมา

ตัวเลือกที่ 1 ถูก · ผลรันจริงในหัวข้อ 4.2 — Rails ปฏิเสธทุก request ที่ไม่ใช่ GET/HEAD ที่ไม่มี token ถูกต้อง โดยที่ controller ไม่ต้องเขียนอะไรเลย

ตัวเลือกที่ 2 ผิด — Rails ไม่รู้และไม่สนว่าใครส่ง มันดูแค่ว่ามี token ไหม · ตัวเลือกที่ 3 สับสนหน้าที่ — x-frame-options คุมเรื่องฝังหน้าใน <iframe> ไม่ได้บล็อก request · ตัวเลือกที่ 4 ผิด — rails new ไม่ได้สร้างระบบ login ให้ (Rails 8 มีคำสั่ง bin/rails g authentication แต่ต้องสั่งเอง · คอร์สนี้ Day 4 ใช้ Keycloak) · จุดที่ต้องจำ: ฟอร์มที่สร้างด้วย form_with มี token ให้เอง · ถ้าเจอ InvalidAuthenticityToken ให้หาว่าฟอร์มไหนไม่ได้สร้างด้วย helper — อย่าแก้ด้วยการปิดระบบกัน
