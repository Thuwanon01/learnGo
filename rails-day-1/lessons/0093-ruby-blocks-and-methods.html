1 · Block — ก้อนโค้ดที่ส่งติดท้าย method

คุณเคยส่ง "ฟังก์ชัน" เข้าไปให้ฟังก์ชันอื่นมาแล้วทั้งสองภาษา · ใน Go คือ closure ที่เขียน func(…) {…} แล้วส่งเป็น argument · ใน TypeScript คือ callback แบบ arrow function ที่ใช้กับ .map ใน บทเรียน 67

Ruby ก็ทำเรื่องเดียวกัน แต่ไม่ได้ส่งเป็น argument — มันมีช่องพิเศษแยกออกมาให้ เรียกว่า block เขียนห้อยไว้ท้ายการเรียก method นอกวงเล็บ นี่คือสไลด์หน้า 22 ทั้งสามภาษา (ผมเติมให้ครบจนรันได้จริง):

GoTypeScriptRuby
 
f := func(n int) int {
  return n * 2
}
apply(xs, f)
 
apply(xs, n => n * 2)
 
xs.map { |n| n * 2 }

xs.each do |n|
  puts n
end
ฟังก์ชันเป็นค่าธรรมดา ส่งเข้าไปเป็น argument ตัวหนึ่ง · ไม่มี syntax พิเศษ callback ก็เป็น argument ธรรมดาตัวหนึ่ง block ไม่ใช่ argument · เป็นช่องพิเศษที่ห้อยท้าย · |n| คือชื่อของที่ method ส่งเข้ามาให้
[2 4 6] [ 2, 4, 6 ] [2, 4, 6] แล้วพิมพ์ 1 2 3 คนละบรรทัด

แถวสุดท้ายคือผลรันจริง (Go ต้องเขียน apply เองเพราะไม่มีใน standard library · go build ผ่าน · TS ผ่าน tsc --noEmit --strict)

"ไม่ใช่ argument" หมายความว่ายังไง? พิสูจน์ได้สองทาง — method ที่นับจำนวน argument จะไม่นับ block และ method รู้ตัวว่ามี block มาไหมผ่าน block_given? · ส่วนการเรียกใช้ block จากข้างใน method ใช้คำว่า yield: 

def twice(label)
  puts "start #{label}"
  yield 1          # เรียก block ครั้งที่ 1 ส่ง 1 เข้าไป
  yield 2          # เรียก block ครั้งที่ 2 ส่ง 2 เข้าไป
  puts "end #{label}"
end

twice("A") { |n| puts "got #{n}" }

def count_args(*args) = args.size
p count_args(1, 2) { "ignored?" }

def has_block? = block_given?
p has_block?
p has_block? { }
# ผลรันจริง

count_args ได้ 2 ไม่ใช่ 3 — block ไม่ถูกนับเป็น argument · ส่วน method ที่ yield แต่ไม่มีใครส่ง block มา จะพังตอนรันด้วย no block given (yield) (LocalJumpError)

กฎที่สไลด์หน้า 22 ให้ไว้ มีสามข้อ:

  1. บรรทัดเดียวใช้ { } — xs.map { |n| n * 2 }
  2. หลายบรรทัดใช้ do … end — เหมือนตัวอย่าง each ด้านบน
  3. block ส่งได้ก้อนเดียวต่อการเรียกหนึ่งครั้ง — ลองเขียน xs.map { |n| n * 2 } { |n| n * 3 } ได้ syntax errors found (SyntaxError) ตั้งแต่ก่อนรัน

ข้อ 1 กับ 2 เป็นธรรมเนียมของทีม ไม่ใช่กฎของภาษา (สไลด์ก็เขียนว่า "กฎที่ทีมส่วนใหญ่ใช้") · แต่สองแบบนี้ไม่ได้เหมือนกันร้อยเปอร์เซ็นต์ — หัวข้อถัดไปจะรันให้ดูว่าต่างกันตรงไหน

🧰 เทียบให้เห็นภาพ — โพสต์อิทคำสั่งที่แปะมากับกล่องพัสดุ

each คือพนักงานคลังสินค้าที่รู้วิธีหยิบของออกจากกล่องทีละชิ้น แต่ไม่รู้ว่าหยิบแล้วต้องทำอะไรต่อ · คุณจึงแปะโพสต์อิทหนึ่งแผ่นไว้ที่กล่องว่า "หยิบได้ชิ้นไหน ให้ตะโกนชื่อมันออกมา" (นั่นคือ block do |n| puts n end)
พนักงานหยิบชิ้นที่ 1 → อ่านโพสต์อิท → ทำตาม · หยิบชิ้นที่ 2 → อ่านโพสต์อิทแผ่นเดิม → ทำตาม · คำว่า yield คือจังหวะ "หยิบโพสต์อิทขึ้นมาอ่าน"

ที่ไม่เหมือนกัน: โพสต์อิทจริงเป็นกระดาษเฉย ๆ แต่ block มองเห็นตัวแปรรอบ ๆ ที่มันถูกเขียน (เป็น closure เหมือนใน Go) · และพนักงานจะไม่อ่านโพสต์อิทเลยก็ได้ — ถ้า method ไม่ yield block ที่คุณแปะไว้ก็ถูกทิ้งเงียบ ๆ ไม่มี error (เหมือน count_args ข้างบน)

🗣 ศัพท์ที่เพิ่งเรียนไป
block
ก้อนโค้ดที่ห้อยท้ายการเรียก method ด้วย { } หรือ do … end · ไม่ใช่ argument ธรรมดา · (คู่มือทางการเรียกช่องนี้ว่า block argument — หมายถึงช่องพิเศษท้ายสุดที่แยกจาก argument ในวงเล็บ ไม่ถูกนับรวม) · พิมพ์ถาม AI ได้ว่า "this method takes a block — what does it yield to the block?" จะได้รู้ว่า |…| ตรงนั้นได้ค่าอะไรมา
yield
คำสั่งใน method ที่แปลว่า "เรียก block ที่ส่งมาตอนนี้ แล้วส่งค่านี้เข้าไป" · ถ้าไม่มี block แต่สั่ง yield จะได้ LocalJumpError
block parameter (|n|)
ชื่อตัวแปรที่รับค่าที่ method yield ออกมา · เทียบได้กับ parameter ของ arrow function n => … ใน TS
closure
ฟังก์ชัน (หรือ block) ที่จำตัวแปรรอบตัวตอนที่มันถูกเขียนได้ · block ของ Ruby เป็น closure เหมือน func ใน Go · ถาม senior ได้ว่า "block ตรงนี้ไปแก้ตัวแปรข้างนอกหรือเปล่า" เวลาอ่านโค้ดที่ไล่ยาก

2 · กับดัก { } vs do…end — block ไปเกาะ method ผิดตัว

สองบรรทัดนี้ต่างกันแค่ใช้ { } กับ do…end · ถ้ากฎในหัวข้อที่แล้วเป็นแค่ "เรื่องความสวยงาม" ผลก็ต้องเหมือนกัน 

puts [1, 2].map { |n| n * 2 }
puts "---"
puts [1, 2].map do |n| n * 2 end
puts "---"

สองบรรทัดแรกกับสองบรรทัดหลังจะพิมพ์อะไร? ต่างกันไหม? มี error หรือ warning ไหม?

$ ruby prec.rb
2
4
---
#<Enumerator:0x000000012480d520>
---

ต่างกันจริง · บรรทัดแรกได้ 2 กับ 4 ตามที่หวัง · บรรทัดที่สามได้ #<Enumerator:0x…> แทน (เลขฐานสิบหกเปลี่ยนทุกครั้งที่รัน) · ไม่มี error · exit code 0 · รันด้วย ruby -w ก็ไม่มี warning สักบรรทัด

นี่แหละที่ทำให้กับดักนี้อันตราย — โปรแกรมไม่พัง แค่ได้ค่าผิด

ทำไม? เพราะ { } เกาะ method ที่อยู่ใกล้ที่สุด ส่วน do…end เกาะ method ที่อยู่ไกลที่สุด (ตัวซ้ายสุดในบรรทัด) · คู่มือทางการของ Ruby เขียนไว้ตรง ๆ ว่า do end has lower precedence than { } · Ruby จึงอ่านสองบรรทัดนั้นแบบนี้:

ที่คุณเขียนที่ Ruby อ่านผล
puts [1, 2].map { |n| n * 2 } puts([1, 2].map { |n| n * 2 }) map ได้ block → คืน [2, 4] → puts พิมพ์ทีละตัว
puts [1, 2].map do |n| n * 2 end puts([1, 2].map) do |n| n * 2 end map ไม่ได้ block → คืน Enumerator (ของที่ "ยังรอ block อยู่") · block ไปตกที่ puts ซึ่งไม่สนใจ block เลย

วิธีหนีมีสามทาง ผลรันจริงของทั้งสามได้ 2 กับ 4 เหมือนกัน: ใช้ { } เมื่ออยู่บรรทัดเดียว · ใส่วงเล็บให้ puts( … ) · หรือเก็บลงตัวแปรก่อน x = [1, 2].map do |n| n * 2 end แล้วค่อย puts x (การกำหนดค่าไม่ใช่การเรียก method block จึงไม่มีที่ให้เกาะผิด)

⚠️ ตอนอ่าน Rails จะเจอ do…end อยู่ทุกไฟล์ เช่นสไลด์หน้า 22 ยกตัวอย่าง respond_to do |format| ใน controller · บรรทัดนั้นปลอดภัยเพราะมี method ตัวเดียว (respond_to) block ไม่มีทางเกาะผิด · กับดักจะโผล่เฉพาะตอนที่มีสอง method ในบรรทัดเดียวโดยไม่มีวงเล็บ — ตัวที่เจอบ่อยที่สุดคือ puts / p ที่เราแปะหน้าบรรทัดตอน debug นี่แหละ

ส่วน format ใน respond_to do |format| คืออะไร? สไลด์บอกว่าเป็น "object ที่ Rails ส่งเข้ามาใน block" · ผมแอบพิมพ์ class ของมันใน controller จริงดู ได้ ActionController::MimeResponds::Collector — เป็นตัวเก็บว่า "ถ้าขอ HTML ทำแบบนี้ · ถ้าขอ JSON ทำแบบนี้" · ตอนนี้แค่จำว่า |format| คือของที่ respond_to yield ออกมาให้ ก็พอ รายละเอียดรอ บทเรียน 102 และวันถัด ๆ ไป

3 · Method คืนค่าบรรทัดสุดท้ายเอง — ไม่ต้องมี return

ใน Go กับ TS คุณต้องพิมพ์ return ทุกครั้งที่จะส่งค่ากลับ · Ruby กลับด้าน: method คืนค่าของบรรทัดสุดท้ายที่ถูกรันเสมอ โดยไม่ต้องบอก (สไลด์หน้า 23)

GoTypeScriptRuby
 
func Add(a, b int) int {
  return a + b
}
 
function add(a, b) {
  return a + b
}
 
def add(a, b)
  a + b        # ไม่มี return
end

def add(a, b) = a + b
# endless method (3.0+)
ต้องมี return · ต้องระบุ type ต้องมี return (ยกเว้น arrow แบบสั้น (a, b) => a + b) บรรทัดสุดท้ายคือค่าที่คืน · แบบ def … = … ใช้ได้เมื่อมีนิพจน์เดียว

p add(2, 3) ได้ 5 ทั้งสองแบบ (รันจริงแล้ว) · แบบที่สองชื่อ endless method เพราะไม่มี end ปิดท้าย — เทียบได้กับ arrow function แบบสั้นของ TS นั่นเอง

"บรรทัดสุดท้าย" หมายถึงบรรทัดสุดท้ายที่ถูกรันจริง ไม่ใช่บรรทัดล่างสุดในไฟล์ · เช่นใน if/else ค่าที่คืนคือบรรทัดสุดท้ายของกิ่งที่ถูกเลือก: 

def grade(score)
  if score >= 50
    "pass"
  else
    "fail"
  end
end
p grade(70)   # => "pass"
p grade(10)   # => "fail"

return ยังมีอยู่และยังใช้กันจริง — ใช้ออกก่อนกำหนด แบบ guard clause ที่คุณเรียนใน บทเรียน 04: return "negative" if n < 0 · สิ่งที่ Rubyist ไม่ทำคือเขียน return ที่บรรทัดสุดท้าย เพราะมันซ้ำซ้อน

⚠️ กับดัก: แปะ puts ไว้บรรทัดสุดท้ายแล้วค่าหาย

def oops(a, b)
  a + b
  puts "done"     # เพิ่มบรรทัดนี้ตอน debug
end
p oops(2, 3)
# ผลรันจริง
done
nil

พอแทรก puts ไว้ท้ายสุด บรรทัดสุดท้ายก็เปลี่ยนเป็น puts "done" ซึ่งคืน nil เสมอ (หัวข้อ 6 จะพิสูจน์) · method ที่เคยคืน 5 จึงคืน nil ทันที ทั้งที่ไม่ได้แตะบรรทัด a + b เลย · ใน Go เรื่องนี้เกิดไม่ได้เพราะ return ระบุชัดว่าคืนอะไร

สไลด์หน้า 23 ยกตัวอย่างฝั่ง Rails ไว้หนึ่งบรรทัด ซึ่งรวมทุกอย่างของหัวข้อนี้ไว้ในที่เดียว: 

def published? = published_at.present?

อ่านว่า: method ชื่อ published? (endless) คืนค่าว่า published_at "มีค่า" หรือเปล่า · ผมลองใส่ใน class ธรรมดาแล้วรันจริง — ได้ false ตอนยังไม่ตั้งเวลา และ true หลังตั้ง · แต่ต้องรันด้วย Active Support (ruby -ractive_support/all) เพราะ present? ไม่ใช่ของ Ruby เปล่า ๆ · รันด้วย Ruby ล้วนได้: 

pub.rb:3:in 'Post#published?': undefined method 'present?' for nil (NoMethodError)

ในแอป Rails ไม่ต้องห่วงเรื่องนี้ เพราะ Rails โหลด Active Support ให้ตั้งแต่บูต · แต่ถ้าวันหนึ่งคุณเขียนสคริปต์ Ruby แยกนอก Rails แล้วเจอ error นี้ ให้นึกถึงย่อหน้านี้

🧰 เทียบให้เห็นภาพ — พนักงานที่ยื่นของในมือให้ตอนเลิกงาน

ใน Go เหมือนพนักงานที่ต้องเดินมายื่นของให้คุณเอง พร้อมพูดว่า "นี่ครับ" (return) — ถ้าไม่พูด คุณไม่ได้อะไรเลย และ compiler จะดุ · ใน Ruby เหมือนพนักงานที่พอหมดเวลางาน ของชิ้นสุดท้ายที่ถืออยู่ในมือจะถูกยื่นให้คุณอัตโนมัติ

ที่ไม่เหมือนกัน: พนักงานจริงจะรู้ตัวว่า "เอ๊ะ ชิ้นนี้ไม่ใช่ของที่ลูกค้าสั่ง" แต่ Ruby ไม่รู้ — ถ้างานสุดท้ายคือ puts ของในมือคือ nil มันก็ยื่น nil ให้หน้าตาเฉย ไม่มี error ไม่มี warning

🗣 ศัพท์ที่เพิ่งเรียนไป
implicit return
การที่ method คืนค่าบรรทัดสุดท้ายเองโดยไม่ต้องเขียน return · ถาม senior ได้ว่า "ทีมนี้ยอมให้เขียน explicit return ที่บรรทัดสุดท้ายไหม" — ในแอปที่สร้างด้วย rails new ถ้าเขียน return ไว้บรรทัดสุดท้าย bin/rubocop จะฟ้อง Style/RedundantReturn: Redundant return detected. (ลองแล้ว)
endless method
method แบบบรรทัดเดียว def name(args) = expression · มีตั้งแต่ Ruby 3.0 · ใช้ได้เมื่อตัวเนื้อเป็นนิพจน์เดียว
early return / guard clause

4 · Keyword argument — ส่งค่าด้วยชื่อ ไม่ต้องจำลำดับ

ซ้ายมือของสไลด์หน้า 24 คือ method ที่รับค่าด้วยชื่อ · title: ที่ไม่มีค่าตามหลัง = ต้องส่ง · body: "" กับ draft: false = มีค่า default ไม่ส่งก็ได้ 

def create(title:, body: "", draft: false)

end

🧰 เทียบให้เห็นภาพ — แบบฟอร์มที่มีช่องติดป้าย vs ใส่ของลงกล่องเรียงแถว

argument ธรรมดาเหมือนใส่ของลงกล่องที่วางเรียงกัน — กล่องแรกคือชื่อเรื่อง กล่องที่สองคือเนื้อหา ใส่สลับเมื่อไหร่ได้ของผิดช่องทันที · keyword argument เหมือนแบบฟอร์มที่ทุกช่องมีป้ายชื่อ ("ชื่อเรื่อง: ___") — กรอกช่องไหนก่อนก็ได้ · ช่องที่มีดอกจัน (title:) เว้นว่างไม่ได้ · ช่องที่มีค่าพิมพ์ไว้ให้แล้ว (draft: false) ไม่กรอกก็ได้

ที่ไม่เหมือนกัน: แบบฟอร์มจริงมีเจ้าหน้าที่ตรวจตอนยื่น แต่ Ruby ไม่มีใครตรวจล่วงหน้าเลย (ไม่เหมือน tsc) — ช่องดอกจันที่ว่างจะถูกจับได้ ตอนโปรแกรมรันมาถึงบรรทัดนั้นจริง ๆ เท่านั้น · บรรทัดที่ไม่เคยถูกรัน ไม่มีวันรู้ว่าผิด — นี่คือเหตุผลที่คนเขียน Ruby ให้ความสำคัญกับเทสมาก (Day 4 รออยู่)

5 · ? กับ ! — แค่ตัวอักษรในชื่อ แต่ทั้งวงการถือเป็นสัญญา

ประโยคที่สำคัญที่สุดของสไลด์หน้า 24 คือ: ? และ ! ไม่ใช่ syntax ของภาษา — เป็นแค่ตัวอักษรในชื่อ method · Ruby ยอมให้ชื่อ method ลงท้ายด้วยสองตัวนี้ได้ แต่ไม่ได้บังคับความหมายอะไรเลย · ความหมายมาจากข้อตกลงของคนเขียน Ruby ทั้งวงการ:

ท้ายชื่อข้อตกลงตัวอย่าง (ผลรันจริง)
? ถามคำถาม yes/no → คืนค่าที่ใช้เป็นจริง/เท็จ [].empty? → true · [1].empty? → false
! "อันตรายกว่าตัวที่ไม่มี !" — ใน Ruby core หมายถึงแก้ตัวเดิม name.upcase! เปลี่ยน name ตรง ๆ

"ไม่บังคับ" จริงแค่ไหน? ลองดู — 5.nonzero? ซึ่งเป็น method ของ Ruby เองคืน 5 (ไม่ใช่ true) และ 0.nonzero? คืน nil · method ที่เราเขียนเองอย่าง def ok? = "yes" ก็คืน "yes" ได้โดยไม่มีใครห้าม · คู่มือทางการก็เขียนไว้ว่า method ที่ลงท้าย ? "may not always return just true or false" · ทำไม 5 กับ nil ถึงใช้แทนจริง/เท็จได้ — นั่นคือเรื่องของ บทเรียน 94

upcase vs upcase! — รันให้เห็นว่า "แก้ตัวเดิม" แปลว่าอะไร

name = "abc"
up = name.upcase     # ไม่มี ! → สร้าง string ใหม่
p up                   # => "ABC"
p name                 # => "abc"   ← ตัวเดิมไม่เปลี่ยน

name2 = "abc"
r = name2.upcase!     # มี ! → แก้ตัวเดิม
p r                    # => "ABC"
p name2                # => "ABC"   ← ตัวเดิมเปลี่ยนแล้ว

ตรงตามสไลด์ทุกตัว · แต่สไลด์ไม่ได้บอกว่า upcase! คืนอะไร — และตรงนี้แหละที่เป็นกับดัก: 

s = "ABC"         # ตัวใหญ่อยู่แล้ว
r = s.upcase!
p r
p s

r กับ s เป็นอะไร?

# ผลรันจริง
nil
"ABC"

r เป็น nil · method ที่มี ! ใน Ruby core หลายตัว คืน nil เมื่อไม่มีอะไรเปลี่ยน — เอกสารทางการเขียน signature ไว้ว่า upcase!(mapping) → self or nil

ผลที่ตามมาคือ ถ้าเอาไปต่อ method ทันที จะพังเฉพาะบางข้อมูล:

# name = "ADMIN" → พังแบบนี้

puts name.upcase!.length
                 ^^^^^^^

นี่คือบั๊กประเภทที่เทสด้วยข้อมูลตัวเล็กผ่านหมด แล้วไปพังบน production เมื่อมีคนกรอกตัวใหญ่ · กฎง่าย ๆ: method ที่มี ! ให้เรียกเป็นบรรทัดเดี่ยว ๆ อย่าเอาค่าที่มันคืนไปใช้ต่อ

อีกเรื่องที่ "แก้ตัวเดิม" ส่งผลมากกว่าที่คิด — ถ้าสองตัวแปรชี้ไปที่ string ก้อนเดียวกัน แก้ทางหนึ่ง อีกทางก็เห็นด้วย (หลักการเดียวกับ slice aliasing ใน บทเรียน 06): 

t = "hello"
t2 = t            # ไม่ได้ก็อป — t2 ชี้ไปที่ก้อนเดียวกับ t
t.upcase!
p t2              # => "HELLO"

💡 warning ที่คุณจะเจอเร็ว ๆ นี้: Ruby กำลังค่อย ๆ เปลี่ยนให้ string ที่พิมพ์ตรง ๆ ในโค้ด (literal) แก้ไม่ได้ · ใน Ruby 4.0.9 การ upcase! string แบบนั้นยังทำได้ และรันปกติไม่มีอะไรขึ้น · แต่ถ้าเปิดการเตือนเรื่อง deprecated (รันด้วย ruby -w หรือ minitest ซึ่งเปิดให้อัตโนมัติ — ภารกิจท้ายบทจะเจอ) จะเห็น warning: literal string will be frozen in the future · และถ้าไฟล์มีบรรทัดแรก # frozen_string_literal: true จะพังทันทีด้วย can't modify frozen String: "abc" (FrozenError) · ทางออกคือสร้างสำเนาที่แก้ได้ก่อนด้วย "abc".dup

save vs save! — ใน Rails ! แปลว่า "พังให้ดังไปเลย"

มุมขวาของสไลด์หน้า 24 มีอีกคู่: post.save คืน false ถ้าไม่ผ่าน · post.save! raise ถ้าไม่ผ่าน · ตัวนี้เป็นของ Active Record ซึ่งจะเรียนจริงใน Day 2 · ตอนนี้ขอแค่หลักการ — ผมสร้าง model Post ที่บังคับว่าต้องมี title ในแอปทดสอบ แล้วลองบันทึกโพสต์ที่ title ว่าง: 

# bin/rails runner — ผลรันจริง
post.save    # => false   (ไปต่อเงียบ ๆ ถ้าไม่มีใครเช็ค)
post.save!   # raise ActiveRecord::RecordInvalid
             #   "Validation failed: Title can't be blank"
post.update(title: "")    # => false
post.update!(title: "")   # raise ActiveRecord::RecordInvalid

สังเกตว่า ! ใน Rails ไม่ได้แปลว่า "แก้ตัวเดิม" แบบ upcase! — ทั้ง save และ save! แก้ฐานข้อมูลเหมือนกัน · ! ตรงนี้แปลว่า "ถ้าไม่สำเร็จ จะไม่ยอมเงียบ" · ความหมายร่วมของทั้งสองแบบคือข้อที่สไลด์เขียนไว้: ตัวที่มี ! อันตรายกว่าตัวที่ไม่มี

คนเขียน Go จะคุ้นกับปัญหาของ save ทันที — มันเหมือนฟังก์ชันที่คืน error ซึ่งลืมเช็คได้ (บทเรียน 05) · save ที่คืน false แล้วไม่มีใครดู ผ่านเงียบ ๆ ทุกครั้ง · save! คือทางเลือกที่ "ลืมเช็คไม่ได้" เพราะถ้าไม่ผ่าน โปรแกรมหยุดทันที

🧰 เทียบให้เห็นภาพ — ถ่ายเอกสารแล้วแก้บนสำเนา vs เขียนทับต้นฉบับ

name.upcase คือถ่ายเอกสารก่อน แล้วแก้บนสำเนา — ต้นฉบับในแฟ้มเหมือนเดิมทุกอย่าง คุณได้กระดาษแผ่นใหม่กลับมา · name.upcase! คือหยิบปากกาเขียนทับต้นฉบับเลย — เร็วกว่า ไม่เปลืองกระดาษ แต่ทุกคนที่เปิดแฟ้มเดียวกันจะเห็นรอยแก้นั้นด้วย (เหมือน t2 ข้างบน)

puts nil กับ puts "" ได้บรรทัดว่างเหมือนกันทุกไบต์ · ถ้าคุณ debug ด้วย puts แล้วเห็นบรรทัดว่าง จะไม่มีทางรู้เลยว่าตัวแปรเป็น nil (ยังไม่ได้ตั้งค่า) หรือเป็นข้อความว่าง (ตั้งแล้วแต่ไม่มีเนื้อ) — สองอย่างนี้มักเป็นบั๊กคนละตัว · p บอกตรง ๆ ว่า nil หรือ "" · ส่วน puts nil.inspect (บรรทัดสุดท้าย) ก็ได้ nil เหมือน p nil เพราะ p x ก็คือการพิมพ์ x.inspect นั่นเอง · นี่คือเหตุผลที่สไลด์บอกว่า "ใช้ p ไม่ใช่ puts ตอน debug"

อีกข้อที่สไลด์บอกคือ p "คืนค่าให้ด้วยจึงแทรกกลางบรรทัดได้" · แปลว่าคุณแอบดูค่ากลางนิพจน์ได้โดยไม่ต้องแยกบรรทัด: x = p(1 + 2) * 10 พิมพ์ 3 ออกมา แล้ว x ก็ยังได้ 30 ตามปกติ (รันจริงแล้ว) · ทำแบบเดียวกันด้วย puts ไม่ได้ เพราะ puts คืน nil แล้ว nil * 10 จะพัง

🗣 ศัพท์ที่เพิ่งเรียนไป
puts / p
puts = แปลงเป็นข้อความ (to_s) แล้วพิมพ์ · คืน nil · p = พิมพ์แบบ inspect (เห็น type) · คืน object ตัวเดิม · debug ใช้ p เสมอ
inspect vs to_s
สอง method ที่แปลง object เป็นข้อความ · to_s สำหรับคนอ่าน ("1" กลายเป็น 1) · inspect สำหรับโปรแกรมเมอร์ ("1" ยังเป็น "1") · พิมพ์ถาม AI ได้ว่า "override inspect for this class so debug output is readable"
Rails.logger
ตัวเขียน log ของแอป Rails · มีระดับ debug · info · warn · error · fatal · ถาม senior ได้ว่า "production ของเราส่ง log ไปที่ไหน แล้วค้นด้วย request id ได้ไหม"
log level
ระดับความสำคัญของข้อความ log · production ของ Rails 8.1 ตั้งไว้ที่ info (เปลี่ยนได้ด้วย env RAILS_LOG_LEVEL) · ข้อความที่ต่ำกว่าระดับที่ตั้งจะถูกทิ้ง
tagged logging / request id
การแปะป้าย [d2ccb67c-…] หน้าทุกบรรทัด log ของ request เดียวกัน · ไว้กรอง log เฉพาะ request ที่มีปัญหา · ป้ายนี้มีเฉพาะข้อความที่ผ่าน Rails.logger
