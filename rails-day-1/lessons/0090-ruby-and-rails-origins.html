2 · Ruby กับ Rails ไม่ใช่อันเดียวกัน

สไลด์หน้า 3 ตั้งคำถามว่า "เดี๋ยวนะ… Ruby กับ Rails ไม่ใช่อันเดียวกันเหรอ" แล้วตอบด้วยภาพสองชั้น:

  • Ruby = ภาษา — ชั้นล่าง · มี syntax, object, block · ใช้เขียนอะไรก็ได้ ไม่จำเป็นต้องเป็นเว็บ
  • Rails = framework — ชั้นบน · มี routing, ORM, view, job, mail · เขียนด้วย Ruby ทั้งหมด และรันอยู่บน Ruby

คุณรู้จักความสัมพันธ์แบบนี้ดีอยู่แล้ว เพราะเคยเจอมาสองรอบ:

วิธีพิสูจน์ว่าเป็นของสองชิ้นจริง: เอาโค้ดสองบรรทัดจากสไลด์หน้า 3 ไปรันด้วย ruby เปล่า ๆ (ไม่มี Rails) — บรรทัดล่างเป็นของ "ชั้นภาษา" ส่วนบรรทัดบนเป็นของ "ชั้น framework"

ชั้นภาษา — Ruby รู้จักเอง

ไฟล์ sort.rb (มีบรรทัดเดียว):

p [3, 1, 2].sort.map { |n| n * 10 }
$ ruby sort.rb
[10, 20, 30]

ชั้น framework — Ruby เปล่า ๆ ไม่รู้จัก

ไฟล์ post.rb (มีบรรทัดเดียว):

Post.where(published: true).order(:title)
$ ruby post.rb
post.rb:1:in '<main>': uninitialized constant Post (NameError)

Post.where(published: true).order(:title)
^^^^

NameError แปลว่า "ไม่รู้จักชื่อ Post" — ก็แน่ล่ะ Ruby ไม่มีทางรู้ว่าบล็อกของเรามีโพสต์ · แต่ถ้ารันบรรทัดเดียวกันในแอป Rails ที่มีโมเดล Post แล้ว มันกลายเป็นคำสั่ง SQL ทันที (ผมสั่ง .to_sql ให้มันพิมพ์ SQL ออกมาดูแทนการยิงจริง): 

$ bin/rails runner 'puts Post.where(published: true).order(:title).to_sql'
SELECT "posts".* FROM "posts" WHERE "posts"."published" = TRUE ORDER BY "posts"."title" ASC

นั่นคือหน้าที่ของ Rails ในประโยคเดียว: เติมของที่เว็บแอปต้องใช้ (ในที่นี้คือ ORM ชื่อ Active Record ที่แปลง Ruby เป็น SQL) ลงบนภาษา Ruby · ส่วน Active Record ทำงานยังไงเป็นเรื่องของ Day 2 — วันนี้แค่รู้ว่ามันเป็นของ "ชั้นบน"

🧰 เทียบให้เห็นภาพ — ภาษาไทย กับแบบฟอร์มที่เขียนด้วยภาษาไทย

Ruby คือภาษาไทย — ใช้เขียนจดหมาย นิยาย สูตรอาหาร อะไรก็ได้
Rails คือชุดแบบฟอร์มสำเร็จรูปของสำนักงาน ที่เขียนด้วยภาษาไทย — มีช่องให้กรอกครบแล้ว หัวกระดาษพร้อม ลำดับหน้าถูกจัดไว้ให้ คุณแค่เติมเนื้อหาของตัวเอง
Gin ก็เป็นแบบฟอร์มเหมือนกัน แต่เขียนด้วยภาษา Go และเป็นแบบฟอร์มหน้าเดียว (แค่ใบรับเรื่อง) ส่วน Rails เป็นแฟ้มทั้งแฟ้ม — ใบรับเรื่อง ใบเก็บข้อมูล ใบส่งต่อ ครบชุด

ที่ไม่เหมือนกัน: แบบฟอร์มกระดาษไม่สามารถเพิ่มคำใหม่เข้าไปในภาษาไทยได้ · แต่ Rails ทำได้ — มันเติม method ใหม่เข้าไปในตัวเลขธรรมดาของ Ruby จนเขียน 3.days.ago ได้ ทั้งที่ Ruby เปล่า ๆ ไม่มีคำว่า days · ข้อนี้แหละที่ทำให้คนสับสนว่าบรรทัดไหนเป็น Ruby บรรทัดไหนเป็น Rails — หัวข้อถัดไปจะรันให้ดู

🗣 ศัพท์ที่เพิ่งเรียนไป
programming language (ภาษา)
ตัวกำหนดว่าเขียนอะไรได้ หน้าตา syntax เป็นยังไง และใช้โปรแกรมอะไรรัน (ในที่นี้คือคำสั่ง ruby) · เวลาถามปัญหา ให้บอกให้ชัดว่าติดที่ชั้นไหน เช่นพิมพ์บอก AI ได้ว่า “Is this a plain Ruby question or a Rails-specific question?” คำตอบจะต่างกันมาก
framework
ชุดโค้ดสำเร็จรูปที่วางโครงให้ แล้วเรียกโค้ดของคุณตามจังหวะของมัน · Gin, Next.js, Rails คือ framework ทั้งหมด · ถาม senior ได้ว่า “ส่วนนี้เป็นของ Ruby เอง หรือเป็นของ Rails” — คำถามนี้ช่วยให้คุณรู้ว่าจะไปเปิดเอกสารเล่มไหน

ตัวแปลง object ในโค้ดเป็นแถวในตาราง SQL และกลับกัน · ใน Go คุณเคยใช้ GORM (บท 27) · ใน Rails ชื่อ Active Record · ถาม senior ได้ว่า “Active Record ต่างจาก GORM ตรงไหนบ้าง” (Day 2 จะตอบเต็ม ๆ)

3 · ทดลอง: บรรทัดที่ Ruby เปล่า ๆ ไม่รู้จัก

สไลด์หน้า 4 ยกโค้ดที่ "ออกแบบมาให้อ่านออกเสียงได้" มาหกตัวอย่าง สไลด์วางทุกบรรทัดไว้ในกล่องเดียวกัน แต่ไม่ได้บอกว่าบางบรรทัดเป็นของ Rails — มาดูกันว่าคุณแยกออกไหม

ไฟล์ try.rb — 4 บรรทัดจากสไลด์หน้า 3–4 (บรรทัดแรกของไฟล์คือบรรทัด 1):

p [3, 1, 2].sort.map { |n| n * 10 }
p "abc".upcase.reverse
p 1.megabyte
p [3, 1, 2].sort.reverse

รันด้วย ruby try.rb (ไม่มี Rails) จะพิมพ์ออกมากี่บรรทัด อะไรบ้าง?
ใบ้: p คือ "พิมพ์ค่าออกมาให้เห็นหน้าตาจริง" คล้าย fmt.Printf("%#v\n", x) ใน Go

ผลรันจริง — ได้แค่สองบรรทัด แล้วพังที่บรรทัด 3:

$ ruby try.rb
[10, 20, 30]
"CBA"
try.rb:3:in '<main>': undefined method 'megabyte' for an instance of Integer (NoMethodError)

p 1.megabyte
   ^^^^^^^^^

สังเกตสามเรื่อง:
1. บรรทัด 1–2 ทำงานไปแล้วก่อนจะพัง — Ruby อ่านไปรันไปทีละบรรทัด ไม่ได้ตรวจทั้งไฟล์ก่อนแบบ go build
2. บรรทัด 4 ไม่ได้รันเลย ทั้งที่มันถูกต้องสมบูรณ์ — โปรแกรมหยุดตั้งแต่บรรทัด 3
3. ข้อความบอกตรง ๆ ว่า ตัวเลข (Integer) ไม่มี method ชื่อ megabyte

ทีนี้รันไฟล์เดิม แต่สั่งให้โหลด Active Support (gem ชิ้นหนึ่งของ Rails) เข้ามาก่อน:

$ ruby -ractive_support/all try.rb
[10, 20, 30]
"CBA"
1048576
[3, 2, 1]

ผ่านครบสี่บรรทัด · 1.megabyte = 1048576 (คือ 1024 × 1024 ไบต์) · ไฟล์เดียวกันเป๊ะ ต่างกันแค่ -r (ย่อมาจาก require) ตัวเดียว — นี่คือหลักฐานว่า megabyte ไม่ใช่ของ Ruby แต่เป็นของ Rails ที่เอาไปเติมให้ตัวเลข

3.days.ago ในสไลด์หน้า 4 ก็เป็นแบบเดียวกัน:

ไฟล์ days.rb (มีบรรทัดเดียว):

puts 3.days.ago
$ ruby days.rb
days.rb:1:in '<main>': undefined method 'days' for an instance of Integer (NoMethodError)

puts 3.days.ago
      ^^^^^

$ ruby -ractive_support/all days.rb
2026-10-28 23:57:16 +0700

แล้ว Active Support มาจากไหน? คำสั่ง gem dependency บอกว่า gem ชื่อ rails แทบไม่มีโค้ดของตัวเองเลย มันคือรายชื่อ gem ย่อยอีกสิบกว่าตัวที่ต้องลงมาด้วยกัน: 

$ gem dependency rails -v 8.1.4

  actionmailbox (= 8.1.4)
  actionmailer (= 8.1.4)
  actionpack (= 8.1.4)
  actiontext (= 8.1.4)
  actionview (= 8.1.4)

activesupport คือตัวที่เติม days / megabyte ให้ตัวเลข · activerecord คือ ORM ที่เห็นในหัวข้อ 2 · ชื่อพวกนี้จะโผล่มาเรื่อย ๆ ทั้งคอร์ส จำไว้แค่ว่ามันคือชิ้นส่วนของ Rails ไม่ใช่ของ Ruby

เกร็ดเล็ก ๆ ที่เจอระหว่างตรวจ: 3.days.ago ในแอป Rails ไม่ได้คืนค่าแบบเดียวกับตอนรันด้วย Ruby + Active Support · ในแอป Rails ได้ object ชื่อ ActiveSupport::TimeWithZone ที่โซนเวลาเป็น UTC (2026-10-28 16:57:31.553548000 UTC +00:00) ส่วนนอกแอปได้ Time ธรรมดาตามเวลาเครื่อง (+0700) · ตอนนี้ยังไม่ต้องสนใจ แค่รู้ว่าแอป Rails ตั้งค่าเพิ่มให้อีกชั้น — ตรงกับความเชื่อข้อ 2 ในหัวข้อ 7

ถ้ารันแต่ละบรรทัดนี้ด้วยคำสั่ง ruby เปล่า ๆ (ไม่ได้โหลดอะไรของ Rails) บรรทัดไหนจะได้ NoMethodError?

ตัวเลือกที่ 4 ถูก · ผลรันจริงคือ undefined method 'days' for an instance of Integer (NoMethodError) จนกว่าจะโหลด active_support เข้ามา

ตัวเลือกที่ 1 และ 3 ผิด เพราะ sort reverse upcase เป็นของ Ruby เอง รันจริงได้ [3, 2, 1] และ "CBA" — การเรียก method ต่อกันเป็นสายเป็นเรื่องปกติของ Ruby · ตัวเลือกที่ 2 ผิด เพราะใน Ruby ตัวเลขก็เป็น object เรียก method ได้ — 5.times พิมพ์ hello ห้าครั้งจริง (บทเรียน 91 จะเล่าเรื่อง "ทุกอย่างเป็น object")

จุดที่ต้องจำ: โค้ดที่ "อ่านเป็นภาษาอังกฤษได้สวย ๆ" ไม่ได้แปลว่าเป็นของ Ruby เสมอ · ถ้าสงสัย ให้รันด้วย ruby เปล่า ๆ ดู — พังเมื่อไหร่แปลว่าเป็นของ Rails

4 · 1995 — Ruby เกิดจากโจทย์ "ให้คนเขียนมีความสุข"

สไลด์หน้า 4 เล่าว่าคนสร้าง Ruby คือ Yukihiro Matsumoto ชาวญี่ปุ่น ที่ทุกคนเรียกว่า "Matz" · หน้า FAQ ของ ruby-lang.org อ้างคำของ Matz เองว่าเขาโพสต์ Ruby 0.95 ลงกลุ่มข่าวในญี่ปุ่นเมื่อธันวาคม 1995 ซึ่งตรงกับสไลด์

ประเด็นสำคัญของหน้านี้คือโจทย์ตั้งต้น: สไลด์บอกว่าภาษาในยุคนั้นออกแบบให้เครื่องทำงานเร็วที่สุด แต่ Matz กลับโจทย์ — ออกแบบให้คนเขียนมีความสุขที่สุด · หลักคิดที่ตามมา สไลด์เรียกว่า Principle of Least Surprise: ถ้าคุณเดาว่าโค้ดน่าจะทำงานแบบไหน มันควรทำงานแบบนั้น

ลองอ่านโค้ดในสไลด์ออกเสียงเป็นภาษาอังกฤษ แล้วดูผลรันจริง: 

# five.rb
5.times { puts "hello" }      # "five times, puts hello"
$ ruby five.rb
hello
hello
hello
hello
hello

เทียบกับ Go ที่ต้องเขียน for i := 0; i < 5; i++ { fmt.Println("hello") } — Go บอกวิธีทำ (ตั้งตัวนับ เช็คเงื่อนไข บวกหนึ่ง) ส่วน Ruby บอกสิ่งที่อยากได้ (ทำห้าครั้ง) · ถ้าคุณเคยใช้ .map ใน TypeScript (บท 67) จะรู้สึกคุ้น ๆ — แนวคิดเดียวกัน

คุณเห็นภาพนี้มาแล้วในคอร์สนี้เอง — ระบบ wongnok ที่ทำมาก็แยกเป็น backend Go กับ frontend Next.js ไม่ได้ใช้ภาษาเดียวทำทั้งหมด · การเลือกเครื่องมือตามงานเป็นเรื่องปกติ ไม่ใช่สัญญาณว่าเครื่องมือตัวไหน "แพ้"

ตัวเลือกที่ 1 คือเวอร์ชันที่คนเล่าต่อกัน ซึ่งสไลด์ตั้งใจหักล้าง · ตัวเลือกที่ 2 ผิด เพราะสไลด์หน้า 8 บอกว่า Twitter เริ่มบน Rails จริง · ตัวเลือกที่ 4 ผิด เพราะ Rails 3 ในสไลด์หน้า 7 คือการรวมร่างกับ Merb ไม่เกี่ยวกับ Twitter

7 · ความเชื่อ 3 ข้อที่ Rails ยืนอยู่

สไลด์หน้า 11 บอกว่า Rails ยืนอยู่บนความเชื่อสามข้อ · ข้อนี้สำคัญที่สุดของบท เพราะมันคือสิ่งที่ทำให้คุณต้องเปลี่ยนวิธีคิดจากตอนเขียน Gin

ข้อ 1 · Convention over Configuration — ตั้งชื่อตามกฎ แล้วไม่ต้องเขียน config

ตอนเขียน Gin คุณต้องบอกทุกอย่างเอง: route นี้ไปฟังก์ชันไหน · struct นี้ตรงกับตารางชื่ออะไร · template อยู่ไฟล์ไหน
Rails กลับด้าน: ถ้าคุณตั้งชื่อตามกฎของมัน มันจะเดาส่วนที่เหลือให้เอง · สไลด์ยกตัวอย่างเป็นห่วงโซ่สั้น ๆ:

posts → Post → PostsController → app/views/posts/ ตาราง โมเดล controller โฟลเดอร์ของ view

แค่รู้คำว่า posts คำเดียว Rails ก็รู้ทั้งสายว่าต้องไปหาอะไรที่ไหน · ดูของจริง — นี่คือไฟล์โมเดล Post ที่ Rails สร้างให้ ทั้งไฟล์มีแค่สองบรรทัด: 

# app/models/post.rb
class Post < ApplicationRecord
end

แบบ Rails: ทุกตู้ติดป้ายชื่อตามกฎเดียวกัน ของ posts อยู่ตู้ชื่อ posts เสมอ ไม่ต้องมีสมุด ใครเดินเข้ามาก็หาเจอเลย — สไลด์หน้า 12 เรียกข้อนี้ว่า "เปิด repo ของคนอื่นแล้วอ่านออกทันที"

ที่ไม่เหมือนกัน: ในฟิตเนสจริง ถ้าคุณเขียนป้ายผิด พนักงานจะเห็นแล้วทักคุณ · แต่ Rails ไม่ทักอะไรเลยตอนคุณพิมพ์ชื่อผิด — มันแค่หาไม่เจอแล้วพังตอนโปรแกรมวิ่งไปถึงจุดนั้น ไม่มี compiler คอยดักเหมือน Go · นี่คือราคาข้อแรกในหัวข้อ 9

ข้อ 2 · Omakase — Rails เลือกเครื่องมือให้ครบชุดแล้ว

ตอนทำ backend Go คุณเลือกเองทุกชิ้น: router ใช้ Gin · ORM ใช้ GORM · migration ใช้ goose · cache ใช้ go-redis · แต่ละตัวมาจากคนละทีม ออกรุ่นคนละจังหวะ คุณเป็นคนประกอบให้มันทำงานด้วยกัน
Rails บอกว่า "ไม่ต้องเลือก ฉันเลือกให้แล้ว" — ทั้งชุดมาในกล่องเดียว (รายการเต็มอยู่หัวข้อถัดไป)

แม้แต่ตัวตรวจสไตล์โค้ดในโปรเจกต์ที่ rails new สร้างให้ ก็ใช้ชื่อตามความเชื่อข้อนี้ตรง ๆ — ใน Gemfile มีบรรทัด gem "rubocop-rails-omakase", require: false

🍣 เทียบให้เห็นภาพ — ร้านซูชิ omakase กับการไปจ่ายตลาดเอง

Omakase เป็นคำญี่ปุ่นที่ใช้ในร้านซูชิ แปลประมาณว่า "แล้วแต่เชฟ" — คุณนั่งลง เชฟเลือกปลา เลือกลำดับ เลือกปริมาณให้ทั้งคอร์ส ทุกจานเข้ากันเพราะคนคนเดียวคิดมาทั้งชุด
Go คือการไปจ่ายตลาดเอง — เลือกได้ทุกอย่าง ได้ของที่ตรงใจเป๊ะ แต่ต้องรู้ว่าอะไรเข้ากับอะไร และถ้าของสองร้านไม่เข้ากัน คุณรับผิดชอบเอง

ที่ไม่เหมือนกัน: ในร้านซูชิ คุณเปลี่ยนจานกลางคอร์สไม่ได้ · แต่ใน Rails คุณถอดชิ้นส่วนออกแล้วใส่ตัวอื่นแทนได้ — มันแค่ไม่ใช่ทางที่ Rails ปูไว้ · ยิ่งเปลี่ยนเยอะ ยิ่งเสียข้อดีของ "อัปเกรดไปพร้อมกัน" และยิ่งเจอ "ฝืนเมื่อไหร่เจ็บเมื่อนั้น" ในสไลด์หน้า 12

ข้อ 3 · The One Person Framework — คนเดียวควรทำได้ครบวงจร

สไลด์ให้นิยามสั้นมาก: คนเดียวควรทำได้ครบวงจร · ลองนึกถึงสิ่งที่คุณทำมาในคอร์สนี้: backend Go หนึ่งโปรเจกต์ + frontend Next.js อีกโปรเจกต์ + Keycloak + Redis + migration · แต่ละชิ้นต้องเรียนแยกกันเป็นวัน ๆ
ความเชื่อข้อ 3 บอกว่า นักพัฒนาคนเดียวควรสร้างเว็บแอปเต็มรูปแบบได้ — ตั้งแต่ฐานข้อมูลจนถึงหน้าเว็บ — ด้วย framework ตัวเดียว · ข้อ 3 เป็นไปได้ก็เพราะมีข้อ 1 (ไม่ต้องเสียเวลาเขียน config) กับข้อ 2 (ไม่ต้องเสียเวลาเลือกและประกอบเครื่องมือ)

🗣 ศัพท์ที่เพิ่งเรียนไป
Convention over Configuration (CoC)
"ทำตามข้อตกลง แทนการเขียนตั้งค่า" · ตั้งชื่อตามกฎแล้ว framework เดาส่วนที่เหลือให้ · คู่มือ Rails ทางการเรียกข้อนี้ว่าหนึ่งในสองหลักใหญ่ของ Rails (อีกข้อคือ DRY — Don't Repeat Yourself) · พิมพ์บอก AI ได้ว่า “follow Rails conventions, don't add explicit configuration unless needed”
Omakase
"แล้วแต่เชฟ" · Rails เลือกชุดเครื่องมือมาให้ครบ และทุกชิ้นออกรุ่นไปพร้อมกัน · ถาม senior ได้ว่า “ทีมเราใช้ของ default ของ Rails ตัวไหนบ้าง แล้วเปลี่ยนตัวไหนออกไป เพราะอะไร” — คำตอบบอกได้เยอะว่าทีมเจอปัญหาอะไรมา
The One Person Framework
ความเชื่อว่าคนคนเดียวควรสร้างเว็บแอปได้ครบวงจรด้วย Rails ตัวเดียว · ใช้คำนี้คุยกับ senior เวลาถกว่า “ส่วนนี้ควรทำใน Rails เลย หรือแยกเป็นอีก service”
opinionated framework
framework ที่มีความเห็นชัดว่าควรทำแบบไหน และทำให้ทางนั้นง่ายที่สุด · คู่มือ Rails ทางการเขียนไว้ตรง ๆ ว่า "Rails is opinionated software" · ตรงข้ามกับ Gin ที่แทบไม่บังคับอะไร · ถาม AI ได้ว่า “what is the Rails way to do X?” แทน “how to do X in Rails”

ในแอป Rails มีไฟล์ app/models/post.rb ที่เขียนแค่ class Post < ApplicationRecord กับ end · Rails จะไปอ่านข้อมูลจากตารางชื่ออะไร?

ตัวเลือกที่ 1 ถูก · ผลรันจริง Post.table_name ได้ "posts" — คลาสเป็นเอกพจน์ (หนึ่งแถว = หนึ่งโพสต์) ตารางเป็นพหูพจน์ (เก็บหลายโพสต์)

ตัวเลือกที่ 2 และ 3 ผิด เพราะ Rails เปลี่ยนเป็นพหูพจน์ด้วย ไม่ได้แค่เปลี่ยนตัวพิมพ์ · ตัวเลือกที่ 4 คือวิธีคิดแบบ Go ที่ต้องบอกทุกอย่างเอง — ใน Rails ไม่ต้อง เพราะ Convention over Configuration (บอกเองก็ได้ ถ้าจำเป็นต้องฝืนกฎ แต่ไม่ใช่ทางปกติ)

จุดที่ต้องจำ: ใน Rails ชื่อคือ config · ตั้งชื่อถูกกฎ = ไม่ต้องเขียนอะไรเพิ่ม · ตั้งชื่อผิดกฎ = หาไม่เจอ และไม่มีใครเตือนจนกว่าจะรัน

เพื่อนพูดว่า "Rails ก็คือ Gin ของภาษา Ruby นั่นแหละ" · ข้อไหนแก้ประโยคนี้ให้ตรงขึ้นได้ดีที่สุด?

ตัวเลือกที่ 2 ถูก · สไลด์หน้า 3 เทียบ Rails กับ Gin ในฐานะ "framework เหมือนกัน" ซึ่งถูก แต่สไลด์หน้า 13 แสดงว่า Rails ครอบคลุมกว้างกว่า Gin มาก — Gin เทียบได้กับแค่แถวแรกของตาราง (router)

ตัวเลือกที่ 1 ผิด เพราะมองข้ามอีก 11 อย่างในกล่อง · ตัวเลือกที่ 3 ผิด เพราะ Rails ไม่ใช่ภาษา — มันเป็นโค้ด Ruby ธรรมดา (เป็น gem ตัวหนึ่ง) · ตัวเลือกที่ 4 ผิด เพราะตัวรันโค้ด Ruby คือคำสั่ง ruby เอง — หัวข้อ 3 ใช้ ruby รันไฟล์โดยไม่มี Rails ได้ปกติ

จุดที่ต้องจำ: Gin = router + middleware · Rails = ทั้งชุดของเว็บแอป · เวลาย้ายจาก Go มา Rails อย่ามองหา "library ที่ต้องลงเพิ่ม" ก่อน ให้มองหา "ของที่ Rails มีให้อยู่แล้ว" ก่อนเสมอ

9 · ราคาที่ต้องจ่าย

สไลด์หน้า 11 ปิดท้ายว่า "ทั้งสามข้อมีราคาที่ต้องจ่าย" แล้วหน้า 12 ก็ไล่ให้ดูตรง ๆ:

สิ่งที่ได้

  • เขียนน้อยลงมาก — สไลด์บอกว่างานเดิมใช้โค้ดไม่ถึงครึ่ง
  • ของครบในกล่องเดียว ไม่ต้องประกอบเอง
  • โครงสร้างเหมือนกันทุกโปรเจกต์ Rails
  • เปิด repo ของคนอื่นแล้วอ่านออกทันที
  • REPL เข้าถึงโค้ดทั้งแอปได้สด ๆ (บท 104)

สิ่งที่เสีย

  • พิมพ์ชื่อ method ผิด รู้ตอน runtime
  • magic เยอะ พอหลุดทางแล้ว debug ยาก
  • image ใหญ่กว่า และกิน RAM มากกว่า
  • ผูกกับ convention ฝืนเมื่อไหร่เจ็บเมื่อนั้น
  • งาน CPU-bound / latency ต่ำมาก ไม่ใช่ที่ของมัน

ข้อแรกของฝั่ง "เสีย" คือข้อที่คนมาจาก Go เจ็บที่สุด · ลองพิมพ์ชื่อ method ผิดตัวเดียวในทั้งสองภาษา:

Go — ตรวจก่อนรัน

ไฟล์ main.go ในโมดูลชื่อ gotypo — ตั้งใจพิมพ์ผิด ToUpperr ที่บรรทัด 10:

package main

import (
	"fmt"
	"strings"
)

func main() {
	fmt.Println("บรรทัดแรก")
	fmt.Println(strings.ToUpperr("abc"))
}
$ go run .
# gotypo
./main.go:10:22: undefined: strings.ToUpperr

"บรรทัดแรก" ไม่ถูกพิมพ์เลย — Go ไม่ยอมรันโปรแกรมที่มีชื่อผิดแม้แต่ตัวเดียว

Ruby — รันไปเจอเอง

ไฟล์ typo.rb — ตั้งใจพิมพ์ผิด upcasee ที่บรรทัด 2:

"บรรทัดแรก" ถูกพิมพ์ไปแล้ว ก่อนจะพัง — ถ้าบรรทัดแรกเป็นการลบข้อมูล มันก็ลบไปแล้ว

ในไฟล์สั้น ๆ แบบนี้ไม่เป็นไร · แต่ในเว็บแอป ชื่อที่พิมพ์ผิดอาจอยู่ในหน้าที่ไม่มีใครเปิดมาสามเดือน แล้วไปพังตอนลูกค้าเปิดพอดี · นี่คือเหตุผลที่คน Rails จริงจังกับการเขียนเทสมาก — เทสคือสิ่งที่ทำหน้าที่แทน compiler (Day 4 จะสอน testing) · ข้อดีเล็ก ๆ ที่ได้คืน: Ruby ช่วยเดาให้ว่า Did you mean? upcase

🗣 ศัพท์ที่เพิ่งเรียนไป
compile-time error กับ runtime error
compile-time = เจอก่อนโปรแกรมได้รัน (แบบ Go) · runtime = เจอตอนโปรแกรมวิ่งไปถึงบรรทัดนั้น (แบบ Ruby) · ถาม senior ได้ว่า “โปรเจกต์นี้ใช้อะไรจับ runtime error ก่อนขึ้น production — เทส, linter หรือ type checker”
magic
คำที่คนใช้เรียกพฤติกรรมที่เกิดขึ้นเองโดยไม่เห็นโค้ดที่สั่ง — เช่น Post รู้ชื่อตารางเองทั้งที่ไฟล์มีแค่สองบรรทัด · ไม่ใช่เวทมนตร์จริง ทุกอย่างมีโค้ดอยู่เบื้องหลัง แค่อยู่ใน gem ของ Rails · พิมพ์บอก AI ได้ว่า “explain what Rails does implicitly in this code” เวลาอ่านโค้ดแล้วไม่รู้ว่าอะไรเกิดขึ้นตรงไหน
monolith
แอปที่โค้ดทุกส่วนอยู่ในโปรเจกต์เดียว deploy เป็นก้อนเดียว · ตรงข้ามกับการแยกเป็นหลาย service · สไลด์หน้า 9 อ้างว่า GitHub เป็น Rails monolith · ถาม senior ได้ว่า “ระบบเราเป็น monolith หรือแยก service แล้วแบ่งตรงไหน”
CPU-bound
งานที่ช้าเพราะต้องคำนวณหนัก (เช่นประมวลผลภาพ เข้ารหัสวิดีโอ) ไม่ใช่เพราะรอฐานข้อมูลหรือรอเครือข่าย · สไลด์บอกว่างานประเภทนี้ "ไม่ใช่ที่ของ Rails" · ใช้คำนี้ตอนเถียงว่าส่วนไหนควรแยกออกไปเขียนด้วย Go — ตรงกับบทเรียนจากเรื่อง Twitter ในหัวข้อ 6
