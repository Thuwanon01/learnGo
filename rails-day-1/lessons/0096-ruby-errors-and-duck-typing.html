เมื่อโค้ดพัง — rescue แทน if err != nil และ duck typing

~20 นาที · ควรผ่าน บทเรียน 93 (method) และ บทเรียน 95 (class) มาก่อน · ถ้าจำ บทเรียน 05 (error ของ Go) ได้คร่าว ๆ จะง่ายขึ้นมาก

ตอนเขียน Go คุณพิมพ์ if err != nil จนชินมือ — แต่ใน Ruby บรรทัดนั้นไม่มีเลย
อ่านจบบทนี้คุณจะ: อ่านข้อความ error ของ Ruby ออกว่าพังที่ไหนเพราะอะไร · เขียน begin / rescue รับ error ได้ · โยน error เองด้วย raise · และเข้าใจ duck typing — เหตุผลที่ Ruby ไม่ต้องประกาศ interface แต่แลกมากับการพังตอนรัน

🔁 ทวนก่อนเริ่ม
  • method — คำสั่งที่เราตั้งชื่อเองด้วย def ชื่อ ... end · บรรทัดสุดท้ายคือค่าที่ส่งคืน (บท 93)
  • class และ < — class คือแม่พิมพ์ของ object · class A < B แปลว่า A สืบทอดของทุกอย่างจาก B (บท 95)
  • nil — ค่าที่แปลว่า "ไม่มีค่า" เช่นหาของใน Hash ไม่เจอ (บท 94)
  • symbol :title — ชื่อสั้น ๆ ที่มีโคลอนนำหน้า ใช้เป็นป้ายชื่อ (บท 92)
  • #{} — เสียบค่าลงไปใน string เช่น "คนละ #{x} บาท" (บท 91)

เวอร์ชันที่ใช้ตรวจ: Ruby 4.0.9 · Rails 8.1.4 · Go 1.26.5 (สไลด์ใช้ Ruby 4.0.6 · Rails 8.1.3 — เป็นรุ่นแพตช์ใกล้กัน ไม่กระทบเรื่องในบทนี้) · โค้ด Ruby ทุกก้อนรันด้วย ruby ชื่อไฟล์.rb ใน terminal · ผลรันทุกกล่องก็อปจากเครื่องจริง

1 · ทวน Go: error คือ "ค่า" ที่ส่งคืนมา

เริ่มจากของที่คุณรู้แล้ว ตัวอย่างทั้งบทจะใช้เรื่องเดียวกัน: แบ่งบิลค่าอาหาร — ยอด 900 บาท หารกันกี่คน
ใน Go ฟังก์ชันที่อาจพังจะคืนค่าสองตัว: ผลลัพธ์ กับ error 

// main.go (Go)
package main

import (
	"errors"
	"fmt"
)

func splitBill(total, people int) (int, error) {
	if people == 0 {
		return 0, errors.New("จำนวนคนเป็น 0 ไม่ได้")
	}
	return total / people, nil
}

func main() {
	share, err := splitBill(900, 0)
	if err != nil {
		fmt.Println("แบ่งบิลไม่ได้:", err)
		return
	}
	fmt.Println("คนละ", share)
}
$ go run .
แบ่งบิลไม่ได้: จำนวนคนเป็น 0 ไม่ได้
  • (int, error) — บอกว่าฟังก์ชันนี้คืนของสองอย่าง: ตัวเลข และ error
  • return 0, errors.New(...) — มีปัญหา: คืนเลข 0 เป็นค่าหลอก ๆ พร้อม error ที่บอกว่าเพราะอะไร
  • return total / people, nil — ไม่มีปัญหา: error เป็น nil (ไม่มี error)
  • if err != nil — คนเรียกต้องเช็คเองทุกครั้ง ว่าที่ได้มามี error ติดมาไหม

สรุปง่าย ๆ: ใน Go error เดินทางมากับค่าที่ return เหมือนของชิ้นหนึ่ง · ใครได้รับก็ต้องหยิบขึ้นมาดูเอง แล้วตัดสินใจว่าจะจัดการเลย หรือ return err ส่งต่อให้ชั้นบน

2 · Ruby: error ถูก "โยน" ขึ้นไปจนกว่าจะมีคนรับ

Ruby ไม่คืน error เป็นค่า · พอเกิดเรื่องผิดปกติ Ruby จะหยุดบรรทัดนั้นทันที แล้วโยน error ออกไปหา "คนรับ" ที่อยู่ข้างบน
"ข้างบน" คือ method ที่เรียกเรามา แล้วก็ method ที่เรียก method นั้นมาอีกที ไล่ขึ้นไปทีละชั้น · ถ้าไม่มีใครรับเลยสักชั้น — โปรแกรมหยุดทั้งตัว

มาดูของจริง นี่คือการแบ่งบิลแบบ Ruby ที่ยังไม่มีใครรับ error:

# crash.rb — แบ่งบิลร้านอาหาร
def split_bill(total, people)
  total / people
end

puts "เริ่มคิดเงิน"
puts split_bill(900, 3)
puts split_bill(900, 0)
puts "คิดเงินเสร็จ"
  • def split_bill(total, people) — method รับยอดเงินกับจำนวนคน · ไม่มีช่อง error เหมือน Go
  • total / people — หารกัน · บรรทัดเดียวของ method จึงเป็นค่าที่คืน
  • บรรทัดล่าง ๆ เรียกสามครั้ง: หาร 3 คน · หาร 0 คน (จะพัง) · แล้วพิมพ์ว่าเสร็จ
$ ruby crash.rb
เริ่มคิดเงิน
300
crash.rb:3:in 'Integer#/': divided by 0 (ZeroDivisionError)
	from crash.rb:3:in 'Object#split_bill'
	from crash.rb:8:in '<main>'
$ echo $?
1

สังเกตว่า "คิดเงินเสร็จ" ไม่ถูกพิมพ์ · พอหารด้วย 0 Ruby โยน error ออกมา ไม่มีใครรับ โปรแกรมจึงหยุดตรงนั้น · echo $? ได้ 1 แปลว่า "จบแบบพัง" (0 = จบปกติ)

🔔 เทียบให้เห็นภาพ — กล่องจดหมาย กับ กริ่งไฟไหม้

Go เหมือนตึกที่ทุกห้องมีกล่องจดหมาย — ข่าวร้ายมาเป็นจดหมายใส่กล่อง คนในห้องต้องเปิดกล่องดูเองทุกครั้ง (if err != nil) ถ้าไม่เปิดดู งานก็เดินต่อไปเหมือนไม่มีอะไรเกิดขึ้น
Ruby เหมือนกริ่งไฟไหม้ — เกิดเรื่องที่ห้องไหน ทุกคนในห้องนั้นหยุดมือทันที เสียงกริ่งดังขึ้นไปทีละชั้น จนกว่าจะเจอชั้นที่มีเจ้าหน้าที่ประจำ (rescue) มารับเรื่อง · ถ้าดังไปถึงดาดฟ้าแล้วไม่มีใครรับ = อพยพทั้งตึก (โปรแกรมหยุด)

ที่ไม่เหมือนกัน: กริ่งจริงทุกคนได้ยินพร้อมกัน แต่ error ของ Ruby ขึ้นไปทีละชั้นตามลำดับที่ method เรียกกันมา · และเจ้าหน้าที่ใน Ruby รับเฉพาะเรื่องที่ตัวเองระบุไว้ (หัวข้อ 4) — ไม่ใช่รับได้ทุกเรื่อง

🗣 ศัพท์ที่เพิ่งเรียนไป
exception
ชื่อเรียก error แบบที่ "ถูกโยน" ใน Ruby · มันเป็น object ตัวหนึ่ง มีชื่อชนิด (เช่น ZeroDivisionError) และข้อความ · ถาม senior ได้ว่า “method นี้ raise exception อะไรได้บ้าง” — เพราะ Ruby ไม่มีอะไรเขียนบอกไว้ที่หัว method เหมือน Go
raise (โยน) · propagate (ลอยขึ้น)
raise คือการโยน exception ออกมา · propagate คือการที่มันลอยขึ้นไปหา method ที่เรียกมาทีละชั้นเอง โดยเราไม่ต้องเขียน return err ส่งต่อ · พิมพ์บอก AI ได้ว่า “let this exception propagate up instead of handling it here”
unhandled exception
exception ที่ลอยขึ้นไปจนสุดแล้วไม่มีใครรับ → โปรแกรมหยุด พิมพ์ข้อความ error และจบด้วย exit code 1 · ถาม senior ได้ว่า “ตรงนี้ควรปล่อยให้พัง หรือควรรับไว้”

3 · อ่านข้อความ error ให้ออก

ข้อความ error ดูน่ากลัว แต่จริง ๆ มันบอกทุกอย่างที่ต้องรู้ · ลองแยกของ crash.rb ทีละท่อน:

ท่อนแปลว่า
crash.rb:3พังที่ไฟล์ crash.rb บรรทัด 3 (นับบรรทัด comment แรกด้วย) — เปิดไฟล์ไปดูบรรทัดนี้ก่อนเลย
in 'Integer#/'พังระหว่างทำ / (การหาร) ของตัวเลข · อ่านว่า "method / ของ class Integer" — เครื่องหมาย # ในข้อความ error แค่คั่นชื่อ class กับชื่อ method · ใน Ruby แม้แต่ / ก็เป็น method ตัวหนึ่ง
divided by 0ข้อความ — บอกเป็นภาษาคนว่าเกิดอะไร
(ZeroDivisionError)ชื่อชนิดของ error อยู่ในวงเล็บท้ายบรรทัดเสมอ · เอาไปใช้ตอน rescue ได้ (หัวข้อถัดไป)
บรรทัด from ...ทางที่ error ลอยขึ้นมา · อ่านบนลงล่าง = จากจุดพัง ย้อนไปหาคนที่เรียก · 'Object#split_bill' คือ method ของเรา (method ที่เขียนนอก class Ruby นับเป็นของ Object — จำแค่นี้พอ) · '<main>' คือ "ตัวไฟล์เอง" ชั้นนอกสุด (บรรทัด 8 คือ split_bill(900, 0))

เคล็ดลับ: ดูวงเล็บท้ายบรรทัดแรกก่อน (พังเพราะอะไร) แล้วดูเลขบรรทัด (พังที่ไหน) · แค่สองอย่างนี้ก็แก้ได้เกินครึ่งแล้ว

4 · begin / rescue — ขึงคนรับ error

ถ้าไม่อยากให้โปรแกรมหยุด เราต้อง "ขึงคนรับ" ไว้ตรงที่คิดว่าจะพัง
ใส่โค้ดเสี่ยงไว้ระหว่าง begin กับ rescue แล้วเขียนว่าจะทำอะไรถ้าพัง: 

# rescue1.rb
def split_bill(total, people)
  total / people
end

begin
  puts split_bill(900, 0)
rescue
  puts "แบ่งบิลไม่ได้"
end
puts "คิดเงินเสร็จ"
$ ruby rescue1.rb
แบ่งบิลไม่ได้
คิดเงินเสร็จ
  • begin — "เริ่มเขตคุ้มครอง" · โค้ดข้างในถ้าพัง จะไม่หลุดออกไปไกล
  • rescue — "ถ้าในเขตพัง ให้กระโดดมาทำตรงนี้แทน" · บรรทัด puts split_bill(...) พังกลางทาง เลยไม่ได้พิมพ์อะไร
  • end — ปิดเขต · จากนั้นโปรแกรมเดินต่อปกติ "คิดเงินเสร็จ" จึงถูกพิมพ์

เทียบ Go: Go ไม่มีคู่คำนี้ — ทุกจุดที่อาจพังต้องเขียน if err != nil { ... } ต่อท้ายทีละจุด · ใน Ruby เขียน begin ... rescue ครอบทีเดียว คลุมได้หลายบรรทัด
ถ้าเคยเขียน TypeScript: begin ≈ try · rescue ≈ catch — คำต่างกันแต่หน้าที่เดียวกัน

รับเฉพาะชนิดที่อยากรับ

ในชีวิตจริง error มีหลายแบบ และแต่ละแบบควรจัดการต่างกัน · Ruby ให้เขียนชื่อชนิดไว้หลัง rescue ได้ แล้วเขียนกี่ช่องก็ได้
ตัวอย่างนี้จำนวนคนมาเป็นข้อความ (เหมือนที่ผู้ใช้พิมพ์มาในฟอร์ม) จึงพังได้สองแบบ: 

# rescue2.rb — แยกรับทีละชนิด
def split_bill(total, people_text)
  people = Integer(people_text)   # แปลงข้อความเป็นตัวเลข
  total / people
end

["3", "0", "สาม"].each do |text|
  begin
    puts "คนละ #{split_bill(900, text)} บาท"
  rescue ZeroDivisionError
    puts "จำนวนคนเป็น 0 ไม่ได้"
  rescue ArgumentError => e
    puts "อ่านจำนวนคนไม่ออก: #{e.message}"
  ensure
    puts "  (ปิดบิล)"
  end
end
  • Integer(people_text) — แปลงข้อความเป็นตัวเลข · หน้าตาเหมือนชื่อ class เพราะขึ้นต้นตัวใหญ่ แต่จริง ๆ เป็น method ธรรมดาที่ Ruby มีให้ · "3" ได้ 3 · แต่ "สาม" แปลงไม่ได้ จะโยน ArgumentError ("ค่าที่ส่งมาใช้ไม่ได้" — เคยเจอใน บท 93)
  • [...].each do |text| ... end — วนทีละตัวในรายการ ตัวปัจจุบันชื่อ text (ทวน บท 93)
  • rescue ZeroDivisionError — ช่องนี้รับเฉพาะเรื่องหารด้วยศูนย์
  • rescue ArgumentError => e — รับเฉพาะ ArgumentError · ท่อน => e แปลว่า "เอา error ก้อนนั้นมาใส่ตัวแปรชื่อ e" จะได้เรียก e.message (ข้อความ) มาพิมพ์ได้ · ตั้งชื่ออื่นแทน e ก็ได้
  • ensure — ทำเสมอ ไม่ว่าจะพังหรือไม่ (ละเอียดในหัวข้อ 6)
$ ruby rescue2.rb
คนละ 300 บาท
  (ปิดบิล)
จำนวนคนเป็น 0 ไม่ได้
  (ปิดบิล)
อ่านจำนวนคนไม่ออก: invalid value for Integer(): "สาม"
  (ปิดบิล)

แต่ละรอบไปตกคนละช่อง: "3" ไม่พัง · "0" ตกช่อง ZeroDivisionError · "สาม" ตกช่อง ArgumentError
Ruby ไล่ช่อง rescue จากบนลงล่าง แล้วเข้าช่องแรกที่ชนิดตรง — เข้าได้ช่องเดียว

แล้วถ้า error ที่เกิดไม่ตรงกับช่องไหนเลยล่ะ?

# only_one.rb — รับไว้แค่ชนิดเดียว
begin
  puts 900 / 0
rescue ArgumentError
  puts "รับ ArgumentError ไว้"
end
puts "ไปต่อ"
$ ruby only_one.rb
only_one.rb:3:in 'Integer#/': divided by 0 (ZeroDivisionError)
	from only_one.rb:3:in '<main>'

ช่อง rescue รอแค่ ArgumentError · ZeroDivisionError วิ่งผ่านหน้าไปเฉย ๆ แล้วไม่มีใครรับต่อ โปรแกรมเลยพัง · ไม่พิมพ์ทั้ง "รับ ArgumentError ไว้" และ "ไปต่อ"

📋 เทียบให้เห็นภาพ — ป้ายแผนรับมือที่ติดผนังครัว

ช่อง rescue แต่ละช่องเหมือนป้ายแผนรับมือที่ติดผนังครัวไว้: "ถ้าแก๊สหมด → โทรร้านแก๊ส" · "ถ้าลูกค้าแพ้อาหาร → เรียกผู้จัดการ"
เกิดเรื่องขึ้น พนักงานอ่านป้ายจากบนลงล่าง เจอป้ายที่ตรงก็ทำตามป้ายนั้นแล้วจบ · เรื่องที่ไม่มีป้ายไหนเขียนไว้ ก็ต้องส่งต่อขึ้นไปให้ชั้นบน

ที่ไม่เหมือนกัน: พนักงานจริงใช้วิจารณญาณได้ เจอเรื่องคล้าย ๆ ก็ประยุกต์เอา · แต่ Ruby ดูชื่อชนิดอย่างเดียว ไม่ตรงคือไม่รับ · และ rescue เปล่า ๆ ที่ไม่เขียนชนิด ดูเหมือน "รับทุกเรื่อง" แต่จริง ๆ รับแค่ "เรื่องทั่วไป" (หัวข้อ 5 จะเล่า)

5 · raise — โยน error เอง และสร้างชนิดของตัวเอง

บางทีเราอยากเป็นคนโยนเอง เช่น ลูกค้าสั่งเมนูที่หมดแล้ว — โค้ดไม่ได้พังทางเทคนิค แต่ทำต่อไม่ได้ทางธุรกิจ
นึกถึงกริ่งไฟไหม้ในหัวข้อ 2: raise คือเราเดินไปกดกริ่งเองเมื่อเห็นปัญหา · ใช้ raise และสร้างชนิด error ของเราเองได้ในสองบรรทัด: 

# raise.rb — โยน error เอง
class OutOfStockError < StandardError
end

def order(menu, stock)
  raise OutOfStockError, "#{menu} หมดแล้ว" if stock == 0
  "ได้ #{menu} 1 จาน"
end

puts order("ข้าวผัด", 5)
begin
  puts order("ต้มยำ", 0)
rescue OutOfStockError => e
  puts "ขอโทษครับ: #{e.message}"
end
$ ruby raise.rb
ได้ ข้าวผัด 1 จาน
ขอโทษครับ: ต้มยำ หมดแล้ว
  • class OutOfStockError < StandardError + end — สร้างชนิด error ใหม่ ชื่อ OutOfStockError โดยสืบทอดจาก StandardError (แม่ของ error "ทั่วไป" ใน Ruby) · ข้างในว่างได้ เพราะได้ของทุกอย่างจากแม่มาแล้ว
  • raise ชนิด, "ข้อความ" — โยน error ชนิดนั้นออกไป พร้อมข้อความ
  • ... if stock == 0 — Ruby ให้เขียน if ไว้ท้ายบรรทัดได้ อ่านว่า "ทำบรรทัดนี้ ถ้า stock เป็น 0"
  • พอ raise แล้ว method หยุดทันที — บรรทัด "ได้ ... 1 จาน" ไม่ถูกรันในรอบต้มยำ
  • rescue OutOfStockError => e — รับชนิดที่เราเพิ่งสร้าง แบบเดียวกับหัวข้อ 4

เพราะ error ทุกชนิดคือ class ที่สืบทอดกันเป็นตระกูล (ทวน < จาก บท 95) · rescue ชนิดไหน ก็รับลูกหลานของชนิดนั้นด้วย — เช่น rescue StandardError รับ OutOfStockError ได้ เพราะมันเป็นลูกของ StandardError

เทียบ Go: เหมือน errors.New("...") หรือสร้าง struct ที่มี method Error() · ต่างกันที่ Go คืน error ออกไป ส่วน Ruby โยน มันออกไป

⚠️ error ของเราเองให้ < StandardError เสมอ

rescue แบบไม่เขียนชนิด (และ rescue => e) รับเฉพาะตระกูล StandardError · ส่วน Exception คือแม่ใหญ่สุดที่ครอบเรื่องระดับระบบด้วย (เช่นการกด Ctrl+C สั่งหยุดโปรแกรม) จึงตั้งใจไม่ให้ rescue ธรรมดารับ · ถ้าเผลอให้ error ของเราสืบทอดจาก Exception: 

# wrong_parent.rb — สืบทอดผิดแม่
class PaymentError < Exception
end

begin
  raise PaymentError, "บัตรถูกปฏิเสธ"
rescue => e
  puts "รับไว้แล้ว"
end
$ ruby wrong_parent.rb
wrong_parent.rb:6:in '<main>': บัตรถูกปฏิเสธ (PaymentError)

ไม่ได้พิมพ์ "รับไว้แล้ว" — rescue => e ปล่อยผ่าน โปรแกรมพัง · แก้แค่เปลี่ยน Exception เป็น StandardError

ท่าย่อ: rescue ห้อยท้าย method (ไม่ต้องมี begin)

ถ้าอยากคุ้มครองทั้ง method ไม่ต้องเขียน begin — เอา rescue ไปห้อยก่อน end ของ method ได้เลย · โค้ด Rails ใช้ท่านี้บ่อยมาก จำหน้าตาไว้: 

# method_rescue.rb — rescue ห้อยท้าย method (ไม่ต้องมี begin)
def parse_people(text)
  Integer(text)
rescue ArgumentError
  puts "อ่านจำนวนคนไม่ออก ขอนับเป็น 1 คน"
  1
end

p parse_people("4")
p parse_people("four")
$ ruby method_rescue.rb
4
อ่านจำนวนคนไม่ออก ขอนับเป็น 1 คน

เขตคุ้มครองคือ "ทั้งตัว method" · ถ้าพัง ค่าบรรทัดสุดท้ายของช่อง rescue (1) จะกลายเป็นค่าที่ method คืน · (p คือพิมพ์ค่าออกมาแบบเห็นชนิดชัด ๆ — ทวน บท 93)

🗣 ศัพท์ของการรับ error
begin / rescue / end
คู่คำที่ขึงเขตคุ้มครอง · ≈ try / catch ของ TypeScript · พิมพ์บอก AI ได้ว่า “wrap only the risky line in begin/rescue and rescue ZeroDivisionError only”
rescue ชนิด => e
รับเฉพาะ error ชนิดนั้น แล้วเก็บตัว error ไว้ในตัวแปร e · ใช้ e.message ดูข้อความ · e.class ดูชนิด · ถาม senior ได้ว่า “ตรงนี้ควร rescue ชนิดไหน ให้แคบที่สุดเท่าที่ได้”
StandardError · custom error
StandardError คือแม่ของ error ทั่วไป · custom error คือชนิดที่เราสร้างเองด้วย class XxxError < StandardError · พิมพ์บอก AI ได้ว่า “define a custom error class that inherits from StandardError”
method-level rescue
เขียน rescue ห้อยท้าย method โดยไม่มี begin (คู่มือ Ruby เรียกว่า begin-less exception handler) · ถาม senior ได้ว่า “ทีมนี้ชอบ rescue ท้าย method หรือ begin ครอบเฉพาะบรรทัด”

6 · ensure — ทำเสมอ ไม่ว่าจะพังหรือไม่

บางงานต้องทำทุกครั้ง ไม่ว่าทางจะราบรื่นหรือพังกลางทาง เช่น ปิดเตา ปิดไฟล์ ปิดการเชื่อมต่อ · ช่อง ensure มีไว้สำหรับงานแบบนี้ — ถ้าเคยใช้ defer ของ Go (บทเรียน 08) มันคือความคิดเดียวกัน: "ออกทางไหนก็ต้องผ่านตรงนี้"

🔥 เทียบให้เห็นภาพ — ป้าย "ออกจากครัวต้องปิดแก๊ส"

ประตูครัวมีป้ายติดไว้: "ใครออกจากครัว ต้องปิดแก๊สก่อนเสมอ" · ทำอาหารเสร็จเรียบร้อยก็ต้องปิด · ทำพังกลางทางแล้ววิ่งไปตามผู้จัดการก็ต้องปิด — ออกทางไหนก็ต้องผ่านป้ายนี้
ensure คือป้ายนั้น · rescue คือ "ถ้ามีปัญหาให้ทำอะไร" ส่วน ensure คือ "ไม่ว่ายังไงก็ทำ"

ที่ไม่เหมือนกัน: คนจริงอาจลืมอ่านป้าย แต่ Ruby ไม่เคยลืม รันช่อง ensure ให้ทุกครั้ง · และ ensure ไม่ได้ "แก้" ปัญหา — ถ้าไม่มี rescue รับ error ก็ยังลอยต่อขึ้นไปหลังปิดแก๊สเสร็จ

🗣 ศัพท์ของ ensure
ensure · cleanup
ensure คือช่องที่รันเสมอ · งานในช่องนี้เรียกรวม ๆ ว่า cleanup (เก็บกวาด เช่นปิดไฟล์ ปิดการเชื่อมต่อ) ≈ defer ของ Go · ≈ finally ของ TypeScript · พิมพ์บอก AI ได้ว่า “put the cleanup in an ensure block so it runs even if this raises”
# predict.rb
def cook
  puts "1. ตั้งกระทะ"
  raise "แก๊สหมด"
  puts "2. ผัดข้าว"
end

begin
  cook
  puts "3. เสิร์ฟ"
rescue => e
  puts "4. แจ้งลูกค้า: #{e.message}"
ensure
  puts "5. ปิดเตา"
end

ข้อ 1 ถึง 5 — ข้อไหนถูกพิมพ์ออกมาบ้าง? (raise "ข้อความ" แบบไม่บอกชนิด = โยน error ชนิดทั่วไปชื่อ RuntimeError · rescue => e = รับ error ทั่วไปทุกชนิด แล้วเก็บไว้ใน e)

  • ข้อ 3 หายไป — error ลอยออกจาก cook มาถึงเขต begin แล้วกระโดดไปที่ rescue เลย ข้าม "เสิร์ฟ"
  • ข้อ 5 มาเสมอ — นี่คืองานของ ensure · ถ้าไม่พัง (ลองลบบรรทัด raise) ก็ยังได้ "5. ปิดเตา" อยู่ดี

8 · ใน Rails: error ที่ไม่มีใครรับ = หน้า 500 (แต่ร้านไม่ปิด)

แอป Rails ก็คือโค้ด Ruby · ถ้าโค้ดใน controller (หัวหน้าเชฟที่รับใบสั่ง — เจอละเอียดใน บท 102) โยน error แล้วไม่มีใครรับ Rails จะเป็นคนรับชั้นบนสุดให้เอง แล้วตอบกลับไปเป็นหน้า error · server ไม่ดับ

ลองในแอป wongnok_blog (แอปบล็อกในสไลด์ — บทความหนึ่งชิ้นเรียกว่า Post) · ตอนนี้ยังไม่มี database (รอ Day 2) จึงจำลองบทความด้วย Hash แทน

👀 ส่วนนี้แค่ดูผล ยังไม่ต้องพิมพ์ตาม

การทำให้โค้ดนี้รันได้ต้องรู้เรื่อง route (พนักงานต้อนรับที่ชี้ว่า URL ไหนไปหาใคร — บท 101) และ controller (บท 102) ก่อน · ตอนนี้ให้ดูแค่ว่า error ใน Rails หน้าตาเป็นยังไง

ไฟล์ app/controllers/posts_controller.rb:

class PostsController < ApplicationController
  # จำลองบทความด้วย Hash (ของจริงจะอยู่ใน database — Day 2)
  POSTS = { 1 => "Rails วันแรก" }

  def show
    title = POSTS[params[:id].to_i]   # หาไม่เจอ → nil
    render plain: title.upcase
  end
end
  • class PostsController < ApplicationController — controller ของบทความ สืบทอดจาก controller แม่ที่ rails new สร้างไว้ให้ (บท 102)
  • POSTS = { 1 => "Rails วันแรก" } — Hash ที่มีบทความเลข 1 อยู่ชิ้นเดียว · ชื่อตัวใหญ่ล้วน = ค่าคงที่ (บท 91)
  • params[:id] — เลขที่อยู่ใน URL เช่น /posts/2 ได้ "2" (เหมือน "จานที่ 2" ในใบสั่ง — บท 102) · .to_i แปลงเป็นตัวเลข
  • render plain: ... — ส่งข้อความกลับไปให้ browser (บท 102)
  • title.upcase — ทำเป็นตัวพิมพ์ใหญ่ · ถ้า title เป็น nil จะพัง (nil ไม่มี upcase)

เปิด server (bin/rails server) แล้วยิง request สามครั้ง: บทความที่มี → บทความที่ไม่มี → บทความที่มีอีกที

  • curl — โปรแกรมส่ง request จาก terminal (เหมือนเปิด browser แต่ได้ผลเป็นข้อความ) · -s -o /dev/null = ไม่ต้องโชว์เนื้อหาหน้าเว็บ · -w "%{http_code}\n" = พิมพ์แค่รหัสสถานะ · 500 = "server พังเอง" (Internal Server Error) · ข้อความที่ส่งกลับไม่มีการขึ้นบรรทัดใหม่ท้าย ถ้าลองเองใน zsh อาจเห็น % ต่อท้าย RAILS วันแรก — ไม่ใช่ error
  • log บอกชนิด error · ข้อความ · และไฟล์กับบรรทัดที่พัง — อ่านแบบเดียวกับหัวข้อ 3 · ตัวเลข ms ในบรรทัด Completed เป็นเวลาที่ใช้ (ของคุณจะต่างไปทุกครั้ง) ข้ามไปได้
  • request ที่สามยังได้คำตอบปกติ — พังแค่ request เดียว ร้านยังเปิดอยู่
  • ถ้าเปิดด้วย browser จะได้หน้า debug ของ Rails ชื่อ Action Controller: Exception caught (เฉพาะตอนพัฒนาในเครื่อง)
🍳 เทียบให้เห็นภาพ — จานเสียหนึ่งจาน ร้านไม่ต้องปิด

ลูกค้าสั่ง "บทความจานที่ 2" (request) · หัวหน้าเชฟ (controller) ไปเปิดตู้แล้วไม่เจอวัตถุดิบ แต่ดันลงมือทำต่อ — ทำไม่ได้ ครัวโวยวายขึ้นมา (error)
ผู้จัดการร้าน (Rails) เดินมารับเรื่อง ยกป้าย "ขออภัย ครัวมีปัญหา" ไปให้โต๊ะนั้น (หน้า 500) · โต๊ะอื่นที่สั่งจานที่ 1 ยังได้อาหารตามปกติ ร้านไม่ต้องปิด

ที่ไม่เหมือนกัน: ผู้จัดการจริงอาจเสนอเมนูอื่นแทนหรือขอโทษอย่างสุภาพ · แต่ Rails ทำแค่ส่งหน้า error มาตรฐาน — ถ้าอยากได้คำตอบที่ดีกว่า เช่น "ไม่พบบทความนี้" (404) เราต้องเขียนเอง · และ 500 ที่ได้ก็ไม่ได้บอกลูกค้าว่าพลาดตรงไหน (รายละเอียดอยู่ใน log ฝั่งร้านเท่านั้น)

ในโค้ด Rails จริง คุณจะเจอวิธี "ขึงคนรับให้ทุก action ทีเดียว" หน้าตาแบบนี้: rescue_from ActiveRecord::RecordNotFound, with: :render_404 — อ่านว่า "ถ้า action ไหนโยน error ชนิด หาข้อมูลไม่เจอ ให้ไปเรียก method render_404 แทน" · มันคือ rescue ที่ครอบทั้ง controller · ตอนนี้แค่จำหน้าตาไว้ ใช้จริงตอน Day 2

🗣 ศัพท์ฝั่ง Rails
500 Internal Server Error
รหัสคำตอบที่แปลว่า "ฝั่ง server พังเอง ไม่ใช่ความผิดของคนขอ" · ใน Rails มักมาจาก exception ที่ไม่มีใครรับ · ถาม senior ได้ว่า “หน้า 500 นี้ ดู log ตรงไหนถึงจะเจอบรรทัดที่พัง”

คำสั่งของ controller ที่บอกว่า "error ชนิดนี้ ไม่ว่าเกิดใน action ไหน ให้ method นี้รับ" · พิมพ์บอก AI ได้ว่า “use rescue_from in ApplicationController to render a custom 404 page” (Day 2)

9 · Duck typing — ไม่ถามว่าเป็นใคร ถามแค่ว่า "ทำได้ไหม"

เปลี่ยนเรื่องนิดหนึ่ง แต่เกี่ยวกันมาก · ใน Go ถ้าอยากให้ฟังก์ชันรับ "ของอะไรก็ได้ที่มี Title()" คุณต้องประกาศ interface ไว้ก่อน แล้ว compiler จะตรวจให้ตอน build (ทวน บทเรียน 10): 

// Go (บางส่วน — ไฟล์เต็มมี package, import และ type Menu ที่มี method Title())
type HasTitle interface {
	Title() string
}

func show(x HasTitle) {
	fmt.Println(x.Title())
}

// ... ใน main
show(Menu{})   // Menu มี Title() → ผ่าน
show(42)       // int ไม่มี Title() → build ไม่ผ่าน
$ go build ./...
# goduck
./main.go:19:7: cannot use 42 (constant of type int) as HasTitle value in argument to show: int does not implement HasTitle (missing method Title)

(# goduck คือชื่อ package ของตัวอย่าง) · Go จับได้ก่อนรัน · โปรแกรมไม่มีโอกาสได้รันสักบรรทัด
Ruby ไม่มี interface ให้ประกาศเลย · method แค่เรียก x.title ไปเฉย ๆ — ใครส่งอะไรมา ถ้ามี title ก็ผ่าน ไม่สนว่าเป็น class อะไร: 

# duck.rb — ใครมี .title ก็ใช้ได้
class Post
  def title
    "Rails วันแรก"
  end
end

class Menu
  def title
    "ข้าวผัดกระเพรา"
  end
end

def show(x)
  puts x.title
end

show(Post.new)
show(Menu.new)
show(42)
  • class Post กับ class Menu — สอง class ไม่เกี่ยวกันเลย ไม่มีแม่ร่วม ไม่มี interface · แค่บังเอิญมี method ชื่อ title เหมือนกัน (Post ตรงนี้เป็น class จำลองธรรมดา ไม่ใช่ Post ของ Rails)
  • def show(x) — ไม่บอกเลยว่า x ต้องเป็นอะไร
  • Post.new — สร้าง object จากแม่พิมพ์ Post (ทวน บท 95)

ชื่อ duck typing มาจากสำนวน "ถ้ามันเดินเหมือนเป็ด ร้องก๊าบ ๆ เหมือนเป็ด ก็ถือว่ามันเป็นเป็ด"
Ruby ไม่ขอดูใบรับรองว่าคุณ "เป็นเป็ดจริงไหม" (เป็น class อะไร) · ขอแค่ตอนที่ต้องร้อง คุณร้องได้ (มี method title) ก็พอ · Go ต่างออกไป: ต้องมีรายชื่อ "สิ่งที่เป็ดต้องทำได้" (interface) แล้ว compiler ตรวจทุกตัวก่อนปล่อยลงบ่อ

ที่ไม่เหมือนกัน: คนดูเป็ดจริงตัดสินได้ตั้งแต่แรกเห็น · แต่ Ruby ไม่ดูก่อนเลย — ปล่อยทุกตัวลงบ่อ แล้วรู้ว่าตัวไหนไม่ใช่เป็ด ก็ตอนสั่งให้ร้องแล้วมันร้องไม่ได้ (พังตอนรัน) · ถ้าอยากรู้ก่อน ต้องถามเอง (respond_to? ข้างล่าง) หรือเขียน test

respond_to? — ถามก่อนว่า "ทำได้ไหม"

ทุก object ใน Ruby มี method respond_to? ไว้ถามล่วงหน้าว่า "ตอบ method ชื่อนี้ได้ไหม":

# respond.rb — ถามก่อนว่า "ทำได้ไหม"
class Menu
  def title
    "ข้าวผัดกระเพรา"
  end
end

p Menu.new.respond_to?(:title)
p 42.respond_to?(:title)

def safe_show(x)
  if x.respond_to?(:title)
    puts "หัวข้อ: #{x.title}"
  else
    puts "(#{x.class} ไม่มี title)"
  end
end

safe_show(Menu.new)
safe_show(42)

🗣 ศัพท์ของ duck typing
duck typing
การตัดสินว่า object ใช้ได้ไหมจากสิ่งที่มันทำได้ (method ที่มี) ไม่ใช่จากชนิดของมัน · ถาม AI ได้ว่า “this method relies on duck typing — what objects can I pass to it?”
runtime · compile time
compile time = ตอน build ก่อนรัน (Go ตรวจ interface ตรงนี้) · runtime = ตอนโปรแกรมกำลังรันอยู่ (Ruby รู้ตรงนี้) · ถาม senior ได้ว่า “error นี้จับได้ตั้งแต่ compile time ไหม หรือต้องรอ runtime”
respond_to?
method ที่ทุก object มี ถามว่า "ตอบ method ชื่อนี้ได้ไหม" · พิมพ์บอก AI ได้ว่า “guard this call with respond_to?(:title) instead of checking the class”
NoMethodError
error ที่ได้เมื่อเรียก method ที่ object นั้นไม่มี — ตัวที่คุณจะเจอบ่อยที่สุดใน Ruby (หัวข้อถัดไป) · ถาม senior ได้ว่า “NoMethodError ตัวนี้ ควรกันที่ต้นทางหรือเช็คที่ปลายทาง”

11 · กับดักของคนที่มาจาก Go

# bill.rb — ขั้นที่ 1: ยังไม่มีใครรับ error
def split_bill(total, people_text)
  people = Integer(people_text)
  total / people
end

  2. แก้ split_bill ให้คืนข้อความแทนตัวเลข: ถ้าสำเร็จคืน "คนละ 300 บาท" (คำใบ้: เปลี่ยนบรรทัดสุดท้ายเป็น string ที่มี #{total / people} อยู่ข้างใน)
  3. เพิ่ม rescue ห้อยท้าย method (หัวข้อ 5) สองช่อง: หารด้วยศูนย์ → คืน "จำนวนคนต้องมากกว่า 0" · แปลงตัวเลขไม่ได้ → คืน "อ่านจำนวนคนไม่ออก (ArgumentError)" โดยดึงชื่อชนิดมาจาก e.class
  4. ต่อท้ายไฟล์ด้วยสามบรรทัดนี้ เพื่อเช็คตัวเอง — ต้องได้ true ทั้งสามบรรทัด:

ถ้าเจอ error นี้ แปลว่า…

  • undefined local variable or method 'e' for main (NameError) → คุณใช้ e แต่ลืมเขียน => e หลัง rescue ArgumentError
  • ยังพังด้วย invalid value for Integer(): "สาม" (ArgumentError) → มีแค่ช่อง ZeroDivisionError ยังไม่มีช่องรับ ArgumentError
  • syntax errors found (SyntaxError) พร้อมข้อความ expected an `end` to close the `def` statement → ลบ end ของ method ไปเผลอ ๆ · rescue ห้อยท้ายต้องอยู่ก่อน end ของ def
