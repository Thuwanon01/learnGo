1 · Go ส่ง error มาเป็น "ค่า" · Ruby "โยน" มันขึ้นไป

เริ่มจากของที่คุณรู้แล้ว ใน Go ฟังก์ชันที่พังได้จะคืน error กลับมาเป็นค่าตัวหนึ่ง เหมือนคืน int คืน string — คนเรียกต้องหยิบขึ้นมาดูเองทุกครั้ง ไม่ดู มันก็กองอยู่ตรงนั้นเฉย ๆ

Ruby (และ TypeScript) ทำอีกแบบ: พอเกิดเรื่อง โค้ดจะหยุดตรงนั้นทันที แล้วกระโดดออกจาก method ไปหา "คนรับ" ที่ใกล้ที่สุดข้างบน — ถ้า method ที่เรียกมาไม่รับ ก็ขึ้นไปอีกชั้น ขึ้นไปเรื่อย ๆ
ไม่มีบรรทัด if err != nil คั่นกลาง เพราะทางเดินของ error ไม่ได้ผ่านค่าที่ return เลย

นี่คือสไลด์หน้า 30 วางเทียบกันสามภาษา:

GoTypeScriptRuby
 
v, err := doThing()
if err != nil {
  return err
}

// error เป็นค่า
// ต้องรับทุกชั้น
// ลืมไม่ได้ compiler เตือน
 
try {
  doThing()
} catch (e) {
  handle(e)
} finally {
  cleanup()
}
 
begin
  do_thing
rescue ArgumentError => e
  handle(e)
rescue => e
  handle_any(e)
ensure
  cleanup
end

เทียบคำต่อคำ: begin ≈ try · rescue ≈ catch · ensure ≈ finally (และใกล้กับ defer ของ Go ใน บทเรียน 08 — "ทางออกไหนก็ต้องผ่านตรงนี้")
แต่มีจุดที่ Ruby เก่งกว่า TypeScript: catch (e) ของ TS รับได้ช่องเดียว ต้องไปเขียน if (e instanceof …) แยกเอง · ส่วน Ruby เขียน rescue ได้หลายช่อง แต่ละช่องระบุ class ของ error ที่จะรับ

โค้ดในสไลด์เป็นโครงเฉย ๆ (ไม่มี do_thing จริง) ผมเลยเติมให้รันได้ แล้วลองทั้งสามกรณี — โยน ArgumentError · หารด้วยศูนย์ · และไม่พังเลย: 

# slide30.rb
def do_thing(kind)
  raise ArgumentError, "จำนวนต้องมากกว่า 0" if kind == :arg
  10 / 0 if kind == :zero
  "ok"
end

[:arg, :zero, :fine].each do |kind|
  puts "--- #{kind}"
  begin
    puts do_thing(kind)
  rescue ArgumentError => e
    puts "handle:     #{e.class} — #{e.message}"
  rescue => e
    puts "handle_any: #{e.class} — #{e.message}"
  ensure
    puts "cleanup"
  end
end

อ่านผลทีละกรณี:

  • :arg — raise ArgumentError, "…" คือการโยน error ออกไป (คำว่า raise = throw ของ TS) · ช่อง rescue ArgumentError => e ตรง class พอดี เลยรับไป · => e แปลว่า "เอา error ก้อนนั้นมาใส่ตัวแปรชื่อ e" จะได้เรียก e.message ได้
  • :zero — 10 / 0 โยน ZeroDivisionError ออกมาเอง ไม่ใช่ ArgumentError ช่องแรกเลยข้าม · ไปตกช่อง rescue => e ที่ไม่ระบุ class
  • :fine — ไม่มีอะไรพัง ไม่เข้า rescue ช่องไหนเลย
  • ทั้งสามกรณีพิมพ์ cleanup — นั่นคืองานของ ensure: พังหรือไม่พังก็ต้องผ่าน

สังเกตอีกอย่าง: บรรทัด "ok" ไม่เคยถูกรันในกรณี :arg · พอ raise แล้ว method หยุดทันที ไม่มีการ "คืนค่าว่าง + error" แบบ Go

⚠️ "ลืมไม่ได้ compiler เตือน" ของฝั่ง Go จริงแค่ครึ่งเดียว

สไลด์เขียนใต้โค้ด Go ว่า "ลืมไม่ได้ compiler เตือน" — ผมลองแล้ว compiler เตือนเฉพาะตอนที่คุณตั้งชื่อตัวแปร err แล้วไม่ใช้: 

// main.go — รับ err มาแล้วไม่เช็ค (go.mod ตั้งชื่อ module ว่า go96)
package main

import (
	"errors"
	"fmt"
)

func doThing() (int, error) {
	return 0, errors.New("พัง")
}

func main() {
	v, err := doThing()
	fmt.Println(v)
}
$ go build ./...
# go96
./main.go:14:5: declared and not used: err

แต่ถ้าเขียน doThing() เฉย ๆ ทั้งบรรทัด หรือ v, _ := doThing() go build ผ่าน · go vet ก็ผ่าน · exit code = 0 ทั้งคู่

ประเด็นของสไลด์ยังถูก — ใน Go error อยู่ตรงหน้า ให้เห็นทุกครั้ง ต้องตั้งใจทิ้งมันถึงจะหาย · ส่วนใน Ruby คุณมองไม่เห็นเลยว่าบรรทัดไหนโยน error ได้บ้าง ต้องรู้เอาเองหรืออ่านเอกสาร

🔥 เทียบให้เห็นภาพ — ใบแจ้งปัญหาแนบกล่อง กับ สัญญาณเตือนไฟไหม้

Go เหมือนโกดังที่พัสดุทุกกล่องมีใบแจ้งปัญหาแนบมาด้วย คนรับกล่องทุกคนต้องหยิบใบนั้นขึ้นมาอ่าน แล้วตัดสินใจเองว่าจัดการเลย หรือส่งต่อให้หัวหน้า · ใบอยู่ติดกล่องตลอด จะทิ้งก็ต้องตั้งใจทิ้ง

Ruby เหมือนสัญญาณเตือนไฟไหม้ — เกิดเรื่องที่ห้องไหน ทุกคนในห้องนั้นหยุดงานทันที แล้วเสียงสัญญาณดังขึ้นไปทีละชั้น จนกว่าจะเจอชั้นที่มีเจ้าหน้าที่ประจำ (rescue) รับเรื่อง · ระหว่างทาง ใครที่มีหน้าที่ปิดแก๊สก่อนออก (ensure) ก็ทำของตัวเองให้เสร็จ · ถ้าขึ้นไปจนถึงดาดฟ้าแล้วไม่มีเจ้าหน้าที่สักคน — อพยพทั้งตึก (โปรแกรมพัง)

ที่ไม่เหมือนกัน: เจ้าหน้าที่ดับเพลิงจริงรับเหตุได้ทุกแบบ แต่ rescue ของ Ruby รับเฉพาะ "ชนิด" ที่ตัวเองระบุไว้ — rescue ArgumentError จะปล่อย ZeroDivisionError วิ่งผ่านหน้าไปเฉย ๆ เหมือนไม่ได้ยิน · และ rescue => e ที่ดูเหมือน "รับทุกอย่าง" ก็ไม่ได้รับทุกอย่างจริง (หัวข้อ 3 จะพิสูจน์)

🗣 ศัพท์ที่เพิ่งเรียนไป
exception
object ที่แทน "เรื่องผิดปกติ" ซึ่งถูกโยนออกมาแล้วทำให้โค้ดหยุดเดินตามปกติ · ใน Ruby ทุกตัวเป็น object ของ class ตระกูล Exception · ถาม senior ได้ว่า “method นี้ raise อะไรได้บ้าง ที่นี่เขียนไว้ตรงไหน” — เพราะ Ruby ไม่มี signature บอก
raise / rescue / ensure
สามคำหลัก: raise = โยน (≈ throw) · rescue = รับ (≈ catch) · ensure = ทำเสมอไม่ว่าจะพังหรือไม่ (≈ finally) · พิมพ์บอก AI ได้ว่า “wrap this in begin/rescue and only rescue ArgumentError, let everything else propagate”
propagate (error ลอยขึ้น)
การที่ exception ที่ไม่มีใครรับ วิ่งขึ้นไปหา method ที่เรียกมาทีละชั้น · ตรงข้ามกับ Go ที่คุณต้อง return err ส่งต่อเองทุกชั้น · ถาม senior ได้ว่า “error ตัวนี้ควรรับตรงนี้ หรือปล่อยให้ propagate ไปถึง controller”

2 · ชุดเต็ม: error ของเราเอง · rescue หลายช่อง · else · ensure

ใน Go คุณสร้าง error ของตัวเองด้วย struct ที่มี method Error() แล้วเช็คด้วย errors.As (บทเรียน 12) · ใน Ruby ง่ายกว่านั้นมาก — ประกาศ class ใหม่ที่สืบทอดจาก StandardError สองบรรทัดจบ แล้วเอาชื่อ class ไปใส่หลัง rescue ได้เลย

ตัวอย่างนี้ใส่ของครบทุกชิ้น — มีช่อง else ที่สไลด์ไม่ได้โชว์ด้วย: 

# shop.rb
class OutOfStockError < StandardError
end

def buy(stock, qty)
  raise ArgumentError, "qty ต้องมากกว่า 0 (ได้ #{qty})" unless qty.positive?
  raise OutOfStockError, "เหลือแค่ #{stock} ชิ้น" if qty > stock
  stock - qty
end

[[5, 2], [5, 9], [5, 0]].each do |stock, qty|
  begin
    left = buy(stock, qty)
  rescue OutOfStockError => e
    puts "ของหมด: #{e.message}"
  rescue ArgumentError => e
    puts "ใส่ค่าผิด: #{e.message}"
  else
    puts "ซื้อสำเร็จ เหลือ #{left}"
  ensure
    puts "  (ปิดตะกร้า)"
  end
end
p OutOfStockError.ancestors.take(3)

beginเสมอ — โค้ดที่อาจพังtry { }
rescue Xxx => eเมื่อ error ที่โยนมาเป็น Xxx หรือลูกหลานของมัน · ไล่จากบนลงล่าง เข้าได้ช่องเดียวerrors.As ของ Go · catch + instanceof ของ TS

ทำไมต้องมี else ในเมื่อเขียนต่อท้ายใน begin ก็ได้? เพราะโค้ดใน else ไม่ได้อยู่ใต้ความคุ้มครองของ rescue — ถ้าบรรทัด "ซื้อสำเร็จ" ไปพังเอง มันจะไม่ถูกจับผิดช่องไปเป็น "ใส่ค่าผิด" · ช่วยให้ begin เหลือแค่บรรทัดที่ตั้งใจจะคุ้มครองจริง ๆ

มีเรื่องหนึ่งที่คนมาจาก Go จะสะดุด: ใน Ruby บรรทัดสุดท้ายคือค่าที่คืน (เรื่องนี้กลับมาอีกทีในข้อควรระวังหัวข้อ 7) · แล้วถ้ามี else กับ ensure ปนอยู่ บรรทัดไหนนับเป็น "บรรทัดสุดท้าย"? 

# return_value.rb
def save
  puts "1. เริ่ม"
  result = Integer("12")
rescue ArgumentError
  puts "2. rescue"
else
  puts "3. else"
ensure
  puts "4. ensure"
end
p save

เพราะพอมีช่อง else ค่าที่คืนจะมาจากบรรทัดสุดท้ายของ else ซึ่งคือ puts (และ puts คืน nil เสมอ) · ส่วน ensure ไม่เคยเป็นค่าที่คืน — ผมลองแยกอีกไฟล์ให้ method ที่มีแค่ ensure ใส่ 99 ไว้บรรทัดท้ายของ ensure ผลที่ได้ยังเป็นค่าจากช่องหลัก (12) ไม่ใช่ 99

begin
  raise ArgumentError, "x"
rescue => e
  puts "rescue => e จับก่อน: #{e.class}"
rescue ArgumentError => e
  puts "ไม่มีวันมาถึงตรงนี้"
end

ตัวเลือกที่ 2 ถูก — รันจริงได้ rescue => e จับก่อน: ArgumentError บรรทัดเดียว · เอกสาร Ruby เขียนไว้ตรง ๆ ว่า exception จะถูกเทียบกับช่อง rescue จากบนลงล่าง และเข้าได้ครั้งเดียว · ArgumentError เป็นลูกของ StandardError ช่องแรกเลยรับไปก่อน

ตัวเลือกที่ 1 ผิดเพราะ Ruby ไม่ได้หา "ช่องที่ตรงที่สุด" หาแค่ "ช่องแรกที่ตรง" · ตัวเลือกที่ 3 ผิดเพราะเข้าได้ช่องเดียว ไม่ไหลต่อเหมือน case ของบางภาษา · ตัวเลือกที่ 4 ผิดเพราะ Ruby รันได้ปกติ — ผมรันด้วย ruby -w (เปิด warning) ก็ไม่มีคำเตือนสักบรรทัด

จุดที่ต้องจำ: เรียง rescue จากเฉพาะเจาะจง → กว้าง เสมอ · ถ้าเอาช่องกว้างขึ้นก่อน ช่องเฉพาะข้างล่างจะกลายเป็นโค้ดตายที่ไม่มีใครเตือน

3 · rescue => e ไม่ได้จับ "ทุกอย่าง"

rescue => e ที่ไม่ระบุ class หน้าตาเหมือน catch (e) ของ TS ที่รับทุกอย่าง · แต่ Ruby ซ่อนกติกาไว้ข้อหนึ่ง: ถ้าไม่ระบุ class มันจะรับแค่ StandardError กับลูกหลาน · ลองทายดูก่อนว่าโค้ดนี้จะเป็นยังไง 

# predict.rb
def load_report
  raise NotImplementedError, "ยังไม่ได้เขียน"
end

begin
  load_report
rescue => e
  puts "จับได้: #{e.class}"
end
puts "ไปต่อ"

จะพิมพ์ "จับได้: NotImplementedError" แล้วตามด้วย "ไปต่อ" ใช่ไหม?

ไม่ใช่ — โปรแกรมพังทั้งตัว ไม่พิมพ์ทั้ง "จับได้" และ "ไปต่อ":

เพราะ NotImplementedError ไม่ได้เป็นลูกของ StandardError — ดูผังครอบครัวข้างล่าง · ชื่อมันฟังดูธรรมดามาก หลายคนใช้ raise NotImplementedError เป็น "ที่คั่นไว้ก่อน" แล้วงงว่าทำไม rescue ไม่ทำงาน

ผมเขียนสคริปต์สั้น ๆ ไล่ .superclass (class แม่) ขึ้นไปจนถึง Exception ให้ดูว่าแต่ละตัวอยู่บ้านไหน: 

# chain.rb
def chain(klass)
  list = [klass]
  list << list.last.superclass while list.last != Exception
  list.join(" < ")
end

puts chain(NoMethodError)

🪤 เทียบให้เห็นภาพ — ตาข่ายนิรภัยใต้นั่งร้าน

rescue => e เหมือนตาข่ายนิรภัยที่ขึงไว้ใต้นั่งร้าน — ออกแบบมารับ "ของที่ร่วงลงมาระหว่างทำงาน" (StandardError): เครื่องมือหล่น อิฐหลุด คนพลาด · แต่ตั้งใจเว้นช่องไว้ให้ "คำสั่งเลิกงาน" (exit) กับ "เสียงไซเรนฉุกเฉิน" (Ctrl+C) ผ่านลงไปได้ · ถ้าคุณเอาผ้าใบปิดทุกช่อง (rescue Exception) ไซเรนดังแค่ไหนก็ไม่มีใครได้ยิน

ที่ไม่เหมือนกัน: ตาข่ายจริงเห็นด้วยตาว่าช่องตรงไหนเปิด · แต่ใน Ruby คุณดูจากชื่อไม่ออกเลย — NotImplementedError ชื่อลงท้ายด้วย "Error" เหมือนพวก ArgumentError ทุกอย่าง แต่ดันอยู่บ้าน ScriptError · วิธีเดียวที่แน่ใจคือ เช็คด้วย .ancestors หรือ .superclass อย่างที่ทำข้างบน

4 · rescue ระดับ method — ท่าที่จะเห็นใน Rails ทุกวัน

ถ้า begin ครอบทั้งตัว method อยู่แล้ว Ruby ให้ตัด begin กับ end ทิ้งได้ แล้วเขียน rescue / ensure ห้อยท้าย method ตรง ๆ · โค้ดใน Rails เขียนท่านี้แทบทั้งหมด เพราะสั้นกว่าและอ่านง่ายกว่า: 

# parse_age.rb
def parse_age(text)
  Integer(text)
rescue ArgumentError => e
  puts "แปลงไม่ได้: #{e.message}"
  0
ensure
  puts "ensure ของ parse_age"
end

p parse_age("forty")

ensure ของ parse_age
0

สามเรื่องที่ผลรันบอก:

  • Integer("forty") โยน ArgumentError — ต่างจาก "forty".to_i ที่คืน 0 เงียบ ๆ · อยากให้พังดัง ๆ ใช้ Integer() · อยากได้ค่า default ใช้ .to_i
  • ค่าที่ rescue คืน (0) กลายเป็นค่าที่ method คืน — คนเรียกได้ 0 ไปใช้ต่อ ไม่รู้ด้วยซ้ำว่ามีอะไรพัง
  • "ensure ของ parse_age" ขึ้นก่อน 42 — เพราะ ensure วิ่งตอน method กำลังจะออก ส่วน p พิมพ์ค่าหลังจาก method ออกไปแล้ว · คนมาจาก Go จะคุ้น: เหมือน defer ที่วิ่งก่อนค่า return ถึงมือคนเรียก

duck typing เหมือนพนักงานหน้าโรงหนังที่ไม่ขอดูบัตรประชาชน — ไม่สนว่าคุณเป็นใคร อายุเท่าไหร่ มาจากไหน ขอแค่ยื่นตั๋วได้ (ตอบ .title ได้) ก็เข้าได้ · ชื่อมาจากสำนวน "ถ้ามันเดินเหมือนเป็ด ร้องเหมือนเป็ด ก็ถือว่าเป็นเป็ด"

ที่ไม่เหมือนกัน: พนักงานจริงตรวจตั๋วที่ประตู ก่อนคุณเข้า · แต่ Ruby ปล่อยทุกคนเข้าไปนั่งก่อน แล้วค่อยขอดูตั๋วตอนหนังกำลังจะเริ่มฉากที่ต้องใช้ — คนไม่มีตั๋วนั่งดูโฆษณาไปได้ตั้งหลายนาทีก่อนโดนเชิญออก (เหมือน 6 บรรทัดแรกของ duck.rb ที่รันผ่านไปก่อน) · respond_to? คือการขอดูตั๋วเองก่อน แต่ไม่มีใครบังคับให้ทำ · สไลด์จึงสรุปว่า "ต้องพึ่ง test แทน compiler"

🗣 ศัพท์ของ duck typing
duck typing
การตัดสินว่า object ใช้ได้หรือไม่จากสิ่งที่มันทำได้ (method ที่มี) ไม่ใช่จาก class ของมัน · และ Ruby ตรวจตอนรันจริงเท่านั้น · ถาม AI ได้ว่า “is this method relying on duck typing? what objects can I pass to it”
NoMethodError
error ที่ได้เมื่อเรียก method ที่ object นั้นไม่มี · ตัวที่เจอบ่อยสุดคือ undefined method '…' for nil ซึ่งแปลว่า "ตัวแปรนี้เป็น nil ทั้งที่คุณคิดว่ามีของ" (เรื่อง nil อยู่ใน บทเรียน 94) · ถาม senior ได้ว่า “nil ตัวนี้มาจากไหน ควรกันที่ต้นทางหรือเช็คที่ปลายทาง”
respond_to?
method ที่ทุก object มี ถามว่า "ตอบ method ชื่อนี้ได้ไหม" คืน true/false · ส่งชื่อเป็น Symbol (:title) · พิมพ์บอก AI ได้ว่า “guard this call with respond_to?(:title) instead of checking the class” — การเช็ค x.is_a?(Post) จะทำลายข้อดีของ duck typing ทิ้ง

แล้วใน Rails? สไลด์หน้า 31 ชี้ไปที่ render partial: "post", object: anything_that_has_title — แปลว่า partial (ชิ้นส่วนของหน้าเว็บ) ที่เรียก .title ใช้ได้กับทุก object ที่มี .title ไม่ต้องเป็น Post · เรื่อง partial เต็ม ๆ รอ Day 3 ตอนนี้จำแค่ว่า view ของ Rails ใช้ duck typing ทั้งระบบ

ใน duck.rb ถ้าย้ายบรรทัด show(42) ขึ้นไปไว้บรรทัดแรกสุดของไฟล์ (ก่อน class Post) จะเกิดอะไร?

ตัวเลือกที่ 4 ถูก — ผมย้ายบรรทัดแล้วรันจริงได้แบบนี้:

duck_top.rb:1:in '<main>': undefined method 'show' for main (NoMethodError)

show(42)
^^^^

Ruby รันจากบนลงล่างทีละบรรทัด · def show เองก็เป็นแค่ "บรรทัดที่สร้าง method" — ถ้ายังรันไม่ถึง method นั้นก็ยังไม่มีอยู่ · บรรทัดแรกจึงพังเพราะไม่รู้จัก show (main คือ object ระดับบนสุดของไฟล์) ไม่ได้ไปถึงการเรียก .title บน 42 เลย

ตัวเลือกที่ 1 คือพฤติกรรมของ Go/TS ไม่ใช่ Ruby — ไม่มีขั้นตรวจ type ก่อนรัน · ตัวเลือกที่ 2 ผิดเพราะพังแล้วบรรทัดที่เหลือไม่ได้รัน · ตัวเลือกที่ 3 ผิดเพราะ respond_to? ป้องกันเฉพาะใน safe_show ที่เขียนเช็คไว้เท่านั้น

จุดที่ต้องจำ: ใน Ruby ลำดับบรรทัดคือทุกอย่าง — ทั้ง method ที่ยังไม่ถูกประกาศ และ method ที่ object ไม่มี ล้วนรู้ตัวตอนรันถึงบรรทัดนั้นจริงเท่านั้น

ตัวเลือกที่ 2 ฟังดูมีเหตุผล แต่ลองคิดกลับ: ถ้า Rails ไปเปิดหาไฟล์ชื่อ blog_post.rb ต่อให้ระบบไฟล์ไม่สนตัวพิมพ์ blogPost.rb ก็ยังไม่ตรงอยู่ดีเพราะขาด _ · ที่รอบ ① ผ่านได้จึงมาจากทางเดียว คือ Zeitwerk ไล่รายชื่อไฟล์ในโฟลเดอร์ (ในซอร์สของ Zeitwerk 2.8.3 ใช้ Dir.each_child) แล้ว camelize ชื่อที่เจอ · ตัวเลือกที่ 3 ผิดเพราะ Rails ไม่แตะชื่อไฟล์ของคุณ (รอบ ① ไฟล์ยังชื่อ blogPost.rb) · ตัวเลือกที่ 4 ผิดเพราะ Zeitwerk ไม่ได้เปิดอ่านไฟล์เพื่อหา class — ถ้าเปิดอ่าน รอบ ② ก็ต้องผ่าน

จุดที่ต้องจำ: ใน Rails ชื่อไฟล์คือสัญญา · ใช้ snake_case ตามที่ generator สร้างให้ แล้วทั้งทางไป (camelize) และทางกลับ (underscore) จะตรงกันเสมอ

8 · ภารกิจ — แปลง error ให้มีความหมาย แล้วเขียน test พิสูจน์

🎯 ภารกิจ: parse_qty

ช่องกรอก "จำนวนสินค้า" ของ wongnok_blog ส่งมาเป็นข้อความ · เขียนไฟล์ qty.rb ที่มี:

  1. class InvalidQuantityError ของคุณเอง (สืบจากอะไร — ทบทวนหัวข้อ 3)
  2. method parse_qty(text) ที่แปลงข้อความเป็นตัวเลขด้วย Integer() · ถ้าไม่ใช่ตัวเลข หรือไม่มากกว่า 0 ให้ raise InvalidQuantityError พร้อมข้อความที่บอกว่าผิดเพราะอะไร · ใช้ rescue ระดับ method (ไม่มี begin)
  3. method safe_qty(text) ที่เรียก parse_qty แล้วรับเฉพาะ InvalidQuantityError พิมพ์ข้อความแจ้งผู้ใช้ แล้วคืน 1 เป็นค่า default
  4. เขียน test พิสูจน์ ใน qty_test.rb ด้วย Minitest (ติดมากับ Ruby — เป็นตัวเดียวกับที่ Rails ใช้ใน test/ · เรื่อง testing เต็ม ๆ อยู่ Day 4) ให้ครอบคลุม: ตัวเลขปกติ · ไม่ใช่ตัวเลข (เช็คข้อความด้วย) · ศูนย์ · และ safe_qty คืน 1

คำใบ้: assert_raises(ErrorClass) { … } คืน error object ออกมา เอาไปเช็ค .message ต่อได้

def parse_qty(text)
  qty = Integer(text)
  raise InvalidQuantityError, "จำนวนต้องมากกว่า 0 (ได้ #{qty})" unless qty.positive?
  qty
rescue ArgumentError
  raise InvalidQuantityError, "ไม่ใช่ตัวเลข: #{text}"
end

def safe_qty(text)
  parse_qty(text)
rescue InvalidQuantityError => e
  puts "แจ้งผู้ใช้: #{e.message}"
  1
end

สามจุดที่ควรสังเกตในเฉลย:

  • raise ข้างใน rescue ได้ — แปลง ArgumentError ที่ไม่มีความหมายทางธุรกิจ ให้เป็น InvalidQuantityError ที่คนอ่านเข้าใจ · คล้าย fmt.Errorf("...: %w", err) ของ Go ที่ห่อ error ให้มีบริบท
  • InvalidQuantityError ที่ raise ตอน qty เป็น 0 ไม่ถูก rescue ArgumentError ของตัวเองจับ เพราะมันไม่ใช่ลูกของ ArgumentError — มันลอยออกไปหาคนเรียกตามที่ตั้งใจ
  • safe_qty รับแค่ InvalidQuantityError ไม่ใช่ rescue => e — ถ้าวันหนึ่ง parse_qty พังด้วยเรื่องอื่นที่ไม่คาดคิด มันจะพังดัง ๆ ให้เห็น แทนที่จะกลายเป็น "1 ชิ้น" เงียบ ๆ

ลองทำต่อ: เปลี่ยน < StandardError เป็น < Exception แล้วรัน test ซ้ำ — ทุกข้อยังผ่าน เพราะทุกที่ระบุชื่อ class ตรง ๆ · แล้วลองแก้ safe_qty ให้ใช้ rescue => e แทน จะเห็นด้วยตาว่าทำไมหัวข้อ 3 ถึงสำคัญ
