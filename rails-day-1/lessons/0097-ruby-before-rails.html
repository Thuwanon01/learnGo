บทเรียน 97 · Rails · Day 1

อ่านโค้ด Rails ไม่งง — 5 ไวยากรณ์ที่ Rails ใช้บ่อย

~25 นาที (มี 5 ชิ้น แต่ละชิ้นสั้น) · ควรผ่าน บท 92 (hash · symbol) · บท 93 (method · block) · บท 95 (class · @ตัวแปร) มาก่อน

เปิดโค้ด Rails ครั้งแรก หลายคนเจอบรรทัดอย่าง validates :title, presence: true แล้วรู้สึกว่า "นี่มันภาษาอังกฤษหรือโค้ด?"
อ่านบทนี้จบ คุณจะถอดบรรทัดแบบนี้ออกเป็นชิ้น ๆ ได้เอง และตอบได้ว่าแต่ละชิ้นคืออะไร
บอกไว้ก่อนเลยว่าไม่มีเวทมนตร์ — ทุกบรรทัดเป็นการเรียก method ธรรมดา แค่เขียนย่อ และใช้ของห้าอย่างที่บทนี้จะถอดให้ดูทีละชิ้น · และเราจะพิสูจน์ด้วย Ruby ล้วน ๆ ที่คุณรันเองได้

🔁 ทวนก่อนเริ่ม (คำจากบทก่อน ๆ ที่บทนี้ใช้)

  • method — คำสั่งที่ตั้งชื่อไว้เรียกใช้ซ้ำ ประกาศด้วย def … end (บท 93)
  • hash — กล่องเก็บของเป็นคู่ "ชื่อ: ค่า" เช่น { title: "สวัสดี" } (บท 92)
  • symbol — ชื่อที่ขึ้นต้นด้วย : เช่น :title ใช้เป็นป้ายชื่อ (บท 92)
  • block — ก้อนโค้ด do … end ที่แนบไปกับการเรียก method · |x| คือช่องรับของ (บท 93)
  • @ตัวแปร — ตัวแปรที่ติดอยู่กับ object (บท 95) · ในบทนี้ @post แปลว่า "บทความหนึ่งชิ้น"

แอปตัวอย่างของสไลด์ คือบล็อกชื่อ wongnok_blog · ของหลักคือบทความ (ภาษาอังกฤษ post) — Post ตัวใหญ่ = แม่พิมพ์ของบทความ · posts ตัวเล็ก = ตารางที่เก็บบทความหลายชิ้น

🧰 เวอร์ชันที่ใช้ตรวจ: Ruby 4.0.9 · Rails 8.1.4 (สไลด์ใช้ Ruby 4.0.6 · Rails 8.1.3 — เรื่องในบทนี้ไม่ต่างกัน) · ผลรันทุกก้อนมาจากการรันจริง

สามบรรทัดที่ดูเหมือนภาษาอังกฤษ

นี่คือโค้ด Rails จริงที่คุณจะเจอในคอร์สนี้ · ยังไม่ต้องเข้าใจ แค่ดูหน้าตาไว้ก่อน: 

validates :title, presence: true

redirect_to @post, notice: "saved"

form_with model: @post do |f|
  f.text_field :title
end

แต่ละบรรทัดอยู่คนละที่ในแอป · เทียบกับร้านอาหาร (ภาพที่ใช้ทั้งคอร์ส) ได้แบบนี้:

บรรทัดอยู่ส่วนไหนของ MVC (บท 90)ในร้านอาหารแปลเป็นภาษาคน
validates …model (Day 2)คนดูแลห้องเก็บวัตถุดิบ"แฟ้มบทความทุกแผ่นต้องมีชื่อเรื่อง ไม่มีห้ามเก็บเข้าตู้"
redirect_to …controller (บท 102)หัวหน้าเชฟ"บันทึกเสร็จแล้ว พาลูกค้าไปหน้าบทความนั้น พร้อมแปะโน้ตว่า saved"
form_with …view (บท 103)การจัดจานก่อนเสิร์ฟ"วาดแบบฟอร์มให้กรอกบทความ มีช่องชื่อเรื่องหนึ่งช่อง"

ถ้าคุณมาจาก Go จะรู้สึกแปลก เพราะใน Go ทุกการเรียกฟังก์ชันมีวงเล็บเสมอ เช่น c.Redirect(http.StatusSeeOther, "/posts/1") ใน Gin
ส่วน Ruby ยอมให้ละของหลายอย่าง จนโค้ดอ่านเหมือนประโยค · บทนี้จะถอดทีละชิ้น ทั้งหมด 5 ชิ้น

ชิ้นที่ 1 — วงเล็บละได้

ใน Ruby การเรียก method จะใส่วงเล็บหรือไม่ใส่ก็ได้ ผลเหมือนกันทุกอย่าง
ลองดูด้วย method เล็ก ๆ ที่เราเขียนเอง: 

# paren.rb
def greet(name)
  puts "สวัสดี #{name}"
end

greet("ต้น")    # แบบมีวงเล็บ
greet "ต้น"     # แบบละวงเล็บ
$ ruby paren.rb
สวัสดี ต้น
สวัสดี ต้น
  • def greet(name) … end — ประกาศ method ชื่อ greet ที่รับค่าหนึ่งตัว (บท 93)
  • "สวัสดี #{name}" — #{} คือการเสียบค่าตัวแปรลงใน string (บท 91)
  • greet("ต้น") กับ greet "ต้น" — คือการเรียก method ตัวเดียวกัน ต่างกันแค่วงเล็บ

เพราะฉะนั้น validates :title ก็คือ validates(:title) — การเรียก method ชื่อ validates ไม่ใช่คำสั่งพิเศษของภาษา
Go ทำแบบนี้ไม่ได้เลย: เขียน fmt.Println "hi" แล้ว go build ไม่ผ่านแน่นอน

🍳 เทียบให้เห็นภาพ — สั่งอาหารแบบพูดย่อ

ลูกค้าประจำเดินเข้าร้านแล้วพูดว่า "กะเพรา ไข่ดาว" แม่ครัวเข้าใจทันที ไม่ต้องพูดเต็มว่า "ขอสั่งเมนูกะเพรา โดยมีตัวเลือกเพิ่มไข่ดาว"
ใบสั่งที่ไปถึงครัวเป็นใบเดียวกัน — พูดย่อหรือพูดเต็ม ครัวทำเหมือนกัน

ที่ไม่เหมือนกัน: คนฟังในร้านเดาจากบริบทได้ แต่ Ruby เดาไม่ได้ — มันมีกฎตายตัว · บางกรณี (เช่นเรียก method ซ้อนกันหลายชั้นในบรรทัดเดียว) ถ้าไม่ใส่วงเล็บ Ruby จะจับคู่ผิดจากที่คุณตั้งใจ
กฎจำง่าย: อ่านแล้วงงเมื่อไหร่ ใส่วงเล็บเองได้เสมอ ไม่ผิด

🗣 ศัพท์ที่เพิ่งเรียนไป
method call · optional parentheses
การเรียก method · ใน Ruby วงเล็บรอบ argument เป็นของไม่บังคับ · ถาม AI ได้ว่า "rewrite this Ruby line with explicit parentheses" แล้วจะเห็นทันทีว่าอะไรคือ method อะไรคือค่าที่ส่งเข้าไป
DSL (Domain-Specific Language)
โค้ดที่ออกแบบให้อ่านเหมือนภาษาเฉพาะเรื่อง · ใน Rails มันคือการเรียก method ธรรมดาที่ละวงเล็บไว้ · บอก senior ได้ว่า "บรรทัดนี้เป็น DSL ของ Rails ใช่ไหมครับ ข้างในคือเรียก method อะไร"

ชิ้นที่ 2 — hash ตัวสุดท้ายละปีกกาได้

ถ้าของชิ้นสุดท้ายที่ส่งเข้า method เป็น hash Ruby ยอมให้ไม่ต้องเขียนปีกกา { }
เวลาเห็น ชื่อ: ค่า ต่อท้ายบรรทัด ให้อ่านว่า "นี่คือ hash ก้อนเดียว ที่ถูกถอดปีกกาออก"

วิธีพิสูจน์ที่ง่ายที่สุด: เขียน validates ปลอมขึ้นมาเอง ให้มันรับของแล้ว p ออกมาดูเฉย ๆ จะได้เห็นว่า Ruby ส่งอะไรเข้าไปจริง (p คือคำสั่งพิมพ์ค่าแบบเห็นชนิดของมัน · บท 93) 

# hash1.rb — validates ปลอม: รับของแล้ว p ออกมาดูเฉย ๆ
def validates(name, options)
  p name
  p options
end

validates :title, presence: true, length: { minimum: 5 }        # แบบที่เขียนใน Rails
validates(:title, { presence: true, length: { minimum: 5 } })   # แบบเขียนเต็ม

สองบรรทัดล่างหน้าตาต่างกันมาก (บรรทัดแรกไม่มีวงเล็บ ไม่มีปีกกาครอบ) — คิดว่า Ruby จะพิมพ์ออกมาเหมือนกันหรือต่างกัน?

$ ruby hash1.rb
:title
{presence: true, length: {minimum: 5}}
:title
{presence: true, length: {minimum: 5}}

เหมือนกันทุกตัวอักษร · ทั้งสองแบบ method ได้ของสองชิ้น: ชิ้นแรกคือ symbol :title · ชิ้นที่สองคือ hash หนึ่งก้อน

อ่านโค้ดทีละส่วน:

  • def validates(name, options) — method ปลอมของเรา รับของสองชิ้น ตั้งชื่อว่า name กับ options
  • presence: true — คู่ "ชื่อ: ค่า" หนึ่งคู่ใน hash (ชื่อ presence ค่า true)
  • length: { minimum: 5 } — อีกคู่หนึ่ง ที่ค่าของมันเป็น hash อีกก้อน (hash ซ้อน hash) · ปีกกาด้านในห้ามละ เพราะมันไม่ใช่ตัวสุดท้าย
  • บรรทัดแบบเขียนเต็ม — ใส่วงเล็บ (ชิ้นที่ 1) และปีกกาครอบ hash ตัวสุดท้ายให้ครบ

redirect_to ในสามบรรทัดแรกก็เป็นแบบเดียวกัน · ลองด้วย method ปลอมอีกตัว (@post ตรงนี้เป็นแค่ string จำลอง · ใน Rails มันคือบทความจริงที่ controller หยิบมา): 

# hash2.rb — redirect_to ปลอม
def redirect_to(target, options)
  p target
  p options
end

@post = "บทความที่ 1 (จำลอง)"   # ใน Rails ตัวนี้คือบทความจริงที่ controller หยิบมา

redirect_to @post, notice: "saved"
redirect_to(@post, { notice: "saved" })
$ ruby hash2.rb
"บทความที่ 1 (จำลอง)"
{notice: "saved"}
"บทความที่ 1 (จำลอง)"
{notice: "saved"}

ใน Go ไม่มีท่านี้ · ถ้าอยากส่ง "ก้อนตัวเลือก" เข้าฟังก์ชัน ต้องประกาศ struct แล้วเขียนปีกกาเองทุกครั้ง (โค้ด Go ข้างล่างเป็นการเลียนแบบรูปร่างเพื่อเทียบเท่านั้น ไม่ใช่ library จริง):

Go — ต้องมีวงเล็บและปีกกาเสมอ

Validates("title", Rules{Presence: true})

Ruby — ละได้ทั้งคู่

validates :title, presence: true
🧾 เทียบให้เห็นภาพ — ใบสั่งอาหารที่มีช่อง "หมายเหตุ"

ใบสั่งหนึ่งใบมีช่อง เมนู (ของหลัก) กับช่อง หมายเหตุ (ตัวเลือกพ่วงท้าย)
ลูกค้าพูดว่า "กะเพรา, เผ็ด: มาก, ไข่: ดาว" พนักงานจดทุกตัวเลือกลงช่องหมายเหตุช่องเดียวให้เอง ลูกค้าไม่ต้องพูดว่า "เปิดวงเล็บหมายเหตุ … ปิดวงเล็บ"
validates :title, presence: true ก็เหมือนกัน — :title คือเมนู · presence: true คือหมายเหตุ · Ruby รวบหมายเหตุทั้งหมดเป็น hash ก้อนเดียวให้

ที่ไม่เหมือนกัน: พนักงานร้านรับหมายเหตุได้ทุกแบบ จะเขียนใส่กระดาษแนบมาก็ยังรับ
แต่ใน Ruby มี method บางตัวที่ "รับหมายเหตุแบบพูดเท่านั้น" (keyword argument · บท 93) ถ้าคุณใส่ปีกกาเอง มันจะปฏิเสธทันที — ดูชิ้นที่ 3

⚠️ เขียนเต็มไว้ "อ่านให้เข้าใจ" เท่านั้น อย่าเติมปีกกาเองในโค้ด Rails จริง — validates กับ redirect_to รับได้ แต่ form_with ใส่ปีกกาแล้วพังด้วย ArgumentError · เขียนแบบไม่มีปีกกา (แบบที่คู่มือ Rails เขียน) ใช้ได้กับทุกตัว

🗣 ศัพท์ที่เพิ่งเรียนไป
options hash · trailing hash
hash ที่ส่งเป็นของชิ้นสุดท้ายเพื่อบอก "ตัวเลือก" · Ruby ให้ละปีกกาได้ · ถาม AI ได้ว่า "in this Rails call, which part is the options hash?"
keyword argument
ช่องรับค่าที่จับคู่ด้วยชื่อ เช่น def form_with(model:) (บท 93) · ตั้งแต่ Ruby 3 ถือว่าเป็นคนละอย่างกับ hash ที่มีปีกกา · บอก senior ได้ว่า "ผมส่ง hash ที่มีปีกกาเข้า method ที่รับ keyword เลยโดน ArgumentError ครับ"

redirect_to @post, notice: "saved", status: :see_other ถ้าเขียนเต็ม (ใส่วงเล็บและปีกกาครบ) จะได้แบบไหน?
(status: :see_other คือตัวเลือกบอกรหัสตอบกลับ · ความหมายไม่สำคัญ ข้อนี้ดูแค่รูปร่าง)

ตัวเลือกที่ 2 ถูก · ของชิ้นแรกคือ @post · ที่เหลือทั้งหมดเป็นคู่ "ชื่อ: ค่า" จึงรวมเป็น hash ก้อนเดียวเป็นชิ้นที่สอง

ตัวเลือกที่ 1 กับ 4 ผิด เพราะเปลี่ยน notice กับ status ให้กลายเป็นการเรียก method ซึ่งไม่ใช่สิ่งที่บรรทัดเดิมทำ — ในบรรทัดเดิมมันเป็นแค่ชื่อช่องใน hash · ตัวเลือกที่ 3 ผิด เพราะยัด @post เข้าไปใน hash ทั้งที่มันไม่มีชื่อช่อง — รันจริง Ruby ไม่ยอมรันเลย (SyntaxError) และบอกว่า expected a `=>` between the hash key and value

จุดที่ต้องจำ: เห็น ชื่อ: ค่า ต่อท้ายบรรทัดเมื่อไหร่ ให้อ่านว่า "hash ก้อนเดียวที่ถอดปีกกาออก"

ชิ้นที่ 3 — block ที่ได้รับของ |f| และ yield

บรรทัด form_with model: @post do |f| ทำให้คนงงมากที่สุด เพราะ f โผล่มาจากไหนไม่รู้
คำตอบคือ: method form_with เป็นคนสร้างของชิ้นหนึ่ง แล้วยื่นให้ block · ช่อง |f| คือมือที่รับของชิ้นนั้น
คำสั่งที่ใช้ "ยื่นของให้ block" ชื่อว่า yield (แปลตรงตัวว่า "ส่งมอบ")

🧰 เทียบให้เห็นภาพ — หัวหน้าห้องจัดจานยื่นกล่องเครื่องมือให้ลูกมือ

หัวหน้าห้องจัดจาน (form_with) เตรียมกล่องเครื่องมือไว้หนึ่งกล่อง แล้วยื่นให้ลูกมือพร้อมบอกว่า "เชิญจัดตามใจเลย" (yield)
ลูกมือ (block) รับกล่องมา เรียกมันว่า f แล้วหยิบเครื่องมือในกล่องมาใช้ (f.text_field :title)
ลูกมือทำเสร็จ ส่งงานคืน · หัวหน้าเก็บงานแล้วยกจานออกไปเสิร์ฟ (ได้ HTML ของฟอร์ม)

ที่ไม่เหมือนกัน: ลูกมือจริงเห็นว่ากล่องมีเครื่องมืออะไรบ้าง แต่ในโค้ด คุณมองไม่เห็นว่า f มี method อะไร — ต้องไปเปิดคู่มือของ form_with ดู
และถ้าไม่มีลูกมือมารับเลย (เรียก method โดยไม่แนบ block) โปรแกรมไม่ได้รอ แต่พังทันที

มาเขียน form_with จิ๋วที่รันได้จริงกัน (จำลองหลักการ ไม่ใช่โค้ดของ Rails จริง · บทความจำลองด้วย hash เพราะยังไม่มี Rails): 

# form.rb — form_with จิ๋ว (จำลองหลักการ ไม่ใช่โค้ดของ Rails จริง)
class FormBuilder
  def initialize(model)
    @model  = model
    @fields = []
  end

  def text_field(name)
    value = @model[name]
    @fields << "  <input name=\"post[#{name}]\" value=\"#{value}\">"
  end

  def to_html
    "<form>\n" + @fields.join("\n") + "\n</form>"
  end
end

def form_with(model:)
  builder = FormBuilder.new(model)   # ① เตรียมกล่องเครื่องมือ
  yield(builder)                     # ② ยื่นกล่องให้ block → กลายเป็น f
  builder.to_html                    # ③ เก็บงาน แล้วส่ง HTML คืน
end

post = { title: "สวัสดี Ruby", body: "บทความแรก" }   # บทความจำลองด้วย hash

html = form_with model: post do |f|
  f.text_field :title
  f.text_field :body
end

puts html
$ ruby form.rb
<form>
  <input name="post[title]" value="สวัสดี Ruby">
  <input name="post[body]" value="บทความแรก">
</form>

ส่วน form_with — หัวใจของเรื่อง:

  • def form_with(model:) — รับค่าแบบ keyword ชื่อ model (บท 93) · ตอนเรียกต้องเขียน model: …
  • ① สร้างกล่องเครื่องมือหนึ่งกล่อง เก็บไว้ในตัวแปร builder
  • ② yield(builder) — กระโดดไปทำ block ที่แนบมา และยื่น builder ให้ · ใน block ของชิ้นนี้จึงมีชื่อว่า f
  • ③ block ทำเสร็จ กลับมาบรรทัดนี้ · บรรทัดสุดท้ายของ method คือค่าที่ส่งคืนอัตโนมัติ (บท 93)
  • form_with model: post do |f| … end — ละวงเล็บ (ชิ้นที่ 1) · ส่ง keyword model: · แนบ block ที่มีช่องรับของชื่อ f

ชื่อ f ไม่ใช่คำพิเศษ · ผมลองเปลี่ยนเป็น |form| แล้วเขียน form.text_field :title ก็ได้ผลเหมือนเดิมทุกตัวอักษร · คนเขียน Rails แค่นิยมใช้ f เพราะสั้น

end

form_with สร้าง f แล้วยื่นให้ block ของคุณ · คุณแค่เรียก f.text_field

ชิ้นที่ 4 — symbol อยู่ทุกที่

ในสามบรรทัดแรกมี symbol ซ่อนอยู่มากกว่าที่ตาเห็น · ทวนจากบท 92: symbol คือ "ป้ายชื่อ" ที่ Rails ใช้เรียกชื่อของต่าง ๆ เช่นชื่อช่อง ชื่อคอลัมน์ ชื่อตัวเลือก

  • :title — โคลอนอยู่หน้า = symbol ตัวเดี่ยว ๆ
  • presence: true — โคลอนอยู่หลัง = คู่ใน hash ที่ชื่อช่องเป็น symbol :presence
  • status: :see_other — มีทั้งสองแบบในคู่เดียว: ชื่อช่องคือ :status ค่าคือ symbol :see_other

พิสูจน์ว่าชื่อช่องใน hash เป็น symbol จริง:

ใน Go คุณใช้ string เป็นชื่อช่องแทน เช่น c.JSON(200, gin.H{"title": "สวัสดี"}) · Ruby เลือกใช้ symbol เพราะเป็นป้ายชื่อที่ "ตายตัว" เทียบกันได้เร็ว

symbol key
ชื่อช่องใน hash ที่เป็น symbol · เขียน { title: "x" } ก็คือ { :title => "x" } (=> คือวิธีเขียน hash แบบเก่า ยังเจอในโค้ดเก่า ๆ) · ถาม AI ได้ว่า "is this hash key a string or a symbol?" — สำคัญตอนอ่านค่าเพราะ h[:title] กับ h["title"] ไม่ใช่ช่องเดียวกัน

ในบรรทัด validates :title, presence: true อะไรเป็น symbol บ้าง?

ตัวเลือกที่ 2 ถูก · presence: true คือคู่ใน hash ที่ชื่อช่องเป็น symbol — sym.rb พิสูจน์ให้เห็นว่า keys ได้ [:presence]

ตัวเลือกที่ 1 ผิด เพราะ string ต้องมีเครื่องหมายคำพูด · ตัวเลือกที่ 3 ผิด เพราะ symbol เป็นของภาษา Ruby ใครเรียก method อะไรก็ใช้ได้ · ตัวเลือกที่ 4 ผิด เพราะ true คือค่าจริง/เท็จ ไม่ใช่ป้ายชื่อ

จุดที่ต้องจำ: โคลอนหน้า (:title) หรือโคลอนหลัง (presence:) ก็คือ symbol ทั้งคู่

ชิ้นที่ 5 — method ที่ Rails สร้างให้ตอนรัน

นี่คือคำถามที่ผู้เรียนถามบ่อยที่สุด: "ใน Go ต้องประกาศ struct ชัดเจน แล้วใน Rails post.title มาจากไหน?"
เพราะไฟล์ model ของบทความใน Rails หน้าตาแบบนี้ — ว่างเปล่าจริง ๆ: 

# app/models/post.rb — ทั้งไฟล์ (Rails สร้างให้)
class Post < ApplicationRecord
end

(< ApplicationRecord แปลว่า "สืบทอดความสามารถจาก ApplicationRecord" · บท 95)
คำตอบสั้น ๆ: ตอนโปรแกรมรัน Rails ไปอ่านชื่อคอลัมน์จากตาราง posts ในฐานข้อมูล แล้วสร้าง method ชื่อเดียวกันให้ · ตารางมีคอลัมน์ title → ได้ method post.title
คุณเห็นผลของเรื่องนี้มาแล้วใน บท 90 กับ บท 95 (Post.column_names) · ชิ้นนี้จะพาดูอีกด้าน: Rails ทำได้ยังไง — จำลองด้วย Ruby ล้วนที่รันเองได้

Go + GORM — เขียน field เอง

type Post struct {
    ID    uint
    Title string
    Body  string
}

เริ่มจาก struct → GORM เอา struct ไปสร้างตาราง

Rails — ไม่เขียน field เลย

class Post < ApplicationRecord
end

เริ่มจาก ตาราง → Rails อ่านตารางแล้วสร้าง method ให้ class

สังเกตว่าทิศทางกลับกัน · Go: struct คือต้นฉบับ · Rails: ตารางในฐานข้อมูลคือต้นฉบับ

🗄 เทียบให้เห็นภาพ — คนดูแลสต็อกที่อ่านป้ายลิ้นชักเอง

model Post คือคนดูแลห้องเก็บของ ที่ไม่มีรายการในมือเลยสักแผ่น
พอร้านเปิด เขาเดินไปดูลิ้นชักบทความ (ตาราง posts) อ่านป้ายช่องทุกช่อง: title · body …
จากนั้นใครถาม "ชื่อเรื่องของแฟ้มนี้คืออะไร" (post.title) เขาก็หยิบให้ได้ทันที · วันไหนช่างมาต่อเติมช่องใหม่ (migration · Day 2) เขาก็รู้เอง โดยไม่ต้องมีใครไปแก้ไฟล์ post.rb

ที่ไม่เหมือนกัน: คนดูแลจริงจดรายการให้คุณดูได้ แต่ไฟล์ post.rb ไม่มีรายการเลย — เปิดไฟล์แล้วไม่รู้ว่ามีช่องอะไร · editor ก็เดาให้ไม่ได้เต็มที่ · อยากรู้ต้องไปเปิดไฟล์ db/schema.rb ที่ Rails เขียนสรุปตารางไว้ให้

ฟังดูเหมือนเวทมนตร์ แต่ Ruby ล้วนก็ทำได้ด้วย method ชื่อ define_method (แปลว่า "สร้าง method ชื่อนี้ให้หน่อย") · มาลองจำลองสิ่งที่ Rails ทำ ด้วย Ruby ล้วน (บทความจำลองด้วย hash เหมือนเดิม): เอารายชื่อคอลัมน์ (สมมติว่าอ่านมาจากตาราง) มาวนสร้าง method ทีละชื่อ 

# magic.rb — จำลองหลักการที่ Rails ใช้ (ของจริงซับซ้อนกว่านี้)
class Post
  def initialize(data)
    @data = data
  end
end
# ตอนนี้ class Post ยังไม่มี method title เลย

column_names = [:title, :body]   # สมมติว่าอ่านมาจากตาราง posts

column_names.each do |name|
  Post.define_method(name) do    # สร้าง method ชื่อตามคอลัมน์
    @data[name]
  end
end

post = Post.new({ title: "สวัสดี Ruby", body: "บทความแรก" })
p post.title
p post.body
p Post.instance_methods(false)
post.author

  • column_names.each do |name| — วนทีละชื่อใน array (บท 92–93) · รอบแรก name = :title รอบสอง = :body
  • Post.define_method(name) do … end — สร้าง method ใหม่ให้ class Post โดยชื่อ method มาจากค่าในตัวแปร · ข้างใน do … end คือเนื้อของ method
  • @data[name] — เนื้อของ method: หยิบค่าจาก hash ของบทความชิ้นที่ถูกเรียก (@data ที่จำไว้ตอน initialize) ด้วยชื่อคอลัมน์
  • Post.instance_methods(false) — ขอรายชื่อ method ที่ class Post มีเอง (false = ไม่รวมที่สืบทอดมา) ได้ [:title, :body]
  • post.author — ไม่มีคอลัมน์ author ในรายชื่อ จึงไม่ถูกสร้าง → พังด้วย NoMethodError (หา method ชื่อนี้ไม่เจอ · บท 91) · แปลว่า class ไม่ได้มี method ทุกชื่อติดมาเอง ต้องมีคนสร้าง

ต่างจาก def ตรงที่ def title ต้องรู้ชื่อตั้งแต่ตอนพิมพ์โค้ด · define_method รับชื่อตอนโปรแกรมรัน — ชื่อจะมาจากไหนก็ได้ รวมถึงจากฐานข้อมูล

ค่าของแต่ละคอลัมน์ในข้อมูลหนึ่งแถว (หนึ่งแถวเรียกว่า record) · method อย่าง post.title / post.title = ที่ Rails สร้างจากคอลัมน์เรียกว่า attribute methods · ถาม senior ได้ว่า "method นี้ไม่มีในไฟล์ model มันมาจากคอลัมน์ในตาราง หรือมาจากที่อื่นครับ"
metaprogramming · define_method
โค้ดที่สร้างโค้ดอื่นตอนโปรแกรมรัน · define_method คือเครื่องมือพื้นฐาน รับชื่อ method เป็นค่า · พิมพ์บอก AI ได้ว่า "explain how Rails generates attribute methods from database columns, at a beginner level"
db/schema.rb
ไฟล์ที่ Rails เขียนสรุปโครงตารางทั้งหมดไว้ (เขียนใหม่ให้เองหลังแก้ตาราง · ไม่ต้องแก้มือ) · ที่แรกที่ต้องเปิดเมื่ออยากรู้ว่า model มี field อะไร

ไฟล์ post.rb มีแค่ class Post < ApplicationRecord กับ end แต่ post.title ใช้ได้ เพราะอะไร?

ตัวเลือกที่ 2 ผิด เพราะไฟล์ post.rb มีแค่สองบรรทัดจริง ๆ ไม่มีอะไรซ่อน · ตัวเลือกที่ 3 ผิด เพราะใน magic.rb class ธรรมดาเรียก post.author แล้วพัง — method ไม่ได้ติดมาเอง · ตัวเลือกที่ 4 ผิด เพราะถ้าประกาศไว้ล่วงหน้า มันจะไม่รู้จัก author ที่เพิ่งเพิ่มทีหลัง

ภารกิจ — ร้านอาหารจำลองในไฟล์เดียว

🛠 เขียน order.rb ใช้ชิ้นที่ 1–3 ของบทนี้ (~10 นาที)

  1. สร้างไฟล์ order.rb ในโฟลเดอร์ไหนก็ได้
  2. เขียน method order(menu, options) ที่ p menu แล้ว p options (แบบเดียวกับ hash1.rb)
  3. เรียกแบบ Rails: order :kaprao, spicy: "มาก", egg: true
  4. เรียกอีกครั้งแบบเขียนเต็ม (วงเล็บ + ปีกกา) ให้ได้ผลเหมือนข้อ 3
  5. เขียน method serve ที่ puts "หยิบจาน" → yield("จานขาว") → puts "ยกไปเสิร์ฟ"
  6. เรียก serve พร้อม block ที่รับของชื่อ plate แล้ว puts "ตักกะเพราลง#{plate}"
  7. รัน ruby order.rb

ควรเห็น สองบรรทัดแรกซ้ำกันสองรอบ แล้วตามด้วยสามบรรทัดของการเสิร์ฟ:

:kaprao
{spicy: "มาก", egg: true}
:kaprao
{spicy: "มาก", egg: true}
หยิบจาน
ตักกะเพราลงจานขาว
ยกไปเสิร์ฟ

ถ้าเจอ error นี้ แปลว่า…

  • wrong number of arguments (given 1, expected 2) (ArgumentError) — เรียก order :kaprao โดยไม่มีตัวเลือกพ่วงท้าย · method ประกาศรับ 2 ชิ้นแต่ได้ 1 · ใส่ spicy: "มาก" ต่อท้าย
  • no block given (yield) (LocalJumpError) — เรียก serve เฉย ๆ โดยไม่แนบ do … end · yield หาลูกมือไม่เจอ

ก่อนกดเฉลย: ในข้อ 6 คำว่า "จานขาว" เดินทางจากบรรทัดไหน ไปโผล่ที่ตัวแปรไหน?

# order.rb — ร้านอาหารจำลอง
def order(menu, options)
  p menu
  p options
end

def serve
  puts "หยิบจาน"
  yield("จานขาว")
  puts "ยกไปเสิร์ฟ"
end

order :kaprao, spicy: "มาก", egg: true
order(:kaprao, { spicy: "มาก", egg: true })

serve do |plate|
  puts "ตักกะเพราลง#{plate}"
end

รันจริงได้ผลตรงกับกล่อง "ควรเห็น" ข้างบนทุกบรรทัด
คำตอบของคำถาม: "จานขาว" ออกจากบรรทัด yield("จานขาว") ใน serve แล้วไปโผล่ที่ตัวแปร plate ใน |plate| — ท่าเดียวกับที่ form_with ยื่น builder ให้กลายเป็น f

✅ ถ้าตอบสี่ข้อนี้ได้ แปลว่าพร้อมเปิดโค้ด Rails แล้ว
1. validates :title, presence: true เขียนเต็มแล้วหน้าตายังไง?
2. ทำไมไม่ควรเติมปีกกาเองตอนเรียก form_with?
3. f ใน do |f| มาจากบรรทัดไหนของ method?
4. model ว่างเปล่า — จะรู้ได้ยังไงว่ามี field อะไร?
ข้อไหนตอบไม่ได้ ก็อปโค้ดกับผลรันของคุณไปถาม AI หรือถามในกลุ่มคอร์สได้เลย บอกด้วยว่า "ติดที่บทเรียน 97 ชิ้นที่เท่าไหร่"
