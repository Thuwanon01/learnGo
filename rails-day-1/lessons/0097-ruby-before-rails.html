1 · hash ตัวสุดท้ายละปีกกาได้ (สไลด์หน้า 34)

กฎนี้คุณเจอแล้วใน บทเรียน 93 หัวข้อ 4 (render json: post, status: :created): ถ้า argument ตัวสุดท้ายเป็น hash จะละปีกกาได้ และการเรียก method ใน Ruby ละวงเล็บได้อยู่แล้ว · บทนี้ไม่สอนซ้ำ แต่จะตรวจสองตัวอย่างของสไลด์หน้า 34 แล้วไปต่อที่เรื่องที่บท 93 ยังไม่ได้แตะ: ใส่ปีกกาเองเมื่อไหร่ถึงพัง

1.1 · กับดักของ Ruby 3+: "keyword argument" กับ "hash" ไม่ใช่ของชิ้นเดียวกันแล้ว

สไลด์เขียนว่า "Ruby เห็นเป็น hash" ซึ่งจริงสำหรับ method ที่ประกาศรับ *args แบบข้างบน · แต่ Ruby มี method อีกแบบที่ประกาศรับ keyword argument (**opts หรือ notice:) และตั้งแต่ Ruby 3.0 ภาษาแยกสองอย่างนี้ออกจากกันเด็ดขาด · ตรงนี้แหละที่การ "ใส่ปีกกาให้ครบตามที่สไลด์บอกว่า Ruby เห็น" จะทำให้ผลเปลี่ยน 

# hash1.rb (ต่อ) — method นี้มีช่อง **opts รอรับ keyword
def validates_kw(*args, **opts)
  p args
  p opts
end

validates_kw :title, presence: true, length: { minimum: 5 }
validates_kw(:title, { presence: true, length: { minimum: 5 } })

สองบรรทัดล่างพิมพ์ต่างกันแค่ปีกกา — คิดว่า args กับ opts ของแต่ละบรรทัดได้อะไร?

$ ruby hash1.rb   (เฉพาะ 4 บรรทัดหลังที่มาจาก validates_kw)

{presence: true, length: {minimum: 5}}
[:title, {presence: true, length: {minimum: 5}}]

ไม่มีปีกกา → Ruby ถือว่าเป็น keyword → ไปลง opts · มีปีกกา → Ruby ถือว่าเป็น hash ธรรมดาหนึ่งก้อน (positional) → ไปลง args แล้ว opts ว่างเปล่า
แปลว่า ปีกกาไม่ใช่แค่ของตกแต่ง — ใน Ruby 3+ มันเปลี่ยนว่าค่าจะไปตกช่องไหน

ที่ไม่เหมือนกัน: ร้านอาหารไม่สนว่าคุณจะพูดตัวเลือกยังไง แต่ Ruby 3+ สน — ครัวบางร้าน (method ที่ประกาศ keyword เช่น form_with) รับเฉพาะตัวเลือกแบบ "พูดลอย ๆ" ถ้าคุณยื่นเป็นกระดาษใส่ซองมา (hash ที่มีปีกกา) ครัวจะบอกว่า "สั่งเกินมาหนึ่งอย่าง" แล้วไม่ทำให้เลย

2 · block ที่รับ object — yield (สไลด์หน้า 35)

บทเรียน 93 หัวข้อ 1 สอนพื้นฐานไปแล้ว — block คือก้อน do … end ที่แนบไปกับการเรียก method · method เรียกมันด้วย yield · ไม่มี block แล้ว yield จะพังด้วย LocalJumpError · เช็คก่อนได้ด้วย block_given?
สิ่งที่สไลด์หน้า 35 เพิ่มมาคือ yield แบบส่ง object ให้ block เอาไปสั่งงานต่อ — ท่าที่ Rails ใช้ทั้ง form · layout · transaction

คิดว่า yield คือ "ถึงตาคุณแล้ว": method ทำงานของตัวเองไปครึ่งหนึ่ง แล้วส่งไม้ให้ block พร้อมยื่น object ให้หนึ่งชิ้น · ชิ้นที่ยื่นให้คือตัวที่โผล่ใน |f| · block ทำเสร็จ ไม้กลับมาที่ method ให้ทำส่วนที่เหลือ
เขียน form_with จิ๋วตามสไลด์หน้า 35 ให้รันได้จริงดูเลย: 

# form.rb
Post = Struct.new(:title, :body)

class FormBuilder
  def initialize(model)
    @model = model
    @fields = []
  end

  def text_field(name)
    value = @model.public_send(name)
    @fields << %(<input name="post[#{name}]" value="#{value}">)
  end

  def to_html
    "<form>\n  " + @fields.join("\n  ") + "\n</form>"
  end
end

def form_with(model:)
  builder = FormBuilder.new(model)
  yield(builder)        # ส่ง builder เข้า block → กลายเป็น |f|
  builder.to_html
end

post = Post.new("Hello Ruby", "...")

html = form_with model: post do |f|
  f.text_field :title
  f.text_field :body
end

puts html
$ ruby form.rb
<form>
  <input name="post[title]" value="Hello Ruby">
  <input name="post[body]" value="...">
</form>

ไล่ทางเดินทีละขั้น: form_with สร้าง builder → yield(builder) กระโดดเข้า block โดย f = builder → block เรียก f.text_field สองครั้ง (เก็บ input ลง @fields) → block จบ กลับมาที่ form_with → builder.to_html ประกอบ HTML คืนออกไป
ของจริงใน Rails ซับซ้อนกว่านี้มาก (มี authenticity_token · สร้าง id ให้ · escape ค่า) แต่รูปร่างของการส่งไม้เหมือนกัน

2.1 · layout · form · transaction — กลไกเดียวกันหมด

สไลด์บอกว่า "layout ก็ใช้ yield · form ก็ใช้ yield · transaction ก็ใช้ yield" — ลองเขียนจิ๋ว ๆ ให้เห็นว่าจริง: 

# layout.rb — layout ห่อหน้าไว้ข้างนอก
def layout
  puts "<html><body>"
  yield
  puts "</body></html>"
end

layout do
  puts "  <h1>หน้า posts</h1>"
end
$ ruby layout.rb
<html><body>
  <h1>หน้า posts</h1>
</body></html>

transaction ก็ห่อแบบเดียวกัน แค่ข้างนอกเป็น BEGIN / COMMIT แทนแท็ก HTML — และมีจังหวะที่ block พังด้วย:

# tx.rb
def transaction
  puts "BEGIN"
  result = yield

3 · method ที่เกิดตอนรัน (สไลด์หน้า 36)

# dm.rb
class TinyRecord
  def self.columns(*names)
    names.each do |name|
      define_method(name) do            # getter: post.title
        @attributes[name]
      end

      define_method("#{name}=") do |value|   # setter: post.title = "Hi"
        @attributes[name] = value
      end
    end
  end

  def initialize
    @attributes = {}
  end
end

class Post < TinyRecord
  columns :title, :published_at   # ในของจริง รายชื่อนี้มาจาก DB
end

5 · @ivar กับ self (สไลด์หน้า 38)

ตัวแปรใน Ruby มีสองแบบที่ต้องแยกให้ออกก่อนเข้า Rails: ตัวแปรธรรมดา (name) อยู่แค่ใน method ที่ประกาศ จบ method ก็หาย · instance variable (@name) ติดอยู่กับ object — method ไหนของ object เดียวกันก็เห็น · และไม่ต้องประกาศล่วงหน้า แค่กำหนดค่าครั้งแรกก็เกิดเลย 

# ivar.rb
class GreetingsController
  def index
    name  = "local"
    @name = "instance"
  end

  def show
    p @name       # ตั้งไว้ใน index — คนละ method แต่ object เดียวกัน
    p @nmae       # สะกดผิด
    p name        # local ของ index ตายไปแล้ว
  end
end

ivar.rb:10:in 'GreetingsController#show': undefined local variable or method 'name' for an instance of GreetingsController (NameError)

สามบรรทัดที่ต้องจำ: @name ข้าม method ได้ · @nmae สะกดผิดได้ nil เงียบ ๆ ไม่ error (ตรงกับที่สไลด์บอก และ บทเรียน 95 หัวข้อ 3 ก็รันให้ดูแล้ว) · name ตัวธรรมดาข้าม method ไม่ได้ → NameError · ของใหม่ของบทนี้คือข้อถัดไป — เรื่องเดียวกันนี้ข้ามจาก controller ไป view ยังไง

5.2 · self — ละได้ตอนอ่าน ห้ามละตอนเขียน

self คือ "object ตัวนี้" (เหมือน this ใน TypeScript · เหมือน receiver p ใน func (p *Post) ของ Go) · สไลด์บอกว่า self.title.downcase กับ title.downcase ใช้แทนกันได้ — จริงตอนอ่าน แต่มีกับดักตอนกำหนดค่าที่สไลด์ไม่ได้พูด: 

# self.rb
class Post
  attr_accessor :title

  def slug
    self.title.downcase    # self = object ตัวนี้
  end

  def slug_short
    title.downcase         # ละ self ได้ตอน "อ่าน"
  end

  def rename_wrong(new_title)
    title = new_title      # ไม่มี self → Ruby สร้างตัวแปร local ชื่อ title
  end

  def rename_right(new_title)
    self.title = new_title # มี self → เรียก method title=
  end
end

post = Post.new
post.title = "Hello Rails"
p post.slug
p post.slug_short
post.rename_wrong("Changed?")
p post.title
post.rename_right("Changed!")
p post.title
$ ruby self.rb
"hello rails"
"hello rails"
"Hello Rails"
"Changed!"

rename_wrong ไม่ error แต่ไม่ได้เปลี่ยนอะไรเลย — กฎจำง่าย: ฝั่งซ้ายของ = ต้องมี self. เสมอ · ตอน Day 2 ที่เขียน callback ใน model จะเจอกับดักนี้แน่

ส่วนเรื่อง "ไม่ต้องประกาศล่วงหน้า" ที่สไลด์เทียบไว้ — TypeScript strict จะไม่ยอม: this.name = "instance" ใน class ที่ไม่ได้ประกาศ name ได้ error TS2339: Property 'name' does not exist on type 'GreetingsController'. (รัน tsc --noEmit --strict จริง) · Ruby ปล่อยผ่าน — สะดวกกว่า แต่ก็ไม่มีใครจับคำสะกดผิดให้

🎒 เทียบให้เห็นภาพ — กระดาษทดกับกระเป๋านักเรียน

ตัวแปรธรรมดา (name) คือกระดาษทด — ใช้ในคาบนั้น หมดคาบก็ทิ้ง · @name คือของในกระเป๋าของนักเรียนคนนั้น — วิชาไหนก็หยิบได้ · ตอน render Rails เปิดกระเป๋าของ controller แล้วยกของทุกชิ้นที่ติดป้าย @ ใส่กระเป๋าใบใหม่ให้ view (view_assigns) · กระดาษทดไม่ได้ถูกยกไปด้วย

ที่ไม่เหมือนกัน: ล้วงกระเป๋าจริงหาของที่ไม่มี คุณรู้ทันทีว่า "ไม่มี" · แต่ล้วงหา @nmae ที่ไม่เคยใส่ Ruby ยื่น nil ให้เฉย ๆ เหมือนเจอของ — หน้าเว็บเลยแสดงช่องว่างโดยไม่มี error ซึ่งหลอกตากว่ากระดาษทดที่หายแล้วพังดัง ๆ (NameError) เสียอีก

🗣 ศัพท์ที่เพิ่งเรียนไป
instance variable (ivar) · @name
ตัวแปรที่ติดกับ object · อ่านตัวที่ไม่เคยตั้งได้ nil ไม่ error · บอก senior ได้ว่า “view ได้ค่าว่างเพราะ controller ไม่ได้ตั้ง ivar ตัวนี้ / สะกดชื่อ ivar ไม่ตรงกัน”
local variable
ตัวแปรไม่มี @ · อยู่ใน method เดียว · ไม่ถูกส่งไป view · ใช้ใน view แล้วได้ NameError
view_assigns
method ใน controller ที่รวบ instance variable เป็น hash ส่งให้ view · เปิดดูได้ใน bin/rails runner · พิมพ์ถาม AI ได้ว่า “how does Rails pass controller instance variables to the view (view_assigns)?”
self · implicit receiver
self = object ปัจจุบัน · เรียก method โดยไม่เขียน self. เรียกว่า implicit receiver · ใช้ได้ตอนอ่าน แต่ setter ต้องมี self. ไม่งั้นกลายเป็นตัวแปร local

action quiz เขียนว่า post = Post.first แล้ว @title = post.title — ใน view ของ action นี้ ข้อไหนตรงกับผลรันจริง?

ตัวเลือกที่ 2 ถูก · รันในแอปจริง: view ที่มี <%= @title %> กับ <%= @post %> ได้ @title = [Hi] และ @post = [] · view ที่มี <%= post.title %> ได้ HTTP 500 undefined local variable or method 'post'
ตัวเลือกที่ 1 ผิด เพราะ "request เดียวกัน" ไม่ได้แปลว่า "object เดียวกัน" — view เป็น object อีกตัว รับได้แค่ ivar · ตัวเลือกที่ 3 ผิด เพราะ ivar ที่ไม่เคยตั้งได้ nil ไม่ใช่ error · ตัวเลือกที่ 4 ผิด เพราะลำดับบรรทัดไม่เกี่ยว ตัวแปร local ไม่ข้ามไป view ไม่ว่าประกาศตอนไหน
จุดที่ต้องจำ: ของที่จะไปถึง view ต้องมี @ · ivar สะกดผิดไม่ error แต่ได้ช่องว่าง

# get.rb
def get(*path_or_actions, as: nil, to: nil, **mapping)
  p path_or_actions
  p as
  p mapping
end

ไม่ต้องใช้ Rails เลย · Ruby ล้วน + Minitest ที่มากับ Ruby (เครื่องตรวจมี minitest 6.0.6)

  1. สร้าง class Record ที่มี def self.columns(*names) — ใช้ define_method สร้าง getter และ setter ให้ทุกชื่อ โดยเก็บค่าใน @attributes (hash ที่ตั้งใน initialize)
  2. เพิ่ม def self.validates(*args) ที่ดึง hash ตัวท้ายออกเอง (ถ้าตัวท้ายเป็น Hash) แล้วจำกฎไว้เป็น array ของ [ชื่อ attribute, options] · มี def self.rules ไว้อ่านกฎ · และ def valid? ที่คืน false ถ้า attribute ที่มี presence: true เป็น nil หรือมีแต่ช่องว่าง
  3. สร้าง class Post < Record ที่มีแค่ columns :title, :body กับ validates :title, presence: true — ห้ามมี def ใน Post
  4. เขียน method transaction (นอก class) ที่ใช้ yield · ไม่มี block คืน "ไม่มีงานให้ทำ" · block จบดีคืน "COMMIT" · block raise คืน "ROLLBACK: ข้อความ error"
  5. เขียนเทสพิสูจน์ ในไฟล์ mini_rails_test.rb (require "minitest/autorun") ให้ครบสี่ข้อ: Post.instance_methods(false).sort เท่ากับ [:body, :body=, :title, :title=] · Post.rules เท่ากับ [[:title, { presence: true }]] · valid? เป็น false เมื่อ title เป็น " " และ true เมื่อเป็น "Hi" · transaction คืนสามแบบตามข้อ 4 · แล้วรัน ruby mini_rails_test.rb ให้ผ่านหมด

ก่อนกดเฉลย ตอบให้ได้: ถ้าเปลี่ยนข้อ 2 เป็น def self.validates(*args, **opts) แล้วใช้ opts แทนการดึงตัวท้ายเอง เทส Post.rules ยังผ่านไหม? แล้วถ้ามีคนเรียก validates(:title, { presence: true }) แบบมีปีกกาล่ะ? (ย้อนดูหัวข้อ 1.1) 

# mini_rails.rb
class Record
  def self.columns(*names)
    names.each do |name|
      define_method(name) { @attributes[name] }
      define_method("#{name}=") { |value| @attributes[name] = value }
    end
  end

  def self.validates(*args)
    options = args.last.is_a?(Hash) ? args.pop : {}
    @rules ||= []
    args.each { |attr| @rules << [attr, options] }
  end

  def self.rules
    @rules || []
  end

  def initialize
    @attributes = {}
  end

  def valid?
    self.class.rules.all? do |attr, options|
      value = public_send(attr)
      !(options[:presence] && (value.nil? || value.strip.empty?))
    end
  end
end

class Post < Record
  columns :title, :body
  validates :title, presence: true
end

def transaction
  return "ไม่มีงานให้ทำ" unless block_given?

  yield
  "COMMIT"
rescue => e
  "ROLLBACK: #{e.message}"
end
# mini_rails_test.rb
require "minitest/autorun"
require_relative "mini_rails"

class MiniRailsTest < Minitest::Test
  def test_columns_create_methods_at_runtime
    assert_equal [:body, :body=, :title, :title=], Post.instance_methods(false).sort
  end

  def test_validates_receives_one_hash
    assert_equal [[:title, { presence: true }]], Post.rules
  end

  def test_valid_checks_presence
    post = Post.new
    post.title = "   "
    refute post.valid?
    post.title = "Hi"
    assert post.valid?
  end

  def test_transaction_uses_yield
    assert_equal "ไม่มีงานให้ทำ", transaction
    assert_equal "COMMIT", transaction { 1 + 1 }
    assert_equal "ROLLBACK: title ว่าง", transaction { raise "title ว่าง" }
  end
end

คำตอบของคำถามก่อนเฉลย: เรียกแบบไม่มีปีกกา (validates :title, presence: true) ค่าจะไปลง opts เป็น {presence: true} เทสยังผ่านได้ถ้าคุณเก็บ opts แทน · แต่ถ้ามีคนเรียกแบบมีปีกกา hash จะไปตกใน args และ opts เป็น {} (ผลเดียวกับ validates_kw ในหัวข้อ 1.1) · ลองรันจริงแล้ว Post.rules ได้ [[:title, {}], [{presence: true}, {}]] — :title เสียกฎ presence ไป และตัว hash เองกลายเป็น "ชื่อ attribute" ปลอม · พอเรียก valid? ก็พังด้วย {presence: true} is not a symbol nor a string (TypeError) · นี่คือเหตุผลที่ validates ตัวจริงของ Rails ใช้ *attributes + extract_options! แบบเดียวกับเฉลยข้างบน ไม่ว่าจะเรียกแบบไหนก็ได้ผลเท่ากัน

สังเกตว่า @rules ใน self.validates เป็น ivar ของตัว class Post (เพราะ self ตอนนั้นคือ class) ไม่ใช่ของ post แต่ละตัว — ถ้าสงสัยตรงนี้ เอาไปถาม AI ต่อได้ว่า “what is a class-level instance variable in Ruby and how is it different from @@class_variable?”
