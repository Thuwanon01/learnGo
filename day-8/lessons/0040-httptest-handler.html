httptest — ทดสอบ handler โดยไม่ต้องเปิดเซิร์ฟเวอร์

~16 นาที · ต้องมี: บทเรียน 16 (table-driven test), บทเรียน 17 (testify), บทเรียน 38 (Gin) · บทเรียน 28 (mockery — ใช้ในหัวข้อ 8)

ตั้งแต่บท 37 เป็นต้นมาคุณเขียน handler ไปหลายตัวแล้ว แต่วิธี "ตรวจว่ามันทำงาน" ยังเป็นการ go run . แล้วเปิดเบราว์เซอร์กด F5 อยู่เลย
บทนี้จะพิสูจน์ว่า คุณไม่ต้องเปิด port ไม่ต้องมี DB ไม่ต้องมี curl ก็ยิง request เข้า router ของตัวเองได้ — เพราะ ServeHTTP เป็นแค่ ฟังก์ชันธรรมดาที่รับ request แล้วเขียนคำตอบลงกล่อง และ httptest ก็คือ "กล่อง" ใบนั้น

📌 บทนี้ไม่มีในสไลด์ Day 8 — ผมเพิ่มเข้ามาเอง
มันเป็นการบ้านที่ค้างมาตั้งแต่ Day 5: วันนั้นเราเรียน table-driven test กับ testify แต่เทสได้แค่ฟังก์ชันคำนวณล้วน ๆ เพราะยังไม่มีใครเขียน HTTP server เป็น
ตอนนี้มี handler แล้ว — หนี้ก้อนนั้นถึงเวลาจ่าย ถ้าข้ามบทนี้ไป บท 41 (Swagger) กับ Day ถัด ๆ ไปจะกลายเป็น "เขียน API ที่ไม่มีใครตรวจ" ทันที

net/http/httptest อยู่ใน standard library ของ Go ไม่ต้อง go get · ที่ต้องโหลดคือ gin กับ testify ซึ่งลงไปแล้วตั้งแต่บท 38 และบท 17

1 · ปัญหาก่อน แล้วค่อยดูเครื่องมือ

ลองนึกว่าจะเทส GET /users/:id ด้วยความรู้ที่มีตอนนี้ ทางที่นึกออกคือ: เปิดเซิร์ฟเวอร์ด้วย r.Run(":8080") แล้วยิง http.Get("http://localhost:8080/users/1")
มันทำงานได้จริง แต่ลองไล่ราคาที่ต้องจ่ายดู:

สิ่งที่ต้องทำปัญหาที่ตามมา
จอง port 8080เครื่อง CI (เครื่องกลางที่รันเทสให้อัตโนมัติทุกครั้งที่ push โค้ด) รันเทสหลายชุดพร้อมกัน → ชนกัน · เครื่องคุณมีอย่างอื่นใช้อยู่ → เทสพังทั้งที่โค้ดถูก
รอให้ server พร้อมก่อนยิงต้อง time.Sleep เดา ๆ ไว้ → เทสช้าลง และกลายเป็น flaky test (เทสที่บางรอบผ่านบางรอบพัง ทั้งที่โค้ดไม่ได้เปลี่ยน)
ปิด server ตอนจบลืมปิด = เทสตัวถัดไปเจอ port ไม่ว่าง
ต่อ DB จริงต้องมี Docker + ข้อมูลตั้งต้น เพียงเพื่อจะเช็คว่า handler ตอบ 404 ถูกไหม

ทั้งหมดนี้เป็นค่าใช้จ่ายของชั้น network ซึ่งเราไม่ได้อยากเทสมันเลย — เราอยากรู้แค่ว่า "ยิง path นี้เข้าไป แล้ว handler ตอบ status/body อะไร"

ทางออกซ่อนอยู่ใน interface ที่คุณเห็นมาตั้งแต่บท 37 แล้วแต่อาจยังไม่ทันสังเกต — http.Handler มี method เดียวเท่านั้น: 

type Handler interface {
    ServeHTTP(ResponseWriter, *Request)
}

อ่านช้า ๆ อีกรอบ: มันคือฟังก์ชันธรรมดาที่รับสองพารามิเตอร์ ตัวหนึ่งคือ "คำถาม" (*http.Request) อีกตัวคือ "สมุดให้เขียนคำตอบ" (http.ResponseWriter)
ในโลกจริง Go เป็นคนสร้างสองตัวนี้จาก TCP socket แล้วเรียก ServeHTTP ให้
แต่ไม่มีกฎข้อไหนบอกว่ามันต้องมาจาก socket — ถ้าเราประกอบสองตัวนี้ขึ้นมาเองแล้วเรียกตรง ๆ handler ก็ทำงานเหมือนเดิมทุกประการ โดยไม่มี network เข้ามาเกี่ยวเลย 

ของจริง
  browser ──TCP──▶ net/http ──สร้าง req + w ให้──▶ router.ServeHTTP(w, req) ──▶ handler

ในเทส  (เราเป็นคนสร้าง req + w เอง แล้วเรียกบรรทัดเดียวกันนั้นตรง ๆ)
  httptest.NewRequest(...) ─▶ req ─┐
                                   ├──▶ router.ServeHTTP(w, req) ──▶ handler
  httptest.NewRecorder()   ─▶ w  ──┘

  (ไม่มี browser · ไม่มี TCP · ไม่มี port — ทุกอย่างอยู่ใน RAM ล้วน ๆ)

net/http/httptest ให้สองอย่างพอดี: NewRequest ปั้น *http.Request ปลอมขึ้นมาจาก method + path และ NewRecorder ให้ ResponseWriter ที่ไม่ส่งอะไรออกไปไหน แต่จดทุกอย่างที่ handler เขียนลงไป แล้วให้เราอ่านย้อนหลังได้

2 · โค้ดที่เราจะเทสกันทั้งบท

นี่คือของที่ต่อยอดตรงจาก บทเรียน 39 — มี c.Param, มี ShouldBindJSON + binding tag ครบ
เซฟเป็น app.go ในโฟลเดอร์เปล่า ๆ ที่ go mod init check ไว้แล้ว (ทุกไฟล์ในบทนี้อยู่โฟลเดอร์เดียวกันหมด · ชื่อ package ต้องตรงกันทุกไฟล์): 

package main

import (
    "net/http"

    "github.com/gin-gonic/gin"
)

type User struct {
    ID   string `json:"id"`
    Name string `json:"name"`
}

type CreateUserReq struct {
    Name  string `json:"name"  binding:"required"`
    Email string `json:"email" binding:"required,email"`
}

var db = map[string]User{
    "1": {ID: "1", Name: "Somchai"},
}

func GetUser(c *gin.Context) {
    id := c.Param("id")
    u, ok := db[id]
    if !ok {
        c.JSON(http.StatusNotFound, gin.H{"error": "user not found"})
        return
    }
    c.Header("X-Course", "go-day8")
    c.JSON(http.StatusOK, u)
}

func CreateUser(c *gin.Context) {
    var req CreateUserReq
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
        return
    }
    c.JSON(http.StatusCreated, gin.H{"name": req.Name, "email": req.Email})
}

// จุดที่สำคัญที่สุดของไฟล์นี้: แยก "สร้าง router" ออกจาก "รัน server"
func NewRouter() *gin.Engine {
    r := gin.New()
    r.GET("/users/:id", GetUser)
    r.POST("/users", CreateUser)
    return r
}

func main() {
    NewRouter().Run(":8080")   // เทสไม่แตะบรรทัดนี้เลย — ดูกล่องข้างล่าง
}
🔑 บรรทัดที่ทำให้เทสได้เลยคือ NewRouter()

ถ้าคุณเขียน r := gin.New() กับ r.Run(":8080") ปนกันอยู่ใน main() — เทสจะเอื้อมไปหยิบ router ไม่ได้เลย เพราะการเรียก main() จากเทสแปลว่าเซิร์ฟเวอร์จะบล็อกค้างอยู่ตรงนั้นตลอดไป
กฎที่ติดตัวไปได้ทุกภาษา: แยก "ประกอบของ" ออกจาก "สั่งให้ทำงาน" เสมอ — main() เหลือแค่บรรทัดเดียวคือ NewRouter().Run(":8080") ส่วนเทสเรียก NewRouter() เฉย ๆ ได้ router มาถือไว้โดยไม่มีอะไรบล็อก
นี่คือหลักเดียวกับ constructor injection ที่ใช้ใน บทเรียน 27

3 · สามบรรทัดที่ต้องจำ

เซฟเป็น basic_test.go ข้าง ๆ app.go — package เดียวกัน จึงเรียก NewRouter() ได้เลยโดยไม่ต้อง import อะไรเพิ่ม:

package main

import (
    "net/http/httptest"
    "testing"

    "github.com/stretchr/testify/assert"
)

func TestGetUser_Basic(t *testing.T) {
    router := NewRouter()

    w := httptest.NewRecorder()                              // 1) กล่องรับคำตอบ
    req := httptest.NewRequest("GET", "/users/1", nil)      // 2) คำถามปลอม
    router.ServeHTTP(w, req)                                // 3) ยิงเข้า router ตรง ๆ

    assert.Equal(t, 200, w.Code)
    assert.JSONEq(t, `{"id":"1","name":"Somchai"}`, w.Body.String())
    assert.Equal(t, "application/json; charset=utf-8", w.Header().Get("Content-Type"))
}

รันจริงแล้วได้แบบนี้ (ผมใส่ t.Logf เพิ่มเพื่อพิมพ์ค่าดิบออกมาให้ดูด้วย):

4 · กับดักตัวแรก: recorder เป็นของใช้ครั้งเดียว

ทายก่อนรัน — โค้ดนี้ใช้ w ตัวเดิมยิงสองครั้ง ครั้งแรก /users/1 (มีจริง) ครั้งที่สอง /users/999 (ไม่มี)

// func TestReuseRecorder(t *testing.T) {  router := NewRouter()
w := httptest.NewRecorder()

router.ServeHTTP(w, httptest.NewRequest("GET", "/users/1", nil))
t.Logf("ครั้งที่ 1: code=%d body=%s", w.Code, w.Body.String())

router.ServeHTTP(w, httptest.NewRequest("GET", "/users/999", nil))
t.Logf("ครั้งที่ 2 (recorder เดิม): code=%d body=%s", w.Code, w.Body.String())

// แล้วยิงเคสเดิมซ้ำอีกรอบ คราวนี้สร้าง recorder ใหม่ ไว้เทียบกัน
w2 := httptest.NewRecorder()
router.ServeHTTP(w2, httptest.NewRequest("GET", "/users/999", nil))
t.Logf("ครั้งที่ 2 (recorder ใหม่): code=%d body=%s", w2.Code, w2.Body.String())

และคำถามแถมมาจากเทสอีกตัวที่สร้าง recorder ขึ้นมาแล้วไม่ยิงอะไรเลย:

// func TestDefaultCode(t *testing.T) {
w := httptest.NewRecorder()
t.Logf("recorder ที่ยังไม่ถูกเขียน: w.Code = %d", w.Code)

บรรทัด "ครั้งที่ 2 (recorder เดิม)" จะพิมพ์ w.Code เป็นเท่าไหร่ และ w.Body หน้าตายังไง?
คำถามแถม: ถ้ายังไม่เคยยิงอะไรเลยสักครั้ง w.Code เท่ากับอะไร

1. w.Code ค้างที่ 200 — เพราะ HTTP เขียน status ได้ครั้งเดียว (บทเรียน 37 เรื่อง WriteHeader เขียนซ้ำไม่ได้) ครั้งแรกชนะ ครั้งที่สองถูกเมิน
2. body ต่อกันเป็นก้อนเดียว — {"id":"1",...}{"error":...} ซึ่งไม่ใช่ JSON ที่ถูกต้องแล้วด้วยซ้ำ

3. คำถามแถมคือข้อที่อันตรายที่สุด: w.Code เริ่มต้นที่ 200 ทันทีที่สร้าง ทั้งที่ยังไม่มีใครเขียนอะไรลงไปเลย
แปลว่าเทสที่ assert แค่ assert.Equal(t, 200, w.Code) อย่างเดียว พิสูจน์ไม่ได้ว่า handler ทำงาน — แม้ handler จะไม่ถูกเรียกเลยเทสก็ยังผ่าน
→ assert body ด้วยเสมอ และ สร้าง recorder ใหม่ทุกเคส

5 · assert.JSONEq ไม่ใช่ของหรู มันคือของจำเป็น

body ที่ handler ตอบมาเป็นสตริง แต่สิ่งที่เราสนใจจริง ๆ คือข้อมูล
ระหว่าง {"id":"1","name":"Somchai"} กับ { "name": "Somchai", "id": "1" } — สำหรับ client สองอันนี้เหมือนกันทุกประการ แต่สำหรับ == มันคนละเรื่อง

❌ assert.Equal

got := w.Body.String()   // = {"id":"1","name":"Somchai"}
expected := `{ "name": "Somchai", "id": "1" }`
assert.Equal(t, expected, got)
    Error:      	Not equal:
                	expected: "{ \"name\": \"Somchai\", \"id\": \"1\" }"
                	actual  : "{\"id\":\"1\",\"name\":\"Somchai\"}"

                	Diff:
                	--- Expected
                	+++ Actual
                	@@ -1 +1 @@
                	-{ "name": "Somchai", "id": "1" }
                	+{"id":"1","name":"Somchai"}
--- FAIL: TestCompareJSON (0.00s)

เทียบสตริงตรงตัว — สลับ key หรือเว้นวรรคก็พังแล้ว

✅ assert.JSONEq

got := w.Body.String()   // ก้อนเดียวกันเป๊ะกับฝั่งซ้าย
expected := `{ "name": "Somchai", "id": "1" }`
assert.JSONEq(t, expected, got)
(ไม่มี error รายงานออกมาเลย = ผ่าน)

แกะทั้งสองฝั่งเป็นโครงสร้างข้อมูลก่อนแล้วค่อยเทียบ — ลำดับ key และช่องว่างไม่มีผล

ทั้งสองบล็อกข้างบนรันกับ body ก้อนเดียวกันคือ {"id":"1","name":"Somchai"} ต่างกันแค่ฟังก์ชันที่ใช้เทียบเท่านั้น
ทำไมเรื่องนี้สำคัญกว่าที่คิด: ลำดับ key ใน JSON ไม่ใช่สิ่งที่คุณควบคุมได้
gin.H คือ map ซึ่ง Go ไม่รับประกันลำดับ วันที่คุณเปลี่ยน handler จากตอบ struct มาเป็นตอบ gin.H (หรือกลับกัน) ลำดับ key ก็เปลี่ยนตาม — เทสที่ใช้ Equal จะพังทั้งแผงทั้งที่ API ตอบข้อมูลเดิมเป๊ะ
สรุปสั้น ๆ: body ที่เป็น JSON ให้ใช้ JSONEq เสมอ · Equal เก็บไว้ใช้กับ w.Code และ header ซึ่งเป็นค่าเดี่ยว ๆ ไม่มีเรื่องลำดับ

6 · table-driven: 200 / 400 / 404 ในลูปเดียว

ตอนนี้ต่อจิ๊กซอว์ได้แล้ว — เอาโครง table-driven จาก บทเรียน 16 มาครอบ: แต่ละแถวคือ "หนึ่ง request หนึ่งคำตอบที่คาดไว้" 

// ในไฟล์ table_test.go — package เดียวกับ app.go
// import เพิ่มจากหัวข้อ 3 อีกสองตัว: "net/http" และ "strings"
router := NewRouter()   // สร้างครั้งเดียว ใช้ได้ทุกเคส (เหตุผลอยู่ในกล่องถัดไป)

tests := []struct {
    name       string
    method     string
    path       string
    body       string
    wantCode   int
    wantJSON   string
    wantSubstr string
}{
    {name: "200 เจอ user", method: http.MethodGet, path: "/users/1",
        wantCode: http.StatusOK, wantJSON: `{"id":"1","name":"Somchai"}`},
    {name: "404 ไม่เจอ user", method: http.MethodGet, path: "/users/999",
        wantCode: http.StatusNotFound, wantJSON: `{"error":"user not found"}`},
    {name: "400 body ไม่ผ่าน validation", method: http.MethodPost, path: "/users",
        body:     `{"name":"","email":"ไม่ใช่อีเมล"}`,
        wantCode: http.StatusBadRequest, wantSubstr: "Field validation"},
}

for _, tc := range tests {
    t.Run(tc.name, func(t *testing.T) {
        var req *http.Request
        if tc.body == "" {
            req = httptest.NewRequest(tc.method, tc.path, nil)
        } else {
            req = httptest.NewRequest(tc.method, tc.path, strings.NewReader(tc.body))
            req.Header.Set("Content-Type", "application/json")
        }
        w := httptest.NewRecorder()          // recorder ใหม่ทุกเคส (หัวข้อ 4)

8 · ต่อยอดจาก mock — เทส handler ที่ต้องใช้ DB โดยไม่มี DB

var ErrNotFound = errors.New("user not found")   // sentinel error ที่ errors.Is เอาไว้เทียบ

type UserService interface {
    GetUser(id string) (User, error)
}

type Handler struct{ svc UserService }

func (h *Handler) GetUser(c *gin.Context) {
    u, err := h.svc.GetUser(c.Param("id"))
    if errors.Is(err, ErrNotFound) {
        c.JSON(http.StatusNotFound, gin.H{"error": "user not found"})
        return
    }
    if err != nil {
        c.JSON(http.StatusInternalServerError, gin.H{"error": "internal error"})
        return
    }
    c.JSON(http.StatusOK, u)
}

สองอย่างที่เปลี่ยนไปจากหัวข้อ 2 — อ่านก่อนไม่งั้นโค้ดข้างล่างจะดูโผล่มาจากไหนไม่รู้

func NewRouter(h *Handler) *gin.Engine { r := gin.New(); r.GET("/users/:id", h.GetUser); return r }

กับดัก 4 — Content-Type ในเทส POST

ผมยิง POST /users ด้วย body เดียวกัน 5 แบบ แล้วดูว่า header มีผลแค่ไหน:

ยิงแบบไหนผลจริง
ไม่ set Content-Type เลย + ShouldBindJSON201 ผ่าน
set application/json + ShouldBindJSON201 ผ่าน
set ผิดเป็น text/plain + ShouldBindJSON201 ผ่าน
ไม่ set + ใช้ c.Bind แทน400 ฟ้องว่า field required ไม่ผ่าน
body เป็น nil400 {"error":"EOF"}

("binder" ในที่นี้คือตัวแปลง body ดิบ ๆ ให้กลายเป็น struct — gin มีหลายตัว เช่น JSON binder, form binder, XML binder)
ShouldBindJSON ไม่ดู header เลย มันบังคับใช้ JSON binder ตรง ๆ เสมอ
แต่ c.Bind / c.ShouldBind เลือก binder จาก Content-Type — ไม่ set ก็ตกไปที่ form binding อ่าน JSON ไม่เจอ แล้วฟ้องว่า Field validation for 'Name' failed on the 'required' tag ซึ่งชี้ไปผิดที่จนหาสาเหตุไม่เจอ (คุณจะนึกว่า body ผิด ทั้งที่ header ต่างหาก)
→ ในเทส set Content-Type ให้ตรงความจริงเสมอ ไม่ใช่เพราะ ShouldBindJSON ต้องการ แต่เพราะเทสควรเลียนแบบ client จริง และวันที่คุณเปลี่ยนไปใช้ ShouldBind เทสจะได้ไม่พังทั้งแผง

💡 httptest.NewRequest กับ http.NewRequest ต่างกันตรงไหน
ที่ต้องรู้ข้อเดียว: httptest.NewRequest คืนค่าตัวเดียว ส่วน http.NewRequest คืน (*http.Request, error) ต้องรับ err ทุกครั้ง — ในเทสที่มี 20 request นั่นคือ 20 บรรทัดที่ไม่ได้ให้อะไร
และเมื่ออาร์กิวเมนต์พัง httptest.NewRequest เลือก panic แทนที่จะคืน error (เช่นใส่ URL "://bad-url" ได้ invalid NewRequest arguments; parse "://bad-url": missing protocol scheme) ซึ่งในเทสถือว่าดีกว่า เพราะพังทันทีตรงจุดที่พิมพ์ผิด
ที่หลายคนเข้าใจผิด: http.NewRequest("GET", "/users/1", nil) ไม่ error และเอาไปยิง router.ServeHTTP ก็ได้ 200 ถูกต้อง — เพราะ ServeHTTP ใช้แค่ req.URL.Path ไม่ได้ต้องการ Host ที่แนะนำ httptest.NewRequest เป็นเรื่องความสั้น ไม่ใช่เพราะอีกตัวใช้ไม่ได้

ทดสอบความเข้าใจ

1. ใช้ w := httptest.NewRecorder() ตัวเดิมยิง /users/1 แล้วยิง /users/999 ต่อ จะเกิดอะไร?

ผลรันจริง: ครั้งที่ 2 (recorder เดิม): code=200 body={"id":"1","name":"Somchai"}{"error":"user not found"}
status เขียนได้ครั้งเดียว (ครั้งแรกชนะ) ส่วน body เป็น buffer ที่ต่อท้ายไปเรื่อย ๆ ผลคือได้สตริงที่ไม่ใช่ JSON ที่ถูกต้องอีกต่อไป
ตัวเลือกที่ 1 ผิดสองชั้น: body ไม่ได้ถูกทับ และ code ก็ไม่ได้เปลี่ยน · ตัวเลือกที่ 3 ผิดเพราะไม่มี panic เลย เทสยัง PASS สบาย ๆ ซึ่งนั่นแหละคือปัญหา · ตัวเลือกที่ 4 ผิด — ไม่มีการรีเซ็ตใด ๆ recorder เป็นของใช้ครั้งเดียว
ทางแก้: w := httptest.NewRecorder() ต้องอยู่ใน t.Run ของทุกเคส

2. ทำไมถึงควรเทียบ body ที่เป็น JSON ด้วย assert.JSONEq แทน assert.Equal?

ผมรันเทียบให้ดูแล้ว: expected := `{ "name": "Somchai", "id": "1" }` กับ body จริง {"id":"1","name":"Somchai"} — JSONEq ผ่าน ส่วน Equal FAIL พร้อม diff ที่ต่างกันแค่ลำดับ key กับช่องว่าง
สำคัญเพราะลำดับ key ไม่ใช่สิ่งที่เราควบคุม (gin.H คือ map) เทสที่ผูกกับลำดับจะพังเองวันที่ refactor ทั้งที่ API ไม่เปลี่ยน
ตัวเลือกที่ 2 ผิด Equal ใช้กับ string ได้ปกติ · ตัวเลือกที่ 3 สลับเรื่องกัน — เรื่อง "หยุดหรือไปต่อ" คือ require กับ assert ไม่ใช่ JSONEq · ตัวเลือกที่ 4 ผิด ทั้งคู่เห็นสตริงชุดเดียวกัน ไม่เกี่ยวกับภาษา

3. เทสยิง path ที่ไม่ได้ลงทะเบียนไว้ แล้ว assert.JSONEq พังแปลก ๆ — เพราะอะไร?

ผลรันจริง: code=404 body="404 page not found" Content-Type="text/plain"
JSONEq ต้องแกะทั้งสองฝั่งเป็น JSON ก่อน พอฝั่ง actual เป็นข้อความเปล่า ๆ จึงพังที่ขั้นตอนแกะ อาการนี้แทบทุกครั้งแปลว่าพิมพ์ path ในเทสผิด ไม่ใช่ handler ผิด
ตัวเลือกที่ 1 ผิด — ผมยิง DELETE ใส่ route ที่มีแค่ GET ก็ยังได้ 404 ไม่ใช่ 405 เพราะ HandleMethodNotAllowed default เป็น false · ตัวเลือกที่ 2 ผิด — r.Run() คือการเปิด port ไม่เกี่ยวกับการลงทะเบียน route · ตัวเลือกที่ 4 ผิด — NewRequest panic เฉพาะตอน method หรือ URL ผิดรูป path ที่ไม่มี route ถือว่าปกติดี

4. เทส handler ที่ต่อกับ mock แล้วลืม svc.On(...) โดย router มี gin.Recovery() ติดอยู่ ผลคือ?

mock ที่ถูกเรียกด้วยอาร์กิวเมนต์ที่ไม่ได้สั่งไว้จะ panic ว่า mock: I don't know what to return because the method call was unexpected แต่ Recovery รับไว้แล้วตอบ code=500 body="" — ผลรันจริงคือ PASS
ป้องกันด้วยการ assert body ด้วยเสมอ (body ว่างจะโป๊ะทันที) และปิดท้ายด้วย svc.AssertExpectations(t) (บทเรียน 28)
ตัวเลือกที่ 1 ผิด — Recovery ไม่ retry อะไรทั้งนั้น มันแค่กัน panic ไม่ให้ล้มทั้งโปรเซส · ตัวเลือกที่ 2 ผิด — ServeHTTP ไม่คืนค่าอะไรเลยตาม signature ของ http.Handler · ตัวเลือกที่ 3 ผิด — mock บันทึกการเรียกตามปกติ ไม่เกี่ยวกับ middleware

🛠️ ภารกิจ — เทส handler ของบท 39 ให้ครบสามเคส

ใช้โค้ดที่คุณเขียนไว้เองใน บทเรียน 39 (ถ้าไม่มีแล้ว ก๊อปโค้ดหัวข้อ 2 ของบทนี้มาใช้ได้เลย) — เป้าหมายไม่ใช่ "เทสผ่าน" แต่คือ เทสที่จะ FAIL เมื่อโค้ดพัง และ FAIL ตรงจุดที่พังจริง

เริ่มจากศูนย์แบบนี้ — โฟลเดอร์เปล่า ๆ หนึ่งอัน แล้วรันสามคำสั่งนี้ในโฟลเดอร์นั้น: 

go mod init check
go get github.com/gin-gonic/gin github.com/stretchr/testify
go mod tidy

จากนั้นสร้าง app.go (โค้ดหัวข้อ 2) กับ app_test.go ไว้ในโฟลเดอร์เดียวกัน ใช้ package ชื่อเดียวกันทั้งสองไฟล์ เทสจึงเรียก NewRouter() ได้โดยไม่ต้อง import
ทุกข้อข้างล่างรันด้วย go test -v -count=1 . จากโฟลเดอร์นี้

  1. แยก NewRouter() ออกจาก main() ให้ได้ก่อน — ถ้ายังทำข้อนี้ไม่ได้ ข้ออื่นทำไม่ได้เลย
    เสร็จแล้ว main() ควรเหลือบรรทัดเดียวคือ NewRouter().Run(":8080")
  2. เทสตัวแรกแบบสามบรรทัด: NewRecorder + NewRequest + ServeHTTP ยิง GET /users/1 แล้ว assert w.Code, w.Body (ด้วย JSONEq) และ Content-Type
    รัน go test -v — ถ้าเจอ [setup failed] ให้ go mod tidy ก่อน (กับดัก 1)
  3. ทำให้ครบสามเคสด้วย table-driven: 200 · 404 · 400 (body ที่ไม่ผ่าน binding)
    เคส 400 ให้ assert แค่ชิ้นส่วนของข้อความ error (เช่น "Field validation") ไม่ใช่ทั้งประโยค — ตอบให้ได้ว่าทำไม
  4. พิสูจน์กับดัก recorder: จงใจใช้ w ตัวเดียวยิงสองเคส แล้ว t.Logf ค่า w.Code กับ w.Body ออกมาดูกับตา แล้วค่อยแก้กลับ
  5. ทำให้เทสพังให้ได้ 1 ครั้ง: แก้ handler ให้ตอบ 200 ตอนไม่เจอ user แล้วยืนยันว่าเคส 404 FAIL จริง · ถ้ายังผ่านอยู่ แปลว่าเทสยังไม่ได้เทสอะไร
  6. ใส่ TestMain + gin.SetMode(gin.TestMode) แล้วเทียบ output ก่อน/หลัง — [GIN-debug] หายไปกี่บรรทัด และ w.Code เปลี่ยนไหม
  7. ต่อยอด mock (บทเรียน 28): เปลี่ยน handler ให้รับ UserService เป็น interface แล้วเทสด้วย mock
    เพิ่มเคสที่ mock คืน error ธรรมดา (ไม่ใช่ ErrNotFound) แล้ว assert 500 — นี่คือเคสที่เทสกับ DB จริงแทบทำไม่ได้
  8. ท้าทาย 1: ลบ svc.On(...) ออกหนึ่งบรรทัด แล้วรันสองแบบ: router ที่มี gin.Recovery() กับที่ไม่มี
    ทายก่อนรันว่าแบบไหน PASS แบบไหน FAIL แล้วอธิบายว่าทำไมแบบที่ PASS ถึงน่ากลัวกว่า
  9. ท้าทาย 2: ยิง DELETE /users/1 ใส่ route ที่ลงทะเบียนไว้แค่ GET
    ได้ status อะไร · body หน้าตายังไง · Content-Type คืออะไร — แล้วตอบว่าถ้าอยากได้ 405 ต้องไปเปิดค่าอะไรของ gin
  10. ท้าทาย 3: เขียนเคสเดียวกันซ้ำด้วย httptest.NewServer + http.Get แล้วเทียบว่าต้องเขียนเพิ่มกี่บรรทัด (อย่าลืม defer srv.Close() และ defer resp.Body.Close()) — ตอบให้ได้ว่าเคสนี้คุ้มจะใช้ตัวไหน

ข้อความจริงที่ validator ตอบกลับมาในเคส 400 คือก้อนนี้:

{"error":"Key: 'CreateUserReq.Name' Error:Field validation for 'Name' failed on the 'required' tag\nKey: 'CreateUserReq.Email' Error:Field validation for 'Email' failed on the 'email' tag"}

สามเหตุผล:
1. มันมีชื่อ struct กับชื่อ field ของ Go ปนอยู่ (CreateUserReq.Name) — วันที่คุณ rename struct เทสจะพังทั้งที่ API เหมือนเดิมเป๊ะ
2. มันเป็นข้อความของ library ภายนอก ที่เราไม่ได้คุมเวอร์ชัน — อัป validator ทีเดียวข้อความอาจเปลี่ยน
3. ลำดับของสอง error ในก้อนเดียวไม่มีใครรับประกันให้
สิ่งที่เป็นสัญญากับ client จริง ๆ มีแค่ status 400 — เทสจึงควรผูกกับ 400 เป็นหลัก แล้วเช็คชิ้นส่วนอย่าง "Field validation" เพียงเพื่อยืนยันว่าพังเพราะ validation จริง ๆ ไม่ใช่พังเพราะ JSON เสีย
