บทเรียน 13 · Day 4 · JSON

JSON และ Struct Tags: ทำไม password ถึงหลุด (หรือหายไปเฉย ๆ)

~16 นาที · ต้องมี: บทเรียน 07 (struct & pointer), บทเรียน 12

JSON คือภาษากลางระหว่างระบบ — REST API, config, message queue, webhook, log ทั้งหมดใช้มัน Go แปลง struct ↔ JSON ให้อัตโนมัติ แต่มีกฎเงียบ ๆ หลายข้อที่ทำให้ข้อมูลหายไปโดยไม่มี error บทนี้เอามาเปิดเผยให้ครบ

1 · สองทิศทาง: Marshal และ Unmarshal

       JSON                                Go struct
  {                                    type Product struct {
    "id": 101,      ──Unmarshal()──▶       ID    int
    "name": "…",                           Name  string
    "price": 2590                          Price int
  }                 ◀──Marshal()───    }
ฟังก์ชันทิศทางจำง่าย ๆ
json.Marshal(v)Go → JSON ([]byte)ส่งออก เช่นตอบ API
json.Unmarshal(data, &v)JSON → Goรับเข้า เช่นอ่าน request body

2 · Struct Tag คือคำสั่งที่แปะไว้ท้าย field

type User struct {
    UserID   int    `json:"userId"`
    FullName string `json:"fullName"`
    Email    string `json:"email"`
}

// json.Marshal ได้:
{
  "userId": 101,
  "fullName": "Alice Smith",
  "email": "alice@email.com"
}

ถ้าไม่ใส่ tag เลย Go ใช้ชื่อ field ตรง ๆ:

// ผลรันจริงเมื่อไม่มี tag:
{"UserID":101,"FullName":"Alice Smith","Email":"alice@email.com"}

ซึ่งผิดธรรมเนียมของฝั่ง JSON — Google JSON Style Guide บอกว่า property name ควรเป็น camelCase ส่วน Go บังคับให้ field ที่จะ export ต้องขึ้นต้นตัวใหญ่ (PascalCase) struct tag คือสะพานเชื่อมสองธรรมเนียมนี้

tag ใส่ได้หลาย package พร้อมกัน คั่นด้วยเว้นวรรค — แต่ละ library อ่านเฉพาะส่วนของตัวเอง: 

UserID int `json:"userId" xml:"userId" validate:"required"`

3 · กับดักที่ 1: field ตัวเล็กหายไปเงียบ ๆ

type User struct {
    ID       int    `json:"id"`
    Name     string `json:"name"`
    password string `json:"password"`   // ← p ตัวเล็ก
}

user := User{ID: 101, Name: "Alice", password: "secret123"}
data, _ := json.Marshal(user)
fmt.Println(string(data))

พิมพ์อะไรออกมา?

{"id":101,"name":"Alice"} — ผมรันทดสอบแล้ว

password ขึ้นต้นด้วยตัวเล็ก = unexported field → package encoding/json ซึ่งอยู่คนละ package มองไม่เห็นเลย ต่อให้แปะ tag ไว้ก็ไม่มีผล
ไม่มี error ไม่มี warning — เงียบสนิท

ด้านกลับ: อันตรายกว่ามาก

type LoginRequest struct {
    Email    string `json:"email"`
    password string `json:"password"`   // ← ตัวเล็ก
}

// รับ JSON: {"email":"peter@email.com","password":"123456"}
// หลัง json.Unmarshal:
req.Email      // "peter@email.com"
req.password   // ""  ← ว่างเปล่า! รหัสผ่านที่ผู้ใช้ส่งมาหายไปหมด
ทำไมถึงอันตราย

Unmarshal ไม่คืน error — มันมองว่า field นั้นไม่มี แล้วปล่อยเป็น zero value ผลคือ login ทุกคนด้วยรหัสว่าง ถ้าโค้ดตรวจรหัสเขียนไว้หลวม ๆ ประตูเปิดพอดี
กฎ: field ที่ต้องเข้า/ออก JSON ต้องขึ้นต้นด้วยตัวใหญ่เสมอ

4 · omitempty — และเหตุผลที่มันหลอกคน

type User struct {
    ID       int    `json:"id"`
    Nickname string `json:"nickname,omitempty"`
}

user := User{ID: 101, Nickname: ""}
// ได้: {"id":101}     ← nickname หายไปเพราะว่าง

ดูสมเหตุสมผล จนกระทั่งเจอกรณีนี้:

type Item struct {
    Price  int  `json:"price,omitempty"`
    Active bool `json:"active,omitempty"`
}

item := Item{Price: 0, Active: false}
data, _ := json.Marshal(item)
fmt.Println(string(data))

ได้ JSON หน้าตายังไง?

{} — ว่างเปล่าทั้งก้อน ผมรันทดสอบแล้ว

omitempty ตัดทิ้งเมื่อค่าเป็น zero value — ซึ่งรวมถึง 0, false, "", nil, slice/map ที่ว่าง
แต่ "สินค้าราคา 0 บาท" กับ "ปิดใช้งาน" เป็นข้อมูลที่มีความหมาย! ฝั่งรับจะแยกไม่ออกว่า "ไม่ได้ส่งมา" กับ "ส่งมาว่าเป็น 0"

ทางแก้: ใช้ pointer

type Item struct {
    Price  *int  `json:"price,omitempty"`
    Active *bool `json:"active,omitempty"`
}

// ไม่ต้องการส่งจริง ๆ — ปล่อยเป็น nil:
Item{}
// ได้: {}

// ต้องการส่งค่า zero จริง ๆ:
var price int
var active bool
Item{Price: &price, Active: &active}
// ได้: {"price":0,"active":false}   ← ส่งออกไปครบ

pointer แยกได้ 3 สถานะ ในขณะที่ค่าธรรมดาแยกได้แค่ 2: nil = "ไม่ได้ส่ง" · &0 = "ส่งมาว่า 0" · &5 = "ส่งมาว่า 5" — สำคัญมากตอนทำ PATCH API ที่ต้องแยก "ไม่แก้ field นี้" กับ "แก้เป็นศูนย์"

5 · json:"-" — ห้าม field นี้เข้าออก JSON

type User struct {
    ID           int    `json:"id"`
    Email        string `json:"email"`
    PasswordHash string `json:"-"`     // ← ไม่ออกไปแน่นอน
}

// ผลรันจริง: {"id":101,"email":"alice@example.com"}
แนวทางที่ปลอดภัยกว่า — แยก struct

json:"-" ใช้ได้ แต่วันไหนมีคนเผลอลบ tag ออก ข้อมูลลับหลุดทันทีโดยไม่มีอะไรเตือน ทีมส่วนใหญ่จึงแยกเป็นคนละ struct ไปเลย:

ใช้ในระบบ — ไม่มี json tag เลย

type UserModel struct {
    ID           int
    Email        string
    PasswordHash string
}

ส่งออกไปข้างนอกเท่านั้น

type UserResponse struct {
    ID    int    `json:"id"`
    Email string `json:"email"`
}

6 · กฎของ json.Unmarshal() ที่ต้องรู้ครบ

6.1 ลืม & = ไม่ทำงาน แต่ได้ error บอก

json.Unmarshal(data, &product)   // ✅
json.Unmarshal(data, product)    // ❌

// error จริงที่ได้:
// json: Unmarshal(non-pointer main.ProductPrice)

เหตุผลย้อนไปที่ บทเรียน 07: Go ส่งค่าแบบ pass by value 100% — ถ้าไม่ส่ง pointer ไป Unmarshal จะแก้ได้แค่ copy อันนี้ยังดีที่มี error เตือน ไม่เหมือนกับดักอื่นในบทนี้

6.2 field ที่ JSON ไม่ได้ส่งมา → zero value

// JSON: {"name":"Alice"}
type User struct {
    Name   string `json:"name"`
    Age    int    `json:"age"`
    Active bool   `json:"active"`
}

// ผลรันจริง: {Name:Alice Age:0 Active:false}  — ไม่มี error

6.3 field ส่วนเกินใน JSON → ถูกทิ้งเงียบ ๆ

// JSON: {"email":"alice@example.com","admin":true}
type LoginRequest struct {
    Email string `json:"email"`
}

// ผลรันจริง: err = <nil>  ← ผ่านฉลุย "admin" หายไปเฉย ๆ

6.4 type ไม่ตรง → อันนี้มี error

// Struct ต้องการ int แต่ JSON ส่ง string มา
type Product struct {
    Price int `json:"price"`
}
// JSON: {"price":"2590"}

// error จริง:
// json: cannot unmarshal string into Go struct field
//       ProductPrice.price of type int

7 · เรื่องที่สไลด์ไม่ได้บอก: การจับคู่ key ไม่ สนตัวพิมพ์

type StrictUser struct {
    ID   string `json:"id"`
    Name string `json:"name"`
}

// JSON ส่งมาเป็นตัวพิมพ์ใหญ่:
json.Unmarshal([]byte(`{"ID":"P001","NAME":"Keyboard"}`), &u)

ได้ค่าเข้า struct ไหม หรือได้ค่าว่าง?

ได้ครบ — {ID:P001 Name:Keyboard} ผมรันทดสอบแล้ว

encoding/json จับคู่แบบ case-insensitive เมื่อหา exact match ไม่เจอ ข้อดีคือทนต่อ API ที่ตั้งชื่อไม่สม่ำเสมอ ข้อเสียคือมันปิดบังบั๊ก — โค้ดทำงานได้ทั้งที่ contract ระหว่างสองระบบไม่ตรงกันจริง ๆ วันหนึ่งอีกฝั่งเปลี่ยนไปใช้ชื่ออื่น คุณจะเพิ่งรู้ว่าไม่เคยตกลงกันชัดเจน

8 · json.NewDecoder() — เมื่อ Unmarshal ไม่พอ

os.ReadFile + Unmarshaljson.NewDecoder
อ่านข้อมูลโหลดทั้งไฟล์เข้า RAM ก่อนอ่านทีละส่วนแบบ stream
ไฟล์ 2 GBกิน RAM 2 GBกิน RAM คงที่
รับจาก networkต้องรออ่านให้ครบก่อนเริ่มแกะได้เลย
กัน field แปลกปลอม❌ ไม่มีทางเลือก✅ DisallowUnknownFields()
file, err := os.Open("product.json")
if err != nil {
    return err
}
defer file.Close()          // ← บทเรียน 08

var product Product
decoder := json.NewDecoder(file)

if err := decoder.Decode(&product); err != nil {
    return err
}

ปิดช่องโหว่ 6.3 ด้วย DisallowUnknownFields()

type User struct {
    ID   string `json:"id"`
    Name string `json:"name"`
}

raw := `{"name":"admin","isAdmin":true}`

decoder := json.NewDecoder(strings.NewReader(raw))
decoder.DisallowUnknownFields()      // ← เปิดโหมดเข้มงวด

if err := decoder.Decode(&user); err != nil {
    fmt.Println("error", err)
    return
}
// ผลรันจริง: error json: unknown field "isAdmin"
ควรเปิดเมื่อไหร่

เปิดเสมอสำหรับ config file และ request body ที่รับจากภายนอก — ผู้ใช้พิมพ์ "tiemout" แทน "timeout" ใน config ถ้าไม่เปิดโหมดนี้ ระบบจะใช้ค่า default เงียบ ๆ แล้วคุณจะหาสาเหตุไม่เจอ ส่วนตอนรับ response จาก API ภายนอก ไม่ควรเปิด เพราะเขาอาจเพิ่ม field ใหม่เมื่อไหร่ก็ได้ แล้วระบบคุณจะพังทันที

9 · ทดสอบความจำ

1. field ชื่อ password (ตัวเล็ก) ที่มี json:"password" จะเป็นยังไง?

field ตัวเล็ก = unexported → encoding/json ซึ่งอยู่คนละ package เข้าถึงไม่ได้ ไม่มี error ไม่มี warning ขา Marshal ก็หาย ขา Unmarshal ก็ได้ค่าว่าง — เคยเป็นสาเหตุของช่องโหว่ login มาแล้วจริง

2. Price int + omitempty เมื่อค่าเป็น 0 จะได้ JSON แบบไหน?

omitempty ตัดทิ้งทุกอย่างที่เป็น zero value — 0, false, "", nil ทั้งที่บางครั้งค่าเหล่านี้มีความหมาย ทางแก้: เปลี่ยนเป็น *int ซึ่งแยก "ไม่ส่ง" (nil) ออกจาก "ส่งค่า 0" ได้

3. JSON มี field เกินกว่าที่ struct ประกาศไว้ — Unmarshal ทำยังไง?

เป็นค่าเริ่มต้นของ encoding/json — ออกแบบมาให้ทนต่อ API ที่เพิ่ม field ใหม่ ถ้าต้องการเข้มงวด ต้องใช้ json.NewDecoder(...) แล้วเรียก DisallowUnknownFields() ซึ่งจะได้ json: unknown field "isAdmin"

4. ทำไมถึงควรใช้ json.NewDecoder แทน ReadFile+Unmarshal?

เหตุผลหลักคือ stream — อ่านทีละส่วน ไม่กิน RAM ตามขนาดไฟล์ เหมาะกับ HTTP request body และไฟล์ใหญ่ ของแถมคือได้ DisallowUnknownFields() มาด้วย
(Decode ยังต้องส่ง & เหมือนเดิมนะ)

10 · ลงมือทำ

ภารกิจ: ค้นหาโปรไฟล์ผู้เล่นและแปลงเป็น JSON (workshop จากสไลด์)

  1. สร้าง type Player struct ที่มี ID, UserName, NickName, Password
  2. เขียน findPlayer(id int) (Player, error) — ไม่พบให้คืน ErrPlayerNotFound (sentinel จาก บทเรียน 12)
  3. ถ้าพบ ให้แปลงเป็น JSON โดยมีเงื่อนไข:
    • key ต้องเป็น camelCase (playerId, userName)
    • Password ห้ามหลุดออกไปใน JSON
    • NickName ถ้าไม่มีค่า ไม่ต้องแสดง
  4. ผลลัพธ์ที่ต้องได้: 
    findPlayer(101) → {"playerId":101,"userName":"go_master"}
findPlayer(999) → error: player not found
  5. ตรวจงานตัวเอง: ทำข้อ "Password ห้ามหลุด" ด้วย json:"-" ไปแล้วใช่ไหม — ลองทำอีกวิธี ด้วยการแยก PlayerResponse ออกมา แล้วตอบตัวเองว่าแบบไหนที่เพื่อนร่วมทีมเผลอทำพังยากกว่า
  6. ท้าทาย 1: ทำให้ findPlayer(101) ที่มี nickname กับไม่มี nickname ให้ JSON ต่างกันจริง — พิสูจน์ว่า omitempty ทำงาน
  7. ท้าทาย 2: เขียนขากลับ — รับ JSON {"playerId":101,"userName":"go_master","isAdmin":true} แล้ว Unmarshal กลับเป็น Player
    • ใช้ json.Unmarshal ธรรมดา → เกิดอะไรกับ isAdmin?
    • เปลี่ยนไปใช้ json.NewDecoder + DisallowUnknownFields() → ต่างกันยังไง?
  8. ท้าทาย 3: ลอง Unmarshal {"PLAYERID":999} (ตัวพิมพ์ใหญ่หมด) เข้า Player — เข้าไหม? ถ้าเข้า อธิบายว่าทำไม (ย้อนดูหัวข้อ 7)

อ่านต่อจากต้นทาง

แหล่งหลักที่แนะนำ: JSON and Go — บทความทางการที่อธิบาย ทั้ง Marshal/Unmarshal/Decoder และเคสที่ไม่รู้โครงสร้างล่วงหน้า (map[string]any) ประมาณ 15 นาที
ตอนเขียนโค้ดจริงให้เปิด pkg.go.dev — json.Marshal ไว้ข้าง ๆ เพราะกฎการแปลงทุกข้อ (รวม omitempty และ -) อยู่ในหน้านั้นครบ

💬 ติดตรงไหนถามได้เลย — ถ้าเจอ JSON ที่โครงสร้าง ไม่แน่นอน (บางครั้งเป็น object บางครั้งเป็น array) บอกมาได้ มีวิธีจัดการที่ยังไม่ได้สอนในบทนี้ (json.RawMessage และ custom UnmarshalJSON)
