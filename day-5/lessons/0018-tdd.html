บทเรียน 18 · Day 5 · Test Practice

TDD: Red, Green, Refactor

~15 นาที · ต้องมี: บทเรียน 17 · บทสุดท้ายของ Day 5

TDD คือการเขียนเทสก่อนเขียนโค้ด ฟังดูกลับหัวกลับหาง แต่ผลที่ได้ไม่ใช่แค่ "มีเทส" — มันคือการบังคับให้คุณตัดสินใจว่า ฟังก์ชันนี้ควรหน้าตายังไงก่อนจะลงมือเขียน และในยุคที่ AI generate โค้ดให้ได้ทั้งไฟล์ในสิบวินาที เทสกลายเป็นสิ่งเดียวที่ยืนยันได้ว่าโค้ดนั้นตรงกับที่ธุรกิจต้องการจริง

1 · วงจร Red → Green → Refactor

       ┌──────────────────────────────────────────┐
       │                                          ▼
   [Red]  ─────────▶  [Green]  ─────────▶  [Refactor]
  เขียนเทสให้พัง      แก้ให้ผ่าน           ทำให้สวย
   (ไฟแดง)          (ไฟเขียว)        (โดยเทสยังเขียว)
ขั้นทำอะไรกฎเหล็ก
🔴 Redเขียนเทสที่อธิบายพฤติกรรมที่ต้องการ แล้วรันให้เห็นว่าพังห้ามเขียน production code ก่อนเห็นไฟแดง
🟢 Greenเขียนโค้ดน้อยที่สุดที่ทำให้ผ่านห้ามเขียนเกินความจำเป็น — สวยทีหลังได้
🔵 Refactorจัดโค้ดให้อ่านง่าย ลดซ้ำซ้อนเทสต้องเขียวตลอดเวลา ไม่แก้เทส

2 · Red มีสองแบบ — และมีแบบเดียวที่ใช่

ผมทดลองให้ดูแล้วด้วย Division(a, b float64) — เริ่มจากเขียนเทสก่อน โดยที่ยังไม่มีฟังก์ชันเลย 

// division_test.go — เขียนอันนี้ก่อน
func TestDivision(t *testing.T) {
    got, err := Division(10, 2)
    if err != nil {
        t.Fatalf("ไม่ควรมี error: %v", err)
    }
    if got != 5 {
        t.Errorf("Division(10,2) = %v; want 5", got)
    }
}

🚫 Red แบบที่ยังไม่ใช่

$ go test ./...
# tdd [tdd.test]
./division_test.go:6:14: undefined: Division
FAIL	tdd [build failed]

นี่คือ build error ไม่ใช่ test failure — แปลว่ายังไม่ได้ทดสอบอะไรเลย เทสของคุณยังไม่เคยได้รันด้วยซ้ำ

✅ Red ที่ต้องการ

// เขียนโครงเปล่า ๆ ก่อน
func Division(a, b float64) (float64, error) {
    return 0, nil
}
$ go test ./...
--- FAIL: TestDivision (0.00s)
    division_test.go:11: Division(10,2) = 0; want 5
FAIL

เทสรันแล้วและพังด้วยเหตุผลที่ถูกต้อง — นี่คือหลักฐานว่าเทสของคุณทำงานจริง

ทำไมต้องเห็นไฟแดงก่อน

เพื่อพิสูจน์ว่าเทสจับได้จริง — เทสที่ไม่เคยแดงเลย อาจเป็นเทสที่ผ่านตลอดไม่ว่าโค้ดจะเป็นยังไง (ลืม assert, assert ผิดตัวแปร, เงื่อนไขกลับด้าน)
เขียนโค้ดก่อนแล้วค่อยเขียนเทส คุณจะไม่มีวันรู้ว่าเทสนั้นมีค่าจริงไหม

3 · Green — เขียนน้อยที่สุด

func Division(a, b float64) (float64, error) {
    return a / b, nil          // พอแล้วสำหรับเทสที่มีตอนนี้
}
$ go test ./...
ok  	tdd	0.464s      ← 🟢

"แต่มันยังไม่กันหารด้วยศูนย์นี่" — ถูกต้อง และนั่นคือเคสถัดไปที่ต้องเขียนเทสก่อน ไม่ใช่สิ่งที่จะแอบใส่ตอนนี้
TDD บังคับให้ทุกบรรทัดของ production code มีเทสที่เรียกร้องมันอยู่ — ถ้าเขียนดักศูนย์ตอนนี้เลย บรรทัดนั้นจะไม่มีเทสไหนพิสูจน์ว่ามันทำงานถูก

รอบที่ 2 — Red อีกครั้ง

// เพิ่มเคสในตาราง (บทเรียน 16)
{"หารด้วยศูนย์", 10, 0, 0, ErrDivideByZero},
$ go test ./...
--- FAIL: TestDivision/หารด้วยศูนย์
    division_test.go:18: err = <nil>; want divide by zero   ← 🔴

Green อีกครั้ง

var ErrDivideByZero = errors.New("divide by zero")

func Division(a, b float64) (float64, error) {
    if b == 0 {
        return 0, ErrDivideByZero
    }
    return a / b, nil
}
$ go test ./...
ok  	tdd	0.464s      ← 🟢 ทั้งสองเคสผ่าน

4 · Refactor — ขั้นที่คนข้ามบ่อยที่สุด

ตอนนี้เทสเขียวแล้ว = คุณมีตาข่ายนิรภัย แก้โครงสร้างโค้ดได้อย่างมั่นใจ เพราะถ้าทำพัง เทสจะบอกทันที

  • ตั้งชื่อตัวแปรใหม่ให้สื่อความหมาย
  • แยกฟังก์ชันที่ยาวเกินไป
  • ยุบ if ซ้อนเป็น guard clause (บทเรียน 04)
  • เปลี่ยน float64 เป็น custom type ให้สื่อความหมาย (บทเรียน 09)
กฎเดียวของขั้น Refactor

ห้ามเปลี่ยนพฤติกรรม และห้ามแก้เทสไปพร้อมกัน — ถ้าคุณแก้ทั้งโค้ดและเทสในรอบเดียว คุณจะไม่รู้ว่าเทสยังจับบั๊กได้อยู่ไหม
อยากเปลี่ยนพฤติกรรม = กลับไปขั้น Red เขียนเทสใหม่ก่อน

5 · TDD ได้อะไรมากกว่า "มีเทส"

สิ่งที่ได้ทำไม
ออกแบบ API ก่อนเขียน เทสคือผู้ใช้คนแรกของฟังก์ชันคุณ — ถ้าเขียนเทสแล้วรู้สึกอึดอัด แปลว่า signature ออกแบบไม่ดี รู้ตั้งแต่ยังไม่ลงทุนเขียน implementation
โค้ดเทสได้โดยธรรมชาติ คุณจะต้องใช้ DI (บทเรียน 17) เพราะไม่งั้นเขียนเทสไม่ได้ตั้งแต่แรก
ไม่เขียนเกินที่ต้องการ ทุกบรรทัดมีเทสที่เรียกร้องมัน — ไม่มีโค้ดที่ "เผื่อไว้" แล้วไม่มีใครใช้
เทสที่พิสูจน์แล้วว่าจับได้ ทุกเทสเคยแดงมาก่อน → รู้แน่ว่ามันไม่ใช่เทสหลอก
รู้ว่า "เสร็จ" เมื่อไหร่ เทสเขียวครบ = เสร็จ · ไม่ต้องเดา ไม่ต้องเถียงกัน

6 · Test with AI workflow

ทุกวันนี้ AI generate โค้ดได้ทั้งไฟล์ในไม่กี่วินาที แต่โค้ดที่ได้อาจไม่ตรงกับสิ่งที่ธุรกิจต้องการ — AI เดาจากบริบทที่คุณให้ ถ้าบริบทกำกวม มันก็เดาไปทางที่ดูสมเหตุสมผลที่สุด ซึ่งอาจไม่ใช่สิ่งที่คุณหมายถึง 

ปัญหา: AI เก่งเรื่อง "เขียนโค้ด" แต่ไม่รู้ "ธุรกิจต้องการอะไร"

  คุณ ──"เขียนฟังก์ชันคำนวณส่วนลด"──▶ AI ──▶ โค้ดที่ดูดี
                                              │
                                              ▼
                                   แล้วยังไงถึงจะรู้ว่าถูก?

ทางแก้: ให้เทสเป็นตัวกำหนดข้อตกลง แล้วปล่อย AI เขียน implementation

  คุณ ──▶ เขียนเทส (สเปกที่รันได้) ──▶ AI เขียนโค้ด ──▶ go test
                     ▲                                          │
                     └──────────── แดง = ยังไม่ตรง ◀────────────┘

ทำไมเทสเหมาะกับงานนี้เป็นพิเศษ

  • เทสคือสเปกที่รันได้ — ต่างจากคำอธิบายภาษาคน ตรงที่ไม่มีทางตีความผิด และตรวจสอบอัตโนมัติได้
  • AI ตรวจงานตัวเองได้ — บอกให้รัน go test แล้วแก้จนเขียว โดยไม่ต้องรอคุณ review ทุกรอบ
  • คุณยังคุมความหมาย — คุณเป็นคนตัดสินใจว่า "ส่วนลด 100% แล้วราคาควรเป็น 0 หรือควร error" ซึ่ง AI เดาเองไม่ได้
อย่าให้ AI เขียนเทสจากโค้ดที่มันเพิ่งเขียนเอง

ถ้าโค้ดผิด เทสที่เขียนตามโค้ดก็จะยืนยันความผิดนั้น ได้เทสเขียวสวยงามที่พิสูจน์ว่าบั๊กทำงานถูกต้องตามที่บั๊กเป็น
ลำดับที่ถูก: คุณกำหนดพฤติกรรม → เทสก่อน → โค้ดทีหลัง
ถ้าจะให้ AI ช่วยคิดเคส ให้มันเสนอรายการเคสมาก่อน (รวมถึงเคสขอบและเคสที่ควรพัง) แล้วคุณเลือกเอง — ต่างจากให้มันเขียนเทสจากโค้ดสำเร็จรูป

รูปแบบที่ใช้ได้จริง

1. คุณ:   เขียน table-driven test ที่ระบุพฤติกรรมทุกเคส (รวมเคสขอบ)
2. คุณ:   รันให้เห็นแดง — พิสูจน์ว่าเทสจับได้จริง
3. AI:    เขียน implementation ให้ผ่านเทสทั้งหมด
4. AI:    รัน go test เอง แก้เอง จนเขียว
5. คุณ:   อ่านโค้ดที่ได้ — ตรวจว่ามันไม่ได้ "โกง" เทส
6. คุณ:   เพิ่มเคสที่นึกออกเพิ่ม → กลับไปข้อ 2
// เทสที่คุณเขียน — มีเคสเดียว
func TestCalculateDiscount(t *testing.T) {
    got, err := CalculateDiscount(100, 10)
    require.NoError(t, err)
    assert.Equal(t, 90, got)
}

// implementation ที่ได้กลับมา
func CalculateDiscount(price, percent int) (int, error) {
    if price == 100 && percent == 10 {
        return 90, nil
    }
    return 0, nil
}

go test จะขึ้นเขียวหรือแดง — และคุณควรรู้สึกยังไงกับผลนั้น?

เขียว — เทสผ่านหมดทุกข้อ

โค้ดนี้ไม่ได้คำนวณส่วนลดเลย มันแค่จำคำตอบของเคสที่คุณเทสไว้ แต่เทสของคุณยืนยันไม่ได้ว่ามันผิด เพราะคุณถามคำถามเดียว

นี่คือสิ่งที่ AI ทำได้จริง ถ้าคุณสั่งแค่ "ทำให้เทสผ่าน" — และมันไม่ได้เจตนาโกง มันแค่ทำตามที่คุณขอเป๊ะ ๆ
ทางแก้ไม่ใช่การเลิกใช้ AI แต่คือการเขียนตารางเทสให้ครบ จนการโกงยากกว่าการเขียนสูตรจริง — เพิ่มเคส (100, 0), (250, 20), (100, 100) แล้วโค้ดข้างบนจะแดงทันที
นี่คือเหตุผลที่บทเรียน 16 ย้ำเรื่องเคสขอบตั้งแต่ก่อนจะมีเรื่อง AI

ข้อ 5 ในลิสต์ข้างบนคือข้อที่ห้ามข้าม — เทสเขียวบอกแค่ว่า "ผ่านคำถามที่คุณถาม" ไม่ได้บอกว่า "โค้ดถูก" · คุณภาพของเทสคือเพดานของความมั่นใจ

7 · ทดสอบความจำ

1. ลำดับของวงจร TDD คืออะไร?

Red → Green → Refactor · หัวใจอยู่ที่ Red มาก่อน — ทำให้คุณออกแบบ API จากมุมของผู้ใช้ ก่อนจะติดกับ implementation ที่เขียนไปแล้ว และพิสูจน์ว่าเทสจับได้จริง

2. undefined: Division / FAIL [build failed] ถือเป็น Red ที่ใช้ได้ไหม?

build failed แปลว่าคอมไพล์ไม่ผ่าน — ยังไม่มีเทสตัวไหนได้รันสักตัว จึงพิสูจน์อะไรไม่ได้ Red ที่ต้องการคือเขียนโครงเปล่า ๆ ให้คอมไพล์ผ่าน แล้วเห็น --- FAIL: TestDivision ... = 0; want 5 ซึ่งพิสูจน์ว่าเทสทำงานและจับความผิดได้จริง

3. ขั้น Green บอกให้ "เขียนน้อยที่สุด" — ทำไม?

ถ้าเขียนดักเคสที่ยังไม่มีเทส บรรทัดนั้นจะไม่มีอะไรพิสูจน์ว่าถูก — และคุณจะไม่รู้ว่ามันทำงานจริงจนกว่าจะไป production
เคสถัดไป = เขียนเทสก่อน แล้วค่อยเพิ่มโค้ด ไม่ใช่แอบใส่ล่วงหน้า

4. ให้ AI เขียนเทสจากโค้ดที่มันเพิ่งเขียนเอง — ปัญหาคืออะไร?

เทสที่เขียนตามโค้ดจะบรรยายสิ่งที่โค้ดทำ ไม่ใช่สิ่งที่โค้ดควรทำ → ได้เทสเขียวสวยงามที่พิสูจน์ว่า บั๊กทำงานถูกต้องตามที่บั๊กเป็น
ลำดับที่ถูก: คนกำหนดพฤติกรรม → เทสก่อน → AI เขียนโค้ดให้ผ่าน

8 · ลงมือทำ

ภารกิจ: เขียน Division ด้วย TDD แบบเคร่งครัด (workshop จากสไลด์)

กติกา: ห้ามพิมพ์ production code ก่อนเห็นไฟแดงเด็ดขาด ทำทีละรอบ อย่าข้าม

  1. รอบ 1 — Red: เขียนเฉพาะ division_test.go ที่เทส Division(10, 2) == 5 → รัน → ได้ build failed ใช่ไหม? นั่นยังไม่ใช่ Red
  2. รอบ 1 — Red จริง: เพิ่ม func Division(a, b float64) (float64, error) { return 0, nil } → รัน → ต้องได้ = 0; want 5
  3. รอบ 1 — Green: เขียน return a / b, nil → เขียว
  4. รอบ 2 — Red: เพิ่มเคส Division(10, 0) ที่คาดว่าได้ ErrDivideByZero → ต้องแดง
  5. รอบ 2 — Green: เพิ่มการดักศูนย์ → เขียว
  6. รอบ 3 — Red: คิดเคสเพิ่มเอง อย่างน้อย 3 เคส — แนะนำ: หารลงตัวไม่ลงตัว, ตัวเลขติดลบ, 0 / 5
    ระวัง: ผลลัพธ์เป็น float64 → ใช้ assert.InDelta ไม่ใช่ Equal (บทเรียน 17)
  7. Refactor: แปลงเทสทั้งหมดเป็น table-driven (บทเรียน 16) โดยที่เทสต้องเขียวตลอด — รัน go test หลังแก้ทุกครั้ง
  8. ท้าทาย 1 — พิสูจน์ว่าเทสไม่ใช่เทสหลอก: จงใจทำให้ Division ผิด (เช่นเปลี่ยนเป็น a * b) → เทสแดงกี่เคส? ถ้าแดงไม่หมดแปลว่ายังขาดเคส
  9. ท้าทาย 2 — ลอง AI workflow จริง:
    1. เขียนเทสอย่างเดียวสำหรับฟังก์ชันใหม่ เช่น ParseDuration(s string) (time.Duration, error) ที่รับ "1h30m", "45s", "abc"
    2. รันให้เห็นแดง
    3. ส่งเทสให้ AI แล้วบอกว่า "เขียน implementation ให้ผ่านเทสนี้ รัน go test เองจนเขียว ห้ามแก้ไฟล์เทส"
    4. อ่านโค้ดที่ได้ — มันโกงเทสหรือเปล่า? มี if s == "1h30m" ไหม?
    5. ถ้าโกง → เพิ่มเคสจนโกงไม่ได้ แล้วทำซ้ำ
