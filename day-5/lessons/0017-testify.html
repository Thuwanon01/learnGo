Testify: assert, require, mock, suite

~18 นาที · ต้องมี: บทเรียน 16, บทเรียน 10 (interface & DI)

testing เปล่า ๆ ทำงานได้ แต่คุณต้องเขียน if เองทุกครั้ง และเขียนข้อความ error เองทุกครั้ง Testify ยุบสามบรรทัดเหลือหนึ่ง พร้อม diff ที่อ่านรู้เรื่อง — และมี mock กับ suite แถมมาด้วย ซึ่งเป็นของที่ standard library ไม่มีให้

1 · ติดตั้ง

go get github.com/stretchr/testify

# แล้วก็
go mod tidy

ต้อง go mod tidy ด้วย — testify พึ่งพา go-spew, go-difflib, yaml.v3 ถ้าไม่ tidy จะเจอ missing go.sum entry for module providing package … (ผมเจอมาแล้วตอนทดสอบ)
เวอร์ชันที่ทดสอบในบทนี้: testify v1.11.1

2 · assert vs require — คู่แฝดของ Error/Fatal

testing เปล่า ๆ

result, err := CalculateDiscount(100, 10)

if err != nil {
    t.Errorf("did not expect error, got %v", err)
}
if result != 90 {
    t.Errorf("CalculateDiscount(100, 10) = %v; want 90",
        result)
}

Testify

result, err := CalculateDiscount(100, 10)

require.NoError(t, err)
assert.Equal(t, 90, result)
assert.Xrequire.X
พฤติกรรมเมื่อไม่ผ่านฟ้องแล้วไปต่อฟ้องแล้วหยุด
เทียบเท่ากับt.Errorft.Fatalf
ใช้เมื่ออยากเห็นทุกจุดที่ผิดในรอบเดียวบรรทัดถัดไปจะพังตามแน่ ๆ

ผมรันทดสอบยืนยันแล้ว:

=== RUN   TestAssertVsRequire_assert
        Error: Not equal: expected: 1  actual: 2
    testify_test.go:33: assert -> บรรทัดนี้ยังรัน    ← มา
--- FAIL: TestAssertVsRequire_assert

=== RUN   TestAssertVsRequire_require
        Error: Not equal: expected: 1  actual: 2
--- FAIL: TestAssertVsRequire_require              ← ไม่มี log ตามมา

สำนวนที่ใช้จริง: require สำหรับ เงื่อนไขก่อนหน้า (ได้ค่ามาแล้วใช่ไหม, ไม่มี error ใช่ไหม) · assert สำหรับ ตัวผลลัพธ์ ที่อยากเห็นครบทุกจุด
require.NoError(t, err) ตามด้วย assert.Equal(...) หลายบรรทัด — คือรูปแบบที่เจอบ่อยที่สุด

3 · ⚠️ กับดักใหญ่: assert.Equal เข้มเรื่อง type

// CalculateDiscount คืน (int, error)
result, err := CalculateDiscount(100, 10)

require.NoError(t, err)
assert.Equal(t, 90.0, result)     // สังเกต .0

เทสนี้ผ่านไหม? (result ได้ค่า 90 ตามที่คาด)

ไม่ผ่าน — ผมรันทดสอบแล้ว ได้ข้อความนี้:

Error: Not equal:
       expected: float64(90)
       actual  : int(90)

assert.Equal ใช้ reflect.DeepEqual เป็นฐาน ซึ่งเทียบทั้ง type และค่า — 90.0 คือ float64 ส่วน result คือ int → คนละ type → ไม่เท่ากัน
ตรงนี้ตรงกับกฎที่เจอมาตั้งแต่ บทเรียน 09: type ต่างกันคือคนละอย่าง ต่อให้ค่าเท่ากัน
ทางแก้: เขียน assert.Equal(t, 90, result)

สไลด์ Day 5 หน้า "Testify" เขียน assert.Equal(t, 90.0, result) ไว้เป็นตัวอย่างของโค้ดที่สะอาดกว่า — แต่โค้ดนั้นเทสไม่ผ่านจริง ๆ ถ้าลอกไปใช้แล้วงงว่าทำไมแดงทั้งที่ logic ถูก นี่คือคำตอบ

ญาติของกับดักนี้: float

a, b := 0.1, 0.2
assert.Equal(t, 0.3, a+b)      // ✗ ไม่ผ่าน!

ผลรันจริง:

a+b = 0.30000000000000004441
0.3 = 0.29999999999999998890

Error: Not equal:
       expected: 0.3
       actual  : 0.30000000000000004
assert.InDelta(t, 0.3, a+b, 0.0001)   // ✓ ผ่าน — เทียบแบบมีค่าคลาดเคลื่อน

เรื่องแปลกที่เจอตอนทดสอบ: ถ้าเขียน assert.Equal(t, 0.3, 0.1+0.2) ตรง ๆ (ไม่ผ่านตัวแปร) มันผ่าน — เพราะ 0.1 + 0.2 เป็น untyped constant ที่ compiler คำนวณให้ตั้งแต่ตอน build ด้วยความละเอียดไม่จำกัด ได้ 0.3 เป๊ะ
ต้องผ่านตัวแปรถึงจะเป็นการคำนวณ float64 ตอน runtime และเห็นปัญหา — เป็นเรื่องเดียวกับ int(3.9) ใน บทเรียน 02
กฎ: float ห้ามใช้ Equal ใช้ InDelta

4 · Diff ที่อ่านรู้เรื่อง — เหตุผลหลักที่คนใช้ Testify

got  := UserProfile{ID: 1, Name: "Alice", Email: "alice@test.com", Age: 30}
want := UserProfile{ID: 1, Name: "Alice", Email: "alice@test.com", Age: 25}

assert.Equal(t, want, got)

ผลรันจริง — มันชี้ field ที่ต่างให้เลย:

Error: Not equal:
       expected: UserProfile{ID:1, Name:"Alice", Email:"alice@test.com", Age:25, ...}
       actual  : UserProfile{ID:1, Name:"Alice", Email:"alice@test.com", Age:30, ...}

       Diff:
       --- Expected
       +++ Actual
       @@ -4,3 +4,3 @@
         Email: (string) (len=14) "alice@test.com",
       - Age: (int) 25,
       + Age: (int) 30,
         Roles: ([]string) <nil>

ถ้าเขียนเองด้วย t.Errorf("got %v; want %v", got, want) คุณจะได้ struct สองก้อนยาว ๆ แล้วต้องนั่งไล่สายตาเองว่า field ไหนต่าง — ยิ่ง struct ใหญ่ยิ่งทรมาน

5 · แคตตาล็อก assert ที่ใช้บ่อย

ทั้งหมดนี้ผมรันผ่านจริงบน testify v1.11.1:

// --- ค่าปกติ ---
assert.Equal(t, expected, actual)               // เท่ากัน (type ต้องตรงด้วย!)
assert.NotEqual(t, unexpected, actual)          // ไม่เท่ากัน
assert.ElementsMatch(t, []int{3,1,2}, list)     // slice เท่ากัน "ไม่สนลำดับ"

// --- สถานะ ---
assert.Nil(t, err)
assert.NotNil(t, obj)
assert.Empty(t, slice)                          // ว่าง (nil ก็นับ)
assert.Len(t, slice, 3)                        // ยาว 3

// --- บูลีน ---
assert.True(t, ok)
assert.False(t, failed)

// --- error (อย่าเทียบข้อความสตริง!) ---
require.Error(t, err)                            // มี error
assert.NoError(t, err)                           // ไม่มี error
assert.ErrorIs(t, err, ErrNotFound)              // ใช่ sentinel ตัวนี้ (แม่นกว่า)
assert.ErrorAs(t, err, &appErr)                  // เป็นชนิดนี้ + ดึงตัวจริง
assert.ErrorContains(t, err, "not found")      // ข้อความมีคำนี้ (หลวม)

// --- float (ห้ามใช้ Equal!) ---
assert.InDelta(t, 3.14, result, 0.001)

// --- slice/map/string ---
assert.Contains(t, "hello world", "world")       // substring
assert.Contains(t, []int{1,2,3}, 2)              // element
assert.Contains(t, map[string]int{"a":1}, "a")     // key

// --- เปรียบเทียบ ---
assert.Greater(t, a, b)                          // a > b
assert.Less(t, a, b)                             // a < b

// --- แสดงข้อมูลเพิ่มเมื่อพัง (arg ท้ายสุด) ---
assert.Equal(t, 10, x, "input ตอนนั้นคือ %d", input)

ErrorIs ดีกว่า ErrorContains — ตัวแรกเดินตาม error chain (บทเรียน 12) ส่วนตัวหลังเทียบข้อความ ซึ่งพังทันทีที่มีคนแก้ข้อความ · ใช้ ErrorContains เฉพาะกับ error จาก library ภายนอกที่ไม่มี sentinel ให้จับ

6 · Dependency Injection — เตรียมโค้ดให้ mock ได้

ก่อนจะ mock ได้ โค้ดต้องออกแบบมาให้รับ dependency เข้ามา ไม่ใช่สร้างเองข้างใน — ตรงกับ บทเรียน 10 เป๊ะ ๆ 

type Result struct { A, B, Sum int }

type Store interface {
    Save(r Result) error
}

type Calculator struct {
    store Store         // ← dependency: Calculator "พึ่ง" Store
}

func NewCalculator(s Store) *Calculator {   // ← constructor รับเข้ามา
    return &Calculator{store: s}
}

func (c *Calculator) Add(a, b int) (int, error) {
    sum := a + b
    if err := c.store.Save(Result{A: a, B: b, Sum: sum}); err != nil {
        return 0, err
    }
    return sum, nil
}
ทำไมออกแบบแบบนี้ถึงเทสได้

ถ้า Add เขียนว่า fileStore := NewFileStore("/data"); fileStore.Save(...) ข้างในเลย → เทสจะต้องเขียนไฟล์จริงทุกครั้ง
พอรับ Store เป็น interface เข้ามา → ยัดอะไรก็ได้ที่มี Save() เข้าไป รวมถึงของปลอม

7 · mock — ของปลอมที่ตอบอะไรก็ได้ และจำได้ว่าถูกเรียกกี่ครั้ง

type MockStore struct {
    mock.Mock            // ← embed เข้ามา (บทเรียน 11)
}

func (m *MockStore) Save(r Result) error {
    args := m.Called(r)      // บันทึกว่าถูกเรียกด้วย r
    return args.Error(0)     // คืนค่าตัวที่ 0 ที่ตั้งไว้
}
func TestCalculator_Add_Success(t *testing.T) {
    mockStore := new(MockStore)

    // ตั้งโปรแกรมล่วงหน้า: ถ้าถูกเรียก Save ด้วยค่านี้ ให้คืน nil
    mockStore.On("Save", Result{A: 2, B: 3, Sum: 5}).Return(nil)

    calc := NewCalculator(mockStore)
    result, err := calc.Add(2, 3)

    require.NoError(t, err)
    assert.Equal(t, 5, result)

    mockStore.AssertExpectations(t)   // ← ตรวจว่าทุกอันที่ On ไว้ ถูกเรียกจริง
}

ทดสอบเส้นทางที่พัง — จุดที่ mock มีค่าที่สุด

func TestCalculator_Add_StoreFails(t *testing.T) {
    mockStore := new(MockStore)

    // สั่งให้ของปลอม "พัง" ตามที่เราต้องการ
    mockStore.On("Save", mock.AnythingOfType("main.Result")).
        Return(errors.New("disk full"))

    calc := NewCalculator(mockStore)
    _, err := calc.Add(2, 3)

    require.Error(t, err)
    assert.ErrorContains(t, err, "disk full")
    mockStore.AssertExpectations(t)
}

ลองคิดดู: จะทำให้ disk เต็มจริง ๆ เพื่อเทสยังไง? ทำไม่ได้ — นี่คือเหตุผลที่ mock มีอยู่ เส้นทางที่พังคือเส้นทางที่เทสยากที่สุดและมีบั๊กเยอะที่สุด

ตัวช่วยจับคู่ argument และตรวจการเรียก

// จับคู่แบบหลวม ๆ
mockStore.On("Save", mock.AnythingOfType("main.Result")).Return(nil)
mockStore.On("Transfer", 1, mock.Anything, mock.Anything).Return(nil)

// ตรวจหลังเรียกเสร็จ
mockStore.AssertExpectations(t)                    // ทุกอันที่ On ไว้ ถูกเรียกครบ
mockStore.AssertCalled(t, "Save", mock.Anything)   // ถูกเรียกจริง
mockStore.AssertNotCalled(t, "Update")             // ไม่ถูกเรียก
mockStore.AssertNumberOfCalls(t, "Save", 2)        // ถูกเรียก 2 ครั้งพอดี

// จำกัดจำนวนครั้ง
mockStore.On("Save", mock.Anything).Return(nil).Once()
mockStore.On("Save", mock.Anything).Return(nil).Twice()
mockStore.On("Save", mock.Anything).Return(nil).Times(3)
อย่า mock ทุกอย่าง

mock เยอะเกินไป = เทสกลายเป็นการยืนยันว่าโค้ดเรียกฟังก์ชันตามลำดับที่คุณเขียนไว้ ไม่ใช่ยืนยันว่ามันทำงานถูก · พอ refactor ทีเทสแดงหมดทั้งที่พฤติกรรมไม่เปลี่ยน
mock เฉพาะสิ่งที่อยู่นอกการควบคุมของคุณ — database, HTTP API, ระบบไฟล์, นาฬิกา, ตัวสุ่ม

8 · suite — จัดกลุ่มเทสที่ใช้ setup ร่วมกัน

type UserServiceSuite struct {
    suite.Suite                    // ← embed
    store *MockUserStore           // สิ่งที่ใช้ร่วมในทุกเทส
    svc   *UserService
}

func (s *UserServiceSuite) SetupTest() {
    s.store = new(MockUserStore)     // สร้างใหม่ทุกเทส → ไม่ปนกัน
    s.svc = NewUserService(s.store)
}

func (s *UserServiceSuite) TestFindUser_ReturnsUser() {
    s.store.On("GetByID", 1).Return(&User{Name: "Bob"}, nil)

    user, err := s.svc.FindUser(1)
    s.Require().NoError(err)              // ⚠️ s.Require() ไม่ใช่ require.X(t, …)
    s.Assert().Equal("Bob", user.Name)     // ⚠️ ไม่ต้องส่ง t
}

func (s *UserServiceSuite) TestFindUser_PropagatesError() {
    s.store.On("GetByID", 2).Return(nil, errors.New("db down"))

    _, err := s.svc.FindUser(2)
    s.Assert().Error(err)
}

// ต้องมีตัวนี้ ไม่งั้น go test ไม่เห็น suite
func TestUserServiceSuite(t *testing.T) {
    suite.Run(t, new(UserServiceSuite))
}

Hook ทั้งหมด

Methodรันเมื่อ
SetupSuite()ครั้งเดียว ก่อนทุกเทสใน suite
SetupTest()ก่อนทุกเทส
BeforeTest(suiteName, testName string)ก่อนแต่ละเทส — รู้ชื่อเทสด้วย
AfterTest(suiteName, testName string)หลังแต่ละเทส
TearDownTest()หลังทุกเทส
TearDownSuite()ครั้งเดียว หลังทุกเทสจบ

ผลรันจริงของลำดับ hook:

=== RUN   TestUserServiceSuite
    SetupSuite: ครั้งเดียวก่อนทุกเทส
=== RUN   TestUserServiceSuite/TestFindUser_PropagatesError
    SetupTest: ก่อนทุกเทส
    TearDownTest: หลังทุกเทส
=== RUN   TestUserServiceSuite/TestFindUser_ReturnsUser
    SetupTest: ก่อนทุกเทส
    TearDownTest: หลังทุกเทส
    TearDownSuite: ครั้งเดียวหลังทุกเทสจบ
--- PASS: TestUserServiceSuite

สังเกตอะไรแปลก ๆ ไหม — PropagatesError รันก่อน ReturnsUser ทั้งที่ในโค้ดผมเขียน ReturnsUser ไว้ก่อน
suite เรียงเทสตามตัวอักษร ไม่ใช่ตามลำดับในไฟล์ → ห้ามเขียนเทสที่ต้องพึ่งพาลำดับเด็ดขาด ทุกเทสต้องตั้งต้นเองได้ครบใน SetupTest

9 · ทดสอบความจำ

1. assert.Equal(t, 90.0, result) เมื่อ result เป็น int ค่า 90?

คอมไพล์ผ่าน (พารามิเตอร์เป็น any) แต่ตอนรัน reflect.DeepEqual เทียบทั้ง type และค่า → expected: float64(90) / actual: int(90)
สไลด์เขียนตัวอย่างนี้ไว้ — แต่มันเทสไม่ผ่านจริง ๆ แก้เป็น assert.Equal(t, 90, result)

2. require.NoError ต่างจาก assert.NoError ยังไง?

require = t.Fatal · assert = t.Error สำนวนที่ใช้จริง: require สำหรับเงื่อนไขก่อนหน้า (ถ้าไม่ผ่านบรรทัดถัดไปจะ panic) แล้วตามด้วย assert หลายบรรทัด สำหรับตรวจผลลัพธ์

3. ต้องออกแบบโค้ดยังไงถึงจะเอา mock ยัดเข้าไปได้?

ถ้าฟังก์ชันสร้าง dependency เองข้างใน (NewFileStore("/data")) ก็ไม่มีทางแทนที่ได้ · รับเป็น interface ผ่าน NewCalculator(s Store) → ยัดของจริงตอน production ยัด mock ตอนเทส นี่คือ DI จากบทเรียน 10 มาใช้งานจริง

4. testify suite รันเทสในลำดับไหน?

ผมรันแล้วเห็นชัด: TestFindUser_PropagatesError รันก่อน TestFindUser_ReturnsUser ทั้งที่ในไฟล์เขียนสลับกัน → ห้ามเขียนเทสที่พึ่งพาลำดับ ทุกเทสต้องตั้งต้นเองได้ครบใน SetupTest

10 · ลงมือทำ

ภารกิจ: เขียนเทสที่ไม่ต้องต่อ database

  1. go get github.com/stretchr/testify && go mod tidy
  2. เอาเทสจาก บทเรียน 16 (Grade) มาแปลง if ทุกอันเป็น assert/require — บรรทัดลดลงกี่บรรทัด?
  3. ลอง assert.Equal(t, "A", grade) โดยที่ grade เป็น type Grade string (custom type จาก บทเรียน 09) — ผ่านไหม? ทำไม?
    สปอยล์ผลรันจริง: expected: string("A") vs actual: Grade("A") → ไม่ผ่าน เพราะ custom type คือคนละ type · แก้ด้วย assert.Equal(t, Grade("A"), grade)
  4. สร้างโครง DI: type UserRepo interface { GetByID(id int) (*User, error) } และ UserService ที่รับมันเข้ามาทาง constructor
  5. เขียน MockUserRepo ที่ embed mock.Mock
  6. เขียนสองเทส:
    • happy path — mock คืน user → service คืน user
    • sad path — mock คืน errors.New("db down") → service ต้องส่ง error ต่อขึ้นไป
    ปิดท้ายด้วย AssertExpectations(t) ทั้งสองเทส
  7. แปลงทั้งสองเทสเป็น suite ที่มี SetupTest สร้าง mock ใหม่ทุกครั้ง — อย่าลืม s.Assert() ไม่ใช่ assert.X(t, ...)
  8. เพิ่ม SetupSuite/TearDownSuite ที่ t.Log แล้วรัน -v เพื่อดูลำดับ hook และลำดับเทสด้วยตาตัวเอง
  9. ท้าทาย 1: ลบ mockStore.On("Save", ...) ออก แต่ยังเรียก calc.Add(2,3) อยู่ → ได้อะไร?
    สปอยล์ผลรันจริง — mock panic พร้อมข้อความที่บอกวิธีแก้ให้เลย: 
    panic:
  assert: mock: I don't know what to return because
  the method call was unexpected.
    Either do Mock.On("Save").Return(...) first,
    or remove the Save() call.
  This method was unexpected:
    Save(day5check.Result)
    0: day5check.Result{A:2, B:3, Sum:5}
    สังเกตว่ามันบอกค่า argument ที่ได้รับจริงมาให้ด้วย — เอาไปวางใน .On() ได้ตรง ๆ
  10. ท้าทาย 2: เขียนเทสที่มี assert.InDelta เทียบ float แล้วลองเปลี่ยนเป็น assert.Equal — พิสูจน์ปัญหา floating point ด้วยตัวเอง

อ่านต่อจากต้นทาง

แหล่งหลักที่แนะนำ: pkg.go.dev — testify/assert มีรายการฟังก์ชันครบทุกตัว กด Ctrl+F หาสิ่งที่ต้องการเร็วกว่าเดา · ส่วน testify/mock มีตัวอย่างครบตั้งแต่ On ถึง Run
ข้อควรรู้: testify เป็น library ของบุคคลที่สาม ไม่ใช่ของทีม Go — บางทีมเลือกไม่ใช้เลยเพราะอยากให้เทสพึ่งพา standard library อย่างเดียว รู้ทั้งสองแบบไว้ดีที่สุด บทเรียน 15–16 คือแบบไม่ใช้ บทนี้คือแบบใช้

💬 ติดตรงไหนถามได้เลย — เรื่องที่คุ้มถามที่สุดคือ "ควร mock อะไร ไม่ควร mock อะไร" ในโปรเจกต์ของคุณ เพราะเป็นเรื่องที่ทำเกินแล้วเจ็บทีหลัง ถ้ามีโครงโปรเจกต์อยู่แล้วส่งมาได้
