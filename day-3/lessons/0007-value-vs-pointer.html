บทเรียน 07 · Pointer & Struct

คุณกำลังแก้ของจริง หรือแก้ copy?

~15 นาที · ต้องมี: บทเรียน 06

บทที่แล้วคือ "แก้แล้วเปลี่ยนทั้งที่ไม่อยากให้เปลี่ยน" บทนี้คืออาการตรงข้าม — เขียนโค้ดแก้ค่า รันแล้วค่าไม่เปลี่ยน เหมือนโค้ดโดนเมิน รากของทั้งสองอาการคือกฎข้อเดียวกัน และมันเป็นกฎที่ Go ไม่มีข้อยกเว้นเลย

1 · กฎข้อเดียวที่ต้องจำ

กฎ

ใน Go ทุกอย่างเป็น pass by value 100% ไม่มีข้อยกเว้น
การใช้ pointer ไม่ได้ทำให้เป็น "pass by reference" — มันแค่เปลี่ยนจาก ก็อปของ เป็น ก็อปที่อยู่ของของ 

func tryValue(n int)  { n = 999 }
func tryPtr(n *int)   { *n = 999 }

x := 42
tryValue(x)   // x ยังเป็น 42  — แก้ copy ของเลข
tryPtr(&x)    // x เป็น 999    — แก้ผ่านที่อยู่
tryValue(x) tryPtr(&x) ┌──────────┐ ก็อปเลข ┌──────────┐ ก็อป "ที่อยู่" │ x = 42 │──────────▶┌────────┐ │ x = 42 │◀─────────┐ └──────────┘ │ n = 42 │ └──────────┘ │ ไม่รู้จักกัน └────────┘ ▲ ┌─────┴────┐ แก้ตัวนี้ └────────────│ n=0x1040 │ ไม่มีผล *n เข้าถึงได้ └──────────┘

ตัว tryPtr ก็ได้ copy ของ pointer มาเหมือนกัน — แต่ copy ของ ที่อยู่บ้าน ก็ยังชี้ไปบ้านหลังเดิม เลยเข้าไปแก้ของในบ้านได้

2 · จุดที่กฎนี้เล่นงานคุณ #1: for range

type User struct{ Name string; Age int }

users := []User{{"Alice", 30}, {"Bob", 25}}

for _, u := range users {
    u.Name = "CHANGED"
}

fmt.Println(users[0].Name)

พิมพ์ออกมาว่าอะไร?

Alice — ไม่เปลี่ยนเลย

ทุกรอบของ for range ตัวแปร u ได้ copy ของ struct มา แก้ u ก็คือแก้ copy พอจบรอบ copy ก็ถูกทิ้ง

แก้ให้ถูกต้องใช้ index แทน:

for i := range users {
    users[i].Name = "CHANGED"   // ✓ เข้าถึงช่องจริงใน slice
}
ทำไม slice ของ int ถึงแก้ได้ แต่ struct แก้ไม่ได้?

มันเหมือนกันทุกประการครับ — for _, v := range nums { v = 0 } ก็ไม่เปลี่ยนอะไรเหมือนกัน สิ่งที่ทำให้คนสับสนคือ users[i].Name = "x" (ผ่าน index) กับ u.Name = "x" (ผ่านตัวแปรวนลูป) หน้าตาคล้ายกันมาก แต่ตัวแรกแตะของจริง ตัวหลังแตะ copy

3 · จุดที่กฎนี้เล่นงานคุณ #2: struct ใน map

type Product struct{ Name string; Qty int }

inv := map[string]Product{
    "SKU-1": {Name: "Mouse", Qty: 50},
}

inv["SKU-1"].Qty = 49

โค้ดนี้ผลลัพธ์เป็นยังไง?

compile ไม่ผ่าน — cannot assign to struct field inv["SKU-1"].Qty in map

inv["SKU-1"] คืน copy ไม่ใช่ที่อยู่จริง Go เลย ห้ามตั้งแต่ตอน compile ไม่ให้คุณเขียนโค้ดที่ดูเหมือนแก้ได้แต่ไม่มีผล

เหตุผลลึก: map ย้ายข้อมูลไปมาได้ตอน ขยายตัว (rehash) ที่อยู่ของ value จึงไม่คงที่ → เอา address มาไม่ได้ → เรียกว่า non-addressable

ทางออก 3 แบบ เรียงตามที่ใช้จริงบ่อยที่สุด:

// 1) เก็บเป็น pointer ตั้งแต่แรก — ใช้บ่อยสุดในงานจริง
inv := map[string]*Product{"SKU-1": {Name: "Mouse", Qty: 50}}
inv["SKU-1"].Qty = 49          // ✓ ได้

// 2) อ่านออกมา แก้ แล้วยัดกลับทั้งก้อน
p := inv["SKU-1"]
p.Qty = 49
inv["SKU-1"] = p               // ✓ ได้

// 3) ถ้า field เป็น slice จะแก้ได้เลย เพราะ index ของ slice addressable เสมอ
inv["SKU-1"].Tags[0] = "new"   // ✓ ได้ (แต่ .Qty ยังไม่ได้)
คู่กับ comma-ok เสมอ

เวลาอ่าน map จำไว้ว่า key ที่ไม่มีจะคืน zero value ไม่ใช่ error ดังนั้น inv["ghost"].Qty ได้ 0 ซึ่งแยกไม่ออกจาก "มีของแต่หมดสต็อก" → ใช้ p, ok := inv[k] ทุกครั้งที่สองกรณีนี้ มีความหมายต่างกัน

4 · จุดที่กฎนี้เล่นงานคุณ #3: receiver ของ method

Method ก็คือฟังก์ชันที่มี parameter พิเศษข้างหน้าชื่อ receiver

func (a *Account) Deposit(amount float64) { … } └────┬────┘ └───┬───┘ └──────┬──────┘ receiver method name signature receiver type = *Account (pointer receiver) base type = Account
func (u User) — valuefunc (u *User) — pointer
ได้อะไรมาcopy ของ structที่อยู่ของ struct จริง
แก้ field แล้วมีผลข้างนอก❌ ไม่มี✅ มี
struct ใหญ่ก็อปทั้งก้อนทุกครั้งส่งแค่ 8 bytes
เหมาะกับgetter / อ่านอย่างเดียวทุกอย่างที่ต้องแก้ค่า
type Account struct{ Balance float64 }

func (a Account)  Show() float64      { return a.Balance }
func (a *Account) Deposit(x float64) { a.Balance += x }

acc := Account{Balance: 1000}
acc.Deposit(500)              // Go แปลงให้เป็น (&acc).Deposit(500)
fmt.Println(acc.Show())      // 1500
syntactic sugar ที่ทำให้งง

acc ไม่ใช่ pointer แต่เรียก acc.Deposit() ได้ เพราะ Go ใส่ & ให้อัตโนมัติเมื่อตัวแปร addressable — เวลาเขียนจึงแทบไม่รู้สึกต่าง แต่ผลลัพธ์ต่างกันสิ้นเชิง ต้องดูที่ประกาศ method เสมอ ไม่ใช่ดูที่จุดเรียก

เกณฑ์ตัดสินจาก Go Code Review Comments

นี่คือเกณฑ์ที่ reviewer จริงใช้ตัดสิน — ย่อจาก Go Code Review Comments · Receiver Type:

  • ถ้า method ต้องแก้ค่า receiver → ต้องเป็น pointer (บังคับ)
  • ถ้า receiver เป็น struct ใหญ่ หรือ array ใหญ่ → pointer มีประสิทธิภาพกว่า ("How large is large? Assume it's equivalent to passing all its elements as arguments")
  • ถ้า receiver มี sync.Mutex อยู่ข้างใน → ต้องเป็น pointer ไม่งั้น copy แล้ว lock ไม่ทำงาน
  • ถ้า receiver เป็น map, func, chan → อย่าใช้ pointer; ถ้าเป็น slice และ method ไม่ได้ reslice/realloc → ก็อย่าใช้
  • ถ้าเป็น struct เล็ก ไม่มี field ที่ต้องแก้ และเป็น value โดยธรรมชาติ (แบบ time.Time) → value receiver เหมาะกว่า
  • "Don't mix receiver types" — type เดียวกันเลือกแบบเดียวทั้งหมด
  • "When in doubt, use a pointer receiver."

5 · ทดสอบความจำ

1. ข้อความไหนถูกต้องเกี่ยวกับการส่งค่าใน Go?

Go ไม่มี pass by reference เลย ส่ง slice = ก็อป slice header (24 bytes) ที่บังเอิญชี้ array เดิม จึงดูเหมือน by reference แต่กลไกคือ by value ทั้งหมด

พิสูจน์ได้: ฟังก์ชันที่รับ []int append ข้างในแล้ว len ของตัวแปรข้างนอกไม่เปลี่ยน เพราะแก้ได้แค่ header ที่ก็อปมา (Rob Pike อธิบายไว้)

2. m := map[string]User{...} แล้ว m["a"].Age = 31 จะเกิดอะไรขึ้น?

Go เลือกที่จะ ห้ามตั้งแต่ compile เพราะถ้าปล่อยให้รันได้แล้ว ค่าไม่เปลี่ยน จะเป็นบั๊กที่หาไม่เจอ — map value เป็น non-addressable

3. struct มี sync.Mutex อยู่ข้างใน ควรใช้ receiver แบบไหน?

copy struct ที่มี mutex = ได้ mutex คนละตัว → lock ไม่ป้องกันอะไรเลย เป็นบั๊ก concurrency ที่เงียบมาก go vet จะเตือนเรื่องนี้ให้

4. for _, u := range users แล้วแก้ u.Name ไม่มีผล เพราะอะไร?

range ก็อป element ใส่ตัวแปรวนลูปทุกรอบ ใช้ users[i].Name = ... หรือประกาศ slice เป็น []*User ถ้าตั้งใจให้แก้ได้

6 · ลงมือทำ

ภารกิจ: แปลง Inventory ให้แก้ค่าได้จริง

  1. ใน Playground สร้าง type Product struct{ Name string; Qty int } และ inv := map[string]Product{...}
  2. ลองเขียน inv["a"].Qty = 5 — อ่าน error ที่ compiler พ่นออกมาให้ครบ คุ้นหน้ามันไว้
  3. ซ่อมด้วยวิธี "อ่าน–แก้–ยัดกลับ"
  4. ซ่อมอีกรอบด้วย map[string]*Product เทียบว่าโค้ดสั้นลงแค่ไหน
  5. เขียน method func (inv Inventory) Add(p Product) แบบ value receiver ก่อน แล้วลองเรียก — สังเกตว่าทำไมมันถึงดูเหมือนได้ผล (คำใบ้: map ข้างในเป็น reference)
  6. ท้าทาย: เพิ่ม field count int ใน Inventory แล้วให้ Add เพิ่ม count ด้วย — ทีนี้ value receiver จะพังให้เห็น อธิบายให้ได้ว่าทำไม

เวลาเห็นโค้ดที่ "แก้แล้วไม่เปลี่ยน" คุณจะไล่ได้ใน 3 คำถาม — ตัวนี้เป็น copy รึเปล่า? มัน addressable ไหม? receiver เป็น value หรือ pointer?
