บทเรียน 05 · Day 2 · Function Design

error pattern และกับดัก := ที่ทำให้ค่าหาย

~14 นาที · ต้องมี: บทเรียน 04

Go ไม่มี try/catch — มันใช้ "คืน error ออกมาเป็นค่าธรรมดา" แทน ซึ่งทำให้โค้ดตรงไปตรงมาแต่ก็เปิดช่องให้บั๊กชนิดหนึ่งที่compiler ไม่เตือน เทสต์ผ่าน แต่ค่าที่คุณคิดว่าเซ็ตแล้วกลับหายไปเฉย ๆ

1 · Go คืน error เป็นค่า ไม่ใช่ throw

func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("cannot divide by zero")
    }
    return a / b, nil
}

// เรียกใช้ — สำนวนมาตรฐานที่จะเจอทุกวัน
result, err := divide(10, 2)
if err != nil {
    fmt.Println("Error:", err)
    return
}
fmt.Println("Result:", result)
กฎ 3 ข้อของ error ใน Go
  1. error เป็น return value ตัวสุดท้ายเสมอ
  2. สำเร็จ = คืน nil เป็น error
  3. เช็ค err != nil ทันทีที่รับค่ามา — ไม่มีข้อยกเว้น

ถ้าฟังก์ชันไม่มีผลลัพธ์อื่นนอกจากสำเร็จ/ไม่สำเร็จ ก็คืนแค่ error ตัวเดียว แล้วรวมกับ short statement ได้เลย: 

func saveUser(u User) error { ... }

if err := saveUser(user); err != nil {
    fmt.Println("save failed:", err)
    return
}

แบบนี้ err มีชีวิตแค่ในบล็อก if — ไม่ไปรกด้านนอก และกันเผลอเอา err เก่ามาใช้ซ้ำ

2 · Named return & naked return

// ตั้งชื่อ return value ได้
func divide(a, b float64) (result float64, err error) {
    if b == 0 {
        err = errors.New("cannot divide by zero")
        return          // ← naked return: คืน result, err ที่มีอยู่ตอนนั้น
    }
    result = a / b
    return
}

divide(1, 0) คืนค่าอะไรออกมา?

0, "cannot divide by zero"

result ไม่เคยถูกเซ็ต จึงเป็น zero value = 0 — นี่คือจุดแข็งของ named return: ไม่ต้องเขียน return 0, err ให้ครบทุกจุด

ใช้ naked return เท่าที่ฟังก์ชันสั้น

ถ้าฟังก์ชันยาว 40 บรรทัดแล้วเจอ return เปล่า ๆ คนอ่านต้องเลื่อนขึ้นไปดู signature ว่าคืนอะไรบ้าง — Effective Go บอกให้ใช้กับฟังก์ชันสั้นเท่านั้น ฟังก์ชันยาวให้เขียนค่าออกมาให้ครบ

แต่ named return มีพลังพิเศษอีกอย่างที่คุ้มมาก — defer เข้าไปแก้มันได้ (เรื่องนี้อยู่ใน บทเรียน 08) ใช้ห่อ error ทุกจุด return ในครั้งเดียว: 

func loadConfig(path string) (err error) {
    defer func() {
        if err != nil {
            err = fmt.Errorf("loadConfig %s: %w", path, err)
        }
    }()
    // ...มี return err อยู่ 5 จุด ทุกจุดถูกห่อให้อัตโนมัติ
}
// ได้: loadConfig app.yaml: file missing

%w ใน fmt.Errorf คือ "wrap" — เก็บ error เดิมไว้ข้างในให้ errors.Is / errors.As ตรวจได้ทีหลัง (ต่างจาก %v ที่แปลงเป็นข้อความอย่างเดียว)

3 · 💀 กับดักใหญ่: := ไม่ได้แปลว่า "สร้างใหม่" เสมอไป

var sum = 0

if true {
    sum := sum + 20
    fmt.Println("ข้างใน  =", sum)
}

fmt.Println("ข้างนอก =", sum)

พิมพ์อะไรออกมา?

ข้างใน  = 20
ข้างนอก = 0     ← ไม่ใช่ 20!

sum := sum + 20 สร้างตัวแปร sum ตัวใหม่ ที่มีชีวิตแค่ใน block นั้น (ค่าเริ่มต้นคำนวณจาก sum ตัวนอก = 20) พอออกจาก block ตัวใหม่ตาย sum ตัวนอกไม่เคยถูกแตะเลย
อาการนี้เรียกว่า variable shadowing — ตัวในบัง ตัวนอก

แก้ง่ายมาก — เปลี่ยน := เป็น =

if true {
    sum = sum + 20    // = ไม่ใช่ := → แก้ตัวนอกจริง
}
// ข้างนอก = 20 ✓

ทำไมถึงอันตราย: เวอร์ชัน err

อาการเดียวกันนี้เกิดกับ err ได้ และตรงนี้แหละที่ทำให้ production พัง

func process() error {
    var err error

    if needFile {
        file, err := os.Open("demo.txt")   // 💀 := สร้าง err ตัวใหม่!
        if err != nil {
            fmt.Println("Cannot open:", err)
        }
        _ = file
    }

    return err   // ← คืน nil เสมอ! error ที่เกิดจริงหายไปแล้ว
}
ทำไมถึงหลบตาคุณได้

ที่ต้องใช้ := เพราะบรรทัดนั้นมี file เป็นตัวแปรใหม่ด้วย — Go ยอมให้ใช้ := ได้ถ้ามีตัวแปรใหม่อย่างน้อย 1 ตัว ทางซ้าย แต่ถ้าตัวที่เหลืออยู่คนละ scope มันจะสร้างใหม่ทั้งคู่ ไม่ใช่ reuse → compiler ไม่เตือนเลย เพราะทุกตัวถูกใช้งานครบ

ทางแก้ 2 แบบ:

// 1) ประกาศ file แยกก่อน แล้วใช้ = ล้วน
var file *os.File
file, err = os.Open("demo.txt")

// 2) จัดการ error ให้จบในที่เดียวกับที่มันเกิด (แนะนำ — ตรงกับ guard clause)
file, err := os.Open("demo.txt")
if err != nil {
    return err       // ส่งออกไปเลย ไม่ต้องเก็บไว้ใช้ทีหลัง
}
ตรวจจับอัตโนมัติ

ไม่ต้องพึ่งสายตาอย่างเดียว — เครื่องมือ errcheck และ shadow analyzer จับได้: 

go vet -vettool=$(which shadow) ./...

4 · ทดสอบความจำ

1. ฟังก์ชัน Go ที่อาจล้มเหลว ควรออกแบบ signature ยังไง?

สำนวนมาตรฐานคือ (result T, err error) — panic สงวนไว้สำหรับ "โปรแกรมพังจนไปต่อไม่ได้" เท่านั้น (Don't Panic ใน Go Code Review Comments)

ส่วน bool ใช้กับ comma-ok ของ map/type assertion ซึ่งไม่ได้บอก "ทำไมถึงล้มเหลว"

2. var sum = 0 แล้วใน if เขียน sum := sum + 20 — ข้างนอกได้เท่าไหร่?

:= ใน block ใหม่ = สร้างตัวแปรใหม่ที่บังตัวนอก ตัวนอกไม่เคยถูกแตะ ถ้าอยากแก้ตัวนอกต้องใช้ =

3. file, err := os.Open(f) ในที่ที่มี err อยู่แล้วข้างนอก — เกิดอะไรขึ้น?

ถ้าอยู่ คนละ scope จะสร้างใหม่ทั้งคู่ → err ข้างนอกยังเป็น nil อยู่ ทำให้ return err ตอนท้ายคืน nil ทั้งที่เกิด error จริง

(ถ้าอยู่ scope เดียวกัน Go จะ reuse err ตัวเดิมให้ ขอแค่มีตัวแปรใหม่อย่างน้อย 1 ตัวทางซ้าย — สองกรณีนี้ต่างกันตรงนี้)

4. func f() (result int, err error) เขียน return เปล่า ๆ ได้อะไร?

naked return — คืนค่าปัจจุบันของ named return value ถ้ายังไม่เคยเซ็ตก็ได้ zero value (0 และ nil)

5 · ลงมือทำ

ภารกิจ: calculatePrice (workshop จากสไลด์ Day 2)

เขียน func calculatePrice(price, discountPercent float64) (float64, error)

  • ถ้า price < 0 → คืน error "price cannot be negative"
  • ถ้า discountPercent < 0 หรือ > 100 → คืน error "discount must be between 0 and 100"
  • ถ้าถูกต้อง → finalPrice = price − (price × discountPercent ÷ 100)
  1. เขียนด้วย guard clause จากบทที่แล้ว (ไม่มี else เลย)
  2. ทดสอบ 3 เคส: (1000, 10) → 900.00 · (-500, 10) → error · (1000, 120) → error
  3. ฝั่งผู้เรียก ต้องเช็ค err != nil ก่อนใช้ค่า และพิมพ์ด้วย fmt.Printf("Final price: %.2f\n", v)
  4. เขียนใหม่อีกรอบด้วย named return + naked return เทียบดูว่าชอบแบบไหน
  5. ท้าทาย 1: ใช้ defer + named return ห่อ error ทุกจุดให้ขึ้นต้นด้วย "calculatePrice: "
  6. ท้าทาย 2 (สร้างบั๊กเอง): จงใจเขียนโค้ดที่มี shadowing ของ err ให้ฟังก์ชันคืน nil ทั้งที่ควรเป็น error — แล้วรัน go vet ./... ดูว่ามันจับได้ไหม
    สปอยล์: go vet เปล่า ๆ จับไม่ได้ — ผมรันทดสอบแล้ว เงียบสนิท ต้องลง shadow analyzer แยกต่างหาก บทเรียนของข้อนี้คือ เครื่องมือ default ไม่ได้กันให้ทุกอย่าง สายตาคุณยังต้องทำงาน 
    go install golang.org/x/tools/go/analysis/passes/shadow/cmd/shadow@latest
go vet -vettool=$(which shadow) ./...
ชัยชนะของบทนี้

ต่อไปเวลาเห็น := ข้างใน if/for ที่มี err อยู่ทางซ้าย คุณจะหยุดคิดหนึ่งวินาทีว่า "นี่กำลังสร้างตัวใหม่หรือใช้ตัวเดิม" — วินาทีนั้นแหละที่กันบั๊กระดับ production
